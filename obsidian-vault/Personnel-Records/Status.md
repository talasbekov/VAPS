# Personnel-Records — Status

_Обновляется по ходу работы. См. также [[Changelog]], [[Decisions]], [[Known-Issues]]._

Стенд поднимается связкой Django `:8100` (`local_postgres`, БД `vaps-db-5434`) + Next-хост `PersonalRecordFront :3106`, оба через `.claude/launch.json` (`personnel-django`, `personalrecord-next-local`) — preview-инструментами, тогда доступны консоль браузера и сеть. Две ямы стенда, каждая маскирует другую: (1) привязку user↔employee не делает ни один сид — все сотрудники стенда создаются с `user=None`, поэтому любая ручка, определяющая подразделение через `User → Employee → StaffUnit → Division` (например `statuses/absence_statistics`), отвечает 400 «Пользователь не привязан к сотруднику», и дашборд выглядит сломанным; чинится привязкой учётки к сотруднику, у которого есть `staff_unit.division`. (2) легаси-восьмёрка красных тестов из импорт-коммита донора `7577182f` — pre-existing, подтверждено A/B, не принимать за свой регресс; двойка из `statuses/` была невидима, пока приложению не добавили `__init__.py` (см. [[Decisions#Namespace-пакет ломает сборку pytest]]). CORS dev-портов уже починен шаблоном в `sqlite.py`. На старом стеке (локально, без контейнеров) бэк поднимается `DJANGO_SETTINGS_MODULE=organization_management.config.settings.sqlite` (sqlite, InMemory channels, без Redis) + `runserver 127.0.0.1:8100`; у app `common` (UserRole/Role/Permission) нет миграций в репо; сиды `create_test_data`/`setup_demo_roles` сломаны (устарели против моделей) — сеять руками через shell (superuser + Division + Employee(+user link) + StaffUnit(+employee)). Фронт — `npm run dev -- -p 3000`, клиентский ApiClient бьёт в бэк напрямую (fallback `localhost:8100` зашит), `NEXT_PUBLIC_API_URL` в `.env.local` не задавать; логин `admin/admin123` через NextAuth → `/api/token/`.

Переезд `/api/core/*` из донора `Backend/VAPS` в целевой Personnel-Records **завершён**: всё, что есть в доноре, есть в целевом бэке (детали и ловушки — [[Decisions#Переезд core из Backend/VAPS в Personnel-Records — где остановились]]). Дальше остаются только 37 путей `/api/ops/*`, которых нет НИ В ОДНОМ бэке — это новая разработка, а не переезд. Реестр `lib/api-gaps.ts` местами устарел: `/api/ops/objects/`, `/api/core/staffing-slots/`, `/api/documents/attachments/` уже живые, хотя баннеры фронта могут утверждать обратное; `/api/operations/expense-reports/` — честный 404.

Тестовая БД Personnel-Records разведена по чекауту через имя `test_personnel_records_<sha1(BASE_DIR)[:8]>` и ручку `PR_TEST_DB_NAME` (детали и история флейков — [[Decisions#Общее имя тестовой БД сталкивает чекауты]], [[Decisions#Тестовая БД разведена по чекауту, не по сессии]]); гейт бэкенда: `PR_TEST_DB_NAME=<уникальное> ./.venv/bin/python -m pytest -q` из Personnel-Records, БЕЗ форса `DJANGO_SETTINGS_MODULE=local_postgres` (краснит тесты изоляции тестовой БД). На срезе 159 переезда core было 2410 passed.

Инвариант «у сотрудника ровно один активный статус» и «у каждого работающего есть действующий статус» держатся сервисным слоем `apps/statuses` (см. [[Decisions#Один активный статус на сотрудника]], [[Decisions#Статус по умолчанию каждому работающему сотруднику]]); на 18.08.2026 все 14 сотрудников стенда были с действующим статусом без дублей, но открытая часть инварианта (Celery-задачи `complete_expired_statuses`/`apply_planned_statuses` не выполняются на локальном стенде) регулярно рвёт это состояние на смоук-обходах — см. [[Known-Issues#Celery-задачи статусов не доезжают на стенде]].

Во фронте PersonalRecordFront статус «На дежурстве» связан с нарядом и дежурными силами объекта через клиентское хранилище (`entities/duty-assignment`, localStorage) — бэкенд полей наряда не несёт (детали — [[Decisions#Связка «На дежурстве» → наряд → дежурные силы объекта]]). Модуль «План дежурств» удалён 13.08.2026; «Боевые группы», «Календарь смен», аналитика и отчёты службы — живы и зависят от тех же данных.
