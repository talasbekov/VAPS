# Архитектура бэкенда (Personnel-Records)

Django-проект `organization_management` в `Backend/PersonnelStatus/Personnel-Records`. DRF + drf-spectacular (схема `/api/schema/`, Swagger `/docs`), JWT (`/api/token/`), Channels (WS), Celery (регламентные задачи; на локальном стенде брокер недоступен — см. [[Known-Issues#Celery-задачи статусов не доезжают на стенде]]). БД — PostgreSQL (контейнер `vaps-db-5434`). Парный фронт — [[../Frontend/Архитектура|PersonalRecordFront]] (:3106).

## Ключевые инварианты (держатся сервисным слоем и БД)

- **Один активный статус на сотрудника** — `create_status` закрывает предыдущий (lte); `EmployeeStatus.save()` зовёт `full_clean()`.
- **Статус по умолчанию каждому работающему** — сигнал on_commit + команда `ensure_employee_statuses` (порядок: применить запланированные → закрыть истёкшие).
- **Append-only аудит** — мутации статусов/сдач/увольнений журналируются; coverage-тест.
- **DB-уровень для инвариантов** — CheckConstraint для choice-полей без дефолта и числовых floor; conditional-CHECK с `isnull=False` (NULL-пробел); EXCLUDE/GiST на пересечение статусов.
- **Сдача дня** — снапшот-срез; ретро-правки только амендментом (новая версия, гонка = 409); блокировка «на завтра» с override.
- **Протокол 409/override** — `OVERRIDABLE_CODES`, `DomainError` + единый exception handler, коды в `error_codes.py` (сверять с raise-сайтами, не с `docs/registries/error-codes.yaml`).
- **Архитектурные гварды** — operations не импортирует core.models; Django Admin — только справочники; ARCH-SEC-030 сканирует и докстринги.
