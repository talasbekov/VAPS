# VAPS - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for VAPS, decomposing the requirements from the PRD, UX Design if it exists, and Architecture requirements into implementable stories.

## Requirements Inventory

### Functional Requirements

**Оргструктура, штат, карточка (реализовано в core — миграция/доработки):**
- FR-1: Администратор управляет деревом Подразделений (создание, тип, родитель, ответственный, активность); пропуск уровней допустим
- FR-2: Штатные единицы: ставка = Подразделение + Должность; занята или Вакансия; вакансии = все ставки − занятые
- FR-3: Карточка Сотрудника: кадровый блок + оперативный блок (антропометрия, допуски, оружие, гражданская форма, знание объектов, Налёт часов — данные для проверки FR-25); история переводов неудаляема; блоки по правам
- FR-4: Увольнение → архив карточки, ставка → Вакансия, всё сохраняется для аудита
- FR-5: Сортировка: по уровню должности → фамилия; при-/откомандированные — отдельными блоками внизу

**Статусный движок (ядро):**
- FR-6: Базовый перечень типов Статусов (12 типов), расширяемый справочником; + статус «уточняется» (PENDING_CLARIFICATION, решение архитектуры)
- FR-7: Статус-интервал (период, комментарий, документ-основание); жизненный цикл PLANNED→ACTIVE→COMPLETED/CANCELLED; авто-переходы — derived-first + материализация эффектов (ARCH-DATA-022)
- FR-8: Продление, досрочное завершение, отмена (только PLANNED); каждая операция сохраняет было/стало/инициатора/время
- FR-9: Авто-возврат после спецстатуса: к следующему PLANNED, иначе «В строю»
- FR-10: Валидации: запрет пересечения несовместимых, границы дат приёма/увольнения, max длительность по типу; пересечение с PLANNED — предупреждение
- FR-11: Гибрид конфликтов: 4 hard-типа (отпуск/больничный/командировка/рапорт) → 422; остальные → 409 + override с фиксацией
- FR-12: Массовое обновление статусов управления одной формой/одним сохранением; неуказанные подтверждаются «В строю»
- FR-13: Каскадный Индикатор (трёхцветный светофор: сдано-совпадает / сдано-разошлось / не сдано — уточнение архитектуры); Необходимые управления + контрольный час настраиваются; уведомления об отставании
- FR-14: Откомандирование: парные Статусы; откомандированный по списку штатного, прикомандированный «+N» у принимающего
- FR-15: Возврат: запрос → подтверждение принимающей → завершение пары → авто-возврат
- FR-16: «Откомандирован» лишает права редактирования статусов (только просмотр)

**Сдача дня и Расход (контрактный артефакт):**
- FR-17: Расход за день/период/«на завтра»; .docx (альбомный, kk-заголовок, шрифты 16/12/8, итог жирным) + .xlsx/.pdf/.csv; асинхронно; формулы сходимости (Штат=Список+Вакансии; Список=Σ статусов); прикомандированные «+N»
- FR-18: Расход «на завтра» блокируется до сдачи всех необходимых управлений; за прошедшие даты — всегда
- FR-DS (архитектура, закрывает OQ-4): DailySubmission — явная сдача дня до 17:00; версии + Amendment-flow (ретро-правка сданного дня обязана триггерить amendment); снапшот фактов JSONB; расход из снапшота; файл хранится байт-в-байт; «взамен исх.№»; события CONFIRMED_NO_CHANGES/CHANGED

**Объекты и дежурства:**
- FR-19: Объекты (Facility) и Паспорта: посты, секторы, чек-лист, проблемные места, история
- FR-20: Дежурства на месяц по видам; авто-проекция статусов DUTY/REST_AFTER_DUTY (+BEFORE_DUTY, длительность — OQ); Отдых = soft-конфликт с override

**Цикл охранного мероприятия (SecurityEvent):**
- FR-21: Создание ОМ + Старший объекта + информационный бюллетень
- FR-22: Рекогносцировка: чек-лист, корректировка расчёта постов/секторов, двойной контроль, обновление Паспорта
- FR-23: Потребность (StaffingDemand): расчёт и утверждение по направлениям/Группам
- FR-24: Двухуровневый брокеридж: запросы Группам → брокеры выделяют; физнаряд — ОМД напрямую
- FR-25: Проверка каждого назначения: конфликты FR-11 + двойное назначение, Отдых, перегрузка, несоответствие Посту
- FR-26: Черновая Расстановка (Placement) автоматически → согласование с возвратом → утверждение (один approver, hash-ready заглушка ЭЦП); версионирование; упрощённая печать
- FR-27: Уведомления о назначении + отметка ознакомления
- FR-28: После утверждения изменения только с санкцией + проверка конфликтов + история; допнаряд маркируется, фиксируется источник снятия
- FR-29: Журнал штаба: инструктаж, указания, Инциденты (объект, пост, участники, фото) → история ОМ + Паспорт + карточки
- FR-30: Закрытие ОМ: итоги всех направлений → архив с историей
- FR-42: Эскалация по бездействию вверх по штатной вертикали (управление → зам → рук. департамента); ОРГД не вовлекается
- FR-43: Опрос по итогам ОМ: фактическое время участников на постах → Налёт часов, нагрузка, основа оценивания (MVP-2)

**Замены и нагрузка:**
- FR-31: Каскадная замена: авто внутри управления → ручная в департаменте → эскалация FR-42
- FR-32: Нагрузка = Дежурства + ОМ (план по назначениям, факт по опросу); Налёт часов день/ночь; перегрузка (>3 дней 8+ ч или превышение лимита Поста) на дашборде и при назначении; коэффициенты — справочник

**RBAC и платформа:**
- FR-33: Роли со scope (ORGANIZATION/DEPARTMENT/OWN_DIVISION/CUSTOM); несколько ролей; динамическое создание из прав (реализовано: PermissionService, 8 ролей, 17 прав)
- FR-34: Дежурные полномочия ОМД/ОРГД: срочные, авто-вкл/выкл; ОРГД read-only
- FR-35: Уведомления in-app + WebSocket-доставка (центр, непрочитанные); best-effort + дочитка REST; kill-switch
- FR-36: Append-only Аудит (актор, тип, объект, время, IP, было/стало), enforced на БД; фильтрация; консолидация на AuditLog
- FR-37: Календари: Сотрудник × месяц; Подразделение × дни (пагинировано, НЕ 5000 строк)
- FR-38: Дашборды MVP: готовность ОМ, расход, нагрузка/перегрузка, отстающие управления
- FR-39: Справочники (должности, звания, типы статусов с is_hard_block/цвет/приоритет, причины, виды дежурств, Группы, коэффициенты) + настройки (Необходимые управления, контрольный час); импорт .csv
- FR-40: Экспорт сотрудников/историй/аудита .csv/.xlsx с маскированием; отчёты «штатное расписание», «сводка по статусам»
- FR-41: Регламентные задачи: watermark catch-up активации/завершения (ARCH-DATA-022), напоминания, идемпотентность + advisory lock

### NonFunctional Requirements

- NFR-1: Закрытый контур: один LAN-сервер, Docker Compose, без интернета; релизы носителем (air-gap комплект: бандл+manifest+sha256+install/smoke+откат N-1+CHECKLIST); kill-switch-флаги; offline-зеркала зависимостей; вендоринг ассетов и шрифтов (kk)
- NFR-2: Безопасность: проверка каждого запроса (токен/роль/scope/ограничивающий статус) через PermissionService; X-User-Id → JWT без изменения PermissionService; маскирование чувствительных полей (экран/экспорт/печать)
- NFR-3: Аудит: append-only, enforced БД (REVOKE/триггер), хранится постоянно
- NFR-4: Производительность: 5000 сотрудников, 200–300 онлайн, пик 16:00–17:00 — contention, не throughput; bulk-селекторы (запрет COUNT-в-цикле); генерация документов асинхронно (Celery)
- NFR-5: Надёжность: идемпотентные beat-задачи + catch-up от watermark; Clock-сервис; business_date — параметр; tzdata-канарейка (UTC+5); ежедневный бэкап БД + файлового volume + restore-репетиция
- NFR-6: Клиенты: 4 ГБ RAM без GPU, Firefox ~100; build.target firefox100; бюджет бандла ≤300КБ gzip; виртуализация; перф-инварианты (1 коммит/keystroke, ≤N DOM-узлов); проверка на эталонной машине в DoD
- NFR-7: Локализация: интерфейс русский, заголовок Расхода казахский
- NFR-8: Качество = выживание (урок донора): MTTD/MTTR мелких багов; property-based ядра расчёта; golden master расхода (числа+XML, не байты); quality gate < 5 мин (охраняется ассертом); RTL keyboard-path в DoD формо-стори
- NFR-9: Данные/доверие: расход генерируется ТОЛЬКО системой; parallel-run с донором (frozen-suite + классификатор диффов + exit: 10 рабочих дней без unclassified, дедлайн зафиксирован до старта); миграция списка — условие выживания №1
- NFR-10: Время: календарные сутки, полночь Asia/Qyzylorda; интервалы [start, end); UTC в БД, конверсия на границе

## Epic List

**Пилот (первый релиз, слитые этапы 0+1): E1–E13. Этап 2: E14–E18. Этап 3: E19–E20.**
**Зависимости:** E1 → E2 → E3 → E4 → E5 → E6 → E7 → {E8→E9→E10, E11} → **13.1–13.3 → E12 (пилот) → 13.4–13.6**; parallel-run — фоновый РЕЖИМ с конца E6 (не эпик). Бумажные контракты 9.1/10.1 отправляются по вертикали сразу после E1. E14…E18 последовательно; E19/E20 после.
**Анти-каскад (повтор смерти донора):** пилот НЕ стартует без работающего канала исправлений — стори 13.1–13.3 пререквизит 12.8.

### Epic 1: Walking Skeleton — расход к 17:00 из реальных данных донора
Тончайший срез «данные донора → derived-расчёт → расход» проходит все слои и проверяет модель времени данными; контур и целевое железо прощупаны спайками. Таймбокс обязателен (R3). Состав: scaffold+Postgres-harness+gate; кастомный User model (AUTH_USER_MODEL — сейчас, потом катастрофа); базовый AuditedModel; Clock/watermark; минимальная модель статуса + ExclusionConstraint; минимальный импорт донора; расчёт расхода + read-only вывод; СПАЙКИ: контур-проба (hello-world носителем в реальный контур), перф-грид на целевой 4ГБ-машине, выгрузка данных донора. Инвентаризация (Glossary/реестры/Decision Register/контракты в спеку) — сопутствующий документ-артефакт, не стори.
**DoD-гейт:** расход за 5–7 реальных дней совпал с донором или расхождения объяснены; сборка запущена в контуре; gate < 5 мин работает; перф-числа целевой машины зафиксированы как бюджет.
**FRs covered:** FR-7/FR-17/FR-DS (минимальные срезы), AR-1, AR-3

### Epic 2: Кадровое ядро, которое попадает в расход
Сотрудники, оргструктура, ставки и справочники в объёме, влияющем на расход (фильтр: «если это поле неверно — расход неверен?»); RBAC перенесён во вложенный app по рецепту SeparateDatabaseAndState. Остальные поля карточки — этап 2.
**FRs covered:** FR-1…FR-5 (по фильтру), FR-33, FR-34, FR-39 (базовые справочники), AR-4

### Epic 3: Статусный движок — один статус на дату

### Правила декомпозиции стори (поправки к файловому лимиту — для шага создания стори)

1. Boilerplate новой Django app (apps.py, __init__, migrations/__init__, 0001) не считается в лимит «≤5 файлов».
2. Модель + её схемная миграция = всегда ОДНА стори; data migrations и SeparateDatabaseAndState — отдельные стори.
3. Стори может трогать ровно две app, если это cross-app FK/зависимость миграций. Не больше двух.
4. Тестовые файлы не входят в лимит «≤5 файлов».
5. DoD каждого эпика содержит «доказательство по риску»: измеренное число / diff-отчёт / исполненный рунбук, не «код написан».
