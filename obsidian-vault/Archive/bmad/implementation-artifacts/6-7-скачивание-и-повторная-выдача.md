# Story 6.7: Скачивание и повторная выдача

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **аудитор**,
I want **чтобы каждое скачивание чувствительного документа фиксировалось в журнале аудита, а повторная выдача уже выпущенного расхода отдавала те же байты с рантайм-сверкой sha256**,
so that **«покажи расход за 3 июня, который ушёл наверх» отвечается за секунды и каждое скачивание доказуемо в аудите (тот же файл — не «свежесобранный», байт-в-байт)**.

## Acceptance Criteria

1. **Аудит скачивания (`DOCUMENT_DOWNLOADED`).** Given легальный `GET …/attachments/{id}/download/` существующего вложения ролью с правом `document.view`, When выдача состоялась, Then записана РОВНО ОДНА строка `AuditLog`: `action="DOCUMENT_DOWNLOADED"`, `entity_type="document"` (по реестру), `entity_id = attachment.id` (UUID), `actor_user_id = request.actor_id` (ARCH-SEC-030), `new_value` несёт лёгкий payload `{original_name, content_type, size, sha256}` — и в X-Accel-режиме (`VAPS_XACCEL_ENABLED=1`), и в FileResponse-fallback (`=0`). Given отказ ДО выдачи (403 без права `document.view`; 404 на неизвестный или мусорный `id`), Then НИ ОДНОЙ строки `DOCUMENT_DOWNLOADED` (аудируем только состоявшуюся выдачу).
2. **Рантайм-сверка sha256 (байт-в-байт).** Given запрос download, When сервис готовит выдачу, Then он читает байты из `storage_path(attachment)` чанками (64 KiB), считает `sha256` и сверяет с `attachment.sha256` ДО отдачи; при совпадении выдача продолжается (X-Accel-заголовок ИЛИ `FileResponse`). Given повторный запрос того же документа, Then те же байты (sha совпал повторно): два последовательных download в fallback-режиме дают побайтово идентичное тело, оба проходят рантайм-сверку; в X-Accel-режиме оба дают тот же `X-Accel-Redirect` на тот же uuid и оба проходят сверку до эмиссии заголовка.
3. **Провал целостности → отказ, без утечки.** Given строка `Attachment` существует, но байты на диске отсутствуют ИЛИ их фактический `sha256` ≠ `attachment.sha256` (порча/подмена приватного стореджа), Then `DomainError` **500 `DOCUMENT_INTEGRITY_FAILED`** (новый код, реестр), тело без деталей наружу (§Format Patterns «500 без деталей»), выдача НЕ происходит (ни `X-Accel-Redirect`, ни байтов в теле), и `DOCUMENT_DOWNLOADED` НЕ записан (несостоявшуюся выдачу не аудируем; specifics `attachment_id`/expected-vs-actual — только в server-log). Отсутствие файла (`FileNotFoundError`) даёт ТОТ ЖЕ 500 (строка есть, байтов нет = серверная порча), а НЕ 404 (404 — про неизвестный `id`, зона `get_attachment`).
4. **Гейт и границы.** `make gate` зелёный (база — состояние после 6.6, HEAD `984c528`; точную дельту тестов дев фиксирует в Dev Agent Record); `makemigrations --check` чист — 6.7 НЕ меняет модели (`idx_attachment_sha256` заложен 6.1, миграции нет); `ruff check` чист, `ruff format` ТОЧЕЧНО по изменённым файлам (урок 6.1). `test_audit_coverage` зелёный БЕЗ правок матриц: facet A строки не требует (`download` — GET, не write-verb), facet B видит новый литерал `DOCUMENT_DOWNLOADED` (уже в реестре с 6.1). Негативный контракт 6.1 `test_download_emits_no_audit_rows` ИНВЕРТИРОВАН в позитивный; `test_download_xaccel_headers_and_empty_body`, `test_download_xaccel_location_setting_respected`, `test_download_fallback_streams_bytes_when_xaccel_disabled`, `test_404_*`, `test_403_download_*` остаются зелёными.

## Dev Notes

### ⚠️ Ловушка №1 (ГЛАВНАЯ): «Django не стримит» ≠ «Django не читает» — рантайм-sha требует чтения файла

Инвариант 6.1 (Ловушка №2 той стори): в X-Accel-режиме тело клиенту отдаёт nginx, Django НЕ проксирует байты через WSGI. AC-2 требует «sha256 совпал, рантайм-проверка» — а посчитать sha256 нельзя, не прочитав ВСЕ байты. Разрешение: `verify_integrity` читает файл чанками В ПРОЦЕССЕ Django (для хэша), но тело ответа клиенту по-прежнему пустое, а байты доставляет nginx. То есть «Django не стримит ТЕЛО» сохраняется; «Django читает файл для верификации» — новая, отдельная и ограниченная операция. Стоимость чтения ограничена сверху `VAPS_MAX_UPLOAD_MB` (upload-whitelist 6.1); расход-документы .docx — десятки КБ, чтение незаметно. Это осознанный trade-off (см. Д7 + ОВ1): при появлении крупных вложений верификацию, возможно, придётся сузить/сэмплировать/вынести — сегодня не оптимизируем.

### ⚠️ Ловушка №2: аудит — через `record()` в СЕРВИСЕ, не во view; entity_type="document"

Запись аудита — только `apps.audit.services.record()` (ARCH-SEC-032, AST-boundary `test_audit_write_boundary`); эмиссия живёт в сервис-слое (канон: `ATTACHMENT_UPLOADED` внутри `create_attachment`, а не во view). Поэтому `DOCUMENT_DOWNLOADED` эмитит `prepare_download`, view остаётся тонкой. `AuditLog.entity_id = UUIDField` → `entity_id = attachment.id`. `entity_type="document"` — так объявлен `DOCUMENT_DOWNLOADED` в реестре (audit-events.yaml:56), хотя скачивается `Attachment` (у `ATTACHMENT_UPLOADED` — `"attachment"`). Асимметрия осознана: каждый action следует СВОЕЙ строке реестра; `test_audit_coverage` facet B сверяет только код action, не `entity_type` (Д3, ОВ3). `action` — строковый ЛИТЕРАЛ прямо в вызове (facet B константы/не-литералы не видит).

### ⚠️ Ловушка №3: порядок — gate → resolve → verify → audit → response; аудит только на успех

`RequirePermissionMixin` гейтит `document.view` fail-closed ДО резолва объекта (6.1); `selectors.get_attachment` даёт 404 на мусор/неизвестный. Значит `verify_integrity` и `record()` достижимы ТОЛЬКО на happy-пути. Отказы (403/404/500-integrity) не пишут `DOCUMENT_DOWNLOADED` — это и есть негативная ветка AC-1/AC-3. `verify` строго ДО `record`: аудит фиксирует, что «правильный файл выдан», а не «была попытка».

### ⚠️ Ловушка №4: аудит на GET без ambient-транзакции — autocommit, не оборачивать

`ATOMIC_REQUESTS` в settings НЕ задан (config/settings.py) → GET исполняется в autocommit. `record()` своего `atomic` не открывает — одиночный INSERT `AuditLog` коммитится сам. НЕ городить `transaction.atomic()` вокруг download (лишняя транзакция на чтение). Риска «aborted connection» из deferred-work.md:253 здесь НЕТ: единственная запись, без пути `IntegrityError`-после-catch, без чтений после ошибки. «Обязательный аудит» (реестр: «обязательный аудит»): если `record()` упадёт (сбой БД) — download 500-ит, и это ПРАВИЛЬНО — нет журнала ⇒ нет выдачи.

### ⚠️ Ловушка №5: контракт 6.1 ИНВЕРТИРОВАТЬ, а не удалять

`test_download_emits_no_audit_rows` (http_contract:117-133) — заглушка-негатив на время до 6.7. Его регресс-ценность («ленивый `record()` в теле `FileResponse` всплыл бы») сохраняется, но знак меняется: теперь ждём РОВНО ОДНУ строку на download, тело fallback по-прежнему дочитываем (`b"".join(streaming_content)`), чтобы ловить двойную/ленивую эмиссию. Удаление теста = потеря регресс-охраны обоих режимов. Также снять фразу в docstring модуля (строка 7) и в docstring `views.py`/`services.py` про «6.7 не эмитить».

### ⚠️ Ловушка №6: `DOCUMENT_INTEGRITY_FAILED` = 500 без деталей; пропажа файла ≠ 404

500-класс (§Format Patterns «без деталей наружу») — `detail={}` в `DomainError`, тело-конверт §36 без specifics. Диагностика (`attachment_id`, expected vs actual sha) — в `logger`, не в ответе. Пропажа байтов существующей строки — серверная порча → тот же `DOCUMENT_INTEGRITY_FAILED` (500), НЕ `ENTITY_NOT_FOUND` (404): 404 отвечает `get_attachment` на неизвестный/мусорный `id` ДО verify. Побочная польза: 6.7 заодно закрывает «`FileResponse(open(...))` на пропавший файл → голый 500» (6.1 fallback такого гарда не имел).
