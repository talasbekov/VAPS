## Dev Notes

### Эталоны — всё уже в кодовой базе 4.x
- **Канон эмиссии:** `status_service.py:313-343` — `record()` ПОСЛЕ вложенного savepoint, внутри внешнего `@transaction.atomic`; комментарий там же объясняет, почему откат мутации не оставляет аудит-фантома. Снимок-хелпер `_status_snapshot` (:41-60) — образец Д3/Task 1.
- **Композитное событие:** `dismissal.py:121-133` (4.7) — before/after + агрегаты в new_value + `reason=`.
- **Контракт record():** `apps/audit/services.py:28-61` — kwarg-only; actor обязателен (ValueError); request_id/IP/UA из contextvar; `created_at=Clock.now()`; пишет в амбиентной транзакции.
- **Тест-канон:** `test_status_audit.py` — `_count`/`_in_request` (:103-116), request_id-пропагация (:413-431), «отклонённая мутация → нет строки» (:434-448); `test_dismissal_audit.py` — rollback-кейсы (:208-237); `test_audit_record.py:74-88` — сентинелы вне request.

### ⚠️ ЛОВУШКА №1 (ГЛАВНАЯ): `AuditLog.entity_id` — UUIDField NOT NULL, а PK сдач — int
Канон уже зафиксирован реестром (audit-events.yaml:72-73): entity_id = UUID сущности-владельца (для статусов — employee_id), int-PK строки едет в new_value. Для сдач: `entity_id = division_id` (UUID, ось сущности), `submission_id` + `version` — в payload. НЕ пытаться класть pk в entity_id (упадёт валидацией UUID) и НЕ менять модель AuditLog (append-only, миграции вне скоупа).

### ⚠️ ЛОВУШКА №2: размещение record — строго ПОСЛЕ savepoint, ВНУТРИ внешнего atomic
До savepoint — аудит-фантом при гонке; внутри savepoint — откатится вместе с racy-INSERT, но сам паттерн ломает канон 4.4 и усложняет except-пути; после return — недостижимо. Только «после `with transaction.atomic():`-блока, перед return» (submit/amend). Гонка тогда физически не может оставить строку: IntegrityError поднимается из savepoint и пробрасывается наружу ДО record.

### ⚠️ ЛОВУШКА №3: action — только строковый ЛИТЕРАЛ в вызове
Facet B (`test_emitted_actions_subset_of_registry`) — AST-скан строковых литералов в kwarg `action=`; константа/f-строка НЕВИДИМА скану → код прошёл бы мимо реестр-гарда. Литерал в каждом record().

### ⚠️ ЛОВУШКА №4: snapshot-JSONB (десятки–сотни КБ) НЕ кладётся в old/new_value
Аудит-снимок = ЛЁГКИЙ дикт метаданных версии (Д3). Snapshot сдачи и так иммутабельно лежит в самой строке `ops_daily_submissions` — аудиту достаточно `submission_id` для восстановления.

### ⚠️ ЛОВУШКА №5: у override_tomorrow_block СЕЙЧАС НЕТ внешнего atomic
В отличие от submit/amend (`@transaction.atomic` на функции), 5.6b-сервис держит только внутренний savepoint. Без внешнего atomic `record()` после create окажется в ДРУГОЙ транзакции (autocommit) — потеря атомарности «мутация+аудит». Обернуть функцию `@transaction.atomic` (additive; savepoint+except внутри целы — отравления нет, паттерн 5.6b сохранён). `return` из `with` отрефакторить, чтобы record стоял вне try/except (дубль → ValueError БЕЗ строки).

### ⚠️ ЛОВУШКА №6: хук 5.4b НЕ трогать — аудит приедет сам
`enforce_amendment_on_retro_edit` уже прокидывает `actor` РЕАЛЬНОГО оператора (сквозь `resolve_pending_clarification` → `mark_days_for_amendment`); «SYSTEM»-актор здесь НЕ применяется (это сентинел-конвенция других путей, ср. test_audit_record.py:79). Правка amend_day автоматически покрывает оба вызывающих (HTTP 5.8b + хук). Вне HTTP contextvar пуст → сентинелы — ожидаемо, пином в тест.

### ⚠️ ЛОВУШКА №7: TOMORROW_BLOCK_OVERRIDDEN отсутствует в реестре
Первый же прогон facet B с новым литералом упадёт, если yaml не дописан. Порядок Task 1 → Task 4 обязателен. Имена SUBMITTED/AMENDED уже в реестре — их НЕ дублировать. Прошлое правило стори «реестры НЕ трогаются» здесь НЕ действует: growth_rule реестра прямо требует «каждая мутирующая стори дописывает свой action тем же PR».
