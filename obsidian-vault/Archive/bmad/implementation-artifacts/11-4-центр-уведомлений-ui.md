6. **AC-6 · WS-событие → мутация кэша (ЯДРО СТОРИ; architecture.md#L258 называет это буквально).** Given установленная подписка, When `subscribeMessages` отдаёт `rows: Notification[]`, Then кэш ключа `['notifications']` обновляется через `queryClient.setQueryData` **без отдельного стора и без `useState`-копии серверных данных** (ARCH-FE-010).
   Правила слияния — все обязательны, каждое покрыто своим тестом:
   - **`prev === undefined` → кэш НЕ засеивать.** Вернуть `prev` как есть **и** вызвать `queryClient.invalidateQueries({queryKey: NOTIFICATIONS_QUERY_KEY})`. Причина: дельта — не список; посеяв её, панель показала бы «всю историю = 1 строка». Инвалидейт при этом **чинит и провалившуюся первую загрузку** (AC-7 + Решение №4): истина — REST/БД (architecture.md#L327/#L459), а WS — сигнал «обнови». Зациклиться не может: после успешной дочитки `prev` определён.
   - **Дедуп по `id` обязателен здесь, а не «уже сделан в 11.3».** Кольцо `seenIds` транспорта (`notificationsSocket.ts:180-193`) дедуплицирует **свой** канал; строка, пришедшая в HTTP-ответе `useQuery`, транспорту неизвестна, и его дочитка `?since=` с grace-окном 5 с честно принесёт её ещё раз. Пересечение каналов — норма, а не баг.
   - **Порядок — комментатором сервера, а не «новые сверху».** Сортировка `by (created_at DESC, id ASC)`: селектор отдаёт `order_by("-created_at", "id")` (`selectors.py:43`), то есть при равном `created_at` меньший `id` идёт **первым**. Компаратор `bTime - aTime || a.id - b.id`. Расхождение клиента с сервером даст «прыгающий» список при каждом рефетче.
   - **Иммутабельность.** Возвращать новый объект и новый массив (`{...prev, count: …, results: […]}`); `prev.results` не мутировать (поля `readonly`, react-query полагается на смену ссылки).
   - **`count` увеличивается ровно на число НОВЫХ строк.** Дубликаты не считаются.
   - **Хвост обрезается до `NOTIFICATIONS_LIMIT`** — панель не растёт бесконечно за долгую сессию.
   - **Нет новых строк → вернуть `prev` ТОЙ ЖЕ ССЫЛКОЙ** (не пересобранный эквивалентный объект): иначе каждый дубликат дёргает ререндер всей шапки.
   Логика слияния — **чистая экспортируемая функция** `mergeNotificationPage(prev, rows)` (образец «чистое ядро + 1:1 тест»: `grammar.ts`, `daySubmission.ts`, `prefill.ts`), тестируется напрямую, без React.
   Подписка — в `useEffect` с обязательным `unsubscribe` в cleanup; зависимости — `[queryClient]`. **Подписка ровно одна** (StrictMode монтирует эффект дважды — Ловушка 7 стори 8.5).
   **🔴 `startNotificationsSocket()`/`stopNotificationsSocket()` НЕ вызывать.** Жизненным циклом транспорта владеет `ConnectionIndicator` (`ConnectionIndicator.tsx:32-37`, комментарий `:1-3` называет 11.4 поимённо). Второй владелец = размонтирование любого из двух убивает сокет обоим.

8. **AC-8 · Даты рендерятся БЕЗ таймзонной конверсии — иначе тест флейкует, а оператор видит чужое время.** `business_date` (`YYYY-MM-DD`) → `DD.MM.YYYY` строковой перестановкой. Время создания → часы:минуты, взятые **из самой строки** `created_at`.
   **🔴 `new Date(created_at).toLocaleTimeString()` / `getHours()` ЗАПРЕЩЕНЫ.** Бэкенд рендерит `created_at` в `Asia/Qyzylorda` со смещением `+05:00` (`TIME_ZONE`, `settings.py:147`; байт-в-байт одинаково в REST и в WS-конверте — `test_ws_notify.py:487-513`). `Date` сконвертирует это в таймзону машины: у оператора одно, в CI (UTC) другое → тест, зелёный локально и красный/бессмысленный в гейте. Ровно этот класс уже кусал проект (баг теста `test_vacancies_endpoint`, и Ловушка 10 стори 11.3: «курсор считать через `Date.parse`, НЕ лексикографикой»).
   `Intl.*` не заводить: в `src/` его сегодня нет ни разу (проверено `grep`), а вводить локале-зависимый рендер ради двух полей — цена без выгоды.
