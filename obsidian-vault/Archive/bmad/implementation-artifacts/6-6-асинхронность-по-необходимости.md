## Story

As a **разработчик**,
I want **замерить wall-clock генерации Расхода на реалистичном объёме — синхронный путь «управление» (`issue_expense_document`) И стоимость «свода» (roll-up по поддереву) — и зафиксировать решение числами: `AsyncJob` (202+поллинг) вводится ТОЛЬКО если измеренный порог превышен**,
so that **асинхронность становится решением по измерению (Принцип отсечения, architecture.md:91-99), а не по умолчанию: пока сгенерённый документ отдаётся быстрее интерактивного бюджета, монолит не тащит Celery/Redis/worker/beat ради воображаемой нагрузки; если же генерация реально блокирует запрос — это доказано, а не предположено.**

> **Тип стори — МЕРИТЕЛЬНЫЙ СПАЙК (семья 1.9/1.10/3.13), НЕ атом реализации.** Первичный продукт — ЗНАНИЕ: дурабельный артефакт с числами + вердиктом, а не прод-код. Измерительный аппарат (бенчмарк) одноразовый, живёт в `spikes/6.6-async-timing/`, НЕ в `apps/`. Если вердикт «синхронно» (ожидаемо, см. Ловушку №2) — код `apps/` НЕ меняется вовсе: только `spikes/` + правки реестров-решений. Если вердикт «async нужен» — стори ЭСКАЛИРУЕТ (постройка AsyncJob = отдельная крупная стори, см. AC-6/Ловушку №5), а не крамит инфраструктуру сюда.

## Dev Notes

### ⚠️ Ловушка №1 (ГЛАВНАЯ): «свод» — это ДВА разных объекта; прод-генератор свода НЕ строим

Эпик просит замерить «управление И свод». Но:
- **Фрактальная сводка 5.11** (`summary_service.py::assemble_summary`) — это ENTITY: тот же `DailySubmission` РОДИТЕЛЯ, чей roster — СТРОГО собственного уровня (штаб родителя), НЕ объединение детей (docstring 5.11 «Ловушка №1»); детей она лишь пиннит аддитивным ключом `sources`. ⇒ выпуск документа для сводного подразделения — ВСЁ РАВНО ОДНОСТРОЧНЫЙ, не тяжелее листа. Это ФАКТ (фиксируем в TIMING.md), а не «свод-документ» для замера.
- **Настоящий многострочный roll-up** — это `StrengthReportService.compute(business_date, division_id)` (`strength_report.py:259-298`): `subtree_ids` → бульк `roster_on`/`allocated_slots_on` → `derive_report` по ВСЕМ подразделениям поддерева → одна `DivisionReportRow` на подразделение. ЭТО реальная стоимость свода по содержанию. НО прод-генератора, рендерящего эти N строк в документ, ЕЩЁ НЕТ — `build_expense_document` одностроч by design (Д11, expense_document.py:20-21), многострочный документ = forward-seam 6.10.
- ⇒ 6.6 меряет свод ПО КОМПОНЕНТАМ: `compute`/`derive` по поддереву (реальный код) + ОДНОРАЗОВЫЙ адаптер N-строк → `generate_expense_docx` (генератор row-агностичен, заQAлено 6.4). НЕ строить прод-билдер свода. НЕ трогать `build_expense_document`.

### ⚠️ Ловушка №2: вердикт «синхронно» почти предрешён — это НЕ повод халтурить замер, а повод не строить инфраструктуру

Одностроч docx уже эмпирически ~34ms/25KB (fpdf2 PDF — там же, 6.4). `derive_report` — чистый stdlib O(Σ сотрудников), без ORM в ядре. Даже свод по всей орг-структуре ~5000 сотрудников = O(5000) derive + рендер N (десятки–сотни) строк ⇒ ожидаемо десятки–низкие сотни мс на dev; ×10 медленнее на 4ГБ-контуре — всё равно ≪ порога 2с. Огромный запас позволяет вердикту устоять на `measured-dev`-числах (логика 1.10: инвариант держится на apparatus-числах при большом margin), target-число — подтверждающий `PENDING-target`. НО замер обязан быть НАСТОЯЩИМ (реальный объём, реальные пути), иначе решение фиктивно. «Async по умолчанию» (architecture.md:49/466/624 предполагает async) — как раз то допущение, которое эта стори проверяет числами, а не наследует.

### ⚠️ Ловушка №3: порог — это ДИЗАЙН-РЕШЕНИЕ, заявленное ДО замера (Q1), а не подгонка под числа

Порог отсечения sync→async — интерактивный бюджет одного HTTP-POST, который руководство ждёт со спиннером после «выпустить расход». Дефолт-предложение: **синхронно, пока p95 худшего реалистичного сценария (свод по крупнейшему поддереву, генерация issuance-пути) < 2.0 с**; жёсткий async-триггер при p95 ≥ 2.0 с ИЛИ любой единичной генерации ≥ 5.0 с. Обоснование: ниже ~2с синхронное ожидание с loading-состоянием терпимо, а машинерия 202/поллинг (новая модель+миграция, worker+beat-контейнеры, `/api/jobs`, WS-ускоритель, фронт `refetchInterval` — architecture.md:466/624/337) — существенная сложность, не оправданная до доказанной блокировки. Порог заявляется в TIMING.md ДО чисел и помечается Q1 (Bratan-overridable). **Пик-контенция 16:00–17:00 — НЕ в скоупе этого порога**: нагрузочный сценарий дедлайна отдельно отложен (ARCH-DEFERRED-045, триггер «перед пилотом»); 6.6 меряет латентность ОДНОЙ генерации, не worker-starvation под пиком (выпуск расхода — действие руководства, малая конкуренция, не грид 5000 строк).

### ⚠️ Ловушка №4: детерминизм и чистота БД — Clock, не wall-clock; откат, не мусор

`business_date` — через `clock.override(...)` (ARCH-DATA-022; wall-clock в домене запрещён). Прогон в `transaction.atomic()`+rollback ЛИБО scratch-БД — ~5000 сотрудников не должны остаться в тест/прод-БД. **Footgun (`deferred-work.md:20`):** `clock.override()` использует ContextVar и НЕ проходит в новые треды — если бенчмарк меряет генерацию в ThreadPool/параллельно, дочерний тред прочитает реальное время. Для этого спайка мерь В ОДНОМ треде (последовательные прогоны) — этого достаточно для латентностного вывода и обходит footgun.
