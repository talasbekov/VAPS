### Review Findings

- [x] [Review][Decision] Идемпотентность клампнутых open-end статусов ломается при другом окне — natural key включает `date_end`, а у клампнутых строк `date_end = window_end + 1` зависит от `--until/--days`: повторный прогон с другим окном вставляет не-hard типы вторым перекрывающимся дублем, а hard-типы ложно репортит как `hard_overlap`. Идемпотентность держится только при идентичных параметрах. Варианты: (а) задокументировать ограничение в отчёте/стори, (б) матчить клампнутые строки по `(employee, type, date_start)` без `date_end`, (в) отложить в E7.
- [x] [Review][Decision] Кламп открытого hard-статуса порождает искусственные `hard_overlap` — open-ended hard-статус (например SICK_LEAVE с `end_date=null`), растянутый до `window_end + 1`, выбивает по exclusion constraint более поздние легитимные hard-статусы того же сотрудника; в отчёте для 1.8 артефакт клампа неотличим от реального пересечения донора, статистика пересечений искажается. Варианты: (а) принять и пометить в отчёте, что hard_overlap может содержать артефакты клампа, (б) вставлять клампнутые hard-строки последними и считать их вытеснение отдельной причиной, (в) отложить в E7.

### Решения, принятые при создании стори (дефолты; менять только осознанно)

1. **Вся логика в apps/migration_legacy, корневой migration/ не создаётся:** структура architecture.md делит «commands (apps/migration_legacy) / чистая логика (migration/ в корне репо)», но корневой пакет вне Backend/VAPS не импортируем из Django без правок packaging — это инфраструктура E7. Компромисс: transform.py внутри app, но БЕЗ ORM — переедет в migration/ при E7 без переписывания.
2. **Identity mapping = `Employee.external_id` = str(donor_pk):** поле создано именно для этого (unique, nullable); «mapping заполнен» из AC разыменовывается запросом `Employee.objects.exclude(external_id=None)`. Отдельная mapping-таблица/файл — когда появятся репетиции миграции (E7).
3. **Вход — формат `dumpdata`:** реальный способ выгрузки неизвестен до спайка 1.11 (допущение A1, уверенность средняя), но формат dumpdata выводим из кода донора в репо и воспроизводим синтетической фикстурой. Если 1.11 принесёт другой формат — меняется только парсер-слой команды, transform не трогается.
4. **`other_absence → OTHER_ABSENCE`, которого НЕТ в DB-OPS-003:** альтернатива — выкинуть строки — фальсифицирует расход (человек отсутствует, его строка обязана попасть в свою категорию). Перенос literal-кода честен; до FK 2.2 колонка свободный текст. Код помечается в transform.py комментарием «кандидат в реестр/спеку — зафиксировать в 1.12 (инвентаризация) и учесть в seed 2.2». НЕ маппить в существующие коды (искажение категорий диффа 1.8).
5. **Сотрудник без ИИН/с битым ИИН — skip с причиной, НЕ синтезировать заглушку:** `iin` в VAPS NOT NULL unique; фейковый ИИН = мусор в master data (причина смерти донора №1). Если реальная выгрузка покажет массовость — это блокер-находка для 1.11/7.1 и объяснимая категория расхождений в 1.8, решение о fallback принимается там.
6. **Открытый конец → кламп `window_end + 1`:** date_end NOT NULL; в окне среза derived-расчёт даёт идентичные ответы при любом значении ≥ window_end+1. Счётчик в отчёте обязателен — 1.8 должен знать, сколько интервалов укорочено.
7. **Пересечения hard×hard в данных донора → per-row savepoint, skip, продолжать:** валидация донора была app-level (clean() с дырами, гонки не ловились) — пересечения в проде донора почти гарантированы. Останов команды на первой грязной строке сделал бы импорт неприменимым; молчаливый пропуск без отчёта — враньё. Середина: skip + причина + donor_pk.
8. **`seconded_from→ATTACHED, seconded_to→DETACHED`:** по семантике DB-OPS-003 (ATTACHED counts_in_staff=false = прикомандированный «+N»; DETACHED = откомандированный по списку штатного) и Glossary (Secondment IN/OUT). Парность статусов (FR-14) — E3 (3.10), здесь только типы-литералы.
9. **Синтетические коды справочников `RANK_<pk>`/`POS_<pk>`:** у донора нет кодов, перевод имён в коды = выдумка (Glossary-СТОП); стабильный код от donor_pk идемпотентен и обратим. CSV-импорт справочников с настоящими кодами — 2.7.
10. **`--until` по умолчанию = максимум дат в экспорте, не «сегодня»:** донор затух — его данные исторические; wall clock дал бы пустое окно. Детерминизм от данных + явный параметр для воспроизводимости.

### Подводные камни для dev-агента

- **Конверсия дат — сердце стори, не перепутать направление:** донор включительный, VAPS полуоткрытый → **всегда +1 день к эффективному концу**. Тест с литеральными датами обязателен (отпуск донора 01.06–14.06 → VAPS [2026-06-01, 2026-06-15)). Однодневный статус донора (start==end) → [D, D+1) — валиден.
- **`Employee.save()` перетирает `full_name`** из last/first/middle — передавать раздельные ФИО, full_name не вычислять самому.
- **`update_or_create` не гоняет валидаторы** (нет full_clean) — ИИН-проверку делает transform (regex), НЕ полагаться на iin_validator.
- **unique-коллизии Employee:** `iin` и `personnel_number` уникальны; два донорских сотрудника с одинаковым personnel_number/ИИН (мусор) → IntegrityError. Ловить per-employee (savepoint) → skip `duplicate_iin`/`duplicate_personnel_number`. Не давать одной грязной строке убить импорт.
- **Статусы пропущенных сотрудников** не должны попадать в шаг 4 — фильтровать по наличию pk в employee_map, причина `employee_skipped`.
- **psycopg3 и имена ошибок:** exclusion → `IntegrityError` с `excl_hard_status_overlap` в str(); `start>end` → **`DataError`** (generated column считается ДО CHECK — воспроизведённый факт ревью 1.5). Ловить обе, по отдельным причинам.
- **Savepoint обязателен вокруг каждой вставки статуса:** голый try/except внутри atomic оставит транзакцию в aborted-состоянии — следующая операция упадёт `InFailedSqlTransaction`. Паттерн: `with transaction.atomic(): EmployeeStatus.objects.create(...)` внутри try.
- **`status_type_code` пишется как есть и literal-точно:** опечатка в маппинге тихо выводит строку из-под exclusion-constraint (условие сравнивает литералы — deferred 1.5). Сверить кортеж hard-кодов теста с импортируемым `HARD_STATUS_TYPE_CODES`, не дублировать строки руками.
- **dumpdata-поля FK** в fields лежат как `"rank": 3`, `"employee": 17`, `"division": 5`, `"parent": null` — голые integer-pk, не объекты; даты — строки `"2026-06-01"`, datetime — `"2026-06-01T10:00:00Z"`.
- **MPTT-поля донора** (`lft`, `rght`, `tree_id`, `level`) в dumpdata Division присутствуют — игнорировать; порядок создания родителей: сортировать по донорскому `level` или двухпроходно (сначала все, потом parent) — у VAPS Division parent nullable, двухпроходный апдейт проще.
- **В рабочем дереве незакоммиченный блок 1.1–1.5** — НЕ откатывать, НЕ включать в свой File List (процесс-правило ревью 1.4: блок коммитится вместе).
- **`make gate` — единственная рабочая команда прогона** (Postgres-only сьюта с 1.5); точечно: `docker compose up -d --wait db && VAPS_DB=postgres VAPS_DB_NAME=vaps VAPS_DB_USER=vaps VAPS_DB_PASSWORD=vaps VAPS_DB_HOST=localhost VAPS_DB_PORT=5433 .venv/bin/pytest apps/migration_legacy`.
- **ruff сразу** (`select=["E","F"]`, py312): длинные строки маппинг-таблицы разбить заранее (урок ревью 1.1–1.4).
