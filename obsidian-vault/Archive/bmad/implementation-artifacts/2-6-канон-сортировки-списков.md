## Story

As a руководитель,
I want переиспользуемый **канон сортировки списочного состава** — чистую функцию в `apps/core`, которая упорядочивает любой список сотрудников детерминированно: сначала «свои» по **уровню должности** (`Position.level` ↑) → **фамилии**, затем блок **прикомандированных**, затем блок **откомандированных** — и подключение этого канона к существующему per-person селектору (`CoreEmployeeSelector.active_in_division`),
so that все списки и расход сортируются одинаково (FR-5): один канон — одна реализация, без расхождения порядка между экранами, документом расхода и API, и без переизобретения сортировки в каждом потребителе.

## Acceptance Criteria

1. **(AC-1) Канон порядка: свои → прикомандированные → откомандированные.** **Given** смешанный список сотрудников с прикомандированными и откомандированными, **When** применяю канон (`sort_roster(entries)`), **Then** порядок групп строго: все «свои» (`OWN`) → блок «прикомандированных» (`ATTACHED`) → блок «откомандированных» (`DETACHED`); группы НЕ чередуются (ни один `ATTACHED` не стоит раньше любого `OWN`, ни один `DETACHED` — раньше любого `ATTACHED`). _Полный трёхгрупповой порядок (включая `DETACHED`) верифицируется на уровне ЧИСТОГО канона (unit + property, Task 3) — там вход содержит все три группы; интеграция `active_in_division` (Task 4) по построению задействует только `OWN`+`ATTACHED` (date-keyed `DETACHED` в core недостижим — Решение №5). Это by-design, НЕ пробел покрытия._
2. **(AC-2) Внутри группы: уровень должности → фамилия.** **And** внутри каждой группы порядок = `Position.level` по возрастанию (меньший `level` = старше по должности = выше в списке; семантика донора `order_by('position__level')`), при равном уровне — по **фамилии** (`last_name`, при пустом — `full_name`) без учёта регистра; финальный детерминирующий tie-break — стабильный ключ `id` (порядок не «плавает» между прогонами на равных ключах — как `_resolve_roster`/`allocated_slots_on`).
3. **(AC-3) Неизвестная должность не роняет сортировку.** **And** сотрудник, чей `position_code` не сматчился ни с одной строкой `Position` (реальность донора: `Employee.position_code` — голая строка, НЕ FK; таблица `Position` на пилоте может быть разрежена до прихода 2.7/2.8), получает sentinel-уровень и сортируется ПОСЛЕ всех известных уровней внутри своей группы (graceful), tie-break — фамилия; исключение НЕ кидается, список выходит.
4. **(AC-4) Канон — чистый, переиспользуемый, без ORM и без операций.** **And** канон — функция уровня модуля в `apps/core/sorting.py` без импорта Django/ORM и **без импорта `apps.operations.*`** (граница core↛operations, `test_isolation` зелёный); принимает уже-классифицированные записи (`group` — ВХОД, канон её НЕ вычисляет) и возвращает их в каноническом порядке, перенося исходный объект (`payload`) для вызывающего; чистота позволяет property-тестам гонять канон без БД (как `derive_report`/`_resolve_roster`).
5. **(AC-5) Подключение к существующему списку, нулевая регрессия.** **And** `CoreEmployeeSelector.active_in_division(division_id)` переведён с `order_by("full_name")` на канон (свои по `level`→фамилии; прикомандированные — блоком внизу через `Employee.is_attached_force`; date-keyed `DETACHED` в core недостижим — forward-hook); возвращаемый тип не меняется (`list[Employee]`); `make gate` зелёный (Postgres :5433), существующие тесты (`test_employee_selectors.py`, `roster_on`/strength-report) не сломаны.

## Dev Notes

### Что это за стори (суть и риск)
Чистая стори-утилита: **один канон сортировки** (`apps/core/sorting.py`) — `Position.level ↑ → фамилия`, прикомандированные/откомандированные блоками внизу — и подключение к единственному реальному per-person списку (`active_in_division`). Риск НЕ в схеме (всё уже есть: `Position.level`, `Employee.last_name`/`is_attached_force`/`position_code`) и НЕ в объёме, а в **двух границах** (точь-в-точь как 2.5):
1. **core↛operations** (AST `test_isolation.py:132-140`): date-keyed классификация ATTACHED/DETACHED = живой `EmployeeStatus` (типы в `apps.operations.statuses`). Core НЕ имеет права её вычислять. ⇒ канон принимает `group` как ВХОД (чистая функция), а live-status классификация — **forward-hook** в operations.
2. **Нет per-person потребителя расхода**: `strength_report` — это СЧЁТЧИК на подразделение (`attached` = `+N`), а не список людей (см. `derive_report`, `strength_report.py:135-239`). Per-person списки расхода/экранов — E6/E9/E10. ⇒ 2.6 не строит operations-адаптер (анти-gold-plating); подключает канон к `active_in_division` и документирует точку расширения.

### Источник истины: целевая кодовая база — `Backend/VAPS`
Работаем в `Backend/VAPS/`. Донор `Backend/PersonnelStatus/` НЕ трогаем — он лишь **эталон канона** (подтверждает порядок). [Source: project memory `project_vaps_architecture.md`, `project_vaps_ux_spines.md`]

### Эталон донора (подтверждение канона — НЕ копировать код)
Донор сортирует списочный состав так: дерево подразделений (`tree_id, lft`) → **`position__level` ↑** → **`last_name, first_name`** (`Employee.Meta.ordering = ['last_name','first_name']`); прикомандированные/откомандированные выводятся **отдельными именными секциями** внизу расхода (`reports/utils.py:198-226`), а не вперемешку с основным списком. VAPS-канон 2.6 = **внутриподразделенческая** часть (уровень→фамилия + блоки при-/откомандированных); сортировка ПОДРАЗДЕЛЕНИЙ уже есть в `strength_report` (по имени). [Source: донорский Explore 2026-06-22; epics.md:439-445]

### Классификация групп — где живёт что (КЛЮЧЕВАЯ граница)
- **Канон (core, чистый):** `group` — ВХОД. Канон НЕ решает, кто прикомандированный.
- **`active_in_division` (core):** классифицирует по СТАТИЧЕСКОМУ `is_attached_force` → `ATTACHED` иначе `OWN`. `DETACHED` в core **недостижим** (нет date-keyed статуса в core; флага «откомандирован» на Employee нет). Это осознанно: core — без даты и без статусов.
- **Date-keyed ATTACHED/DETACHED (forward-hook, operations):** когда E6/E9/E10 дадут per-person списки расхода, operations-вызывающий резолвит живой статус (`resolve_status` → `ATTACHED`/`DETACHED`, `strength_report.py:74-103`/`STATUS_TYPE_PRIORITIES`), строит `RosterEntry(group=...)` из `apps.core.sorting` и зовёт `sort_roster`. operations МОЖЕТ импортировать `apps.core.sorting` (запрещён лишь `apps.core.models`, `test_isolation.py:23-29`) — поэтому канон держим без импорта моделей. Никакого «тихого пропуска»: задокументировано как hook, как секондмент-пары в 2.5.

- **Ошибки** [architecture.md:431-433]: `DomainError` вводится в 3.1 — на 2.6 НЕ нужен (канон не кидает доменных ошибок; AC-3 — graceful, без исключения). Не вводить try/except.

### Решения, принятые при создании стори (дефолты; менять только осознанно)
1. **Ось «уровень должности» = `Position.level`** (через lookup `position_code`→`Position.code`), **НЕ `Employee.rank_index`** (это ЗВАНИЕ). AC буквально просит «уровень должности». Tempting-ловушка: `rank_index` денормализован на Employee (без join) — но семантически неверен. Если заказчик захочет вторичный ключ по званию — это уточнение AC, не дефолт 2.6.
2. **Меньший `level` = выше в списке** (ascending) — семантика донора (`order_by('position__level')`, supervisor = `min level`) и `Position.level`.
3. **Фамилия = `last_name or full_name`** (last_name nullable; донор-импорт мог не разбить ФИО — `transform.py:196` ставит `last_name` или ""). casefold для регистронезависимости. Не локаль-aware collation (overkill; при необходимости — follow-up).
4. **`UNKNOWN_LEVEL` sentinel = после известных** (AC-3). На пилоте `Position` может быть пуст → ВСЕ получают sentinel → де-факто сортировка по фамилии (graceful fallback, совпадает с «по фамилии»); ось уровня «оживает» по мере наполнения `Position` (2.7 CSV-импорт / 2.8 Admin). Это НЕ баг — задокументировать.
5. **Группа в `active_in_division` = `is_attached_force`** (статический core-сигнал; единственный доступный без даты/статусов). `DETACHED` в core недостижим — forward-hook. (Альтернатива — тянуть live-status классификацию в core — ОТКЛОНЕНА: ломает core↛operations.)
6. **Канон отдаёт `payload` назад** (исходный Employee/строка), сам сортирует лёгкие `RosterEntry` — переиспользуем и core (Employee), и operations (status-строки) без общего типа модели.
7. **Канон в новом модуле `apps/core/sorting.py`** (не в `selectors.py`): «переиспользуемый селектор сортировки» (эпик) → отдельный чистый модуль, который импортируют и core-selectors, и будущий operations. (Альтернатива — функция в `selectors.py` — рабочая, но хуже для импорта из operations и для чистоты property-тестов.)
8. **Анти-gold-plating:** НЕ строить operations-адаптер расхода (нет per-person потребителя до E6/E9/E10), НЕ строить API/пагинацию (E8/E10), НЕ вводить factory_boy, НЕ менять `strength_report` (счётчик, не список). 2.6 = канон + одно подключение.
