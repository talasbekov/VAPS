# Story 5.11: Фрактальная сводка

## Story

As a **руководство**,
I want **сводную сдачу уровня выше как ТУ ЖЕ сущность `DailySubmission` родительского подразделения над сдачами прямых детей (иммутабельные пины `sources`), с derived-свежестью и явной пересборкой «взамен»**,
so that **пересдача внизу протухает сводку ВИДИМО, а не молча (ARCH-DATA-021 «Фрактальность»: одна модель на все эшелоны), и никакой каскад пере-выпуска не срабатывает автоматически**.

> **Контекст:** единственный forward-referenс 5.11 в коде — snapshot.py:24: «Роллап вверх по дереву — отдельная DailySubmission родителя (5.11), здесь только own-level». Сводка = новая строка СУЩЕСТВУЮЩЕЙ модели: `division_id` родителя, снапшот = own-level `{schema_version:1, roster, rows}` билдера 5.3a **+ additive-ключ `sources`** — пины действующих сдач прямых детей `[{division_id, submission_id, version}]`. Модель, миграции, констрейнты НЕ меняются. Три кита дизайна: (1) **roster сводки строго own-level** (штаб родителя), НЕ union детей — иначе `covering()` (JSONB containment по roster) втянет сводку в авто-amendment хука 5.4b при ретро-правке сотрудника ребёнка, убив «пересборка — явным действием»; (2) **свежесть derived, не хранится** — «помечена устаревшей» = чтение `summary_freshness` (пины vs текущие версии детей), ни одна существующая строка не мутируется (property 5.10 стоит на страже байт-иммутабельности); (3) **пересборка = amendment сводки** (v+1, event=AMENDED, свежие own-срез И пины) — «новый номер „взамен"» на уровне сущности это version-chain; документный «взамен исх.№» — E6 (6.2/6.5), forward-seam. Фрактальный каскад получается сам: leaf пересдал → сводка mid протухла; mid пересобрался явно → протухла сводка root; root пересобирается явно. Каждый уровень — явное действие (AC-2 эпика).

## Acceptance Criteria

1. **Сборка сводки.** **Given** родительское подразделение (есть прямые дети в `children_map()`) и у ВСЕХ required-детей есть действующая сдача на `business_date`, **When** `assemble_summary(division_id=..., business_date=..., actor=...)`, **Then** создаётся `DailySubmission` родителя `version=1, is_current=True`: `snapshot = build_division_snapshot(родитель, дата)` (own-level roster/rows, `schema_version` остаётся 1) + ключ `sources` — пины ВСЕХ прямых детей, имеющих current-сдачу (required и non-required), вид `{"division_id": str(uuid), "submission_id": int(pk), "version": int}`, отсортированы по `division_id` (детерминизм — зеркало сортировок билдера); `event` — по диффу против `previous_for` (Д6), `late` — по `_is_late()`, `submitted_at=Clock.now()`. Валидации зеркалят `submit_day` и в его порядке: пустой actor → `VALIDATION_ERROR` 400; несуществующее подразделение → `ENTITY_NOT_FOUND` 404; вне окна `{today, tomorrow}` → `BUSINESS_DATE_OUT_OF_WINDOW` 422; повторная сборка → `DAY_ALREADY_SUBMITTED` 409; подразделение без прямых детей (лист) → `VALIDATION_ERROR` 400 (Д10). Аудит `DAILY_SUMMARY_ASSEMBLED` (Д7).

2. **Полнота детей (required-гейт).** **Given** хотя бы один required-ребёнок без current-сдачи, **When** `assemble_summary` (или `rebuild_summary`), **Then** `DomainError("SUMMARY_CHILDREN_NOT_SUBMITTED", 422)` с `detail={"laggards": [str(id), ...]}` (sorted by str — зеркало `tomorrow_block`), строка НЕ создаётся. Required = прямой ребёнок, в чьём ПОДДЕРЕВЕ own-ростер на дату непуст (bulk `roster_on` по поддеревьям — зеркало NEUTRAL-семантики 5.5b: «нечего сдавать» не блокирует). Ребёнок с пустым поддеревом-ростером БЕЗ сдачи не блокирует; если сдал (пустой день валиден — 5.3b) — пинится. Сводка с `sources=[]` (все дети exempt, никто не сдал) — валидна.

3. **AC-1 эпика — протухание derived.** **Given** сформированная сводка, **When** любой запиненный ребёнок получает новую версию (`amend_day` напрямую ИЛИ через хук 5.4b ретро-правкой), **Then** `summary_freshness(division_id, business_date)` → `STALE` с `superseded=[{division_id, pinned_version, current_version}]`; сама строка сводки (перечитанная `by_id`) байт-в-байт не изменилась — свежесть НИЧЕГО не пишет. Также STALE при `missing` (у запиненного ребёнка не осталось current-версии — §82.1-класс) и `unpinned` (появился новый required-ребёнок вне пинов). Сразу после сборки → `FRESH`, все три оси пусты. Нет действующей сводки на (division, date) ИЛИ current без ключа `sources` → `None`. Read-path бюджет: ≤4 SQL (children_map + roster_on + current_for + current_for_many), пиновано `CaptureQueriesContext` (NFR-4, канон 5.5b).

4. **AC-1 эпика — пересборка «взамен».** **Given** сводка (протухшая ИЛИ свежая — не гейтится по drift) + непустые reason и sanction + actor, **When** `rebuild_summary`, **Then** создаётся `version=prev+1`: `event=AMENDED`, СВЕЖИЙ own-срез + СВЕЖИЕ пины (required-гейт AC-2 применяется), flip-before-insert в одной транзакции (зеркало `amend_day`), `late=False`, reason/sanction сохранены; прежняя версия сохранена (`is_current=False`, snapshot байт-в-байт, пины в ней — старые); `summary_freshness` после пересборки → `FRESH`. Окно НЕ применяется (amendment-flow — прошлые даты легальны). Пустые reason/sanction → `VALIDATION_ERROR` 400 ДО вставки (DB-констрейнт `chk_daily_submission_amended_requires_reason_sanction` — backstop); нет ни одной версии → `NO_SUBMISSION_TO_AMEND` 422; head цепочки без `sources` → `VALIDATION_ERROR` 400 (Д10). Аудит `DAILY_SUMMARY_REBUILT` с before/after (Д7).

5. **AC-2 эпика — фрактальный каскад БЕЗ автоматики.** **Given** три уровня root→mid→leaf, у mid и root сформированы сводки (пины root указывают на сводку mid — фрактальность: пин не различает лист/сводку), **When** leaf пересдаёт v2, **Then** `freshness(mid)=STALE`, а `freshness(root)=FRESH` (его пин mid не менялся — протухание идёт ПО УРОВНЯМ, не транзитивно); **When** mid пересобирается явно (v2), **Then** `freshness(root)=STALE` (superseded=mid), у root число версий НЕ изменилось (никакого авто-rebuild); **When** root пересобирается явно, **Then** `freshness(root)=FRESH`. Ни одна операция стори не создаёт версий у ДРУГИХ подразделений. Каскад пере-выпуска ДОКУМЕНТОВ с номерами («взамен исх.№») — forward-seam E6 (6.2/6.5/6.7): здесь пинится только сущностный уровень.

6. **Взаимодействие с хуком 5.4b.** **Given** сводка родителя сформирована: (а) **When** ретро-правка статуса сотрудника РЕБЁНКА, накрытого сданным днём (`resolve_pending_clarification` — единственная мутация, дёргающая хук), **Then** авто-amendment создаётся у РЕБЁНКА (его v2), у родителя-сводки НОВОЙ версии НЕТ (`covering` не находит — roster сводки own-level), `freshness` → STALE; (б) **When** ретро-правка сотрудника из OWN-ростера родителя, **Then** хук амендит сводку через `amend_day` (v2 AMENDED), и `sources` ПЕРЕНОСЯТСЯ VERBATIM из вытесненной версии (правка amendment_service — Task 1): own roster/rows пересняты свежими, пины байт-равны прежним — консолидация обновляется ТОЛЬКО явной пересборкой.

7. **Гейт и реестры.** `make gate` зелёный (база 1846 + новые тесты); `SUMMARY_CHILDREN_NOT_SUBMITTED` добавлен в `docs/registries/error-codes.yaml`, `DAILY_SUMMARY_ASSEMBLED`/`DAILY_SUMMARY_REBUILT` — в `docs/registries/audit-events.yaml` (closed-world: audit-coverage Facet B AST-сканом найдёт новые `record()`-вызовы); `makemigrations --check` пуст (модель НЕ меняется — additive JSONB-ключ миграции не требует); ruff format строго по файлам стори; RBAC-матрица и `seed_operations` НЕ трогаются (новых роутов/permission-кодов нет — сервис-слой, Д8).

### ⚠️ Ловушка №1 (ГЛАВНАЯ): roster сводки — только own-level
`covering()` ищет сдачи JSONB-containment'ом по `snapshot.roster`. Если сводка внесёт в roster сотрудников детей, хук 5.4b начнёт АВТО-амендить сводку при любой ретро-правке внизу — прямое нарушение «пересборка — явным действием» (AC-1 эпика). Протухание доносится ТОЛЬКО derived-свежестью по пинам.

### ⚠️ Ловушка №2: `amend_day` строит свежий own-срез и ПОТЕРЯЕТ `sources`
Хук 5.4b по own-сотруднику родителя зовёт `amend_day` → новый снапшот БЕЗ `sources` → сводка молча деградирует в обычную сдачу (и `summary_freshness` вернёт None — сводка «исчезла»). Task 1 обязателен: перенос `sources` verbatim из вытесняемой версии. НЕ пере-пиновать свежие версии в этом пути — консолидация обновляется только явной пересборкой.

### ⚠️ Ловушка №3: свежесть — чтение, не запись
Никаких флагов/мутаций строк: property-тест 5.10 (`test_snapshot_immutability_properties`) уже пинит байт-иммутабельность снапшотов v1 после любых мутаций — «пометка» устаревания обязана быть derive-функцией. Любой соблазн `update(...)` на сводке = красный 5.10.

### ⚠️ Ловушка №4: AMENDED требует непустых reason И sanction на уровне БД
`chk_daily_submission_amended_requires_reason_sanction` (модель:132-138). `rebuild_summary` валидирует оба ДО вставки (`_require_text`-паттерн amendment_service:43-53), иначе dev получит IntegrityError вместо DomainError 400.

### ⚠️ Ловушка №5: какой селектор где
