# Story 3.10: Секондменты — инициация

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **оператор штатного управления**,
I want **инициировать откомандирование сотрудника в выбранное принимающее подразделение одной атомарной операцией: создаётся СВЯЗАННАЯ пара статусов — `DETACHED` («Откомандирован», у домашнего/штатного) + `ATTACHED` («Прикомандирован», «+N» у принимающего) — связанных через первоклассную сущность `Secondment`, несущую принимающее подразделение**,
so that **перемещение фиксируется честно и атомарно (обе ноги или ни одной); 3.11 сможет «завершить пару» по этой связи; пара не само-конфликтует в детекторе; а «+N у принимающего» получит точку данных (`Secondment.to_division_id`) для рендера расходом позже (E6/E9)**.

1. **AC-1 (модель `Secondment` — связь пары + принимающее подразделение).** NEW `Secondment` (TimeStampedModel, BigAuto PK как ARCH-002): `employee_id` (flat UUIDField, ARCH-003), `out_status` FK→EmployeeStatus `on_delete=PROTECT` (нога DETACHED), `in_status` FK→EmployeeStatus `on_delete=PROTECT` (нога ATTACHED), `from_division_id` (flat UUID), `to_division_id` (flat UUID — принимающее), `document_basis` (TextField, blank). `db_table=ops_status_secondments` + индекс `(employee_id, -created_at)`. Миграция `0007_secondment` CreateModel — обратима, round-trip forward→reverse→forward.
2. **AC-2 (атомарное создание пары).** Given сотрудник + принимающее подразделение + интервал, When `initiate_secondment(employee_id, *, to_division_id, date_start, date_end, actor, document_basis="")`, Then в ОДНОЙ транзакции созданы: DETACHED-статус (на сотруднике, `source=USER`), ATTACHED-статус (на том же сотруднике, `source=USER`) и `Secondment`-запись, связывающая их (out_status/in_status) + `from_division_id`=текущее подразделение сотрудника + `to_division_id`. Возвращает `Secondment`. Сотрудник лочится (`_lock_employee` → 404 если нет). Обе ноги или НИ ОДНОЙ (savepoint).
3. **AC-3 (валидации + конфликт-детектор ДО записи).** `_require_actor` (пустой → 400). `to_division_id == from_division_id` → 400 `VALIDATION_ERROR` (нельзя откомандировать в своё же подразделение). `to_division_id` не существует → 404 `ENTITY_NOT_FOUND` (проверка через `CoreDivisionTreeSelector`, ARCH-004). Обе ноги прогоняются через `_validate_interval` (границы приёма/увольнения) и `_assert_no_conflict` против СУЩЕСТВУЮЩИХ live-статусов сотрудника ДО записи: пересечение с hard-статусом (напр. VACATION) → 422 `OVERLAPPING_HARD_STATUS`, ничего не создано; пересечение с soft → 409 `STATUS_OVERLAP_WARNING` (без override в 3.10).
4. **AC-4 (COMPATIBLE_PAIRS — пара не само-конфликтует).** Заполнить `COMPATIBLE_PAIRS = frozenset({frozenset(("DETACHED", "ATTACHED"))})` ([conflict_matrix.py:42]) → `classify_pair("DETACHED","ATTACHED")` = `COMPATIBLE` → `detect_conflicts` пропускает (`continue`). Given пара DETACHED+ATTACHED на ОДНОМ сотруднике на ОДИН интервал, Then создание второй ноги НЕ ловит первую как конфликт (нет ложного 409). **Починить exhaustive property-тест** ([test_conflict_matrix.py] — сейчас ассертит `HARD ⟺ either_hard`, сломается на COMPATIBLE среди soft-пар) + добавить тест COMPATIBLE-ветки (раньше мёртвый код, ноль покрытия — deferred-work «COMPATIBLE мёртв до 3.10»).
5. **AC-5 (БД не блокирует пару; source=USER).** DETACHED/ATTACHED — soft (НЕ в `HARD_STATUS_TYPE_CODES`), поэтому `excl_hard_status_overlap` (условный на hard) НЕ блокирует две перекрывающиеся ноги; `gist_status_employee_period` — ИНДЕКС, не exclusion → пара хранится. Обе ноги `source=USER` (операторская инициация). COMPATIBLE_PAIRS — pure-python, миграция НЕ нужна (DETACHED/ATTACHED не в вмороженном GiST-tuple).
6. **AC-6 (закрытый мир + гейт).** Новых кодов ошибок НЕТ (реюз `VALIDATION_ERROR`/`ENTITY_NOT_FOUND`/`OVERLAPPING_HARD_STATUS`/`STATUS_OVERLAP_WARNING`/`INVALID_DATE_RANGE`/`DATE_OUTSIDE_EMPLOYMENT` — все в реестре). Миграция 0007 round-trip. `make gate` зелёный; `makemigrations --check` чист после 0007. Регресс нулевой: strength_report конвергенция держится (на домашнем DETACHED priority 40 < ATTACHED 50 → побеждает DETACHED, «+N» НЕ всплывает дважды — bounded); donor-diff/render не тронуты.
7. **AC-7 (out of scope — bounded, Решение B; без протечек).** НЕ строится: перенос «+N» к ПРИНИМАЮЩЕМУ в `derive_report`/roster (сейчас «+N» считается у домашнего) → роста/расход-стори E6/E9; живые сорт-блоки `RosterGroup` по статусу (сейчас от статич. `is_attached_force`) → E6/E9; возврат/завершение пары (FR-15) → 3.11; FR-16 enforcement DETACHED read-only → 3.11; синхронное закрытие пары при увольнении (хук dismissal.py#L54-56) → 3.11; прод-REST/сериализатор/ConflictDialog → E10; ATTACHED_PLUS/чужое-ведомство (`is_attached_force`) — не трогать.
