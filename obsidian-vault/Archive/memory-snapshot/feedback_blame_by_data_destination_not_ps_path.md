При разборе конфликта за общий ресурс (БД, порт, том, префикс) **не назначай виновным чекаут по пути бинаря в `ps`**. Определяй по тому, куда процесс реально ходит за данными: грепни имя ресурса по настройкам/конфигам всех чекаутов на машине.

**Why:** путь интерпретатора не равен владельцу конфига. 2026-08-04 я записал в столкнувшиеся чекаут `govtech/pr_gov`, увидев его `.venv/bin/python` в `ps`, — на деле это был чужой интерпретатор, запущенный из каталога VAPS-worktree. У govtech `settings.test` вообще SQLite in-memory, боевая БД `organization_db:5432`, и спорную `test_personnel_records` он создать физически не мог. Грепом по настройкам нашлись ровно два чекаута — оба наши. Тот же класс ошибки атрибуции, что в [[feedback_docker_port_foreign_container]], где владельца порта тоже пришлось искать не по очевидному признаку.

**How to apply:**
- Симптом «кто-то держит/удалил мой ресурс» → сначала `grep -r '<имя-ресурса>'` по конфигам всех чекаутов, потом уже `ps`.
- `ps`/`lsof` годятся, чтобы увидеть **что** конфликтует, но не **чей** это процесс по проекту: `cwd` и venv могут принадлежать разным репозиториям.
- Подтверждай атрибуцию отрицанием: способен ли подозреваемый вообще создать этот ресурс (его драйвер, его хост, его имя БД)? Если нет — гипотеза мертва, ищи дальше.
- Полный кейс с симптомами и фиксом: [[feedback_shared_test_db_name_collides_across_checkouts]].
