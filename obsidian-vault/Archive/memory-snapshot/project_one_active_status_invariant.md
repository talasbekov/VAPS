Коммит `458c8cf6` (14.08.2026).

`EmployeeStatus.clean()` запрещает пересекающиеся статусы (state ACTIVE/PLANNED),
а `save()` вызывает `full_clean()`. Значит **у сотрудника ровно один активный
статус**, и любой код, рассчитывающий на сосуществование двух, сломан.

На этом правиле разбились сразу два места:
- `secondments/api/views.py::approve` заводил пару SECONDED_TO + SECONDED_FROM
  на один период → вторая падала, 500, запрос помечен одобренным, статус
  осиротел. Теперь заводится **ОДИН** статус `SECONDED_TO` с
  `related_division` = принимающее подразделение; принимающая сторона
  выводится из него (и в `DataAggregator`, и в `reports/utils.py`);
- `StatusApplicationService.create_status` исключал прикомандирование с обеих
  сторон из авто-закрытия предыдущего статуса. Исключение снято.

Ловушки смены статуса:
- выборка закрываемых — `start_date__lte`, НЕ `lt`. С `lt` статус, заведённый
  сегодня, оставался активным и валил новый пересечением: вторая смена статуса
  за день была невозможна;
- однодневного предшественника нельзя «завершить вчера» (`actual_end_date <
  start_date` модель запрещает) — он **отменяется** (`CANCELLED`);
- `clean()` при проверке пересечений смотрит на `end_date`, а НЕ на
  `actual_end_date`. Досрочно завершённый статус не мешает новому только
  потому, что его `state` становится `COMPLETED` и он выпадает из выборки
  пересечений;
- `terminate_status_early` заводит «В строю» с ДНЯ завершения (коммит
  `1b84d6bc`; раньше со следующего — в день возврата человек оставался без
  активного статуса). Следствие: в день возврата в окно даты попадают ОБЕ
  строки, поэтому `DataAggregator` предпочитает ДЕЙСТВУЮЩИЙ статус
  завершённому, а «прикомандирован» считает по действующему статусу человека,
  а не по строке откомандирования;
- запланированное «В строю» больше НЕ блокирует (коммит `49319a7e`):
  `create_status` его отменяет как перекрытое. Реальные плановые статусы
  (отпуск, командировка) блокируют по-прежнему — это обещание человеку.
  ВАЖЕН ПОРЯДОК: снятие плана идёт ПЕРЕД закрытием активного статуса, иначе
  `full_clean` при пересохранении активного валит его о плановый, и отказ
  выглядит так, будто мешает новый статус.

- активация запланированного (`apply_planned_statuses`) тоже закрывает прежний
  статус — общий `_close_active_statuses` (коммит `b72b3e16`). Раньше не
  закрывала: наутро после планового отпуска было ДВА активных статуса;
- `EmployeeStatus.save()` выводит state из ФАКТИЧЕСКОЙ даты, а не из
  переданной. Поэтому `apply_planned_statuses(будущая_дата)` статус НЕ
  активирует (модель вернёт PLANNED) — а прежний к тому моменту уже закрыт;
  теперь состояние сверяется с базой и шаг откатывается;
- пробы на стенде через `manage.py shell` идут в AUTOCOMMIT: `transaction.savepoint()`
  там не откатывает, данные меняются по-настоящему. Оборачивать в `atomic()`.

- МАССОВОЕ обновление (`staff_unit` → `directorate_management`) тоже должно
  идти через сервис: сериализатор кладёт статус РЯДОМ с действующим и падает
  на пересечении. Валидировать сериализатором на этом пути нельзя — он гоняет
  ту же проверку ДО закрытия предыдущего (коммит `0328b493`);
- ручка отвечает 200 и на ПОЛНЫЙ отказ: смотреть `updated.statuses`/`errors`,
  а не код ответа.

Тестовые ловушки: `EmployeeStatus` требует `created_by`; пару пересекающихся
строк можно завести только `bulk_create`; API прикомандирования на JWT —
`Client.force_login` даёт 401, нужен `APIClient.force_authenticate`; прогон
через `manage.py shell` требует `SERVER_NAME='localhost'` (иначе 400 от
ALLOWED_HOSTS).

`settings.test`, а форс `local_postgres` краснит два теста изоляции тестовой БД.
