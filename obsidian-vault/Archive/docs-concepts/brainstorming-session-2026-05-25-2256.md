# Brainstorming Session Results

**Facilitator:** Bratan
**Date:** 2026-05-25

## Session Overview

**Topic:** Архитектура взаимодействия сервисов PersonnelStatus и VisitX — связать два сервиса в единый налаженный механизм. Третий сервис (Аккредитационный центр, внешний + внутренний) в этой сессии не рассматривается.

**Goals:**
1. Схема архитектуры интеграции с конкретными API/событиями
2. Карта владения сущностями («кто чем владеет») с чёткими границами ответственности
3. Список рисков и проблемных точек
4. Приоритезированный план доработок и решение по возобновлению работ PersonnelStatus
5. Решения по поведению при конфликтных ситуациях (изменение статуса в PS во время активного ОМ в VX и т.п.)

### Контекст из исходной документации

**PersonnelStatus** — ежедневный расход личного состава. Карточка сотрудника, статусы (В строю / На дежурстве / В отпуске / Командировка / Больничный / Прикомандирован / Откомандирован), жизненный цикл PLANNED → ACTIVE → COMPLETED, генерация .docx расхода, оргструктура, индикатор обновлений.

**VisitX** — полный цикл охранного мероприятия: бюллетень → рекогносцировка → расчёт сил и средств → расстановка → согласование → ЭЦП → инструктаж → проведение → закрытие → архив. Карточки сотрудников с оперативными характеристиками, рейтинг, налёт часов, логистика, штаб, инциденты.

### Ключевые пересечения, выявленные при чтении документации

- **VisitX §10.1** явно ссылается на PersonnelStatus как на источник статусов сотрудников
- **VisitX §10.1** требует, чтобы изменения статусов сотрудников другого департамента в ходе подготовки/проведения ОМ фиксировались в системе мероприятия
- Карточка сотрудника существует в обоих сервисах с разными ракурсами (кадровый vs. оперативный)
- Оргструктура (организация → департамент → управление → отдел) общая
- Откомандирование/прикомандирование в PS напрямую связано с заявками VX на сотрудников из смежных подразделений
- Налёт часов на ОМ (VX) и учёт сменности дневных/ночных смен (PS) — пересекающиеся данные

## Фаза 2: Morphological Analysis — Раскладка осей

### Контекстные ограничения (выявлены 2026-05-31)

**Критичные факторы, влияющие на все решения:**
1. **Соло-разработчик** на оба сервиса — capacity = bottleneck для всех архитектурных решений
2. **Будущая система КУ** (Кадровый Учёт, чужая команда) — Фаза 2 интеграции после запуска PS+VX и фидбэка. PS позиционируется как **временный кадровый фасад** до прихода КУ.
3. **Серые зоны обнулены** пользователем:
   - Рейтинг → два независимых (PS-кадровый отношений и ежедневной работы; VX-оперативный на ОМ)
   - Налёт часов → только VX
   - Оргструктура → временно в PS, потом из КУ

### Решение по Оси 6 — Граница владения данными

**Выбор:** **6B с фазированием** (PS-owned employee + кэш в VX по событиям, фазируется)

**Идея — формат IDEA TEMPLATE:**

**[Category #6: Граница владения данными]:** **PS-как-кадровый-фасад, VX-как-операционный-хост, граница по бизнес-функции с фазируемой денормализацией**

*Концепт:*
- **PS** владеет: employee identity, кадровые статусы, оргструктура (временно до КУ), PS-рейтинг (отношения + ежедневная работа)
- **VX** владеет: все ОМ-сущности (бюллетень, рекогносцировка, расстановка, ЭЦП, инструктаж, инциденты, архив), VX-рейтинг (оперативный на ОМ), налёт часов
- **Карточка сотрудника в VX** = прокси к данным PS:
  - **Фаза 1 (MVP):** HTTP-вызовы PS → VX на каждый запрос. Просто, быстро, отлаживаемо.
  - **Фаза 2 (после фидбэка):** denormalized read-cache в VX с обновлениями по событиям из PS. Включаем, когда дашборд дежурного начнёт лагать.
- **Никакого shared kernel** — он не нужен, потому что роль «общего справочника» возьмёт на себя КУ в будущем

*Новизна:*
Решение **сознательно временное**: PS — это временный фасад между организацией и проектом до прихода КУ. Это позволяет НЕ строить shared kernel сейчас (он реализуется как КУ позже). Решение оптимизировано под одного разработчика и реалистичный roadmap, а не под «идеальную архитектуру».

*Trade-offs:*
- ✅ Минимум движущихся частей для соло-разраба
- ✅ Чёткое разделение функциональных обязанностей
- ✅ Естественный путь миграции к КУ
- ⚠️ Фаза 1 имеет высокую зависимость VX от PS (если PS лёг, VX тормозит)
- ⚠️ Нужна дисциплина — не пускать оперативные данные в PS «по привычке»

**Что закрывается этим решением:**
- Серые зоны (отсутствуют по сути)
- Базовая модель синхронизации (она есть, но простая)
- Будущая миграция к КУ (естественна, не требует переделки VX)

**Что НЕ закрывается (откладывается на следующие оси):**
- Конкретные правила синхронизации статусов между PS и VX (Ось 1)
- Как технически разделять монолит/микросервисы при одном разработчике (Ось 3)
- Что делать при конфликте «отпуск в PS vs расстановка в VX на ту же дату»


### Стратегический пересмотр (2026-05-31) — переопределение функций PS и VX

В ходе Фазы 2 пользователь поставил под сомнение исходную раскладку и предложил **более чистое деление**:

**PS = Talent & Performance Management** (управление качеством людей)
- Несколько типов рейтингов (peer-to-peer, руководитель→сотрудник, оценка кандидатов)
- Постановка задач сотрудникам на день / прозрачность дневной работы
- OKR / цели
- Skills matrix (навыки и компетенции)
- Кадровый резерв
- Поощрения и взыскания
- Аналитика по людям

**VX = Operations & Deployment** (расстановка и оперативная деятельность)
- **Все статусы сотрудников** (включая «в строю», «на дежурстве», часть кадровых — синхронизируется из КУ)
- Полный цикл ОМ (бюллетень → архив, как в `/docs/VisitX/`)
- Расстановка сил и средств
- Налёт часов, инциденты
- VX-рейтинг оперативной деятельности
- **Расход ЛС .docx** — здесь (как операционный артефакт)

**Внешние системы:**
- **Auth Microservice** (уже существует) — аутентификация + роли/права. VAPS только потребляет JWT.
- **КУ** (Кадровый Учёт, чужая команда, Фаза 2) — даст сотрудников, должности, оргструктуру, основные справочники, часть кадровых статусов.

### Решение по Оси 3 — Модель деплоя

**Выбор:** **Модульный монолит на Django**

**[Category #3: Модель деплоя]: Django Modular Monolith с строгими модульными границами**

*Концепт:*
```
vaps/
  core/             # Employee, Position, OrgUnit (кэш из КУ), shared utilities
  talent/           # Рейтинги, OKR, навыки, кадровый резерв, поощрения, аналитика
  operations/       # Статусы, ОМ, расстановки, ЭЦП, налёт, инциденты, расход .docx
  integration_ku/   # Sync с КУ (Celery beat tasks) — заглушка для Фазы 1
  integration_auth/ # Middleware валидации JWT от Auth-микросервиса
```
- Один Django-проект, один деплой, один Postgres
- Модули = Django apps с строгими границами (общение только через явные API-слои `talent.api`, `operations.api`)
- БД может использовать разные schema (`talent.*`, `operations.*`, `core.*`) для логической изоляции
- Если завтра понадобится разделить — границы уже готовы

*Новизна:* Решение оптимизировано под профиль соло-разработчика. Django выбран не за «модность», а за **Django Admin** (экономит недели на CRUD для справочников Talent и Operations) и за то, что PS уже на Django. FastAPI отклонён, потому что отсутствие готовой админки = месяцы дополнительной работы для соло.

*Стек:*
- Django 5.x + Django REST Framework
- PostgreSQL
- Django Admin (для управления справочниками)
- django-rules или Casbin для ABAC (если потребуется поверх RBAC из Auth-сервиса)
- Celery + Redis для асинхронных задач (sync с КУ, генерация .docx, нотификации)
- Современный фронт (React/Vue) поверх DRF API + Django Admin для админских задач

### Решение по Оси 1 — Источник истины статусов (упрощено)

**Выбор:** **Все оперативные статусы в модуле `operations` (бывший VX). Кадровые статусы из КУ — кэшируются в `core`. Никакой кросс-сервисной синхронизации (всё в одном процессе).**

**[Category #1: Источник истины]: Statuses-as-operations с КУ-кэшем**

*Концепт:*
- Все статусы (отпуск, командировка, больничный, в строю, на дежурстве, прикомандирован) хранятся в `operations.models.EmployeeStatus`
- Источники записей:
  - Пользователь VX (через UI) — для оперативных статусов («на дежурстве», «в строю»)
  - Sync из КУ (Celery task) — для кадровых статусов (отпуск, командировка, больничный)
  - Триггер при подписании расстановки ЭЦП — автоматически создаёт «на дежурстве»
- Конфликты статусов разрешаются **внутри одного модуля одной транзакцией** — никаких HTTP, idempotency keys, outbox patterns
- В записи статуса хранится `source` (USER, KU_SYNC, OM_AUTO) для аудита

*Новизна:* Сложный сценарий «отпуск vs ОМ» теперь решается локальной валидацией в `operations` модуле, а не межсервисной саге. Расход .docx — это просто SQL JOIN внутри одной БД. Когда придёт КУ, sync-задача просто пишет в ту же таблицу с `source=KU_SYNC` — формат данных и API не меняются.

### Решение по Оси 4/12 — Auth & ABAC

**Выбор:** **Внешний Auth-микросервис как единственный источник аутентификации и ролей. VAPS не хранит users/groups/permissions.**

*Концепт:*
- Django middleware валидирует JWT из заголовка Authorization
- Из токена извлекаются: user_id, фио, текущая роль, набор permission claims
- Кладётся в `request.user` (custom User backend)
- Django Admin доступен по тому же JWT (через custom auth middleware)
- ABAC, если потребуется — поверх через `django-rules`, читая атрибуты из JWT (роль, подразделение, время)

*Новизна:* VAPS не имеет своей таблицы users — это не «своя система учёта пользователей», а **потребитель чужой identity**. Это исключает целый класс багов (расхождение паролей, дублирование ролей, синхронизация при отключении сотрудника) и упрощает интеграцию.

## Фаза 2 (продолжение, 2026-05-31): Ось A — Брокеридж и актёрная модель дежурных

### Контекст оргструктуры
Иерархия переменной глубины: Организация → (департаменты) → управления → отделы → группы. Возможны ветки без департамента (организация→управления→…) вплоть до организация→группы.

### [Ось A — РЕШЕНО]: Двухуровневый брокеридж + дежурные ОРГД/ОМД

**Актёры:**
- **Руководитель управления/отдела** — ежедневно проставляет статусы своим людям: `в строю / больничный / командировка / на дежурстве → (физнаряд | специалист)`. Делает каждое управление каждый день.
- **ОРГД** (дежурный по организации, суточный) — read-only надзор: сводка по организации (количество + списки по статусам). Людей не двигает.
- **ОМД** (дежурный по ОМ, суточный) — на каждое ОМ формирует расход + расстановку. 5 ОМ в день = 5 расходов и 5 расстановок.
- **Брокер департамента** — назначенная роль (привязка к конкретному сотруднику внутри подразделения, без жёсткой привязки к уровню; главное — в подразделении назначен брокер). Видит весь список департамента, согласует выделение людей.

**Поток выделения людей на ОМ:**
1. Сотрудники со статусом **«ОМ-физнаряд»** видны ОМД → ОМД ставит их в расстановку **напрямую** (без согласования).
2. Нужно больше → ОМД шлёт запрос-уведомление **брокеру департамента** → брокер считает, запрашивает управления → руководитель управления (или **замещающий**, если отсутствует) выделяет людей → статус `ОМ→физнаряд`.
3. ОМД **не берёт чужих людей сам** — только через согласование брокер ↔ руководитель управления.

**Зафиксированные правила:**
1. **Прямой захват:** статус «физнаряд» → ОМД ставит на ОМ напрямую.
2. **Конфликт ОМ:** если несколько ОМ претендуют на одного (статус физнаряд) — **ОМД вправе решать сам, без ограничений**.
3. **Нехватка/избыток:** запросил 10, получил больше/меньше — система ничего не делает, ОМД работает с тем, что есть (никаких очередей/частичных автоматизаций).
4. **Брокер без департамента:** брокер обязательно назначается кому-то внутри подразделения; уровень не фиксирован.
5. **Возврат:** ОМД подтверждает завершение ОМ → на **следующий день у всех участников статус авто-обновляется на запланированный**.

*Новизна:* брокер — роль уровня департамента (не один на организацию); согласование двухступенчатое (ОМД→брокер→управление), субординация соблюдена; дежурные ОРГД/ОМД — суточные роли, брокерство = распределённое полномочие. Появляется концепт **«запланированный статус»** (next-day default), к которому система откатывает людей после ОМ.

**Связи с другими осями:**
- Понятие «замещающий» (п.2 потока) → завязка на **Ось B (каскадная замена)**.
- ОРГД-надзор и сводки → **Ось C (дежурный/командный центр)** уже частично закрыта.
- «Запланированный статус» / next-day откат → завязка на жизненный цикл статусов и календарь (Ось «Время»).

### [Ось B — РЕШЕНО]: Авто-каскад замены по штатной должности с ручным override

*Концепт:* Сотрудник недоступен → система автоматически поднимает следующего по штатной должностной цепочке; ответственный может вручную выбрать другого.

**Зафиксированные правила:**
1. **Алгоритм:** строго по **штатной должности** (зам → и.о.). Без тай-брейков по стажу/налёту/рейтингу.
2. **Граница каскада:**
   - **Авто** — только **внутри управления**.
   - **Ручной выбор** — в пределах **подразделения первого уровня под Организацией** (департамент; либо управление, если департамента в ветке нет).
   - За этой границей — эскалация (некого заменить автоматом).
3. **Кого замещаем:** **любого** сотрудника (не только руководящие роли, но и любого в расстановке ОМ).

*Новизна:* авто-предложение поверх которого человек властен; система обязана знать **иерархию должностей**, а не только подразделений. Две разные зоны действия: авто — узкая (управление), ручная — широкая (топ-подразделение).

### [Ось — Жизненный цикл статусов — РЕШЕНО]: Статус-как-интервал, авто-активация по дате

*Концепт:* Статус хранится с диапазоном дат; расход на день вычисляется на запрошенную дату. Планирование наперёд на любую будущую дату уже в основе модели.

**Зафиксированные правила:**
1. **Конфликт интервалов — снят by design:** ОМД не может выбрать произвольного/занятого сотрудника. Он выбирает **только тех, у кого стоит статус ОМ (физнаряд)**. Человек на отпуске/больничном просто не попадает в выборку — конфликт не «разрешается», а **предотвращается статус-гейтингом**.
2. **Активация — автоматическая:** при наступлении даты запланированный статус сам переходит `PLANNED → ACTIVE` (с запланированного на текущий). Next-day откат после ОМ — тоже авто.
3. **Правка будущего:** запланированные статусы можно менять/удалять; правит тот, кто **вправе ставить** — руководитель управления или назначенный сотрудник.

*Новизна:* единая временная ось вместо снимков по дням; ежедневное проставление = подтверждение/правка уже запланированного. Конфликт «отпуск vs ОМ» устранён архитектурно через гейтинг по статусу, а не через сложную сагу разрешения.

### [Ось D — РЕШЕНО]: Single on-prem сервер в закрытом контуре; планшеты — отложенная офлайн-фаза

*Концепт:* VAPS = один сервер в закрытой сети, web-клиенты в LAN, без облака/интернета. Синхронизация для MVP не нужна (совпадает с модульным монолитом). Планшеты — отдельная будущая фаза.

**Зафиксированные правила:**
1. **MVP:** один сервер, закрытый контур, никакой межузловой синхронизации.
2. **Планшеты (будущая фаза):** офлайн-устройство, в основном **«читалка»** (расстановка/списки, скачанные перед ОМ) **+ возможность ставить рейтинг сотрудникам**. Синхронизация на сервер — **после окончания ОМ**.
3. **Авторитет синхронизации:** **сервер всегда главный**. Планшет только **дописывает факты** (рейтинги, отметки), ничего не перезатирая. Двусторонний мерж расстановки не требуется.

*Новизна:* офлайн-сложность (CRDT/мерж) сознательно вынесена за MVP; планшет = ещё один клиент с локальным кэшем и отложенной отгрузкой фактов. Рейтинг с планшета → завязка на VX-оперативный рейтинг (Talent/Operations split).

### [Ось E — РЕШЕНО]: Единый портал, ролевые экраны; дежурные = назначение на личную учётку

*Концепт:* Один URL, один вход (JWT из Auth-сервиса). Меню и экраны определяются ролью. Никакого деления на «PS»/«VX» для пользователя — это деталь бэкенда (модули talent/operations).

**Зафиксированные правила:**
1. **Карточка сотрудника — одна**, блоки скрываются по правам (док VisitX §9 — богатая карточка: фото, антропометрия, налёт, рейтинг, статус; §14.3 — часть полей не идёт в печать).
2. **Мульти-роль у пользователя** разрешена; в т.ч. дежурные роли.
3. **Дежурство = назначение на ЛИЧНУЮ учётку** (вариант α, НЕ общая учётка):
   - Сущность `DutyAssignment(user, роль, с 08:00, по 08:00 след. дня)`.
   - Заступление в 08:00 на сутки → права роли включаются на срок назначения, авто-гаснут по окончании.
   - Даёт аудит «кто именно был ОМД/ОРГД и что делал» (критично для силовой структуры) = журнал дежурства.
   - Не конфликтует с Auth-микросервисом: Auth владеет личностью, VAPS владеет назначениями на дежурство (operations).
4. **Один ОМД на сутки** на все ОМ дня (5 ОМ в один день → один ОМД; 5 ОМ в разные дни → разные ОМД).

*Новизна:* «дежурство» моделируется как срочное полномочие на личную учётку, а не должность и не общий логин — параллельные дежурные + полный аудит без общих паролей.

### Модель ролей VAPS ↔ канон VisitX (из /docs/VisitX/VisitX.md)

| Канон VisitX | Роль в VAPS |
|---|---|
| Старший наряда (формирует расстановку, §3.2) | **Старший по ОМ** — владелец конкретного ОМ, лепит расстановку |
| Старшие направлений (§3.3, вносят расчёт блока) | Старшие направлений внутри ОМ |
| Руководитель подразделения (§3.4, выделяет ЛС) | **Руководитель управления/отдела** |
| Руководство 2-го департамента (§3.5, ЭЦП, санкции) | Утверждающий уровень |
| Орган-координатор / Штаб (§3.1, запуск ОМ, заявки приданных сил §6.4) | **ОМД** (координатор дня) + **брокер департамента** (канал запроса людей) |
| Администратор (§29.1) | Админ (Django Admin) |

**Слоистость ролей (подтверждено):**
- **ОРГД** — суточный, read-only надзор за орг-расходом.
- **ОМД** — суточный статус/дежурство, координатор дня (общий расход по всем ОМ дня, связь с брокерами). Это **роль-дежурство**, а не должность.
- **Старший по ОМ** — владелец конкретного ОМ, формирует расстановку.
- **Брокер департамента** — канал «запроса приданных сил» в подразделения.
- ОМД и старший по ОМ — **разные люди**; человек может быть старшим по ОМ, но **не в тот день, когда он заступил ОМД**.

**Связь с MVP:** док VisitX §31 содержит собственную разбивку MVP-1…MVP-4 — взять за основу в Фазе 4 (план доработок).

### [Ось F — РЕШЕНО]: In-app уведомления (колокольчик), событийные, эскалация вверх по вертикали

*Концепт:* Закрытый контур без интернета → внешних каналов (push/SMS/Telegram/почта) нет. Все уведомления — «колокольчик» внутри портала + признак непрочитано. Список событий взять из VisitX §30.

**Зафиксированные правила:**
1. **Канал:** только in-app (колокольчик в портале). Никаких внешних каналов.
2. **Адресность:** уведомление прилетает затронутому лицу по факту. Пример: сотрудник стоял в расстановке ОМ → его внезапно заменили на другого → ему прилетает уведомление, что его сняли/заменили.
3. **Эскалация по бездействию (вверх по вертикали подразделения, НЕ через ОРГД):**
   - заявка/запрос не отработан → уведомление **руководителю управления**;
   - не отреагировал → **заместителю руководителя департамента** и **руководителю департамента**.
   - ОРГД в эскалацию ОМ **не вовлекается** (его роль — только надзор за орг-расходом).

*Новизна:* эскалация = подъём по штатной вертикали (управление → зам. деп. → рук. деп.), а не через дежурного. Соответствует субординации; ОРГД остаётся чистым наблюдателем.

## Сверка с функциональным протоколом «План Расстановка» (2026-06-01)

**Источник:** `docs/VisitX/ПланРасстановка.docx` — «ПРОТОКОЛ функциональных требований проекта „Автоматизация составления и планирования ежедневного расхода личного состава, нарядов дежурств, охранных мероприятий и боевого расчёта подразделений“».

Это наиболее авторитетный функциональный документ из всех входных. Он переопределяет ряд решений сессии и вводит сущности, которых в брейншторминге не было. Ниже — реконсиляция (что меняем) и дополнение (что добавляем).

### A. Расхождения с ранее принятыми решениями (ТРЕБУЮТ ПРАВКИ)

#### A1. Конфликты статусов — ПРЕДУПРЕЖДЕНИЕ, а не жёсткий гейтинг ⚠️ ИЗМЕНЕНО

**Было (Ось «Жизненный цикл статусов», правило 1):** «Конфликт снят by design — ОМД выбирает только тех, у кого статус ОМ; занятый/отпускник не попадает в выборку».

**Стало (протокол §8.6):** Система **предупреждает** о конфликте, но **не подменяет решение человека** — «окончательное распределение остаётся за тем, кто планирует… позволяет в обоснованных случаях поступить по обстановке, но не вслепую».

**Решение:** заменяем модель «hard gating» на **«soft warning + override с фиксацией»**. Назначение возможно вопреки предупреждению, но факт игнорирования конфликта пишется в историю расстановки (кто, когда, какой конфликт проигнорировал). Это сохраняет нашу идею «статус как фильтр по умолчанию» (выборка показывает доступных вперёд), но добавляет легальный путь обхода.

**Канонический перечень проверяемых конфликтов (§8.6):**
1. Статус из КУ (отпуск/больничный/командировка/учёба/прикомандирование/откомандирование) → недоступен.
2. Двойное назначение (уже на дежурстве или на другом ОМ в эту дату).
3. Отдых после дежурства (назначение приходится на обязательные сутки отдыха).
4. Перегрузка (см. формулы нагрузки ниже).
5. Несоответствие посту (антропометрия / требуемый рейтинг).

#### A2. Центральная сущность — ОБЪЕКТ, а не ОМ ⚠️ СТРУКТУРНОЕ ИЗМЕНЕНИЕ

**Было:** модель сессии была ОМ-центричной (всё крутится вокруг охранного мероприятия).

**Стало (протокол §4):** в центре — **Объект** (постоянная сущность с паспортом). От объекта расходятся **два направления службы**:
- **Ежедневные дежурства** — предсказуемая служба, планируется на месяц вперёд (базовая нагрузка).
- **Охранные мероприятия** — планируются заново под каждый выезд ОЛ.
Оба направления задействуют одних людей и сходятся в **общем расходе ЛС** и в **карте нагрузки**.

**Решение:** модуль `operations` реструктурируется вокруг агрегата **Object**:
```
operations/
  objects/      # Объект, Паспорт, Пост, Сектор, Чек-лист
  duties/       # Виды дежурств, планирование смен, статусы БД/отдых
  events/       # ОМ: рекогносцировка → потребность → запрос → расстановка → утверждение
  groups/       # Справочник групп
  load/         # Нагрузка (агрегатор дежурств + ОМ)
  ratings/      # Оценивание ОМ, рейтинг сотрудника
```
«Расход ЛС» = сводка по всем ролям сотрудника на дату (дежурство + ОМ + отдых).

#### A3. Терминология ролей — выровнять с каноном ⚠️ УТОЧНЕНО

| Роль в сессии | Канон протокола | Действие |
|---|---|---|
| Старший по ОМ | **Старший объекта** (§8.1) — готовит и проводит ОМ | Переименовать в «старший объекта» |
| Брокер департамента | **ГАП СПС / распределяющие ЛС** (§1.3, §8.4) — выделяют конкретных людей по запросу | Согласовать: брокеридж = механизм запроса/распределения протокола |
| ОМД (дежурный по ОМ) | **нет прямого аналога** | Сессионная надстройка — валидировать с заказчиком |
| ОРГД (дежурный по организации) | **нет прямого аналога** (близко — дашборд расхода §11.3) | Сессионная надстройка — валидировать с заказчиком |
| Старший сектора | **Старший сектора** (§2, §10.2) | Подтверждено |

**Вывод:** наши ОМД/ОРГД — это сессионные роли поверх протокола; перед реализацией свериться с заказчиком, не дублируют ли они «старшего объекта» + ГАП + дашборды.

### B. Подтверждения (протокол валидирует решения сессии) ✅

- **B1. Владение статусами (Ось 1)** — подтверждено §3.1. КУ владеет ФИО/должность/звание/подразделение + длительные статусы; **VAPS владеет** оперативными статусами и всеми сущностями ОМ/дежурств/нагрузки/оценок.
- **B2. Внешний вход через КУ (Ось 4/12)** — §3.1: «через кадровую систему производится вход в систему». Согласуется с моделью «VAPS — потребитель чужой identity».
- **B3. Карточка/рейтинг закрытый** — §10.4 (закрытость оценок) усиливает решение «единая карточка, блоки по правам» (Ось E).
- **B4. Журнал действий / аудит** — §5.2: «ведётся журнал действий — кто, когда, к каким сведениям обращался и что менял». Подтверждает аудит-домен Фазы 1.

### C. ДОПОЛНЕНИЕ — сущности и правила из протокола, которых не было в сессии 🆕

#### C1. Объект и Паспорт объекта (§6.1)
Постоянная сущность. Паспорт: наименование/тип, посты, секторы, проблемные места, чек-лист, привлекаемые группы, **история изменений** (что/когда/кем). Объекты различаются частотой ОМ (частые → расстановка почти не меняется; редкие → рекогносцировка заново).

#### C2. Посты и Секторы (§6.2)
**Пост** — точка несения службы. Атрибуты:
- задачи поста (что делать/контролировать);
- особенности (проблемные направления, специфика);
- тип: **наружный** (улица) / **внутренний** (помещение);
- **предельное время несения без смены** (§6.2.1) — зависит от типа поста, времени суток/года, погоды; основа сменяемости;
- требования по **антропометрии**;
- требования к **рейтингу**.
Задачи+особенности доводятся при уведомлении = **предварительный инструктаж** (§8.5).
**Сектор** — зона ответственности из нескольких постов; за сектор отвечает старший сектора.

#### C3. Чек-лист объекта (§6.3)
**Типовой** единый чек-лист + возможность дополнить/изменить под конкретный объект. Итог прохождения: либо подтвердить расчёт постов/секторов, либо внести изменения; решение и обоснование фиксируются. = механизм рекогносцировки (§8.2).

#### C4. Справочник групп (§6.4)
**Группа** — специализированное подразделение (боевое прикрытие, снайперское/антиснайперское, досмотр, ПТУ, тех.обеспечение). Хранит: наименование/специализация, состав/численность, задачи. На пост/задачу можно назначить **группу целиком ИЛИ отдельного сотрудника**.

#### C5. Ежедневные дежурства (§7)
- Постоянная служба на объекте, планируется **на месяц вперёд**.
- Посменно: заступил на сутки → следующие сутки **обязательный отдых**.
- **Жёсткое правило:** после суток дежурства сотрудник **недоступен для ЛЮБОГО назначения** (ни дежурство, ни ОМ).
- Статусы: на сутки — «на дежурстве», на след. сутки — «отдых после дежурства».
- Дежурства = базовая картина, поверх которой накладываются ОМ.

#### C6. Поток охранного мероприятия (§8) — канонические 8 шагов
1. **Создание** ОМ вокруг объекта, назначение старшего объекта (§8.1).
2. **Рекогносцировка** через чек-лист; контролирующие руководители могут править расчёт — двойной контроль (§8.2).
3. **Расчёт и утверждение потребности** в людях (§8.3).
4. **Запрос и распределение** (§8.4): система рассылает запрос группам → группы выделяют конкретных людей → собирается **расстановка** (наименование ОМ, посты, группы, поимённо сотрудники). Расстановка не статична.
5. **Уведомление и ознакомление** (§8.5): сотрудник видит пост/задачи/особенности, ставит отметку ознакомления; старший видит, кто не ознакомился.
6. **Проверка конфликтов** (§8.6) — см. A1.
7. **Утверждение итоговой расстановки** руководителем (§8.7) — становится действующим основным документом ОМ.
8. **Оперативные изменения** (§8.8): даже утверждённую расстановку можно менять (выбытие, доп. силы); каждое изменение проходит проверку конфликтов и фиксируется в истории — видно отличие от первоначально утверждённой и почему.

#### C7. Потребность (§8.3) 🆕 СУЩНОСТЬ
Рассчитанное количество сотрудников, необходимое от каждого СПС и от каждой группы. Складывается из постов/задач, которые нужно закрыть. Утверждается → становится основанием для запроса. (Это формализует наш «двухуровневый брокеридж»: потребность → запрос группам → распределение.)

#### C8. Нагрузка — конкретные формулы (§9)
Нагрузка = вся занятость (дежурства + ОМ). Два признака перегрузки:
1. **По постоянной задействованности:** > 3 дней подряд ежедневно > 8 часов → перегрузка, нужна разгрузка.
2. **По времени на посту:** факт (фиксируется при опросе по итогам ОМ) > предельного времени поста (§6.2.1) → перегрузка по этому посту.
Используется при планировании (предупреждение §8.6) и при контроле (дашборды §11).

#### C9. Оценивание мероприятий (§10) — уточняет рейтинг
- **Двустороннее:** старший объекта → группа и каждый сотрудник; сотрудник → свои старшие (сектора, объекта).
- **10-балльная шкала, default = 8** автоматически каждому участнику (нет замечаний → ничего делать не нужно).
- Снижение **< 8 требует обязательного комментария** с причиной, иначе не принимается.
- **Закрытость (§10.4):** никто не видит выставленную лично ему оценку; сотрудник видит только итоговый рейтинг; старший не видит оценок от подчинённых.
- Рейтинг ≈ 8 — норма; заметное отклонение вниз — сигнал руководству.

> **Связь с Talent/Operations split:** этот рейтинг — **оперативный (ОМ)**, живёт в `operations/ratings`. PS-рейтинг отношений/ежедневной работы (Talent) — отдельный, как и решено в Фазе 2.

#### C10. Дашборды и рекомендации (§11)
1. **Готовность к ОМ** — чек-лист пройден? потребность утверждена/закрыта? ознакомились? расстановка утверждена?
2. **Нагрузка на людей** — для начальников подразделений; кто перегружен, кому разгрузка.
3. **Общий расход ЛС** — «где сейчас сотрудники» на любую дату (дежурства/ОМ/отдых).
4. **Рекомендации руководству** — по накопленным оценкам/нагрузке: проблемные объекты/ОМ, регулярная перегрузка, группы/люди, требующие внимания.

### D. Что цифровая система НЕ делает (§3.2) — границы
Не ведёт кадровый учёт; не заменяет приказы (издаются вне системы); не присваивает уровень угрозы объекту; не оценивает оперативную обстановку.

### E. Открытые вопросы, поднятые сверкой (на Фазу 3/4)
1. Судьба ролей **ОМД/ОРГД** — оставляем как надстройку или сворачиваем в «старший объекта + ГАП + дашборды»? (валидация с заказчиком)
2. Статусы **ГЭВ** (группа экстренного выезда), **учёба**, **соревнования** — не были в сессии; куда ложатся в enum статусов и кто владелец (ГЭВ — VAPS; учёба/соревнования — КУ).
3. **«Отдых после БД» как абсолютный блокер** vs наш «soft warning» — отдых, похоже, жёстче прочих конфликтов. Уточнить, является ли он непреодолимым.
4. **Опрос по итогам ОМ** (источник факт. времени на посту и оценок) — отдельная сущность/процесс, не проектировался в сессии.
5. **Предельное время поста** зависит от погоды/сезона — нужен ли ввод этих факторов вручную или справочник коэффициентов.

## Фаза 4: Resource Constraints & Decision Tree — Приоритезированный план (2026-06-01)

### Жёсткие ограничения (рамка плана)
1. **Соло-разработчик** — план линейный, без параллельных треков.
2. **КУ ещё нет** — оргструктуру/сотрудников поставляет заглушка `integration_ku` (Admin + сидер); контракт sync фиксируем сейчас, реализуем позже.
3. **Закрытый контур, один сервер** — нет внешних каналов/облака.
4. **Объект-центричная модель** (протокол) — Object корневой агрегат.

### Решения по развилкам (decision tree)
- **Старт проекта (пересмотр выбора 1.C → brownfield-гибрид):** модуль ежедневных дежурств **уже написан**, но в коде бардак → НЕ чистый старт. Существующий код дежурств = фундамент, который **рефакторим и расширяем**, а не выбрасываем. PS возобновляется через рефакторинг.
- **Критичная находка:** текущие дежурства **плоские, без привязки к Объекту**. Введение агрегата `Object` и пересадка дежурств на него — **самый тяжёлый пункт рефакторинга (0.3)** и ключевой риск этапа.
- **Порядок (выбор 2.A+B разбит):** дежурства (база нагрузки, §7) ПЕРВЫМИ → ОМ накладывается сверху.
- **ОМД/ОРГД — отложить** до валидации с заказчиком (открытый вопрос E1). MVP живёт на «старший объекта + руководитель управления + дашборды».
- **Нагрузка** — рано (в ядре расхода). **Оценивание/рейтинг** — последним (нужен факт. опыт ОМ).
- **Целевой MVP (выбор 3.C):** несколько объектов, дежурства + ОМ + дашборд нагрузки — как горизонт; промежуточные боевые срезы на каждом этапе.

### Поэтапный план

**Этап 0 — Аудит + Рефакторинг существующих дежурств** 🎯 первый этап
- 0.1 Аудит кода через `bmad-document-project` (реверс-инжиниринг в документацию) — ВЫПОЛНЯЕТСЯ
- 0.2 Привести к целевой структуре `core / operations`, схемы, явные границы `*.api`
- 0.3 **Объект-центричность** — ввести агрегат `Object`, пересадить плоские дежурства на него (главный риск)
- 0.4 Статус-как-интервал `EmployeeStatus(interval, source, авто-активация)`
- 0.5 Auth/JWT middleware `integration_auth`
- 0.6 КУ-заглушка `integration_ku` (Admin + сидер), контракт sync

**Этап 1 — Дежурства до полноты:** виды дежурств, план на месяц, статусы «на дежурстве»/«отдых после», нагрузка (>3дн >8ч), дашборд «Общий расход ЛС на дату», расход .docx.

**Этап 2 — Полный цикл ОМ:** 8 шагов протокола, `groups`, `Потребность`, брокеридж, конфликты (soft warning + override), каскадная замена, in-app уведомления + эскалация по вертикали.

**Этап 3 — Масштаб + интеллект (целевой MVP 3.C):** несколько объектов, наложение дежурств+ОМ в общей нагрузке, перегрузка по посту, дашборды (готовность/нагрузка/рекомендации), опер. изменения с историей.

**Этап 4 — Talent + Оценивание:** рейтинги/OKR/навыки/резерв, двустороннее оценивание ОМ (10б, default 8, закрытость), опрос по итогам ОМ.

**Этап 5 — Будущие фазы:** реальная интеграция КУ (контракт готов с Этапа 0), планшеты (офлайн-читалка + рейтинг), денормализованный read-cache при лагах.
