# План: этап «Расстановка» без боксов потребности и выделения сил

Задача Plane **№110** «ОМ. Этап Расстановка.». Формулировка заказчика: «Убери с
этапа Расстановка эти боксы они не нужны» + два снимка карточки ОМ-2027-8 на
шаге 2 — «Расстановка · подготовка расчёта» (строки потребности) и
«Расстановка · выделение сил» (числа по группам).

## Решение заказчика (26.08.2026)

Развилка «убрать совсем / вынести в свой шаг как в эталоне / убрать один из
двух» задана заказчику вопросом. Выбран вариант **«убрать совсем, стадии
проходить автоматом»**: человек этих форм не видит никогда, шаг 2 всегда
открывается доской подбора.

Отвергнуто: вынести в свой шаг «Потребность» по прототипу
(`stepNames = [… "Потребность", "Выделение", "Расстановка" …]`, отдельный пункт
меню). Эталон так и устроен, но заказчик сказал «не нужны», а не «не здесь».
Расхождение с эталоном — в [[../Frontend/Decisions]].

## Что вскрылось до кода (грепом по читателям)

Автопроход стадий `DEMAND` и `FORCES` — не косметика. На эти две стадии
завязана ВСЯ цепочка «Сбор сил на ОМ» (задача заказчика Plane №73, шаги
СС-1…СС-6), живущая на `/employees`:

| Читатель | Как отбирает сегодня | Что будет при автопроходе |
|---|---|---|
| `app/employees/page.tsx:306` — лента «Запросы с рекогносцировки» | `useSecurityEvents({stage:"DEMAND"})` | лента пуста всегда |
| `app/employees/page.tsx:296` — «Запрос сил по мероприятиям» | `useSecurityEvents({stage:"FORCES"})` | лента пуста всегда |
| `apps/ops/security_events.py:1209` — `_ALLOCATION_STAGES` | `("DEMAND","FORCES")` | раскладку/оповещение/приёмку сервер отобьёт 422 |
| `features/forces-split/ui/ForcesSplitPanel.tsx` | рисуется в строке ленты | не рисуется никогда |
| `assign_placement` (`security_events.py:2081`) | фильтрует пул по `force_roster`, если он не пуст | без состава пул = весь личный состав |

Молча снять боксы значило бы погасить модуль, который заказчик сам заказывал
(и по которому в очереди стоит открытая №74). Поэтому в ту же задачу входит
перевод лент сбора со СТАДИИ на ФАКТ: «рекогносцировка пройдена, сбор ещё не
закрыт».

## Шаги

- РБ-1. Сервер: автопроход `DEMAND`+`FORCES` при завершении рекогносцировки
    - Внутренняя `_autopass_demand_and_forces(event)`: строки потребности из расчёта постов рекогносцировки, `demand_approved=True`, `force_need`, `force_requests` одной строкой на мероприятие; стадия → `PLACEMENT`; обе записи истории (`DEMAND→FORCES`, `FORCES→PLACEMENT`) пишутся, чтобы лента переходов не врала
    - `complete_recon` возвращает мероприятие уже на `PLACEMENT`
    - Ручки `approve_demand` и `complete_forces` НЕ удаляются: контракт живёт, ими ведут заведённые ранее мероприятия
    - `pytest` apps/ops + apps/operations целиком
- РБ-2. Сервер: раскладка сил разрешена на «Расстановке»
    - `_ALLOCATION_STAGES` += `PLACEMENT`; цепочка СС-1…СС-6 продолжает работать, пока ОМ уже стоит на расстановке
    - Приёмка штабом дополняет `force_roster` — пул подбора на доске растёт по ходу
    - Красная проба: раскладка на `PLACEMENT` до правки обязана падать 422
- РБ-3. Сервер: миграция с бэкфиллом для заведённых ОМ
    - Мероприятия, стоящие сейчас на `DEMAND`/`FORCES`, проводятся тем же автопроходом — иначе они заперты навсегда (форм, которыми их вели, на клиенте больше нет)
    - Откат миграции — no-op с записью причины
- РФ-4. Клиент: `PlacementStage` всегда рисует доску
    - Удалить `DemandPanel` и `ForcesPanel` из `features/security-event-stages/ui/PlacementStage.tsx`
    - Хуки `useApproveDemand` / `useCompleteForces` снимаются с экрана, но остаются в слое: ручки живы
    - Перед кодом — скилл `/ui-ux-pro-max`
- РФ-5. Клиент: ленты сбора сил — по факту, а не по стадии
    - `app/employees/page.tsx`: входящие = прошедшие рекогносцировку и не закрывшие сбор; «Запрос сил» — по тому же признаку
    - Мок-слой `mocks/ops/security-events-handlers.ts` приводится к новому поведению в тот же заход
- РФ-6. Пины проб и полный гейт
    - `e2e/forces-gathering.spec.ts`, `e2e/approval-stage.spec.ts`, `e2e/acknowledgement-stage.spec.ts`, `e2e/mock-contract.spec.ts` — пины стадий правятся осознанно, с комментарием
    - `seed_smoke_fixtures` больше не может оставить ОМ на `FORCES` — фикстура пересматривается
    - `tsc` + полный smoke `SMOKE_LIVE=1`, снимок экрана шага 2

## Зависимости

РБ-1 → РБ-2 → РБ-3 → РФ-4 → РФ-5 → РФ-6. РФ-5 нельзя выпускать раньше РБ-2:
лента покажет мероприятие, действия в котором сервер отобьёт.

## Риски

- Пул подбора у ОМ без состава — весь личный состав: правило `NOT_IN_ROSTER`
  включается только при непустом `force_roster`. Это поведение существующее,
  задачей не меняется, но теперь встречается чаще.
- `recon_force_request` считается по постам; у мероприятий, где число ввёл
  человек, автопроход его не затирает — это уже заложено в `complete_recon`.
