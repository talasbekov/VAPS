# План: рейтинг до расстановки, оценивание на каждом ОМ

Две карточки заказчика, разрешённые им к работе: **№96** «Рейтинг не связан с
кадрами: на расстановке он не показывается никогда» и **№67** «Отбор кандидатов
по рейтингу считается по показанной странице». Указания заказчика записаны в
самих карточках: «Рейтинг необходимо добавить в систему, оценивание на каждом
ОМ» и «Научи отдавать рейтинг».

## Что есть сегодня (проверено по коду)

| Кусок | Состояние |
|---|---|
| `OpsRatedParticipant` (`models_rating.py:51`) | `participant_code` — свободная строка вида `employee-1`, связи с `Employee` НЕТ |
| `OpsEvaluationEvent` | поле `security_event_id` уже есть и необязательное |
| Кто заводит мероприятия оценивания | ТОЛЬКО `seed_operations`; из живого ОМ не создаётся ни одно |
| `/api/ops/operational-ratings/` | отдаёт `employeeId = participant_code` |
| Доска расстановки (`PlacementStage.ratingOf`) | ищет рейтинг по КАДРОВОМУ id — совпадений на живом стенде не бывает |
| `/api/ops/personnel/` | о рейтинге не знает вовсе; отбор и сортировка по рейтингу идут по загруженной странице |

Отсюда и симптом: бейдж рейтинга не появляется, фильтр «Рейтинг» отбирает
пустоту, требование поста `minRating` не проверяется. На моке идентификаторы
совпадают — мок зелен, живой стек молчит.

## Порядок и почему такой

Сначала связь участника с кадрами (без неё рейтингу неоткуда взяться у
конкретного человека), затем заведение оценивания на ОМ (без него связь
останется пустой у всех, кого не засеяли), и только потом отдача рейтинга в
подбор — иначе ручка кадров возвращала бы `null` всем и выглядела бы сломанной.

## Шаги

- РЙ-1. Связь участника рейтинга с кадровой записью
    - Поле `employee_id` у `OpsRatedParticipant` (плоская ссылка без FK — идиома раздела, как `chief_employee_id` у ОМ) + миграция
    - Бэкфилл: `participant_code` вида `employee-<pk>` разбирается в ссылку; всё, что не разбирается, остаётся без связи и НЕ выдумывается
    - Проба бэкфилла с красной пробой по правилу из [[../Personnel-Records/Decisions|Decisions]]
- РЙ-2. Сводка рейтинга отдаёт кадровый идентификатор
    - `employeeId` в ответе `/api/ops/operational-ratings/` — кадровый id связанного участника; несвязанный участник отдаёт `null` и НЕ притворяется кадровым
    - Мок-слой приводится к тому же правилу в тот же заход
- РЙ-3. Оценивание заводится на закрытии ОМ
    - `close_event` создаёт `OpsEvaluationEvent` со ссылкой `security_event_id` и участниками из состава расстановки
    - Повторное закрытие не плодит второе мероприятие оценивания
    - Мероприятие без расстановки оценивания не заводит: оценивать некого
- РЙ-4. Кадровая ручка отдаёт рейтинг
    - `/api/ops/personnel/` возвращает `aggregateRating` — ТОЛЬКО при праве `rating.view_aggregate`, иначе поля нет вовсе
    - Параметры `ordering=rating` и `rating_band`; без права отбор по рейтингу недоступен, а не молча игнорируется
- РЙ-5. Доска подбора перестаёт врать про полноту отбора
    - Сортировка и фильтр по рейтингу уезжают на сервер; строка-оговорка «отбор по показанной странице» снимается
    - Сортировка «по соответствию» остаётся клиентской осознанно: соответствие считается против ВЫБРАННОГО поста, о котором ручка кадров не знает
- РЙ-6. Пины проб и полный гейт
    - Живые пробы расстановки, рейтинга и подбора; красная проба на каждую новую
    - `pytest` `ops`+`operations`, `tsc`, снимок доски с видимым бейджем рейтинга

## Отвергнутые варианты

Словарь соответствия отдельной таблицей вместо поля отвергнут: у связи один
владелец и одно значение на участника, а таблица завела бы вторую правду о том,
кто есть кто, и требовала бы синхронизации.

Заводить оценивание при СОЗДАНИИ ОМ отвергнуто: оценивать нечего, пока люди не
отработали, и пустое мероприятие оценивания висело бы в очереди оценщика с
первого дня.
