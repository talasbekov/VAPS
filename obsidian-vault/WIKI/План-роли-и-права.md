# План: система ролей и прав (Plane №36)

Задача заказчика дословно: «Роли и права должны быть очень гибким. Должна быть возможность из ряда функции группируя доступ к ним создавать права, а также из ряда прав группируя права создавать роли для пользователей. В настройках добавь эти возможности. Обязательно у них у всех должен быть поиск, чтобы ручным способом не искать функции, права или роли. Реализация должна быть как на бэкенде так и на фронте.»

## Что уже есть (разведка 26.08.2026)

| Сущность | Где | Состояние |
|---|---|---|
| `Permission` (код, имя, описание, активность) | `operations/models.py` | таблица есть, API нет |
| `Role` (код, имя, описание, активность) | там же | таблица есть, API нет |
| `RolePermission` (роль ↔ право) | там же | таблица есть, API нет |
| `UserRole` (пользователь ↔ роль ↔ **область-подразделение**) | там же | таблица есть, API нет |
| `TemporaryDutyPermission` | там же | временные дежурные права, отдельный механизм |
| Гейт ручек | `operations/api/permissions.py` (`RequirePermissionMixin`) | работает: `permission_map = {action: code}`, fail-closed; **66 файлов** объявляют карты |
| Права актора | `GET /api/operations/my-permissions/` | работает; клиент — `useOpsPermissions`, `*` = суперправо |

⚠️ **Поправка разведки (26.08.2026, по ходу шага `П-1`).** Первая разведка смотрела только `ops/api/urls.py` и объявила, что API управления доступом нет. Это неверно: админ-API RBAC живёт в СОСЕДНЕМ приложении — `operations/api/` (`/api/operations/roles/`, `/permissions/`, `/user-roles/`, `/temporary-duty/`), с гейтом `admin.roles` и пробами `test_rbac_admin_api.py`. Урок тот же, что уже стоил времени раньше: искать по имени ресурса во всех приложениях, а не по одному файлу маршрутов.

Что там **есть**: список и чтение ролей, список и чтение прав, список назначений с фильтром `user_id`, выдача роли с областью, снятие роли.

Чего **нет** и что остаётся работой: заведение и правка прав и ролей (обе ручки `ReadOnlyModelViewSet`), состав прав роли (добавить/снять право), **поиск на всех трёх реестрах**, учётные записи целиком, экраны.

Шаги `П-2`…`П-4` поэтому не «завести API», а «дописать существующий до записи и поиска» — старое не переписывается, новое добавляется рядом.

## Решения заказчика (26.08.2026, вилки закрыты им же)

**Уровней два, а не три.** Сегодняшний `Permission` (`event.manage`) и есть ПРАВО. «Функции» — read-only каталог: где право применяется (какие ручки и экраны оно открывает). Отдельной сущностью функции не хранятся: они выводятся из карт `permission_map`, у которых уже есть владелец в коде. Заводить третий уровень заказчик отказался — из двух вариантов выбран этот.

**Учётки заводятся из интерфейса**, не только назначаются роли: создание, сброс пароля, блокировка.

**Роль назначается С ОБЛАСТЬЮ** (подразделение или «вся служба») — поле в модели уже есть; без него `№74` (разделение сбора сил по департаментам) не сделать.

## Чего в плане СОЗНАТЕЛЬНО нет

Третий уровень «функция» отдельной таблицей — отвергнут заказчиком; каталог применения строится из кода, а не хранится. Наследование ролей (роль включает роль) — не просили, а без запроса это лишний источник неожиданных прав. Права на отдельные записи (этот объект — да, тот — нет) — тоже не просили; область по подразделению закрывает известные сценарии.

## Шаги

- П-1. Право на администрирование доступа и каталог функций
  - Бэк: код права `access.manage`, гейт на все ручки раздела; ручка каталога — какие ручки и действия открывает каждое право (собирается из `permission_map`, не хранится)
  - Проба: каталог называет для `event.manage` реальные действия; красная — подменить карту
- П-2. API прав: список с поиском, заведение, правка, деактивация
  - Бэк: `PermissionViewSet` из read-only дорастает до записи; удаления НЕТ — только деактивация (код живёт в картах ручек, удаление оставило бы гейт без словаря); заведение кода, которого нет ни в одной карте, — предупреждение, а не запрет
  - Проба: поиск по коду и имени; деактивация не ломает гейт
- П-3. API ролей: список с поиском, заведение, правка, состав прав
  - Бэк: `RoleViewSet` из read-only дорастает до записи + добавление и снятие прав; роль без прав допустима (заготовка); журнал мутаций на каждое изменение состава
  - Проба: состав роли меняется, след в журнале назван поимённо
- П-4. API назначения ролей пользователю с областью
  - Бэк: у существующих list/create/destroy появляются поиск и разрешение имени пользователя; выдача и снятие роли с `scope_division_id`; повтор не удваивает; снятие своей последней административной роли отбивается
  - Проба: два назначения одной роли в разных областях живут рядом; красная — снять уникальность
- П-5. API учётных записей: список с поиском, заведение, блокировка, сброс пароля
  - Бэк: создание пользователя, `is_active`, сброс пароля с выдачей временного; пароль в журнал НЕ пишется
  - Проба: заблокированный не входит; в журнале нет пароля
- П-6. Экран «Права» в настройках
  - Фронт: реестр с поиском, карточка права с каталогом применения, заведение и деактивация
- П-7. Экран «Роли» в настройках
  - Фронт: реестр с поиском, карточка роли, состав прав с поиском по правам
- П-8. Экран «Пользователи» в настройках
  - Фронт: реестр с поиском, роли пользователя с областью, выдача и снятие
- П-9. Заведение учётки, блокировка и сброс пароля на экране
  - Фронт: окно заведения, подтверждение блокировки, показ временного пароля ОДИН раз
- П-10. Связность: гвард раздела, мок-слой, аудит на экране
  - Фронт+бэк: раздел закрыт правом `access.manage`; мок-слой повторяет правила; действия видны на экране аудита подписями, а не кодами
