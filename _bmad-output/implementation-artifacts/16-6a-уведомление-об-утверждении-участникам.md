# Story 16.6a: Уведомление участников об утверждении Расстановки (FR-27, часть 1/4)

Status: ready-for-dev

## Story

As a **сотрудник, назначенный на пост, и старший мероприятия**,
I want **получить уведомление, когда Расстановка утверждена**,
so that **я узнаю о своём назначении без ручного опроса планировщика (FR-27, `docs/registries/ws-message-types.yaml::ASSIGNMENT_APPROVED`)**.

## Scope Decision (найдено при create-story)

- **Часть 1/4 расщепления Story 16.6.** Исходный текст epics.md (`Story 16.6: Уведомления о назначении + отметка ознакомления (FR-27); эскалация неподтверждённых`) смешивает 3 разные ответственности — уведомление, отметка ознакомления (новое состояние `PlacementAssignment.acknowledged_at`), эскалация неподтверждённых (`ACK_MISSING_ESCALATION`) — плюс скрытый 4-й кусок, найденный при проектировании (см. ниже). Расщепление по тому же принципу, что 16.3a-d: одна стори — один message-kind/один сервис, не смешивая уведомление с отметкой/эскалацией.
- **КРИТИЧЕСКАЯ находка при проектировании: только ОДИН из 4 зарегистрированных `docs/registries/ws-message-types.yaml`-типов для 16.6 реально резолвится сегодняшними данными без изобретения нового конвент-решения.** `ws-message-types.yaml` уже несёт `ASSIGNMENT_SUBMITTED` (recipients: «approver»), `ASSIGNMENT_RETURNED` (recipients: «creator/senior»), `ASSIGNMENT_APPROVED` (recipients: «assigned employees/senior»), `ACK_REQUIRED`/`ACK_MISSING_ESCALATION` — НИ ОДИН из них не вызывается `notify()` сегодня (16.4 писал только `record()`-аудит). Из всех:
  - `ASSIGNMENT_APPROVED` → «assigned employees» = `PlacementAssignment.employee_id` (реальное поле, реальные данные) + «senior» = `SecurityEvent.senior_employee_id` (реальное nullable-поле, `apps/operations/events/models.py:65`) — ОБА резолвятся напрямую.
  - `ASSIGNMENT_SUBMITTED` → «approver» требует permission-код «кто утверждает Расстановку» — ГРЕП всего `docs/registries/`+`apps/operations/rbac/` не находит НИ ОДНОГО зарегистрированного permission-кода для этого действия (естественно: API/permissions-обвязка approve — Story 16.8, ещё не построена). Изобретать permission-код здесь означало бы решать чужую стори без спецификации.
  - `ASSIGNMENT_RETURNED` → «creator» требует поле «кто создал версию» — `AssignmentVersion` НЕ хранит `created_by`/`author` (только `event`/`status`/`version`/`is_current`/`signature_hash`, `apps/operations/events/models.py`) — не изобретается.
  - `ACK_REQUIRED`/`ACK_MISSING_ESCALATION` — требуют новое состояние «ознакомление» (`PlacementAssignment.acknowledged_at`, УЖЕ существует как поле-заглушка с 16.1, но НИ ОДНОГО сервиса его не устанавливает) и периодическую эскалацию (`escalate_stale_force_requests()`, 15.10, — буквальный образец для будущей 16.6c) — самостоятельный кусок работы.
  Эта стори реализует ТОЛЬКО `ASSIGNMENT_APPROVED` — единственный тип, резолвящийся сегодняшними полями без изобретения.
- **`employee_id` → «получатель уведомления» — НОВЫЙ мост, не существовавший до этой стори.** `notify()`'s `recipient` — «flat actor id» (тот же паттерн, что все существующие вызовы `notify()`, все — `UserRole.user_id`-подобные строки, НЕ `core.Employee`-UUID). `apps/core/models.py::UserEmployeeBinding` (`user_id` (external auth account id) ↔ `employee` OneToOne) — уже существующая, но НИ РАЗУ не читанная кросс-контекстно модель, буквально созданная для этого моста (`BR-ACCOUNT-001`). Новый батч-селектор `CoreEmployeeSelector.user_ids_for(employee_ids)` (образец — `denorm_for()`/`operational_profile_for()`, тот же селектор, одна батч-выборка) — сотрудник БЕЗ привязанного `UserEmployeeBinding`-аккаунта (ещё не заведена учётка в системе) — трактуется как «уведомить некого», проекция для него ПРОПУСКАЕТСЯ (не ошибка, тот же принцип «нет данных = пропуск», что 16.3b-d/16.5).
- **Новый `Notification.Kind.ASSIGNMENT_APPROVED` + миграция.** `Notification.kind`'s DB `CheckConstraint` («chk_notification_kind») зеркалит `Kind.values` буквально (drift ловит `test_kind_check_covers_kind_choices`) — добавление НОВОГО вида уведомления требует и Python-`Kind`-записи, и SQL-констрейнта в ОДНОЙ миграции (тот же паттерн, что миграции `GROUP_FORCE_REQUEST_ESCALATED`/`TEMP_PERMISSION_ACTIVE` уже показывают, `apps/notifications/migrations/0004-0007`).
- **Вызывается ТОЛЬКО на реальном `SUBMITTED->APPROVED`-переходе, внутри `approve_assignment_version()`'s существующего `transaction.atomic()`, СИММЕТРИЧНО 16.5's `project_placement_assignment()`-вызову** (тот же idempotent-replay-гейт — ранний `if version.status == APPROVED: return version` уже исключает повторный вызов на replay, тот же принцип, не переоткрывается).
- **«Один per recipient per день» — `notify()`'s собственный контракт, НЕ изобретается заново.** Один `notify(recipient=user_id, kind="ASSIGNMENT_APPROVED", business_date=Clock.today_local(), payload={...})`-вызов НА ПОЛУЧАТЕЛЯ (не на назначение) — сотрудник с несколькими назначениями в ОДНОЙ утверждённой версии (12.3b's intra-version duplicate-сценарий) получил бы ОДНО уведомление за день по конструкции `notify()`'s ключа `(recipient, kind, business_date)`, «первый payload побеждает» — та же семантика, что `escalate_stale_force_requests()` (15.10) уже принимает как данность для многострочных дайджестов.

## Acceptance Criteria

1. **AC-1 (уведомление участнику на реальном approve).** `approve_assignment_version(version, actor=...)` на РЕАЛЬНОМ переходе `SUBMITTED->APPROVED` — для каждого `PlacementAssignment.employee_id` версии, у которого ЕСТЬ `UserEmployeeBinding`, создаётся `Notification` с `kind="ASSIGNMENT_APPROVED"`, `recipient=<его user_id>`, `business_date=Clock.today_local()`.
2. **AC-2 (уведомление старшему мероприятия).** `event.senior_employee_id` задан И у него есть `UserEmployeeBinding` — он ТОЖЕ получает `ASSIGNMENT_APPROVED`-уведомление (свой `recipient`, та же `business_date`).
3. **AC-3 (нет привязки аккаунта — пропуск, не ошибка).** Сотрудник (участник ИЛИ старший) без `UserEmployeeBinding`-строки — approve НЕ падает, уведомление для него просто не создаётся.
4. **AC-4 (senior не задан — пропуск).** `event.senior_employee_id is None` — уведомление старшему не создаётся (участникам — создаётся как обычно).
5. **AC-5 (payload несёт минимум для перехода по ссылке).** `payload` содержит как минимум `event_id`/`version_id` (`action_url: "/assignment-versions/{id}"` из `ws-message-types.yaml` — id версии нужен клиенту).
6. **AC-6 (идемпотентный replay approve не дублирует и не падает).** Повторный вызов `approve_assignment_version()` на УЖЕ `APPROVED`-версии — не создаёт новых `Notification`-строк (та же idempotent-replay-семантика 16.4/16.5, `notify()`'s собственная `(recipient, kind, business_date)`-идемпотентность — вторая линия защиты).
7. **AC-7 (несколько назначений одного сотрудника — одно уведомление).** Сотрудник назначен на 2+ поста в ОДНОЙ утверждаемой версии (16.3b's intra-version duplicate) — РОВНО одна `Notification`-строка для него (не по числу строк `PlacementAssignment`).
8. **AC-8 (регресс нулевой).** `make gate` зелёный; миграция — ТОЛЬКО добавление `ASSIGNMENT_APPROVED` в `Kind`+`CheckConstraint` (никаких новых полей на `PlacementAssignment`/`AssignmentVersion`/`SecurityEvent`).

## Out of Scope

- **`ASSIGNMENT_SUBMITTED`/`ASSIGNMENT_RETURNED`-уведомления** («approver»/«creator» нерезолвируемы сегодняшними данными, см. Scope Decision) — Story 16.6d (после 16.8 определит permission-код утверждающего/введёт `created_by`, либо получит собственное сужение).
- **Отметка ознакомления (`PlacementAssignment.acknowledged_at`)** — Story 16.6b.
- **`ACK_REQUIRED`/`ACK_MISSING_ESCALATION`-уведомления и эскалация неподтверждённых** — Story 16.6b/16.6c.
- **WS-доставка в реальном времени** — `notify()` уже публикует в WS-группу получателя on commit (E11, переиспользуется без изменений, не переоткрывается здесь).
- **API `GET /notifications`** — уже существует (5.7c), не трогается.
- **Отзыв/отмена `ASSIGNMENT_APPROVED`-уведомления** при последующей отмене мероприятия — вне объёма (тот же принцип, что 16.5's «отмена — Epic 17»).

- `apps/notifications/models.py::Notification.Meta.constraints` — `chk_notification_kind` зеркалит `Kind.values`; `test_kind_check_covers_kind_choices` (искать по имени) — гейт ловит рассинхрон.

- `docs/registries/ws-message-types.yaml::ASSIGNMENT_APPROVED` — `priority: INFO`, `recipients: "assigned employees/senior"`, `action_url: "/assignment-versions/{id}"`, `trigger: "версия утверждена"`.
