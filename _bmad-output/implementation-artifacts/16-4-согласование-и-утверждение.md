# Story 16.4: Согласование Расстановки с возвратом; утверждение one-approver + hash-ready заглушка ЭЦП

Status: ready-for-dev

## Story

As a **старший объекта / утверждающий**,
I want **подать черновик Расстановки на согласование, вернуть на доработку ИЛИ утвердить**,
so that **Расстановка проходит контролируемый жизненный цикл (FR-26), а не остаётся вечным черновиком**.

## Scope Decision (найдено при create-story)

- **Три перехода `AssignmentVersion.status`**: `submit_assignment_version()` (DRAFT→SUBMITTED), `return_assignment_version()` (SUBMITTED→RETURNED, ТЕРМИНАЛЬНО для этой версии + создаёт НОВУЮ DRAFT-версию v+1 для доработки), `approve_assignment_version()` (SUBMITTED→APPROVED, «один approver», + hash-ready заглушка ЭЦП). **Одна стори, не расщепляется** — три структурно однородных, маленьких шага одного жизненного цикла ОДНОЙ модели, переиспользующие уже установленные примитивы (`select_for_update`, override-гейт, `record()`) — тот же прецедент, что 15.3c (dual-control recon, тоже один многопереходный сервис в одной стори) и `approve_duty_plan()` (single-actor approve+idempotent+audit в одной функции).
- **«Возврат» — НЕ мутация версии на месте.** `AssignmentVersion`'s докстринг (16.1) ЯВНО заявляет версии immutable по паттерну `DailySubmission` (ARCH-DATA-021/025). Research личным чтением `amend_day()` (5.4, `apps/operations/submissions/services/amendment_service.py`) подтвердила буквальный паттерн: старая версия НЕ правится, `is_current` флипается на `False`, затем создаётся НОВАЯ строка `version=latest.version+1, is_current=True`. **`return_assignment_version()` копирует этот паттерн буквально**: `SUBMITTED→RETURNED` — статус-флип на ТЕКУЩЕЙ версии (не «редактирование содержимого», просто lifecycle-статус — не противоречит immutable-докстрингу), СРАЗУ следом — flip-before-insert (`RETURNED`-версия`.is_current=False` → `INSERT` новой `DRAFT`, `version+1`, `is_current=True`) — планировщик правит уже НОВУЮ версию, старая (`RETURNED`) остаётся аудит-следом навсегда.
- **«Один approver»** — переиспользует `approve_duty_plan()`'s single-actor паттерн (`apps/operations/duties/services.py`) буквально: НЕ dual-control (15.3c's recon-паттерн — единственный такой прецедент в кодовой базе, специально помечен как bespoke, НЕ шаблон для копирования). Идемпотентный повторный вызов на уже `APPROVED` — no-op (200, без повторного аудита), тот же паттерн, что `approve_duty_plan`.
- **`hash-ready заглушка ЭЦП`** — `architecture.md:183` явно откладывает РЕАЛЬНОЕ ЭЦП («Честно отложены: ЭЦП (OQ-1, hash-заглушка)»), implementation-readiness-отчёт: «ЭЦП (hash-ready stub)... MVP-2, обязательны». Нет НИ ОДНОГО криптографического прецедента в кодовой базе (`grep hash` по всем моделям — пусто). **Реализация — новое nullable-поле `AssignmentVersion.signature_hash`** (SHA-256 канонической JSON-сериализации `PlacementAssignment`-строк версии на момент утверждения), заполняется ТОЛЬКО при `approve_assignment_version()`. Никакой реальной подписи/PKI/внешнего сервиса — честная заглушка с явным маркером «MVP-2», не притворная интеграция.
- **Конфликты гейтят утверждение через override, не блокируют жёстко.** FR-11's гибридная модель (`epics.md:42`): hard-типы → 422 (не применимо здесь — 16.3b/16.3c's конфликты фиксированно SOFT), soft → 409+override. `error-codes.yaml`'s `SOFT_CONFLICT_DETECTED` (409, `overridable: true`) — точный прецедент. `approve_assignment_version()` ПЕРЕСЧИТЫВАЕТ конфликты СВЕЖО (`detect_placement_conflicts(version)`, не полагается на возможно устаревший прошлый прогон) ПЕРЕД проверкой — если хоть одна `PlacementAssignment.conflict_severity` непуста И `override` не передан (или `override_reason` пуст) → `SOFT_CONFLICT_DETECTED` (409). Тот же `override`/`override_reason`-паттерн, что `status_service.py`'s override-гейт.
- **Аудит — 3 новых записи** (`ASSIGNMENT_VERSION_SUBMITTED`/`_RETURNED`/`_APPROVED`), тот же `entity_type="assignment_version"`/`entity_id=uuid.UUID(int=version.pk)`-паттерн, что `PLACEMENT_DRAFT_FORMED` (16.2, единственная существующая запись Epic 16 на момент этой стори).
- **Область — сервис+модель-поле+миграция+аудит, БЕЗ API/HTTP-обёртки** (16.8) и БЕЗ реального ЭЦП (MVP-2, вне этой стори по явному указанию implementation-readiness-отчёта).

## Acceptance Criteria

1. **AC-1 (новое поле).** `AssignmentVersion.signature_hash` — `CharField(max_length=64, blank=True)` (SHA-256 hex — 64 символа), пусто до утверждения.
2. **AC-2 (подача на согласование).** `submit_assignment_version(version, *, actor)` — `DRAFT→SUBMITTED`. Повторный вызов на уже `SUBMITTED` — идемпотентный no-op. Вызов НЕ из `DRAFT`/`SUBMITTED` — `INVALID_LIFECYCLE_TRANSITION` (422).
3. **AC-3 (возврат создаёт новую версию).** `return_assignment_version(version, *, actor, reason)` — `SUBMITTED→RETURNED` на ТЕКУЩЕЙ версии (становится `is_current=False`) + СРАЗУ создаёт НОВУЮ `DRAFT`-версию (`version+1`, `is_current=True`), КОПИРУЯ все `PlacementAssignment`-строки исходной версии (планировщик правит копию, не начинает с пустого листа). `reason` — обязателен, непустой (тот же паттерн, что `amend_day`'s `reason`/`sanction`). Вызов НЕ из `SUBMITTED` — `INVALID_LIFECYCLE_TRANSITION` (422).
4. **AC-4 (утверждение — one-approver, идемпотентно).** `approve_assignment_version(version, *, actor, override=False, override_reason="")` — `SUBMITTED→APPROVED`. Повторный вызов на уже `APPROVED` — идемпотентный no-op (без повторного аудита/пересчёта hash). Вызов НЕ из `SUBMITTED` — `INVALID_LIFECYCLE_TRANSITION` (422).
5. **AC-5 (конфликт-гейт).** Утверждение СНАЧАЛА пересчитывает конфликты (`detect_placement_conflicts(version)`) — если ЛЮБАЯ строка версии несёт непустой `conflict_severity` И (`override=False` ИЛИ `override_reason` пуст) → `SOFT_CONFLICT_DETECTED` (409, `overridable: true`), утверждение НЕ происходит. С `override=True`+непустым `override_reason` — утверждение проходит НЕСМОТРЯ на конфликты, `override_reason` попадает в аудит.
6. **AC-6 (hash при утверждении).** Успешное утверждение вычисляет `signature_hash` — SHA-256 канонической JSON-сериализации `[{employee_id, post_id} for each PlacementAssignment ORDER BY id]` версии — заполняет поле.
7. **AC-7 (аудит).** `ASSIGNMENT_VERSION_SUBMITTED`/`_RETURNED`/`_APPROVED` — по одной записи на РЕАЛЬНЫЙ переход (не на идемпотентный no-op-повтор).
8. **AC-8 (регресс нулевой).** `make gate` зелёный, миграция чистая.

- Уведомления (`ASSIGNMENT_SUBMITTED`/`_RETURNED`/`_APPROVED` WS-типы уже зарезервированы в `ws-message-types.yaml`) — Story 16.6.

## Dev Notes

- `apps/operations/submissions/services/amendment_service.py::amend_day()` — буквальный образец flip-before-insert (`is_current=False` СНАЧАЛА, `create()` НОВОЙ версии ПОСЛЕ, `version=latest.version+1`), читать целиком.
- `apps/operations/duties/services.py::approve_duty_plan()` — буквальный образец single-actor idempotent approve.
- `apps/operations/statuses/services/status_service.py` — `override`/`override_reason`-гейт-паттерн (`if override and not (override_reason or "").strip(): raise DomainError("VALIDATION_ERROR", 400, ...)`), читать существующий call-сайт.
- `apps/operations/events/services.py::detect_placement_conflicts()` (16.3b/16.3c) — вызывается СНАЧАЛА внутри `approve_assignment_version()`, не полагаться на возможно устаревший прошлый прогон.
- `docs/registries/error-codes.yaml`'s `INVALID_LIFECYCLE_TRANSITION` (422) и `SOFT_CONFLICT_DETECTED` (409, overridable) — переиспользовать, не изобретать новые коды.
- `apps/operations/statuses/services/status_service.py` — `override=False, override_reason=""`-паттерн (kwarg-пара + `if override and not (override_reason or "").strip(): raise DomainError("VALIDATION_ERROR", 400, detail={"field": "override_reason"})`), встречается 3+ раз в этом файле — буквальный образец, не единичный случай.
- `apps/documents/services.py`'s `hashlib.sha256()`-использование (файловый чексум вложений) — ближайший, хоть и не строго применимый, прецедент хеширования в кодовой базе; `signature_hash` использует ту же примитив (`hashlib.sha256`), не изобретает свою криптографию.
