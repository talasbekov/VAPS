# Story 16.3c: Конфликт-детектор — несоответствие Посту (FR-25, часть 3/4)

Status: review

## Story

As a **планировщик Расстановки**,
I want **видеть, что сотрудник не соответствует требованиям Поста (рост/пол/звание/должность/допуски)**,
so that **черновик несёт видимое предупреждение до утверждения, а не тихую несостыковку (FR-25, оперативный блок 14.10)**.

## Scope Decision (найдено при create-story)

- **Часть 3/4 расщепления Story 16.3.** 16.3b (done) — двойное назначение+Отдых. Эта часть — «несоответствие Посту» из заголовка Story 16.3, единственная проверка, реально опирающаяся на «оперативный блок 14.10» (`EmployeeOperationalProfile`).
- **КРИТИЧЕСКОЕ архитектурное решение, найденное при проектировании: НЕ отдельная функция, а РАСШИРЕНИЕ `detect_placement_conflicts()` (16.3b) в том же проходе.** 16.3b's функция делает ПОЛНЫЙ пересчёт `conflict_codes` на каждый вызов (перезаписывает, не накапливает) — если 16.3c добавит ВТОРУЮ отдельную full-recompute функцию, она БЕЗ порядка вызова затрёт результаты 16.3b's проверок (двойное назначение/Отдых) при своём собственном перезаписывающем `.update()`. Единственный корректный вариант с уже выбранной архитектурой «полный пересчёт за один проход» — все проверки ОДНОГО прохода в ОДНОЙ функции, каждая добавляет свои коды в ОДИН и тот же `codes`-список ПЕРЕД записью. Эта стори РАСШИРЯЕТ существующую функцию, не создаёт новую (тот же принцип, что заявлен явно в 16.3b's Scope Decision: «shared storage… each detector appends into the same list»).
- **Cross-context чтение через `apps.core.selectors` (ARCH-004)** — `operations` не может импортировать `apps.core.models` напрямую (`test_isolation.py::test_operations_does_not_import_core_models`). Новый батч-метод `CoreEmployeeSelector.operational_profile_for(employee_ids)` (буквальный образец — `denorm_for()`, тот же селектор, одна батч-выборка, не цикл по одному сотруднику) — `apps/core/models.py`'s `EmployeeOperationalProfile`-докстринг ЛИЧНО называет себя «data for the future FR-25 post-requirement matching (Story 16.3)» — прямая, недвусмысленная цитата.
- **`Post.requirements` — ПОЛНОСТЬЮ невалидированный JSON** (14.1's Scope Decision: «validating that nested schema is a service/API concern, out of scope for this models-only story»). Эта стори — ПЕРВЫЙ реальный потребитель — читает ЗАЩИТНО: отсутствующий/неверного типа ключ = «требование не задано», НЕ падение/500 (нет данных для более строгой валидации, чем запрошено; изобретать JSON Schema-энфорсмент здесь — вне объёма).
- **Разделение источников требований**: `min_height_cm`/`gender`/`min_rank_index`/`max_rank_index`/`required_position_codes`/`allow_overqualification` — из `Post.requirements`-JSON (донор-схема); `requires_weapon`/`requires_special_equipment`/`requires_uniform` — ОТДЕЛЬНЫЕ булевы колонки `Post`, НЕ в JSON (уже существуют, `apps/operations/facilities/models.py`).
- **«Звание» vs «должность» — `Employee.rank_index` (не `Position.rank_index`), `Employee.position_code`.** Обе модели несут поле `rank_index` (звание сотрудника vs уровень штатной единицы, две разные оси) — `Post.requirements`'s `min_rank_index`/`max_rank_index` сравниваются с ЛИЧНЫМ `rank_index` сотрудника (не с уровнем его должности), т.к. `error-codes.yaml`'s описание явно разделяет «звание» и «должность» как ДВА отдельных измерения проверки.
- **`allow_overqualification` — PROVISIONAL-дефолт `True` (разрешено), если ключ отсутствует в JSON.** `error-codes.yaml`'s `OVERQUALIFICATION_DETECTED`-описание («звание... выше min_rank_index... при `allow_overqualification=false`») читается как «по умолчанию разрешено, `false` — явное ограничение» — тот же принцип, что везде в проекте: не изобретать более строгое поведение, чем прямо запрошено.
- **Отсутствие `EmployeeOperationalProfile`-строки у сотрудника** (14.10's модель — не гарантированно создана для КАЖДОГО сотрудника, 1:1 БЕЗ авто-создания) — трактуется как «все оперативные поля неизвестны» (не «сотрудник не соответствует» — недостающие данные не равны провалу проверки, та же логика, что «нет расписания — пропуск», 16.3b).

## Acceptance Criteria

1. **AC-1 (новый селектор).** `CoreEmployeeSelector.operational_profile_for(employee_ids)` — `employee_id → {rank_index, position_code, gender, height_cm, has_weapon_permit, has_uniform_issued, has_special_equipment}` (batch, одна выборка на Employee + одна на EmployeeOperationalProfile).
2. **AC-2 (рост).** `Post.requirements.min_height_cm` задан, `Employee.height_cm` меньше — `POST_REQUIREMENT_MISMATCH_CONFLICT`. `height_cm` неизвестен (нет строки/поля) — пропуск, не конфликт.
3. **AC-3 (пол).** `Post.requirements.gender` задан, не совпадает с `Employee.gender` — `POST_REQUIREMENT_MISMATCH_CONFLICT`.
4. **AC-4 (звание — недостаточное).** `Post.requirements.min_rank_index` задан, `Employee.rank_index` меньше — `POST_REQUIREMENT_MISMATCH_CONFLICT`.
5. **AC-5 (звание — избыточное).** `Post.requirements.max_rank_index` задан, `Employee.rank_index` больше, И `allow_overqualification` — `false` (явно) — `OVERQUALIFICATION_DETECTED`. `allow_overqualification` отсутствует ИЛИ `true` — не конфликт (PROVISIONAL-дефолт разрешён).
6. **AC-6 (должность).** `Post.requirements.required_position_codes` — непустой список, `Employee.position_code` не в списке — `POST_REQUIREMENT_MISMATCH_CONFLICT`.
7. **AC-7 (допуски).** `Post.requires_weapon`/`requires_special_equipment`/`requires_uniform` (отдельные колонки, не JSON) — сравниваются с `EmployeeOperationalProfile.has_weapon_permit`/`has_special_equipment`/`has_uniform_issued`; недостающий допуск — `POST_REQUIREMENT_MISMATCH_CONFLICT`.
8. **AC-8 (защитное чтение JSON).** `Post.requirements` — пустой словарь, отсутствующий ключ, ключ неверного типа (напр. `min_height_cm: "не число"`) — соответствующая проверка ПРОПУСКАЕТСЯ (не падение, не 500).
9. **AC-9 (severity — SOFT).** Все несоответствия Посту — `SOFT` (реестр не несёт HARD-вариант; согласуется с 16.3b's severity-моделью).
10. **AC-10 (расширяет, не дублирует).** `detect_placement_conflicts()` остаётся ОДНОЙ функцией — двойное назначение/Отдых (16.3b) И несоответствие Посту (эта стори) пишутся в ОДНОМ проходе, `conflict_codes` может содержать коды ОБЕИХ категорий одновременно.
11. **AC-11 (регресс нулевой).** `make gate` зелёный, миграция чистая (новых полей эта стори не добавляет — только сервис+селектор+тесты).

## Out of Scope

- Валидация/JSON Schema-энфорсмент на `Post.requirements` — не эта стори (14.1's явное решение, не переоткрывается).
- Перегрузка (`WORKLOAD_EXCEEDED_CONFLICT`) — Story 16.3d.
- Блокировка/утверждение на основе конфликтов — Story 16.4.
- Изменение `EmployeeOperationalProfile`-модели (14.10) — только чтение через новый селектор.
- Auto-создание `EmployeeOperationalProfile`-строки для сотрудников без неё — не изобретается (отсутствие данных = пропуск проверки, см. Scope Decision).
- API/HTTP-обёртка — Story 16.8.
