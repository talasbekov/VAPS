# Story 19.4a: Bulk-селектор месячного календаря статусов по сотруднику

Status: done

## Story

As a **держатель права `event.manage`/`status.view`**,
I want **получить статус сотрудника на КАЖДЫЙ день месяца ОДНИМ bulk-запросом**,
so that **будущий экран «Календарь Сотрудник × месяц» (FR-37) не породит N+1/COUNT()-в-цикле того же класса, что донор — тот же принцип, что уже действует для `overlapping_on`/`status_on`**.

## Scope Decision

- **Разбор FR-37**: `«Календарь Статусов: по Сотруднику (месяц с цветами статусов) и по Подразделению (сотрудники × дни)»` — ДВЕ независимые проекции. Эта стори строит ТОЛЬКО backend bulk-селектор для ПЕРВОЙ половины (по Сотруднику × месяц). Вторая половина (по Подразделению × дни, 19.5 — уже отдельная стори в epics.md) НЕ реализуется здесь — разные query-паттерны (один сотрудник × много дней, vs много сотрудников × дни), разный объём данных, разные тесты.
- **Backend-only, без API/экрана** — фронтенд-декомпозиция этого проекта (CLAUDE.md: API-клиент/layout/…/тесты — отдельные стори) требует НЕ смешивать backend-селектор, API-эндпоинт и React-экран в одной стори. Эта стори (19.4a) — ТОЛЬКО селектор. API-эндпоинт и экран — будущие under-19.4 стори (`19.4b`/`19.4c`+), создаются отдельно, когда придёт их очередь.
- **Живёт в `apps.operations.statuses`, не `apps.operations.load`** — FR-37 (Календарь Статусов) принадлежит домену статусов (`EmployeeStatus`, `StatusType`), а не домену нагрузки (Epic 19's `load/` app из 19.1-19.3). Несмотря на то, что обе story-серии сгруппированы в Epic 19 «Нагрузка и календари», они читают РАЗНЫЕ модели/домены — календарь НЕ импортирует `apps.operations.load`.
- **НЕ новый запрос-в-цикле** — переиспользует УЖЕ существующий `resolve_status(rows, on_date)` (`apps.operations.statuses.services.strength_report`, чистая функция без запросов к БД) буквально: ОДИН bulk-запрос (`EmployeeStatusSelector.overlapping_on`-подобный, но с диапазоном месяца, не одной датой) достаёт ВСЕ живые факты, пересекающие месяц, затем ЧИСТЫЙ Python-цикл по 28-31 дню месяца вызывает `resolve_status(rows, day)` — цикл БЕЗ дополнительных запросов к БД (тот же принцип, что `status_on`'s docstring запрещает: «MUST NOT be called in a loop» относится к `status_on`/`overlapping_on` — методам, КАЖДЫЙ вызов которых бьёт БД, а не к `resolve_status`, чистой функции).
- **Возвращает `Dict[date, str]`** (день → `status_type_code`) — ДЕНСЬ (плотный) диапазон, В ОТЛИЧИЕ от 19.1's sparse `Dict[date, Decimal]`: КАЖДЫЙ день месяца получает ключ (не только дни с фактами) — `resolve_status` уже возвращает `"IN_SERVICE"` (FR-9's дефолт) для дней без активного факта, так что плотность — естественное свойство переиспользуемой функции, не специальный код в этой стори.
- **Out of scope**: API/эндпоинт HTTP-слоя; React-экран/компонент; календарь по Подразделению (19.5); цветовая палитра статусов (уже есть `StatusType.color`, FR-39 — эта стори её не трогает, только код статуса); настройка часового пояса запроса (месяц передаётся как `year`/`month`, интерпретируется в календарных датах, без TZ-математики — `EmployeeStatus.date_start/date_end` уже `DateField`, не `DateTimeField`).

## Acceptance Criteria

1. **AC-1.** `month_calendar(employee_id, year, month)`: сотрудник с ОДНИМ статусом, покрывающим ВЕСЬ месяц → каждый день месяца в результате имеет этот `status_type_code`.
2. **AC-2.** Сотрудник БЕЗ единого факта за месяц → каждый день месяца получает `"IN_SERVICE"` (FR-9 дефолт, через `resolve_status`).
3. **AC-3.** Факт, покрывающий ТОЛЬКО часть месяца (напр. дни 10-15) → дни 10-15 несут код факта, остальные дни месяца — `"IN_SERVICE"`.
4. **AC-4.** Факт, начинающийся В ПРЕДЫДУЩЕМ месяце и заканчивающийся В СЕРЕДИНЕ запрошенного месяца (пересекает границу месяца) → дни запрошенного месяца ДО даты окончания несут код факта — подтверждает, что bulk-запрос выбирает факты по ПЕРЕСЕЧЕНИЮ с диапазоном месяца, а не по `date_start` внутри месяца.
5. **AC-5.** ДВА конкурирующих факта на один день (разные `status_type_code`, разный `priority`) → результат несёт код с МЕНЬШИМ `priority` (тот же tie-break, что `resolve_status`, — переиспользуется буквально, не переизобретается).
6. **AC-6.** Результат — плотный `dict`: количество ключей РОВНО равно числу дней в запрошенном месяце (28/29/30/31 в зависимости от месяца/года — тест на февраль високосного и невисокосного года).
7. **AC-7.** ОДИН SQL-запрос на весь вызов (`django.test.utils.CaptureQueriesContext` или `assertNumQueries` — доказывает bulk-путь, не N+1/цикл-запросов).
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Dev Notes

- `apps/operations/statuses/selectors.py:28-91` (`EmployeeStatusSelector`) — образец класса: `@staticmethod`/`@classmethod` bulk-методы, `cancelled_at__isnull=True` фильтр общий для всех. `overlapping_on(on_date, employee_ids=None)` — образец ОДНОДНЕВНОГО bulk-запроса (`period__contains=on_date`); эта стори — его многодневный аналог (`period__overlap=daterange(month_start, month_end)`, не `__contains`).
- `apps/operations/statuses/services/strength_report.py:80-109` (`resolve_status`) — ПЕРЕИСПОЛЬЗУЕТСЯ буквально, НЕ копируется/переизобретается: принимает `rows` (список dict с `status_type_code`/`date_start`/`date_end`) + `on_date`, возвращает `str`. Уже реализует priority-tie-break (AC-5) и `"IN_SERVICE"`-дефолт (AC-2) — эта стори не пишет свою версию этой логики.
- `apps/operations/statuses/models/employee_status.py:105-113` (`period`, `GeneratedField`, `daterange(date_start, date_end, '[)')`, GiST-индекс `gist_status_employee_period`) — `period__overlap=<range>` использует ТОТ ЖЕ индекс, что `period__contains` (14.x/1.5's exclusion constraint инфраструктура) — новый запрос не требует новой миграции/индекса.
- Диапазон месяца: `calendar.monthrange(year, month)` (стандартная библиотека) даёт число дней месяца (обрабатывает високосные годы автоматически) — `month_start = date(year, month, 1)`, `month_end = date(year, month, monthrange[1]) + timedelta(days=1)` (half-open, тот же `[)` паттерн, что `EmployeeStatus.period`).
- `overlapping_on`'s `values("employee_id", "status_type_code", "date_start", "date_end")` — ТОТ ЖЕ набор полей нужен `resolve_status`; новый bulk-запрос строит `.values(...)` идентичной формы, меняется только фильтр диапазона.
- Никакого нового импорта `apps.operations.load` — этот селектор НЕ пересекается с 19.1-19.3's `apps/operations/load/`.

### Completion Notes List

Реализовано по AC 1-8. `EmployeeStatusSelector.month_calendar(employee_id, year, month)` — ОДИН bulk-запрос (`period__overlap=DateRange(month_start, month_end, bounds="[)")`) + чистый Python-цикл по дням месяца, вызывающий уже существующий `resolve_status()` (без доп. запросов). `calendar.monthrange()` обрабатывает високосные годы. Обнаружено в процессе: `EmployeeStatus` несёт `ExclusionConstraint excl_hard_status_overlap` (ARCH-DATA-020) — ДВА HARD-статуса (`SICK_LEAVE`/`LEAVE_BY_REPORT`/`VACATION`/`COMMAND`) для одного сотрудника не могут пересекаться в БД; AC-5's тест на конкурирующие факты использует пару hard+soft (`SICK_LEAVE`+`DUTY`), не hard+hard — исходная версия теста (`VACATION`+`SICK_LEAVE`, оба hard) падала на `IntegrityError` от РЕАЛЬНОГО бизнес-правила, не от бага. 9 тестов (включая параметризованный на 3 варианта месяца/года для AC-6), все прошли. `make gate` — 4236 passed, 0 regressions.

**Ревью (Blind Hunter + Edge Case Hunter + Acceptance Auditor)** — все 8 AC подтверждены. Действия применены: (1) guard `1 <= month <= 12` — было: `calendar.monthrange(13, ...)` кидал невнятный `calendar.IllegalMonthError` вместо явной ошибки; (2-6) 6 регрессионных тестов на найденные пробелы покрытия — граница «факт заканчивается РОВНО на начале месяца» (симметрично уже существовавшему тесту на «пересекает с предыдущего месяца»), граница «факт начинается РОВНО в конце месяца», отменённый факт (`cancelled_at`) исключается, факты ДРУГОГО сотрудника не протекают, два несмежных факта оставляют разрыв `IN_SERVICE`, невалидный `month` кидает `ValueError`. Находка «`resolve_status` кидает `ValueError` на неизвестном `status_type_code`, роняя весь месяц» — НЕ исправлена: это существующее НАМЕРЕННОЕ поведение (`resolve_status`'s docstring: «unknown code is a programming error... a silent OTHER would mask it»), уже присущее `status_on()` для ОДНОГО дня — не новый регресс этой стори, а последовательное распространение уже принятой STOP-семантики на диапазон дней. `make gate` — 4242 passed после фикса.
