## Контекст

Стори 6.5 — сервис `issue_expense_document` (одна транзакция под
submission-локом: снапшот → release-гварды → .docx → файл+sha256+номер →
`IssuedDocument`, при amendment — «взамен исх. №») + модель с 6 констрейнтами.
HTTP-поверхности НЕТ (Д3: POST/RBAC — зона 6.10) — API-тестов нет по
определению; UI нет — браузерных E2E нет. «E2E» домена = реальный
`submit_day`/`amend_day` → выпуск → файл на диске/счётчик/аудит — dev-сьют
(16 сервисных + 10 модельных) уже несёт его. QA-проход искал оси мутационным
принципом 6.2–6.4: «какая правка прод-кода не краснит НИ ОДИН тест».

Главные находки: (1) вторая половина AC-5 — кросс-ассерт «числа контракта ==
независимому derive, расхождение = громкий отказ» — не судилась НИКЕМ:
удаление вызова `_assert_matches_derive` оставляло весь гейт зелёным (проба 1);
(2) год документа/счётчика: сегодняшний wall-clock год совпадает с годом
тестовой даты D — мутация `business_date.year` → `date.today().year`
(запрещённый ARCH-DATA-022 wall-clock) была невидима (проба 2); (3) все
dev-тесты живут в ОДНОМ подразделении — перевод счётчика §82.3 на
пер-division семантику не краснил ничего; (4) `_json_safe_findings` (UUID→str
для конверта §36) снималась без красноты — dict-сравнение равенство держит,
а `json.dumps` в 6.10 упал бы (проба 3).

## Найденные пробелы покрытия (auto-applied, gate 2095 → 2103)

Восемь судей в НОВОМ файле
`apps/operations/submissions/tests/test_document_release_qa.py` (тесты — в
app, чей код судят; мир — свои копии фикстур, канон сьютов). Прод-код,
контракт 6.3, генераторы — не тронуты.

1-3. **Дрейф билдер↔derive → громкий отказ (AC-5, вторая половина;
   параметризация ×3: totals-staff / row-vacancies / column-count).**
   Прод-билдер frozen (Ловушка №2) — дрейф имитирует monkeypatch-обёртка,
   искажающая ОДНО число контракта на каждой оси `_assert_matches_derive`.
   Судится и сам отказ (`AssertionError` с «контракт == derive»), и его
   позиция в пайплайне: ни строки, ни Attachment, ни бутстрапа счётчика,
   ни аудита DOCUMENT_* (отказ ДО траты номера и ДО файла — Ловушка №6).
4. **Счётчик — канал (doc_type, year), НЕ пер-division (§82.3).** Два
   подразделения, одна дата: номера сквозные 1→2, строка счётчика
   ЕДИНСТВЕННАЯ (last_number=2); оба выпуска ISSUED (partial-unique скоуплен
   division_id), supersede-цепи нет; у каждого свой Attachment,
   `created_by` = его actor, имя файла несёт номер ИЗ СЧЁТЧИКА
   («расход_…_исх-2.docx»), ATTACHMENT_UPLOADED — по одному на файл.
5. **Год = business_date.year, НЕ wall-clock (Д6/Ловушка №10) + rollover
   §82.3.** Зимняя сдача 2025-12-31 при wall-clock 2026: year=2025, №1, имя
   «расход_2025-12-31_исх-1.docx»; следом летний выпуск 2026 → №1 заново,
   счётчики лет независимы ({2025:1, 2026:1}); зимний выпуск НЕ вытеснен
   летним (partial-unique скоуплен днём).
6. **Малформный division_id падает громко** (`ValueError`, docstring-контракт
   uuid-коэрции) — ни строки, ни счётчика, ни аудита.
7. **`reason` аудит-строк DOCUMENT_* = reason выпускаемой сдачи**: "" у
   первого выпуска; после amendment — reason сдачи и на DOCUMENT_SUPERSEDED,
   и на новом DOCUMENT_ISSUED (снятие `reason=locked.reason` с `record()`
   было невидимым).
8. **Details отказа сходимости — JSON-safe (§36)**: `json.dumps(error.detail)`
   проходит, `division_id` финдинга — str(UUID) (опора конверта ошибок 6.10).
