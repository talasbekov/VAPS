# Story 14.11e: API — перепланирование смены дежурства

Status: ready-for-dev

## Story

As an **оператор с правом `duty.manage`**,
I want **`POST /api/operations/duty-plans/{plan_id}/shifts/{shift_id}/replan`**,
so that **смену дежурства можно перепланировать (частично изменить поля) через API, с автоматической отменой старой и созданием новой**.

`epics.md:1411` (буква, до разделения): «Story 14.11: API и экраны плана дежурств». Пятая из ~12 подсторий разделения.

## Scope Decision (найдено при create-story)

- **Тонкая HTTP-обёртка над `replan_duty_shift(shift, *, actor, reason, **new_fields)` (14.9b).** Донор молчит (как и для cancel, 14.9a/14.11d) — VAPS-оригинальная территория.
- **`replan_duty_shift()` НЕ требует собственного ревью-фикса на блокировку.** Её `transaction.atomic()` оборачивает вызов уже захарденной (14.11d) `cancel_duty_shift()`, которая делает `select_for_update()` ПЕРВЫМ действием внутри вложенного atomic-блока (вложенные `atomic()` на одном соединении — тот же уровень блокировки). Строка `values = {field: getattr(shift, field) ...}` читает поля СТАРОГО (пред-локового) объекта `shift`, но это безопасно: `cancel_duty_shift()` мутирует ТОЛЬКО `cancelled_at`/`cancelled_by`/`cancelled_reason` — ни одно из них не входит в `REPLANNABLE_FIELDS`.
- **URL — `POST .../{plan_id}/shifts/{shift_id}/replan`, зеркалит 14.11d's `cancel_shift`-паттерн буквально.** Тот же `isdigit()`-гард на `shift_id` (тот же класс бага, что 14.11d исправила).
- **Новый сериализатор `DutyShiftReplanSerializer` — ВСЕ поля кроме `reason` опциональны (`required=False`), НЕ переиспользует `DutyShiftCreateSerializer` (там все обязательны — семантика создания, не частичного изменения).** Эмпирически подтверждено (create-story): DRF's `PrimaryKeyRelatedField(required=False, allow_null=True)` корректно различает «поле отсутствует» (пропущено в `validated_data`) от «поле явно `null`» (присутствует как `None`) — соответствует `replan_duty_shift()`'s собственной семантике (14.9b: явный `None` снимает пост, отсутствие поля наследует старое значение).
- **`full_clean()`'s `django.core.exceptions.ValidationError` → DRF `ValidationError` — та же явная конвертация, что 14.11b's `_create_shift`.** `replan_duty_shift()` вызывает `new_shift.full_clean()` внутри, НЕ перехватывая `DjangoValidationError` сама — вьюха должна это сделать.
- **Коды ошибок — уже зарегистрированы, ничего нового.** `VALIDATION_ERROR`(400, неизвестное поле перепланирования ИЛИ пустая `reason`), `INVALID_LIFECYCLE_TRANSITION`(422, старая смена уже отменена/уже началась — переиспользуется `cancel_duty_shift()`'s гарды изнутри).
- **Ответ — НОВАЯ смена (`DutyShiftSerializer`), `201`.** Перепланирование создаёт РЕАЛЬНО новую строку `DutyShift` (не изменяет старую на месте) — `201`, тот же паттерн, что 14.11a/b's `create`, а не `200`, как 14.11c/d's state-transition/cancel-in-place (осознанный выбор, не диктуется существующим кодом).
- **Роут — `ops-duty-plan-replan-shift`.** Требует строку в `MATRIX`/`AUDIT_MATRIX` (существующий `_url_for()`-helper УЖЕ поддерживает 2-kwarg роуты, изменений не требует).
- **RBAC-строка/HTTP audit-логирование — 14.12.**

## Acceptance Criteria

1. **AC-1 (happy path — частичное изменение).** Требует `duty.manage`. Тело: `{"reason": "...", "starts_at": "...", "ends_at": "..."}` (только изменяемые поля). Успех — `201`, `DutyShiftSerializer` НОВОЙ смены; неуказанные поля (`employee_id`/`post`/`duty_type`/`duty_role_code`/`notes`) унаследованы от старой.
2. **AC-2 (старая смена отменена, новая спроецирована).** После вызова — старая `cancelled_at is not None`, её `EmployeeStatus`-записи сняты; новая смена имеет собственные `EmployeeStatus`-записи (`source_ref` по НОВОМУ pk).
3. **AC-3 (явный `null` снимает поле, отличается от отсутствия поля).** `{"reason": "...", "post": null, "starts_at": "...", "ends_at": "..."}` → новая смена без поста, ДАЖЕ если старая имела пост; отсутствие `post` в теле — пост наследуется.
4. **AC-4 (несуществующий план/смена → 404, оба независимо).**
5. **AC-5 (смена из ДРУГОГО плана в URL → 404).**
6. **AC-6 (нечисловой `shift_id` в URL → 404, не 500).**
7. **AC-7 (пустой `reason` → 400).**
8. **AC-8 (уже отменённая/уже начавшаяся старая смена → 422).**
9. **AC-9 (несовместимый `post`/`duty_type` (новой смены) → 400, старая смена НЕ отменена — транзакционный откат, переиспользование 14.9b's гарантии).**
10. **AC-10 (без `duty.manage` → 403).**
11. **AC-11 (регресс нулевой, `make gate` зелёный).**
