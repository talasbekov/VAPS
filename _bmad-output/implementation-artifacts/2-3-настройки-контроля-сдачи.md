# Story 2.3: Настройки контроля сдачи

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a администратор,
I want singleton-настройки контроля сдачи — `control_hour` (TimeField, default **17:00** в `Asia/Qyzylorda`) и `required_division_ids` (настраиваемый перечень UUID «необходимых управлений», flat-ссылки на `core_divisions`) — в новом вложенном app `apps.operations.submissions` (label `ops_submissions`), читаемые через `SubmissionControlSettingsSelector`,
so that светофор (5.5), блокировка «на завтра» (5.6) и beat-уведомления (5.7) имеют конфигурируемую основу — единый источник «к какому часу» и «кто обязан сдавать».

## Acceptance Criteria

1. **(AC-1) Модель + singleton.** **Given** app `ops_submissions`, **When** применяю миграцию `0001`, **Then** существует таблица `ops_submission_control_settings` с `control_hour` (TimeField, default `17:00`) и `required_division_ids` (`ArrayField(UUIDField)`, default `[]`); в БД может существовать **не более одной** строки (singleton, enforced констрейнтом); `makemigrations --check` чист; модель реэкспортирована из `models/__init__.py`; `db_table == "ops_submission_control_settings"`.
2. **(AC-2) Чтение через селектор + дефолт 17:00.** **Given** пустая БД, **When** читаю `SubmissionControlSettingsSelector.control_hour()` и `.required_division_ids()`, **Then** получаю `time(17, 0)` и `[]` (singleton лениво материализуется дефолтом); повторное чтение идемпотентно (вторая строка не создаётся). **And** при настройке трёх управлений и часа 17:00 селектор возвращает их перечень и час.
3. **(AC-3) Flat-UUID, без FK через границу.** **And** `required_division_ids` — `UUIDField`-массив (ARCH-003: cross-context = плоский UUID, НЕ FK на `core.Division`); резолв имён управлений — только через `CoreDivisionTreeSelector` (operations→core читается селектором, не моделями). AST-изоляция (`apps/core/tests/test_isolation.py`) зелёная для нового app.
4. **(AC-4) Контрольный час — config, не wall-clock.** **And** `control_hour` — конфиг-`TimeField` (значение порога), НЕ чтение часов: никаких `timezone.now()`/`date.today()` в модели/селекторе; сравнение «сейчас vs контрольный час» живёт у консьюмеров (E5) и читает время через `Clock`. Isolation-denylist не срабатывает.

## Dev Notes

### Что это за стори (суть и риск)
Низкорисковая инфра-добавка: новый вложенный app `ops_submissions` с ОДНОЙ singleton-моделью настроек + ридер-селектор. **НЕ** реализует светофор/блокировку/уведомления — только конфиг, который они (E5) прочитают. Главный риск — не «протечь» в скоуп E5 и корректно лечь на границы (flat-UUID, Clock-запрет, селектор-канал).

### Спека фиксирует СЕМАНТИКУ, но НЕ storage (важно)
В `docs/PersonnelStatus/VAPS_7.8.2.md` **нет** settings-таблицы (95 `CREATE TABLE`, ни одной про control_hour/required-divisions). 2.3 проектирует форму сам. Семантика:
- **Контрольный час 17:00 «за день вперёд»**: расход «на завтра» сдают сегодня до 17:00 накануне [Source: architecture.md:49, :287; prd.md:118 FR-18]. Часовой пояс — `Asia/Qyzylorda`, `USE_TZ=True`, business-date — локальная календарная дата [Source: VAPS_7.8.2.md:172-190]. **Один глобальный час** (не per-division) [Source: prd.md:54].
- **Необходимые управления** = настраиваемый перечень подразделений типа `management`, обязанных обновляться к контрольному часу; он же — знаменатель светофора (не в наборе → серый) [Source: prd.md:54, :207 SM-1; FR-13 prd.md:102]. Канонических дефолт-ID нет — перечень задаётся деплоем; в 2.3 дефолт `[]`, «три управления» из AC — лишь тест-фикстура [Source: epics.md:418].
- ⚠️ **Несостыковка значений** (не блокер): PRD SM-1 иллюстрирует час `09:00` [Source: prd.md:207], а epics/architecture — `17:00`. Именно поэтому час конфигурируем; seed-дефолт стори = **17:00** [Source: epics.md:414].

### Консьюмеры — OUT of scope (граница)
Светофор (5.5, `epics.md:695-704`), блокировка «на завтра» (5.6, `epics.md:706-712`, `422 TOMORROW_BLOCKED`), beat-уведомления к 17:00−N (5.7, `epics.md:714-720`) — всё Epic 5, в app `submissions`. 2.3 даёт ТОЛЬКО настройки + ридер. Сравнение «сейчас vs control_hour» и derived-блокировка — там, не здесь.

### Архитектурные правила и границы (соблюсти)
- **Flat UUID, без FK через границу** [Source: architecture.md:127, :404, :745 ARCH-003]: `required_division_ids` = `ArrayField(UUIDField)` → `core_divisions.id`. Прецедент: `EmployeeStatus.employee_id = UUIDField()` [Source: apps/operations/statuses/models/employee_status.py:15-16]. `Division` — UUID-PK (`UUIDTimeStampedModel`) [Source: apps/core/models.py:11-12, 129-147].
- **Чтение core — только селектором** [Source: architecture.md:586, :746 ARCH-004]: резолв имён/валидация дивизий — `CoreDivisionTreeSelector` (`subtree_ids`/`divisions_map`) [Source: apps/core/selectors.py:28-66], НЕ `import apps.core.models`.
- **Clock-запрет** [Source: architecture.md:300, :429 ARCH-DATA-022]: `control_hour` — это поле-конфиг (декларация `TimeField`, не вызов), денилист `test_isolation.py` ловит только *вызовы* `timezone.now`/`date.today`/… [Source: apps/core/tests/test_isolation.py:56-66, 107]. `Clock.now()`/`Clock.today_local()` [Source: apps/core/clock.py:27-40] — у консьюмеров. `TimeField` — первый в кодбазе, но полностью комплаентен.
- **Селекторы**: именованный `<Context><Domain>Selector` ВНУТРИ app [Source: architecture.md:413, :521]; god-модуль `operations/selectors.py` (легаси `OpsUserRoleSelector`) НЕ трогаем и НЕ дополняем [Source: architecture.md:594]. Девиация: list-селекторы берут `actor` первым [Source: architecture.md:451], но это singleton-config-ридер — `actor`-скоуп неприменим (config глобален); зафиксировать в докстринге.
- **Вложенный app — конвенции 2.1/2.2**: свой `migrations/`, явный `db_table`, реэкспорт в `models/__init__.py` [Source: architecture.md:581, :596], ручное имя миграции [Source: architecture.md:406].
- **TimeStampedModel** (база, BigAutoField PK + created/updated/created_by) — «no third base model» [Source: architecture.md:421; apps/operations/models.py:4-18]. Singleton накладываем `unique`-полем, не подменяя PK.

### Singleton-механика (точный рецепт)
- Поле `singleton_key = PositiveSmallIntegerField(default=1, unique=True, editable=False)` → уникальность гарантирует ≤1 строки. Селектор: `get_or_create(singleton_key=1)` — на пустой БД создаёт дефолт (`control_hour=17:00`, `required_division_ids=[]`), далее возвращает её. Альтернатива (если предпочтёшь чистый read-only селектор) — seed-команда/data-миграция создаёт дефолт-строку, селектор делает `.get(singleton_key=1)`; см. вопрос в конце.

### Project Structure Notes
- **Variance (осознанный)**: новый app = ~10 create + 1 modify (выше эвристики «≤5»), но это неустранимый минимум каркаса вложенного app (пустые `__init__`/`apps.py`/`migrations/__init__`), одна ответственность — настройки контроля сдачи. Прямой аналог создания `ops_statuses`.
- **Дом-app = `submissions`** (а не отдельный `settings`/core): архитектура размещает светофор/DailySubmission в `operations/submissions` [Source: architecture.md:524] — настройки контроля сдачи живут с будущими консьюмерами; forward-compatible с 5.2/5.5/5.6. (Решение стори — архитектура дом для settings явно не называет; см. вопрос.)

- [x] [Review][Decision] **Singleton не существует «в покое» + запись в read-пути.** `0001` — голый `CreateModel`, дефолт-строка материализуется только при первом вызове `Selector.get()` → `get_or_create` (INSERT на пути чтения).
