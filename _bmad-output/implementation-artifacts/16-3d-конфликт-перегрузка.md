# Story 16.3d: Конфликт-детектор — перегрузка (FR-25, часть 4/4)

Status: ready-for-dev

## Story

As a **планировщик Расстановки**,
I want **видеть, что назначение продолжает 3-дневную перегрузку сотрудника (>8 ч/день)**,
so that **черновик несёт видимое предупреждение до утверждения, а не тихую перегрузку (FR-25, VAPS_7.8.2 §6/BR-006)**.

## Scope Decision (найдено при create-story)

- **Часть 4/4 расщепления Story 16.3.** 16.3a (SecurityEvent-расписание) → 16.3b (двойное назначение+Отдых) → 16.3c (несоответствие Посту) → эта стори — «перегрузка» (`WORKLOAD_EXCEEDED_CONFLICT`), последний код из `docs/registries/error-codes.yaml`'s SOFT-набора, ещё не реализованный. `error-codes.yaml`: *«3 дня подряд: total_hours + новые > 8.0 (перегрузка)»* (BR-006, §6 Allowed conflict_code).
- **Та же архитектура «одна функция, один проход», что 16.3b/16.3c.** `detect_placement_conflicts()` делает ПОЛНЫЙ перезаписывающий пересчёт `conflict_codes` за вызов — вторая независимая функция стёрла бы результаты первых трёх проверок. Эта стори РАСШИРЯЕТ существующую функцию новым хелпером `_workload_conflicts(...)`, дописывающим в ТОТ ЖЕ `codes`-список, тем же принципом, что уже явно заявлен в 16.3b/16.3c's Scope Decision.
- **КРИТИЧЕСКОЕ сужение объёма, найденное при проектировании: источник `total_hours` — ТОЛЬКО `PlacementAssignment` (домен Расстановки), НЕ `DutyShift` (домен Дежурств).** `validate_duty_plan()`'s собственный докстринг (14.11f) уже называет «workload» как «Story 16.3's territory» без уточнения источника, но у Дежурств нет доступного источника ЧАСОВОГО (не календарно-дневного) объёма без нового кросс-доменного запроса за пределами уже установленных проверок: `EmployeeStatus`'s `DUTY`-проекция (14.9a, `project_duty_shift()`) хранит только `date_start`/`date_end` (`DateField`, через `_to_date_range()` — та же конвертация, что 16.3b использует для `REST_AFTER_DUTY`), БЕЗ времени начала/конца смены — календарного дня достаточно для «пересекается ли интервал», но недостаточно для «сколько часов». Читать сырой `DutyShift.starts_at/ends_at` напрямую означало бы либо игнорировать `DutyPlan.status_code` (DRAFT-планы посчитались бы как реальная нагрузка — нет прецедента, что «черновик» считается committed-часами нигде в проекте), либо изобретать новый фильтр по статусу плана — ни один из вариантов не установлен существующим кодом. **FR-32 (`Нагрузка = Дежурства + ОМ`) — ЯВНО отдельная фича (Epic 19, Story 19.1–19.3/19.6, `implementation-readiness-report`'s собственная трассировка), не эта стори.** Эта стори — узкий FR-25-срез: перегрузка ВНУТРИ домена Расстановки (несколько текущих `PlacementAssignment` одного сотрудника), не полный кросс-доменный расчёт нагрузки. Полная Дежурства+ОМ-агрегация — территория Epic 19, здесь НЕ изобретается.
- **Гранулярность часов — на уровне события (event-level), как 16.3a/16.3b.** `PlacementAssignment` не хранит собственное время — часы назначения = `event.ends_at - event.starts_at` (та же аппроксимация, что double-assignment-детектор уже использует: «event granularity, not per-assignment», явно зафлагано 16.3a). Многодневное событие (`date_start`…`date_end` шире 1 дня) вносит СВОЮ ПОЛНУЮ продолжительность в КАЖДЫЙ календарный день, который затрагивает (простейшая консервативная аппроксимация без изобретения почасового разбиения per-day — не установлено нигде в проекте, тот же принцип «не изобретать точность точнее запрошенной», что 16.3c's `Post.requirements`-чтение).
- **«3 дня подряд» — окно `[D-1, D, D+1]`, где `D` = календарный день начала события (`event.starts_at`'s локальная дата, `_to_date_range()`).** Для КАЖДОГО из 3 дней считается `total_hours(day)` = сумма продолжительностей (в часах) всех событий ДРУГИХ текущих (`is_current=True`) `PlacementAssignment` того же сотрудника, чьё `[date_start, date_end)` пересекает `day`, ПЛЮС часы САМОГО проверяемого назначения на дни, которые его событие затрагивает. `WORKLOAD_EXCEEDED_CONFLICT` — если ВСЕ 3 дня имеют `total_hours(day) > 8.0`. Отсутствие расписания у события (`event_has_schedule=False`, установлено 16.3a) — проверка ПРОПУСКАЕТСЯ целиком (та же логика, что double-assignment/rest-violation уже применяют: нет данных = недостижимо, не конфликт).
- **Внутриверсионные дубликаты (intra-version) НЕ учитываются повторно** — `intra_version_duplicates`-сотрудник уже получает `DOUBLE_ASSIGNMENT_CONFLICT` (16.3b); часы дублирующей строки того же события считались бы дважды в `total_hours`, если не исключить — исключаются явно (одна строка на событие на сотрудника при суммировании).

## Acceptance Criteria

1. **AC-1 (одиночная перегрузка одного дня недостаточна).** Ровно 1 или 2 из 3 дней окна имеют `total_hours(day) > 8.0` — НЕ конфликт (нужны все 3 подряд).
2. **AC-2 (перегрузка на всех 3 днях).** Все 3 дня окна (`D-1, D, D+1`) имеют `total_hours(day) > 8.0` (за счёт ДРУГИХ текущих назначений сотрудника + этого назначения на затронутые дни) — `WORKLOAD_EXCEEDED_CONFLICT`.
3. **AC-3 (граница — ровно 8.0 не перегрузка).** `total_hours(day) == 8.0` (не строго больше) — этот день не считается перегруженным (порог `> 8.0`, не `>=`).
4. **AC-4 (нет расписания — пропуск).** `event_has_schedule=False` для проверяемого назначения — `WORKLOAD_EXCEEDED_CONFLICT` не проверяется (нет данных, не конфликт).
5. **AC-5 (чужое событие без расписания — пропуск в сумме).** Другое текущее назначение сотрудника ссылается на событие без расписания — его событие пропускается при суммировании `total_hours` (не даёт `0` часов трактовкой «нет конфликта», а именно исключается из суммы как неопределённое).
6. **AC-6 (многодневное событие).** Событие с `date_start`…`date_end` шириной 2+ дня вносит свою ПОЛНУЮ продолжительность (в часах) в total_hours КАЖДОГО затронутого календарного дня окна.
7. **AC-7 (intra-version дубликат не задваивает часы).** Сотрудник дважды в ТЕКУЩЕЙ проверяемой версии (сценарий 16.3b's `DOUBLE_ASSIGNMENT_CONFLICT`) — часы события считаются ОДИН раз в `total_hours`, не по числу строк.
8. **AC-8 (severity — SOFT).** `WORKLOAD_EXCEEDED_CONFLICT` — `SOFT` (реестр не несёт HARD-вариант для этого кода; согласуется с 16.3b/16.3c's severity-моделью).
9. **AC-9 (расширяет, не дублирует).** `detect_placement_conflicts()` остаётся ОДНОЙ функцией — все 4 категории конфликтов (16.3b/16.3c/эта стори) пишутся в ОДНОМ проходе, `conflict_codes` может содержать коды всех категорий одновременно на одной строке.
10. **AC-10 (регресс нулевой).** `make gate` зелёный, миграция чистая (новых полей эта стори не добавляет — только сервисная логика+тесты).

## Out of Scope

- **Дежурства (`DutyShift`) как источник `total_hours`** — не эта стори (см. Scope Decision: нет доступного источника точных часов из домена Дежурств без нового, неустановленного конвент-решения по фильтрации `DutyPlan.status_code`). Полная кросс-доменная Дежурства+ОМ-нагрузка — Epic 19 (FR-32, Story 19.1–19.3/19.6).
- **Дашборд нагрузки/перегрузки** — Story 20.3.
- **Превышение предельного времени Поста** (вторая половина FR-32's «перегрузка (>3 дней подряд по 8+ ч ИЛИ превышение предельного времени Поста)») — `Post` не несёт поле предельного времени сегодня; не изобретается здесь.
- **Почасовое разбиение многодневного события по дням** — событие вносит полную продолжительность в каждый затронутый день (консервативная аппроксимация, см. Scope Decision), не пропорциональное деление.
- **Блокировка/утверждение на основе конфликтов** — Story 16.4 (уже done, конфликты некритичны для approve).
- **API/HTTP-обёртка** — Story 16.8.
- **`ServiceHours`/фактический налёт часов** (18.4) — эта проверка работает по ПЛАНОВЫМ назначениям, не по факту.
