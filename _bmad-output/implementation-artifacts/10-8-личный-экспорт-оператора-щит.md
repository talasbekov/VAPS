# Story 10.8: Личный экспорт оператора («щит») — backend API

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **Решение о разбиении (по фактам кода, не a priori):** epics.md формулирует стори как «кнопка + выгрузка» — по букве похоже на фронт+бэк в одной стори. Факт-проверка показала: (а) готового бэкенд-эндпоинта, отдающего .xlsx конкретной `DailySubmission`, **не существует** — `GET /{id}/` (5.8c) отдаёт JSON со снапшотом, но не файл; (б) xlsx-генератор 6.4 (`expense_xlsx.py`) жёстко завязан на `ExpenseDocumentData` (агрегированный расход по дереву), не на одиночный снапшот сдачи — переиспользовать напрямую нельзя, нужен новый небольшой генератор по тому же паттерну; (в) «личный» экспорт требует нового бизнес-правила (own-scope: `submitted_by == actor`), которого в `PermissionService`/`ensure_division_scope` нет — это не переиспользование существующего, а новая проверка; (г) новое действие подлежит аудиту → новый `action`-код в закрытом реестре `audit-events.yaml` (growth_rule). Совокупно это полноценная бэкенд-стори (генератор + view-action + own-guard + audit-код + RBAC-строка + `make schema`/`npm run generate:api`), которая по правилу декомпозиции (backend/frontend не смешивать, ≤5 файлов) **не может** нести ещё и фронтовую кнопку. **10.8 = ТОЛЬКО backend API экспорта.** Фронтовая кнопка «моя копия» — предложена как отдельная стори 10.8b в разделе «Открытые вопросы» ниже; она НЕ создана этой стори (policy-решение — за Bratan).

## Story

As a **оператор (держатель `daily_report.mark_update`, автор конкретной сдачи)**,
I want **HTTP-эндпоинт `GET /api/operations/daily-submissions/{id}/export/`, отдающий .xlsx-копию МОЕЙ сданной версии дня (снапшот + время сдачи + версия), с аудитом каждого скачивания**,
so that **у меня будет личное доказательство сдачи дня, независимо проверяемое (файл + запись в audit_logs), при этом чужие сдачи выгрузить нельзя — только свои**.

## Goal

Новый read-only экшен на существующем `DailySubmissionViewSet` (5.8a/b/c), который берёт уже резолвленную `DailySubmission` по pk (реюз `DailySubmissionSelector.by_id`, канон 5.8c), проверяет **own-scope** (`submission.submitted_by == request.actor_id` — ЖЁСТЧЕ, чем division-scope 5.8c: не «моё поддерево», а буквально «сдал я»), рендерит .xlsx новым генератором (паттерн 6.4, openpyxl, ленивый импорт) с данными снапшота + `submitted_at`/`version`/`event`, и логирует скачивание через `record()` (паттерн 6.7) новым кодом `DAILY_SUBMISSION_EXPORTED`.

## Scope

1. **Own-scope проверка** — новая бизнес-проверка (НЕ существует в проекте): актор может экспортировать только сдачу, где `submission.submitted_by == request.actor_id`. Это ýже, чем существующий `ensure_division_scope` (тот пускает любого держателя `daily_report.mark_update` в поддереве — «any в scope», не «own»). Чужая (по автору) сдача, даже в своём поддереве, → 403.
2. **Новый xlsx-генератор** `generate_submission_export_xlsx(submission)` в `apps/documents/generators/` (паттерн 6.4, НЕ переиспользует `expense_xlsx.py` — другой вход/контракт): титул с `business_date`/`division_id`, таблица ростера+статусов из `snapshot.roster`/`snapshot.rows`, отдельный блок «Сдано: {submitted_by}, {submitted_at}, версия {version}, событие {event}».
3. **Новый view-экшен** `@action(detail=True, methods=["get"], url_path="export")` на `DailySubmissionViewSet`: резолв `by_id` → 404 → own-guard → 403 → генерация xlsx → `record()` аудит → `FileResponse`/`HttpResponse` с `Content-Disposition: attachment`.
4. **Новый audit action** `DAILY_SUBMISSION_EXPORTED` (`entity_type=daily_submission`) в `docs/registries/audit-events.yaml` (growth_rule: тем же PR, что вводит зону) + эмиссия в сервисном/view-слое ПОСЛЕ успешной генерации, ДО отдачи байт (зеркало порядка 6.7: подготовка → аудит → отдача).
5. **RBAC-матрица**: новая строка `MATRIX["ops-daily-submission-export"]` (гейт mixin — `daily_report.mark_update`, own-guard — отдельная проверка внутри экшена, вне матрицы, зеркало паттерна `ensure_division_scope` в 5.8c).
6. **Схема**: новый эндпоинт → `make schema` (Backend) + `npm run generate:api` (frontend, регенерация `schema.d.ts` — фронтовый файл технически меняется, но это генерируемый артефакт, не ручная правка кода; фронт-функциональность НЕ добавляется).

- **Формат PDF/CSV личного экспорта** — epics AC говорит только про `.xlsx`.

## Acceptance Criteria

1. **AC-1 (own-экспорт успешен).** Given сданный день (`DailySubmission` с `is_current=True`, `submitted_by == actor`), When актор GET `/api/operations/daily-submissions/{id}/export/`, Then ответ 200, `Content-Type` xlsx-MIME, тело — валидный `.xlsx` (открывается `load_workbook`), содержит: заголовочный блок с `submitted_at` (человекочитаемый), `version`, `event`; таблицу с данными `snapshot.roster`/`snapshot.rows` (минимум сотрудник + статус-код + интервал).
2. **AC-2 (чужая сдача — 403, даже в своём поддереве).** Given `DailySubmission` с `submitted_by != actor`, When тот же держатель `daily_report.mark_update` (в том числе с доступом к дивизиону через `ensure_division_scope`) запрашивает export, Then `403 PERMISSION_DENIED` — own-guard проверяется ПОСЛЕ division-scope (division-scope 403 для чужого поддерева всё ещё первичен), но own-guard отдельно валит «своё поддерево, чужой автор».
3. **AC-3 (несуществующая/устаревшая версия).** Given несуществующий/мусорный `{id}`, Then `404 ENTITY_NOT_FOUND` (реюз `by_id`, канон 5.8c). Given `{id}` устаревшей (не is_current) версии, ПРИНАДЛЕЖАЩЕЙ актору, Then экспорт ЭТОЙ версии успешен (точечное чтение — та же семантика retrieve 5.8c, не head/latest).
4. **AC-4 (аудит скачивания).** Given успешный export (200), Then записана РОВНО ОДНА строка `AuditLog`: `action="DAILY_SUBMISSION_EXPORTED"`, `entity_type="daily_submission"`, `entity_id=submission.id`, `actor_user_id=request.actor_id`, `new_value` несёт лёгкий payload (`{division_id, business_date, version}` — БЕЗ снапшота целиком). Given отказ (403/404) ДО генерации, Then НИ ОДНОЙ строки `DAILY_SUBMISSION_EXPORTED` не записано (аудируем только состоявшийся экспорт, зеркало 6.7 AC-1).
5. **AC-5 (гейт прав, coarse).** Given аноним, When GET export, Then `403 PERMISSION_DENIED` (mixin, fail-closed). Given actor без `daily_report.mark_update` (например VIEWER), Then `403`, own-guard не достигается (coarse-гейт первичен).
6. **AC-6 (RBAC-матрица + audit-coverage).** `MATRIX["ops-daily-submission-export"]` — новая строка (`get: daily_report.mark_update`), `test_matrix_covers_every_registered_route`/`test_method_gates_cover_exactly_served_methods` зелёные. `test_audit_coverage` (facet B) видит новый литерал `DAILY_SUBMISSION_EXPORTED` в реестре (facet A: GET — не write-verb, строки не требует своей мутации, но `record()`-эмиссия в GET-пути допустима — прецедент `DOCUMENT_DOWNLOADED` 6.7 — export семантически «скачивание», не «мутация»).
7. **AC-7 (гейт/границы).** `make gate` зелёный (Postgres :5433, при занятости — :5434); `makemigrations --check` пуст (модель не меняется); `ruff check`/`ruff format` точечно по изменённым файлам; `make schema` + `npm run generate:api` выполнены после появления нового эндпоинта (AC OpenAPI-схема несёт `export`-роут); фронт НЕ затронут ничем, кроме регенерированного `schema.d.ts`.
