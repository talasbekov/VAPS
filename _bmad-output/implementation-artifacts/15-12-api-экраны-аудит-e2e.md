# Story 15.12: HTTP-уровневый e2e-тест полной цепочки ОМ «создание → потребность → выделение»

Status: ready-for-dev

## Story

As a **QA/ревьюер эпика**,
I want **один тест, который реально проходит всю цепочку ОМ через HTTP так, как это сделал бы настоящий клиент**,
so that **композиция маршрутов Epic 15 доказана целиком, а не только «каждый маршрут по отдельности»**.

## Scope Decision (найдено при create-story)

- **Story 15.12 (`epics.md:1427`)**: «API/экраны + аудит + e2e цепочки «создание → потребность → выделение»» — завершающая стори Epic 15.
- **Research-агент подтвердил (эксхаустивная сверка перед стори): API/аудит для ВСЕЙ цепочки Epic 15 УЖЕ ПОСТРОЕНЫ ПОСТРОЧНО каждой предыдущей стори (15.1-15.11).** `SecurityEventViewSet` (`apps/operations/events/api/views.py`) уже содержит ВСЕ действия цепочки как `@action`-маршруты: create → `bulletin` → `recon/confirm` (dual-control) → `staffing-demand` (PUT) → `staffing-demand/approve` → `force-requests/generate` → `GroupForceRequestViewSet.allocate`. **Изобретать/строить API заново здесь — прямой дубль-риск**, противоречащий явному тексту research-агента.
- **Аудит для цепочки УЖЕ ЗАКРЫТ.** `docs/registries/audit-events.yaml`/`test_audit_coverage.py` — единственные `_DeferredAudit` в зоне Epic 15 (`ops-security-event-checklist`, `ops-security-event-sector-posts`, `ops-security-event-staffing-demand` PUT) — уже ЯВНО задокументированное дизайн-решение прежних стори («working-draft строки, не финализированное бизнес-событие»), не забытый долг. Все РЕАЛЬНЫЕ переходы (`recon-confirm`, `staffing-demand-approve`, `force-requests-generate`, `force-request-allocate`) уже `_Audited()`. **Эта стори НЕ добавляет и не переоткрывает аудит-записи.**
- **`schema.yaml` уже полон и гейтится непрерывно** (`test_schema_drift.py`, часть `make gate` с 15.1) — не задача этой стори.
- **Фронтенд для цепочки УЖЕ ЕСТЬ** (`docs/frontend/FRONTEND_TRACEABILITY_MATRIX.md`, «Полный жизненный цикл ОМ» — по большей части «Verified», включая «Полный цикл ОМ ... кликабелен от создания до утверждения», зафиксировано 2026-07-24) и e2e-моки (`frontend/e2e-mock/security-event-lifecycle.spec.ts`, `security-event-approval-to-closure.spec.ts`) — **вопреки первоначальной гипотезе «Epic 15 — только бэкенд», фронтенд НЕ строится этой стори**.
- **Реальный, единственный незакрытый разрыв: НЕТ ни одного теста, который проходит ВЕСЬ HTTP-путь одним потоком, используя ответ каждого шага как вход следующего.** Каждый файл `apps/operations/events/tests/test_*.py` тестирует СВОЙ маршрут ИЗОЛИРОВАННО, сея фикстуры напрямую в БД (`SecurityEvent.objects.create(status_code=DEMAND)` и т.п.), а не проходя цепочку с начала через реальные HTTP-вызовы. Ни одна композиция маршрутов не доказана как работающая ВМЕСТЕ через реальный клиентский поток.
- **Стори — ЧИСТО тестовая, без изменения производственного кода.** Один новый файл теста, ноль production-файлов — по конструкции удовлетворяет «одна ответственность» (CLAUDE.md), расщепление не требуется. Если тест обнаружит реальный разрыв композиции (маршрут, не принимающий выход предыдущего), это odin отдельный баг-репорт/фикс, не причина расщеплять стори заранее.
- **Полная цепочка (единственный путь DRAFT→ALLOCATED через реальные статус-переходы, не короткий путь):** `POST /security-events` (DRAFT) → `POST .../bulletin` (BULLETIN) → `POST .../recon/confirm` ×2 РАЗНЫХ актёра (dual-control, RECON) → `PUT .../staffing-demand` (черновик потребности) → `POST .../staffing-demand/approve` (DEMAND) → `POST .../force-requests/generate` (создаёт `GroupForceRequest`, статус SENT) → `PATCH /force-requests/{id}/allocate` (ALLOCATED). На каждом шаге — реальный `APIClient`-вызов, ответ предыдущего шага (id события/id запроса) передаётся в URL следующего, не пересеян напрямую в БД.

## Acceptance Criteria

1. **AC-1 (полная цепочка одним тестом).** Один тест проходит все 7 HTTP-шагов последовательно, каждый — реальный вызов через `APIClient` (`reverse(...)`), не прямое создание модели.
2. **AC-2 (проверка состояния на каждом шаге).** После каждого шага — assert на `status_code`/поле ответа, подтверждающий реальный переход (не просто `200`).
3. **AC-3 (dual-control РЕАЛЬНО двумя разными актёрами).** `recon/confirm` вызывается ДВАЖДЫ разными `X-User-Id`, воспроизводя реальное разделение обязанностей — не сокращённый одноактёрный путь.
4. **AC-4 (аудит-трейл цепочки видим).** Финальная проверка — все РЕАЛЬНЫЕ (не `_DeferredAudit`) переходы цепочки оставили `AuditLog`-записи (минимум: `bulletin`, `recon-confirm`, `staffing-demand-approve`, `force-requests-generate`, `force-request-allocate`) — цепочка не только меняет статус, но и оставляет полный журнал.
5. **AC-5 (негативный сценарий цепочки).** Минимум один тест, доказывающий, что цепочка НЕ может «перепрыгнуть» шаг (например: `force-requests/generate` до `staffing-demand/approve` — событие ещё не в DEMAND — 4xx, не 200) — доказывает, что композиция маршрутов реально ограничивает порядок, не просто «всё разрешено».
6. **AC-6 (регресс нулевой).** `make gate` зелёный; НИ ОДИН production-файл не изменён (только новый тестовый файл).

## Out of Scope

- Изменение/добавление production-кода — реальный разрыв ТОЛЬКО в тестовом покрытии (см. Scope Decision).
- Новые аудит-записи — уже закрыто прежними стори.
- Фронтенд/frontend e2e — уже существует (см. Scope Decision), не строится здесь.
- `checklist`/`sector-posts` PUT-шаги — по дизайну прежних стори НЕ обязательны для перехода в RECON (только `bulletin`→`recon/confirm`); не включаются в «обязательную» цепочку, чтобы не изобретать несуществующее требование.
- Ретроспектива Epic 15 (`epic-15-retrospective: optional` в sprint-status.yaml) — отдельный шаг после этой стори, не её часть.
