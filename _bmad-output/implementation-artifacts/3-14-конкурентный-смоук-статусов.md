## Story

As a **система**,
I want **тест: два оператора одновременно мутируют одного сотрудника**,
so that **гонка даёт один коммит и понятный 409, не 500 и не lost update**.

## Acceptance Criteria

Источник: [epics.md#L592-598] (Story 3.14), FR-11 [epics.md#L42], ARCH-DATA-020 [architecture.md#L748], ARCH-DATA-022 [architecture.md#L750].

**Читай Решение №1 перед первой строкой кода.** Формулировка AC в epics.md («второй — 409») — до-реестровая; она верна ровно для SOFT-гонки. HARD-гонка даёт **422**.

1. **AC-1 (SOFT-гонка → 409, нет lost update).** **Given** реальный `Employee` и soft-тип `STUDY`, **When** два потока со стартом на общем барьере одновременно вызывают `create_status` с пересекающимися SOFT-интервалами, у которых `date_start <= Clock.today_local()`, **Then** ровно один поток получает `201`, второй — `409` с `error_code == "STATUS_OVERLAP_WARNING"`, `EmployeeStatus.objects.filter(employee_id=E).count() == 1`, и ни один поток не увидел `500`.
   *Почему это главный тест стори:* у SOFT-пересечений **нет DB-констрейнта** (`excl_hard_status_overlap` условен на hard-типах). Единственное, что не даёт двум soft-строкам закоммититься, — `select_for_update()` на строке сотрудника внутри `create_status`. Это и есть «не lost update».

2. **AC-2 (HARD-гонка через сервис → 422).** **Given** hard-тип `VACATION`, **When** два потока с общего барьера одновременно вызывают `create_status` с пересекающимися HARD-интервалами, **Then** ровно один `201`, второй — `422` `OVERLAPPING_HARD_STATUS`, `count() == 1`, ни одного `500`.
   *Слоение:* проигравший останавливается **пре-чеком** `_assert_no_conflict` под employee-локом; GiST-констрейнт здесь **не срабатывает** — он backstop [architecture.md#L283]. Ассерт пишем на HTTP-исход (422), а не на класс исключения — тогда тест верен при любом из двух путей.

3. **AC-3 (backstop под симметричной гонкой → 422, никогда 500).** **Given** сырые `EmployeeStatus.objects.create(...)` в обход сервиса (и, значит, в обход employee-лока), **When** два потока с общего барьера вставляют пересекающиеся HARD-интервалы, каждый через **реальный DRF-dispatch**, **Then** ровно один `201`; проигравший — `422` `OVERLAPPING_HARD_STATUS` **независимо от того, чем Postgres разрешил гонку**: `IntegrityError` с именем `excl_hard_status_overlap` **или** `OperationalError` SQLSTATE `40P01`/`40001`; `count() == 1`; ни одного `500`. Фактически сработавший путь фиксируется в Debug Log.
   *Это закрывает прямую передачу из 3.1:* «Реальный конкурентный deadlock-репро остаётся за 3.14» [3-1-domainerror-и-единый-exception-handler.md#L58,L253].

4. **AC-4 (тонкая версия в gate, без маркера).** **Given** соседняя сессия, держащая `SELECT … FOR UPDATE` на строке сотрудника, **When** в основной сессии при `SET lock_timeout = '250ms'` вызывается `create_status`, **Then** он падает с `OperationalError` SQLSTATE `55P03` (`lock_not_available`) — доказательство, что `create_status` **действительно берёт row-lock на сотрудника**. Тест **без потоков**, **без маркера** `concurrency` → исполняется в `make gate`, < 1 с.
   *Мутационная проверка (обязательна):* убрать `select_for_update()` из `CoreEmployeeLockSelector.lock_employee` → AC-4 краснеет детерминированно. Вернуть.
   ⚠️ `55P03` **не входит** в `_CONFLICT_SQLSTATES` → §36 handler отдаёт на нём `500` **по замыслу** [exception_handler.py#L94-98]. Поэтому AC-4 ассертит **сырое исключение**, не HTTP-код. НЕ «чинить» handler.

5. **AC-5 (маркер + контракт гейта).** **Given** тесты AC-1..AC-3, **Then** каждый несёт `@pytest.mark.concurrency` **и** `@pytest.mark.django_db(transaction=True)`; `make gate` их деселектит (`-m "not property and not concurrency and not slow"` [Makefile#L47]), остаётся зелёным и укладывается в бюджет 300 с (NFR-8); число `deselected` растёт **ровно на 3**. `pytest -m concurrency` прогоняется отдельно, числа — в Dev Agent Record.
   ⚠️ Маркер `concurrency` **уже зарегистрирован** [pyproject.toml#L26-30] и при `--strict-markers` повторная регистрация не нужна. **MUST NOT** править `pyproject.toml`.

6. **AC-6 (анти-ложно-зелёный).** **Given** завершённая реализация, **Then** в Dev Agent Record зафиксированы: (а) числа `make gate` (passed/deselected/секунды); (б) числа `pytest -m concurrency`; (в) результат мутационной проверки AC-4 (красный без лока, зелёный с локом); (г) `make test-full` без **новых** teardown-ERROR.

### Подводные камни (каждый из них молча зазеленит неверный тест)

1. **PLANNED-soft — это НЕ 409, а warning.** [conflict_matrix.py#L104,L112-117]: `is_planned = row["date_start"] > business_date`, и `elif is_planned: warnings.append(...)`. Если у соперника `date_start` в будущем — пре-чек проигравшего вернёт пустой `report.soft`, **обе строки закоммитятся**, и тест «пройдёт», продемонстрировав ровно тот lost update, который обязан запрещать. ⇒ В AC-1 у **обоих** писателей `date_start <= Clock.today_local()`.
2. **`clock.override()` — это `ContextVar`, он не пересекает границу потока** [clock.py#L20], [deferred-work.md#L20]. Не использовать его в потоковых тестах. Даты считать от реального `Clock.today_local()` с запасом ≥1 дня по обеим границам (иначе тест хрупок ровно в локальную полночь). Никогда не `timezone.now().date()` — это баг, уже исправленный в 3.13.
3. **`create_status` требует реального `Employee`** (`_lock_employee` → `select_for_update().get(id=...)`, иначе 404). Сеять `Organization → DivisionType → Division → Employee` + `StatusType`.
4. **Сеять до барьера, из главного потока, без `transaction.atomic()`.** Под `django_db(transaction=True)` главный поток в autocommit → `.objects.create()` коммитится и виден соединениям воркеров. Обёртка в `atomic()` спрячет данные от потоков и подвесит их на локах.
5. **`connection.close()` в `finally` каждого потока.** Django выдаёт потоку собственное соединение; утечка ломает teardown-TRUNCATE.
6. **Никогда не ассертить внутри потока** — исключение будет проглочено. Складывать в `results` / `unexpected`, ассертить после `join`.
7. **`thread.join(timeout=WAIT * 3)` + `assert not thread.is_alive()`** — зависание должно падать, а не вешать сюит. `WAIT = 10` уже определён в файле.
8. **`other_session` обязан отключить autocommit** (`conn.set_autocommit(False)`) — иначе `SELECT … FOR UPDATE` отпустит row-lock сразу по завершении стейтмента, AC-4 не дождётся таймаута и **зазеленеет ложно**. Прецедент из 3.12 брал только *advisory*-локи (они сессионные), поэтому autocommit там был безвреден — копировать фикстуру буквально нельзя.
9. **`SET lock_timeout` — сессионный на default-соединении.** Сбросить `SET lock_timeout = 0` в `finally`, иначе протечёт в последующие тесты процесса.
10. **`55P03` (`lock_not_available`) — не конфликт.** `_CONFLICT_SQLSTATES = {"40P01", "40001"}` [exception_handler.py#L98]. Через §36 handler `55P03` стал бы 500 — это сознательное сужение (правка ревью 3.1). AC-4 ассертит сырое `OperationalError`, минуя dispatch.
11. **Сид — плоским хелпером, не фикстурой с `db`.** Маркер `django_db(transaction=True)` уже поднимает БД; явный `_seed()` в теле теста снимает любые вопросы о взаимодействии `db`/`transactional_db`.
12. **`Employee.iin` уникален** — генерировать уникальный ИИН на сотрудника (в файле уже есть идиома итератора в `test_status_service.py`).
13. **`ruff`** гоняется как `ruff check .` (select = `E,F`). Идиома файла — `except Exception as exc:  # noqa: BLE001`. Форматировать **только изменённый файл**, не каталог.
