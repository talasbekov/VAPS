# Story 12.5: CHECKLIST переноса и deploy-rehearsal

Status: ready-for-dev

## Story

As a **админ, переносящий релиз в закрытый контур**,
I want **бумажный `CHECKLIST.md` (кто понёс, что проверил, версия было/стало, каким каналом переданы секреты) + интерактивный `deploy-rehearsal.sh`, логирующий каждый шаг с временем и требующий подтверждения на каждом пункте**,
so that **перенос носителем — воспроизводимая процедура, а не полагание на память оператора**.

## Acceptance Criteria

Источник: `epics.md#L1310-1316` (буква стори) + `architecture.md#L566-567` (целевой путь `deploy/CHECKLIST.md`) + `architecture.md#L643` (`make deploy-rehearsal` — «интерактивный чеклист-скрипт (логирует шаги и время)») + `deploy/.env.example`'s явно поставленный ОТКРЫТЫЙ вопрос (доставка секретов), адресованный этой стори по номеру с 12.1.

Скоуп — 4 файла (≤5, одна ответственность — процедура переноса): `deploy/CHECKLIST.md` (NEW), `deploy/scripts/deploy-rehearsal.sh` (NEW), `Backend/VAPS/config/settings.py` (MOD — см. AC-0, реальный баг, найденный при исследовании), структурный+юнит тест.

0. **AC-0 (найдено при create-story — реальный, не гипотетический баг в уже смёрженном коде).** `deploy/.env.example`'s собственный комментарий с 12.1 предписывает: многострочный PEM (`VAPS_JWT_KEY`) — ОДНОЙ .env-строкой с буквальными `\n` (docker compose's `.env`-парсер не умеет многострочные значения). Но `config/settings.py`'s `jwt_config_from_env` НИКОГДА не разэкранировал `\n` обратно в реальные переводы строк — **эмпирически подтверждено**: `cryptography`'s PEM-загрузчик реально падает `InvalidKeyError` на буквальном `\n`-варианте, работает только с реальными переводами строк. Оператор, буквально следующий существующей документации, получил бы падающую верификацию JWT на ПЕРВОМ реальном запросе (ключ читается лениво PyJWT, не при старте — тихий провал, не явная ошибка загрузки). Исправлено: `key.replace("\\n", "\n")` в `jwt_config_from_env` — безопасно и для уже-корректных многострочных значений (`.replace()` на отсутствующей подстроке — no-op).
1. **AC-1 (`deploy/CHECKLIST.md` — кто понёс, что проверил, версия было/стало, канал доставки секретов).** Таблица с колонками: `Шаг | Что делает | Кто выполнил | Время начала | Время конца | Проверено (да/нет)`. Версия «было» — НЕ ручной поиск: `install.sh`'s (12.3) `.installed-sha` — уже существующий, персистентный источник истины («было» = его содержимое ДО запуска install.sh; печатается самим install.sh как «текущая установка: X»). Версия «стало» — `manifest.json`'s `sha` (install.sh уже печатает «Бандл sha: Y»). Секреты — отдельная секция с явным чек-пунктом «каким каналом переданы (отдельный физический носитель / введены вручную с бумаги) — обвести», НЕ единственный жёсткий протокол (в проекте нет docker secrets/vault-инфраструктуры — навязывать конкретный инструмент было бы избыточным для закрытого LAN с ручным переносом; фиксация ВЫБОРА — то, что нужно для аудита).
2. **AC-2 (`deploy-rehearsal.sh` — интерактивный, лог шагов С ВРЕМЕНЕМ, локальная репетиция, НЕ 12.7).** **Скоуп-решение (буква эпика не уточняет явно, зафиксировано create-story по division-of-labor эпика):** это ЛОКАЛЬНАЯ репетиция (та же машина, засечь время + попрактиковать процедуру ДО реального переноса) — НЕ физический перенос на целевое железо (это 12.7, `RUNBOOK.md`'s буквальный рунбук, реальный бандл + FF100-смок + 4ГБ-машина). Отличается и от `restore-rehearsal.sh` (12.4 — восстановление БЭКАПА, другая забота). Явный header-комментарий в файле различает все три, чтобы не путать.
3. **AC-3 (лог — структурный столбец времени, не проза).** `deploy/spike-1.9/RUNBOOK.md`'s прецедент таблицы (Шаг/Команда/Статус/Заметка) НЕ имеет структурного столбца времени (дата — часть свободного текста в «Заметке») — эпик здесь явно требует «лог шагов **с временем**», значит нужен настоящий timestamp per-шаг, не проза. `deploy-rehearsal.sh` печатает `[HH:MM:SS] шаг N: <описание>` на каждом шаге И пишет тот же лог в файл (`deploy/rehearsal-logs/<timestamp>.log`) для последующей вставки в `CHECKLIST.md`.
4. **AC-4 (интерактивность — пауза + подтверждение на каждом пункте, «чеклист заполняется без пропусков»).** Скрипт НЕ прогоняет всё автоматически молча — на каждом шаге печатает соответствующий пункт `CHECKLIST.md` и ждёт `Enter` (или `y`) от оператора ПЕРЕД продолжением. Это и есть механизм «без пропусков» — пропустить пункт означало бы не нажать продолжение, скрипт просто ждёт.
5. **AC-5 (репетиция — реальные шаги `install.sh`'s последовательности, не воображаемые).** `deploy-rehearsal.sh` идёт по ТЕМ ЖЕ логическим шагам, что `install.sh` (12.3): sha-check бандла → бэкап → load → up → smoke → фиксация install-sha — но выполняет их РЕАЛЬНО (не «представь, что...») на локальной машине под ОТДЕЛЬНЫМ compose-проектом (`vaps-deploy-rehearsal` — третье уникальное имя, не `vaps-install`/`vaps-restore-rehearsal`/generic `deploy`).
6. **AC-6 (регресс нулевой + реальный прогон).** Дев-агент реально прогоняет `deploy-rehearsal.sh` целиком (включая подтверждения — можно скриптовать `yes`/pipe для неинтерактивного авто-прогона в целях теста), проверяет лог-файл содержит временные метки на каждом шаге, стек убран под правильным именем. `make gate` зелёный.

## Dev Notes

- **AC-0 — реальный баг, не гипотетический.** Эмпирически проверено (create-story): `cryptography`'s PEM-парсер падает `InvalidKeyError` на буквальном `\n`-варианте ключа, работает только на реальных переводах строк. Без этого фикса JWT-верификация в проде НИКОГДА бы не заработала при следовании собственной документации `.env.example`.
- **Три «rehearsal»-скрипта в `deploy/scripts/` — разные заботы, разные имена compose-проектов.** `restore-rehearsal.sh` (12.4) — восстановление БЭКАПА в изолированный стек. `deploy-rehearsal.sh` (эта стори) — практика ПОСЛЕДОВАТЕЛЬНОСТИ install.sh с засечкой времени, локально. Полная физическая репетиция на целевом железе — 12.7, отдельная стори, реальный рунбук `RUNBOOK.md`. Не смешивать имена/скоупы — каждый явно документирует отличие от других двух.
- **«Было/стало» — не ручной поиск.** `install.sh`'s (12.3) `.installed-sha`-маркер уже несёт «было», `manifest.json`'s `sha` — «стало», ОБА уже печатаются install.sh'ом в свой stdout («текущая установка: X», «Бандл sha: Y») — `CHECKLIST.md` инструктирует переписать их ИЗ ВЫВОДА install.sh, не искать заново.
- **Секреты — фиксация выбора, не навязанный протокол.** В проекте нет docker secrets/vault (философия «нет лишней инфраструктуры», уже установленная другими сторями сессии). CHECKLIST.md документирует ДВЕ реалистичные опции для закрытого LAN с ручным переносом (отдельный физический носитель / ручной ввод с бумаги) и требует ОТМЕТИТЬ, какая использована — открытый вопрос закрыт процедурно, не техническим протоколом, которого проект сознательно не строит.
