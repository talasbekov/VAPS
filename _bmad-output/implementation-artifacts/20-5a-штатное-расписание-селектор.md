# Story 20.5a: Отчёт «штатное расписание» — агрегатный селектор (Division × Position)

Status: done

## Story

As a **держатель права `status.view`/кадровик**,
I want **получить штатное расписание (по управлению И должности: сколько единиц выделено / занято / вакантно) ОДНИМ bulk-вызовом**,
so that **FR-40's «отчёт «штатное расписание»» закрыт данными, которых СЕЙЧАС нигде в проекте не существует в нужной детализации — ни `StrengthReportService` (только по управлению, без разбивки по должности), ни `allocated_slots_on()` (тоже только по управлению)**.

## Scope Decision

- **Разбор FR-40/эпика**: «штатное расписание» — классический кадровый документ: строка = (управление, должность), колонки = «по штату» (allocated)/«по списку» (filled)/«вакансии» (vacant). Исследованием подтверждено: НИ ОДНА существующая функция не даёт эту детализацию — `StrengthReportService.compute()` (Epic 19/20.2a) агрегирует ТОЛЬКО по управлению (`DivisionReportRow`, без должности); `CoreStaffingSelector.allocated_slots_on()` тоже только по управлению (читает `DivisionHistoricalSlot`, не `StaffingSlot`); `compute_free_slots()` (`apps/core/services.py`) — per-slot список ВАКАНСИЙ одного управления, не агрегат по должностям, не bulk по многим управлениям. Эта стори строит НОВУЮ агрегацию, а не переиспользует существующую (в отличие от 20.1a/20.2a/20.3a).
- **`compute_staffing_table(business_date, division_ids=None)`** — НОВАЯ функция в `apps/core/selectors.py` (`CoreStaffingSelector`, дополняет существующий класс — та же граница домена, что `allocated_slots_on()`, обе про штат). ДВА bulk-запроса (не N+1 по управлениям/должностям):
  1. `StaffingSlot` (активные, валидные на `business_date`) → `GROUP BY (division_id, position_code)`, `COUNT` — «по штату» (allocated).
  2. `EmployeeStaffingAssignment` (активные на `business_date`, чей `staffing_slot` тоже активен/валиден на ту же дату) → `GROUP BY (staffing_slot__division_id, staffing_slot__position_code)`, `COUNT` — «по списку» (filled).
- **Дата-математика — тот же приём, что `allocated_slots_on()`**: `local_midnight(business_date)` (не наивное сравнение `date` с `DateTimeField`, тот же паттерн, что уже установлен в этом же классе).
- **`vacant = allocated - filled`** (никогда не может быть меньше 0 по построению: `EmployeeStaffingAssignment.staffing_slot` — FK на КОНКРЕТНЫЙ `StaffingSlot`, один слот не может иметь больше активных назначений, чем... — ПРОВИЗИОНАЛЬНО принято: если `filled > allocated` для какой-то строки — ПРИЗНАК ДАННЫХ (двойное занятие одного слота, не должно происходить по бизнес-правилам, но эта стори НЕ гейтит это как ошибку/исключение, отчёт просто покажет отрицательное число как есть — честный симптом проблемы данных, не скрывать).
- **Возвращает `List[Dict]`**: `{"division_id": UUID, "position_code": str, "position_name": str, "allocated": int, "filled": int, "vacant": int}` — ОДНА строка на КАЖДУЮ (управление, должность)-комбинацию, где `allocated > 0` (штатных единиц без должностей в штатном расписании быть не должно — комбинации `filled>0`/`allocated=0` теоретически возможны при рассинхроне данных, но включаются в результат явно, не отбрасываются молча).
- **`division_ids=None` → весь орг** (тот же дефолт, что `allocated_slots_on`/`StrengthReportService.compute`).
- **Out of scope**: API/эндпоинт HTTP-слоя; экран/печатная форма отчёта (будущая стори); экспорт в `.csv`/`.xlsx` (20.4-семейство, отдельная интеграция при явном запросе); сортировка/группировка вывода (плоский список, сортировка — фронтенд/API-слой); историческая генерация «штатное расписание НА дату в прошлом с учётом уволенных сотрудников» сверх уже данной семантики `EmployeeStaffingAssignment`-интервалов (эта стори просто читает интервалы как есть).

## Acceptance Criteria

1. **AC-1.** Управление с 3 выделенными единицами должности «Инспектор» (3 `StaffingSlot`), 2 из которых заняты (`EmployeeStaffingAssignment` активны на дату) → строка `{allocated: 3, filled: 2, vacant: 1}`.
2. **AC-2.** Должность с `allocated=0` (все слоты неактивны/невалидны на дату), но с активным назначением на ОДИН из ЭТИХ слотов (данные рассинхронизированы) → строка присутствует явно с `filled=1, allocated=0, vacant=-1` (не скрывается, не гейтится исключением).
3. **AC-3.** Слот, чей `valid_to <= business_date` (истёк) → НЕ учитывается в `allocated` для этой даты.
4. **AC-4.** Назначение (`EmployeeStaffingAssignment`), чей `ends_at <= business_date` (завершено) → НЕ учитывается в `filled`.
5. **AC-5.** ДВА разных управления с одинаковым `position_code` → каждое получает СВОЮ строку (изоляция по `(division_id, position_code)`, не смешивание должностей между управлениями).
6. **AC-6.** `division_ids=[div_a]` (сужение) → результат содержит ТОЛЬКО строки этого управления, другие управления не встречаются.
7. **AC-7.** РОВНО ДВА SQL-запроса на вызов (`assertNumQueries(2)`/`CaptureQueriesContext`), независимо от числа управлений/должностей — доказывает bulk-путь (`GROUP BY`, не построчный Python-цикл с запросом на слот).
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Валидация/исправление рассинхронизированных данных (`filled > allocated`) — отчёт показывает как есть.

## Dev Notes

- `apps/core/selectors.py:328-352` (`CoreStaffingSelector.allocated_slots_on`, существующий) — СТРУКТУРНЫЙ образец: `local_midnight(business_date)`, `Q(valid_to__isnull=True) | Q(valid_to__gt=t)` — БУКВАЛЬНО тот же паттерн для `StaffingSlot.valid_from`/`valid_to` в новой функции (те же имена полей, та же семантика интервала).
- `apps/core/models.py:370-390` (`StaffingSlot`) — `division` (FK), `position_code` (FK на `Position`), `is_active`, `valid_from`/`valid_to` (DateTimeField). Группировка: `.filter(is_active=True, valid_from__lte=t).filter(Q(valid_to__isnull=True)|Q(valid_to__gt=t)).values("division_id", "position_code").annotate(allocated=Count("id"))`.
- `apps/core/models.py:407-421` (`EmployeeStaffingAssignment`) — `staffing_slot` (FK на `StaffingSlot`), `starts_at`/`ends_at` (DateTimeField). **Реализовано (правка при разработке, найдено red-phase тестом AC-2)**: `filled` считается ТОЛЬКО по активности САМОГО назначения (`starts_at__lte=t, (ends_at__isnull=True | ends_at__gt=t)`) — БЕЗ доп. фильтра на текущую активность/валидность слота (`staffing_slot__is_active`/`valid_from`/`valid_to`). Первоначальный план добавить зеркальный фильтр на слот был ОШИБОЧЕН: он исключил бы ровно тот AC-2 рассинхрон-сценарий («слот стал неактивным ПОСЛЕ назначения»), который эта стори обязана честно показать — фильтр на слот молча убирал бы занятую единицу из `filled` вместо отрицательного `vacant`.
- Группировка второго запроса: `.values("staffing_slot__division_id", "staffing_slot__position_code").annotate(filled=Count("id"))` — имена ключей результата будут `staffing_slot__division_id`/`staffing_slot__position_code` (Django `.values()` convention), нормализовать до `division_id`/`position_code` при мёрдже в Python-словарь.
- **Мёрдж allocated+filled**: `Counter`/`defaultdict` по ключу `(division_id, position_code)` — объединение ДВУХ множеств ключей (из allocated-запроса И из filled-запроса, см. AC-2 — ключ может быть ТОЛЬКО в filled, если данные рассинхронизированы), `.get(key, 0)` для отсутствующей стороны.
- **CAVEAT для будущего потребителя (ревью, Edge Case Hunter)**: `division_id` в обоих запросах — ТЕКУЩЕЕ подразделение слота (`StaffingSlot.division`, live-join), не подразделение НА `business_date` — `StaffingSlot.division` изменяем (PATCH через API, `personnel.edit`). Для сегодняшней/будущей даты это не проблема; для запроса «штатное расписание на дату В ПРОШЛОМ» ПОСЛЕ того, как слот сменил подразделение, оба счётчика (`allocated`/`filled`) прикрепятся к НЫНЕШНЕМУ подразделению слота, не к тому, в котором он состоял на `business_date` — тот же класс допущения, что уже явно исключён в Out of Scope («историческая генерация... эта стори просто читает интервалы как есть»), но здесь явно проговорено для будущего 20.5b (API-слоя), если тот когда-нибудь предложит выбор даты в прошлом.
- `apps/core/models.py:114-128` (`Position`) — `code`/`name`. Имя должности разрешается ОДНИМ доп. запросом `Position.objects.filter(code__in=<все встреченные position_code>).values_list("code", "name")` — это ТРЕТИЙ запрос, НЕ второй/не входит в AC-7's «ровно 2»; ЛИБО избежать третьего запроса, обогатив `position_name` через `.values("position_code__name")` в ПЕРВОМ (allocated) запросе (Django `.values()` умеет джойнить FK-поле напрямую — `position_code__name` не требует отдельного запроса) — ПРЕДПОЧТИТЕЛЬНЫЙ путь, держит AC-7's «ровно 2» буквально. Для строк, которых нет в allocated (AC-2's рассинхрон-случай), `position_name` может быть `None`/резолвиться отдельно — не блокирует AC-7 (редкий edge-case, не на hot path).
- `apps/core/services.py:131-148` (`compute_free_slots`, существующий) — НЕ переиспользуется буквально (та функция — per-slot список ОДНОГО управления, эта стори — bulk-агрегат по многим), но её date-условия («активный слот» + «занятость по `EmployeeStaffingAssignment`») — тот же СМЫСЛОВОЙ инвариант, сверить семантику дат один-в-один при написании тестов (не переизобретать бизнес-правило «когда слот занят»).
