# Story 14.10: Оперативный блок карточки

Status: ready-for-dev

## Story

As a **разработчик**,
I want **модель `EmployeeOperationalProfile` (антропометрия/допуски/оружие/форма/знание объектов) 1:1 к `Employee`**,
so that **«Карточка Сотрудника» (FR-3) имеет оперативный блок данных, готовый послужить источником для FR-25's будущей проверки соответствия сотрудника требованиям поста (16.3)**.

`epics.md:1410` (буква): «Story 14.10: Оперативный блок карточки (FR-3: антропометрия, допуски, оружие, форма, знание объектов — данные для FR-25)». FR-3 (epics.md:32): «Карточка Сотрудника: кадровый блок + оперативный блок... блоки по правам».

## Scope Decision (найдено при create-story)

- **Донор НЕ даёт схему для этого блока.** Полный грep донор-документа — ни одной таблицы `ops_employee_*` под антропометрию/допуски/оружие/форму/знание объектов; эти поля упоминаются ТОЛЬКО как redaction-список для печатных форм (`BR-POST-003`, «не выводить... расширенную антропометрию»). Единственная реальная таблица в этой смысловой зоне — `ops_employee_service_hours` (рейтинг/налёт часов, `BR-RATING-*`) — принадлежит Epic 19 (`Story 19.6: Налёт часов в карточке сотрудника`), НЕ этой стори. **Заказчик подтвердил при create-story**: строить оперативный блок буквально по epics.md's перечислению полей, несмотря на отсутствие донор-схемы — это решение зафиксировано здесь, не пересматривается без явного нового запроса.
- **Модель — в `apps.core`, НЕ `apps.operations`.** «Карточка Сотрудника» — это `Employee` (`apps/core/models.py`), уже несущая «кадровый блок» (ФИО, ИИН, звание, должность, `height_cm` и т.д.). Оперативный блок — 1:1 расширение ТОЙ ЖЕ карточки, тем же паттерном, что `UserEmployeeBinding` (существующий `OneToOneField` к `Employee` внутри `core`). `apps/core/tests/test_isolation.py::test_core_does_not_import_other_context_models` явно запрещает `core`'у импортировать `apps.operations` (и другие контексты) — размещение в `operations` было бы архитектурно неверным для данных, которые логически принадлежат самой карточке.
- **«Знание объектов» — плоский список кодов, НЕ FK/M2M на `facilities.Object`.** Прямое следствие предыдущего пункта: `core` не может ссылаться на `operations.facilities.Object`. `known_object_codes` — `JSONField(default=list)`, список строк-кодов объектов (тот же класс «плоской кросс-контекстной ссылки», что `ObjectPassport.responsible_employee_id` в обратную сторону, ARCH-007).
- **Поля — VAPS-оригинальный дизайн, документированный явно (не донор-литерал).** Без донор-схемы поля спроектированы по буквальному перечислению epics.md's заголовка:
  - антропометрия → `weight_kg` (доп. к уже существующему `Employee.height_cm`, не дублируется);
  - допуски → `clearance_level` (свободный текст-код, нет донор-перечисления допустимых значений — не вводится закрытый enum без опоры);
  - оружие → `has_weapon_permit` + `weapon_permit_expires_at` (зеркалит `Post.requires_weapon`'s булеву семантику + типовой срок действия допуска);
  - форма → `has_uniform_issued` (зеркалит `Post.requires_uniform`);
  - (доп., зеркалит `Post.requires_special_equipment`, тот же смысловой набор «может ли сотрудник закрыть требования поста») → `has_special_equipment`;
  - знание объектов → `known_object_codes` (см. выше).
- **`SensitiveFieldPolicy` (существующая модель `core`) — «блоки по правам»'s инфраструктура уже существует, эта стори её НЕ трогает.** FR-3's «блоки по правам» (RBAC-гейтинг видимости полей карточки) — API/serializer-слой, вне этой (models-only) стори; `SensitiveFieldPolicy` уже в `apps/core/models.py` как соответствующий механизм для будущей API-стори.
- **Только модель+миграция+тесты. Никакой service/selector/API-логики.** FR-25's полная проверка соответствия (Post-требования vs операционный блок) — `Story 16.3`, явно ссылающаяся на «оперативный блок 14.10» как на источник данных (epics.md:1433) — эта стори лишь СОЗДАЁТ данные, не строит логику сопоставления.
- **Admin — НЕ регистрируется.** Тот же аргумент, что для растущих бизнес-моделей в `facilities` (14.1-14.4): персональные операционные данные сотрудника, не справочник.

## Acceptance Criteria

1. **AC-1 (модель `EmployeeOperationalProfile`).** `apps/core/models.py`: `OneToOneField(Employee, on_delete=PROTECT, related_name="operational_profile")`, `weight_kg` (`PositiveSmallIntegerField(null=True, blank=True)`), `clearance_level` (`CharField(max_length=100, blank=True)`), `has_weapon_permit` (`BooleanField(default=False)`), `weapon_permit_expires_at` (`DateField(null=True, blank=True)`), `has_uniform_issued` (`BooleanField(default=False)`), `has_special_equipment` (`BooleanField(default=False)`), `known_object_codes` (`JSONField(default=list, blank=True)`).
2. **AC-2 (`db_table`, `verbose_name`).** `db_table="core_employee_operational_profiles"`.
3. **AC-3 (`PROTECT` на `Employee`).** Тот же паттерн, что везде в кодовой базе для «не должно исчезнуть молча» — сотрудник не может быть удалён, пока у него есть операционный профиль (мягкое увольнение — `EmploymentStatus`, не хард-delete, так что это защита от редкого прямого `Employee.objects.filter(...).delete()`).
4. **AC-4 (`weapon_permit_expires_at` требует `has_weapon_permit=True` — DB `CheckConstraint`).** `CHECK (has_weapon_permit=True OR weapon_permit_expires_at IS NULL)` — дата истечения допуска без самого допуска бессмысленна.
5. **AC-5 (одна карточка — один профиль).** `OneToOneField` сам обеспечивает уникальность на уровне БД.
6. **AC-6 (изоляция).** `apps/core/tests/test_isolation.py::test_core_does_not_import_other_context_models` проходит без изменений — новая модель не импортирует `apps.operations`.
7. **AC-7 (регресс нулевой, `make gate` зелёный).**

## Out of Scope

- Логика сопоставления «сотрудник соответствует требованиям поста» (FR-25) — `Story 16.3`.
- API/сериализаторы/RBAC-гейтинг видимости полей («блоки по правам») — будущая API-стори, использует существующий `SensitiveFieldPolicy`.
- `ops_employee_service_hours`/рейтинг/налёт часов — `Story 19.6` (Epic 19), другая сущность.
- Admin-регистрация — не строится (персональные операционные данные).
