# Story 10.2b: Обратный канал маркеров в грид

Status: done

## Story

As a **оператор управления**,
I want **видеть КОНКРЕТНЫЕ строки грида, отклонённые bulk-ответом (жёлтая/красная заливка), а не только текст в инлайн-панели ниже грида**,
so that **не искать сотрудника по ФИО в списке причин — конфликтная строка подсвечена там же, где я её редактирую**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/10-2-экран-массового-обновления.md:34,255` ("Обратный канал маркеров в строки грида (serverMarkers-проп)... вынесен в 10.2b"); `epic-9-retro-2026-07-14.md:52` ("onCellCommit-seam непригоден по направлению данных для bulk-ответа... 10.2 обязана заложить обратный канал (markers-проп/императивный ref)").

1. **AC-1 (bulk-отказ красит строки грида).** Given bulk-отправка вернула 409/422 с `detail.rows[]`, When ответ приходит, Then КАЖДАЯ строка грида, чей `employee_id` есть в `rows[]`, получает маркер: `http_status===422` → `'hard'` (красная заливка), `http_status===409` → `'soft'` (жёлтая заливка) — тот же визуальный язык, что клиентский `markers`-стейт (9.5/9.6, `MARKER_ROW`).
2. **AC-2 (маркер снимается редактированием той же строки).** Given серверный маркер на строке, When оператор редактирует ИМЕННО эту строку (коммит ячейки), Then маркер сменяется на клиентский вердикт этого коммита (invalid/soft/hard/чисто) — существующий `setMarker`/`clearMarker`-путь `validateAndMark` НЕ переписывается, серверный маркер просто оказывается в ОДНОМ и том же `markers`-стейте и естественно перезаписывается следующим коммитом той же строки.
3. **AC-3 (маркер снимается новым УСПЕШНЫМ submit).** Given предыдущий отказ оставил серверные маркеры, When следующая отправка возвращает 201, Then все серверные маркеры исчезают (bulk успешен — 0 rows osталось отклонённых).
4. **AC-4 (маркер снимается новым submit БЕЗ конкретной строки в отказе).** Given предыдущий отказ пометил строки A и B, When следующая отправка отказывает СНОВА, но теперь только строка A в `rows[]` (B исправлена), Then маркер B снимается, маркер A остаётся/обновляется — прунинг устаревших, не просто добавление новых (тот же паттерн, что прунинг маркеров при смене `rows`-пропа, 9.5/9.6).
5. **AC-5 (не переписывает существующий `onCellCommit`-seam).** `onCellCommit` (9.6, синхронный per-cell seam) остаётся НЕТРОНУТЫМ — `DailyUpdatePage` по-прежнему НЕ передаёт его (сетевой вызов на строку недопустим, defer 9.6). `serverMarkers` — НОВЫЙ, независимый проп с другим направлением данных (async, ПОСЛЕ bulk-ответа, не на каждый коммит ячейки).
6. **AC-6 (инлайн-панель остаётся — не заменяется).** Текстовая детализация (AC-8/9 стори 10.2, номер строки+ФИО+причина) остаётся как есть — маркеры ДОПОЛНЯЮТ, не заменяют (EXPERIENCE.md#L238: цвет никогда не единственный сигнал — уже соблюдено инлайн-панелью).
7. **AC-7 (регресс нулевой).** Прямой рендер `DailyGrid` без `serverMarkers`-пропа (существующие E9-тесты) — без изменений поведения (проп опциональный, дефолт `undefined`/пустой объект = маркеры не трогаются). `npm run gate` зелёный.

## Dev Notes

- **Почему НЕ через `onCellCommit`**: тот seam синхронный, зовётся В МОМЕНТ коммита ОДНОЙ ячейки — bulk-ответ приходит асинхронно ПОСЛЕ `onBulkSubmit`, когда фокус мог уйти на другую строку (ретро E9 AI явно называет это несовместимым по направлению данных). `serverMarkers` — отдельный, императивный по духу канал: родитель диктует набор id→маркер, грид синхронизирует свой внутренний `markers`-стейт эффектом.
- **Один и тот же `markers`-стейт, не два параллельных.** Серверные и клиентские маркеры живут в ОДНОМ `Record<string, RowMarker>` (`useState` внутри `DailyGrid`) — не заводится отдельный "serverMarkers-стейт" для визуального слияния (упростило бы на бумаге, но раздвоило бы источник истины для `MARKER_ROW`-рендера и `blockedCount`-подсчёта на кнопке отправки). `serverMarkers`-ПРОП — вход синхронизации, не параллельное состояние.
- **Прунинг, не просто добавление** (AC-4) — критично: без diff-против-предыдущего-пропа исправленная строка B осталась бы жёлтой/красной НАВСЕГДА после первого отказа, пока оператор её вручную не отредактирует (маркер не самоочищается временем/следующим успешным submit'ом чужой строки).
- **`useMemo` на стороне `DailyUpdatePage` для `serverMarkers`** — обязателен: без него `rowErrors.map(...)` строил бы новый объект-литерал на КАЖДЫЙ рендер экрана, `useEffect` в `DailyGrid` триггерился бы избыточно (не баг per se — эффект идемпотентен, — но лишняя работа и потенциальная путаница при отладке).
