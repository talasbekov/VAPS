## Story

As a **разработчик**,
I want **проверить и задокументировать поведение системы при переводе часов назад, прыжке вперёд и тихом дрейфе часов сервера контура без NTP**,

   - **Верхнего sanity-потолка на `N` нет; гарда `--today` на CLI нет** (команда не принимает аргументов [catchup_status_effects.py#L9]). Beat-путь читает `Clock.today_local()` — CLI-гард его в принципе не покрыл бы.

   - **Триггер, когда риск становится настоящим:** заполнение сеймов — E4 (`AuditLog`, стори 4.1) и E5 (уведомления, стори 5.7). До этого момента процедура восстановления дёшева — поэтому рунбук пишется **сейчас**.
   - После коррекции часов назад `today < watermark` → **бессрочный halt** до момента, когда реальное время догонит отравленный watermark. Это и есть цена forward-прыжка.

### Точная механика на этой ветке (проверено чтением кода, `63842c3`)

- **Алерт:** `logging.getLogger(__name__)` → имя логгера **`apps.core.clock`**; уровень **ERROR**; сообщение ровно `clock behind watermark: catch-up halted`; `extra={"watermark": …isoformat(), "today": …isoformat()}` [clock.py#L91-L94]. Единственное место в проекте со структурированным `extra=`. Отдельной alert-абстракции/канала **нет** — в закрытом контуре внешних каналов нет вовсе [prd.md#L174]; «алерт» = ERROR-запись [epics.md#L304: «пишется алерт-лог»] + ненулевой exit команды.
- **`catchup_plan` отдаёт `[]` для ТРЁХ разных случаев** (`today < watermark`, `today == watermark`, `watermark is None`) → по пустому списку halt **не отличить**; раннер обязан сравнивать сам [tasks.py#L84-L90]. Алерт пишется только для первого; `watermark is None` — молча [clock.py#L88-L89].
- **Порядок в раннере:** `advisory_lock` → (не взят → `locked`) → **единственное** чтение wall clock `Clock.today_local()` → `read_watermark` → (None → `bootstrap` → выход) → `catchup_plan(...)` (**зовётся ДО halt-проверки — чтобы сработал ERROR-лог**) → `today < watermark` → `halted` → пустой план → `noop` → кап 400 + WARNING → цикл: `transaction.atomic(){ materialize_day_effects(day); advance_watermark(to=day) }`.
- **`advance_watermark` строго вперёд:** `to <= current` → `ValueError` [watermark.py]. Тихий откат watermark назад невозможен из кода — только руками через SQL (Вариант C рунбука).
- **`materialize_day_effects` — NO-OP** [effects.py#L38-L47]: `record_catchup_audit` (E4) и `emit_catchup_notifications` (E5) возвращают `None`. **Отсюда:** «данные не перезаписываются» сегодня доказывается тем, что (1) эффекты не вызваны и (2) watermark не сдвинут; никаких бизнес-строк раннер не пишет **в принципе**.
- **`Watermark.updated_at = auto_now=True`** [core/models.py] → Django пишет `django.utils.timezone.now()`, т.е. **реальные OS-часы мимо `Clock`**. AST-гард `test_no_wall_clock_reads_in_domain_layers` это **не ловит** (`auto_now` — kwarg, не вызов). Следствие для рунбука: при перекосе часов `updated_at` идёт за перекошенными часами и **не годится как источник истины при разборе инцидента**.
- **tz:** `settings.TIME_ZONE = VAPS_LOCAL_TIMEZONE = "Asia/Qyzylorda"`, `USE_TZ=True` [config/settings.py#L86-L87]. Канарейка `apps/core/tests/test_tzdata_canary.py` (3 теста: лето/зима `+05:00` + `settings.TIME_ZONE`). Ловушка из 1.9 §2.4: dev-хост может быть `Asia/Almaty` (тоже +05) — канон **`Asia/Qyzylorda`**; контейнер живёт в **UTC**.
- **`today_local()` = календарная дата в `Asia/Qyzylorda`** [clock.py#L37-L40]. Отсюда режим (г): дрейф **на часы**, пересекающий полночь, сдвигает `today_local()` на сутки — этого **достаточно**, чтобы материализовать завтрашний день сегодня, увести watermark на день вперёд и получить halt после коррекции. Большой прыжок не нужен.

### Расчёт blast radius forward-прыжка (в `FINDINGS.md` — числами)

`watermark = W`, часы прыгнули на `N` дней вперёд (`today = W + N`):
1. План `(W, today]` = `N` дат. За прогон обрабатывается `min(N, 400)`; при `N > 400` — `logger.warning` + `remaining = N − 400`, watermark → `W + 400`.
2. Следующие прогоны продолжают (**кап — не стоп**), пока `watermark == today`. Итог: материализованы **все `N`** «будущих» дней.
3. Сегодня эффекты NO-OP → в БД изменился **только** `core_watermarks`. Бизнес-данные целы. **После E4/5.7** это `N` дней ложного аудита и уведомлений за будущие даты.
4. Коррекция часов назад → `today_real < watermark` → **halt** [tasks.py#L87] и он держится, пока реальное время не догонит отравленный watermark (дни→месяцы). Выход — Вариант C рунбука.
5. Пока сеймы пусты, Вариант C **безопасен** (нечего откатывать) — поэтому процедура фиксируется сейчас, а не после E4/E5.
