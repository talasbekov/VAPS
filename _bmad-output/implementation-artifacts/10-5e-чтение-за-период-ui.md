# Story 10.5e: Чтение расхода за период — UI + типизация

Status: done

## Story

As a **руководитель**,
I want **на экране `/reports` посмотреть read-only расход за диапазон дат (страница-на-дату, без выпуска)**,
so that **я вижу динамику численности за период, не выпуская номерной документ на каждую дату**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/sprint-status.yaml:398-399` («10.5e — UI чтения за период + типизация `ExpensePeriodResponse.pages` (сегодня `{[k:string]:unknown}[]` — долг класса 10.1c)»). Роут `GET /api/operations/expense-reports/period/` (6.10a) уже существует и полностью реализован на бэке (`derive_period`) — БЕЗ HTTP-потребителя и БЕЗ типизированной схемы ответа.

1. **AC-1 (типизация `pages` — закрывает долг класса 10.1c).** Given ответ роута `period`, Then схема несёт ТИПИЗИРОВАННУЮ форму `pages[]` (`business_date`, `totals: {staff_total, list_total, vacancies, attached, columns}`, `rows: [{division_id, name, staff_total, list_total, vacancies, attached, columns}]`) — НЕ `DictField()`/`{[k:string]: unknown}`. Домен (`derive_period`/`_serialize_report`, `expense_read_service.py`) НЕ меняется — эта стори типизирует УЖЕ существующую форму ответа, не переизобретает её.
2. **AC-2 (UI-секция «Чтение за период» на `/reports`).** Given `divisionId !== null`, Then видна секция с полями `date_from`/`date_to` (текстовые `type="date"`, зеркало полей выпуска на этом же экране) и кнопкой «Показать» — запрос уходит ТОЛЬКО по клику (read-only просмотр — не автозагрузка при каждом наборе символа).
3. **AC-3 (таблица страниц — по датам).** Given `200 {pages: [...]}`, Then одна строка таблицы на дату: `business_date`, `staff_total`, `list_total`, `vacancies`, `attached` (`totals`, не `rows` — период про ДИНАМИКУ ПО ПОДРАЗДЕЛЕНИЮ ЦЕЛИКОМ, `rows`-детализация по дочерним подразделениям — вне экрана этой стори, дерево уже есть на `/organization`, 10.4).
4. **AC-4 (400/422 — инлайн, не крах).** Given `date_from > date_to` или диапазон `> 62` дней (400) или `date_from` до горизонта данных (422 `REPORT_NO_DATA_FOR_DATE`), Then `role="alert"` с текстом ИЗ ОТВЕТА (не сочинённым клиентским пересказом лимита — бэк несёт точное число `max`/`data_horizon` в `details`).
5. **AC-5 (пустой диапазон — не ошибка).** Given валидный диапазон, но `pages: []` НЕ возникает штатно (сервис всегда возвращает ≥1 страницу на валидный непустой диапазон — `date_from<=date_to` гарантирует), Then клиентский код НЕ обязан обрабатывать пустой `pages[]` как отдельный UI-стейт (домен-инвариант: непустой диапазон ⇒ непустой `pages`); тест ЭТОГО не выдумывает.
6. **AC-6 (независимость от карточки выпуска).** Секция периода — СОБСТВЕННЫЙ запрос (`['expense-period', divisionId, dateFrom, dateTo]`), не связана с `ExpenseReportPanel`/`ExpenseJournalPanel` состоянием — ошибка/успех периода не влияет на выпуск и наоборот (тот же принцип независимости, что 10.5c AC-4).
7. **AC-7 (регресс нулевой).** `ExpenseReportPanel`/`ExpenseJournalPanel` (выпуск/скачивание/блокировка/обход/журнал) — без изменений. `make gate`/`npm run gate` зелёные.

## Dev Notes

- **Домен НЕ меняется — эта стори чисто поверхностная (типизация+UI).** `derive_period`/`_serialize_report`/`assert_report_date_has_data` (`expense_read_service.py`) — READ-ONLY, ПОЛНОСТЬЮ РЕАЛИЗОВАНЫ (6.10a). Task 1 меняет ТОЛЬКО `@extend_schema`-аннотацию `views.py`, не тело `period()`.
- **`totals`, не `rows`, на экране (AC-3).** Ответ несёт И `totals` (подразделение целиком), И `rows` (по дочерним подразделениям, если запрошенное — родитель с детьми). Экран показывает ТОЛЬКО `totals` — динамика по КОНКРЕТНОМУ выбранному подразделению за диапазон дат. `rows`-детализация по дочерним — избыточна здесь (дерево светофора `/organization`, 10.4, уже даёт per-division обзор ЗА ОДНУ дату); не рендерить `rows` в этой стори — сознательный вырез, не забытая часть.
- **Отложенный запрос («Показать»), не автозагрузка.** Диапазон дат — ДВА поля ввода; автозапрос на каждое изменение `dateFrom` дал бы наполовину введённую дату (`2026-0` → 400 инвалид) как штатный, а не переходный, UX-шум. Кнопка — явное намерение, зеркало паттерна `ExpenseReportPanel`'s «Сформировать» (явное действие, не сайд-эффект набора).
- **`MAX_PERIOD_DAYS=62` (bakend-константа) — текст ошибки ИЗ ОТВЕТА, не задублирован на клиенте.** `derive_period` уже несёт точное число `62` в `details.max` 400-ответа (`expense_read_service.py:117-122`) — свой клиентский лимит-текст создал бы риск рассинхрона при будущей правке константы на бэке (тот же принцип, что «допустимые даты — дословно из ответа», уже устоявшийся в этом файле для `TOMORROW_BLOCKED`).
