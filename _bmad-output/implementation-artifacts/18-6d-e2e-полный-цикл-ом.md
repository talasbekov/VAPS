# Story 18.6d: e2e — опрос по итогам (полный цикл ОМ, завершение)

Status: done

## Story

As a **разработчик**,
I want **e2e-покрытие опрос-панели (18.6c) в РЕАЛЬНОМ chromium**,
so that **jsdom-эмуляция реального fetch/навигации не маскирует дефекты трёх последовательных мутаций, которые unit-тесты структурно не ловят (тот же принцип, что 16.8i/17.7e для остального цикла Расстановки)**.

## Scope Decision

- **Расширяет СУЩЕСТВУЮЩИЙ e2e-харнес и спек, НЕ новый файл** — `frontend/e2e-harness/placement.tsx` (16.8i, монтирует реальный `AppRoutes`+`Providers`) и `frontend/e2e/placement-lifecycle.spec.ts` (16.8i/17.7e) уже несут ПОЛНЫЙ клиентский цикл Расстановки, `OprosCell` (18.6c) уже смонтирована на ТОЙ ЖЕ `PlacementVersionDetailPage`, что и `JournalPanel`/`AcknowledgeCell` — новый харнес не нужен, буквальный прецедент 17.7e (которая расширила ЭТОТ ЖЕ файл для журнала/замены).
- **⚠️ Название стори вводит в заблуждение относительно реального объёма**: «полный цикл ОМ» по epics.md означал бы create→bulletin→recon→demand→placement→proведение→ЗАКРЫТИЕ→опрос. Из этого в РЕАЛЬНОМ UI (не Smart Josparlau mock-прототип `features/security-events/`) существует ТОЛЬКО цепочка Расстановки (`features/placement/`: draft→submit→return→approve→acknowledge, 16.8i/17.7e) + опрос (`OprosCell`, 18.6c). `close`/`archive` (18.6a's API) НЕ имеют UI вообще — ни одна стори 18.6a-c не строила экран/кнопку для них (18.6c's Scope Decision прямо перечисляет фронт закрытия/архива как «Story 18.6c» из ИСХОДНОГО единого плана 18.6, который был разбит — экран закрытия НЕ попал ни в одну из под-стори 18.6a-d). Эта стори добавляет e2e ТОЛЬКО для того, что реально кликабельно — опрос-панель поверх уже покрытого 16.8i/17.7e цикла Расстановки. Закрытие/архив — задокументированный пробел (не эта стори его закрывает), см. Out of Scope.
- **Расширяет СУЩЕСТВУЮЩИЙ стаб** (`stubApi()` в `placement-lifecycle.spec.ts`) — добавляет `page.route` для `POST .../placement-assignments/{id}/actual-time/`, `.../service-hours/`, `.../overload/`, буквальный образец существующих маршрутов того же файла (`submit`/`approve`/`acknowledge`'s regex-на-URL + `route.fulfill`-паттерн).
- **Добавляет шаги в СУЩЕСТВУЮЩИЙ полный-цикл тест** (не отдельный сценарий) — «one scenario, whole cycle», установленная конвенция файла (16.8i/17.7e). Опрос — ПОСЛЕ «Отметить ознакомление» (последний существующий шаг), три клика подряд (Записать факт → Вычислить налёт → Проверить перегрузку), тот же приём, что 17.7e's журнал-шаг был вставлен между «Утвердить» и «Отметить ознакомление».
- **Стаб не гейтит `is_current`/`CLOSED`** (тот же принцип, что 17.7e's Dev Notes: «e2e тестирует ФРОНТ-поведение, не бэк-инварианты, те уже покрыты `make gate`») — реальный бэковый двойной-гейт (18.3-18.5) уже протестирован на уровне Django (`make gate`), здесь только happy-path реального браузера.
- **`datetime-local`-ввод через Playwright `.fill()`** — заполнить `input[type=datetime-local]` буквенно-цифровым значением (`"2026-08-04T09:00"`), тот же формат, что уже используется в `duty-plan-lifecycle.spec.ts` для аналогичных полей (если существует прецедент — сверить при реализации; иначе `.fill()` с ISO-подобной строкой без секунд, стандартный Playwright-паттерн для `datetime-local`).
- **Out of scope**: e2e для `close`/`archive` (18.6a) — НЕТ UI, эта стори его не строит и не тестирует; e2e для 403/422-веток опроса (уже покрыты jsdom-тестами 18.6c с mutation-проверкой — e2e добавляет ТОЛЬКО реал-браузерный happy-path); UI для закрытия события (отдельная будущая стори, если понадобится); tz-конверсия `zonedDateTimeToIso()` в реальном браузере с ДРУГОЙ системной таймзоной (jsdom-тест 18.6c уже фиксирует конверсию через тело запроса, e2e не переизобретает этот тест).

## Dev Notes

- `frontend/e2e/placement-lifecycle.spec.ts` — ПОЛНЫЙ файл читать перед правкой. `stubApi()` держит `versions: Version[]` в замыкании; назначение из `versions[0].assignments[0]` несёт `id: 1` — маршруты `actual-time`/`service-hours`/`overload` матчатся по `placement-assignments/(\d+)/...`, тот же regex-стиль, что `acknowledge`'s существующий маршрут (`services.py:172` эквивалент во фронте — `PlacementVersionDetailPage.tsx`'s `OprosCell`).
- `OprosCell` (18.6c, `PlacementVersionDetailPage.tsx`) — три ПОСЛЕДОВАТЕЛЬНЫХ шага, гейтится на `mutation.data === undefined` каждой из трёх мутаций — стаб должен вернуть тело, СОДЕРЖАЩЕЕ `day_hours`/`night_hours` (`service-hours`-стаб) и `is_overloaded`/`overload_minutes` (`overload`-стаб), иначе `OprosCell` не продвинется на следующий шаг (JSX буквально проверяет наличие полей через `.data`, не статус-код).
- `datetime-local`-инпуты несут `aria-label` (не `<label>`), Playwright — `page.getByLabel(...)` работает и с `aria-label` (подтверждено в jsdom-тестах 18.6c через `screen.getByLabelText`, тот же API-контракт `@testing-library`/Playwright).
- Кнопочный текст буквально: «Записать факт», «Вычислить налёт», «Проверить перегрузку» (`PlacementVersionDetailPage.tsx`, `OprosCell`) — не перефразировать.
- Стаб `actual-time` может вернуть ЛЮБОЕ валидное `actual_start_at`/`actual_end_at` (фронт не парсит ответ на предмет соответствия отправленному — просто использует наличие `.data` как триггер шага 2), но для реализма — эхо отправленного тела (тот же приём, что `return`/`replace-departed`'s стабы уже делают).
