# Story 14.3a: Привязка чек-листа к объекту и ADD/MODIFY/DISABLE-оверрайды

Status: done

## Story

As a Старший объекта / Администратор,
I want привязывать типовой чек-лист к объекту и точечно дополнять/править/выключать его пункты под конкретный объект,
so that рекогносцировка (15.3) получает резолвнутый чек-лист объекта (BR-CHECKLIST-003) без ручного дублирования типового набора.

## Acceptance Criteria

1. **ChecklistBinding.** Given активный объект и активный шаблон, when `create_binding(actor, facility_id, template_code, name?, is_default?)`, then привязка создана (TimeStampedModel, `db_table="ops_checklist_bindings"`), facility FK CASCADE, template FK **PROTECT** (донорский RESTRICT) `db_column="template_code"`, `name` — CharField(255) NULL (NULL = единственное пустое состояние, conditional-\S CHECK), `is_default` default False, `is_active` default True; аудит `CHECKLIST_BINDING_CREATED`; дубль (facility, template) среди активных → структурный 409 `CHECKLIST_BINDING_ALREADY_EXISTS` (pre-check + partial-уник `uq_checklist_binding_facility_template` (is_active=True) как race-бэкстоп в CONSTRAINT_ERROR_MAP); неактивный/несуществующий шаблон → VALIDATION_ERROR 400.
2. **is_default.** Then среди активных привязок объекта не более одной is_default=True (partial-уник `uq_checklist_binding_default_per_facility`: facility WHERE is_default AND is_active); создание/обновление с is_default=True при живом дефолте → структурный 409 `CHECKLIST_DEFAULT_ALREADY_SET` (pre-check + race-бэкстоп; смена дефолта — двухшагово: снять старый, поставить новый, БЕЗ скрытых мутаций чужих строк).
3. **ChecklistOverride — форма по типу.** Given активная привязка, when `add_override(actor, binding_id, override_type, source_item_id?, text?, category?, is_required?, sort_order?, reason?)`, then оверрайд создан (`db_table="ops_checklist_overrides"`, binding FK CASCADE, source_item FK **PROTECT** null — ПИН РЕВЬЮ 14.3: не донорский SET_NULL, осиротевший MODIFY = неопределённое поведение резолвера); на уровне БД (conditional-CHECKs, красные пробы транзакционные, обе стороны):
   - `override_type` ∈ {ADD, MODIFY, DISABLE} (CHECK, без дефолта);
   - ADD → source_item IS NULL И text \S;
   - MODIFY/DISABLE → source_item IS NOT NULL;
   - DISABLE → payload пуст (text/category/is_required/sort_order все NULL);
   - MODIFY → хотя бы одно payload-поле NOT NULL (пустой MODIFY — мусор);
   - text/category: NULL или \S; sort_order: NULL или ≥0.
4. **Инварианты оверрайда (сервис).** Then source_item обязан принадлежать шаблону привязки (чужой шаблон → VALIDATION_ERROR 400) и быть активным на момент создания; source_item резолвится ПОД ЛОКОМ внутри транзакции (TOCTOU-канон 14.2 — конкурентный admin-delete пункта блокируется); повторный оверрайд того же пункта в привязке → структурный 409 `CHECKLIST_OVERRIDE_ALREADY_EXISTS` (pre-check + partial-уник `uq_checklist_override_binding_source` (source_item NOT NULL) — один оверрайд на пункт: MODIFY и DISABLE одновременно невозможны, резолвер детерминирован); аудит `CHECKLIST_OVERRIDE_CREATED`.
5. **Мутации и жизненный цикл.** Given `update_binding(actor, binding_id, changes)` (whitelist {name, is_default} + drift-тест, лок, дифф, honest-noop со снимком updated_at) / `deactivate_binding` / `remove_override(actor, override_id)` (hard-DELETE строки, полный снимок в audit old_value), then каждая мутация — под select_for_update с гвардом замороженного объекта (facility.is_active) и активной привязки; повторная деактивация / мутация под неактивной привязкой → структурный 409 `CHECKLIST_BINDING_ALREADY_INACTIVE`; деактивация привязки УДАЛЯЕТ её оверрайды под локами (зеркало донорского CASCADE при soft-delete: мёртвые оверрайды через PROTECT навсегда запирали бы удаление пункта в admin — Д1), `removed_override_ids` в audit new_value только при непустом списке (канон untied_post_ids); аудит `CHECKLIST_BINDING_UPDATED`/`CHECKLIST_BINDING_DEACTIVATED`/`CHECKLIST_OVERRIDE_REMOVED`; entity-ось — uuid5 своих неймспейсов (vaps:checklist_binding / vaps:checklist_override), плоские публичные ключи (template_code, source_item_id) в аудите и changes.
6. **Резолвер BR-CHECKLIST-003.** Given привязка с оверрайдами, when `resolve_checklist(actor, binding_id)` (селекторный read), then возвращается список пунктов: активные пункты шаблона + оверрайды объекта — DISABLE исключает пункт, MODIFY патчит (NULL payload-поля = «не менять»), ADD добавляет (дефолты при NULL: is_required=True, sort_order=0); глобально-неактивный пункт шаблона исключён ВСЕГДА (его MODIFY/DISABLE игнорируются); каждый элемент несёт origin (STANDARD/MODIFIED/ADDED), source_item_id/override_id, text, category, is_required, sort_order; порядок детерминирован: (sort_order, added-флаг, id) — буквальный пин в тесте (не вакуумная проба); резолв неактивной привязки → 409 `CHECKLIST_BINDING_ALREADY_INACTIVE`.
7. **Гейт и границы.** `make gate` из Backend/VAPS зелёный: миграции 0009/0010 по-сущности, `makemigrations --check` пуст; бизнес-модели в admin НЕ регистрируются (CATALOG_MODELS не растёт); ChecklistItem с живыми ссылками оверрайдов защищён от удаления на уровне БД (ProtectedError — прямой тест admin-опасного пути из пина ревью).

## Dev Notes

### Ключевые решения (Д)

- **Д1. source_item — PROTECT, не SET_NULL** (исполнение пина ревью 14.3): выбран DB-уровень, а не сервисный guard — admin-delete пункта (единственный путь удаления, пункты admin-managed) получает ProtectedError и честно отказывает; осиротевший MODIFY невозможен по построению. Побочка: удалить пункт шаблона можно только после снятия его оверрайдов на всех объектах — это фича (админ видит, что пункт в работе), а глобальное выключение остаётся через is_active.
- **Д2. Один оверрайд на пункт в привязке** (`uq_checklist_override_binding_source`, partial source_item NOT NULL): донор молчит, но два MODIFY одного пункта (или MODIFY+DISABLE) делают BR-CHECKLIST-003 недетерминированным — класс «category ''≠NULL» из ревью 14.3: инвариант формы данных ради резолвера. ADD-дубли не ограничиваем (Д4-14.3: дубль текста может быть легитимен).
- **Д3. MODIFY: NULL = «не менять».** Очистить category через MODIFY нельзя (DISABLE + ADD — путь для радикальной правки); пустой MODIFY (все payload NULL) отвергается CHECK'ом. DISABLE несёт только reason — payload-CHECK держит форму чистой (предпочтение Bratan: инварианты формы на БД).
- **Д4. remove_override — hard-DELETE**: у донора на оверрайдах нет is_active — оверрайд не учётная сущность, а правка конфигурации; восстановление = повторное создание; полный снимок уходит в audit old_value. «Сервис не DELETEит» из 14.2 — про зеркало SET_NULL для СУЩНОСТЕЙ, не канон для конфиг-строк.
- **Д5. is_default — двухшаговая смена** (409 при живом дефолте, никаких скрытых снятий дефолта с чужой строки): семантику «дефолтной» привязки донор не раскрывает; потребитель — 15.3; auto-unset был бы молчаливой мутацией второй строки мимо явного намерения актора.
- **Д6. Резолвер НЕ перепроверяет is_active шаблона**: гейт активности шаблона стоит на create_binding; выключение шаблона позже не рвёт существующие объекты (операционная непрерывность). Глобально-неактивные ПУНКТЫ исключаются всегда (is_active пункта = глобальный выключатель, Д6-14.3). Поднять на ревью при несогласии.
- **Д7. BR-CHECKLIST-004 (permission на DISABLE required-пункта) — named-defer**: сервисы принимают actor-строку (ARCH-007), permission-гейт — зона API-стори (14.11/15.3) + RBAC-строк (14.12). Зафиксировать комментарием в add_override.
- **Д8. update_override НЕ заводим**: минимальная поверхность (add/remove; правка = remove+add); донорский API-раздел даёт только POST bindings; расширение — по требованию 15.3.
- **Д9. Partial-уник (facility, template) по is_active=True** — канон 14.2 (soft-delete не скваттит идентификаторы; реактивации нет, повторная привязка = новая строка с чистыми оверрайдами). Донорский тотальный UNIQUE рассчитан на DELETE, которого у нас нет.
