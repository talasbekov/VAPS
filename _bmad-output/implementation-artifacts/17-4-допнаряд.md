# Story 17.4: Допнаряд — маркировка внепланового, источник снятия

Status: done

## Story

As a **держатель права `assignment.amend` (штаб на проводимом ОМ)**,
I want **при оперативном добавлении допнаряда (17.3's механизм) явно пометить строку как внеплановую и зафиксировать, из какого подразделения/наряда сняты люди**,
so that **допнаряд отличим от планового назначения в истории версий, а источник снятия прослеживаем (для последующего анализа нагрузки/учёта, вне этой стори)**.

## Scope Decision

- **FR-28**, вторая половина (первая — 17.3): «...доп. силы (допнаряд) маркируются отдельно с фиксацией, из какого подразделения/наряда сняты люди.» Эта стори реализует ТОЛЬКО маркировку+источник — НЕ логику «откуда автоматически взять допнаряд» (это Story 17.5's каскадная замена, отдельный механизм поиска замены).
- **`PlacementAssignment` расширяется** (не новая таблица) — три новых поля: `is_unplanned` (BooleanField, default=False), `source_division_id` (UUIDField, nullable, flat — ARCH-003, буквальный образец `ObjectPassport.responsible_employee_id`'s «no FK into core»), `source_duty_shift_id` (BigIntegerField, nullable, flat — тот же ARCH-003 принцип для cross-subdomain ссылки в `duties.DutyShift`, НЕ настоящий FK, т.к. `PlacementAssignment` (events) и `DutyShift` (duties) — сиблинг-поддомены, ссылка не обязана быть referential-integrity-checked, тот же компромисс, что `Attachment`-ссылки). Источник — «подразделение ИЛИ наряд» (FR-28's «/»), минимум один заполнен, когда `is_unplanned=True` (асимметричный CheckConstraint, ИЛИ, не И — буквальный образец с изменённой связкой относительно 17.1/17.2/17.3's И-образцов).
- **`amend_assignment_version()` (17.3) рефакторится** — `assignments`-параметр переходит с 2-tuple `(employee_id, post)` на dict-форму `{"employee_id", "post", "is_unplanned"?, "source_division_id"?, "source_duty_shift_id"?}` (последние три — опциональны, по умолчанию `False`/`None`/`None`). Это ВНУТРЕННИЙ рефакторинг сервисной функции, у которой пока НЕТ ни одного внешнего потребителя (API/экраны — 17.7, ещё не построены) — 17.3's собственные тесты обновляются вместе с этим (та же стори владеет обеими правками, не откладывается на отдельный «рефакторинг»-тикет).
- **DutyShift существует РЕАЛЬНО** (`apps/operations/duties/models.py:75`, Story 14.5) — `source_duty_shift_id` ссылается на РЕАЛЬНУЮ модель, не гипотетическую; референциальная целостность НЕ проверяется (флэт-ссылка, тот же принцип, что `photo_attachment_id`, 17.2).
- **Не проверяется**, что `source_division_id`/`source_duty_shift_id` действительно СВЯЗАНЫ с конкретным `employee_id` в строке (т.е. что сотрудник ДЕЙСТВИТЕЛЬНО был снят именно оттуда) — это поле фиксации факта (штаб вводит источник вручную/из контекста 17.5), не автоматическая сверка. Открытый вопрос Bratan, если нужна сверка.
- **RBAC** — переиспользуется `assignment.amend` (17.3), новый код не нужен (та же операция — оперативное изменение, допнаряд просто маркирует некоторые строки внутри неё).
- **Audit** — переиспользуется `ASSIGNMENT_VERSION_AMENDED` (17.3), не нужен отдельный audit action (те же version-level мутации; допнаряд-факты — на уровне строк `PlacementAssignment`, видны через сами данные версии).

## Acceptance Criteria

1. **AC-1.** Given `amend_assignment_version(..., assignments=[{"employee_id":..., "post":..., "is_unplanned": True, "source_division_id": div_id}])`, when вызов, then созданная `PlacementAssignment`-строка несёт `is_unplanned=True`, `source_division_id=div_id`.
2. **AC-2.** Given `is_unplanned=True` БЕЗ `source_division_id` И БЕЗ `source_duty_shift_id` (оба `None`), when вызов, then `DomainError`, версия не создаётся.
3. **AC-3.** Given `is_unplanned=True` С `source_duty_shift_id` (без `source_division_id`), when вызов, then успешно — источник ЛИБО подразделение, ЛИБО наряд, не обязательно оба (FR-28's «/»).
4. **AC-4.** Given `is_unplanned` не передан (обычный элемент `{"employee_id", "post"}`), when вызов, then строка создаётся с `is_unplanned=False`, `source_division_id=None`, `source_duty_shift_id=None` — обратная совместимость с 17.3's вызовами без допнаряда.
5. **AC-5.** Given смешанный список (часть строк `is_unplanned=True` с источником, часть — обычные), when вызов, then каждая строка несёт СВОИ значения независимо (не глобальный флаг на версию).
6. **AC-6.** `chk_placement_assignment_unplanned_requires_source`-констрейнт на DB — прямой `.objects.create(is_unplanned=True, source_division_id=None, source_duty_shift_id=None, ...)` в обход сервиса — `IntegrityError`.
7. **AC-7.** 17.3's существующие тесты (`test_amend_assignment_version.py`) обновлены на dict-форму `assignments` и ПРОХОДЯТ без изменения проверяемого поведения (регрессия не сломана).
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Previous Story Intelligence (17.3)

- Guard-порядок: дешёвые проверки ДО `transaction.atomic()`, lifecycle-гварды ПОСЛЕ `select_for_update()` — новый guard (допнаряд-источник) ставится в ТОТ ЖЕ цикл, что уже проверяет `post.object_id` (перед вложенным savepoint, вместе с существующей проверкой).
- 17.3's ревью нашёл: вложенный savepoint вокруг flip+create+bulk_create (буквальный образец `amend_day()`) — эта стори НЕ трогает этот блок, только данные, которые в него попадают.
- 17.3's ревью нашёл: `post=None` в assignments должен явно проверяться (не `AttributeError`) — та же дисциплина применяется к новым dict-ключам (`.get()` с дефолтом, не `[...]`-доступ, который упал бы `KeyError` на обратно-совместимых 17.3-вызовах без допнаряд-ключей).
