# Story 15.4: `PUT /security-events/{id}/passport` — обновление Паспорта объекта, привязанное к ОМ (FR-22)

Status: review

## Story

As a **оператор, завершивший рекогносцировку**,
I want **обновить Паспорт объекта ЭТОГО ОМ (по итогам рекогносцировки), пока ОМ в статусе `RECON`**,
so that **Паспорт отражает актуальное состояние объекта ДО того, как ОМ продвинется дальше (Потребность/брокеридж/расстановка)**.

## Scope Decision (найдено при create-story)

- **Story 15.4 — genuinely underspecified.** Research-агент лично проверил: `epics.md:1419` — однострочный заголовок «Story 15.4: Обновление Паспорта до начала ОМ», без AC/деталей. FR-22 (`epics.md:60`) только упоминает «обновление Паспорта» как часть рекогносцировки, тоже без полей/правил. Ни architecture.md, ни frontend-прототип не дают конкретики (личная проверка, включая `frontend/src/features/objects/pages/ObjectPassportPage.tsx` — автономная форма без связи с ОМ/рекогносцировкой). 15.3c's Scope Decision явно резервировала эту работу под будущую стори — это она.
- **Никакого API для `ObjectPassport` НЕ существует до этой стори** (14.1 — models+migration only, models.py's собственный докстринг это подтверждает). Эта стори — ПЕРВЫЙ API для `ObjectPassport`, узко привязанный к ОМ-контексту (не общий CRUD).
- **Синтезированная (не выдуманная произвольно) интерпретация «обновление Паспорта до начала ОМ»:** модель уже несёт `last_verified_at`/`last_verified_by` поля (14.1, ещё не задействованы нигде в кодбейзе — личная проверка, только 1 test asserting default). Естественное прочтение — «до начала» = пока ОМ ещё в `RECON` (после дубль-контроля 15.3c, ДО продвижения в `DEMAND`/`BROKERAGE`/`PLACEMENT`/`IN_PROGRESS`). Обновление Паспорта в этом окне — партиальный `PATCH`-подобный `PUT` (только переданные поля) на `ObjectPassport`, ЗАПИСЫВАЮЩИЙ `last_verified_by=actor`/`last_verified_at=now()` при каждом успешном вызове. Это не изобретение бизнес-правил — это буквальное включение уже существующих, но неиспользуемых полей модели в реальный write-path, привязанный к естественной точке цикла (после рекогносцировки, до продвижения).
- **Гейт по статусу ОМ — СТРОГО `RECON`.** Не `BULLETIN`/`DRAFT` (паспорт обновляется ПОСЛЕ рекогносцировки, не до неё) и не пост-`RECON` (`DEMAND`+, ОМ уже «начался» в смысле дальнейшего цикла — заголовок стори буквально говорит «до начала ОМ»). Конфликт статуса → `INVALID_LIFECYCLE_TRANSITION` (422, тот же переиспользуемый код).
- **`get_or_create()` для `ObjectPassport`** — 14.1 не гарантирует, что паспорт объекта уже создан (модель существует с 14.1, но ничто не форсирует его создание при создании `Object`). Первый вызов на объекте без паспорта создаёт его.
- **Permission — `object.manage`** (уже существует в `seed_operations.py`, «Управление объектами» — семантически верный код: это мутация `ObjectPassport`, объект-уровневая сущность, НЕ `event.manage`, который гейтит только `SecurityEvent`-мутации).
- **`completeness_status` — записываемое клиентом поле** (не авто-вычисляемое: никакой формулы «когда GREEN» нигде не найдено — `CompletenessStatus` используется только как enum-дефолт, ни одного места вычисления в кодбейзе). Оператор явно проставляет статус как часть обновления.

## Acceptance Criteria

1. **AC-1 (успешное обновление).** `PUT /security-events/{id}/passport` на ОМ в `RECON`, с частичным набором полей `ObjectPassport` → 200, поля обновлены, `last_verified_by`/`_at` проставлены сервером (актор + текущее время).
2. **AC-2 (создание при отсутствии).** Если у объекта ОМ ещё нет `ObjectPassport` — создаётся (не 404).
3. **AC-3 (partial update).** Непереданные поля НЕ затираются (буквальный `PATCH`-семантика под `PUT`-методом, консистентно с самим названием — обновление, не замена).
4. **AC-4 (гейт статуса).** Вызов на ОМ НЕ в `RECON` → 422 (`INVALID_LIFECYCLE_TRANSITION`).
5. **AC-5 (permission).** Требует `object.manage` — без него 403.
6. **AC-6 (регресс нулевой).** `make gate` зелёный, роут — в обоих живых реестрах (audit `_Audited()` — реальная мутация с compliance-следом, не черновик, в отличие от 15.3b; RBAC `_Gate("object.manage")`).

## Out of Scope

- Автовычисление `completeness_status` по заполненности полей — не найдено формулы, не эта стори.
- `ops_object_passport_history` (donor DB-OPS-015, field-change audit trail) — явно вне объёма ещё с 14.1's Scope Decision.
- Общий CRUD для `ObjectPassport` вне ОМ-контекста — не запрошено, эта стори строго ОМ-привязанная.
