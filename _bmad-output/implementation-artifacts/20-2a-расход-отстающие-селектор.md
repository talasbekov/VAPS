# Story 20.2a: Дашборд расхода и отстающих управлений — композитный селектор

Status: done

## Story

As a **держатель права `status.view`/`event.manage`** (потребитель будущего дашборда),
I want **получить расход (по управлениям) И список отстающих управлений ЗА ОДИН вызов**,
so that **будущий дашборд (FR-38, UJ-2 — «руководитель к 09:00 скачивает расход; если управление не обновилось — красный индикатор, кто отстаёт») не собирает два независимых источника вручную на каждом экране**.

## Scope Decision

- **Разбор эпика**: epics.md's Story 20.2 — «Дашборд расхода и отстающих управлений». Исследованием найдено: ОБА источника данных УЖЕ ПОЛНОСТЬЮ СУЩЕСТВУЮТ и протестированы — `StrengthReportService.compute(business_date)` (2.x, расход по управлениям) и `tomorrow_block(business_date)` (5.6a, отстающие). Эта стори НЕ строит новую агрегацию — она ТОНКАЯ композиция двух уже готовых produce-функций + разрешение UUID отстающих управлений в читаемые имена (для дашборда, не для HTTP-гейта — см. ниже).
- **Живёт в `apps/operations/selectors.py`** (существующий, package-level модуль операционного контекста, НЕ внутри `apps.operations.statuses` или `apps.operations.submissions` — ни один из двух доменов не должен владеть логикой, читающей ОБА домена; тот же файл уже содержит `OpsUserRoleSelector`, cross-cutting паттерн). Новой Django-app НЕ создаётся (нет новых моделей, boilerplate избыточен).
- **`compute_expense_dashboard(business_date)`** — вызывает `StrengthReportService.compute(business_date)` (business_date, `division_id=None` → расход по ВСЕМ управлениям) И `tomorrow_block(business_date)` (ОДИН и тот же `business_date` — UJ-2's «за сегодня» и «кто не сдал за сегодня» ссылаются на ОДНУ дату, не «завтра» буквально: `tomorrow_block`'s имя относится к тому, ЧТО он блокирует — расход НА завтра, но параметр `business_date`, который он проверяет, это дата, за которую сдача уже должна была случиться).
- **Отстающие — с фильтром «призраков»** (тот же приём, что `apps/operations/submissions/services/tomorrow_gate.py`'s `assert_tomorrow_not_blocked()`, review D1 2026-07-13): `CoreDivisionTreeSelector.active_ids(block.laggards)` ПЕРЕД разрешением имён — удалённое/деактивированное управление в `required_division_ids` не должно попасть на дашборд как «отстающее» (никто не может сдать за несуществующее управление).
- **Разрешение имён — НОВОЕ для этого контекста, НЕ копирует `tomorrow_gate.py`'s решение**: `tomorrow_gate.py`'s HTTP-422 ответ ЯВНО остаётся UUID-only («laggards список намеренно org-wide, без имён, review D4 2026-07-13») — ТО решение о HTTP-гейте ошибки, ЭТА стори — про ЭКРАН дашборда, где голые UUID бесполезны руководителю. Два разных контекста, разные требования — не конфликт с прежним design-решением, не его отмена.
- **Возвращает `Dict`**: `{"business_date": date, "expense": StrengthReportResult, "laggards": [{"division_id": UUID, "name": str}], "blocked": bool, "overridden": bool}` — `expense`/`blocked`/`overridden` ПРОЗРАЧНО прокинуты из существующих типов (не переупаковываются), `laggards` — единственное НОВОЕ преобразование (UUID→{id,name} после stale-фильтра).
- **Out of scope**: API/эндпоинт HTTP-слоя (20.2b); экран дашборда (20.2c+); экспорт `.docx`/`.xlsx` (FR-40, Story 20.4, отдельная функциональность); тренд/история за прошлые дни (не запрошено); изменение `StrengthReportService`/`tomorrow_block` (оба существуют и протестированы, эта стори их НЕ трогает, только вызывает).

## Acceptance Criteria

1. **AC-1.** `compute_expense_dashboard(business_date)` возвращает `expense`, идентичный прямому вызову `StrengthReportService.compute(business_date)` (не переизобретает расчёт).
2. **AC-2.** Управление в `required_division_ids`, у которого ЕСТЬ текущая сдача на `business_date`, НЕ попадает в `laggards`.
3. **AC-3.** Управление в `required_division_ids` БЕЗ текущей сдачи → попадает в `laggards` как `{"division_id": <uuid>, "name": <str>}`.
4. **AC-4.** Управление в `required_division_ids`, которое УДАЛЕНО/ДЕАКТИВИРОВАНО (не активно) → НЕ попадает в `laggards`, даже если формально не сдало (stale-фильтр).
5. **AC-5.** Пустой `required_division_ids` (ничего не обязательно) → `laggards=[]`, `blocked=False`.
6. **AC-6.** `blocked`/`overridden` в результате — ТЕ ЖЕ значения, что вернул бы прямой вызов `tomorrow_block(business_date)` (после stale-фильтра на `laggards`, но `blocked`/`overridden` НЕ пересчитываются заново этой стори — прокинуты как есть, за исключением случая, где ВСЕ laggards оказались призраками — см. Dev Notes про согласованность с `blocked`).
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

## Dev Notes

- `apps/operations/statuses/services/strength_report.py:249-260` (`StrengthReportService.compute`) — `compute(business_date, division_id=None)` → `StrengthReportResult(business_date, rows, totals, violations, warnings)`. Вызывать С `division_id=None` (весь орг) — дашборд по умолчанию показывает ВСЕ управления, не одно.
- `apps/operations/submissions/tomorrow_block.py` (`tomorrow_block`) — `TomorrowBlock(blocked, laggards, overridden=False)`. `laggards` — уже `sorted(..., key=str)`, UUID-список. Пустой `required_division_ids` → ранний `TomorrowBlock(blocked=False, laggards=[])` (уже гарантирует AC-5 на уровне `tomorrow_block`, эта стори просто НЕ ломает этот путь).
- `apps/operations/submissions/services/tomorrow_gate.py:39-45` (`assert_tomorrow_not_blocked`) — СТРУКТУРНЫЙ ОБРАЗЕЦ stale-фильтра: `active = CoreDivisionTreeSelector.active_ids(block.laggards)`, затем `[d for d in block.laggards if d in active]`. Буквально копировать этот приём (не изобретать заново) — тот же class бага (review D1 2026-07-13, «config garbage не должен блокировать/показывать»).
- **Согласованность `blocked` после stale-фильтра (AC-6's нюанс)**: `tomorrow_gate.py`'s прецедент — если ПОСЛЕ stale-фильтра `laggards` стал пустым (все призраки), исходный `blocked=True` от `tomorrow_block()` становится ЛОЖНЫМ сигналом (реальных отстающих нет). `tomorrow_gate.py` явно обрабатывает это («Every «laggard» is config garbage... → day is NOT blocked»). Эта стори ОБЯЗАНА повторить ТУ ЖЕ логику: если `filtered_laggards` пуст, но исходный `block.blocked` был `True` (из-за призраков) — вернуть `blocked=False` в композитном результате (НЕ прокидывать сырое `block.blocked`, если фильтр его обесценил). Если `filtered_laggards` непуст — прокинуть `block.blocked`/`block.overridden` как есть.
- `apps/core/selectors.py:124-129` (`CoreDivisionTreeSelector.divisions_map`) — `id -> name`, ОДИН запрос, тихо ОПУСКАЕТ несуществующие ID (не исключение) — вызывать ПОСЛЕ stale-фильтра (`active_ids`), не до: `active_ids` уже гарантирует, что оставшиеся ID реальны и активны, `divisions_map` на этом отфильтрованном множестве не должен потерять ни одного имени.
- `apps/operations/submissions/tests/test_tomorrow_block.py` — структурный образец фикстур (`make_division`, `set_required` через `SubmissionControlSettings.objects.get_or_create(singleton_key=1)`, `_submit(division, business_date)` через `clock.override`). Переиспользовать паттерн, не изобретать заново.
- Для AC-4 (деактивированное управление) — проверить точный API «неактивности» Division у `CoreDivisionTreeSelector.active_ids` (вероятно `is_active=False` и/или `archived_at`-подобное поле на `Division`/`DivisionHistoricalSlot` — свериться с `apps/core/models.py`'s `Division`-моделью перед написанием теста, НЕ гадать).
