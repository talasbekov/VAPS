# Story 13.2: Выгрузка диагностики носителем

Status: review

## Story

As a **разработчик**,
I want **команду `manage.py export_diagnostics` — экспорт багрепортов (13.1a) + структурного журнала аудита за период в файл-архив, с маскированием ПДн, скачивание отмечено в аудите**,
so that **диагностика легально выносится из закрытого контура носителем, без ручного copy-paste из БД**.

## Scope Decision (найдено при create-story — критично для скоупа)

Буква стори (`epics.md#L1356-1362`) предполагает существование «structured-логов» — их НЕТ. Research при create-story подтвердил: `config/settings.py` не содержит `LOGGING`-словаря вовсе, `structlog`/`python-json-logger` не установлены, приложение НЕ пишет собственные структурные логи (исключений, трасс запросов, диагностических событий) НИКУДА. Строить полноценную logging-инфраструктуру (JSON-логгер + хранилище + ротация) — самостоятельный, крупный кросс-катинг инфраструктурный кусок работы, не умещающийся в одну стори по декомпозиции CLAUDE.md, и не то, что буква эпика 13 явно просит (эпик про цикл исправлений, не про observability-платформу).

**Решение**: «структурный журнал» переинтерпретирован как то, что УЖЕ реально структурно, per-событийно и существует в БД — `apps.audit.models.AuditLog` (actor/action/entity_type/entity_id/created_at/request_id — уже структурная, машиночитаемая запись каждой бизнес-мутации). Экспорт = `BugReport`-строки (13.1a) + `AuditLog`-строки за период — БЕЗ `old_value`/`new_value` JSON-полезной нагрузки (см. AC-2 — там же живут потенциально чувствительные бизнес-данные, маскировать произвольный вложенный JSON контент-сканированием не входит в скоуп, безопаснее и проще исключить эти два поля целиком из экспорта). Полноценная инфраструктура «application logs» (исключения/трассы) остаётся явным будущим долгом, не имитируется и не выдаётся за существующую.

## Acceptance Criteria

1. **AC-1 (экспорт за период → архив).** `manage.py export_diagnostics --from YYYY-MM-DD --to YYYY-MM-DD --actor <cli-user>` — новый `.zip` в `deploy/diagnostics-exports/` (гитигнорирован, зеркалит `deploy/dist-bundle/`'s конвенцию), содержит: `bugreports.json` (все `BugReport.created_at` в диапазоне), `audit_log.json` (все `AuditLog.created_at` в диапазоне, БЕЗ `old_value`/`new_value`), `manifest.json` (диапазон дат, кол-во строк каждого файла, sha256 каждого файла, timestamp экспорта, `--actor`-значение).
2. **AC-2 (ПДн маскированы — `description`, единственное реально рискованное поле).** `BugReport.description` — свободный текст, оператор может вписать что угодно (ФИО/телефон/ИИН) — единственное поле реального PII-риска (`user_id`/`screen_path` — не ПДн, `apps/operations/bugreports/models.py`'s собственный комментарий уже фиксирует `user_id` как внешний auth-id, не персональные данные, ARCH-007/BR-ACCOUNT-002). Маскирование — best-effort regex-скрабер (ИИН-подобные 12-значные последовательности, телефон-подобные паттерны, email) применяется к `description` ПЕРЕД записью в архив — явно документировано как best-effort, не исчерпывающий NLP-анализ. `AuditLog`'s `old_value`/`new_value` (где живёт реальный риск бизнес-данных) — не экспортируются вовсе (AC-1), не маскируются построчно (проще и безопаснее исключить, чем content-scan произвольный вложенный JSON).
3. **AC-3 (скачивание отмечено в аудите — ПЕРВАЯ management-команда, пишущая AuditLog).** Ни одна существующая management-команда сегодня не вызывает `apps.audit.services.record()` (research подтвердил — вне HTTP-запроса `get_request_context()` возвращает пустой контекст). Команда вызывает `record()` явно: `actor=<--actor CLI-значение>`, `action="DIAGNOSTICS_EXPORTED"` (новая строка в `apps/audit/audit-events.yaml`, канон-реестр), `entity_id=<sha256 архива>` (единственный стабильный идентификатор экспорта), `new_value={"from": ..., "to": ..., "bugreports_count": N, "audit_rows_count": M}`. `record()`'s уже существующий IP-сентинел (`_SYSTEM_IP = "0.0.0.0"`) корректно покрывает «нет HTTP-контекста» — не требует правки самого `record()`.
4. **AC-4 (`--actor` обязателен, не угадывается).** Команда падает с понятной ошибкой без `--actor` — вне HTTP нет `request.actor_id`, отсутствие явного значения означало бы либо пустой/фиктивный actor в аудите (нарушает `record()`'s собственный контракт непустого actor), либо угадывание через `whoami` (ненадёжно на носителе/контуре, разные ОС-пользователи).
5. **AC-5 (регресс нулевой).** `make gate` зелёный.

## Out of Scope

- Полноценная structured application-logging инфраструктура (исключения/трассы запросов) — реальный, явно задокументированный будущий долг, НЕ имитируется.
- Content-scanning произвольного вложенного JSON (`AuditLog.old_value`/`new_value`) — решено проще: не экспортировать эти поля вовсе.
- Ротация/автоочистка `deploy/diagnostics-exports/` — ручной процесс (носитель уносит и удаляет), как `deploy/dist-bundle/`.

## Dev Notes

- **«Структурные логи» = `AuditLog`, не выдумка.** `AuditLog` — actor/action/entity_type/entity_id/created_at/request_id, машиночитаемая, per-событийная запись — структурно СООТВЕТСТВУЕТ понятию «structured log» для целей этой стори, даже не будучи application-exception-логом. Явно задокументировано как переинтерпретация буквы, не имитация несуществующей инфраструктуры.
- **`mask_employee_data` (apps/core/services.py) НЕ подходит напрямую.** Та функция маскирует ПОЛЯ по `SensitiveFieldPolicy.field_code` (iin/phone/email как ИМЕНОВАННЫЕ поля структуры), а не свободный текст. `BugReport.description` — свободный текст без структуры, требует другого подхода (regex по содержимому, не по имени поля) — не переиспользовать `mask_employee_data`, писать отдельный скрабер.
- **`record()` уже готов к вызову вне HTTP.** `_SYSTEM_IP = "0.0.0.0"`-сентинел (`apps/audit/services.py`) уже покрывает пустой `get_request_context()` — команда просто вызывает `record()` напрямую, без правки самого сервиса.

### Completion Notes

- **AC-1**: `apps/audit/diagnostics_export.py::build_export` — тонкая `export_diagnostics`-команда только парсит CLI и вызывает оркестрацию. `.zip` содержит ровно 3 файла, живой прогон (`--from 2020-01-01 --to 2030-12-31 --actor test-operator`) подтвердил: `manifest.json` содержит диапазон/actor/timestamp/счётчики/sha256 обоих JSON.
- **AC-2**: `scrub_description` — regex на ИИН-подобные 12-значные последовательности, телефон-подобные паттерны, email. Живой прогон с реальным PII-подобным текстом («Мой ИИН 123456789012, звоните +7 701 234 56 78 или пишите test@example.com») подтвердил все три маскированы в архиве. `AuditLog.old_value`/`new_value` физически отсутствуют в сериализации (`_audit_log_payload` их не читает вовсе) — тест `test_audit_log_export_excludes_old_new_value` пинует это напрямую.
- **AC-3 — реальное отклонение от буквы AC-3 (`entity_id=sha256 архива`), найдено и исправлено ДО отправки на ревью.** `AuditLog.entity_id` — `UUIDField` (`apps/audit/models.py`), а sha256-дайджест — hex-строка, не UUID; буквальная запись сломала бы миграцию/тип поля. Исправлено тем же приёмом, что уже установлен в кодовой базе для нечисловых natural keys (`TomorrowBlockOverride`'s `uuid5`-паттерн, дословно упомянутый в Dev Notes) — `uuid.uuid5(uuid.NAMESPACE_OID, archive_sha256)`, детерминированный, не изобретён с нуля. Полный sha256 сохранён в `new_value.archive_sha256` — ничего не потеряно, просто не в самом `entity_id`.
- **Путь реестра `audit-events.yaml` — стори указала неверно (`apps/audit/audit-events.yaml`), реальный путь — `docs/registries/audit-events.yaml`** (найдено при реализации, не при ревью). `DIAGNOSTICS_EXPORTED` дописана туда — `test_emitted_actions_subset_of_registry` (facet B AST-скан) подтвердил зелёным, живым `make gate`, не декларативно.
- **`--actor`-валидация проверена живьём в обе стороны**: полностью отсутствующий флаг → argparse's `error: the following arguments are required: --actor` (до `handle()` вовсе); пустая строка `--actor ""` → `CommandError: --actor must not be blank` (наш явный гард).
- **Найден и исправлен реальный баг СВОИМ ЖЕ тестом (не ревью), до отправки на ревью**: `_audit_log_payload`'s `"id": r.id` — `AuditLog.id` тоже `UUIDField`, `json.dumps` упал бы `TypeError: Object of type UUID is not JSON serializable` на ЛЮБОМ непустом `AuditLog`-экспорте (мой первый прогон живого теста имел ПУСТУЮ `audit_logs`-таблицу — баг не проявился бы, пока тест `test_audit_log_export_excludes_old_new_value` не посеял РЕАЛЬНУЮ строку). Исправлено: `"id": str(r.id)`.
- **AC-5**: `make gate` — 2989 passed (было 2981), `ruff check` чисто, миграций-drift нет (новых моделей эта стори не добавляет).
- **Живой E2E-прогон целиком** (не только юнит-тесты): реальная `BugReport`-строка с PII-подобным текстом → `export_diagnostics` → распакованный `.zip` → визуально подтверждено маскирование → `AuditLog`-запись с `action=DIAGNOSTICS_EXPORTED`, `ip_address=0.0.0.0` (сентинел, не HTTP-контекст) реально существует в БД после прогона.
