# Story 12.7: Полная деплой-репетиция

Status: ready-for-dev

## Story

As a **разработчик**,
I want **подтвердить рунбук 1.9 (перенос носителем → load → up → smoke) на РЕАЛЬНОМ бандле текущего приложения (не hello-world спайка) настолько, насколько это проверяемо БЕЗ физического целевого контура/FF100/4ГБ-железа, и явно задокументировать, что именно осталось заблокировано на реальном контуре**,
so that **day-X подготовлен максимально возможно из этой среды, а оставшийся разрыв (физический перенос, FF100-браузер, 4ГБ-машина) явно виден как ручной шаг, а не молчаливый пробел**.

## Scope Decision (найдено при create-story — критично для скоупа)

Буква эпика (`epics.md#L1327-1333`) требует: «прогон пути носителя с РЕАЛЬНЫМ бандлом по рунбуку 1.9 (реплика/контур), смок на архивном FF100, прогон на целевой 4ГБ-машине». **Ни один из трёх физических компонентов не выполним в текущей среде разработки:**

1. **Реальный/реплика закрытый контур** — `deploy/spike-1.9/RUNBOOK.md` уже документирует, что путь A (реальный контур) заблокирован гейтом A5 (эскалация заказчику составлена, но не отправлена/без ответа на момент спайка 1.9) — путь B (dev-реплика) был выбран ТОГДА по этой же причине. Ничего не изменилось: у агента в этой среде нет доступа к реальному закрытому LAN-контуру заказчика.
2. **Архивный FF100 (Firefox ~100 ESR)** — `architecture.md:260` явно отмечает: «Playwright на FF100 невозможен (патченые сборки)» — это не просто «браузер недоступен агенту», это специальная патченая сборка, которую спайк 1.9 тоже не смог получить (`UNVERIFIED-pending-contour` в RUNBOOK.md).
3. **Целевая 4ГБ-машина** — физическое оборудование заказчика, недоступное из dev/CI-среды.

**Решение (зафиксировано пользователем при create-story, опция «сделай, что можно»):** стори переопределена на CI-АВТОМАТИЗИРУЕМОЕ подмножество — реальный прогон deploy-rehearsal.sh (12.5) на ТЕКУЩЕМ ПОЛНОМ бандле приложения (не hello-world спайка 1.9), подтверждающий, что весь путь `bundle.sh → sha-check → load → up → migrate → smoke` (12.2/12.3/12.5) по-прежнему зелёный на актуальном коде — плюс явное обновление `RUNBOOK.md` статусом «переподтверждено на полном бандле, физические пункты остаются `UNVERIFIED-pending-contour`». Три физических пункта выше остаются explicitly blocked — задокументированы как ручной follow-up для оператора с реальным доступом к контуру/FF100/железу, не помечены `done` и не сымитированы.

3. **AC-3 (RUNBOOK.md переподтверждён на актуальном коде).** `deploy/spike-1.9/RUNBOOK.md`'s таблица шагов (раздел 1) дополнена записью «переподтверждено на полном бандле [дата, sha]» для VERIFIED-на-dev строк; физические `UNVERIFIED-pending-contour` строки (перенос носителем, LAN-доступ с клиента, FF100) НЕ переводятся в VERIFIED — остаются заблокированными, с явной пометкой, что 12.7 не смогла их снять по той же причине, что и сам спайк (нет доступа к реальному контуру/FF100/4ГБ-железу).
4. **AC-4 (явный ручной follow-up задокументирован).** Story File Completion Notes перечисляет ТРИ оставшихся физических шага как чек-лист для оператора с реальным доступом (перенести бандл физическим носителем в контур → `install.sh` → smoke; открыть с клиента через архивный FF100; прогнать на целевой 4ГБ-машине) — со ссылкой на уже готовые `CHECKLIST.md`/`install.sh`/`smoke.sh` (12.2-12.5), которые оператор использует БЕЗ дополнительной разработки.

## Dev Notes

- **Это НЕ повтор 12.5.** 12.5 доказало, что `deploy-rehearsal.sh` МЕХАНИЗМ работает (на тестовом окружении, включая параллельно с реальным prod-стеком). 12.7 (в этом переопределённом скоупе) доказывает, что тот же механизм ОСТАЁТСЯ зелёным на ТЕКУЩЕМ полном бандле приложения (а не тестовой конфигурации) — регрессионная проверка перед реальным day-X, не первое доказательство концепции.
