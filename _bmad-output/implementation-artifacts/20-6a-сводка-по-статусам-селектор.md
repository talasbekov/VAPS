# Story 20.6a: Отчёт «сводка по статусам» — именованный агрегат (селектор)

Status: done

## Story

As a **держатель права `status.view`** (потребитель будущего отчёта),
I want **получить сводку по статусам (org-wide/по-подразделению, по 11 отчётным колонкам) ЧЕРЕЗ ИМЕНОВАННУЮ функцию, не разбираясь во внутренностях `StrengthReportService`**,
so that **FR-40's «отчёт «сводка по статусам»» закрыт явным, тестируемым контрактом, а не подразумевается как побочный эффект другой функции**.

## Scope Decision

- **Разбор эпика**: epics.md's Story 20.6 — «Отчёт «сводка по статусам»». Исследованием подтверждено: РАСЧЁТ уже полностью существует — `StrengthReportService.compute(business_date, division_id).totals` (`ReportTotals`, `apps/operations/statuses/services/strength_report.py`) УЖЕ агрегирует по всем 11 отчётным колонкам (`SICK`/`VACATION`/`COMMAND`/.../`IN_SERVICE`) — org-wide при `division_id=None`, по поддереву при заданном `division_id` (`derive_report()`'s totals-цикл, строки 158-221, суммирует `columns` по КАЖДОМУ подразделению, `ARCH-DATA-025`'s convergence-инвариант `Σ columns == Список` уже перепроверен на totals). Эта стори НЕ строит новый расчёт — она даёт ему ИМЯ и ЯВНЫЙ, узкий контракт.
- **`compute_status_summary(business_date, division_id=None) -> ReportTotals`** — тонкая обёртка в ТОМ ЖЕ файле (`strength_report.py`, не новый модуль — тот же принцип, что `compute_fact_load`→`compute_fact_load_bulk` обёртка в 20.3a, обёртка живёт РЯДОМ с оборачиваемым). Возвращает ТОЛЬКО `.totals` (не весь `StrengthReportResult` с построчными `rows`/`violations`/`warnings` по каждому подразделению) — «сводка по статусам» по определению НЕ построчный отчёт (это Story 20.5/«штатное расписание»'s домен), а агрегат.
- **Почему отдельная именованная функция, а не «просто использовать `.totals`»**: будущий API-слой (20.6b) не должен знать, что «сводка по статусам» — побочный продукт функции, чьё ИМЯ («штатность/расход») не намекает на статусы. Явное имя `compute_status_summary` — контракт, который переживёт рефакторинг `StrengthReportService`'s внутренностей (если тот когда-нибудь перестанет попутно считать totals, эта обёртка — единственное место, которое нужно поправить).
- **11 отчётных колонок (уже collapsed), НЕ per-StatusType детализация** — `REPORT_COLUMN_BY_CODE` (существующий) уже схлопывает 17 `StatusType`-кодов (`SICK_LEAVE`/`LEAVE_BY_REPORT`/`VACATION`/`STUDY`/`COMPETITION`/`CONFERENCE`/...) в 11 колонок. Донор-спека/epics.md НЕ запрашивают более гранулярную разбивку — эта стори НЕ строит альтернативный per-StatusType агрегат.
- **Out of scope**: API/эндпоинт HTTP-слоя (20.6b); экран/печатная форма отчёта (20.6c+); экспорт `.csv`/`.xlsx` (20.4-семейство, отдельная интеграция); per-StatusType (не-collapsed) детализация (не запрошена); изменение `StrengthReportService.compute()`/`derive_report()`'s поведения (только явная обёртка поверх, никакой новой логики).

## Acceptance Criteria

1. **AC-1.** `compute_status_summary(business_date)` (без `division_id`) возвращает `ReportTotals`, ИДЕНТИЧНЫЙ `.totals`, который вернул бы прямой вызов `StrengthReportService.compute(business_date)`.
2. **AC-2.** `compute_status_summary(business_date, division_id=X)` возвращает `.totals`, ИДЕНТИЧНЫЙ `.totals` прямого вызова `StrengthReportService.compute(business_date, division_id=X)` (агрегат по поддереву `X`, не по всему орг).
3. **AC-3.** Результат — `ReportTotals` с полями `staff_total`/`list_total`/`vacancies`/`columns` (11 ключей)/`attached` — та же форма, что существующий тип, не переупакован в новый dict/класс.
4. **AC-4.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- API/эндпоинт HTTP-слоя (20.6b).
- Экран/печатная форма отчёта (20.6c+).
- Экспорт `.csv`/`.xlsx` (20.4-семейство).
- Per-StatusType (не-collapsed) детализация.
- Изменение `StrengthReportService`/`derive_report()`'s поведения.
