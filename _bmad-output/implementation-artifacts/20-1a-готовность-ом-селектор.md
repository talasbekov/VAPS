# Story 20.1a: Готовность ОМ — агрегатный селектор блокеров (селектор)

Status: done

## Story

As a **держатель права `event.manage`/`status.view`** (потребитель будущего дашборда),
I want **получить агрегированный снимок «что не готово» для одного ОМ (чек-лист/потребность/расстановка/ознакомление/конфликты) ОДНИМ вызовом**,
so that **будущий дашборд готовности ОМ (FR-38, UC-DASH-001) сможет показать блокеры и % готовности без собственной агрегации по 5 разным таблицам**.

## Scope Decision

- **Разбор эпика**: epics.md's Story 20.1 — «Дашборд готовности ОМ (FR-38)». `extract-usecases.md`'s UC-DASH-001 (донор-контекст, найден исследованием) явно перечисляет состав «готовности»: **блокеры** (чек-лист, потребность утв/закрыта, ознакомление, расстановка утв) + % готовности + «что не готово и где задержка» — это НЕ единое булево поле, а СОСТАВНОЙ снимок из 4 независимых источников.
- **Декомпозиция по CLAUDE.md** (тот же паттерн, что 19.4a/19.5a/19.6a): эта стори = ТОЛЬКО backend-селектор (чтение, агрегация). API-эндпоинт, экран дашборда, WS-live-обновления (`ACK_REQUIRED`/`ACK_MISSING_ESCALATION`, уже зарезервированы в `docs/registries/ws-message-types.yaml`, 16.6) — будущие стори (20.1b+), создаются отдельно.
- **`SecurityEventReadinessSelector.readiness_for(event)`** — НОВЫЙ метод в УЖЕ СУЩЕСТВУЮЩЕМ `apps/operations/events/selectors.py` (не новый модуль): файл уже содержит `SecurityEventArchiveSelector` (18.2) — тот же паттерн («plain classes, @staticmethod queries», «Plain-dict return — не DRF-сериализатор, это API-слоя забота»). Живёт в `apps.operations.events`, не `apps.operations.load` (в отличие от 19.6a) — все 4 источника блокеров (чек-лист/потребность/расстановка/ознакомление) — модели ИМЕННО `events`-домена, cross-domain импорта не требуется.
- **4 независимых блокера** (компонентная модель, не единая формула):
  1. **Чек-лист** — `SecurityEventChecklistItem.done` (event-scoped, 15.3a): готов, если ВСЕ пункты `done=True` (пустой чек-лист — вырожденно готов, тот же принцип, что «нет данных = не блокирует», см. 19.6a's аналогичное решение для пустого агрегата).
  2. **Потребность утверждена/закрыта** — донор-спека НЕ даёт отдельного «approved»-флага у `SecurityEventStaffingDemand` (модель — просто строки потребности, `need`, без статуса). Утверждение потребности выражено ПЕРЕХОДОМ `SecurityEvent.status_code` через `DEMAND` (см. `StatusCode`-цикл, 15.x) — готово, если `event.status_code` НЕ `DRAFT`/`BULLETIN`/`RECON`/`DEMAND` (т.е. прошло эту стадию цикла: `BROKERAGE` и далее).
  3. **Расстановка утверждена** — `AssignmentVersion.is_current=True` строка с `status == APPROVED` (16.1). НЕТ текущей версии ИЛИ текущая версия не `APPROVED` → не готово.
  4. **Ознакомление** — ВСЕ `PlacementAssignment` строки ТЕКУЩЕЙ версии (`version__is_current=True`) имеют `acknowledged_at IS NOT NULL`. Нет назначений вообще → вырожденно готово (нечего подтверждать) — ТОТ ЖЕ вырожденный случай, что чек-лист.
  5. **Конфликты** (доп. блокер, найден исследованием, epics.md's UC-DASH-001 не называет явно, но `conflict_severity` — прямой сигнал незакрытого конфликта) — ВСЕ `PlacementAssignment` строки текущей версии имеют `conflict_severity == ""` (пусто/не заполнено — `ConflictSeverity`-choices `blank=True`, реальная детекция — 16.3, ещё не реализована в этой кодовой базе; поле УЖЕ существует, читаем как есть).
- **% готовности** — `100 * (число TRUE-блокеров) / 5` (простое равновзвешенное среднее по 5 булевым индикаторам — донор-формулы для взвешивания нет, `UC-DASH-001` не задаёт веса; PROVISIONAL: равный вес каждого блокера, подлежит подтверждению с Bratan, если появится другая формула).
- **Возвращает `Dict`**: `{"checklist_ready": bool, "demand_ready": bool, "placement_ready": bool, "acknowledgement_ready": bool, "conflicts_ready": bool, "readiness_pct": int}` — плоский словарь, тот же стиль, что `SecurityEventArchiveSelector.full_history()`.
- **НЕ материализует, НЕ кэширует** — вычисляется на лету при каждом вызове (тот же принцип, что `compute_plan_load`/`compute_cumulative_service_hours`, 19.1/19.6a) — Story 20.1's дашборд по своей природе «живой», материализация создала бы риск рассинхронизации без явного триггера инвалидации.
- **Один event за вызов, НЕ bulk-список** — в отличие от 19.5a's bulk-подхода (список подразделений): «дашборд готовности» по UC-DASH-001 — это ЭКРАН ОДНОГО события (детализация «что не готово и где задержка» требует показать КОНКРЕТНЫЕ незакрытые пункты чек-листа/неподтверждённые назначения, не агрегат по многим событиям сразу). Bulk-версия (список активных ОМ с их % готовности) — если понадобится для сводного дашборда — отдельная будущая стори, не изобретается здесь без явного запроса.
- **Out of scope**: API/эндпоинт HTTP-слоя (20.1b); экран дашборда, live WS-обновления (20.1c+); bulk-версия по списку событий (не запрошена, отдельная стори при необходимости); детальный список «что именно не готово» (конкретные незакрытые пункты чек-листа/неподтверждённые сотрудники) — эта стори даёт ТОЛЬКО булевы флаги+%, не детализацию (UC-DASH-001's «где задержка» — вероятно отдельный drill-down эндпоинт, вне scope backend-агрегата верхнего уровня); реальная детекция конфликтов (16.3, ещё не существует — читаем поле `conflict_severity` как есть, каким бы оно ни было).

## Acceptance Criteria

1. **AC-1.** Событие с ПУСТЫМ чек-листом (0 строк `SecurityEventChecklistItem`) → `checklist_ready=True` (вырожденно готов).
2. **AC-2.** Событие с чек-листом, где ХОТЯ БЫ ОДИН пункт `done=False` → `checklist_ready=False`; ВСЕ `done=True` → `checklist_ready=True`.
3. **AC-3.** Событие в статусе `DRAFT`/`BULLETIN`/`RECON`/`DEMAND` → `demand_ready=False`; в `BROKERAGE`/`PLACEMENT`/`APPROVED`/`IN_PROGRESS`/`CLOSED` → `demand_ready=True`.
4. **AC-4.** Нет текущей `AssignmentVersion` ИЛИ текущая версия НЕ `APPROVED` → `placement_ready=False`; текущая версия `APPROVED` → `placement_ready=True`.
5. **AC-5.** Текущая версия БЕЗ назначений (`PlacementAssignment`) → `acknowledgement_ready=True` (вырожденно готов); хотя бы одно назначение с `acknowledged_at IS NULL` → `False`; ВСЕ с `acknowledged_at IS NOT NULL` → `True`.
6. **AC-6.** Текущая версия с хотя бы одним назначением, где `conflict_severity != ""` → `conflicts_ready=False`; ВСЕ пустые → `conflicts_ready=True`.
7. **AC-7.** `readiness_pct` — целое число `0..100`, кратное 20 (5 равновзвешенных индикаторов): все 5 `True` → 100; все 5 `False` → 0; 3 из 5 `True` → 60.
8. **AC-8.** Функция принимает ОДИН запрос на чек-лист + ОДИН на назначения текущей версии (не N+1 по пунктам чек-листа/назначениям) — `assertNumQueries` с разумным верхним пределом (≤5 запросов суммарно, включая чтение `event.status_code`/текущей версии).
9. **AC-9.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- API/эндпоинт HTTP-слоя (20.1b).
- Экран дашборда, live WS-обновления через `ACK_REQUIRED`/`ACK_MISSING_ESCALATION` (20.1c+).
- Bulk-версия по списку событий (не запрошена).
- Детальный drill-down «какие именно пункты не готовы» (только булевы флаги+% в этой стори).
- Реальная детекция конфликтов (16.3, читаем `conflict_severity` как есть).

Новый класс `SecurityEventReadinessSelector` добавляется В ЭТОТ ЖЕ файл, не новый модуль.
- `apps/operations/events/models.py:143-158` (`SecurityEventChecklistItem`) — `event.checklist_items` (related_name), `done` (BooleanField). Один запрос: `event.checklist_items.values_list("done", flat=True)` → `all(done)` в Python (пустой список → `all([])==True`, ровно вырожденный случай AC-1, встроенное поведение Python, не нужен явный if-guard).
- `apps/operations/events/models.py:38-53` (`SecurityEvent.StatusCode`) — цикл `DRAFT → BULLETIN → RECON → DEMAND → BROKERAGE → PLACEMENT → APPROVED → IN_PROGRESS → CLOSED` (+ `CANCELLED`). «Потребность утверждена» = `status_code` НЕ в `{DRAFT, BULLETIN, RECON, DEMAND}` — простое множество-проверка, `event.status_code` уже загружен на объекте (не требует доп. запроса, если `event` передан как ORM-инстанс, не голый UUID — см. сигнатуру ниже).
- `apps/operations/events/models.py:382-420` (`AssignmentVersion`) — `event.assignment_versions.filter(is_current=True).first()` (тот же паттерн, что `SecurityEventArchiveSelector.full_history()`, строка `current_version = event.assignment_versions.filter(is_current=True).first()` — БУКВАЛЬНО копировать этот вызов, не изобретать новый). `.status == AssignmentVersion.Status.APPROVED` — прямое сравнение.
- `apps/operations/events/models.py:487-543` (`PlacementAssignment`) — `related_name="assignments"` на `AssignmentVersion`. Если текущая версия существует: ОДИН запрос `current_version.assignments.values_list("acknowledged_at", "conflict_severity")` — переиспользовать РЕЗУЛЬТАТ ЭТОГО ОДНОГО запроса для ОБОИХ блокеров (ознакомление + конфликты), не два отдельных запроса (AC-8's лимит запросов).
- **Сигнатура функции — принимает `event`-ОБЪЕКТ (не `event_id`)**: в отличие от 19.5a/19.6a (принимают `employee_id`/UUID), эта стори следует `SecurityEventArchiveSelector.full_history(event)`'s буквальному прецеденту (принимает ORM-инстанс, не ID) — тот же файл, тот же стиль, каждый лишний запрос на перезагрузку события избегается.
- **Порядок вычисления блокеров, если `event` без текущей версии** (`AssignmentVersion` ещё не создана — событие на ранней стадии цикла, `DRAFT`/`BULLETIN`/etc.): `placement_ready=False` (нет утверждённой версии), `acknowledgement_ready` и `conflicts_ready` — ВЫРОЖДЕННО `True` (нет назначений текущей версии, потому что версии вообще нет — тот же принцип «нечего проверять = не блокирует», AC-5/AC-6 formulate это для «версия без назначений», тест ДОЛЖЕН явно покрыть и подслучай «версии вообще нет»).
- `apps/operations/events/tests/test_service_hours.py`/`test_post_overload.py` (18.4/18.5) — структурный образец фикстур для `SecurityEvent`/`AssignmentVersion`/`PlacementAssignment` (`FacilityObject`, `Post`, `AssignmentVersion.objects.create(...)`, `PlacementAssignment.objects.create(...)`) — переиспользовать паттерн создания фикстур, не изобретать заново.
- **CAVEAT для будущего потребителя (20.1b/c, ревью Blind Hunter + Edge Case Hunter)**: вырожденные `True`-умолчания МОГУТ дать обманчиво высокий `readiness_pct` для СОВСЕМ свежего события (пустой чек-лист + нет версии → `checklist_ready`/`acknowledgement_ready`/`conflicts_ready` все вырожденно `True`, реальны только `demand_ready`/`placement_ready`) — событие, где буквально ничего не сделано, может показать 60% «готовности» едва пройдя `DEMAND`-стадию. Это НАМЕРЕННОЕ scope-решение (тот же принцип «нечего проверять = не блокирует», что везде в проекте — 19.6a, `month_calendar()`), не баг этой стори, но будущий экран дашборда (20.1c) ОБЯЗАН показывать блокеры раздельно (что и требует UC-DASH-001), не ТОЛЬКО агрегатный %, — иначе % станет вводящим в заблуждение summary-числом.
- **`CANCELLED`-статус исключён из `demand_ready`-набора явно** (ревью, 2 независимых агента совпали): без явного добавления в `_DEMAND_NOT_READY_CODES` blocklist-подход пропустил бы `CANCELLED` как «готов» (не входит в 4 явно перечисленных «не готов» кода) — отменённое событие никогда не «готово» ни по какому блокеру. PROVISIONAL: ни AC-3, ни UC-DASH-001 явно не называют `CANCELLED`; подлежит подтверждению с Bratan, если появится другая семантика (например «CANCELLED = не применимо» вместо «не готово»).
