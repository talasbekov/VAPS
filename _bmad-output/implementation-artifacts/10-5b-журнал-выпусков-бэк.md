# Story 10.5b: Журнал выпусков — бэк

Status: ready-for-dev

## Story

As a **руководитель**,
I want **HTTP-роут, отдающий ВСЮ историю выпусков расхода по подразделению (и ISSUED, и SUPERSEDED, с указанием, какой документ какой заменил и почему)**,
so that **на экране (10.5c) видна цепочка «взамен исх.№ N» целиком, а не только последний действующий документ**.

Источник: `_bmad-output/implementation-artifacts/sprint-status.yaml:385-388` («10.5b — БЭК: журнал выпусков. 1. **AC-1 (`reason`/`supersedes_number`/`supersedes_year` в `IssuedExpenseReportSerializer`).** Given любой ответ, несущий этот сериализатор (`create`/`list`/новый `journal`), Then он несёт `reason` (модельное поле, `""` у v1, непустой у amended-сдачи — `document_release_service.py:310-313`), `supersedes_number`/`supersedes_year` — `int`+`int` предыдущего документа при `supersedes IS NOT NULL`, `null`+`null` при `supersedes IS NULL` (первый выпуск дня). Именование `supersedes_number` — НЕ новое: уже используется в audit-payload (`document_release_service.py:342`), эта стори делает его видимым в API.
2. **AC-2 (новый роут `GET /api/operations/expense-reports/journal/`).** Given `division_id` (query, обязателен — точечный запрос по ОДНОМУ подразделению, «весь скоуп» здесь не имеет смысла, зеркало решения 10.3c AC про `division_id`), Then **200**, пагинированный конверт `{count, next, previous, results}` (зеркало 10.1c `DailySubmissionListResponse`), `results` — ВСЕ документы (`ISSUED` **и** `SUPERSEDED`) подразделения, отсортированные `-business_date, -number` (новые сверху).
3. **AC-3 (существующий point-lookup НЕ меняется).** `GET /api/operations/expense-reports/?division_id=&business_date=` (6.10a) — БЕЗ изменений семантики (по-прежнему одиночный объект-точка или 404). Deferred-work закрывается ДОБАВЛЕНИЕМ `journal`, а не переделкой существующего роута — ломать уже смонтированный фронт-экран 10.5 нельзя.
4. **AC-4 (гейт/scope — зеркало `period`/point-lookup).** Право `daily_report.generate` (`_EXPENSE_PERMISSION`, тот же код, что весь `ExpenseReportViewSet`), `ensure_division_scope`+`_ensure_division_exists` — тот же порядок, что `list`/`period` (exists-проверка ПОСЛЕ scope). 403 чужой scope; 404 нет подразделения.
5. **AC-5 (N+1 не заведён).** Селектор `journal`-запроса использует `select_related("supersedes", "attachment")` — сериализация `sha256`/`supersedes_number`/`supersedes_year` по N строкам НЕ даёт N дополнительных запросов (query-count пин в тесте).
6. **AC-6 (пустой подразделение → пустая страница, не 404).** Given подразделение существует, но выпусков НЕТ, Then **200** `{count: 0, results: []}` — НЕ 404 (404 зарезервирован за point-lookup'ом «конкретной даты», список — за отсутствие данных не наказывает).
7. **AC-7 (RBAC-матрица + схема).** `MATRIX["ops-expense-report-journal"]`; `schema.yaml`/`schema.d.ts` содержат роут и обновлённый `IssuedExpenseReport` (с новыми тремя полями).
8. **AC-8 (регресс нулевой).** `create`/`list`/`period`/`override_block` — без изменений бизнес-логики (только серализатор несёт больше полей — аддитивно, старые консьюмеры полей не теряют). `make gate` зелёный.

## Dev Notes

- **Прямой прецедент по пагинации/стилю — `DailySubmissionViewSet.list` (10.1c/5.8c).** Bare `ViewSet` (не `GenericViewSet`) — `pagination_class` spectacular не читает автоматически, конверт собирается ВРУЧНУЮ (`paginator.paginate_queryset` → `paginator.get_paginated_response`), схема — `inline_serializer` с явными `count/next/previous/results`. Копировать буквально, не изобретать.
- **`journal` — НОВЫЙ роут, НЕ переделка `list`.** Deferred-work (`deferred-work.md:572`) допускал ДВА варианта закрытия: «честный retrieve» (уже есть — существующий `list` де-факто point-lookup) ИЛИ «list-семантика с фильтрами». Эта стори выбирает ВТОРОЙ вариант как ДОБАВЛЕНИЕ, не замену — существующий фронт-экран 10.5 (`ExpenseReportPage.tsx`) уже полагается на точечную семантику `list` (404 = «не выпущен» — читается как штатный ответ, не ошибка, `ExpenseReportPage.tsx:181-186`). Переопределить `list` на реальный список сломал бы 10.5/10.5a без всякой пользы для эпик-AC.
- **`supersedes_number` — уже установленное имя, не изобретение стори.** `document_release_service.py:342` уже кладёт `supersedes_number` в audit-payload (`new_value`) для `DOCUMENT_ISSUED`. Сериализатор просто делает то же значение видимым по API тем же именем — согласованность имён между audit-журналом и HTTP-ответом снижает когнитивную нагрузку читающего логи/API вместе.
- **И ISSUED, и SUPERSEDED в `journal` — осознанно, не забытый фильтр.** Цепочка «взамен исх.№ N» непрослеживаема, если видна только текущая ISSUED-строка: 10.5c ("UI журнала выпусков") должна нарисовать ВСЮ историю, включая замещённые документы (они и несут смысл цепочки).
- **`select_related` — обязателен, не оптимизация «на будущее».** `IssuedExpenseReportSerializer` уже читает `attachment.sha256` (существующее поле) и теперь ещё `supersedes.number`/`supersedes.year` — без `select_related("supersedes", "attachment")` каждая строка журнала — 2 дополнительных запроса, при 50 строках на странице это 100 лишних SELECT. Существующие `create`/`list`/`retrieve`-пути (одна строка) этой проблемы не имеют — там N+1 несущественен на N=1.
