# Story 19.2: Агрегатный детектор перегрузки — >3 дней подряд по 8+ часов

Status: done

## Story

As a **держатель права `event.manage`**,
I want **определить, какие календарные дни сотрудника входят в серию из БОЛЕЕ ЧЕМ 3 дней подряд с нагрузкой 8+ часов**,
so that **это станет единым источником для подсветки перегрузки на дашборде (Epic 20) и при назначении (будущая интеграция в конфликт-детектор расстановки), а не пересчитывается заново каждым потребителем**.

## Scope Decision

- **Разбор FR-32's ВТОРОЙ половины**: `«подсвечивает перегрузку (свыше 3 дней подряд по 8+ часов ... ) на дашборде и при назначении»`. ПЕРВАЯ половина («превышение предельного времени Поста», per-instance) — уже Story 18.5 (`flag_post_overload`). ЭТА стори — агрегатное, много-дневное правило, явно вынесенное в заголовок Story 19.2 (epics.md:1462) и явно НЕ реализованное в 18.5 (та стори's Scope Decision: «агрегатный >3-дневный детектор — Story 19.2, не эта стори»).
- **«Свыше 3 дней подряд»** — прочитано буквально: серия ДОЛЖНА содержать СТРОГО БОЛЬШЕ 3 подряд идущих календарных дней (т.е. МИНИМУМ 4), каждый из которых `>= 8` часов, чтобы считаться перегрузкой. Ровно 3 дня подряд по 8+ часов — НЕ перегрузка (граница «свыше», не «от»). Открытый вопрос (если Bratan увидит на живой демонстрации иначе — «от 3 дней» тоже разумное чтение) — задокументировано как PROVISIONAL-выбор, не немой дефолт.
- **Чистая функция над `Dict[date, Decimal]`** — `detect_overload_days(day_hours, *, threshold_hours=Decimal("8"))`, принимает ГОТОВЫЙ результат `compute_plan_load()`/`compute_fact_load()` (19.1), НЕ делает собственных запросов к БД. И план, и факт могут быть перегружены — вызывающая сторона выбирает, какой из двух передать (дашборд, вероятно, оба; «при назначении» — план). Эта стори не решает, ЧТО передаётся — только сам алгоритм детекции над одним переданным dict.
- **Никакой персистентности** — как и 19.1, результат не хранится: агрегат вычисляется по требованию из `apps.operations.load.selectors`' результатов. Нет новой модели, нет миграции.
- **Не переиспользует и не трогает `_workload_conflicts()`** (`events/services.py:687`, Story 16.3d) — та же граница, что уже проведена в 18.5's Scope Decision: `_workload_conflicts()` — ПЛАНОВЫЙ конфликт-детектор расстановки (другой слой цикла ОМ, другие данные — соседние `PlacementAssignment` того же черновика, не общий `Dict[date, Decimal]` за произвольный период), не расширяется и не заменяется этой стори.
- **Возвращает `List[date]`** — отсортированный список ВСЕХ дней, входящих хотя бы в одну квалифицирующую серию (не только «первый день серии» — потребителю на дашборде/календаре нужно подсветить КАЖДЫЙ день серии, не начало).
- **Out of scope**: справочник коэффициентов поправок (19.3, влияет на САМ лимит часов — здесь лимит фиксированный параметр функции, не читается из справочника); интеграция подсветки в `_workload_conflicts()`/API расстановки («при назначении», будущая стори — не эта); дашборд/экран (Epic 20); календари (19.4/19.5); карточка сотрудника (19.6); API/эндпоинт HTTP-слоя.

## Acceptance Criteria

1. **AC-1.** Ровно 4 дня подряд, каждый `>= 8` часов → ВСЕ 4 дня попадают в результат.
2. **AC-2.** Ровно 3 дня подряд, каждый `>= 8` часов (граница «свыше 3», не «от 3») → результат НЕ включает ни один из этих дней.
3. **AC-3.** 5 дней подряд, каждый `>= 8` часов, но ОДИН день в середине серии `< 8` часов (серия прерывается) → прерывание делит на две суб-серии по ≤3 дня каждая (2+2) → результат пустой (ни одна суб-серия не превышает 3).
4. **AC-4.** Два дня подряд `>=8`, затем ПРОПУЩЕННЫЙ день (отсутствует ключ в `day_hours`, не 0) → серия прерывается пропуском так же, как явным днём `<8` (пропущенный день не считается ни продолжением, ни `>=8`).
5. **AC-5.** Пограничное значение РОВНО `8.00` часов — засчитывается как перегруженный день (`>= 8`, не `> 8`); `7.99` — не засчитывается.
6. **AC-6.** ДВЕ раздельные квалифицирующие серии в одном вызове (напр. 4 дня подряд, разрыв, ещё 4 дня подряд) → результат содержит дни ОБЕИХ серий.
7. **AC-7.** Пустой входной `day_hours={}` → пустой результат, без исключений.
8. **AC-8.** Настраиваемый `threshold_hours` (напр. `Decimal("6")`) — правило применяется с ПЕРЕДАННЫМ порогом, не жёстко зашитыми 8 часами.
9. **AC-9.** `make gate` (Backend/VAPS) зелёный.

## Dev Notes

- `apps/operations/load/selectors.py` (Story 19.1, уже существует) — `compute_plan_load(employee_id, start_date, end_date)`/`compute_fact_load(employee_id, start_date, end_date)` возвращают `Dict[datetime.date, Decimal]`, ключи — ТОЛЬКО дни с ненулевой активностью (sparse dict, НЕ dense-диапазон — 19.1's Blind Hunter-находка, задокументирована как by-design: "downstream consumers assuming a dense dict over the full date range would get a `KeyError`"). ЭТА стори обязана трактовать ОТСУТСТВУЮЩИЙ ключ как разрыв серии (AC-4), а не как `0`, поскольку 19.1 намеренно не заполняет нулевые дни — так что "пропуск" и "0 часов" неразличимы во входном dict, но семантически ОБА прерывают серию одинаково (день без активности не может быть частью серии 8+ часов).
- Алгоритм: отсортировать ключи `day_hours` по возрастанию, пройти линейно, накапливая текущую серию ПОДРЯД ИДУЩИХ дат (`day - previous_day == timedelta(days=1)`) с `hours >= threshold_hours`; при разрыве (не подряд ИЛИ `hours < threshold_hours`) — если накопленная серия длиннее 3 дней, добавить её целиком в результат, затем сбросить накопитель. Не забыть проверить финальную серию ПОСЛЕ цикла (последняя серия не завершается явным разрывом).
- Работает НАД ЛЮБЫМ `Dict[date, Decimal]`, включая как результат `compute_plan_load()`, так и `compute_fact_load()`, так и произвольный dict в тестах (тесты этой стори НЕ обязаны создавать `DutyShift`/`SecurityEvent`/`PlacementAssignmentActual` через БД — чистая функция, dict передаётся литералом, `pytest.mark.django_db` не нужен).
- `apps/operations/events/services.py:687` (`_workload_conflicts`, 16.3d) — НЕ читать, НЕ трогать, НЕ импортировать отсюда (разные слои/данные, см. Scope Decision выше и 18.5's Dev Notes с тем же разбором).
