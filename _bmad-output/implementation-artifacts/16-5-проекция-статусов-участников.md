# Story 16.5: Проекция статусов участников (OM_AUTO «выделен на мероприятие»)

Status: done

## Story

As a **система**,
I want **автоматически проставлять сотруднику статус «привлечён на мероприятие» при утверждении Расстановки**,
so that **расход/КУ видят реальную занятость участника без ручного дублирования статуса (epics.md Story 16.5, `EVENT_ASSIGNMENT`)**.

## Scope Decision (найдено при create-story)

- **Буквальный аналог `project_duty_shift()`/`approve_duty_plan()` (14.9a/BR-017), перенесённый в домен Расстановки.** Тот же паттерн: один хелпер-проектор на строку (`project_placement_assignment(assignment)`), вызываемый в цикле ВНУТРИ `approve_assignment_version()`'s существующего `transaction.atomic()`-блока (уже держит `select_for_update()` на версии — доп. лока не требуется, сериализация уже есть), идемпотентно через `EmployeeStatus.objects.get_or_create(source_ref=...)`.
- **Код статуса — `EVENT_ASSIGNMENT`, уже засеян.** `apps/operations/statuses/management/commands/seed_statuses.py`: `("EVENT_ASSIGNMENT", "Привлечён на мероприятие", 80, "IN_SERVICE")` — НЕ в `HARD_BLOCK_CODES`, значит SOFT (не участвует в `excl_hard_status_overlap`-констрейнте БД, `EmployeeStatus.Meta`). Конфликты (двойное назначение и т.п.) уже отловлены на этапе `approve_assignment_version()`'s `detect_placement_conflicts()`-гейта (16.3b/c/d) до этой точки — проекция НЕ дублирует конфликт-детекцию, просто фиксирует факт после утверждения.
- **Дата-диапазон проекции — из `event.starts_at/ends_at`, через `_to_date_range()` (та же конвертация, что 16.3a-d уже используют).** `PlacementAssignment` не хранит собственное время (16.3d's Scope Decision уже это устанавливает — event-level granularity). Если у события НЕТ расписания (`event.starts_at`/`ends_at` пусты) — проекция для строк ЭТОЙ версии ПРОПУСКАЕТСЯ целиком (нет данных = недостижимо, тот же принцип, что 16.3b/c/d's `event_has_schedule`-гард); утверждение версии НЕ блокируется отсутствием расписания (approve уже проходит вне зависимости от расписания — новый гард здесь не изобретается).
- **Проекция вызывается ТОЛЬКО на РЕАЛЬНОМ переходе `SUBMITTED->APPROVED`, не на идемпотентном replay.** `approve_assignment_version()`'s собственный ранний `if version.status == APPROVED: return version` (буквальная idempotent-replay-семантика, установленная 16.4, та же форма, что `submit_assignment_version()`/`issue_bulletin()`) — эта стори НЕ переоткрывает это решение: замена на «повторный approve тоже досчитывает проекцию» была бы новым поведением, не запрошенным ни эпиком, ни существующим кодом (единственный прецедент, `approve_duty_plan()`, ре-проецирует на повторном approve, НО там `was_draft`-гард тоже не блокирует projection-цикл — другая структура функции; `approve_assignment_version()`'s early-return устроен иначе и его переписывание — вне объёма этой стори).
- **Отмена/снятие проекции при отмене мероприятия или пере-утверждении — ЯВНО вне объёма.** Grep всей кодовой базы — НЕТ функции отмены `SecurityEvent`/АssignmentVersion после APPROVED (`SecurityEvent.StatusCode.CANCELLED` существует в enum, но ни один сервис его не устанавливает); Epic 17 (`Story 17.3: Оперативные изменения после утверждения — только с санкцией + версия`) — явно названная территория пост-утверждённых изменений, включая, предположительно, снятие/замену участника (17.5 «каскадная замена выбывшего»). Изобретать cancel-проекцию здесь означало бы решать проблему раньше её родной стори без спецификации отмены.

## Acceptance Criteria

1. **AC-1 (проекция на реальном approve).** `approve_assignment_version(version, actor=...)` на РЕАЛЬНОМ переходе `SUBMITTED->APPROVED`, событие с расписанием — для КАЖДОЙ строки `version.assignments` создаётся `EmployeeStatus` со `status_type_code="EVENT_ASSIGNMENT"`, `source=OM_AUTO`, `source_ref=f"EVENT_ASSIGNMENT:{assignment.pk}"`, `date_start`/`date_end` = `_to_date_range(event.starts_at, event.ends_at)`.
2. **AC-2 (идемпотентность по source_ref).** Повторный вызов `project_placement_assignment()` для ТОЙ ЖЕ строки — `get_or_create` не создаёт дубликат (та же `source_ref`), не падает.
3. **AC-3 (нет расписания — пропуск проекции, approve не блокируется).** `event.starts_at`/`ends_at` пусты — approve всё равно завершается (`status` → `APPROVED`), но НИ ОДНА `EmployeeStatus`-строка не создаётся ни для одной строки версии.
4. **AC-4 (идемпотентный replay approve не досчитывает и не дублирует).** Повторный вызов `approve_assignment_version()` на УЖЕ `APPROVED`-версии (существующая early-return-семантика 16.4) — не создаёт НОВЫХ `EmployeeStatus`-строк сверх тех, что уже спроецированы первым реальным approve (и не падает, если их 0 из-за AC-3).
5. **AC-5 (SOFT — не участвует в hard-overlap-констрейнте).** Проекция для 2 разных сотрудников/событий с пересекающимися датами — обе строки создаются успешно, без `IntegrityError` (`excl_hard_status_overlap` не применяется к `EVENT_ASSIGNMENT`, `HARD_BLOCK_CODES` его не содержит).
6. **AC-6 (несколько назначений одной версии — несколько строк).** Версия с N (`N>1`) строками `PlacementAssignment` для РАЗНЫХ сотрудников — N разных `EmployeeStatus`-строк, каждая со своим `employee_id` и собственным `source_ref` (по pk назначения, не по версии).
7. **AC-7 (комментарий/провенанс не изобретается).** Никаких новых полей на `EmployeeStatus`/`PlacementAssignment` — только `source`/`source_ref` из уже существующих колонок (тот же принцип, что 14.9a).
8. **AC-8 (регресс нулевой).** `make gate` зелёный, миграция чистая (новых полей эта стори не добавляет).

## Out of Scope

- **Отмена/снятие `EVENT_ASSIGNMENT`-проекции** (отменённое мероприятие, снятый/заменённый участник) — Epic 17 (17.3/17.5), нет живого cancel-пути сегодня для проецирования обратно.
- **Проекция при идемпотентном replay approve** — реальный переход уже проецирует; повторный вызов на уже-`APPROVED` — no-op (существующая 16.4-семантика, не переоткрывается).
- **BEFORE_DUTY-аналог** (проекция «до мероприятия») — `epics.md`'s текст Story 16.5 не упоминает такой статус, `EVENT_ASSIGNMENT` — единственный засеянный код для расстановки; не изобретается.
- **Учёт `EVENT_ASSIGNMENT` в конфликт-детекторе (16.3b-d)** — конфликты уже проверяются ДО этой проекции (approve-гейт), обратная связь «спроецированный статус влияет на будущие проверки» — не требуется этой стори (расход/отчёты её просто читают).
- **API/HTTP-обёртка** — Story 16.8.

Реализовано по AC 1-8. `project_placement_assignment(assignment, event)` — новая функция в `apps/operations/events/services.py`, буквальный образец `project_duty_shift()` (14.9a): один `get_or_create(source_ref=f"EVENT_ASSIGNMENT:{assignment.pk}", defaults={...})`-вызов, `status_type_code="EVENT_ASSIGNMENT"`, `source=OM_AUTO`. Отклонение от исходной сигнатуры в Task 1 (`project_placement_assignment(assignment)` → фактически `(assignment, event)`): `event` передаётся явно вызывающей стороной (`approve_assignment_version()`'s уже загруженный `version.event`), а не через `assignment.version.event` — иначе каждая строка тянула бы отдельный запрос на `AssignmentVersion` (N+1), т.к. `version.assignments.all()` не делает `select_related("version__event")`. Не влияет ни на один AC. Вызов — цикл `for assignment in version.assignments.all(): project_placement_assignment(assignment, version.event)` внутри `approve_assignment_version()`'s существующего `transaction.atomic()`, ПОСЛЕ гейта конфликтов, ДО флипа `status`/записи `signature_hash` — единственная реальная транзакция уже держит `select_for_update()` на версии. Гард на отсутствие расписания — внутри `project_placement_assignment()` самой (`if not (event.starts_at and event.ends_at): return`), симметрично `event_has_schedule`-гарду 16.3a-d. 6 новых тестов (AC 1-6 по отдельности; AC-7/AC-8 подтверждены косвенно — миграций нет, новых полей нет), все прошли с первого запуска. `make gate` — 3748 passed (было 3742, +6), 0 regressions, ruff чист, `makemigrations --check --dry-run` — без изменений.

**3-агентное ревью — 1 Medium исправлен (живо подтверждён), остальные — false positive/пре-существующий паттерн, не регресс:**
- **Medium (Blind Hunter, живой пробник подтвердил): `test_approve_projects_event_assignment_status`'s ассерт сравнивал UTC-дату с local-датой — реальное, воспроизводимое окно флейка, не гипотетическое.** `status.date_start == now.date()` сравнивал `timezone.now().date()` (UTC-aware, `.date()` даёт UTC-календарный день) с `_to_date_range()`'s результатом (конвертация в `TIME_ZONE="Asia/Qyzylorda"`, UTC+5). Живая проверка: `datetime(2026,8,1,21,30,tzinfo=UTC).astimezone(Asia/Qyzylorda)` даёт `2026-08-02` — UTC-дата и local-дата РАСХОДЯТСЯ в окне 19:00-23:59 UTC (00:00-04:59 по Кызылорде), тест упал бы именно в это время. **Исправлено**: ассерт теперь сравнивает с `_to_date_range(event.starts_at, event.ends_at)`'s собственным результатом (корректно в любое время запуска), не с сырым `now.date()`.
- **High→OK (Blind Hunter поднял, но сам же объяснил корректно): «неатомарные записи в цикле — partial failure».** Весь цикл — внутри ЕДИНОЙ `transaction.atomic()` (та же, что держит `select_for_update()` версии) — исключение на любой строке откатывает ВСЮ транзакцию целиком (включая флип `APPROVED`), это all-or-nothing по конструкции, не частичный сбой. Тот же паттерн, что `approve_duty_plan()`'s собственный цикл по `project_duty_shift()` — не изобретён здесь, не регресс.
- **High→OK (Blind Hunter поднял; Edge Case Hunter независимо проверил конструкцией и закрыл): «нет уникального DB-констрейнта на `source_ref` — гонка».** `source_ref` ключуется по `assignment.pk` (не по `employee_id`/`version.pk`) — `PlacementAssignment.pk` уникален по построению, так что ДАЖЕ конкурентное утверждение ДВУХ РАЗНЫХ версий, затрагивающих ОДНОГО сотрудника, пишет в РАЗНЫЕ `source_ref`-ключи — не может столкнуться на дубликате. Тот же уровень защиты (`select_for_update()` на версию), что `project_duty_shift()`'s собственный docstring уже принимает как достаточный для ОДНОЙ версии — не новый пробел.
- **Low (Blind Hunter): `get_or_create`'s `defaults` не обновляет `date_start`/`date_end` при повторном вызове с ИЗМЕНИВШИМся расписанием события.** Недостижимо сегодняшним кодом — approve вызывает проекцию РОВНО один раз на реальном переходе (idempotent-replay выходит РАНЬШЕ цикла), нет пути, где `event.starts_at/ends_at` меняется между двумя реальными approve одной версии. Не исправлено — гипотетический сценарий вне текущих call-сайтов, тот же принцип, что «не изобретать защиту от недостижимого».
- **Low (Blind Hunter): N+1 — цикл проекции повторно запрашивает `version.assignments.all()`, а не переиспользует уже загруженный `pairs`.** `pairs` — `values_list()` без `id` в достаточном виде для `source_ref`; экономия одного запроса не стоит усложнения ради этой стори. Не исправлено — тот же класс находки (perf, не корректность), что было принято Low в 16.3d.
