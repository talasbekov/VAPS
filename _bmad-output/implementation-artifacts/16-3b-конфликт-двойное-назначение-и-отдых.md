# Story 16.3b: Конфликт-детектор — двойное назначение и Отдых (FR-25, часть 2/4)

Status: ready-for-dev

## Story

As a **планировщик Расстановки**,
I want **видеть, что сотрудник уже назначен в другое место или ещё отдыхает после дежурства**,
so that **черновик перед согласованием несёт видимые предупреждения, а не тихие противоречия (FR-25/FR-11)**.

## Scope Decision (найдено при create-story)

- **Часть 2/4 расщепления Story 16.3.** 16.3a (done) добавила `SecurityEvent.starts_at`/`ends_at` — пререквизит для ЛЮБОЙ интервальной проверки. Эта часть — только ДВЕ проверки из заголовка Story 16.3 (двойное назначение + Отдых), НЕ «несоответствие Посту» (16.3c) и НЕ «перегрузка» (16.3d, заблокирована открытым продуктовым вопросом FR-32 §8).
- **Прямой прецедент — `validate_duty_plan()` (`apps/operations/duties/services.py`, Story 14.11f), чей ДОКСТРИНГ ЛИЧНО называет это «territory Story 16.3»**: read-only конфликт-скан, переиспользующий `apps.operations.statuses.conflict_matrix.classify_pair()` (FR-11's гибридная hard/soft-матрица, Story 3.4) — тот же паттерн буквально переносится сюда, не изобретается заново.
- **Обе проверки — ФИКСИРОВАННО SOFT**, не через `classify_pair()`'s hard/soft-логику: `docs/registries/error-codes.yaml`'s `conflict_codes`-реестр держит `DOUBLE_ASSIGNMENT_CONFLICT`/`REST_VIOLATION_CONFLICT` ИСКЛЮЧИТЕЛЬНО под `SOFT_CONFLICT_DETECTED` — нет HARD-варианта ни для одного из двух на уровне assignment (в отличие от FR-11's status-уровневого hard-block, `OVERLAPPING_HARD_STATUS`, 422, — другой механизм, другой уровень, НЕ вызывается здесь). Обобщённая проверка «пересечение с ЛЮБЫМ hard-block статусом» (`UNAVAILABLE_STATUS_CONFLICT`/`OVERLAPPING_HARD_STATUS`) — шире заголовка этой стори, НЕ строится здесь (не изобретается без явного запроса).
- **Новое поле `PlacementAssignment.conflict_codes`** (JSONField, список строк) — `conflict_severity` (16.1) сам по себе не несёт, КАКОЙ конфликт сработал, только severity; `SOFT_CONFLICT_DETECTED`'s error-response несёт `conflicts[]` (`docs/registries/error-codes.yaml`) — нужна структура для будущей API-стори (16.8), не изобретается заново каждой последующей проверкой (16.3c/16.3d допишут в ТОТ ЖЕ список, не создадут параллельное хранилище).
- **Гранулярность — событийная** (16.3a's явно флагованное v1-допущение): двойное назначение проверяется как «тот же `employee_id` в ДРУГОМ `AssignmentVersion.is_current=True` строке, чьё `SecurityEvent`-окно пересекается с этим». Оба события ДОЛЖНЫ иметь заполненные `starts_at`/`ends_at` — если у ЛЮБОГО из двух пара не заполнена, пересечение НЕОПРЕДЕЛИМО и пропускается (не считается ни конфликтом, ни его отсутствием — не изобретается предположение без данных).
- **Отдых — против `EmployeeStatus(status_type_code="REST_AFTER_DUTY")`**, переиспользуя ТОТ ЖЕ `_to_date_range()`-хелпер, что `validate_duty_plan()` (`apps/operations/duties/services.py`) — не дублируется (подтверждённая, ревью-закалённая логика локальной таймзоны, дублирование рискует расхождением).
- **Read+write, НЕ блокирует.** Функция ПЕРЕЗАПИСЫВАЕТ `conflict_severity`/`conflict_codes` на каждой строке `PlacementAssignment` версии (полный пересчёт при каждом вызове, не инкрементальный накопитель) — не отклоняет/не блокирует утверждение (это Story 16.4's территория, «согласование с возвратом»).
- **Аудит — НЕ на каждый вызов** (это read+recompute функция, может дёргаться часто, напр. после каждого добавления строки в черновик планировщиком) — аудит-стори для конфликт-скана появится там, где он реально мутирует бизнес-состояние (16.4's согласование), не здесь (тот же принцип, что `validate_duty_plan()` — read-only, без аудита).

## Acceptance Criteria

1. **AC-1 (новое поле).** `PlacementAssignment.conflict_codes` — `JSONField(default=list)`.
2. **AC-2 (двойное назначение обнаруживается).** Сотрудник, назначенный в ДВУХ разных текущих версиях с пересекающимися `SecurityEvent`-окнами — обе строки получают `conflict_severity=SOFT`, `conflict_codes` содержит `DOUBLE_ASSIGNMENT_CONFLICT`.
3. **AC-3 (Отдых обнаруживается).** Сотрудник с активным (не отменённым) `EmployeeStatus(status_type_code="REST_AFTER_DUTY")`, чей календарный интервал пересекается с окном события назначения — строка получает `conflict_severity=SOFT`, `conflict_codes` содержит `REST_VIOLATION_CONFLICT`.
4. **AC-4 (оба конфликта на одной строке — накапливаются).** Строка с ОБОИМИ проблемами — `conflict_codes` содержит ОБА кода, `conflict_severity` остаётся `SOFT` (нет HARD-варианта у этих двух типов).
5. **AC-5 (нет данных о времени события — пропуск, не ложный конфликт).** Оба (текущее и/или candidate) события без `starts_at`/`ends_at` — пересечение НЕ проверяется, строка не помечается конфликтом ИЗ-ЗА отсутствия данных.
6. **AC-6 (без конфликтов — явный сброс).** Повторный вызов после устранения конфликта (например, другая версия перестала быть текущей) — `conflict_severity`/`conflict_codes` СБРАСЫВАЮТСЯ (полный пересчёт, не накопитель, см. Scope Decision).
7. **AC-7 (регресс нулевой).** `make gate` зелёный, миграция чистая.

## Out of Scope

- Несоответствие Посту (`POST_REQUIREMENT_MISMATCH_CONFLICT`) — Story 16.3c.
- Перегрузка (`WORKLOAD_EXCEEDED_CONFLICT`) — Story 16.3d, заблокирована открытым продуктовым вопросом (FR-32 §8, коэффициенты нагрузки).
- Обобщённая проверка «пересечение с ЛЮБЫМ hard-block статусом» на уровне assignment (`UNAVAILABLE_STATUS_CONFLICT`/`OVERLAPPING_HARD_STATUS`-эквивалент) — шире заголовка стори, не строится.
- Блокировка/утверждение на основе конфликтов — Story 16.4.
- Пересечение с `SecurityEventDirectAssignment` (физнаряд) — известный, задокументированный (15.9/16.1) коллизионный риск, НЕ решается здесь (физнаряд «система пассивна» по конструкции, разный уровень цикла).
- API/HTTP-обёртка — Story 16.8.
