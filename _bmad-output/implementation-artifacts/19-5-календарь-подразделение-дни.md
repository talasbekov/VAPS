# Story 19.5a: Bulk-селектор календаря статусов по Подразделению × дни

Status: done

## Story

As a **держатель права `status.view`**,
I want **получить месячный календарь статусов ВСЕХ сотрудников подразделения ОДНИМ bulk-запросом (без запроса на сотрудника)**,
so that **будущий экран «Календарь Подразделение × дни» (FR-37) не породит 5000-строчный ответ ни в БД-запросах, ни в HTTP-теле — пагинация по сотрудникам решается на уровне API/вызывающего кода, а не N+1 запросов здесь**.

## Scope Decision

- **Разбор FR-37**: `«Календарь Статусов: ... по Подразделению (сотрудники × дни)»`. 19.4a/b/c/d уже закрыли половину «по Сотруднику × месяц». Эта стори — ВТОРАЯ половина, backend bulk-селектор для СПИСКА сотрудников (не одного). API-эндпоинт и экран — будущие стори (19.5b+), создаются отдельно.
- **«Пагинировано, не 5000 строк» (эпик epics.md's явная формулировка)** — ЭТА стори НЕ решает пагинацию сама (это ответственность API-слоя, 19.5b, через `pagination_class`/`page`/`page_size`, тот же DRF-паттерн, что везде в проекте — `apps/core/api/views.py`'s `DefaultPagination`). Селектор принимает УЖЕ ограниченный список `employee_ids` (пагинированная страница, решённая вызывающим кодом) — НЕ весь ростер подразделения целиком. Так «не 5000 строк» становится СВОЙСТВОМ вызывающего API-слоя (маленький `page_size`), а не специальным кодом в селекторе.
- **`EmployeeStatusSelector.division_month_calendar(employee_ids, year, month)`** — ОДИН bulk-запрос на ВСЕХ переданных сотрудников СРАЗУ (`employee_id__in=employee_ids`), не N+1 вызовов существующего `month_calendar()` (19.4a) в цикле по сотрудникам — тот же анти-паттерн, что `status_on`'s docstring явно запрещает («MUST NOT be called in a loop»). Группировка bulk-результата по `employee_id` — ЧИСТЫЙ Python (`itertools.groupby` или `dict`-накопление) над уже загрученными строками, без доп. запросов.
- **Возвращает `Dict[UUID, Dict[date, str]]`** — сотрудник → его плотный месячный календарь (тот же формат значения, что `month_calendar()`, 19.4a) — КАЖДЫЙ переданный `employee_id` присутствует в результате как ключ, даже если у него ноль фактов за месяц (весь месяц `IN_SERVICE`).
- **Переиспользует `resolve_status()` буквально** — та же чистая функция, что `month_calendar()` (19.4a), не переизобретается.
- **Живёт в `apps.operations.statuses`, не `apps.operations.load`** — та же граница домена, что 19.4a (FR-37 = домен статусов, не нагрузки).
- **Out of scope**: пагинация (решается вызывающим API-слоем, 19.5b); список `employee_ids` подразделения (переиспользует существующий `HistoricalEmployeeSelector.roster_on()`, не строится заново); API/эндпоинт HTTP-слоя; React-экран; сортировка/фильтрация сотрудников.

## Acceptance Criteria

1. **AC-1.** `division_month_calendar([e1, e2], year, month)`: каждый переданный `employee_id` присутствует как ключ результата.
2. **AC-2.** Сотрудник БЕЗ фактов за месяц → его календарь целиком `IN_SERVICE` (тот же дефолт, что 19.4a).
3. **AC-3.** ДВА сотрудника с РАЗНЫМИ фактами за один и тот же месяц → каждый получает СВОЙ корректный календарь, без перекрёстного смешивания дней/статусов между сотрудниками (изоляция по `employee_id` в группировке).
4. **AC-4.** Пустой список `employee_ids=[]` → пустой `dict`, без исключений.
5. **AC-5.** Факт, пересекающий границу месяца (аналогично 19.4a AC-4) — для КАЖДОГО из нескольких сотрудников корректно учитывается независимо.
6. **AC-6.** ОДИН SQL-запрос на весь вызов, НЕЗАВИСИМО от числа `employee_ids` в списке (`CaptureQueriesContext`/`assertNumQueries(1)`) — доказывает bulk-путь для ЛЮБОГО количества сотрудников на странице.
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

- API/эндпоинт HTTP-слоя (19.5b).

- Сортировка/фильтрация сотрудников.

## Dev Notes

- `apps/operations/statuses/selectors.py` (Story 19.4a, уже существует) — `month_calendar(employee_id, year, month)` — СТРУКТУРНЫЙ образец: `calendar.monthrange`, `DateRange(month_start, month_end, bounds="[)")`, `period__overlap`, цикл `resolve_status()` по дням. Эта стори — его many-employee вариант: та же дневная логика, но группировка bulk-результата ПО employee_id ПЕРЕД дневным циклом (для каждого сотрудника — свой список `rows`, отфильтрованный из общего bulk-результата).
- Фильтр запроса: `employee_id__in=employee_ids` вместо `employee_id=employee_id` (19.4a) — единственное структурное отличие в самом запросе; `cancelled_at__isnull=True` + `period__overlap` — идентичны.
- Группировка: `rows_by_employee: dict[UUID, list] = defaultdict(list)`, один проход по bulk-результату (`for row in rows: rows_by_employee[row["employee_id"]].append(row)`), затем для каждого `employee_id` из ВХОДНОГО списка (не только тех, что есть в `rows_by_employee` — сотрудник без фактов получает пустой список, что для `resolve_status()` естественно даёт `IN_SERVICE` на каждый день) — дневной цикл, идентичный `month_calendar()`.
- `apps/operations/statuses/tests/test_employee_status_month_calendar.py` (19.4a) — структурный образец тестов (fixtures `local()`-подобные хелперы для `EmployeeStatus.objects.create`, `assertNumQueries`/`CaptureQueriesContext` для AC-6).
