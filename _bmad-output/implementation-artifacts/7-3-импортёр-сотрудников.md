# Story 7.3: Импортёр сотрудников

Status: done

## Story

As a разработчик,
I want полный импорт сотрудников с identity mapping и правилами слияния дублей (с санкцией, не молча),
so that список верен — лекарство от причины смерти донора №1.

## Acceptance Criteria

1. **Given** дубль (один человек, два donor_pk), **Then** кандидаты на слияние в отчёт на ручную санкцию, не автослияние; golden-кейсы грязного входа в тестах импортёра.
2. **And** расширяет импортёр 1.6 (код переиспользуется, не пишется заново).

## Dev Notes

- `import_donor_slice._import_employees` (1.6) УЖЕ импортирует сотрудников идемпотентно с identity-mapping (`external_id`=donor_pk) и уже НЕ автосливает дубли ИИН (IntegrityError на unique `iin` → skip `duplicate_iin`) — но это ПОБОЧНЫЙ эффект constraint'а, не структурированный отчёт для ручной санкции. 7.3 добавляет ЯВНУЮ детекцию ГРУПП дублей (пре-пасс), не полагаясь только на DB-исключение.
- division_map для отдельной команды `import_donor_employees`: в отличие от 7.2 (создаёт divisions с нуля), employees ССЫЛАЮТСЯ на УЖЕ импортированные Division — команда должна резолвить division по donor pk из уже существующих в БД записей (запрос `Division.objects.filter(...)` по коду, построенному тем же путём, что `import_orgstructure.import_divisions` — либо просто требовать, чтобы `import_donor_orgstructure` (7.2) был запущен раньше, и строить division_map из `divisions.division` секции ТОЙ ЖЕ выгрузки через повторный вызов `import_divisions` в режиме "только резолвинг" (update_or_create идемпотентен — повторный вызов на той же выгрузке ничего не меняет, только возвращает map).
- Маскирование ИИН в merge_candidates — тот же паттерн, что уже применялся в 7.1 (`donor_profile._mask`).

## Deferred (см. `deferred-work.md`)

- Малформед staff_unit-строки (нет `fields`/`pk`) считаются в `employees`-report, а не в отдельном "staff_units"-счётчике (такого отдельного report-объекта не заведено ни в одной из двух команд); низкий приоритет.
- Пре-пасс группирует ТОЛЬКО в рамках текущей выгрузки — коллизия с Employee от ПРЕДЫДУЩЕГО прогона (другой donor_pk, тот же ИИН) по-прежнему ловится только IntegrityError-safety-net'ом и не попадает в `merge_candidates`; задокументировано в docstring, не регрессия.
- `import_donor_employees` повторно пишет Division/Rank/Position внутри своей транзакции (тот же паттерн, что 7.2) — за пределами номинального "импорта сотрудников"; сознательный trade-off простоты (переиспользовать идемпотентные функции 7.2, не запрашивать состояние из БД).
- Пустой JSON-массив `[]` не даёт явного предупреждения (в отличие от employees-only кейса) — низкий приоритет, редкий вход.
- `merge_candidates` не помечает, был ли какой-то кандидат группы САМ ПО СЕБЕ невалиден (например, уже нет division) — человек, читающий отчёт, видит группу donor_pks без указания, какие из них в принципе импортируемы; уточнить, если реальная санкция потребует этой детализации.
