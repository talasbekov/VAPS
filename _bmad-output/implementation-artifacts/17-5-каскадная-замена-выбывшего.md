# Story 17.5: Каскадная замена выбывшего

Status: done

## Story

As a **держатель права `assignment.amend` (штаб на проводимом ОМ)**,
I want **при выбытии сотрудника с поста получить автоматическое предложение замены внутри его управления по штатной цепочке, при отсутствии — выбрать вручную в пределах департамента, а при невозможности — увидеть эскалацию по вертикали**,
so that **пост не остаётся молча пустым, а решение о замене прослеживаемо (кто/откуда/почему), поверх 17.3/17.4's версионирования**.

## Scope Decision

- **FR-31** (prd.md:147): «Каскадная замена выбывшего: автоматическое предложение следующего по штатной цепочке внутри управления; ручной выбор — в пределах департамента; при невозможности — эскалация по штатной вертикали (механизм FR-42).»
- **«Штатная цепочка внутри управления» = буквально `CoreEmployeeSelector.active_in_division()`'s канонический roster-порядок** (`apps/core/selectors.py:164-193`, FR-5 canon, Story 2.6) — сортировка `Position.level` → фамилия → attached-блок. «Следующий по штатной цепочке» = ПЕРВЫЙ элемент этого списка среди доступных кандидатов (не сам выбывший, не уже назначенные в текущей версии, не на hard-block статусе в дату события). Это НЕ изобретение нового алгоритма — переиспользование уже существующего, единственного в кодовой базе канона сортировки персонала.
- **«Управление» = собственное подразделение выбывшего** (`Employee.division_id`), **«департамент» = его РОДИТЕЛЬСКОЕ подразделение** (`Division.parent`, ОДИН уровень вверх) — PROVISIONAL интерпретация, открытый вопрос Bratan: research-агент подтвердил, что `DivisionType`-каталог НЕ несёт литерального различения «управление»/«департамент» ни в одном enum, только произвольные `type_code`-записи справочника; здесь взят буквальный смысл слов (управление — своё, департамент — над ним), без предположений о конкретных кодах типов.
- **«Ручной выбор»** — эта стори НЕ строит UI выбора; принимает `manual_replacement_employee_id` как ЯВНЫЙ опциональный параметр сервиса (штаб уже выбрал человека вне системы/через будущий 17.7-экран) — при его наличии авто-поиск ПРОПУСКАЕТСЯ целиком (ручной выбор имеет приоритет).
- **«Эскалация» — ТОЛЬКО аудит-событие**, НЕ уведомление (`notify()`/`Notification.Kind`) — Story 17.6 «Уведомление снятого/заменённого сотрудника» явно отдельная стори именно для уведомлений; эскалация здесь — `record()`-запись с признаком «замена не найдена», видимая через аудит-лог, механизм FR-42 (буквальный образец `escalate_stale_force_requests()`, 15.10) БЕЗ реального нотификационного канала (не изобретается здесь заранее 17.6).
- **Отсутствие кандидата на ВСЕХ уровнях (авто + вручную не передан) → ОТКАЗ, не пустой пост.** Транзакция откатывается целиком (эскалация записывается, `amend_assignment_version()` НЕ вызывается) — «система пассивна» тот же принцип, что `SecurityEventDirectAssignment` (15.9's докстринг) — не молчаливое создание вакантного поста.
- **Строится НА `amend_assignment_version()` (17.3) + допнаряд-полях (17.4)** — новый сервис `cascade_replace_departed()` собирает ПОЛНЫЙ новый `assignments`-список (копия текущих строк версии, кроме поста(ов) выбывшего, который получает нового `employee_id`, `is_unplanned=True`, `source_division_id`=кандидата) и вызывает `amend_assignment_version()`, не дублирует его логику.
- **RBAC** — переиспользуется `assignment.amend` (17.3), новый код не нужен.
- **Audit** — переиспользует `ASSIGNMENT_VERSION_AMENDED` (17.3) на успешной замене; новый action `ASSIGNMENT_REPLACEMENT_ESCALATED` только для случая «кандидат не найден».

## Acceptance Criteria

1. **AC-1.** Given выбывший сотрудник держит пост в текущей `APPROVED`-версии, и в ЕГО ЖЕ подразделении есть доступный кандидат (не сам выбывший, не занят в версии, не hard-block статус на дату события), when `cascade_replace_departed(version, actor=..., departed_employee_id=..., reason=..., sanction=...)` без `manual_replacement_employee_id`, then создаётся новая версия (17.3's механизм) с ПЕРВЫМ кандидатом roster-порядка на месте поста, `is_unplanned=True`, `source_division_id`=подразделение выбывшего.
2. **AC-2.** Given в подразделении выбывшего кандидатов НЕТ, но есть в РОДИТЕЛЬСКОМ подразделении, when вызов без `manual_replacement_employee_id`, then кандидат берётся из родительского (Tier 2), `source_division_id`=родительское подразделение.
3. **AC-3.** Given `manual_replacement_employee_id` передан, when вызов, then авто-поиск ПРОПУСКАЕТСЯ, используется переданный сотрудник напрямую (Tier 1/2 не вызываются вообще).
4. **AC-4.** Given кандидатов нет НИ в управлении, НИ в департаменте, И `manual_replacement_employee_id` не передан, when вызов, then `DomainError`, пишется `ASSIGNMENT_REPLACEMENT_ESCALATED`-аудит, версия НЕ создаётся, `amend_assignment_version()` не вызывается.
5. **AC-5.** Given выбывший держит НЕСКОЛЬКО постов в версии, when вызов, then заменяются ВСЕ его посты (независимый поиск кандидата на каждый — не один кандидат на все посты сразу).
6. **AC-6.** Given выбывший НЕ держит ни одного поста в текущей версии, when вызов, then `DomainError` (нечего заменять), без побочных эффектов.
7. **AC-7.** Given кандидат уже назначен НА ДРУГОЙ пост в ТОЙ ЖЕ версии, when поиск кандидатов, then он ИСКЛЮЧАЕТСЯ (не двойное назначение).
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Уведомление выбывшего/заменённого/эскалированных ролей (17.6).
- Автоматическое ДЕТЕКТИРОВАНИЕ выбытия (напр. триггер на новый `EmployeeStatus`) — `departed_employee_id` ВСЕГДА явный входной параметр, не auto-обнаружение.
- UI ручного выбора (17.7).
- Новый RBAC-код.
- Реальный `Notification.Kind`-канал эскалации (только аудит).
