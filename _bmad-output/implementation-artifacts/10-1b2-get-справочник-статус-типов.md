# Story 10.1b2: GET справочник статус-типов

Status: done

## Story

As a **оператор управления**,
I want **GET-эндпоинт `/api/operations/statuses/types/`, возвращающий активные типы статусов из `StatusType`**,
so that **combobox грида массового обновления (10.2) читает справочник по сети вместо жёстко зашитой копии `STATUS_TYPE_OPTIONS`, которая может разойтись с бэком незаметно**.

## Acceptance Criteria

Источник: `frontend/src/features/daily-grid/statusTypes.ts:1-14` (докстринг: "GET-роута справочника статус-типов не существует... Константа заменяется GET-справочником в стори 10.1b" — вторая половина, справочник, вынесена в 10-1b2 per decomposition rule).

1. **AC-1 (happy path → 200 + список).** Given держатель `status.view`, GET без параметров, When вызываю, Then **200**, тело — список активных (`is_active=True`) `StatusType`, отсортированный по `(priority, code)` (модельный `Meta.ordering`, тот же порядок, что seed). Каждая строка — `{code, name, color, is_hard_block, priority}`.
2. **AC-2 (деактивированные типы не попадают).** Given `StatusType` с `is_active=False`, Then он отсутствует в ответе (справочник для ЖИВОГО выбора оператором, не для исторического разрешения кодов — в отличие от `StatusTypeSelector.names_map()`, которая намеренно включает деактивированные для export/report).
3. **AC-3 (грубый гейт права → 403 ДО вьюхи).** Аноним или актор без `status.view` → **403**, вьюха не вызывается.
4. **AC-4 (нет query-параметров, нет scope — глобальный справочник).** Справочник — не подразделение-скоуповые данные; `status.view` без scope-проверки division (тот же держатель, что видит статусы ЛЮБОГО подразделения, видит и справочник — единый грубый гейт).
5. **AC-5 (схема регенерирована + нет дрейфа).** `schema.yaml` содержит `GET /api/operations/statuses/types/`; `test_schema_drift.py` зелёный; `frontend/src/shared/api/schema.d.ts` перегенерирован.
6. **AC-6 (RBAC-матрица покрывает роут).** `MATRIX["ops-status-type-list"] = _Gate("status.view")`.
7. **AC-7 (регресс нулевой).** `on_date`/`bulk`-экшены `StatusViewSet`, `StatusTypeSelector.names_map()` (7.9-precedent, export-путь) — без правок. `make gate` зелёный.

## Dev Notes

- **`is_active=True`-фильтр — намеренное расхождение с `StatusTypeSelector.names_map()`** (`apps/operations/statuses/selectors.py:17-25`), который ВКЛЮЧАЕТ деактивированные типы (нужны для разрешения кодов в исторических export/report строках). Этот эндпоинт — для ЖИВОГО выбора оператором нового статуса (combobox), деактивированный тип не должен предлагаться к выбору. Разные consumers, разная семантика — не унификация, а сознательное разделение (тот же принцип, что разделение `on_date` от справочника).
- **Отдельный `basename`, не действие на `StatusViewSet`.** `StatusViewSet` уже гейтит по `status.manage`(bulk)/`status.view`(on_date) с division-scope-логикой; справочник — глобальный, без division. Смешивание раздуло бы `permission_map`/scope-логику одного ViewSet двумя несвязанными моделями ответственности (`EmployeeStatus` vs `StatusType`). Отдельный `StatusTypeViewSet` — чище (прецедент: `MyPermissionsViewSet`/`RoleViewSet` — тоже отдельные read-only справочные ViewSet'ы).
- **Нет division-scope проверки** — справочник статус-типов не подразделение-специфичен; единственный гейт — грубый `status.view`.
