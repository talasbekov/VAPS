## Story

As a оператор,
I want сервис увольнения сотрудника на дату D с основанием — карточка в архив, открытая ставка → вакансия с D, открытый интервал принадлежности (`EmployeeDivisionHistory`) закрывается датой D, активные статусы завершаются датой D, и ничего не удаляется физически,
so that выбытие корректно отражается в расходе (сотрудник выпадает из `roster_on(D)` — знаменателя Списка, стори 2.4) и вся история сохраняется (soft-delete, ARCH-DATA-025, §«Удаление» architecture.md:468).

## Acceptance Criteria

1. **(AC-1) Увольнение: архив + вакансия + закрытие интервала + soft-delete.** **Given** действующий сотрудник (`employment_status=WORKING, is_active=True`) на открытой ставке (открытый `EmployeeStaffingAssignment`) с открытым интервалом принадлежности, **When** вызываю `dismiss_employee(employee, date=D, reason, actor)`, **Then** атомарно: (а) `employment_status=ARCHIVED`, `is_active=False`, `dismissal_date=D`, `separated_at=local_midnight(D)`; (б) открытый `EmployeeDivisionHistory` закрыт `ends_at=local_midnight(D)` (история сохранена, не удалена); (в) открытый `EmployeeStaffingAssignment` закрыт `ends_at=local_midnight(D)` И создана `Vacancy(staffing_slot, status=OPEN, opened_at=local_midnight(D), reason=<основание>)` → `compute_free_slots(div, on_date=local_midnight(D'))` показывает слот свободным с D; (г) с D сотрудник вне `roster_on(D)` (выпал из знаменателя Списка); (д) физический `DELETE` сотрудника не производится сервисом — только архивирование.
2. **(AC-2) Активные статусы завершаются датой D.** **And** активные (`cancelled_at IS NULL`, `date_end > D`) `EmployeeStatus` уволенного, покрывающие/следующие за D, усекаются `date_end = D` (полуоткрытый `[date_start, date_end)` → статус действует по D-1 включительно); «фиксация» = `created_by`/трейл (богатый `cancelled_by`/`reason` — машинерия 3.6, поля ещё нет). Кросс-контекст: усечение выполняет сервис в `apps.operations.statuses` (core не импортирует operations), оркестрируется атомарно с AC-1.
3. **(AC-3) Парные секондмент-статусы — forward-hook (НЕ реализуется в 2.5).** **And** «парные секондмент-статусы синхронно у обоих подразделений» **отложено в E3 (3.10/3.11)**: модели секондмент-ПАРЫ (связи откомандированного «по списку» ↔ прикомандированного «+N») в коде НЕ существует — нет ключа, по которому найти парную строку у принимающего подразделения. 2.5 закрывает СОБСТВЕННЫЕ статусы уволенного (вкл. строки типов `DETACHED`/`ATTACHED`, если есть) по AC-2; синхронное закрытие ПАРЫ у другого подразделения активируется, когда 3.10 введёт модель пары. Документировано как явный forward-hook, без «тихого пропуска».
4. **(AC-4) Сервис-слой: атомарность, actor, без wall-clock, переиспользование.** **And** сервис — `@transaction.atomic`, lock сотрудника (`CoreEmployeeLockSelector.lock_employee`), `actor: str` обязателен (непустой, как `assign_employee_division`), `date`/`D` — явный аргумент, время только через `local_midnight(...)` (ARCH-DATA-022, `test_isolation` зелёный); переиспользованы close-паттерн `assign_employee_division`, `compute_free_slots`, существующие поля Employee/Vacancy/Assignment — **новой модели не создаётся**; миграция не нужна (см. Решение №8 про enforcement no-hard-delete).
5. **(AC-5) Интеграция: archive-экшен через сервис, нулевая регрессия.** **And** существующие view-экшены `archive`/`restore` (`apps/core/api/views.py:70-88`), которые сейчас прямо мутируют `employment_status`/`is_active` мимо сервиса/аудита/интервалов (нарушение Layer Contract architecture.md:447), переведены на новый сервис (`archive` → `dismiss_employee`); `make gate` зелёный (Postgres :5433), `roster_on`-тесты и существующие тесты не сломаны.

## Dev Notes

### Что это за стори (суть и риск)
Сервисная стори: транзакционный **dismiss_employee** (core) — архивирует сотрудника, закрывает интервал принадлежности и ставку (→ вакансия), без физического удаления; замыкает петлю стори 2.4 (уволенный выпадает из `roster_on(D)`). Риск — НЕ в схеме (все поля/модели существуют), а в (1) **двух границах**: закрытие статусов кросс-контекстно (core↛operations, AST-енфорс) и парные секондменты без модели; (2) атомарности multi-write (Employee + интервал + assignment + Vacancy + статусы) с lock; (3) семантике «вне состава с D» при бинарном employment-фильтре roster (не date-keyed).

### Источник истины: целевая кодовая база — `Backend/VAPS`
Работаем в `Backend/VAPS/`. Донор `Backend/PersonnelStatus/` не трогаем. [Source: project memory `project_vaps_architecture.md`]

### Решения, принятые при создании стори (дефолты; менять только осознанно)
1. **`employment_status=ARCHIVED`** (эпик «карточка в архив» + существующий `archive`-экшен; roster исключает ARCHIVED и FIRED одинаково). FIRED как отдельное состояние не вводим в 2.5.
2. **`dismissal_date` (DateField) — авторитетная дата D** (календарный день, ARCH-DATA-023); `separated_at` = `local_midnight(D)` (datetime-форма).
3. **Основание → `Vacancy.reason`** (поле существует; миграция не нужна; модель Vacancy оживляется). Доп. поля основания на Employee НЕ добавляем.
4. **Вакансия = ОБА**: закрыть `EmployeeStaffingAssignment` (derived-free через `compute_free_slots`) + создать явную `Vacancy`-строку (реестр + reason). Наиболее буквально «ставка → Вакансия».
5. **Закрытие интервала — close-only** (reuse close-половины `assign_employee_division`, без открытия нового интервала).
6. **KEY DECISION — закрытие статусов (AC-2): кросс-контекст — ПОДТВЕРЖДЕНО Bratan (2026-06-22): Shape B.** Сервис `close_active_statuses_on` в `apps.operations.statuses` + атомарная оркестрация (orchestrator в operations ЛИБО из view; core НЕ оркестрирует — граница). 2.5 доставляет полный AC-2, трогает 2 app (core + operations) — допустимо decomp-правилом 3. (Рассмотренная альтернатива Shape A — отложить закрытие статусов в 3.6, 2.5 = core-only — отклонена: оставила бы у уволенного «висячий» открытый статус до 3.6.)
7. **⚠️ Секондмент-пары (AC-3): forward-hook, НЕ реализуется в 2.5.** Модели пары нет (3.10/3.11). 2.5 закрывает собственные статусы уволенного; синхронная пара — за 3.10. Никакого «тихого пропуска» — задокументировано в AC-3/Out of Scope.
8. **No-hard-delete: de-facto** (сервис не удаляет; UI-delete нет). ENFORCEMENT (override `Employee.delete()` → raise + миграция) — отдельное решение/стори (не раздувать 2.5). → возможный вопрос Bratan.
9. **Известное ограничение (наследие 2.4): roster employment-фильтр БИНАРНЫЙ, не date-keyed.** Флип `is_active=False`/`ARCHIVED` исключает сотрудника на ВСЕ даты (и до D), не только ≥D. Версионированную половину даёт закрытый интервал; date-keyed employment-membership (в составе ДО D) — **E7** (2.4 это явно отложила). Для AC «с D вне состава» (от D вперёд) — выполнено флипом. Документировать.

### Подводные камни для dev-агента
- **core ↛ operations** (AST): закрытие EmployeeStatus только в operations-сервисе; оркестрация — operations/view, не core.
- **Секондмент-пары нерешаемы** — нет связи между DETACHED↔ATTACHED строками; НЕ трактовать «закрыть все DETACHED+ATTACHED сотрудника» как «парно» (это не то, чего хочет AC). Forward-hook.
- **Атомарность**: всё (Employee lock + интервал + assignment + Vacancy + статусы) в ОДНОЙ `transaction.atomic`; иначе частичное увольнение/гонка с `roster_reconciliation` (defer 2.4).
- **EmployeeStatus truncate = UPDATE → Postgres пере-проверяет ExclusionConstraint** (тест `test_employee_status_model.py:112-127`); усечение сужает диапазон (ОК), но обернуть в atomic, ждать IntegrityError-маппинг по имени.
- **Wall-clock**: `date`/`D` — аргумент; `local_midnight` для datetime-колонок; никаких `timezone.now()` в сервисе (в view — можно).
- **`compute_free_slots(on_date)`** сравнивает с DateTimeField → передавать `local_midnight(...)`, не голую дату.
- **ruff E501** — заворачивать сразу; `ruff format` по файлу, не по папке (память `feedback_vaps_ruff_format_scoping`).
- **Postgres обязателен** для django_db-тестов (SQLite не строит схему — EXCLUDE; как в 2.4).
