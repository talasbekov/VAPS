# Story 18.1: Закрытие — итоги всех направлений обязательны

Status: done

## Story

As a **держатель права `event.manage`**,
I want **закрыть ОМ только после того, как итог написан по КАЖДОМУ направлению**,
so that **архив мероприятия (FR-30) несёт полную историю, без пропущенных направлений**.

## Scope Decision

- **КРИТИЧЕСКИ ВАЖНО (research-находка, скорректировала scope)**: ни один сервис в кодовой базе не переводит `SecurityEvent.status_code` из `APPROVED` в `IN_PROGRESS` — вся Epic 17 (журнал/оперативное изменение, гейт `event.status_code == IN_PROGRESS`) фактически недостижима через реальный workflow. Story 18.1's собственная предпосылка (закрытие ТРЕБУЕТ `IN_PROGRESS`) была бы так же недостижима. Решение с Bratan: добавить недостающий переход `APPROVED → IN_PROGRESS` ПЕРВОЙ задачей этой стори (не отдельная стори — минимальный однострочный transition, буквальный образец `approve_staffing_demand()`'s single-actor gate).
- **Направление = `sector`** (буквальное поле `SecurityEventSectorPost.sector`, Story 15.3a) — тот же канон, что фронт-мок donor-прототипа (`ClosureDirectionSummary`'s докстринг: "Направление = сектор reconSectorPosts"). Итоги нужны по КАЖДОМУ ДИСТИНКТ-`sector`, встречающемуся в `event.sector_posts.all()`.
- **Новая модель `SecurityEventClosureSummary`** (event-scoped, буквальный образец `SecurityEventSectorPost`/`SecurityEventChecklistItem`'s паттерна): `event` FK, `sector` (CharField, значение ДОЛЖНО совпадать с одним из `sector_posts`' sector'ов — сервис проверяет, не DB-констрейнт, т.к. `sector` — свободный текст, не FK), `summary` (TextField, непустой), `unique_together (event, sector)` — повторная запись по тому же направлению — upsert, не дубликат.
- **`close_security_event(event, *, actor, summaries)`** — `summaries: list[{"sector", "summary"}]`, ВСЕ дистинкт-секторы `event.sector_posts` должны быть покрыты (400 VALIDATION_ERROR со списком недостающих секторов, если нет) — тот же generic-код, что остальная per-spec-валидация этого домена (не заводит отдельный registry-код, не state-конфликт, а input-completeness). Upsert-строки `SecurityEventClosureSummary`, переход `IN_PROGRESS → CLOSED`, аудит.
- **`start_security_event(event, *, actor)`** — `APPROVED → IN_PROGRESS`, буквальный образец `approve_staffing_demand()` (single-actor, идемпотентно на уже-IN_PROGRESS, 422 из любого другого статуса).
- **Out of scope**: архив/read-модель ОМ с полной историей (Story 18.2); опрос по итогам (18.3); API/экраны (18.6, буквальный образец 17.7's решения — этот блок эпика тоже расширяет существующую `SecurityEventViewSet`, отдельная стори).

## Acceptance Criteria

1. **AC-1.** `start_security_event()`: `APPROVED → IN_PROGRESS`, идемпотентно на уже-IN_PROGRESS (чистый возврат, не ошибка), 422 из любого другого статуса, аудит `SECURITY_EVENT_STARTED`.
2. **AC-2.** `close_security_event()` со `summaries`, покрывающими ВСЕ дистинкт-секторы `sector_posts` → `IN_PROGRESS → CLOSED`, строки `SecurityEventClosureSummary` записаны, аудит `SECURITY_EVENT_CLOSED` (снимок всех итогов в `new_value`).
3. **AC-3.** `summaries` пропускает хотя бы один сектор → 400 `VALIDATION_ERROR`, событие НЕ закрывается, детали содержат список недостающих секторов.
4. **AC-4.** Пустой `summary`-текст для присутствующего сектора → 400 `VALIDATION_ERROR` (тот же `_require_text()`-паттерн, что `amend_assignment_version()`).
5. **AC-5.** Событие без `sector_posts` вовсе (пустой список направлений) → `summaries=[]` закрывает событие (нет направлений — нечего покрывать, не 400).
6. **AC-6.** Событие не `IN_PROGRESS` (например, `APPROVED` или уже `CLOSED`) → 422 `INVALID_LIFECYCLE_TRANSITION`.
7. **AC-7.** Повторный `close_security_event()` на уже-`CLOSED` → 422 (закрытие НЕ идемпотентно — реальное терминальное действие, не replay-safe как `submit`/`approve`; буквальный образец `issue_bulletin()`'s строгого NOT-idempotent поведения там, где переход не re-reachable).
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Опрос по итогам (18.3).

### Completion Notes List

Реализовано по AC 1-8. `start_security_event()` — буквальный образец `approve_staffing_demand()` (single-actor, idempotent-on-target, 422 иначе); закрывает найденный structural gap — Epic 17's журнал/оперативное изменение теперь реально достижимы. `close_security_event()` — НЕ идемпотентно на уже-CLOSED (буквальный образец `issue_bulletin()`'s strict-паттерна, не `approve_staffing_demand()`'s permissive) — терминальный переход. Покрытие секторов проверяется на сервисном уровне (`set()`-разница), не DB-FK (sector — свободный текст, нет справочника). `SecurityEventClosureSummary.objects.update_or_create()` — upsert, повторное закрытие того же сектора (если бы оно было возможно до CLOSED) переписывает итог, не дублирует строку. `make gate` — 4088 passed (было 4078), 0 regressions, ruff чист, drift-check чист.

После ревью (3 агента): Blind Hunter и Edge Case Hunter независимо совпали на ДВУХ реальных дефектах — (1) сектор, отсутствующий у `sector_posts`, молча упсертился бы как мусорная запись (Dev Notes явно обещали эту проверку, реализация её не несла) — закрыто явным отказом `unknown_sectors`; (2) дубликат сектора в одном `summaries`-payload молча перезаписывался бы `update_or_create` без сигнала об ошибке — закрыто явным отказом `duplicate_sector`. Также принято: `_require_text()`'s хардкод-сообщение «обязателен для amendment» бессмысленно в контексте закрытия (переиспользовано из чужого call site) — заменено на inline-проверку с корректным текстом. Acceptance Auditor нашёл мутационный пробел — тесты проверяли только `.exists()`/`http_status`, не содержимое `detail`/`new_value` снимка — закрыто прямыми ассертами. Acceptance Auditor также поймал ФАКТИЧЕСКУЮ ОШИБКУ в собственной докстринге этой стори: `close_security_event()` цитировала `issue_bulletin()` как прецедент «строгого NOT-idempotent» перехода — при перепроверке кода `issue_bulletin()` ОКАЗАЛСЯ idempotent-on-target (как и `approve_staffing_demand()`), строгая не-идемпотентность закрытия — НОВОЕ решение этой стори, не заимствованный прецедент — докстринг исправлен. Добавлен тест `CLOSED` как wrong-starting-status для `start_security_event()` (раньше только `DRAFT`). Отклонены: отсутствие permission-проверки внутри сервиса — established-конвенция (RBAC на API-слое, 18.6); race на чтении `sector_posts` без лока — тот же риск-профиль, что весь остальной файл (ни один сиблинг-сервис не лочит смежные таблицы); malformed non-dict/non-string записи в `summaries` — API-слой/сериализатор типизирует вход до сервиса (established разделение труда, тот же принцип, что `amend_assignment_version()`'s спеки); `DoesNotExist`-race на `select_for_update()` — established конвенция КАЖДОГО сиблинг-сервиса этого файла, не специфично для этой стори; claim о `created_by`-поле — ложный (модель его не несёт). `make gate` — 4091 passed (было 4088), 0 regressions.
