# Story 19.6a: Кумулятивный Налёт часов по сотруднику (селектор)

Status: done

## Story

As a **держатель права `status.view`** (потребитель будущей карточки сотрудника),
I want **получить накопительный Налёт часов сотрудника (день/ночь, всего) ОДНИМ агрегатным запросом**,
so that **будущий экран карточки сотрудника (FR-3, оперативный блок) сможет показать «Налёт часов» без собственной агрегации по `ServiceHours`**.

## Scope Decision

- **Разбор эпика**: epics.md's Story 19.6 — «Налёт часов в карточке сотрудника». `apps/operations/load/selectors.py`'s собственный докстринг (Story 19.1) уже явно анонсирует этот файл как «единый источник ... и карточки сотрудника (19.6)» — эта стори реализует ровно то, что было зарезервировано заранее, без придумывания новой архитектуры.
- **Декомпозиция по CLAUDE.md** (тот же паттерн, что 19.4a/b/c/d и 19.5a/b): эта стори = ТОЛЬКО backend-селектор (агрегатная функция чтения). API-эндпоинт, вплетение в существующий сериализатор карточки и фронтенд-отображение — будущие стори (19.6b+), создаются отдельно, когда придёт их очередь. Sprint-status ключ переименован `19-6-налёт-часов-в-карточке` → `19-6a-налёт-часов-кумулятив` (тот же приём, что 19.5's переименование `19-5-*` → `19-5-*` с суффиксом `a`).
- **`compute_cumulative_service_hours(employee_id)`** — В `apps/operations/load/selectors.py` (не `apps.operations.events`, не `apps.core`): файл уже владеет агрегацией нагрузки по сотруднику (`compute_plan_load`/`compute_fact_load`, 19.1) и уже читает через границу `events`-домена (`PlacementAssignment`, `PlacementAssignmentActual`) — тот же прецедент, не новый cross-domain импорт. `apps.core.models.EmployeeOperationalProfile` (где физически лежит «оперативный блок» карточки, FR-3/14.10) НЕ может импортировать `operations` (`test_core_does_not_import_other_context_models`, ARCH-003) — поэтому агрегат ЖИВЁТ в `operations` и читается будущим API-слоем карточки (19.6b), а не сохраняется как FK/поле в `core`.
- **ОДИН агрегатный SQL-запрос** (`.aggregate(Sum(...), Sum(...))`), не построчная выборка `ServiceHours` + сложение в Python — тот же принцип «bulk, не N+1», что 19.5a.
- **Гейт идентичен `compute_fact_load()` (19.1)**: `actual__assignment__version__is_current=True` + `actual__assignment__version__event__status_code=CLOSED` — `ServiceHours`-строка, чей `PlacementAssignment` был впоследствии заменён (`is_current=False`) новой версией расстановки, НЕ должна учитываться в кумулятиве (тот же гейт, что при ЗАПИСИ `ServiceHours` в 18.4, но перепроверяется на ЧТЕНИЕ — версия могла смениться ПОСЛЕ вычисления `ServiceHours`).
- **Возвращает `Dict[str, Decimal]`**: `{"day_hours": Decimal, "night_hours": Decimal, "total_hours": Decimal}` — сотрудник БЕЗ единой строки `ServiceHours` получает `{"day_hours": Decimal("0.00"), "night_hours": Decimal("0.00"), "total_hours": Decimal("0.00")}` (не `None`/исключение — «нет данных» и «нулевой налёт» неразличимы для карточки, тот же принцип, что `month_calendar()`'s дефолт `IN_SERVICE`).
- **Кумулятив = ВСЁ ВРЕМЯ, без периода** — PRD (`prd.md:65`): «Налёт часов — накопительная история фактического времени Сотрудника на постах»; UX (`EXPERIENCE.md:190`) не описывает период/фильтр на карточке. Период/фильтр по датам — не запрошен ни донором, ни PRD, ни UX; добавление `start_date`/`end_date`-параметров без потребителя было бы preemptive-абстракцией (не делается).
- **Out of scope**: API/эндпоинт HTTP-слоя (19.6b); вплетение в сериализатор `EmployeeOperationalProfile`/карточки (19.6b/c); React-отображение на экране карточки (будущая стори); период/фильтр по датам (не запрошен); `is_overloaded`/`overload_minutes` (18.5, per-instance поля `ServiceHours`, не относятся к кумулятиву); пересчёт/материализация — функция читает существующие `ServiceHours`-строки на лету, ничего не сохраняет.

## Acceptance Criteria

1. **AC-1.** Сотрудник с ДВУМЯ `ServiceHours`-строками (день=8+ночь=2 и день=3+ночь=5) → `{"day_hours": 11.00, "night_hours": 7.00, "total_hours": 18.00}`.
2. **AC-2.** Сотрудник БЕЗ единой `ServiceHours`-строки → `{"day_hours": 0.00, "night_hours": 0.00, "total_hours": 0.00}` (нули, не `None`/исключение).
3. **AC-3.** `ServiceHours`, чьё `PlacementAssignment.version.is_current=False` (версия заменена) → НЕ учитывается в кумулятиве.
4. **AC-4.** `ServiceHours`, чьё событие (`SecurityEvent.status_code`) НЕ `CLOSED` (например `IN_PROGRESS`) → НЕ учитывается в кумулятиве.
5. **AC-5.** ДВА сотрудника с независимыми `ServiceHours` → вызов для сотрудника A не подмешивает часы сотрудника B (изоляция по `employee_id`).
6. **AC-6.** ОДИН SQL-запрос на вызов (`assertNumQueries(1)`), независимо от числа `ServiceHours`-строк у сотрудника.
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

## Dev Notes

- `apps/operations/load/selectors.py:156-186` (`compute_fact_load`, 19.1) — структурный образец двойного гейта и cross-domain импорта из `apps.operations.events.models`. Эта стори не переиспользует `compute_fact_load()` целиком (та режет по календарным дням, эта суммирует `ServiceHours.day_hours`/`night_hours` напрямую — уже посчитанные 18.4, дублировать деление день/ночь не нужно), но ЖИВЁТ в том же файле и следует тому же гейту.
- Путь полей от `ServiceHours` до `employee_id`: `ServiceHours.actual` (OneToOne → `PlacementAssignmentActual`) → `.assignment` (OneToOne → `PlacementAssignment`) → `.employee_id` (плоский UUID, НЕ FK, ARCH-002/003) / `.version` (FK → `AssignmentVersion`) → `.is_current` / `.event.status_code`.
- Django ORM путь фильтра: `ServiceHours.objects.filter(actual__assignment__employee_id=employee_id, actual__assignment__version__is_current=True, actual__assignment__version__event__status_code=SecurityEvent.StatusCode.CLOSED).aggregate(day=Sum("day_hours"), night=Sum("night_hours"))`.
- `.aggregate()` на пустом queryset возвращает `{"day": None, "night": None}` (Django-поведение при отсутствии строк, НЕ `Decimal("0")`) — функция обязана подставить `Decimal("0.00")` явно при `None`, иначе AC-2 упадёт с `TypeError` при попытке сложить `day_hours+night_hours` для `total_hours`.
- `apps/operations/events/models.py:791` (`ServiceHours`) — `day_hours`/`night_hours` уже `DecimalField(max_digits=6, decimal_places=2)`, `CheckConstraint`-гарантированы неотрицательными на уровне БД — эта стори полагается на инвариант, не перепроверяет.
- `apps/operations/load/tests/test_selectors.py` — структурный образец фикстур (`make_object`/`make_event`/`make_assignment`/`make_actual`, `local()`-хелпер для aware-datetime в `Asia/Qyzylorda`). Для этой стори тестам дополнительно нужен хелпер создания `ServiceHours`-строки напрямую (`ServiceHours.objects.create(actual=actual, day_hours=..., night_hours=..., computed_at=...)`) — не обязательно проходить через `compute_service_hours()` (18.4), т.к. эта стори тестирует ЧТЕНИЕ уже существующих строк, а не их вычисление.
- `apps/operations/events/models.py:791-802` (`ServiceHours` fields) — `computed_at` NOT NULL без дефолта: тестовый фабричный хелпер обязан передать явное значение (например `local(2026, 8, 1, 0, 0)`), иначе `IntegrityError` при создании фикстуры.
