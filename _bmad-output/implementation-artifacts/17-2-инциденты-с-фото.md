# Story 17.2: Инциденты с фото (Attachment) → история ОМ + Паспорт + карточки участников

Status: review

## Story

As a **держатель права `event.journal.create` (штаб на проводимом ОМ)**,
I want **фиксировать Инцидент (объект, пост, участники, описание, фото) в том же журнале штаба, что и инструктаж/указания (17.1)**,
so that **Инцидент виден в истории ОМ, находим по Объекту (для «Паспорта») и по участнику (для «карточки»), без отдельной таблицы, дублирующей журнал**.

## Scope Decision

- **FR-29**, вторая половина (первая — 17.1): «Инциденты (объект, пост, участники, описание, фото); Инцидент попадает в историю ОМ, Паспорт Объекта и карточки участников.»
- **`JournalEntry` (17.1) РАСШИРЯЕТСЯ, не дублируется новой таблицей** — «история ОМ» уже И ЕСТЬ `JournalEntry` (append-only, event-scoped); Инцидент — четвёртый `EntryType` с доп. полями, которые у `BRIEFING`/`DIRECTIVE` остаются `null`/пустыми. Подтверждено research-агентом: `create_journal_entry()` (17.1) уже явно резервирует `INCIDENT` как «ещё не реализовано» — эта стори снимает резерв.
- **Объект** Инцидента — НЕ новое поле: `event.object` уже даёт объект (SecurityEvent 1:1 Object) — FR-29's «объект» удовлетворён транзитивно через `event`, отдельного FK не нужно.
- **Пост** — `post` FK на `apps.operations.facilities.models.Post` (уже используется `PlacementAssignment`, 16.1), `on_delete=PROTECT` (тот же выбор, что везде в `events/models.py` для `Post`-ссылок). Обязателен ТОЛЬКО для `INCIDENT` (CheckConstraint, asymmetric-форма — образец `chk_daily_submission_amended_requires_reason_sanction`), у `BRIEFING`/`DIRECTIVE` — `null`.
- **Участники** — `participant_ids = JSONField(default=list, blank=True)`, буквальный образец `PlacementAssignment.conflict_codes` (16.3, `models.py:527`) — та же форма (список значений на одной строке). Research-агент подтвердил: НЕТ established M2M/child-table паттерна для «N сотрудников на одной записи» нигде в кодовой базе; `JSONField`-список — не изобретение, а перенос уже принятого в этом же файле решения. Пустой список допустим (не каждый Инцидент обязательно называет участников поимённо — например, неисправность оборудования).
- **Фото** — `photo_attachment_id = UUIDField(null=True, blank=True)` — ПЛОСКАЯ ссылка, НЕ FK (ARCH-003, `apps/documents/models.py` — `Attachment` не пересекает границы приложений через FK, только `attachment_id`, буквальный образец существующих owner-полей). Сам аплоад файла — существующий Story 6.1 document-upload сервис/эндпоинт, ЭТА стори его не трогает, только принимает готовый `attachment_id`. Референциальная целостность `attachment_id` НЕ проверяется (тот же принцип, что у всех остальных плоских owner-полей — ARCH-003 сознательно жертвует FK-проверкой ради развязки границ).
- **«Попадает в Паспорт Объекта» / «карточки участников» — READ-side, не write.** Research-агент подтвердил: ни у `ObjectPassport` (`facilities/models.py:66`), ни у `Employee` (`core/models.py:181`) нет поля/суб-таблицы для инцидент-лога в донор-схеме — придумывать её здесь means изобретать несуществующий контракт. Вместо записи-дублирования — два `JournalEntrySelector`-метода (образец `StatusTypeSelector`/`EmployeeStatusSelector`, `apps/operations/statuses/selectors.py`): `incidents_for_object(object_id)`, `incidents_for_participant(employee_id)` — читают `JournalEntry.objects.filter(entry_type=INCIDENT, ...)`. UI-подключение этих селекторов к реальным страницам Паспорта/карточки — Story 17.7 (API/экраны) или дальше, не эта.
- **RBAC** — переиспользуется `event.journal.create`/`event.journal.view` (17.1), НЕ новый код: Инцидент — тот же журнал, та же гранулярность прав, нет продуктового сигнала для отдельного «incident»-права.
- **API/экраны/e2e — Story 17.7**, не эта. Объём — модель-расширение + миграция + сервис-расширение + 2 селектора + тесты, тот же уровень, что 17.1.

## Acceptance Criteria

1. **AC-1.** Given `event.status_code == IN_PROGRESS`, when actor вызывает `create_journal_entry(event, actor=..., entry_type=INCIDENT, text=description, post=post, participant_ids=[...], photo_attachment_id=attachment_id)`, then создаётся `JournalEntry` со всеми полями заполненными.
2. **AC-2.** Given `entry_type=INCIDENT` БЕЗ `post`, when создание, then `DomainError`, строка не создаётся (пост обязателен для Инцидента — CheckConstraint на DB-уровне тоже).
3. **AC-3.** Given `entry_type=INCIDENT` с пустым `participant_ids` (`[]`) и `photo_attachment_id=None`, when создание, then строка создаётся успешно — участники/фото НЕ обязательны (FR-29 не требует «всегда с фото», Инцидент может быть заявлен без снимка).
4. **AC-4.** Given существующий `entry_type=BRIEFING`/`DIRECTIVE` (17.1), when создание, then `post`/`participant_ids`/`photo_attachment_id` остаются `null`/`[]` — регрессия 17.1 не сломана, новые поля не просачиваются в старые типы.
5. **AC-5.** Given несколько `INCIDENT`-записей на разных событиях одного объекта, when `JournalEntrySelector.incidents_for_object(object_id)`, then возвращает ровно все `INCIDENT`-записи событий этого объекта, в хронологическом порядке.
6. **AC-6.** Given `INCIDENT`-запись с `participant_ids=[emp_a, emp_b]`, when `JournalEntrySelector.incidents_for_participant(emp_a)`, then запись найдена; для `emp_c` (не в списке) — не найдена.
7. **AC-7.** `chk_journal_entry_incident_requires_post`-констрейнт на DB — прямой `.objects.create(entry_type="INCIDENT", post=None, ...)` в обход сервиса — `IntegrityError`.
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Аплоад самого файла (существующий Story 6.1 document-upload, не трогается).
- Запись/новое поле на `ObjectPassport`/`Employee` — только чтение через селекторы.
- API endpoints/экраны — Story 17.7.
- Отдельное RBAC-право для Инцидента — переиспользуется `event.journal.*`.
- Валидация существования `photo_attachment_id`/`post.object == event.object`-сверка — ЭТА стори НЕ добавляет доп. cross-проверку `post.object_id == event.object_id` (в отличие от `PlacementAssignment.clean()`, 16.x) — намеренное упрощение, открытый вопрос Bratan, не блокер AC.
