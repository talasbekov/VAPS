# Story 14.12a: Аудит-логирование дежурного цикла

Status: done

## Story

As an **офицер аудита (право `audit.view`)**,
I want **`AuditLog`-строки на approve/cancel/replan/create-действиях плана дежурств**,
so that **изменения планов/смен видны в аудите, не только в бизнес-данных**.

Разделение Story 14.12 («аудит + RBAC-строки + e2e дежурного цикла») на 2 сфокусированные подстории по CLAUDE.md: 14.12a (backend-аудит) + 14.12b (frontend e2e). RBAC-часть исходного 14.12 закрыта БЕЗ кода — см. Scope Decision.

## Scope Decision (найдено при create-story, research-агент + явное решение пользователя)

- **RBAC role-binding — ЗАКРЫТО без изменений кода.** Явное решение пользователя (create-story): роли в VAPS назначаются гибко, без статичных биндингов «код-права → конкретная роль» в seed-данных — `duty.manage` уже зарегистрирован (`seed_operations.py:22`) и уже гейтует все duty-plan-роуты (14.11a-g, `MATRIX`), присвоение конкретной роли — операционное решение через существующий Role/RolePermission-механизм (админ-редактируемый), НЕ хардкод в seed-команде. Никакой код здесь не пишется.
- **Аудит — буквальный образец Story 5.9** (`dd2af16`, `apps/submissions/services/day_submission_service.py` и др.): `record()`/`record_many()`-вызов ВНУТРИ сервисного слоя (не вьюхи), внутри уже существующего `transaction.atomic()`, рядом с самой мутацией. Новые action-коды — в `docs/registries/audit-events.yaml` (registry — forward-seed, `test_emitted_actions_subset_of_registry` требует `emitted ⊆ registry`).
- **Какие роуты флипаются `_DeferredAudit`→`_Audited`**: `ops-duty-plan-shifts`(create-часть)/`-approve`/`-cancel-shift`/`-replan-shift` — реальные мутации. `ops-duty-plan-list`/`ops-duty-plan-conflicts` (GET) остаются как есть (не входят в audit-completeness-гейт, тот завязан на мутирующие методы — уже установлено 14.11g). `ops-duty-plan-validate` — POST, но НЕ мутирует (dry-run, 14.11f) — НЕ аудируется (нечего логировать, ничего не изменилось), но флипается формально из `_DeferredAudit`, раз уже не откладывается технически — ИЛИ явно документируется в `test_audit_coverage.py`'s комментарии, почему POST-без-мутации не нуждается в audit-эмиссии (не входит в `_Audited`, но и не «отложено» — третья категория, если такая уже есть в кодовой базе; если нет — оставить `_DeferredAudit` с обновлённым комментарием «dry-run, эмитить нечего»).
- **`ops-duty-plan-shifts`'s create-часть** (`POST .../shifts/`, часть комбинированного GET+POST action) — тоже флипается: создание смены — реальная мутация.
- **`ops-duty-plans-create`** (создание самого ПЛАНА, `POST /duty-plans/`) — тоже в объёме (мутация, была `_DeferredAudit`).
- **Тест — новый файл `apps/operations/duties/tests/test_duty_plan_audit.py`**, буквальный образец `test_submission_audit.py` (5.9): HTTP-smoke через реальный роут, ассерт наличия `AuditLog`-строки после вызова (behavioral test, не просто service-level emission — `_Audited`'s собственный докстринг требует именно поведенческий тест).

## Acceptance Criteria

1. **AC-1 (create-plan эмитит audit-строку).** `POST /api/operations/duty-plans/` → `AuditLog`-строка с корректным action-кодом, `actor`, деталями (например `plan_id`, `object`, `year`, `month`).
2. **AC-2 (create-shift эмитит).** `POST .../shifts/` → `AuditLog`-строка (`shift_id`, `plan_id`, `employee_id`).
3. **AC-3 (approve эмитит).** `POST .../approve/` → `AuditLog`-строка (`plan_id`, статус-переход DRAFT→APPROVED). Идемпотентный повторный вызов на уже-APPROVED — НЕ эмитит вторую строку (нет реального перехода) ИЛИ эмитит с явной пометкой no-op — решить при dev-story по образцу 5.9's идемпотентных случаев, если такие есть.
4. **AC-4 (cancel-shift эмитит).** `POST .../shifts/{id}/cancel/` → `AuditLog`-строка (`shift_id`, `reason`).
5. **AC-5 (replan-shift эмитит).** `POST .../shifts/{id}/replan/` → `AuditLog`-строка (`old_shift_id`, `new_shift_id`, `reason`).
6. **AC-6 (registry).** Все новые action-коды — в `docs/registries/audit-events.yaml`; `test_emitted_actions_subset_of_registry` зелёный.
7. **AC-7 (AUDIT_MATRIX).** Пять `_DUTY`-строк (list-create, shifts-create, approve, cancel-shift, replan-shift) флипнуты на `_Audited()`; `validate`/`list`/`conflicts` — не флипаются (обоснование в комментарии рядом со строкой).
8. **AC-8 (регресс нулевой).** `make gate` зелёный, ни одна существующая мутация не сломана.

### Completion Notes

Реализовано по AC 1-8. **Найдено при dev-story (не в исходном плане)**: `AuditLog.entity_id` — строгий `UUIDField` (NOT NULL), но `DutyPlan`/`DutyShift` используют целочисленные (не UUID) PK — прямая передача `entity_id=plan.pk` упала бы на уровне БД/валидации. Решение — `uuid.UUID(int=pk)`, тот же приём, что уже санкционирован в кодовой базе для другой цели (`bulk_status_service.py`'s `_BULK_SUMMARY_ENTITY_ID = uuid.UUID(int=0)`-сентинел); здесь он кодирует РЕАЛЬНЫЙ id сущности, не сентинел — детерминированно, обратимо через `.int`.

`approve_duty_plan(plan)` не имела параметра `actor` — добавлен как обязательный keyword-only (`actor` уже required-kwarg у `cancel_duty_shift`/`replan_duty_shift`, теперь консистентно у всех трёх). Обновлены ~6 существующих вызовов в `test_services.py` (были без actor) + вьюха (`actor=request.actor_id`). `record()` эмитится ТОЛЬКО на реальном DRAFT→APPROVED-переходе (не на идемпотентном повторном вызове — нет перехода, нечего логировать), подтверждено отдельным тестом.

`replan_duty_shift()` внутренне вызывает `cancel_duty_shift()` — решение: `cancel_duty_shift()`'s `record()` эмитится ВСЕГДА при реальной отмене (включая изнутри replan — старая смена РЕАЛЬНО отменяется в обоих случаях), `replan_duty_shift()` дополнительно эмитит СВОЙ `DUTY_SHIFT_REPLANNED`. Итог: HTTP-вызов cancel даёт 1 строку, HTTP-вызов replan даёт 2 (cancelled+replanned) — оба факта реальны, подтверждено тестом.

`create`(план)/`_create_shift` не имеют своей сервис-функции (прямые ORM-вызовы в вьюхе) — `record()` живёт в `views.py`, не в `services.py`, в отличие от approve/cancel/replan (задокументировано комментарием в коде).

`validate` — POST, но read-only dry-run (14.11f) — НЕ аудируется (нечего логировать), но остаётся `_DeferredAudit` с ОБНОВЛЁННОЙ причиной («structural no-op, не долг», не старая ссылка на «14.12 отложит») — подтверждено тестом на ОТСУТСТВИЕ audit-строки.

7 новых HTTP-smoke тестов (буквальный образец 5.9's `test_submission_audit.py`), все зелёные с первой попытки (после мелкой правки — ruff line-length). RBAC role-binding — закрыто явным решением пользователя (см. 14.12a Scope Decision), кода не потребовалось. `make gate` — 3371 passed (было 3364, +7), 0 regressions, no migration/schema drift.

**Ревью (Blind Hunter/Edge Case Hunter/Acceptance Auditor, параллельно):** Acceptance Auditor подтвердил все 8 AC PASS (полный целевой прогон — 187 passed). Blind Hunter — Medium-находка: `create()`/`_create_shift()` в `views.py` не были обёрнуты в `transaction.atomic()` (в отличие от ВСЕХ вызовов в `services.py`) — при отказе `record()` (нет ATOMIC_REQUESTS в settings.py, Django авто-коммитит по инструкции) план/смена остались бы закоммичены БЕЗ аудит-строки. Edge Case Hunter эмпирически подтвердил (реальный Postgres-проб, потом удалён) самое важное свойство стори — откат при сбое `replan`'s `new_shift.full_clean()` ПОСЛЕ уже выполненного `cancel_duty_shift()`'s `record()` реально откатывает ОБА (смену и аудит-строку) — держится. Также нашёл Low-асимметрию: `approve_duty_plan()` не имела defensive-гарда на пустой `actor` (в отличие от `cancel_duty_shift()`), хоть и недостижимо сегодня (require_permission уже гарантирует непустой actor). Исправлено: (1) `transaction.atomic()` обёртка вокруг create+record() в обоих view-действиях; (2) defensive-гард в `approve_duty_plan()` (симметрия с cancel_duty_shift); (3) новый тест на гард. `make gate` после фиксов — 3372 passed, 0 regressions.
