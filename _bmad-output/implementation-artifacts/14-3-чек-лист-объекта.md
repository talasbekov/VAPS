# Story 14.3: Чек-лист объекта — типовой шаблон и пункты (справочники)

Status: done

## Story

As a Администратор,
I want вести типовой единый чек-лист (шаблоны и их пункты) через админку,
so that рекогносцировка (15.3) и объектные дополнения (14.3a) опираются на выверенный типовой набор пунктов проверки.

## Acceptance Criteria

1. **Модели.** ChecklistTemplate — справочник с natural PK `code` (≤100, house-канон PostType; донорский UUID+UNIQUE(code) сведён к канону), `name`(255), `description` (Text, ""), `is_active`; ChecklistItem — FK template (CASCADE), `text` (Text, NOT NULL), `category` (CharField 100, null), `is_required` (default True), `sort_order` (default 0), `is_active`; `db_table` = `ops_checklist_templates` / `ops_checklist_items` (канон `ops_<plural_snake>`; донорский префикс object_ снят вслед за 14.1/14.2); ordering пунктов: `sort_order, id`.
2. **DB-инварианты.** Отвергаются на уровне БД: whitespace-only `name` шаблона и `text` пункта; `sort_order` < 0; неизвестные значения не завозим (choice-полей нет). Красные пробы транзакционные.
3. **Admin.** Оба справочника ведутся через админку: ChecklistTemplateAdmin с inline-пунктами (TabularInline) + отдельный ChecklistItemAdmin не нужен (пункты — только через шаблон); CATALOG_MODELS стража расширен на ChecklistTemplate (пункты inline-only — в admin-реестре их НЕТ, «обе модели» из ранней редакции AC невыполнимо: ревью-правка); Facility/Sector/Post/бизнес-модели — по-прежнему НЕ в admin.
4. **Гейт.** `make gate` зелёный: миграции 0007/0008 по-сущности, `makemigrations --check` пуст, все стражи молчат.
5. **Декомпозиция.** В sprint-status добавлена стори `14-3a-привязка-чек-листа-и-оверрайды` (backlog) с границей: bindings (UNIQUE(object,template)), overrides (ADD/MODIFY/DISABLE + conditional-CHECKs формы), резолвер BR-CHECKLIST-003, сервисы/аудит/локи.

## Dev Notes

### Ключевые решения (Д)

- **Д1. Справочник, не бизнес-модель**: типовой чек-лист ведёт Администратор редко и целиком (FR-5.5 «типовой единый»); admin-путь каноничен (Admin = справочники), сервисы/аудит НЕ заводятся — как у Position/Rank/StatusType/PostType. Объектные операции (привязка, оверрайды) — бизнес-слой 14.3a с полным сервисным каноном.
- **Д2. Natural PK code** у шаблона (house-канон справочников; донорский UUID-суррогат не переносим — 14.1-прецедент «DDL = семантический контракт»). Пункты — int PK (не справочник верхнего уровня, а состав шаблона).
- **Д3. Пункт без актор-полей и timestamps** (models.Model): admin-managed состав справочника; TimeStampedModel-канон — для бизнес-агрегатов.
- **Д4. Уникальность текста пункта в шаблоне НЕ вводится**: донор молчит, «молчание = не выдумывать» (дубль текста может быть легитимен в разных категориях).
- **Д5. category — nullable CharField(100)** по донору; справочника категорий нет ни в одном источнике — свободный текст (аналог object_type Д2-14.1).
- **Д6. is_active на пунктах** — выключение пункта шаблона (глобально); НЕ путать с DISABLE-оверрайдом 14.3a (точечно под объектом).

### Наследуемые каноны

Ревью-секции 14.1/14.2 — дефолт. Для этой стори активны: обе-границы-пробы, `\S`-непустота, ordering с tie-breaker id, миграции по-сущности, CATALOG_MODELS-страж (legitimate growth), «Admin-inline не даёт бизнес-инвариантов — их нет у справочника».

### Границы (что 14.3 НЕ делает)

- **Bindings + overrides + резолвер + сервисы/аудит** → 14.3a (создаётся в sprint-status этой стори).
- **Прохождение чек-листа, решение/обоснование, статусы рекогносцировки** (DB-OPS-019/020) → 15.3.
- **Seed** — донор типовой набор пунктов не задаёт; наполнение — руками Администратора (или будущей data-миграцией при появлении утверждённого списка).
- **API/экраны** → API-стори эпика.
