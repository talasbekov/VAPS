# Story 14.3: Чек-лист объекта (модели)

Status: ready-for-dev

## Story

As a **разработчик**,
I want **модели типового чек-листа (`ChecklistTemplate`+`ChecklistItem`) и per-объектной привязки с дополнениями (`ChecklistBinding`+`ChecklistOverride`)**,
so that **Epic 15's рекогносцировка/готовность ОМ и API-стори будущего имеют модельный фундамент, сверенный с донор-спекой VAPS_7.8.2**.

`epics.md#L1403` (буква: «Чек-лист объекта (типовой + дополнения)»). Третья стори Epic 14, строится поверх 14.1/14.2's `Object`/`Sector`/`Post` (done).

## Scope Decision (найдено при create-story)

- **«Типовой + дополнения» — донор моделирует ДВУМЯ слоями, 4 таблицы, не одним флагом.** `docs/PersonnelStatus/VAPS_7.8.2.md` §17.5 (DB-OPS-017/018) даёт ГЛОБАЛЬНЫЙ слой: `ops_object_checklist_templates` (каталог шаблонов) → `ops_object_checklist_items` (пункты шаблона, БЕЗ `object_id` — не принадлежат объекту напрямую). §50 (DB-OPS-048/049, «High Fix — Object-Specific Checklist Overrides», добавлено донором позже как отдельный фикс) даёт PER-ОБЪЕКТНЫЙ слой: `ops_object_checklist_bindings` (Object↔Template, M2M через join-таблицу) → `ops_object_checklist_overrides` (per-binding дельты ADD/MODIFY/DISABLE). Решение: строить ВСЕ 4 модели одной стори — оба слоя вместе реализуют буквальное «типовой + дополнения» FR-19, ни одна половина не имеет смысла без другой (привязка без шаблона — пусто; шаблон без привязки — не применяется ни к одному объекту).
- **Резолвинг «итогового» чек-листа (`template items + object overrides`, BR-CHECKLIST-003) — НЕ строится.** Это ВЫЧИСЛЯЕМОЕ представление (сервис/API), не модельный атрибут — мирроит 14.1's решение не автовычислять `completeness_status`. Модели этой стори — только сырое хранилище template/items/bindings/overrides.
- **Гейтинг готовности ОМ через `ISSUE`-пункты чек-листа (BR-RECON-003, `409 CHECKLIST_ISSUES_UNRESOLVED`) — Epic 15's Reconnaissance-территория (DB-OPS-019/020, `ops_event_reconnaissance_items` — не существует в кодовой базе).** Эта стори НЕ строит Reconnaissance-таблицы и не реализует никакого гейтинга — только чек-лист-хранилище, от которого рекогносцировка Epic 15 будет читать.
- **`template_id` на `ChecklistBinding` — `PROTECT`, не `RESTRICT` буквально.** Донор: `ON DELETE RESTRICT`. Django's `models.RESTRICT` существует, но `PROTECT` — уже установленный в ЭТОМ файле паттерн (14.1's `ObjectPassport.object`, review-раунд) для «не должно молча исчезнуть» — используется `PROTECT` для консистентности с соседними моделями того же файла, не `RESTRICT` (семантически эквивалентны для этого случая — оба блокируют удаление, differ только в момент проверки FK constraint внутри транзакции, что не имеет значения для этой стори).
- **Проактивная защита от cross-template несоответствия (урок 14.2's ревью).** 14.2's ревью НЕЗАВИСИМО дважды нашло: `Post.sector` мог указывать на `Sector` другого `Object`, ничем не защищено. Тот же класс дыры существует здесь: `ChecklistOverride.source_item` мог бы указывать на `ChecklistItem` из ДРУГОГО шаблона, чем `binding.template`. Закрывается ПРЕВЕНТИВНО в этой стори (не ждать повторной находки ревью) — `ChecklistOverride.clean()` проверяет `source_item.template_id == binding.template_id`.

## Acceptance Criteria

1. **AC-1 (модель `ChecklistTemplate`).** `ChecklistTemplate(TimeStampedModel)`: `code` (CharField, max_length=100, unique=True), `name` (CharField, max_length=255), `description` (TextField, blank=True), `is_active` (BooleanField, default=True). `db_table="ops_object_checklist_templates"`.
2. **AC-2 (модель `ChecklistItem`).** `ChecklistItem(TimeStampedModel)`: `template` (`ForeignKey(ChecklistTemplate, on_delete=CASCADE, related_name="items")`), `text` (TextField), `category` (CharField, max_length=100, blank=True), `is_required` (BooleanField, default=True), `sort_order` (PositiveIntegerField, default=0), `is_active` (BooleanField, default=True). `db_table="ops_object_checklist_items"`. НЕТ `object`-поля (донор: пункты принадлежат шаблону, не объекту — см. Scope Decision).
3. **AC-3 (модель `ChecklistBinding`).** `ChecklistBinding(TimeStampedModel)`: `object` (`ForeignKey(Object, on_delete=CASCADE, related_name="checklist_bindings")`), `template` (`ForeignKey(ChecklistTemplate, on_delete=PROTECT, related_name="bindings")`), `name` (CharField, max_length=255, blank=True), `is_default` (BooleanField, default=False), `is_active` (BooleanField, default=True). `db_table="ops_object_checklist_bindings"`. `created_by` — переиспользуется УЖЕ существующее поле `TimeStampedModel.created_by`, НЕ дублируется новым полем. `UniqueConstraint(fields=["object", "template"])` (донор: `unique_object_template_binding`).
4. **AC-4 (модель `ChecklistOverride`).** `ChecklistOverride(TimeStampedModel)`: `binding` (`ForeignKey(ChecklistBinding, on_delete=CASCADE, related_name="overrides")`), `source_item` (`ForeignKey(ChecklistItem, on_delete=SET_NULL, null=True, blank=True, related_name="overrides")` — донор: NULL для чистого ADD, заполнено для MODIFY/DISABLE), `override_type` (CharField, choices `ADD`/`MODIFY`/`DISABLE`, TextChoices), `text`/`category` (blank-поля, ADD-специфичные), `is_required` (BooleanField, null=True, blank=True — `NULL` = «не переопределено»), `sort_order` (PositiveIntegerField, null=True, blank=True), `reason` (TextField, blank=True). `db_table="ops_object_checklist_overrides"`.
5. **AC-5 (`override_type` — DB CheckConstraint, не только choices).** Тот же паттерн, что `completeness_status` (14.1)/`Notification.Kind` (13.5a-13.5c) — `CheckConstraint` `Q(override_type__in=["ADD","MODIFY","DISABLE"])`.
6. **AC-6 (проактивный cross-template гард — урок 14.2).** `ChecklistOverride.clean()`: если `source_item` задан, `source_item.template_id` ДОЛЖЕН равняться `binding.template_id` — иначе `ValidationError`. Тот же паттерн, что `Post.clean()` (14.2's ревью-фикс), задокументирован тот же caveat (`.objects.create()`/`bulk_create()` пропускают `full_clean()`).
7. **AC-7 (миграция).** Одна `0004_...` в `apps/operations/facilities/migrations/` — все 4 модели, все `db_table`, оба `UniqueConstraint`/`CheckConstraint` (на `ChecklistBinding` и `ChecklistOverride`).
8. **AC-8 (Admin — не регистрируется).** Тот же аргумент, что 14.1/14.2: `ChecklistTemplate`/`ChecklistItem`/`ChecklistBinding`/`ChecklistOverride` — растущий бизнес-реестр, не статичный справочник.
9. **AC-9 (тесты + границы контекста).** Модельные тесты: создание всех 4 моделей, уникальность `code` на шаблоне, уникальность `(object, template)` на привязке, `ChecklistItem` без `object`-поля (структурная проверка — пункт существует независимо от объекта), удаление `Template` каскадно удаляет `Item`, удаление `Binding` каскадно удаляет `Override`, удаление `ChecklistItem` (`source_item`) → `Override.source_item` становится `NULL` (не удаляет override, `SET_NULL`), удаление `Object` каскадно удаляет `Binding` (не `Template`/`Item` — они независимы от объекта), удаление `Template` при живой `Binding` → `ProtectedError` (`PROTECT`), `override_type` вне `{ADD,MODIFY,DISABLE}` → `IntegrityError` (DB-red-probe), cross-template `source_item` → `ValidationError` через `full_clean()` (позитивный + негативный путь, AC-6). `test_isolation.py` — автоматически покрывает (тот же app).
10. **AC-10 (регресс нулевой).** `make gate` зелёный.

## Out of Scope

- Резолвинг «итогового» чек-листа (`template items + object overrides`, BR-CHECKLIST-003) — сервис/API будущей стори.
- Reconnaissance-модели/гейтинг готовности ОМ через `ISSUE`-пункты (BR-RECON-003, `CHECKLIST_ISSUES_UNRESOLVED`) — Epic 15's территория.
- API/сериализаторы/вьюхи для чек-листа (§50.3's эндпоинты) — отдельная будущая стори.
- RBAC-право `object.checklist.override_required` (BR-CHECKLIST-004) — 14.12 или отдельная стори.
- Реальные seed-данные типовых шаблонов/пунктов — из скоупа этой стори (модели, не данные).

## Dev Notes

- **Строится ПОВЕРХ живого `models.py`** (14.1/14.2, включая ревью-фиксы: lat/long `CheckConstraint`, `ObjectPassport.object` `PROTECT`, `Post.clean()`) — читать файл ПЕРЕД правкой.
- **`ChecklistItem` НЕ имеет `object`-поля.** Это частая ошибка при беглом чтении буквы «чек-лист ОБЪЕКТА» — пункты принадлежат ШАБЛОНУ (глобальный каталог), связь с конкретным объектом идёт ЧЕРЕЗ `ChecklistBinding`, не напрямую. Не добавлять `object` на `ChecklistItem` — это сломало бы «один шаблон переиспользуется многими объектами».
- **`created_by` — переиспользовать `TimeStampedModel`'s поле, не дублировать.** Донор явно даёт `created_by VARCHAR(100) NOT NULL` на `ops_object_checklist_bindings` — но `TimeStampedModel` (эта кодовая база) УЖЕ имеет `created_by` (`CharField(null=True, blank=True)`). Донор's `NOT NULL` — расхождение с живым базовым классом; живой код весит больше (тот же аргумент, что PK-типа в 14.1's Scope Decision) — НЕ переопределять `created_by`, использовать унаследованное поле как есть (nullable).
- **`ChecklistOverride.clean()` — прямое применение урока 14.2.** Не ждать, пока ревью найдёт ТУ ЖЕ дыру второй раз в другой форме (тот же класс: две FK на разные родственные сущности без гарантии согласованности между ними) — закрыто на этапе dev-story, задокументировано как «известный класс проблемы», не как реакция на конкретную находку.
- **`PROTECT` вместо буквального `RESTRICT`** — см. Scope Decision, семантически эквивалентно для целей этой стори, консистентность с соседними моделями важнее буквального совпадения с донор-SQL-ключевым-словом.
