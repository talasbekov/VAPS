# Story 17.1: Режим проведения — журнал штаба (инструктаж, указания)

Status: done

## Story

As a **держатель права `event.journal.create` (штаб/оперативный дежурный на проводимом ОМ)**,
I want **фиксировать в журнале мероприятия записи инструктажа и указаний, пока `SecurityEvent.status_code == IN_PROGRESS`**,
so that **есть неизменяемая хронология штабных действий по мероприятию — основа для 17.2 (инциденты дописываются в тот же журнал), 17.7 (API/экраны) и 18.2 (архив с полной историей)**.

## Scope Decision

- **FR-29** (prd.md:140): «В режиме проведения ведётся журнал штаба: инструктаж, указания, Инциденты (объект, пост, участники, описание, фото); Инцидент попадает в историю ОМ, Паспорт Объекта и карточки участников.» Эта стори реализует ПЕРВУЮ половину — инструктаж/указания. Инциденты (вторая половина FR-29, отдельная модель-расширение с фото/постом/участниками) — Story 17.2, отдельная стори по декомпозиции (epics.md:1443), не эта.
- **`SecurityEvent.StatusCode.IN_PROGRESS`** уже существует (`events/models.py:49`, Story 15.1) — эта стори НЕ добавляет новый статус-переход, только гейтит запись журнала им (событие обязано УЖЕ быть в проведении; расстановка/утверждение — Epic 16, предшествующие статусы).
- **Не `AuditLog`-паттерн** (`apps/audit/models.py`) — тот системный (actor/action/entity_type/entity_id/old_value/new_value), рассчитан на диффы состояния, не на человеко-читаемый текст инструктажа. Журнал штаба — доменная модель `TimeStampedModel`-наследник (буквальный образец — ВСЕ event-scoped модели `events/models.py`: `AssignmentVersion`, `SecurityEventChecklistItem` и т.д.), с собственным `created_by` (унаследован, ARCH-007/BR-ACCOUNT-002) как автором записи. `record()`-аудит (`apps/audit/services.py`) пишется ДОПОЛНИТЕЛЬНО при создании записи — не вместо доменной модели, тот же паттерн, что `submit_assignment_version()` (16.4/16.6d).
- **`entry_type` — ТОЛЬКО `BRIEFING`/`DIRECTIVE`** в этой стори. `INCIDENT` — зарезервированное будущее значение 17.2 (епикс явно разделяет «журнал штаба» и «Инциденты» на разные стори с разными полями — Инцидент несёт `post`/`participants`/`photo`, которых у инструктажа/указания нет); сервис этой стори отклоняет `INCIDENT` (ещё не реализовано).
- **CheckConstraint на `entry_type`** — буквальный образец `chk_notification_kind` (16.6d, `apps/notifications/models.py`) — DB-уровень, drift-guard тест по `feedback_vaps_db_integrity_checks.md`.
- **Новые RBAC-коды** `event.journal.create`/`event.journal.view` — нет существующего кода в `seed_operations.py` для журнала (просканировано лично); `event.manage` существует, но управляет самим `SecurityEvent`, не журналом (более узкое право для штаба, не для всех, у кого есть `event.manage`) — раскладка ролей PROVISIONAL, тот же паттерн, что `personnel.*`/`document.*` (открытый вопрос Bratan, тест проверяет механизм не политику).
- **API/экраны/e2e — Story 17.7**, не эта. Эта стори — модель + миграция + сервис + аудит + RBAC-код + тесты (сервисный уровень), буквальный объём, который 16.6d держал для нотификаций.

## Acceptance Criteria

1. **AC-1.** Given `event.status_code == IN_PROGRESS`, when actor с `event.journal.create` вызывает сервис создания записи (`entry_type=BRIEFING`, текст), then создаётся `JournalEntry` со `created_by=actor`, `created_at`, привязкой к `event`.
2. **AC-2.** Given `event.status_code != IN_PROGRESS` (любой другой статус, включая `APPROVED`/`CLOSED`), when попытка создать запись, then `ValidationError`, строка не создаётся.
3. **AC-3.** Given несколько записей по одному событию, when читаются, then порядок — хронологический по `created_at` (пин `Meta.ordering`, буквальный литерал, не поведенческая проба — `feedback_update_persistence_assert_from_db.md`).
4. **AC-4.** Given `entry_type=INCIDENT` (ещё не реализовано в этой стори), when попытка создать через сервис, then отклонено (`ValueError`/`ValidationError`) — не путается с «пустой Инцидент».
5. **AC-5.** Given успешное создание записи, then один `AuditLog`-ряд (`record()`, action `JOURNAL_ENTRY_CREATED`) с `entity_type="event"`, `entity_id=event.pk`.
6. **AC-6.** `chk_journal_entry_type`-констрейнт на DB — CREATE вне `{BRIEFING, DIRECTIVE}` в обход сервиса (прямой `.objects.create()`) — `IntegrityError`, drift-guard тест `Kind.values`-паттерн (сверка допустимых значений с DB-констрейнтом байт-в-байт).
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Инциденты (`INCIDENT`-тип, фото/пост/участники) — Story 17.2.
- API endpoints/экраны — Story 17.7.
- Уведомления о новой записи журнала — не запрошено ни FR-29, ни epics.md (в отличие от 16.6's assignment-уведомлений); не изобретается здесь.
- Редактирование/удаление записей — append-only журнал (тот же принцип, что `AuditLog`), UPDATE/DELETE не поддерживаются вообще.
