# Story 10.1: Бумажные контракты экранов сдачи и расхода

Status: review

## Story

As a **оператор-испытатель**,
I want **бумажные контракты двух несущих экранов E10 — светофор-дерева готовности (→10.4) и экрана расхода по вертикали (→10.5) — с зафиксированным ПОВЕДЕНИЕМ и явной сверкой с реальной API-поверхностью бэкенда**,
so that **экраны утверждены на бумаге ДО заморозки их API-вызовов, а расхождения фронт-ожиданий с живым бэком пойманы сейчас (урок 9.7/9.9), а не в середине реализации 10.4/10.5**.

## Scope

Два markdown-контракта в `docs/contracts/` по формату-эталону 09-01 (структура §1-12): (A) **светофор-дерево** — раскладка дерева подразделений с трёхцветными маркерами, каскад, фильтр «только отстающие», polling; границы с `traffic_light.py` (5.5a/5.5b) + флаг «HTTP-роут дерева отсутствует → бэкфилл»; (B) **экран расхода** — выбор даты/«на завтра», 422-блокировка со списком отстающих + override с причиной, скачивание .docx/.xlsx, история «взамен исх.№»; контракт ВЫРОВНЕН с УЖЕ существующими `expense-reports`-эндпоинтами (сверка shape сейчас). Каждый контракт — секция «что требует ПОДПИСИ ДО заморозки API» + «расхождения с API».

## Out of Scope

- **Код экранов** (роуты/компоненты/query/mutation) — 10.4 (светофор), 10.5 (расход). Контракт фиксирует ПОВЕДЕНИЕ, не реализацию.
- **Экран сдачи дня (10.3)** — его поведение (предпросмотр diff/«Сдать день»/drift-маркер) частично уже в 09-01 §7 (преднабор/сдача) + питается светофором (drift = YELLOW); отдельный контракт не заводим, взаимосвязь фиксируем ссылкой из контракта светофора.
- **seam-контракт данных** (bulk-ответ→маркеры) — вход 10.2 (ретро E9), не 10.1. **HTTP-роут светофор-дерева** — бэкфилл-стори (как AI-4 REST-слоя), контракт лишь фиксирует требуемый shape. Реальный .docx/.xlsx-рендеринг — бэк (6.5/E-выпуск).

## Acceptance Criteria

1. **Контракт светофор-дерева.** Given экран №2 (готовность сдачи по дереву подразделений), Then `docs/contracts/10-01-светофор-дерево.md` фиксирует: раскладку (вложенные строки-карточки по прототипу, ленивые ветки — 400 подразделений на 4ГБ), семантику цветов РОВНО по `traffic_light.py` (GREEN=есть сдача+расход сходится; YELLOW=сдача есть, но derived-расход дрейфанул; RED=нет сдачи; NEUTRAL/UNKNOWN — каскад-only 5.5b, лист их не возвращает), каскад вверх по дереву, фильтр «только отстающие», polling-обновление (не WS — E11). Явно: **светофор ТОЛЬКО вскрывает (surfaces) расхождение, никогда не переписывает расход** (by-design 5.5a). Нумерация экранов зафиксирована: грид=№1 (09-01), светофор=№2, расход=№3 — и обратная ссылка 09-01 §1 приведена в соответствие (E1: 09-01 форвард-ссылался на «экран №2, контракт 10.1» как один контракт — теперь 10.1 = два файла 10-01/10-02).

2. **Контракт экрана расхода.** Given экран №3 (выпуск/чтение суточного расхода), Then `docs/contracts/10-02-расход.md` фиксирует: выбор даты + «на завтра», 422-блокировку `TOMORROW_BLOCKED` со списком отстающих подразделений, override «на завтра» с причиной (право `daily_report.override_block`, day-level, горизонт +31д), скачивание .docx (юр-артефакт с бэка) / .xlsx, историю выпусков «взамен исх.№» (цепочка прослеживается), read-only чтение за период.

3. **Сверка с живой API-поверхностью (урок 9.7).** Given `expense-reports`-эндпоинты УЖЕ в schema.d.ts (list/create/override-tomorrow-block/period), Then контракт расхода сверен с их фактическими кодами (403 чужой scope / 404 нет подразделения / 409 нет сдачи | уже выпущен / 422 дата до начала данных | несходимость | TOMORROW_BLOCKED) — расхождения фронт-ожиданий с бэком записаны в §«Расхождения с API», НЕ отложены до 10.5. Для светофора: зафиксировано, что HTTP-роута дерева НЕТ (`traffic_light.py` — сервис без роута) → требуемый shape описан + помечен как бэкфилл ДО 10.4.

4. **Что требует ПОДПИСИ Bratan.** Given оба контракта, Then каждый несёт секцию «что требует ПОДПИСИ ДО заморозки API» (спорные решения раскладки/поведения) + «Открытые вопросы», как 09-01 §10-11. Контракт — НА СОГЛАСОВАНИЕ, не финал.

5. **Границы, формат, регресс.** Оба файла следуют структуре-эталону 09-01 (§1 назначение/§2 раскладка/§поведение/§границы с бэком/§что требует подписи/§открытые вопросы/§ссылки), ссылаются на реальные эталоны (key-rashod.html, DESIGN.md, EXPERIENCE.md, traffic_light.py, schema.d.ts). Ноль кода. Existing 09-01 не трогается (только ссылка из светофора на §7 сдачи). Markdown-линт/битые ссылки чисты.

## Dev Notes

### ⚠️ Ловушка №1 (ГЛАВНАЯ): это КОНТРАКТ, не код

Как 9.1: deliverable — markdown в `docs/contracts/`, фиксирующий ПОВЕДЕНИЕ (раскладку, семантику цветов, коды ошибок, что требует подписи) так, чтобы утвердить на бумаге ДО заморозки API. Ноль React/TS. Реализация светофора = 10.4, расхода = 10.5.

### ⚠️ Ловушка №2: расход — сверять с ЖИВЫМ бэком СЕЙЧАС (урок 9.7/9.9)

`expense-reports`-эндпоинты УЖЕ существуют в schema.d.ts с точными кодами. Ретро E9: «сверить при появлении роута» часто решаемо СЕЙЧАС чтением схемы/бэка — 9.7-контракт bulk заведомо падал бы 400, потому что сверку отложили. Контракт расхода ОБЯЗАН пройти фактические коды expense-reports и записать расхождения, а не отложить до 10.5.

### ⚠️ Ловушка №3: светофор — роута дерева НЕТ → бэкфилл, не выдумка

`traffic_light.py` = сервис 5.5a (одно подразделение) + 5.5b (каскад по поддереву), HTTP-роута в schema.d.ts НЕТ. Контракт фиксирует ТРЕБУЕМЫЙ shape дерева, но помечает: роут — бэкфилл ДО 10.4 (тот же механизм, что AI-4 REST-слоя статусов до 10.2). Не описывать поведение, противоречащее сервису: цвета РОВНО GREEN/YELLOW-drift/RED + NEUTRAL/UNKNOWN каскад-only; светофор НЕ переписывает расход, только вскрывает расхождение (by-design 5.5a).

### ⚠️ Ловушка №4: два контракта — предел стори, не три

Эпик-заголовок «сдачи и расхода», но AC-детализация называет светофор-дерево + расход. Сдача-дня (10.3) уже частично в 09-01 §7 — отдельный контракт НЕ заводим (иначе стори распухнет; BMAD «одна стори — один deliverable», а тут уже два). Связь сдачи со светофором (drift=YELLOW) — ссылкой.
