# Story 15.11a: Аудит выдачи и гашения дежурных полномочий (дотяжка FR-34, часть 1/3)

Status: done

## Story

As a **аудитор**,
I want **видеть в audit-логе, кто и когда выдал/погасил временное дежурное полномочие ОМД/ОРГД**,
so that **срочные («на скорую руку») полномочия не остаются вне журнала штаба (FR-34, FR-38)**.

## Scope Decision (найдено при create-story)

- **Story 15.11 (`epics.md:1426`) целиком** — «Временные полномочия ОМД в действии (дотяжка FR-34 к процессам ОМ)». FR-34 (`epics.md:78`): «Дежурные полномочия ОМД/ОРГД: срочные, авто-вкл/выкл; ОРГД read-only».
- **Research-агент подтвердил (2 независимых прогона, второй скорректировал ложный "architecture.md не существует" — файл есть, `_bmad-output/planning-artifacts/architecture.md`): модель/сервис/API `TemporaryDutyPermission` УЖЕ построены в Epic 1-2** (`architecture.md:126`: «operations (RBAC-слайс): Role/Permission/UserRole/TemporaryDutyPermission... — есть»). Сама стори 2.1 лишь перенесла их в `apps/operations/rbac/` — не строила заново. Изобретать модель/API повторно здесь — прямой дубль-риск.
- **Реальный незакрытый разрыв, а не новая фича:** `RoleAdminService.grant_temporary_duty()`/`expire_temporary_duty()` НЕ вызывают `apps.audit.services.record()` вообще — подтверждено чтением `services.py:139-167`. `apps/operations/tests/test_rbac_matrix.py:149-150` (`ops-temp-duty-list`/`ops-temp-duty-expire`, `_Gate("admin.roles")`) и `apps/audit/tests/test_audit_coverage.py:243-244` (те же ключи, `_DeferredAudit(_RBAC)`) УЖЕ содержат стубы, явно помечающие эту пару как отложенный аудит — это named, признанный проектом разрыв, не самостоятельно изобретённая гипотеза.
- **Story 15.11 — «дотяжка FR-34» — расщепляется на 3 независимые стори** (правило CLAUDE.md: одна цель на стори): **15.11a (эта, аудит)**, 15.11b (ОРГД read-only — реальный, ранее незамеченный разрыв в `PermissionService`, см. ниже), 15.11c (WS-уведомления `TEMP_PERMISSION_ACTIVE`/`TEMP_PERMISSION_EXPIRED` + авто-гашение `is_active` по границе `ends_at`, паттерн 15.10). Каждая — отдельный файл сервиса/теста, без пересечения областей правки.
- **`ops-temp-duty-list` в AUDIT_MATRIX покрывает И `list` (GET), И `create` (POST)** — подтверждено чтением `apps/operations/api/urls.py:28` (`router.register(..., basename="ops-temp-duty")`): DRF-роутер маппит `list`/`create` на ОДИН и тот же URL-паттерн (`{basename}-list`), различая по HTTP-методу. Аудит нужен только на мутации (`create`/`expire`), но матрица держит один ключ на весь `list`-URL — тот же паттерн, что везде в проекте (см. `docs/registries/audit-events.yaml`-запись других list+create-совмещённых маршрутов).
- **`entity_id` — `uuid.UUID(int=grant.pk)`** (та же конвенция, что везде: `operations` — integer PK, `AuditLog.entity_id` — UUID-колонка).
- **`expire_temporary_duty(grant_id)` не принимает `actor`** сегодня — добавляется keyword-only `actor` параметр (аналог `revoke_role`/`assign_role`), `TemporaryDutyViewSet.expire` передаёт `request.actor_id` (тот же паттерн, что `create`).

## Acceptance Criteria

1. **AC-1 (аудит на выдаче).** `grant_temporary_duty()` пишет `TEMP_DUTY_GRANTED` через `record()` — `actor=created_by`, `entity_type="temporary_duty_permission"`, `entity_id=uuid.UUID(int=grant.pk)`, `new_value` — снимок `user_id`/`duty_role_code`/`starts_at`/`ends_at`/`scope_division_id`/`event_id`.
2. **AC-2 (аудит на гашении).** `expire_temporary_duty(grant_id, *, actor)` пишет `TEMP_DUTY_EXPIRED` — только если строка реально существовала и была активна (не пишет строку на несуществующий/уже погашенный `grant_id` — идемпотентность аудита, не задваивать запись).
3. **AC-3 (актёр из HTTP-слоя).** `TemporaryDutyViewSet.expire` передаёт `request.actor_id` в `expire_temporary_duty`.
4. **AC-4 (реестр закрыт).** `docs/registries/audit-events.yaml` — 2 новые записи (`TEMP_DUTY_GRANTED`, `TEMP_DUTY_EXPIRED`).
5. **AC-5 (матрицы обновлены).** `test_audit_coverage.py`: `ops-temp-duty-list`/`ops-temp-duty-expire` — `_DeferredAudit` → `_Audited()`.
6. **AC-6 (регресс нулевой).** `make gate` зелёный, миграция чистая (изменений схемы в этой стори нет — только сервисный код).

- WS-уведомления `TEMP_PERMISSION_ACTIVE`/`TEMP_PERMISSION_EXPIRED` + авто-гашение `is_active` по границе времени — Story 15.11c.
- Изменение модели `TemporaryDutyPermission` (FK на `event`, замена плоского UUID) — не запрошено этой стори, вне FR-34's текста.

### Completion Notes

Реализовано по AC 1-6. `RoleAdminService.grant_temporary_duty()` пишет `TEMP_DUTY_GRANTED` в той же `transaction.atomic` (снимок полей в `new_value`); `expire_temporary_duty(grant_id, *, actor)` получил новый keyword-only `actor` и пишет `TEMP_DUTY_EXPIRED` ТОЛЬКО на реальном `is_active: True → False` переходе — реализовано условным `.filter(id=grant_id, is_active=True).update(...)` + проверка `updated`-счётчика (не через `select_for_update`+ветвление, поскольку `.update()` уже атомарен на уровне одного UPDATE-запроса и возвращает точное число затронутых строк). `TemporaryDutyViewSet.expire` теперь передаёт `request.actor_id`. Оба route-ключа (`ops-temp-duty-list`, `ops-temp-duty-expire`) переведены `_DeferredAudit` → `_Audited()` в `test_audit_coverage.py`; 2 новые записи в `docs/registries/audit-events.yaml`. Один найденный по ходу баг: `entity_id=uuid.UUID(int=grant_id)` в `expire_temporary_duty` падал `TypeError` — `grant_id` приходит строкой из URL-пути DRF (`pk` в `TemporaryDutyViewSet.expire`), исправлено явным `int(grant_id)` до `uuid.UUID(int=...)`. 4 новых теста в `test_temp_duty_api.py` (выдача пишет аудит; гашение пишет аудит; повторное гашение НЕ дублирует; `GET list` не пишет аудит). `make gate` — 3645 passed (было 3641, +4), 0 regressions, no drift.

**3-агентное ревью (Blind Hunter / Edge Case Hunter / Acceptance Auditor) — чисто, реальных багов не найдено:**
- Blind Hunter: порядок `full_clean() → save() → record()` безопасен (исключение из `clean()` предотвращает и запись, и аудит); идемпотентный гард `.filter(id=..., is_active=True).update(...)` race-safe под Postgres READ COMMITTED (статически обосновано); `int(grant_id)`-каст безопасен для всех текущих вызывающих; JSON-сериализация payload'а чистая; `_Audited()`-маркер на совмещённом list/create-маршруте — унаследованная, не новая неточность матрицы, закрытая реальным поведенческим тестом; `request.actor_id` гарантированно непустая строка (fail-closed `require_permission`).
- Edge Case Hunter (живой прогон против реального Postgres): невалидное окно (`starts_at >= ends_at`) — 0 аудит-строк после `ValidationError`, подтверждено живым запуском; **конкурентный пробник — 2 реальных потока, 5 прогонов, КАЖДЫЙ раз ровно 1 `TEMP_DUTY_EXPIRED`-строка**, race-safety подтверждена не статически, а живой конкурентностью; `scope_division_id=None`/`event_id=None` сериализуются чисто; полный прогон `apps/operations/`+`apps/audit/` — 2688 passed, только известные pre-existing teardown-ошибки (ARCH-SEC-032 TRUNCATE-гард на `transaction=True`-тестах, не регресс).
