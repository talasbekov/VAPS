## Story

As a **руководитель**,
I want **для одного подразделения и даты получить трёхцветный светофор `TrafficLightStatus` (GREEN = сдано-и-совпадает / YELLOW = сдано-но-разошлось c diff-деталями / RED = не сдано) плюс отметку `late`, где «разошлось» = `derive(снапшот) != derive(live)` на уровне расход-победителей**,
so that **видно и отставание (RED), и drift после сдачи (YELLOW) — при том что расход остаётся по снапшоту by design (ARCH-DATA-021), а каскад по дереву (5.5b) складывает это per-division состояние вверх**.

## Acceptance Criteria

1. **GREEN — сдано и совпадает.** **Given** действующая `DailySubmission` для (`division_id`, `business_date`) и live-данные дают тот же расход, **When** вызываю `division_traffic_light(division_id, business_date)`, **Then** `status == GREEN`, `late == submission.late`, `drift is None`. Совпадение проверяется по DERIVED-победителям (`resolve_status` по сотруднику), а не по сырым фактам. [Source: epics.md 5.5/5.5a; architecture.md ARCH-DATA-021 L291]
2. **YELLOW-drift — сдано, но разошлось.** **Given** после сдачи внесён интервал, меняющий derived-победителя хотя бы одного сотрудника (или изменился состав live-ростера), **Then** `status == YELLOW`, `drift` несёт детали `{added:[emp_id…], removed:[emp_id…], changed:[{employee_id, from, to}]}` (employee_id — str, from/to — status_type_code). `late == submission.late`. [Source: epics.md 5.5; architecture.md L291 «drift = diff(derive(снапшот), derive(live)) — показывается»]
3. **RED — не сдано.** **Given** нет действующей сдачи (`current_for → None`) для (`division_id`, `business_date`), **Then** `status == RED`, `late == False`, `drift is None`. Контрольный час НЕ гейтит RED (он уже накормил `late` при сдаче 5.3b); RED = просто «нет действующей сдачи». [Source: epics.md 5.5 «сдачи нет к контрольному часу → RED»]
4. **Поздняя сдача: RED → GREEN c отметкой.** **Given** сдача проставлена `late=True` и совпадает с live, **Then** `status == GREEN`, `late == True` (перед сдачей было RED; после поздней сдачи — GREEN+late). [Source: epics.md 5.5 «поздняя сдача: RED → GREEN с отметкой «с опозданием»»]
5. **Перевод задним числом → drift у сдавшего.** **Given** подразделение A сдало день, затем сотрудник переведён/секондмент задним числом так, что live-ростер A или его победитель разошёлся со снапшотом A, **Then** A показывает `YELLOW` c diff-деталями. (Принимающее B — отдельный вызов: его день не сдан → `RED`; per-division независимость.) [Source: epics.md 5.5 «drift у сдавшего A, корректный live у принимающего B»]
6. **Drift — на уровне derive, не сырых фактов.** **Given** после сдачи внесена правка, НЕ меняющая ни одного derived-победителя (напр. добавлен факт МЕНЬШЕГО приоритета под уже-победившим; или пере-создан идентичный по типу/датам факт с новым `status_id`; или переименованы ФИО/звание), **Then** `status == GREEN` (расход держится по снапшоту by design). Это отличает 5.5a от сырого-факт-diff 5.3b `_diff_key`. [Source: architecture.md ARCH-DATA-021 L289-291; epics.md 5.10 иммутабельность]
7. **Самодостаточность снапшота + полуоткрытость.** **Given** снапшот `{schema_version, roster, rows}`, **Then** `derive(снапшот)` считает победителей ТОЛЬКО из снапшота (`date.fromisoformat` для ISO-дат rows; нет повторного `roster_on`/EmployeeStatus по снапшоту); факт с `date_end == business_date` НЕ действует (half-open). Сотрудник в roster без rows → `IN_SERVICE`. [Source: 5-3a snapshot.py; strength_report.py:97]
8. **Гейт + анти-gold-plating.** **Given** функция в `apps/operations/submissions/`, **Then** `make gate` зелёный, `ruff` чист, `makemigrations --check` пуст (миграций НЕТ — read-only). **And** 5.5a НЕ строит каскад/обход дерева/tree-primitive/bulk (5.5b); НЕ API (5.8/10.4); НЕ RBAC-scope (как `StrengthReportService`); НЕ нотиф (5.7)/блок (5.6)/аудит (5.9)/фрактал (5.11)/триггер-amendment (5.4b). [Source: реш. границы]

- **NFR-4:** bulk-селекторы, запрет COUNT-в-цикле → один `overlapping_on` + group-by Python, НЕ `status_on` на сотрудника.

### 🔑 Решения по реализации (ДЕФОЛТЫ — подтвердить/переопределить; вопросы в конце)

1. **Drift = per-employee-winner-diff [ДЕФОЛТ, РЕКОМЕНД.].** Сравниваем `{employee_id: resolve_status(...)}` снапшота против live: `added/removed/changed`. *Почему:* (а) расход = гистограмма победителей → per-employee diff строго чувствительнее column-counts (ловит свопы, что дают те же счётчики); (б) снапшот НЕ хранит Штат → `derive_report` (нужен `staff_map`) неприменим к снапшоту as-is; (в) per-employee diff даёт actionable diff-детали (employee X: IN_SERVICE→SICK). *Альтернатива:* сравнить `derive_report` status-колонки (грубее, `staff_map={}`) — отклонено. *Вопрос Q1.*
2. **derive(live) — OWN-LEVEL [ДЕФОЛТ].** `roster_on(date, {division_id})` + `overlapping_on`, НЕ `StrengthReportService.compute` (он subtree-агрегирует через `subtree_ids` → это уже каскад). Снапшот own-level (5.3a реш.№2) → сравнение like-with-like. Subtree-роллап — 5.5b.
3. **RED = нет действующей сдачи [ДЕФОЛТ].** Контрольный час НЕ гейтит RED в селекторе — он уже определил `late` при сдаче (5.3b `_is_late`, поле на модели). Поздняя сдача RED→GREEN+late = «как только сдано (пусть поздно) → не RED». *Альтернатива:* RED только если `now > control_hour` (серый-до-дедлайна) — отклонено (усложняет, AC буквально «сдачи нет → RED», late уже несёт «поздно»). Дедлайн/«необходимые управления» — забота блокировки 5.6. *Вопрос Q2.*
4. **Пустой ростер + нет сдачи → RED [ДЕФОЛТ].** Без 4-го состояния (3 цвета строго, architecture L387). Различение «не-сдающий промежуточный узел / neutral» — забота КАСКАДА 5.5b (он решает, как складывать узлы без своей сдачи). 5.5a per-division: нет current_for → RED. *Вопрос Q3.*
5. **Без actor/RBAC-scope [ДЕФОЛТ].** Зеркало `StrengthReportService.compute` (его докстринг: «MUST NOT take request/actor … RBAC narrowing arrives with the API stories»). Видимость/scope-403 — 5.8/10.4. 5.5a считает по любому переданному `division_id`.
6. **Ключи — str ОБЕ стороны + ISO→date [ДЕФОЛТ, ТРАП].** snapshot `employee_id`=str, dates=ISO; live `employee_id`=UUID, dates=date. Нормализовать ключи `str(...)`, парсить снапшот-даты `date.fromisoformat`. Иначе ложный 100%-drift (UUID≠str) или TypeError в `resolve_status` (str≤date).
7. **Светофор ТОЛЬКО показывает drift [ДЕФОЛТ, граница].** НЕ триггерит amendment. Энфорс amendment = 5.4b и покрывает ТОЛЬКО `resolve_pending_clarification`; прочие правки (create_status/секондмент-after-submit) drift'ят молча → светофор = safety-net (YELLOW). Amended-путь сам-лечится (снапшот v2 == live → GREEN).
8. **Лениент к несуществующему division [ДЕФОЛТ].** 5.5a — селектор-проекция: неизвестный валидный UUID → `current_for` None + `roster_on` пусто → RED (пустой live). Existence/404 — API-слой (5.8/10.4), как 5.3a builder лениент, а 5.3b service валидирует. Без `CoreDivisionTreeSelector.exists` здесь.

```python
# apps/operations/submissions/traffic_light.py
from dataclasses import dataclass
from datetime import date
from django.db import models
from apps.core.selectors import HistoricalEmployeeSelector
from apps.operations.statuses.selectors import EmployeeStatusSelector
from apps.operations.statuses.services import resolve_status   # pure winner
from apps.operations.submissions.selectors import DailySubmissionSelector

class TrafficLightStatus(models.TextChoices):
    GREEN = "GREEN", "Зелёный"
    YELLOW = "YELLOW", "Жёлтый"
    RED = "RED", "Красный"

@dataclass(frozen=True)
class DivisionTrafficLight:
    status: str
    late: bool
    drift: dict | None

def _live_winners(division_id, business_date) -> dict[str, str]:
    emp_ids = HistoricalEmployeeSelector.roster_on(business_date, {division_id}).get(division_id, [])
    rows = EmployeeStatusSelector.overlapping_on(business_date, emp_ids)  # ONE query
    by_emp: dict[str, list] = {}
    for r in rows:
        by_emp.setdefault(str(r["employee_id"]), []).append(r)          # dates already date-objects
    return {str(e): resolve_status(by_emp.get(str(e), []), business_date) for e in emp_ids}

def _snapshot_winners(snapshot, business_date) -> dict[str, str]:
    by_emp: dict[str, list] = {}
    for r in snapshot["rows"]:
        by_emp.setdefault(r["employee_id"], []).append({
            "status_type_code": r["status_type_code"],
            "date_start": date.fromisoformat(r["date_start"]),           # ISO -> date
            "date_end": date.fromisoformat(r["date_end"]),
        })
    return {row["employee_id"]: resolve_status(by_emp.get(row["employee_id"], []), business_date)
            for row in snapshot["roster"]}

def _diff_winners(snap, live) -> dict | None:
    added = sorted(set(live) - set(snap))
    removed = sorted(set(snap) - set(live))
    changed = sorted(
        [{"employee_id": e, "from": snap[e], "to": live[e]} for e in set(snap) & set(live) if snap[e] != live[e]],
        key=lambda d: d["employee_id"],
    )
    if not (added or removed or changed):
        return None
    return {"added": added, "removed": removed, "changed": changed}

def division_traffic_light(division_id, business_date) -> DivisionTrafficLight:
    current = DailySubmissionSelector.current_for(division_id, business_date)
    if current is None:
        return DivisionTrafficLight(TrafficLightStatus.RED.value, late=False, drift=None)
    drift = _diff_winners(_snapshot_winners(current.snapshot, business_date),
                          _live_winners(division_id, business_date))
    status = TrafficLightStatus.GREEN if drift is None else TrafficLightStatus.YELLOW
    return DivisionTrafficLight(status.value, late=current.late, drift=drift)
```

### Подводные камни для dev-агента

- **str vs UUID ключи:** снапшот `employee_id` уже str; live `roster_on`/`overlapping_on` дают UUID → `str(...)` ОБЕ стороны до сравнения. Регресс = 100%-ложный-drift.
- **ISO vs date:** снапшот-rows dates — строки; `resolve_status` сравнивает `date_start <= on_date < date_end` с `on_date: date` → `date.fromisoformat` снапшот-даты. Live-rows уже `date` (ORM). `business_date` передавать как `date`.
- **НЕ `status_on` в цикле** — N+1 (его докстринг прямо запрещает). Один `overlapping_on(date, roster_ids)` + Python-группировка.
- **НЕ `StrengthReportService.compute`** для live — он subtree-агрегирует (`subtree_ids`) → это каскад 5.5b. 5.5a own-level через `roster_on(date, {division_id})`.

- **Снапшот roster — это denominator:** сотрудник в roster без rows ⇒ derive IN_SERVICE; нельзя пропускать таких при сборке снапшот-победителей (итерировать по roster, не по rows).
