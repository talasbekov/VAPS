# Story 16.2: Черновик авто-формирования Расстановки из выделенных (FR-26)

Status: ready-for-dev

## Story

As a **система расстановки**,
I want **автоматически собрать черновую версию Расстановки из уже назначенных физнарядом сотрудников**,
so that **планировщик не начинает Расстановку с пустого листа (FR-26 «Черновая Расстановка автоматически»)**.

## Scope Decision (найдено при create-story — КРИТИЧЕСКОЕ сужение объёма)

- **Research-агент нашёл ДВА реальных, независимых разрыва данных, делающих буквальное «авто-формирование из ВЫДЕЛЕННЫХ [Группам]» невозможным СЕГОДНЯ — не гипотеза, проверено чтением моделей:**
  1. **`GroupForceRequest.allocated_count` — ЧИСЛО, не список сотрудников.** `Group` (`apps/operations/events/models.py`) — плоский 3-полевой справочник (code/name/sort_order), БЕЗ ростера участников; `SecurityEventStaffingDemand.group` — свободный текст. **Нет пути от «выделенной Группы» к именованным сотрудникам** — ни модели `GroupMember`, ни любой другой связности. Изобретать её здесь — прямой риск неверного предположения (тот же класс решения, что 15.10/15.11's PROVISIONAL-сужения).
  2. **`SecurityEventSectorPost.post` — свободный текст (label), НЕ FK.** `PlacementAssignment.post` (16.1) — FK на РЕАЛЬНЫЙ `ops_facilities.Post`. Между «пост из рекогносцировки» (текстовая метка) и «реальный Пост объекта» (FK-таргет) сегодня НЕТ связи в коде.
  3. **Фронтенд-прототип ТОЖЕ не строит это** — `FRONTEND_TRACEABILITY_MATRIX.md`: «Черновик расстановки (авто) | ... | Not started». Единственный реализованный путь расстановки в прототипе — 100% ручной (один `employeeId`+`postId` за раз, `findPersonnel()`-поиск).
- **PROVISIONAL-решение (сужение объёма, задокументировано явно, не изобретается новая бизнес-логика без данных):**
  1. **Авто-формирование драфтит ТОЛЬКО из `SecurityEventDirectAssignment`** (физнаряд, 15.9) — это ЕДИНСТВЕННАЯ структура Epic 15 с реально именованными сотрудниками (`employee_id`, плоский UUID). `GroupForceRequest`'s headcount-выделения (без имён) — ЯВНО ВНЕ ОБЪЁМА этой стори; их наполнение именами — задача планировщика ВРУЧНУЮ (будущая стори с ручным добавлением строк в черновик, не 16.2). Заголовок стори («из выделенных») трактуется как «из физнаряда, уже несущего реальных людей», не буквально «из всех Epic 15's allocation-путей».
  2. **Post-резолюция — best-effort по `(object, code)`, с явным «unmatched»-списком** (тот же паттерн, что 15.7b's `unmatched_groups`): для каждого `SecurityEventDirectAssignment.sector_post.post`-текста ищется `facilities.Post` с `object=event.object, code=<текст>` (та же пара, что `uq_object_post_code`-констрейнт). Совпало → создаётся `PlacementAssignment`. Не совпало → строка попадает в `unmatched` (не в `PlacementAssignment`, не блокирует остальные строки) — планировщик добавляет вручную позже.
  3. **Один вызов = одна НОВАЯ DRAFT-версия** (`AssignmentVersion.status=DRAFT`), а НЕ мутация существующей — повторный вызов ПОСЛЕ уже созданного драфта либо 409 (есть текущая версия, драфт нельзя пересобрать поверх), либо явно требует, чтобы текущей версии не было ИЛИ была не-DRAFT (см. AC-5) — не молча дублирует.
- **Область стори — сервис + management-обвязка НЕ строится** (это не catch-up job, а разовое действие «сформировать черновик») — вызывается сервисной функцией напрямую, HTTP-обёртка/API — Story 16.8, не эта.
- **Аудит** — новая запись `PLACEMENT_DRAFT_FORMED` (реестр `docs/registries/audit-events.yaml` пуст для Epic 16 — первая запись эпика, подтверждено research-агентом Story 16.1).

## Acceptance Criteria

1. **AC-1 (черновик формируется из физнаряда).** `form_draft_placement(event_id, actor)` создаёт `AssignmentVersion(status=DRAFT, version=1, is_current=True)` + одну `PlacementAssignment` на КАЖДЫЙ `SecurityEventDirectAssignment` события, чей `sector_post.post`-текст резолвится в реальный `facilities.Post` (тот же `object`, `code=` совпадение).
2. **AC-2 (нерезолвленные — в `unmatched`, не блокируют).** `SecurityEventDirectAssignment`, чей `sector_post.post` НЕ совпал ни с одним `Post.code` того же объекта — возвращается в `unmatched`-списке (сотрудник+исходный текст поста), НЕ создаёт `PlacementAssignment`, не прерывает формирование остальных.
3. **AC-3 (нет физнарядов — пустой черновик, не ошибка).** Событие без `SecurityEventDirectAssignment` — черновик всё равно создаётся (пустая версия, ноль `PlacementAssignment`), не 4xx/exception — планировщик может начать с пустого листа осознанно.
4. **AC-4 (повторный вызов при существующей текущей версии — отклоняется).** Событие с УЖЕ существующей `is_current=True`-версией (любого статуса) — повторный вызов `form_draft_placement` НЕ создаёт вторую текущую версию (нарушило бы 16.1's partial-unique) — явная доменная ошибка, не молчаливый no-op и не `IntegrityError`, всплывающий наружу.
5. **AC-5 (аудит).** `record(action="PLACEMENT_DRAFT_FORMED", ...)` — одна запись на успешное формирование, `new_value` несёт `matched_count`/`unmatched_count`.
6. **AC-6 (регресс нулевой).** `make gate` зелёный, миграция чистая (новых полей/моделей эта стори не добавляет — только сервис+тесты).

## Out of Scope

- Авто-формирование из `GroupForceRequest` (нет ростера) — открытый вопрос, требует будущей стори с реальным `GroupMember`/ростер-моделью, если продукт решит, что она нужна.
- Ручное добавление/редактирование строк черновика планировщиком — будущая стори (16.2 создаёт стартовую точку, не полный CRUD).
- Согласование/возврат/утверждение версии (`SUBMITTED`/`RETURNED`/`APPROVED`-переходы) — Story 16.4.
- Конфликт-детекция (`conflict_severity`-заполнение) — Story 16.3.
- API/HTTP-обёртка — Story 16.8.
- Автоматическое создание недостающих `facilities.Post`-строк для нерезолвленных постов — не изобретается; `unmatched` остаётся явным сигналом человеку, не auto-fix.
