# Story 15.8: `PATCH /force-requests/{id}/allocate` — выделение людей брокером (FR-24)

Status: ready-for-dev

## Story

As a **брокер**,
I want **проставить количество выделенных людей на запрос Группы**,
so that **статус запроса отражает прогресс комплектования, а ОМД видит, сколько ещё не хватает**.

## Scope Decision (найдено при create-story)

- **Story 15.8 (`epics.md:1423`, личная проверка research-агента + ре-верификация):** «Выделение людей брокером (двухуровневый брокеридж, FR-24)». Единственный текст — нет отдельного story-файла ещё, нет AC. FR-24 (`epics.md:62`): «Двухуровневый брокеридж: запросы Группам → брокеры выделяют; физнаряд — ОМД напрямую».
- **«Физнаряд — ОМД напрямую» — НЕ эта стори.** Story 15.9 (`epics.md:1424`) — «Физнаряд: прямое назначение ОМД; правила «спора за человека» и дефицита» — отдельная стори, подтверждено research-агентом.
- **Выделение — количественное, НЕ по конкретным людям.** Frontend-прототип (`frontend/src/features/security-events/api/pending-contracts.ts:86-90`, soft-сигнал) — `UpdateForceAllocationRequest {allocatedCount, comment}`, без `employeeId`. `GroupForceRequest.allocated_count` (15.7a) уже смоделирован как счётчик, не M2M на сотрудников — подтверждает выбор.
- **`status`-переход выводится из сравнения `allocated_count` vs `requested_count`** (тот же паттерн, что frontend-прототип's `updateForceAllocation`, soft-сигнал): `allocated_count == 0` → остаётся `SENT`; `0 < allocated_count < requested_count` → `PARTIALLY_ALLOCATED`; `allocated_count >= requested_count` → `ALLOCATED`. Не отдельное клиентское поле — сервер вычисляет.
- **`SecurityEvent.status_code` НЕ переходит в `BROKERAGE` этой стори.** Нет backend-свидетельства, что переход в `BROKERAGE` триггерится записью `allocated_count` (research-агент подтвердил: `BROKERAGE` — только enum-значение, ни одного raise-сайта). Frontend-прототип использует ОТДЕЛЬНОЕ поле (`stage`, не `status_code`) с ОТДЕЛЬНЫМ явным действием-завершением (`completeForces`), гейтующим на «все запросы полностью укомплектованы» — по аналогии by-inference, НЕ прямому свидетельству. Переход `SecurityEvent.status_code` в `BROKERAGE`/далее — открытый вопрос, оставлен будущей стори (или уточнению продукта), не изобретается здесь без спеки.
- **Permission — переиспользуется существующий `brokerage.manage`** (уже в `seed_operations.py`, «Брокеридж», уже назначен роли `OMD`) — НЕ frontend-прототипа's `ops.force_allocation.manage` (другая строка, не backend-авторитетная). Backend-код семантически точнее совпадает с FR-24's «брокеры выделяют».
- **`allocated_count` НЕ может превышать `requested_count`.** Не найдено явного запрета в спеке, но логически необходимо (нельзя выделить больше, чем запрошено) — консервативный валидационный гвард, не бизнес-изобретение.
- **Гейт по статусу запроса — НЕ ограничен.** Донор-спека не даёт правила «можно выделять только из SENT» — разрешено из любого статуса (переставление `allocated_count` вручную/коррекция — легитимный сценарий, тот же принцип, что везде в Epic 15 — не гейтовать без спеки).

## Acceptance Criteria

1. **AC-1 (выделение, полное).** `PATCH /security-events/{id}/force-requests/{request_id}/allocate` с `{allocated_count: N}`, `N >= requested_count` → 200, `status` становится `ALLOCATED`.
2. **AC-2 (частичное выделение).** `0 < N < requested_count` → `status` становится `PARTIALLY_ALLOCATED`.
3. **AC-3 (`N == 0`).** `status` возвращается/остаётся `SENT` (не `PARTIALLY_ALLOCATED`/`ALLOCATED`).
4. **AC-4 (валидация — не больше запрошенного).** `N > requested_count` → 400 (`VALIDATION_ERROR`).
5. **AC-5 (permission).** Требует `brokerage.manage` — без него 403.
6. **AC-6 (404).** Нечисловой/несуществующий `request_id` — 404, не 500.
7. **AC-7 (аудит).** `GROUP_FORCE_REQUEST_ALLOCATED` — на каждом реальном изменении `allocated_count` (idempotent-повтор того же значения — без дублирующего аудита).
8. **AC-8 (регресс нулевой).** `make gate` зелёный, роут — в обоих живых реестрах.

## Out of Scope

- Выделение по конкретным сотрудникам (не количество) — не запрошено, frontend-прототип тоже количественный.
