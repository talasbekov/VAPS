# Story 15.11c: Авто-гашение и WS-уведомления дежурных полномочий (дотяжка FR-34, часть 3/3)

Status: review

## Story

As a **дежурный ОМД/ОРГД и его руководство**,
I want **получать уведомление о начале и окончании временного полномочия, а сама строка гранта автоматически гаситься по истечении окна**,
so that **дежурство «срочные, авто-вкл/выкл» (FR-34) не остаётся молчаливым фактом в БД без сигнала участникам**.

## Scope Decision (найдено при create-story)

- **Завершающая часть 3/3 расщепления Story 15.11** (`epics.md:1426`, FR-34). 15.11a закрыла аудит, 15.11b закрыла «ОРГД read-only». Эта часть закрывает последнюю половину FR-34's текста — «авто-вкл/выкл» — и реализует уже зарезервированные, но никогда не эмитируемые типы уведомлений.
- **Авторизационная сторона «авто-вкл» УЖЕ работает** — `PermissionService._active_grants()` (`apps/operations/services.py`) считает активность строго по окну `starts_at__lte=now, ends_at__gte=now` НЕЗАВИСИМО от статического поля `is_active`, так что реальный доступ уже включается/выключается «на лету» по часам (ARCH-SEC-031, `architecture.md:318,757`: «гашение — со следующего запроса», уже соблюдено). Эта стори НЕ трогает `PermissionService` — доступ и так корректен.
- **Реальный незакрытый разрыв:** (1) поле `is_active` само по себе НИКОГДА не флипается автоматически по `ends_at` — остаётся `True` в БД вечно, если никто не вызовет `POST /expire/` вручную (не влияет на авторизацию, но вводит в заблуждение в списке/аудите — «висящий» грант выглядит активным). (2) `TEMP_PERMISSION_ACTIVE`/`TEMP_PERMISSION_EXPIRED` зарегистрированы в `docs/registries/ws-message-types.yaml` (строки ~207-220), но `grep` по всей кодовой базе — НОЛЬ совпадений эмиссии (подтверждено дважды двумя research-агентами в рамках 15.11a). Это единственные два типа во всём реестре без `generated_by_story`-цитаты (все прочие типы либо реально эмитируются, либо явно помечены как форвард-семя будущего эпика) — сильный сигнал, что это именно то, что стори 15.11 («в действии») должна была закрыть.
- **Механизм — тот же beat-ready-без-Celery паттерн, что 15.10** (`escalate_stale_force_requests`): management-команда, вызываемая по расписанию, без импорта Celery.
- **Переиспользуется `RoleAdminService.expire_temporary_duty()` из 15.11a целиком** — авто-гашение по `ends_at` не изобретает новый путь мутации `is_active`, а вызывает УЖЕ СУЩЕСТВУЮЩИЙ идемпотентный, аудируемый метод с `actor="SYSTEM"` (тот же паттерн, что `escalate_stale_force_requests()`'s `actor="SYSTEM"` из 15.10). Аудит `TEMP_DUTY_EXPIRED` уже пишется этим вызовом — новой аудит-записи для гашения эта стори НЕ добавляет.
- **Новое поле `activated_notified_at`** (nullable, проставляется один раз, никогда не сбрасывается) — необходимо ТОЛЬКО для WS-уведомления о НАЧАЛЕ (`TEMP_PERMISSION_ACTIVE`): в отличие от гашения (где `is_active: True → False` — естественный, самодостаточный маркер идемпотентности), «начало» не меняет ни одного поля модели сегодня — без отдельного маркера повторный прогон catch-up-джобы посылал бы уведомление о начале повторно на каждом прогоне.
- **Уведомления — ПЕРСОНАЛЬНЫЕ (per-grant), НЕ digest** (в отличие от 15.10's батч-агрегации): реестр (`recipients: "duty user"`) явно про ОДНОГО получателя — держателя гранта (`grant.user_id`), не список ролей. `notify()`'s `(recipient, kind, business_date)`-уникальность здесь работает ЕСТЕСТВЕННО без коллизий — один пользователь редко получает 2+ дежурных гранта в один день, но даже если так, `kind`-константа общая для ВСЕХ грантов пользователя за день (не по `grant.id`) — задокументированный, принятый предел (см. Out of Scope), тот же класс упрощения, что 15.10's «digest» для избежания per-row-коллизии, только в обратную сторону (здесь digest НЕ нужен, коллизия — редкий крайний случай, не системная).
- **Триггер команды — оба направления в ОДНОМ прогоне** (активация + гашение), как единая catch-up-функция — не два отдельных management-команды (меньше файлов, одна ответственность «обработать переходы дежурных грантов»).

## Acceptance Criteria

1. **AC-1 (поле-маркер).** Новое nullable-поле `activated_notified_at` на `TemporaryDutyPermission`.
2. **AC-2 (management-команда).** `process_temp_duty_transitions` (или аналогичное имя) — единый catch-up: активация + гашение.
3. **AC-3 (уведомление о начале).** Для гранта с `starts_at <= now <= ends_at`, `activated_notified_at IS NULL` — `notify(recipient=grant.user_id, kind="TEMP_PERMISSION_ACTIVE", ...)`, `activated_notified_at` проставляется.
4. **AC-4 (авто-гашение + уведомление о конце).** Для гранта с `is_active=True`, `ends_at < now` — `RoleAdminService.expire_temporary_duty(grant.id, actor="SYSTEM")` (флипает `is_active`, пишет `TEMP_DUTY_EXPIRED`-аудит, идемпотентно) + `notify(recipient=grant.user_id, kind="TEMP_PERMISSION_EXPIRED", ...)`.
5. **AC-5 (идемпотентность).** Повторный прогон НЕ отправляет повторное уведомление ни о начале (гард `activated_notified_at`), ни о конце (гард `is_active=True`, тот же принцип, что 15.11a).
6. **AC-6 (грант, истёкший ДО начала мониторинга, — не паникует).** Грант, у которого `ends_at` УЖЕ в прошлом на первом же прогоне (никогда не видел «активного» состояния) — гасится и получает `TEMP_PERMISSION_EXPIRED`; `TEMP_PERMISSION_ACTIVE` для него НЕ отправляется (т.к. `activated_notified_at` мог остаться `NULL` — не путать «не успел стать активным» с багом).
7. **AC-7 (регресс нулевой).** `make gate` зелёный, миграция чистая.

## Out of Scope

- Изменение `PermissionService`/логики авторизации — уже корректна (см. Scope Decision), не трогается.
- Digest-агрегация нескольких уведомлений в одно (в отличие от 15.10) — не нужна, «один держатель — один грант за раз» типичный случай; редкая коллизия (2+ гранта одному пользователю в один день) — принятый предел, `notify()`'s «первый payload побеждает» может потерять второе уведомление в этом редком случае (тот же класс упрощения, что был БЫ у 15.10 без агрегации — но здесь коллизия на порядок реже, аудит/данные не теряются, только WS-сигнал).
- Beat/Celery-регистрация — будущая стори (тот же принцип, что 5.7b2/12.6/15.10).
- Уведомление руководства/вертикали о начале/конце дежурства — реестр (`recipients: "duty user"`) явно про самого дежурного, не про эскалацию (в отличие от 15.10's FR-42 — разные FR, разная семантика получателя).
