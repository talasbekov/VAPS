# Story 3.6: Операции жизненного цикла статуса

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **оператор**,
I want **управлять жизненным циклом созданного статуса тремя операциями — продление (новая, более поздняя дата конца), досрочное завершение (фактический конец ≤ сегодня) и отмена (только для ещё не начавшегося PLANNED), причём отмена фиксирует append-once факты `cancelled_at/by/reason`**,
so that **статусы управляемы и исправимы с полным следом «было/стало», при этом необратимые факты (отмена не-начавшегося, досрочное завершение начавшегося) нельзя подменить или переписать — данные остаются доверенными**.

## Acceptance Criteria

Источник: [epics.md#L522-L529] (Story 3.6), FR-10 (lifecycle) [epics.md#L174], ARCH-DATA-022 (derived-first, append-once cancel) [architecture.md#L83], а также три forward-defer из 3.1–3.5: append-once `cancelled_at` без охраны + механика отмены [deferred-work.md#L33], edit-override [deferred-work.md#L286], non-DEFERRABLE exclusion как скрытый контракт edit-сервисов [deferred-work.md#L34].

1. **AC-1 (отмена — только PLANNED).** Given USER-статус в состоянии **PLANNED** (`date_start > today`, не отменён), When оператор отменяет с непустой причиной, Then записываются append-once факты `cancelled_at=Clock.now()`, `cancelled_by=actor`, `cancelled_reason=reason`; производное состояние → **CANCELLED** (через существующий `derive_state`); строка покидает конфликт/exclusion-периметр (фильтр `cancelled_at__isnull=True` уже в детекторе и в GiST-constraint).
2. **AC-2 (отмена не-PLANNED → 422).** Given статус в **ACTIVE** или **COMPLETED**, When отменяю, Then `DomainError(422)` `INVALID_LIFECYCLE_TRANSITION` — ничего не мутировано (отмена = «событие не состоялось»; начавшийся/прошедший факт завершают досрочно, не отменяют). Already-CANCELLED → тоже 422 (см. AC-3).
3. **AC-3 (append-once / необратимость на сервис-уровне).** Given уже-CANCELLED статус, When повторная отмена ИЛИ любая lifecycle/edit-операция (extend/early-complete/update), Then `DomainError(422)` `INVALID_LIFECYCLE_TRANSITION`; `cancelled_at/by/reason` единожды установленные НЕ перезаписываются и НЕ обнуляются сервисом. **Раз-отмена (`cancelled_at=NULL`) и правка отменённой строки на уровне БД (REVOKE/триггер) — Epic 4**; 3.6 закрывает инвариант на сервис-уровне и явно документирует DB-level → E4 (deferred-work.md#L33).
4. **AC-4 (причина отмены обязательна — Решение №1=A).** Given отмена с пустой/whitespace `reason`, Then `DomainError(400)` `VALIDATION_ERROR` — проверка до любой мутации; ничего не записано. (Зеркалит контракт причины override из 3.5.)
5. **AC-5 (досрочное завершение — факт ≤ сегодня).** Given USER-статус в **ACTIVE**, When завершаю досрочно с `actual_end`, где `date_start < actual_end ≤ today`, Then `date_end = actual_end`, состояние на сегодня → **COMPLETED** (полуоткрытый `[start, actual_end)`, `today ≥ actual_end`), исходный интервал замещён (след «было/стало» — изменение поля; полное audit-событие → E4/4.4).
6. **AC-6 (досрочное завершение — границы).** Given `actual_end > today` (конец в будущем — это не «факт»), Then `DomainError(422)` `INVALID_LIFECYCLE_TRANSITION`. Given `actual_end ≤ date_start` (пустой/инвертированный), Then `DomainError(422)` `INVALID_DATE_RANGE`. Given статус не-ACTIVE (PLANNED/COMPLETED/CANCELLED), Then `DomainError(422)` `INVALID_LIFECYCLE_TRANSITION` (PLANNED отменяют, COMPLETED уже завершён).
7. **AC-7 (продление — более поздняя дата конца).** Given USER-статус не-CANCELLED, When продлеваю новой `date_end > текущей date_end`, Then после ре-валидации (граница увольнения + `max_duration_days` типа, через существующий `_validate_interval`) и конфликт-проверки (`_assert_no_conflict`, `exclude_pk=self`) `date_end` обновлён. Given `new_date_end ≤ текущей date_end` (не продление, а сокращение) → `DomainError(422)` `INVALID_LIFECYCLE_TRANSITION` (сокращение = досрочное завершение, AC-5). CANCELLED → 422 (AC-3).
8. **AC-8 (override при продлении — закрывает defer 3.5).** Given продление натыкается на soft-409 (`STATUS_OVERLAP_WARNING`), When повторяю с `override=True` + непустой причиной, Then soft обойдён и создана `Override`-запись (реюз 3.5-машинерии: `_assert_no_conflict(override=True)` → запись в том же savepoint); hard-пересечение → 422 `OVERLAPPING_HARD_STATUS`, override НИКОГДА не обходит hard. (Закрывает deferred-work.md#L286 «edit-override → 3.6».)
9. **AC-9 (editability + lock + атомарность — общий каркас).** Все три операции: (а) под `_lock_employee` (404 если нет сотрудника) внутри `@transaction.atomic` + внутренний savepoint вокруг записи (race-бэкстоп `excl_hard_status_overlap` → 422 через §36-handler, прецедент 3.3/3.5); (б) вызывают `status.assert_user_editable()` ДО мутации → проекционные строки (`source != USER`: OM_AUTO/KU_SYNC) → 422 `AUTO_STATUS_READONLY`. Системное закрытие проекционных строк (`dismissal`) этот путь НЕ трогает.
10. **AC-10 (закрытый мир + миграция).** Вводится РОВНО один новый код `INVALID_LIFECYCLE_TRANSITION` (422, `overridable: false`) в `error-codes.yaml` (Решение №2=A — реестр не покрывает «недопустимый переход», ближайшие коды семантически чужие). Прочие коды переиспользуются (`VALIDATION_ERROR`, `INVALID_DATE_RANGE`, `OVERLAPPING_HARD_STATUS`, `STATUS_OVERLAP_WARNING`, `AUTO_STATUS_READONLY`, `MAX_DURATION_EXCEEDED`, `DATE_OUTSIDE_EMPLOYMENT`). Миграция `0006` (AddField `cancelled_by`, `cancelled_reason`) обратима; round-trip forward→reverse→forward на одноразовой БД (прецедент 3.2/3.5); `makemigrations --check` чист.
11. **AC-11 (регрессия нулевая).** Существующие тесты 3.3 (`create_status`/`update_status`), 3.4 (конфликт-детектор), 3.5 (override) — зелёные без правок; новые поля nullable с дефолтами, новые функции — аддитивны.

## Dev Notes

### Решения (ПРИНЯТО = A по рекомендации; Bratan может переиграть на B перед/во время dev-story)

> **№1 = A** (причина отмены обязательна) · **№2 = A** (один новый код `INVALID_LIFECYCLE_TRANSITION`) · **№3 = A** (override включён в `extend`, закрывает defer 3.5). Приняты по рекомендации; не финальное «РЕШЕНО Bratan» — флипай при желании.

> **Решение №1 — обязательность `reason` при отмене. → A.**
> - **Вариант A (предложено):** непустая причина обязательна (`.strip() != ""`), иначе 400 `VALIDATION_ERROR`. AC формулирует `cancelled_reason` как append-once ФАКТ и требует «полный след было/стало»; пустая отмена не несёт следа. Зеркалит контракт причины override (3.5 Решение №1=A).
> - Вариант B: причина опциональна (отмена может быть без объяснения). Проще, но «след» теряет смысл и расходится с override-прецедентом.
> Рекомендация: **A** (непустая причина; граница длины 10–500 BR-003 — отдельный follow-up при HTTP-сериализаторе, как в 3.5).

> **Решение №2 — новый код vs реюз для «недопустимый переход». → A.**
> - **Вариант A (предложено):** ввести РОВНО один `INVALID_LIFECYCLE_TRANSITION` (422). Реестр (см. References) НЕ содержит кода для state-guard-нарушения; `AUTO_STATUS_READONLY` — про проекцию, `INVALID_DATE_RANGE` — про инверсию интервала, `INVALID_STATUS_TYPE` — про справочник. «Отмена только PLANNED» (AC буквально 422) не маппится ни на один → честный новый код, один на все три перехода.
> - Вариант B: переиспользовать `INVALID_DATE_RANGE` (422) для всего. Экономит код, но семантически ложно (отмена ACTIVE — не про даты) и теряет диагностичность (клиент/тест не отличит «переход запрещён» от «интервал пуст»).
> Рекомендация: **A** (один новый код; closed-world 3.5 нарушается минимально и обоснованно — гэп реальный, не угаданный).

> **Решение №3 — override в `extend_status`. → A.**
> - **Вариант A (предложено):** `extend` принимает `override`/`override_reason` и пишет `Override` при обходе soft (реюз 3.5). Закрывает явный forward-defer «edit-override → 3.6» (deferred-work.md#L286); продление — ровно тот «edit интервала в обход soft-конфликта», что 3.5 отложила.
> - Вариант B: extend без override (soft-overlap при продлении всегда 409, обход — позже). Меньше поверхность, но оставляет defer открытым и делает продление в пересечение неоперабельным.
> Рекомендация: **A** (закрыть defer; `early-complete`/`cancel` override НЕ нужен — сокращение/отмена не создают новых пересечений).

### Архитектурные правила (developer guardrails)

- **Реюз 3.3/3.4/3.5-инфраструктуры — НЕ переписывать.** Все хелперы готовы: `_require_actor`, `_lock_employee` (404), `_resolve_status_type` (422), `_validate_interval` (увольнение/max_duration/инверсия → 422), `_assert_no_conflict(..., exclude_pk=, override=)` (hard→422, soft→409|обход+возврат), `_conflict_details`, `Override`. 3.6 = ТРИ новые функции, собранные из этих кубиков + state-guard. [status_service.py:36-264]
- **Производное состояние — единственный источник.** `derive_state(date_start, date_end, cancelled_at, business_date)` и `EmployeeStatus.state_on(business_date)`/`.state` уже дают PLANNED/ACTIVE/COMPLETED/CANCELLED. State-guard'ы 3.6 читают `status.state_on(Clock.today_local())` — НЕ хранят состояние, НЕ дублируют логику. CANCELLED проверяется первым (orthogonal к датам). [employee_status.py:29-42, 115-124]
- **`cancelled_at` уже существует и уже включён в периметр.** Поле есть (3.2); фильтр `cancelled_at__isnull=True` уже в `_assert_no_conflict` (status_service.py:151) и в `excl_hard_status_overlap` + partial-условии (employee_status.py:160). Отмена → строка автоматически выпадает из конфликтов/exclusion. 3.6 НЕ трогает детектор/constraint — только ДОБАВЛЯЕТ by/reason и сервис отмены.
- **Append-once на сервис-уровне, DB-level → E4.** 3.6 гарантирует необратимость через state-guard (CANCELLED → 422 на любую операцию) и `update_fields`-точечные сохранения. БД сейчас НЕ запрещает `UPDATE cancelled_at=NULL` (deferred-work.md#L33) — REVOKE UPDATE/DELETE + триггер append-only это Epic 4 (audit). Явно записать остаточный риск в `deferred-work.md` (не тихо).
