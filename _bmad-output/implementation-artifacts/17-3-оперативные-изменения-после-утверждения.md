# Story 17.3: Оперативные изменения после утверждения — только с санкцией + версия

Status: review

## Story

As a **держатель права `assignment.amend` (штаб на проводимом ОМ)**,
I want **изменить состав Расстановки УЖЕ УТВЕРЖДЁННОГО события (замена/добавление/снятие) только с явной санкцией + причиной, с проверкой конфликтов и записью новой версии**,
so that **любое оперативное изменение после утверждения оставляет полную историю версий (кто, когда, зачем, с чьей санкции) — фундамент, на котором 17.4 (допнаряд) и 17.5 (каскадная замена) строят СВОИ конкретные сценарии замены**.

## Scope Decision

- **FR-28**, полный текст (prd.md:139): «После утверждения оперативные изменения (замены, доп. силы) допускаются только с санкцией, проверкой конфликтов и записью в историю версий; доп. силы (допнаряд) маркируются отдельно с фиксацией, из какого подразделения/наряда сняты люди.» Эта стори реализует ОБЩИЙ механизм (санкция + версия + проверка конфликтов); маркировка допнаряда — Story 17.4, каскадная замена выбывшего — Story 17.5, обе отдельные стори по декомпозиции (epics.md:1445-1446), НЕ эта.
- **НЕТ существующего сервиса, создающего версию ИЗ `APPROVED`** — research-агент проверил все 4 сервиса `events/services.py` (`form_draft_placement`/`submit_assignment_version`/`return_assignment_version`/`approve_assignment_version`): `APPROVED` — терминальный статус для своей цепочки версий, `return_assignment_version()` создаёт новый DRAFT только ИЗ `SUBMITTED`. Эта стори добавляет ЕДИНСТВЕННЫЙ новый переход: `APPROVED` (текущая, `is_current=True`) → новая версия, СРАЗУ `APPROVED` (без под-цикла submit/approve — санкция САМА ЕСТЬ авторизация, буквальный образец `DailySubmission`'s `AMENDED`-паттерна, не изобретение второго workflow).
- **«Санкция» — буквальный образец `DailySubmission.amend_day()`** (`apps/operations/submissions/services/amendment_service.py:56-89`) — `reason`+`sanction`, ОБА обязательны, непустые ПОСЛЕ `.strip()` (`_require_text()`-хелпер, тот же паттерн переносится в `events/services.py`), сохраняются trimmed. Это НЕ то же самое, что `approve_assignment_version()`'s `override`/`override_reason` (16.4) — тот гейтит ТОЛЬКО при обнаруженном конфликте; `sanction`/`reason` этой стори ОБЯЗАТЕЛЬНЫ ВСЕГДА для любого пост-утверждённого изменения, конфликт есть или нет (буква FR-28: «допускаются ТОЛЬКО с санкцией», не «санкция нужна только при конфликте»).
- **Конфликты — считаются и ЗАПИСЫВАЮТСЯ, НЕ блокируют.** `detect_placement_conflicts()` (16.3, `events/services.py:747-806`) — ВСЕ типы конфликтов в этой кодовой базе fixed-SOFT (`SOFT_CONFLICT_DETECTED`, overridable — `approve_assignment_version()`'s прецедент). Решение этой стори: санкция УЖЕ есть безусловная авторизация оперативного изменения — вводить ВТОРОЙ override-гейт поверх санкции избыточно (санкция замещает, не дополняет). Конфликты пишутся на новую версию (видимость для 17.7-экрана), но не отменяют создание версии. Открытый вопрос Bratan, если это неверная интерпретация FR-28.
- **`assignments` — ПОЛНЫЙ новый состав**, не diff/patch. Мирроринг `form_draft_placement()`'s формы (`(employee_id, post)`-пары) — эта стори НЕ добавляет частичное add/remove API, только «здесь новый полный список назначений версии N+1». 17.4/17.5 решают, КАК построить этот список (снятие/замена конкретного человека) — эта стори просто принимает готовый список и версионирует его.
- **Новые поля на `AssignmentVersion`**: `reason`(TextField, blank/default=""), `sanction`(CharField(255), blank/default=""), `is_amendment`(BooleanField, default=False) — заполняются ТОЛЬКО версиями, созданными ЭТИМ сервисом; версии из 16.x (DRAFT→SUBMITTED→APPROVED через обычный цикл) остаются `is_amendment=False`, `reason`/`sanction` пустые. Симметричный CheckConstraint — буквальный образец 17.2's `ck_journal_entry_incident_requires_post` (`is_amendment=True` ⟺ `reason`/`sanction` непустые regex `\S`, буквальный образец `chk_daily_submission_amended_requires_reason_sanction`).
- **НЕ трогает**: 16.5's `EVENT_ASSIGNMENT`-проекцию статусов, 16.6's уведомления (Story 17.6 — «Уведомление снятого/заменённого» — отдельная стори именно для этого), допнаряд-маркировку (17.4), каскадную логику замены (17.5), API/экраны (17.7).
- **RBAC** — новый код `assignment.amend` (НЕ переиспользование `assignment.create` — пост-утверждённое изменение во время живого мероприятия выше по риску, чем черновое формирование расстановки; отдельная гранулярность прав).

## Acceptance Criteria

1. **AC-1.** Given текущая (`is_current=True`) версия в статусе `APPROVED` и `event.status_code == IN_PROGRESS`, when actor вызывает `amend_assignment_version(version, actor=..., reason=..., sanction=..., assignments=[...])`, then создаётся НОВАЯ версия (`version.version + 1`), сразу `APPROVED`, `is_amendment=True`, `is_current=True`; старая версия — `is_current=False`.
2. **AC-2.** Given пустой/whitespace-only `reason` ИЛИ `sanction`, when вызов, then `DomainError`, новая версия не создаётся (ни одно из двух полей не может быть пустым — FR-28 требует ОБА).
3. **AC-3.** Given версия НЕ `is_current` (историческая) ИЛИ статус ≠ `APPROVED`, when вызов, then `DomainError` (`INVALID_LIFECYCLE_TRANSITION`) — амендить можно только ТЕКУЩУЮ утверждённую версию.
4. **AC-4.** Given `event.status_code != IN_PROGRESS`, when вызов, then `DomainError` — оперативное изменение возможно только в режиме проведения (FR-28's контекст — «после утверждения», Epic 17's «Проведение»).
5. **AC-5.** Given `assignments`, содержащие конфликтующее назначение (двойное/отдых/перегрузка), when вызов, then версия ВСЁ РАВНО создаётся (санкция — безусловная авторизация), но `conflict_severity`/`conflict_codes` записаны на затронутых строках (видимость, не блок).
6. **AC-6.** Given успешное создание, then `AuditLog`-ряд (`ASSIGNMENT_VERSION_AMENDED`) с `reason`, `sanction`, `new_version_id`, `old_version_id`.
7. **AC-7.** `chk_assignment_version_amendment_requires_reason_sanction`-констрейнт на DB — обход сервиса прямым `.objects.create(is_amendment=True, reason="", sanction="", ...)` — `IntegrityError`; симметрично — `is_amendment=False` с непустым `reason`/`sanction` — тоже `IntegrityError`.
8. **AC-8.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Допнаряд-маркировка/источник снятия (17.4).
- Каскадная замена выбывшего/эскалация (17.5).
- Уведомление снятого/заменённого сотрудника (17.6).
- Обновление `EVENT_ASSIGNMENT`-статус-проекции (16.5) для добавленных/снятых участников амендмента — 17.4/17.5 решают точечно, кого конкретно проецировать.
- Частичный add/remove API (только полный список назначений на версию).
- Экраны/API-эндпоинты (17.7).
