# Story 10.6b: Метка протухшей сводки — UI

Status: ready-for-dev

## Story

As a **руководитель**,
I want **видеть на панели сдачи явную метку «сводка устарела», если пины сводки моего подразделения разошлись с текущими версиями детей**,
so that **я не принимаю решение по данным, которые молча протухли — тот же принцип, что серверный drift-маркер 10.3b, но для другой оси (5-11:97)**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/sprint-status.yaml:401-421` («10.6b — UI: метка протухшей сводки поверх 10.6a. ⚠️ свежесть пинов — ОТДЕЛЬНАЯ ось от цвета светофора (5-11:97), выводить одно из другого нельзя»). Также `10-6-amendment-флоу-ui.md` (Story 10.6, done) явно оставила эту метку НЕ реализованной: «метка протухшей сводки (третья треть epic-AC): `summary_freshness` существует сервисом БЕЗ HTTP-поверхности... Тянуть неоткуда → 10.6a (роут) + 10.6b (UI)» (`DaySubmissionPanel.tsx:19-27`, комментарий уже на месте в коде).

1. **AC-1 (метка видна ТОЛЬКО на STALE).** Given `GET /daily-submissions/freshness/` вернул `status: "STALE"`, Then на `DaySubmissionPanel` виден блок с текстом «Сводка устарела» (или эквивалент, словом — не только цветом, DESIGN.md:349,371). Given `status` — `"FRESH"` ИЛИ `"NOT_SUMMARY"`, Then блока нет ВООБЩЕ (зеркало `serverDrift`-паттерна 10.3b: обогащение, не первичный сигнал — рендерится только когда есть что показать).
2. **AC-2 (запрос — enrichment, тот же гейт, что серверный drift).** `useQuery({queryKey: ['summary-freshness', divisionId, businessDate], ..., enabled: divisionId !== null && dateValid && current !== null})` — ТОТ ЖЕ гейт, что `serverDriftQuery` (`DaySubmissionPanel.tsx:229`): на несданный день сводки нет смысла спрашивать. Загрузка/ошибка/сетевой обрыв → блока нет (тот же посыл, что у `serverDrift`: нет явного error-UI, просто нечего показать).
3. **AC-3 (три оси текстом, не JSON-дампом).** Given `superseded`/`missing`/`unpinned` непусты, Then блок называет КОЛИЧЕСТВО расхождений человеческим текстом (например, «N подразделений пересдали после сборки сводки» для `superseded`) — НЕ читать `division_id` как имя (у ответа `freshness` имён нет, в отличие от `serverDrift`, который резолвит `resolveName` из состава дня; тянуть имена подразделений сюда — вне скоупа, это read-only индикатор наличия расхождения, не детальный дифф).
4. **AC-4 (инвалидация на amend — урок 10.3b, не повторять баг).** `submitMutation.onSuccess` И `amendMutation.onSuccess` оба зовут `queryClient.invalidateQueries({queryKey: ['summary-freshness', divisionId, businessDate]})` — ОБЯЗАТЕЛЬНО на обоих, не только на одном (10.3b Blind Hunter поймал ИМЕННО этот класс бага: серверный drift не инвалидировался на amend, хотя amend меняет то самое состояние, от которого drift зависит; здесь тот же риск — амендмент ЭТОЙ сдачи не меняет её собственную свежесть напрямую, но инвалидация всё равно ставится защитно, зеркалом уже существующего паттерна на этой же панели).
5. **AC-5 (свежесть — ОТДЕЛЬНАЯ ось, не производная от светофора).** Компонент/модель этой стори НЕ читает `TrafficLightStatus`/`DivisionTrafficLight` ни в каком виде для расчёта метки — источник ИСКЛЮЧИТЕЛЬНО ответ `/freshness/`. Доменный инвариант `5-11:97` («свежесть пинов — ОТДЕЛЬНАЯ ось от цвета светофора») — нарушение здесь означало бы вывод одного из другого, что явно запрещено постановкой.
6. **AC-6 (чистая модель, типы из схемы).** Новый файл `frontend/src/features/daily-grid/freshness.ts` — чистые функции (без React/`apiClient`, тестируются в env `node`, зеркало `amendment.ts`/`daySubmission.ts`). Типы — ИЗ `schema.d.ts` (`components['schemas']['SummaryFreshnessResponse']`, добавлен 10.6a) — НЕ рукописное зеркало (в отличие от `amendment.ts`, где зеркало было вынужденным по историческим причинам этой стори; здесь схема свежая и полная, ARCH-FE-011 требует переиспользовать её без исключений).
7. **AC-7 (регресс нулевой, границы фич соблюдены).** `ExpenseJournalPanel`/`ExpensePeriodPanel`/`traffic-light`-фича — не тронуты (ARCH-FE-013: `features/A → features/B` запрещено, метка живёт строго в `daily-grid`, зеркало решения №1 10.3 «панель лежит ВНУТРИ features/daily-grid»). `npm run gate` зелёный (928+N тестов).

## Dev Notes

- **Дом стори — `DaySubmissionPanel.tsx`, не `traffic-light`-фича.** Сама Story 10.6 (done) уже назвала точку врезки в коде: `DaySubmissionPanel.tsx:19-27` явно перечисляет метку протухшей сводки как «осознанно НЕ реализовано» и форвард-ссылается на 10.6a+10.6b. Alternative-гипотеза (метка на дереве светофора 10.4) отклонена: 400 узлов дерева ⇒ N+1 point-lookup запросов на каждый видимый узел сломал бы перф-бюджет AC-4 стори 10.4 (`TrafficLightNode.tsx` монтирует только развёрнутые узлы, но даже это — десятки одновременных фетчей без batch-роута, которого не существует). `DaySubmissionPanel` уже держит `divisionId`+`businessDate` в контексте одной сдачи — точечный запрос естественен.
- **Прямой прецедент — `serverDriftQuery` (10.3b), скопировать структуру буквально.** `DaySubmissionPanel.tsx:221-229` (гейт `enabled`) и `:656-708` (рендер только когда есть что показать, амбер-карточка, `role="alert"`, честная пограничная фраза). Freshness — тот же паттерн: «обогащение, не первичный сигнал», рендерится только на непустом/релевантном состоянии, никакого явного error-UI (ошибка чтения = «нечего показать», не блокирующий сбой).
- **Свежесть — ОТДЕЛЬНАЯ ось, доменный инвариант, не деталь реализации.** `sprint-status.yaml:420` и `DaySubmissionPanel.tsx:24-27` (комментарий уже в коде от Story 10.6): «Выводить свежесть из светофора НЕЛЬЗЯ: это отдельная ось — сводка, которая есть, не RED, а пины при этом могут быть протухшими». AC-5 — прямая тестируемая гарантия этого инварианта: два независимых MSW-сценария (YELLOW-drift без STALE-freshness и наоборот) должны рендерить РАЗНЫЕ, не связанные блоки.
- **Большинство сдач — `NOT_SUMMARY`, это норма, не край.** Только подразделения-родители со сводкой (сервис 5.11, `sources`-ключ в snapshot) когда-либо получат `FRESH`/`STALE`; обычная сдача листового подразделения — всегда `NOT_SUMMARY`. Тесты обязаны покрыть `NOT_SUMMARY` как ОСНОВНОЙ путь (большинство панелей в проде), а не только STALE как «интересный» случай.
- **`ExpenseJournalPanel`/`ExpensePeriodPanel` key-коллизия (10.5e) — урок, НЕ повторяется здесь.** Эта стори не добавляет новый sibling-компонент с собственным `key`-пропом на общем родителе — freshness-блок рендерится ВНУТРИ уже существующего `DaySubmissionPanel`, а не как отдельный монтируемый сосед. Урок 10.5e неприменим напрямую, но упомянут для полноты — если в будущем метка вынесется в отдельный компонент-соседа, применить префиксованный `key`.
- **Именование запроса.** `['summary-freshness', divisionId, businessDate]` — НЕ `['freshness', ...]` (слишком общее имя рискует коллизией queryKey с будущими фичами; `summary-freshness` однозначно указывает на 5.11-домен, зеркало специфичности `['division-traffic-light', ...]`/`['division-submissions', ...]`).
