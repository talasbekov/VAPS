# Story 14.11d: API — отмена смены дежурства

Status: review

## Story

As an **оператор с правом `duty.manage`**,
I want **`POST /api/operations/duty-plans/{plan_id}/shifts/{shift_id}/cancel`**,
so that **смену дежурства можно отменить через API с указанием причины**.

`epics.md:1411` (буква, до разделения): «Story 14.11: API и экраны плана дежурств». Четвёртая из ~12 подсторий разделения.

## Scope Decision (найдено при create-story)

- **Донор молчит про cancel-эндпоинт (подтверждено дважды — 14.9a's и этой стори's research).** VAPS-оригинальная территория — тонкая HTTP-обёртка над уже существующей `cancel_duty_shift(shift, *, actor, reason)` (14.9a).
- **URL — вложенный `@action` на существующем `DutyPlanViewSet`, с ДВУМЯ ID через кастомный `url_path`-regex, НЕ новый `DutyShiftViewSet`.** Обычный `@action(detail=True)` даёт ТОЛЬКО ОДИН path-параметр (`pk`) от роутера. Прецедента «двойной вложенности через кастомный `url_path`» в кодовой базе нет — ни `django-rest-framework-nested`, ни `DutyShift`-специфичного роута ещё не существует, и заводить новый `DutyShiftViewSet` ради ОДНОГО action'а было бы избыточно (`DutyShift` не является самостоятельным ресурсом с собственным списком/созданием вне плана — 14.9a's дизайн явно держит его подчинённым плану). Решение: `@action(detail=True, methods=["post"], url_path=r"shifts/(?P<shift_id>[^/.]+)/cancel")` на `DutyPlanViewSet` — `pk` (роутер) = ID плана, `shift_id` — доп. kwarg из regex. `get_object_or_404(plan.shifts, pk=shift_id)` — заодно гарантирует, что смена реально принадлежит указанному плану (404 при cross-plan подмене id).
- **Коды ошибок — уже зарегистрированы, ничего нового в `error-codes.yaml`.** `cancel_duty_shift()` бросает `VALIDATION_ERROR`(400, пустые `actor`/`reason`) и `INVALID_LIFECYCLE_TRANSITION`(422, уже отменена/уже началась) — оба уже в реестре (общие коды, не duty-специфичные). `DomainError` пропагирует через существующий unified exception handler без явного перехвата во вьюхе.
- **`actor` — из `request.actor_id` (auth-контракт), НЕ из тела запроса.** ARCH-SEC-030's установленный паттерн (14+ прецедентов в кодовой базе) — actor никогда не берётся из payload.
- **Тело запроса — только `reason` (обязательное, непустое).** `DutyShiftCancelSerializer(serializers.Serializer)`: `reason = serializers.CharField()`.
- **Ответ — существующий `DutyShiftSerializer`, `200`.** Уже экспонирует `cancelled_at`/`cancelled_by`/`cancelled_reason` (read-only, 14.11b) — новый сериализатор ответа не нужен.
- **Роут — `ops-duty-plan-cancel-shift`** (действие названо `cancel_shift`, не голое `cancel` — сегмент `shifts/.../cancel` уже занят структурно `shifts`-action'ом). Требует строку в `MATRIX`/`AUDIT_MATRIX`.
- **RBAC-строка/HTTP audit-логирование — 14.12.**

## Acceptance Criteria

1. **AC-1 (happy path).** Требует `duty.manage`. Тело: `{"reason": "..."}`. Успех — `200`, `DutyShiftSerializer` с `cancelled_at`/`cancelled_by`/`cancelled_reason` заполненными.
2. **AC-2 (несуществующий план/смена → 404).** Оба случая — несуществующий `plan_id`, несуществующий `shift_id`.
3. **AC-3 (смена из ДРУГОГО плана в URL → 404).** `get_object_or_404(plan.shifts, pk=shift_id)` — cross-plan подмена id не находит смену.
4. **AC-4 (пустой `reason` → 400).**
5. **AC-5 (уже отменённая смена → 422).**
6. **AC-6 (уже начавшаяся/прошедшая смена → 422).**
7. **AC-7 (без `duty.manage` → 403).**
8. **AC-8 (регресс нулевой, `make gate` зелёный).**
