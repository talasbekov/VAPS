# Story 11.4a: Бэк — отметка прочтения

Status: ready-for-dev

## Story

As a **оператор с непрочитанными уведомлениями**,
I want **эндпоинт, которым бэкенд реально записывает `read_at` на моё собственное уведомление**,
so that **11.4b сможет навесить на него мутацию UI, и счётчик непрочитанных в колокольчике (11.4) наконец начнёт гаснуть, а не расти монотонно до конца сессии**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/11-4-центр-уведомлений-ui.md:251` (передача из 11.4, Решение №1): «11.4a — бэк: отметка прочтения. Эндпоинт (форму выбирает та стори: `POST /api/notifications/{id}/read/` либо bulk `POST /api/notifications/mark-read/`), самоскоуп по `recipient=actor` (чужая строка не отмечается), запись в `test_rbac_matrix.py` (матрица fail-closed — незамапленный роут валит сьют), `@extend_schema` (иначе spectacular не эмитит тело), regen `schema.yaml` + `schema.d.ts`, плюс unread-индекс под `read_at IS NULL` — прямая незакрытая половина `deferred-work.md:495`».

**Решение по форме эндпоинта (принято при create-story):** ЕДИНИЧНЫЙ, не bulk — `POST /api/notifications/{id}/read/`. Обоснование: `11-4-центр-уведомлений-ui.md:145` уже фиксирует форму будущего потребителя — «11.4b добавит в строку кнопку «прочитано»» (per-row, не «отметить всё разом»). Bulk-эндпоинт под несуществующего потребителя был бы сочинительством сверх скоупа (урок 5.7c: «не расширяй поверхность»).

1. **AC-1 (эндпоинт существует и пишет `read_at`).** `POST /api/notifications/{id}/read/` — новый `@action(detail=True, methods=["post"])` на существующем `NotificationViewSet` (`Backend/VAPS/apps/notifications/api/views.py`), либо отдельная запись в `apps/notifications/api/urls.py` тем же паттерном `path()` (НЕ router — коллизия `api-root` уже задокументирована в файле). Given уведомление с `read_at IS NULL`, принадлежащее актору, When `POST .../read/`, Then `read_at` в БД становится не-`NULL` (текущее время через `Clock`, НЕ голый `timezone.now()` — канон проекта), ответ `200`.
2. **AC-2 (самоскоуп — чужое уведомление не отмечается).** Given уведомление `recipient != request.actor_id`, When `POST .../{id}/read/`, Then `403 PERMISSION_DENIED` (уже зарегистрированный код, реестр не трогается), `read_at` целевой строки НЕ меняется (ассертить из БД). Given `id`, которого не существует вовсе, When `POST`, Then `404 ENTITY_NOT_FOUND` (уже зарегистрированный код). Порядок проверок — сначала существование (404 для фантомного `id` любому актору), потом владение (403) — зеркало `DailySubmissionViewSet.amend` (`submissions/api/views.py:277-311`: resolve pk → 404 если нет → scope-check → мутация).
3. **AC-3 (идемпотентность — повторный вызов не взрывается).** Given уже прочитанное уведомление (`read_at` не `NULL`), When повторный `POST .../{id}/read/` тем же актором, Then `200` без ошибки, `read_at` НЕ перезаписывается новым временем (первый факт прочтения — источник истины, не последний клик; иначе "когда реально прочитано" разъезжается при двойном клике/повторном фокусе вкладки).
4. **AC-4 (RBAC-матрица — fail-closed).** Новая запись в `MATRIX` (`Backend/VAPS/apps/operations/tests/test_rbac_matrix.py`) для нового имени роута — `_AnyAuthenticated()` (зеркало существующей `"notification-list": _AnyAuthenticated()`, строки 219-223: доступ — не RBAC-право, а самоскоуп в бизнес-логике). `seed_operations.py` НЕ трогается (нет нового RBAC-кода). Пропуск этой записи валит ВЕСЬ модуль `test_rbac_matrix.py` (`test_matrix_covers_every_registered_route`) — не факультатив.
5. **AC-5 (схема эмитит тело, а не пустышку).** `@extend_schema` на новом action/view с `responses` (мини-сериализатор ответа: например `{id, read_at}` — НЕ полный `NotificationSerializer`, которому не место в write-пути с `read_only_fields = fields`). `make schema` (из `Backend/VAPS/`) → `schema.yaml` содержит путь `/api/notifications/{id}/read/` с непустым `post`. `cd frontend && npm run generate:api` → `schema.d.ts` регенерируется, `schema-check.mjs` (байт-в-байт) зелёный.
6. **AC-6 (unread-индекс — закрывает `deferred-work.md:495`).** Новая миграция `0003_notification_ix_notif_recipient_unread.py` — частичный индекс под `read_at IS NULL` на `(recipient, ...)`, зеркало именования существующего `ix_notif_recipient_recency` (миграция 0002). EXPLAIN на запрос вида `WHERE recipient = ? AND read_at IS NULL` использует новый индекс, не seq scan (доказать тестом или явным EXPLAIN-выводом в Dev Notes, не декларативно).
7. **AC-7 (регресс нулевой).** `make gate` (из `Backend/VAPS/`) зелёный: существующие `test_notifications_read_api.py` (5.7c) не сломаны, `test_rbac_matrix.py` зелёный целиком (не только новая запись), `test_ws_notify`/консьюмеры (E11) не задеты — это чисто REST-мутация, WS-слой не трогается. `frontend`'s `npm run gate` тоже зелёный (только `schema.d.ts` меняется аддитивно — новый путь, существующие типы `notifications_list` не трогаются).

## Dev Notes

- **Форма эндпоинта — единичная, не bulk (решено при create-story).** `11-4-центр-уведомлений-ui.md:145` уже фиксирует будущий UI-потребитель: «11.4b добавит в строку кнопку «прочитано»» — per-row действие. Bulk-`mark-all` эндпоинт сегодня не имеет потребителя ни в 11.4, ни в 11.4b — было бы расширением поверхности сверх текущего скоупа (урок 5.7c: «`read_at`/mark-read/unread-фильтр — вне скоупа... не расширяй поверхность»). Если продукту позже понадобится «отметить всё» — отдельная стори с явным потребителем.
- **Доступ — самоскоуп, НЕ новый RBAC-код.** Существующий `NotificationViewSet` уже задокументировал этот принцип для GET (`views.py`, докстринг: «Personal feed: any authenticated actor reads ONLY their own notifications»). Мутация наследует ту же философию на уровне объекта: `recipient == actor_id` — единственный контроль доступа, не право из `seed_operations.ROLE_PERMISSIONS`. Зеркало Решения Q1 из 5.7c.
- **Идемпотентность — первый факт прочтения побеждает, не последний.** AC-3 намеренно НЕ перезаписывает `read_at` при повторном вызове. Если бы перезаписывал — двойной клик или повторный фокус вкладки после 11.4b's мутации молча искажал бы момент "когда реально прочитано" (потенциально важно для будущей аналитики/аудита, хотя сегодня это не читается нигде явно — принцип "не удивлять" важнее отсутствия текущего потребителя).
- **Порядок 404-перед-403 — зеркало `amend`, не изобретение.** `submissions/api/views.py:277-311` (`DailySubmissionViewSet.amend`) уже установил паттерн «resolve pk → 404 если нет → scope-check → мутация» для похожей формы (единичный ресурс + владение). 11.4a копирует форму, не скоуп-механизм (там `ensure_division_scope`/RBAC-право, здесь голое равенство `recipient == actor_id` — принципиально разные проверки, тот же порядок операций).
- **`@action` на non-router `path()`-ViewSet — единственная реальная техническая неопределённость этой стори.** `apps/notifications/api/urls.py` НЕ использует `DefaultRouter` (осознанно, docstring: коллизия `api-root` с `list` на `^$`). Стандартный `@action(detail=True, methods=["post"])` на ViewSet предполагает роутер, который сам генерирует url для action по `url_path`/`url_name`. При ручном `path()`-роутинге нужно либо (а) явно замапить `path("<int:pk>/read/", NotificationViewSet.as_view({"post": "mark_read"}), name="notification-mark-read")` БЕЗ `@action`-декоратора (обычный метод ViewSet), либо (б) подтвердить, что `@action` + `.as_view({"post": "read"})` действительно резолвится DRF без роутера. **Первым шагом Task 2 — red-проба этого механизма** (написать минимальный вызов, увидеть, резолвится ли URL), прежде чем достраивать остальное — иначе риск часов на отладку несуществующей комбинации.
- **RBAC-матрица требует `callback.cls`/`callback.actions` присутствия для интроспекции** (`test_rbac_matrix.py` `_served_routes`, walks live URL resolver). И `ViewSet.as_view({...})`, и `@action`-based резолвинг ДОЛЖНЫ давать `callback.cls == NotificationViewSet` — подтвердить это для выбранного варианта Task 2 явным прогоном, не полагаться на аналогию с существующим `notification-list`.
- **Не трогать `apps/notifications/consumers.py`/`routing.py`/`groups.py` (WS-слой, Epic 11).** Эта стори — чисто REST-мутация на существующей модели; WS-доставка уведомлений (11.1-11.3) не подписана на `read_at` и не должна быть задета.
- **`Clock`, не `timezone.now()` напрямую** — проектный канон времени (см. `1-3-clock-сервис-и-watermark.md`), сверить точный импорт-путь по соседним файлам этого приложения перед написанием `mark_read`.
