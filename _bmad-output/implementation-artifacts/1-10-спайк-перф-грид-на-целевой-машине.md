## Story

As a разработчик,
I want собрать одноразовый прототип клавиатурного грида (Vite + React + TanStack Virtual, ~1000 строк статики, навигация Enter↓/Tab→/Esc слепым вводом), собранный под `build.target: 'firefox100'`, и провести на нём ОДИН замер на целевой слабой машине (4 ГБ RAM, без GPU, Firefox ~100) — слепой ввод 100 символов с фиксацией TTI, памяти вкладки и p95-латентности клавиши,
so that допущение A9 («4ГБ/FF100 потянут грид») проверено ДАННЫМИ, а перф-бюджет Epic 9 (9.4 грид, 9.8 перф-смоук) ИЗМЕРЕН, а не предположен — до того, как E8/E9 начнут строить настоящий грид на этих числах.

## Acceptance Criteria

1. **Given** одноразовый прототип на статике (Vite + React + TanStack Virtual, ~1000 строк, минимальная клавиатурная навигация Enter↓/Tab→/Esc + слепой ввод значения в ячейку), собранный командой `vite build` с **`build.target: 'firefox100'`** и `browserslist Firefox >= 100`, **When** статическая сборка (`dist/`) открывается в Firefox ~100, **Then** страница интерактивна без ошибок в консоли, грид прокручивается и принимает слепой ввод, а виртуализация подтверждена: в DOM присутствует НЕ ~1000 строк, а только видимое окно (зафиксировано числом DOM-узлов грида).

2. **Given** прототип запущен на целевой машине (4 ГБ RAM, без GPU, Firefox ~100 — реальный клиентский ПК контура ЛИБО эталонная замена, см. Task 0), **When** оператор вводит **100 символов слепым вводом** (без мыши, по грамматике Enter↓/Tab→/Esc), **Then** зафиксированы три числа AC и два инварианта:
   - **TTI** (Time To Interactive) — момент готовности страницы к вводу;
   - **память вкладки** — пиковое потребление вкладки на 4 ГБ (читается ИЗ Firefox `about:processes`/`about:memory`, НЕ через `performance.memory` — его в FF нет);
   - **p95-латентность клавиши** (keydown → React commit) по выборке ≥100 нажатий — измеряется ВНУТРИСТРАНИЧНОЙ инструментацией (Playwright на FF100 невозможен, architecture.md:258);
   - **инвариант детерминизма:** React Profiler `onRender` → ровно **1 коммит на keystroke** (architecture.md:244);
   - **инвариант виртуализации:** число DOM-узлов грида ≤ N при ~1000 строк (не растёт со строками).

3. **And** результат — ДУРАБЕЛЬНЫЙ артефакт `BUDGET.md` (коммитится), фиксирующий измеренные числа **как явный перф-бюджет Epic 9**: таблица «метрика → значение → откуда питается стори» (9.4 грид-компонент, 9.8 перф-смоук — 9.8 в epics.md:1071 прямо требует «сверены с бюджетом спайка 1.10»), плюс методология (как измерялась каждая метрика, на каком железе и какой именно сборке FF), плюс вердикт по A9 («тянет / тянет с оговоркой / не тянет → план Б»). ### Главное отличие от стори 1.1–1.8 и сходство с 1.9

- 1.1–1.8 — кодовые стори (Django: модели/сервисы/команды/тесты/гейт). **1.10 — измерительный фронтенд-спайк, как 1.9 был инфраструктурным.** Это ПЕРВЫЙ фронтенд-код в репозитории (сейчас фронтенда нет вовсе — проверено: ни `package.json`, ни `.tsx`, ни Vite).
- Сходство с 1.9: есть **человеко-исполняемая часть** — слепой ввод 100 символов на реальной целевой машине делает Bratan руками (как внос носителя в контур в 1.9). Роль dev-агента: собрать прототип + встроить инструментацию + подготовить шаблон бюджета так, чтобы замер свёлся к механическому проходу. «Тесты» здесь — не pytest и не RTL, а воспроизводимость замера и полнота `BUDGET.md`.
- Тот же паттерн путь A / путь B, что в 1.9 (Task 0): целевое железо есть → меряем; нет → меряем предварительно на dev, авторитетный прогон делегируем. A9 здесь — более достижимый гейт, чем A5 в 1.9: эталонная замена (4 ГБ-VM + FF100 ESR) создаётся без допуска в контур.

### Гейт A9 — целевое железо (Task 0)

- **A9 = «4ГБ/FF100 потянут грид»** — вероятность *средняя*, влияние *высокое*; митигация — САМ этот спайк (epics.md:268). Перф-бюджет 1.10 — это ещё и заявленная замена отсутствующей UX-спеки по перфу (readiness-report:252): «для соло-разработчика связка бумажные контракты + канон ARCH-FE + перф-бюджеты со спайка 1.10 — рабочая замена UX-спеки». Поэтому числа load-bearing для всего фронтенд-трека.
- Идеал замера — реальный клиентский ПК контура (тот же класс, что в 1.9). Приемлемо — эталонная замена: любая машина/VM, ограниченная 4 ГБ, + **архивный Firefox 100 ESR**. Fallback (путь B) — dev + CPU-throttle, числа `PRELIMINARY`.
- Почему важно мерить на ИМЕННО таком железе: дефолтная сборка Vite 7 таргетит FF≥104 — прототип без `build.target:'firefox100'` может вообще не открыться на FF~100 (белый экран), и сам факт этого — уже находка спайка.

### Что именно измеряем и КАК (методология для BUDGET.md)

| Метрика | Как снять | Важная оговорка |
|---|---|---|
| **TTI** | Navigation Timing API (`performance.getEntriesByType('navigation')`) или ручной маркер «готова к вводу» | На прод-сборке (`vite build`), не в dev-режиме — dev-перф ≠ прод-перф |
| **Память вкладки** | **Firefox `about:processes` / `about:memory`** ПОСЛЕ ввода 100 символов | `performance.memory` — Chrome-only, в Firefox ОТСУТСТВУЕТ. Не закладываться на него — читать вручную из FF |
| **p95 keydown→commit** | Внутристраничная инструментация: `performance.now()` на keydown → дельта на коммите (`<Profiler onRender>`), выборка ≥100, p95 | Playwright на FF100 НЕВОЗМОЖЕН (патченые сборки, architecture.md:258) → только in-page + ручное списывание с HUD. Тайминги — тренд, не блок-гейт (architecture.md:244) |
| **Коммитов/keystroke** | `<Profiler onRender>` счётчик | Инвариант: ровно 1 (architecture.md:244). >1 → красный флаг в бюджет |
| **DOM-узлы грида** | `querySelectorAll(...).length` на HUD | Инвариант: ≈ окно виртуализации, не ~1000 |
| **Размер бандла** | gzip initial из `vite build` (информационно) | Бюджет канона ≤300 КБ gzip (architecture.md:231) — у прототипа меньше нагрузки, фиксируем как точку данных, не как гейт |

HUD-оверлей (числа прямо на экране) — ключевой приём: исполнитель замера на целевой машине списывает значения глазами, без DevTools-автоматизации, которой на FF100 нет.

### Решения, принятые при создании стори (дефолты; менять только осознанно)

1. **Прототип = голый Vite+React+TanStack Virtual, одна страница-грид.** Достаточно, чтобы упражнять ровно то, ради чего A9: виртуализация ~1000 строк, 1-коммит/keystroke, латентность слепого ввода на слабом CPU без GPU. Канон-стек (Mantine/RHF/Query/…) добавляет вес и время без нового знания о ЖИЗНЕСПОСОБНОСТИ и явно относится к E8.
2. **Инструментация — внутристраничная (HUD + console/JSON-экспорт).** Потому что Playwright на FF100 невозможен. Числа списываются глазами на целевой машине.

### Подводные камни для dev-агента

- **`build.target: 'firefox100'` — НЕ опционально.** Без него Vite 7 таргетит FF≥104; прототип на FF~100 рискует белым экраном из-за неподдержанного синтаксиса. Это центральная техническая деталь спайка (его смысл — жизнеспособность на FF~100).
- **dev-режим ≠ прод-перф.** Мерить ТОЛЬКО прод-сборку (`vite build` → `dist/`), не `vite dev` (HMR/несжатый/без firefox100-транспиляции искажает все три числа).
- **`performance.memory` нет в Firefox.** Память — только вручную из `about:processes`/`about:memory`. Не писать код, который её «измеряет» в FF — он вернёт `undefined`.
- **Playwright не водит FF100.** Не пытаться автоматизировать замер на целевой среде Playwright'ом (architecture.md:258). In-page инструментация + ручной ввод — единственный путь.
- **Спайк ≠ E8/E9.** Соблазн «раз уж пишу грид — подключу Mantine/Query/кодоген сразу». НЕТ: это E8 (первая-вторая фронт-стори) и E9 (полная грамматика + property-тесты). Раздувание = риск преждевременного канона на непроверенном железе.
- **localhost-dev ≠ целевое железо.** `vite preview` на мощном ноутбуке покажет радужные числа. Авторитетен только прогон на 4 ГБ/FF~100 (путь A) — иначе путь B + честный `PRELIMINARY`.
- **Слепой ввод = без мыши.** 100 символов вводятся клавиатурой по Enter↓/Tab→/Esc — это упражняет именно тот путь (keydown→commit), который меряем. Не «накликать» значения мышью.
- **Числа пишутся ПО ХОДУ замера, а не по памяти.** Ценность 1.10 для 9.8 («сверены с бюджетом 1.10») = достоверность чисел и метода. Аномалии (фриз, потеря нажатия, >1 коммита) — отдельными строками.
- **Таймбокс E1 (A10):** E1 таймбоксирован 3 неделями, дедлайн **2026-07-02** (sprint planning 2026-06-11). Спайк — дешёвый дисконт риска на часы-день, а не мини-проект.
- **A9 может физически блокировать Task 3 сегодня** (нет целевой машины под рукой). Это нормально → путь B + `PRELIMINARY`, а не имитация.
