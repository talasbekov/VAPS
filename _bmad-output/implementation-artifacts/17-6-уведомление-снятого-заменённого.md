# Story 17.6: Уведомление снятого/заменённого сотрудника

Status: review

## Story

As a **снятый/заменённый сотрудник (или держатель права `assignment.amend`, отслеживающий последствия своей замены)**,
I want **получить уведомление, что моё назначение на пост было отменено оперативным изменением (17.3/17.5), и чтобы старший события тоже узнал об этом**,
so that **никто не остаётся неосведомлённым о своём снятии — тот же принцип прозрачности, что 16.6a's уведомление об утверждении**.

## Scope Decision

- **`REPLACEMENT_CREATED`** — УЖЕ зарезервирован в `docs/registries/ws-message-types.yaml:179-185` (`recipients: "senior/affected users"`, `trigger: "замена после утверждения"`) — тот же паттерн, что 16.6d нашла для `ASSIGNMENT_SUBMITTED`/`ASSIGNMENT_RETURNED`: реестр УЖЕ решил вопрос «кто получатели», реализация просто соединяет провода. Новый `Notification.Kind`-член не изобретается — его буквальное имя уже задано реестром.
- **Один хук ВНУТРИ `amend_assignment_version()` (17.3) покрывает ОБОИХ вызывающих** — `cascade_replace_departed()` (17.5) целиком делегирует мутацию туда (собственный докстринг подтверждает), поэтому хук ставится ОДИН РАЗ, не дублируется в 17.5. Прямые вызовы `amend_assignment_version()` (без 17.5's каскада — например, ручное оперативное изменение) тоже покрываются автоматически.
- **«Снятый» и «заменённый» — ОДНО и то же множество получателей**: `employee_id`, присутствовавший в СТАРОЙ версии (`version.assignments`), но ОТСУТСТВУЮЩИЙ в НОВОЙ (`new_version.assignments`) — не важно, заменён ли он кем-то или пост просто опустел (17.3 разрешает оба исхода, полный новый список решает). Разделять «снят» vs «заменён» на разные уведомления НЕ требуется — реестр несёт ОДИН kind на оба случая.
- **Получатели** — буквальный образец `_notify_assignment_approved()`'s (16.6a) bridging-идиомы: `employee_id`-множество → `CoreEmployeeSelector.user_ids_for()` → `set(...values())`-дедуп → `notify()` в цикле. Плюс `event.senior_employee_id`, если задан (реестр: «senior/affected users» — ОБА получателя, буквально как 16.6a уже делает для `ASSIGNMENT_APPROVED`).
- **Хук ставится ПОСЛЕ commit'а вложенного savepoint'а**, но ДО/ПОСЛЕ `record()`-аудита неважно (сам `notify()` откладывает WS-доставку до `transaction.on_commit()`, свой собственный откат уже встроен) — размещение сразу после `signature_hash`-сохранения, симметрично `_notify_assignment_approved()`'s места в `approve_assignment_version()`.
- **НЕ трогает** `cascade_replace_departed()` (17.5) — ни строчки кода там не меняется, уведомление приходит «бесплатно» через делегирование.
- **НЕ добавляет** отдельного уведомления НОВОМУ занявшему пост сотруднику — это уже покрыто `ASSIGNMENT_APPROVED` (16.6a) семантически (новый занявший узнаёт о СВОЁМ назначении через существующий канал; эта стори — только про СНЯТОГО).

## Acceptance Criteria

1. **AC-1.** Given `amend_assignment_version()` реально меняет состав (сотрудник X был в старой версии, отсутствует в новой), when вызов завершается успешно, then `X`'s `user_id` получает `Notification` (`kind=REPLACEMENT_CREATED`, `business_date=Clock.today_local()`).
2. **AC-2.** Given у события задан `senior_employee_id`, when вызов завершается успешно И есть хотя бы один снятый, then старший ТОЖЕ получает `REPLACEMENT_CREATED`-уведомление.
3. **AC-3.** Given старший события ОДНОВРЕМЕННО является снятым сотрудником, when вызов, then РОВНО ОДНО уведомление (дедуп, буквальный образец `_notify_assignment_approved()`'s `set()`-идиомы, 16.6a).
4. **AC-4.** Given `assignments`, где ВСЕ старые сотрудники присутствуют в новой версии (никто не снят — например, чистое добавление допнаряда без замены существующих), when вызов, then уведомлений НЕТ (пустое множество снятых — не ошибка, просто нет получателей).
5. **AC-5.** Given несколько сотрудников снято за один вызов (несколько постов выбывшего, 17.5), when вызов, then КАЖДЫЙ получает СВОЁ уведомление (не одно уведомление на всех сразу).
6. **AC-6.** Given `cascade_replace_departed()` (17.5) вызывает `amend_assignment_version()` внутри себя, when каскадная замена успешна, then выбывший ПОЛУЧАЕТ уведомление БЕЗ каких-либо изменений в коде 17.5 (хук сработал через делегирование).
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope
