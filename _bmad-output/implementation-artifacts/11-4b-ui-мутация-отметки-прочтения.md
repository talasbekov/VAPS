# Story 11.4b: UI — мутация отметки прочтения

Status: done

## Story

As a **оператор с непрочитанными уведомлениями в колокольчике**,
I want **кнопку «прочитано» на каждой непрочитанной строке, которая реально гасит счётчик**,
so that **колокольчик (11.4) перестаёт монотонно расти в течение сессии — единственное честно заявленное ограничение 11.4 наконец снимается**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/11-4-центр-уведомлений-ui.md:252-253` (передача из 11.4, Решение №1): «11.4b — UI-мутация отметки прочтения. `useApiMutation` + обычный инвалидейт `['notifications']`, optimistic ЗАПРЕЩЁН (architecture.md#L472 + буква epic-AC #L1258). Пререквизит — 11.4a». Бэкенд-пререквизит (11.4a, `POST /api/notifications/{id}/read/`) уже done (коммит `273579e`).

1. **AC-1 (кнопка «прочитано» — только на непрочитанных строках).** Given строка с `read_at === null` (уже отрисован текстовый бейдж непрочитанного — `NotificationBell.tsx`'s `NotificationRow`), Then рядом с бейджем есть кнопка «Прочитано» (`aria-label`, не голая иконка — EXPERIENCE.md#L238: не только цвет/иконка). Given строка с `read_at !== null`, Then кнопки нет вовсе (не disabled — идемпотентность уже на бэке, но повторный клик по уже-прочитанному не имеет смысла показывать пользователю).
2. **AC-2 (мутация — `useApiMutation`, без optimistic).** Клик по кнопке вызывает `useApiMutation<NotificationMarkReadResponse, {id: number}>` с `mutationFn: (v) => apiClient.post(...)`, путь `/api/notifications/${v.id}/read/` (типы из `schema.d.ts`'s `notifications_read_create`, ARCH-FE-011 — сгенерированные, не рукописные). Строка НЕ меняется до ответа сервера (не серым/не вычеркнутой сразу по клику) — только `onSuccess` инвалидирует кэш; `queryClient.setQueryData` НЕ вызывается этой мутацией (architecture.md#L472, буква запрета optimistic; единственный существующий `setQueryData`-каллсайт — WS-мёрж в `useNotificationsFeed.ts`, эта стори его не трогает).
3. **AC-3 (инвалидейт — обычный, канон `['notifications']`).** `onSuccess` вызывает РОВНО `queryClient.invalidateQueries({ queryKey: ['notifications'] })` (константа `NOTIFICATIONS_QUERY_KEY` из `useNotificationsFeed.ts`, не литерал-дубликат) — зеркало `DaySubmissionPanel.tsx`'s паттерна (`useApiMutation` + `invalidateQueries` в `onSuccess`, без ретрая мутации). После инвалидейта и рефетча счётчик непрочитанных (`unreadCount`, уже производный от `read_at === null`) реально уменьшается — это и есть снятие ограничения 11.4.
4. **AC-4 (ошибка мутации — видима, не проглочена молча).** `useApiMutation`'s общий контракт: 403/404 (чужое/несуществующее уведомление — оба уже покрыты бэком 11.4a) попадают в «остальное» ветку (`mutation.error`, БЕЗ автотоста — сверено с `useApiMutation.ts:83`-областью). Given такая ошибка, Then строка показывает краткий инлайн-текст ошибки (не модалка, не toast — соразмерно последствиям личной UX-мутации), кнопка остаётся кликабельной для повтора. Это НЕ конфликт-диалог (`useApiMutation`'s `conflict`-путь здесь не задействован — mark-read не 409-совместимая операция).
5. **AC-5 (не interactive-in-menuitem — семантика панели не ломается).** Кнопка — обычный `<button>` внутри `<li>` (текущая разметка `NotificationRow` — БЕЗ `role="menu"`/`role="menuitem"`, подтверждено чтением файла целиком). Клик по кнопке НЕ триггерит существующий outside-click-close хендлер панели (кнопка внутри `panelRef`) — регресс-тест на этот сценарий обязателен, не только логическое рассуждение.
6. **AC-6 (кэш `['notifications']` чистится при смене актора — закрывает открытый вопрос №1 родительской 11.4).** `_bmad-output/implementation-artifacts/11-4-центр-уведомлений-ui.md:258,419`: ревью 11.4 явно подтвердило адрес — `AuthContext.tsx`'s `login()`/`logout()` чистят ТОЛЬКО `['me']` (`removeQueries`), `['notifications']` не тронут → уведомления актора А доживают в кэше до первого рефетча под актором Б. Добавить `queryClient.removeQueries({ queryKey: ['notifications'] })` в ОБА колбэка (`login`, `logout`), тем же паттерном, что существующая строка для `['me']`. Отдельный AC/файл-запись — НЕ бандлится молча в AC-1..5 (единственная причина эту правку вообще делать в 11.4b, а не отдельной стори — она мала и её адрес уже подтверждён ревью 11.4; при этом `AuthContext.tsx` — единственный файл этой стори ВНЕ `NotificationBell.tsx`/`useNotificationsFeed.ts`).
7. **AC-7 (регресс нулевой).** `npm run gate` (frontend, из `frontend/`) зелёный: существующие 13 тестов `NotificationBell.test.tsx` + тесты `useNotificationsFeed.test.tsx` не сломаны (ни один не тестирует кнопку — новое покрытие, не пересечение). `schema-check` не задет (11.4a уже коммитнула регенерацию — эта стори НЕ трогает `schema.d.ts`/`schema.yaml`).

## Dev Notes

- **AC-0 родительской 11.4 устарел — не копировать.** `11-4-центр-уведомлений-ui.md`'s reverse-gate («GET-only, `put/post/... = never`») был верен ДО 11.4a. Сейчас `schema.d.ts` уже несёт `notifications_read_create` (`post`, `path: {id: number}`, `requestBody?: never`, `responses: {200: NotificationMarkReadResponse}`). Эта стори НЕ повторяет reverse-gate проверку — вместо неё позитивно опирается на уже сгенерированный тип.
- **Мутация — внутри строки, не в родителе.** `NotificationRow` заводит собственный `useApiMutation`-инстанс на строку (не единая мутация в `NotificationBell` с id-параметром через `mutate()`) — изоляция: ошибка/pending-состояние одной строки не переиспользует один и тот же `isPending`/`error` для всех строк панели (было бы багом — клик по строке A показал бы pending/error и на строке B).
- **Никакого `setQueryData` из этой стори.** Единственный существующий каллсайт — WS-мёрж (`useNotificationsFeed.ts`, 11.3/11.4, closed). Мутация 11.4b добавляет ВТОРОГО писателя в тот же query-key ТОЛЬКО через `invalidateQueries` (запускает `queryFn` заново — свежие данные с сервера), никогда напрямую не пишет в кэш — иначе obsolete optimistic-подобная запись гонялась бы с настоящим WS-мёржем за то, кто «последний писал».
- **`useApiMutation`'s `TVariables extends Record<string, unknown>`.** Нельзя вызвать `mutate()` без аргументов (`void` не подходит под констрейнт) — используем `{ id: number }` даже притом что путь строится из этого же `id` (не тела запроса — `requestBody?: never` в схеме, `id` едет только в URL). `apiClient.post` вызывается с пустым телом (`{}`) — сверить сигнатуру `apiClient.post` на предмет опционального тела, чтобы не отправить лишний непустой JSON туда, где сервер его не ожидает (11.4a's `mark_read` action не читает `request.data` вовсе — тело безопасно пустое/отсутствующее).
- **AC-6 (auth-контур) — единственная правка вне `shared/notifications`/`shared/ui`.** Уже подтверждена ревью родительской 11.4 как адрес именно 11.4b (`11-4-центр-уведомлений-ui.md:419`). Держать её отдельным AC/задачей/файл-записью — не размазывать по коммиту молча, чтобы ревью этой стори могло явно оценить именно эту правку.
- **Не трогать `notificationsSocket.ts`/WS-транспорт.** Эта стори — чисто мутация + инвалидейт кэша; WS-доставка (11.1-11.3) и её мёрж-логика (`mergeNotificationPage`) не меняются.

**Ревью (3 агента, cross-model):**
- **Blind Hunter** (diff-only) нашёл единственную содержательную находку: `onSuccess`-инвалидейт мутации ничем не гардится от смены auth-состояния между кликом и ответом сервера — если `logout()`/`login()` срабатывает, пока `POST .../read/` в полёте, `invalidateQueries(['notifications'])` может выстрелить уже под новым/отсутствующим credential, той же природы гонка, от которой `login`/`logout` защищают `['me']` через `removeQueries` (не `invalidate`).
- **Решение — НЕ фиксить, задокументировать как принятый риск.** Практическое воздействие низкое: (1) после `logout()` `NotificationBell` размонтируется (редирект на `/login` под `RequireAuth`) раньше, чем типичный POST успевает резолвиться, так что `invalidateQueries` на уже несуществующий query — no-op (у TanStack Query нет активного наблюдателя, значит нет рефетча); (2) даже если бы рефетч всё же случился, глобальный `QueryCache.onError → handle401` (`providers.tsx`) уже перехватывает любой 401 и повторно чистит состояние — та же защита, что уже стоит на любом другом фоновом запросе после logout, не специфика этой мутации. Добавление явного гарда (например, чек `isAuthenticated` перед `invalidateQueries`) — сверхинженерия против маловероятного, самозаживающего сценария; урок проекта «не расширять поверхность сверх необходимого» перевесил.
- **Edge Case Hunter** (полный доступ к проекту) независимо подтвердил: изоляция мутации по строкам — реальная (React per-`<li>` hook state, `useMemo` мемоизирует только массив элементов, не хук-состояние); WS-гонка с `invalidateQueries` — безобидна (рефетч авторитетен, худший случай — визуальное мерцание, не потеря данных, задокументировано в Dev Notes `useNotificationsFeed.ts`); `markReadError.message` рендерится напрямую — тот же устоявшийся паттерн, что `SecurityEventDetailPage.tsx`/`DailyUpdatePage.tsx` (не отклонение); ARCH-FE-013-граница подтверждена живым `eslint`-прогоном, не только матрицей на бумаге.
- **Acceptance Auditor** независимо перепрочитал код, прогнал целевой набор (70/70) и полный `npm run gate` (1000/1000, size-gate 212.5 KB/300 KB) — все 7 AC подтверждены удовлетворёнными без расхождений.
