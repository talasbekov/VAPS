# Story 19.3: Справочник коэффициентов поправок нагрузки

Status: done

## Story

As an **администратор**,
I want **вести справочник коэффициентов поправок нагрузки (код, название, множитель, активность) через Admin**,
so that **структура справочника существует и готова к заполнению реальными значениями, когда владелец/значения определятся (OQ-6), не блокируя остальной Epic 19 на неразрешённом открытом вопросе**.

## Scope Decision

- **OQ-6 НЕ разрешён** (`prd.md#L228`: `«Коэффициенты поправок нагрузки: значения, единицы, владелец справочника»` — открытый вопрос §8, БЕЗ ответа). Эта стори строит СТРУКТУРУ справочника (PROVISIONAL, задокументировано, не немой дефолт) — не применение коэффициентов к какому-либо расчёту. Тот же класс решения, что уже принят в проекте для других нерешённых OQ (ЭЦП — hash-заглушка, Epic 14-16; BEFORE_DUTY — параметр, Story 14.7): построить готовую-к-заполнению структуру, честно отложить семантику применения.
- **Минимальная, НЕ специфичная форма** — `code` (уникальный slug, вводится администратором свободно — ЕДИНИЦЫ И ТАКСОНОМИЯ «сезон/погода» НЕ известны из OQ-6, поэтому НЕ строится `season_code`/`weather_code` choices-поле, которое пришлось бы придумывать без спецификации), `name` (отображаемое название), `multiplier` (`DecimalField`, множитель к лимиту — >0, NOT NULL, семантика умножения ТОЖЕ часть нерешённого OQ-6, поле существует как «число, которое когда-то будет коэффициентом», не более), `is_active` (BooleanField). Тот же шаблон справочника, что `StatusType` (`code` PK, `name`, `is_active`) — буквальное переиспользование конвенции reference-таблицы этого проекта.
- **НЕ применяется ни к одному расчёту** — `Post.max_service_minutes` (14.2, `flag_post_overload`, 18.5), `compute_plan_load`/`compute_fact_load` (19.1), `detect_overload_days` (19.2) — НИ ОДИН из них не читает, не импортирует, не изменяется этой стори. Применение коэффициента (умножает лимит Поста? умножает часы факта? за какой период?) — ОТДЕЛЬНАЯ будущая стори, когда OQ-6 будет разрешён с Bratan; изобретать это сейчас означало бы гадать за заказчика.
- **Admin-регистрация** — справочник (config, admin-managed), НЕ бизнес-запись — регистрируется в Admin, тот же прецедент, что `StatusType`/`DivisionNotifyRecipient` (не `EmployeeStatus`/`DailySubmission`, которые ARCH#L467/L485 запрещает регистрировать).
- **Модель живёт в `apps/operations/load/models.py`** — ПЕРВАЯ модель этого app (19.1/19.2 были без моделей, только селекторы) — architecture.md:531-533 уже резервирует `load/` под «нагрузку, ServiceHours»; этот справочник — часть той же поддомена нагрузки. Первая реальная миграция для `apps.operations.load` (19.1's `migrations/__init__.py` был пуст).
- **Никакого seed-скрипта с реальными значениями** — таблица создаётся ПУСТОЙ; заполнение — ручная работа администратора через Admin ИЛИ будущая data-migration, когда значения появятся (вне объёма этой стори).
- **Out of scope**: применение коэффициента к любому расчёту нагрузки/лимита; API/эндпоинт HTTP-слоя (Admin — единственный интерфейс); экран управления (вне Admin); seed реальных значений; сезон/погода как структурированная таксономия.

## Acceptance Criteria

1. **AC-1.** Модель `LoadCoefficient`: `code` (уникальный, PK или unique-поле), `name`, `multiplier` (Decimal, > 0), `is_active` (default `True`) — миграция создаёт таблицу, `make gate`'s `makemigrations --check --dry-run` зелёный.
2. **AC-2.** DB CheckConstraint: `multiplier > 0` (строго положительный — множитель `<= 0` не имеет смысла ни при каком будущем прочтении OQ-6).
3. **AC-3.** `code` уникален на уровне БД (повторная попытка создать с уже существующим `code` → `IntegrityError`, не тихий дубль).
4. **AC-4.** Модель зарегистрирована в Django Admin (`LoadCoefficientAdmin`) с `list_display` (`code`, `name`, `multiplier`, `is_active`) и `search_fields`/`list_filter`, тот же паттерн, что `StatusTypeAdmin`.
5. **AC-5.** `apps.operations.load` НЕ импортирует `apps.core.models` (ARCH-003 — покрывается уже существующим generic-тестом `test_operations_does_not_import_core_models`, новых assertion'ов не требуется, тест сканирует всё дерево `operations/`).
6. **AC-6.** Ни один существующий модуль (`events/services.py`, `load/selectors.py`) не импортирует `LoadCoefficient` — применение остаётся будущей работой (проверяется grep-тестом или явным assertion в тестах этой стори).
7. **AC-7.** `make gate` (Backend/VAPS) зелёный.

## Out of Scope

- Применение коэффициента к `Post.max_service_minutes`/`compute_plan_load`/`compute_fact_load`/`detect_overload_days` — будущая стори после разрешения OQ-6.
- API/эндпоинт HTTP-слоя.
- Экран управления вне Admin.
- Seed реальных значений (сезон/погода коэффициенты).
- Структурированная таксономия сезон/погода (choices-поле) — `code` остаётся свободным текстом до появления спецификации.
