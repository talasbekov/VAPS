# Story 14.4: Справочник видов дежурств

Status: done

## Story

As a Старший объекта / Администратор,
I want вести виды дежурств объекта с параметрами проекций (длительность, отдых после, время «перед дежурством», требование рекогносцировки),
so that план дежурств (14.5) и сервис проекций OM_AUTO (14.6/14.7) получают выверенные параметры DUTY/REST_AFTER_DUTY/BEFORE_DUTY без хардкода.

## Acceptance Criteria

1. **Модель DutyType.** TimeStampedModel + `created_by` (канон Sector/Post), `db_table="ops_duty_types"` (префикс object_ снят вслед за 14.1–14.3), facility FK **CASCADE**, `code` CharField(100) и `name` CharField(255) — оба `\S`-CHECK; `description` Text default "" (house-канон tasks/features, задекларированное отклонение от донорского NULL); `default_post_type` FK на PostType **SET_NULL** null `db_column="default_post_type_code"` (зеркало донора — подсказка, не контракт, в отличие от PROTECT у Post.post_type); `default_duration_minutes` int NULL; `rest_after_minutes` int NOT NULL default 1440; `before_duty_minutes` int NOT NULL default 0; `requires_reconnaissance` bool default False; `is_active` default True; ordering `code, id`.
2. **DB-инварианты.** CHECK-и (красные пробы транзакционные, обе стороны, ассерт имени констрейнта): `default_duration_minutes` NULL или >0 (донорский CHECK; ветка «>0» с `isnull=False` — урок NULL-пробела 14.3a); `rest_after_minutes` ≥ 0; `before_duty_minutes` ≥ 0; `code`/`name` `\S`; partial-уник `uq_duty_type_facility_code` (facility, Lower(code)) WHERE is_active — канон 14.2 вместо донорского тотального UNIQUE(object,code).
3. **Сервисы.** `services/duty_type_service.py`: `create_duty_type(actor, facility_id, code, name, **params)` / `update_duty_type(actor, duty_type_id, changes)` / `deactivate_duty_type(actor, duty_type_id)`; единый словарь канонизаторов create+update (канон _POST_CANONIZERS) + `DUTY_TYPE_EDITABLE_FIELDS` (whitelist {name, description, default_post_type_code, default_duration_minutes, rest_after_minutes, before_duty_minutes, requires_reconnaissance} — `code` не редактируется: идентификатор для потребителей 14.5+) + drift-тест whitelist↔модель; `default_post_type_code` резолвится через `_resolve_post_type` topology_service (is_active-гейт; неактивный/несуществующий → VALIDATION_ERROR 400; NULL легален); числовые параметры через `_canonize_int` (int4-потолок; duration nullable min 1, rest/before min 0); каждая мутация под `select_for_update` с frozen-aggregate guard (facility.is_active); дубль code среди активных → структурный 409 `DUTY_TYPE_ALREADY_EXISTS` (pre-check case-insensitive + race-бэкстоп в CONSTRAINT_ERROR_MAP); повторная деактивация / мутация неактивного → 409 `DUTY_TYPE_ALREADY_INACTIVE`; honest-noop со снимком updated_at.
4. **Аудит.** `DUTY_TYPE_CREATED`/`DUTY_TYPE_UPDATED`/`DUTY_TYPE_DEACTIVATED` (реестр audit-events.yaml + 2 кода в error-codes.yaml категории state); entity-ось uuid5 неймспейса `vaps:duty_type`; плоские публичные ключи (`default_post_type_code`, не объект) в new_value/changes.
5. **Селектор.** `DutyTypeSelector` (get / get_for_update с `of=("self","facility")` / list_for_facility) общим `_canonize_pk`; лок-ассерты в тестах таблично-фильтрованные, of= запинен буквально (урок 3×High 14.3a).

## Dev Notes

### Ключевые решения (Д)

- **Д1. Object-scoped бизнес-модель, НЕ admin-справочник.** FR-39 называет «виды дежурств» справочником, но донорский DDL (DB-OPS-046, Critical Fix 4 — позднее и авторитетнее списка FR-39) делает их per-object: FK на объект CASCADE, UNIQUE(object,code), натуральный ключ импорта object_code+code. Канон 14.1 «DDL = семантический контракт» + канон «Admin = только глобальные справочники» → DutyType идёт путём Sector/Post (сервисы/аудит/локи), НЕ путём PostType/ChecklistTemplate. Глобального справочника видов дежурств не существует ни в одном источнике.
- **Д2. default_post_type — SET_NULL (зеркало донора), не PROTECT.** У Post.post_type донор давал RESTRICT → мы усилили до PROTECT (тип поста — контракт поста). Здесь донор сознательно даёт SET_NULL: default_post_type — необязательная подсказка для 14.5, потеря которой не ломает вид дежурства. Разные on_delete — по донорскому различию, не разнобой.
- **Д3. code нередактируем после создания**: идентификатор для плана дежурств (14.5) и импорта (object_code+code); правка кода = деактивация + создание нового. Донор молчит — решение по классу «Д2-14.3 natural identity».
- **Д4. deactivate_facility НЕ каскадит виды дежурств**: frozen-guard блокирует их мутации, PROTECT-ловушки (причина каскада привязок в 14.3a) здесь нет — все внешние ссылки НА DutyType появятся только в 14.5 (duty_shifts RESTRICT, зона DB-OPS-047). Канон Sector/Post: замороженный объект хранит топологию как есть.
- **Д5. Параметры проекций — только хранение + DB-floor.** Семантика rest_after (REST_AFTER_DUTY, BR-DUTY-TYPE-002) → 14.6; before_duty (BR-DUTY-TYPE-003, «длительность — параметр» OQ-3) → 14.7; requires_reconnaissance (BR-DUTY-TYPE-004 — гейт утверждения плана) → 14.5/15.3. Здесь их бизнес-правила НЕ исполняются — верхних капов не выдумываем (молчание донора), кроме int4-потолка канонизатора.
- **Д6. rest_after=0 легален** (донор CHECK ≥0, не >0): вид дежурства без обязательного отдыха — валидная конфигурация; 14.6 просто не создаст проекцию нулевой длины.

### Наследуемые каноны (ревью 14.1–14.3a — дефолт)

Локи в селекторе внутри atomic (of= БЕЗ nullable-стороны JOIN, но С facility); frozen-aggregate guard НА КАЖДОЙ мутации; резолв справочных ссылок пейлоада внутри транзакции (битая ссылка = 400, не 404); pre-check дублей + race-бэкстоп map (точные кортежи в дрейф-гварде); honest-noop со снимком updated_at; state-конфликты = структурные 409; капы длин до БД; `_canonize_int` с int4-потолком; sorted unknown-ключей; плоские ключи аудита; `\S`-непустота; conditional-CHECK с `isnull=False` в regex/числовой ветке (NULL-пробел 14.3a); обе-границы-пробы; ordering с tie-breaker id; лок-ассерты таблично + of=-пин; «молчание донора = не выдумывать».
