# Story 14.4: Справочник видов дежурств (модель)

Status: review

## Story

As a **разработчик**,
I want **модель `DutyType` (вид дежурства объекта: длительность, отдых после, требование рекогносцировки)**,
so that **Epic 14's дальнейшие стори плана дежурств (14.5+, `ops_duty_shifts`/проекции OM_AUTO) имеют модельный фундамент справочника видов дежурств, сверенный с донор-спекой VAPS_7.8.2**.

`epics.md#L1404` (буква: «Справочник видов дежурств (FR-39)»). Четвёртая стори Epic 14, строится поверх `Object` (14.1, done).

## Scope Decision (найдено при create-story)

- **«Справочник видов дежурств» — PER-ОБЪЕКТНЫЙ, не глобальный.** PRD's FR-39 (`prd.md:166`) перечисляет «виды дежурств» ОДНИМ списком рядом с глобальными справочниками (должности/звания/типы статусов/причины/Группы/коэффициенты) — читается как «ещё один глобальный справочник». Но донор (`docs/PersonnelStatus/VAPS_7.8.2.md`, §48 «Critical Fix 4 — Object Duty Types», `DB-OPS-046`) моделирует `ops_object_duty_types` С `object_id NOT NULL REFERENCES ops_objects(id)` — вид дежурства ПРИНАДЛЕЖИТ конкретному объекту (тот же паттерн, что `Post`/`ChecklistTemplate`+`Binding` — donor's «Critical Fix» разделы регулярно уточняют/переопределяют исходную PRD-формулировку конкретной схемой). Донор — источник схемы, PRD's группировка — не обязывающая структура (тот же аргумент, что 14.1's `Object`-vs-`Facility` Scope Decision). Модель `DutyType` — `ForeignKey(Object, ...)`, НЕ глобальная таблица.
- **`ops_duty_shifts`'s расширение (`DB-OPS-047`: `duty_type_id`/`duty_role_code`/`notes`) — ОТЛОЖЕНО.** Таблица `ops_duty_shifts` не существует в кодовой базе (Epic 14's Story 14.5+ — «план дежурств на месяц»). Эта стори строит ТОЛЬКО справочник (`DutyType`), не трогает несуществующую таблицу смен.
- **`REST_AFTER_DUTY_POLICY`/`BR-DUTY-REST-001/002` (hard-block vs soft-override при назначении в период отдыха) — ОТЛОЖЕНО.** Это бизнес-правило НАЗНАЧЕНИЯ сотрудника на дежурство (сервис/API), не атрибут справочника — принадлежит будущей стори проекции (14.6-14.9's территория, "Сервис проекции OM_AUTO"/"Конфликт Отдыха").
- **`default_post_type_code` — тот же deferred-FK паттерн, что `Post.post_type_code`/`Object.importance_level_code` (14.1/14.2).** `ops_post_types` не существует — plain `CharField`, не FK.
- **`default_duration_minutes` — DB `CheckConstraint` СТРОГО `> 0`, не переиспользовать `PositiveIntegerField`'s implicit `>=0`.** Донор: `CHECK (default_duration_minutes > 0)` — `0` донор явно запрещает, а `PositiveIntegerField` его бы пропустил (0 ≥ 0). Требуется ЯВНЫЙ `CheckConstraint`, зеркалит 14.1/14.2's установленный DB-first паттерн.
- **`rest_after_minutes`/`before_duty_minutes` — БЕЗ дополнительного `CheckConstraint` на нижнюю границу.** Донор: `CHECK (>= 0)` — но `PositiveIntegerField` УЖЕ даёт implicit DB-уровневый `>= 0`-CHECK сам по себе (урок 13.5a's ревью, Acceptance Auditor: избыточный явный constraint поверх уже покрытого диапазона — тот же класс вакуумности, что red-probe на `-1`, когда `PositiveIntegerField` уже блокирует отрицательные значения). Не дублировать.

## Acceptance Criteria

1. **AC-1 (модель `DutyType`).** `DutyType(TimeStampedModel)`: `object` (`ForeignKey(Object, on_delete=CASCADE, related_name="duty_types")`), `code` (CharField, max_length=100), `name` (CharField, max_length=255), `description` (TextField, blank=True), `default_post_type_code` (CharField, max_length=50, blank=True — deferred-FK), `default_duration_minutes` (PositiveIntegerField, null=True, blank=True — донор без `NOT NULL`), `rest_after_minutes` (PositiveIntegerField, default=1440), `before_duty_minutes` (PositiveIntegerField, default=0), `requires_reconnaissance` (BooleanField, default=False), `is_active` (BooleanField, default=True). `db_table="ops_object_duty_types"`.
2. **AC-2 (уникальность).** `UniqueConstraint(fields=["object", "code"])` (донор: `unique_object_duty_type_code UNIQUE(object_id, code)`).
3. **AC-3 (`default_duration_minutes` — строгий `> 0` DB-гард).** `CheckConstraint` `Q(default_duration_minutes__isnull=True) | Q(default_duration_minutes__gt=0)` — nullable-поле, констрейнт обязан пропускать `NULL` явно (не полагаться на implicit Postgres NULL-passthrough при составном условии с `|`, см. Dev Notes про `[[feedback_conditional_check_null_gap]]`-класс урока).
4. **AC-4 (миграция).** Одна `0005_...` в `apps/operations/facilities/migrations/` — модель, `db_table`, `UniqueConstraint`, `CheckConstraint`.
5. **AC-5 (Admin — не регистрируется).** Тот же аргумент, что 14.1-14.3.
6. **AC-6 (тесты + границы контекста).** Модельные тесты: создание, уникальность `(object, code)`, удаление `Object` каскадно удаляет `DutyType`, `default_duration_minutes` red-probe (`0` отклонён DB-уровнем; отрицательное значение отклонено `PositiveIntegerField`'s собственным уровнем — НЕ дублировать red-probe на это, см. Scope Decision), `default_duration_minutes=NULL` принимается (constraint пропускает), `rest_after_minutes`/`before_duty_minutes` дефолты (`1440`/`0`) верны. `test_isolation.py` — автоматически покрывает.
7. **AC-7 (регресс нулевой).** `make gate` зелёный.

## Dev Notes

- **Строится ПОВЕРХ живого `models.py`** (14.1-14.3, включая все ревью-фиксы) — читать файл ПЕРЕД правкой.
- **Nullable-поле + `CheckConstraint` — `isnull=True` ветка ОБЯЗАТЕЛЬНА в условии, не полагаться на «Postgres CHECK молча пропускает NULL».** Это верно ТОЛЬКО для простых сравнений одного столбца (как `latitude__gte=-90` в 14.1 — `NULL >= -90` действительно UNKNOWN→проходит). Но при СОСТАВНОМ условии через `|`/`&` с несколькими операторами есть класс багов, где часть выражения НЕ покрывает NULL правильно (`[[feedback_conditional_check_null_gap]]`-урок: «regex-ветка обязательного поля в CHECK требует isnull=False; CHECK проходит на NULL» — зеркальный случай). Для ПРОСТОГО `default_duration_minutes__gt=0` (без composite-веток) `NULL > 0` тоже UNKNOWN→проходит АВТОМАТИЧЕСКИ, явный `isnull=True`-OR технически избыточен здесь — НО пишется явно ради читаемости и как страховка от будущей правки, которая случайно превратит constraint в composite-условие и молча потеряет NULL-passthrough. Тест на `NULL` в AC-6 подтверждает поведение эмпирически, не полагается на то, что комментарий прав.
- **`PositiveIntegerField`'s implicit `>=0` — урок 13.5a, не дублировать.** Ревью 13.5a (Acceptance Auditor) доказал: red-probe на `-1` при `PositiveIntegerField` вакуумен ДЛЯ НОВОГО constraint — `-1` отклоняется implicit-гардом самого типа поля, ещё до именованного `CheckConstraint`. `rest_after_minutes`/`before_duty_minutes` НЕ получают дублирующий `>=0`-constraint по этой же причине.
