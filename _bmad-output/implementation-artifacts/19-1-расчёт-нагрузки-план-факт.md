# Story 19.1: App operations/load — нагрузка план/факт по дням (селекторы)

Status: done

## Story

As a **держатель права `event.manage`**,
I want **получить помесячную нагрузку сотрудника (план — по Дежурствам и назначениям ОМ, факт — по опросу) с разбивкой по календарным дням**,
so that **эти данные станут единым источником для агрегатного перегрузка-детектора (Story 19.2), справочника-коэффициентов (19.3), календарей (19.4/19.5) и карточки сотрудника (19.6) — ни одна из них не пересчитывает нагрузку заново своим алгоритмом**.

## Scope Decision

- **Разбор FR-32**: `«Система считает нагрузку как сумму Дежурств и ОМ (план — по назначениям, факт — по опросу FR-43)»` — эта стори реализует ИМЕННО эту сумму, per-day, per-employee, ЧИСТЫМИ read-функциями (селекторами). `«подсвечивает перегрузку (свыше 3 дней подряд по 8+ часов...)»` — агрегатное правило по НЕСКОЛЬКИМ дням уже принадлежит **Story 19.2** (явно в её заголовке, epics.md:1462) — не реализуется здесь, но 19.2 обязана переиспользовать эти селекторы, не писать собственный запрос. `«коэффициенты поправок»` — Story 19.3, не эта стори.
- **Новый Django-app `apps/operations/load/`** (`OpsLoadConfig`, label `ops_load`) — architecture.md:531-533 уже резервирует `load/` под нагрузку. Регистрируется в `INSTALLED_APPS` (config/settings.py) СЕЙЧАС, чтобы 19.2/19.3 (которым понадобится модель — коэффициенты, агрегатный флаг) не переносили app из «просто пакет» в «Django app» посреди своей стори. Миграций НЕТ (нет моделей) — только `migrations/__init__.py` (пустой пакет, требуется Django даже без миграций, если app зарегистрирован).
- **Никакой новой персистентной модели.** Обе величины (план/факт) вычисляются on-the-fly из УЖЕ существующих таблиц: `DutyShift` (14.5, план-дежурства), `PlacementAssignment`+`SecurityEvent.starts_at/ends_at` (16.1/16.3a, план-ОМ), `PlacementAssignmentActual` (18.3, факт-ОМ по опросу). Хранить агрегат смысла нет: он тривиально пересчитывается, а хранимая копия немедленно устареет при правке любого исходника (та же логика, что «ServiceHours не пересчитывается автоматически» в 18.4/18.5 — здесь наоборот: НЕ материализуем вовсе, всегда читаем свежее).
- **Гранулярность — per calendar LOCAL day, не day/night-смена.** FR-32's `«>3 дней подряд по 8+ часов»` считает ДНИ целиком, не «дневную половину дня» — так что здесь НУЖНА другая граница нарезки (местная полночь), чем `_split_day_night_hours()`'s 22:00/06:00-граница (18.4, `events/services.py:2234`). Эта стори НЕ переиспользует `_split_day_night_hours()` напрямую (ведущее подчёркивание = приватная функция чужого модуля — тот же анти-паттерн, что явно отмечен в 18.4's Dev Notes про `apps/core/clock.py`'s `_local_tz()`) — пишет свою чистую функцию `_split_hours_by_local_day(start_at, end_at)` с ДРУГОЙ границей (местная полночь), локально в `load/selectors.py`.
- **Факт — не читает `ServiceHours` (18.4).** `ServiceHours.day_hours`/`night_hours` — это ОДНА агрегированная сумма на весь `PlacementAssignmentActual` (может охватывать несколько дней, 18.4 AC-4), без разбивки по календарным дням — не хватает гранулярности для 19.1/19.2. Вместо этого факт-селектор режет СЫРОЙ интервал `PlacementAssignmentActual.actual_start_at/actual_end_at` той же `_split_hours_by_local_day()`, что и план. Гейт факта — тот же двойной гейт, что 18.3/18.4 (`version.is_current` + `event.status_code == CLOSED`) — факт без утверждённого/закрытого события не существует по построению этих моделей.
- **План-ОМ читает `SecurityEvent.starts_at/ends_at`, не индивидуальное время назначения** — `PlacementAssignment` не несёт собственного времени (16.3a's явное architectural-решение: «интервал принадлежит EVENT, не каждому назначению отдельно», подтверждено с Bratan). План-ОМ включает только назначения текущей версии (`version.is_current=True`) НЕ отменённого события (`status_code != CANCELLED`); `starts_at`/`ends_at` — nullable (16.3a retrofit) — назначения событий без интервала пропускаются (0 плановых часов), не падают с ошибкой.
- **План-Дежурства читает `DutyShift.starts_at/ends_at` напрямую** (14.5, всегда NOT NULL) — исключает отменённые смены (`cancelled_at IS NULL`).
- **Возвращаемая форма — `Dict[date, Decimal]`** (сумма часов за календарный день, план и факт — раздельные функции/вызовы, не смешиваются в одну структуру): вызывающий код (19.2, 19.6) сам решает, как объединить план+факт для своего сценария (19.2 работает с фактом; 19.6, возможно, показывает оба).
- **Out of scope**: агрегатный >3-дневный/8+ч детектор перегрузки и подсветка (19.2); справочник коэффициентов (19.3); календарные экраны (19.4/19.5); карточка сотрудника (19.6); нагрузочные тесты (19.7); API/эндпоинт (эта стори — только backend-селекторы, без HTTP-слоя, как 18.4/18.5 были без API до 18.6).

## Acceptance Criteria

1. **AC-1.** `compute_plan_load(employee_id, start_date, end_date)`: одна `DutyShift` целиком внутри одного дня → весь день получает её длительность в часах.
2. **AC-2.** `compute_plan_load(...)`: `DutyShift`, пересекающая местную полночь (напр. 20:00–06:00) → часы корректно распределены на ДВА календарных дня, сумма равна полной длительности смены.
3. **AC-3.** `compute_plan_load(...)`: `PlacementAssignment` текущей версии ОМ с `SecurityEvent.starts_at/ends_at` заданными → часы события распределены по дням так же, как AC-1/AC-2; ОМ и Дежурства ОДНОГО дня СКЛАДЫВАЮТСЯ в одну сумму на этот день.
4. **AC-4.** `compute_plan_load(...)`: назначение НЕ текущей версии (`is_current=False`) ИЛИ события со `status_code=CANCELLED` ИЛИ `starts_at`/`ends_at` не заданы (`NULL`) — исключается из суммы.
5. **AC-5.** `compute_plan_load(...)`: отменённая смена (`cancelled_at IS NOT NULL`) — исключается из суммы.
6. **AC-6.** `compute_fact_load(employee_id, start_date, end_date)`: `PlacementAssignmentActual`, чьё событие `CLOSED` и версия `is_current` → часы распределены по дням той же логикой local-midnight нарезки, включая многодневный факт.
7. **AC-7.** `compute_fact_load(...)`: факт назначения НЕ текущей версии ИЛИ событие не `CLOSED` — исключается из суммы (тот же гейт, что 18.3/18.4).
8. **AC-8.** Оба селектора: диапазон `[start_date, end_date]` — записи/интервалы, целиком лежащие ВНЕ диапазона, не влияют на сумму; интервал, ЧАСТИЧНО пересекающий диапазон, вносит только пересекающуюся часть.
9. **AC-9.** Оба селектора: сотрудник без единой записи за период → пустой `dict` (не `KeyError`/исключение).
10. **AC-10.** `make gate` (Backend/VAPS) зелёный; `apps.operations.load` зарегистрирован в `INSTALLED_APPS`, `makemigrations --check --dry-run` зелёный (нет забытых миграций).

## Out of Scope

- Агрегатный >3-дневный/8+ часов перегрузка-детектор и подсветка на дашборде/при назначении (Story 19.2).
- Справочник коэффициентов поправок (Story 19.3, OQ-6).
- Календарь Сотрудник × месяц / Подразделение × дни (19.4/19.5).
- Налёт часов в карточке сотрудника (19.6).
- Нагрузочные тесты «дедлайн 17:00» (19.7).
- API/эндпоинт HTTP-слоя — только backend-селекторы.
- Материализация/кэш агрегата — всегда вычисляется на лету.

- `apps/operations/duties/models.py` (`DutyShift`, 14.5) — `starts_at`/`ends_at` (DateTimeField, NOT NULL), `employee_id` (плоский UUID), `cancelled_at` (nullable — Story 14.9a). - `apps/operations/events/models.py`:
  - `SecurityEvent` (line 38) — `starts_at`/`ends_at` (nullable, DateTimeField, Story 16.3a), `status_code` (`TextChoices`, включает `CANCELLED`/`CLOSED`).
  - `AssignmentVersion` (line 382) — `is_current` (BooleanField).
  - `PlacementAssignment` (line 487) — `employee_id` (плоский UUID), `version` FK на `AssignmentVersion`; НЕТ собственного времени — берётся из `version.event.starts_at/ends_at`.
  - `PlacementAssignmentActual` (line 738, Story 18.3) — `assignment` OneToOne, `actual_start_at`/`actual_end_at` (оба NOT NULL, DB CHECK `actual_start_at < actual_end_at` уже гарантирован — не перепроверять).
- `apps/operations/events/services.py:2234` (`_split_day_night_hours`, 18.4) — СТРУКТУРНЫЙ образец итеративной нарезки интервала по границе (while-цикл, `Decimal`-суммирование секунд, `.astimezone(ZoneInfo(...))`), но у ДРУГОЙ границы (22:00/06:00) — эта стори копирует ПАТТЕРН нарезки, не саму функцию, с границей местной полночи (00:00) и с ключом результата `date` (не `(day_hours, night_hours)` tuple).
- `apps/core/clock.py` — `settings.VAPS_LOCAL_TIMEZONE` (`Asia/Qyzylorda`), `ZoneInfo(...)` — тот же импорт-паттерн, что 18.4 (не импортировать `apps.core.clock._local_tz()` напрямую — приватная функция чужого модуля).
- Селекторы принимают ГОТОВЫЕ `date`-объекты (`start_date`, `end_date`) в МЕСТНОМ времени; сравнение с `DateTimeField` (UTC в БД) — фильтровать в Python после `.astimezone(tz)`, а не через ORM `__date`-lookup (тот бы сравнивал по UTC-дате, не местной — тонкая ошибка на границах суток, тот же класс проблемы, что «замороженные часы прячут построчное время», см. project memory).
- `apps/operations/tests/test_isolation.py` (`test_operations_does_not_import_core_models`, ARCH-003) — новый `load/selectors.py` не должен импортировать `apps.core.models`; `employee_id` остаётся плоским UUID-параметром на всех уровнях (тот же паттерн, что `JournalEntrySelector`/`CoreEmployeeSelector`-обёртки, `events/selectors.py`).
- Селекторы — ПЛОСКИЕ функции (`def compute_plan_load(...)`), не классы-с-`@staticmethod`: `events/selectors.py`'s `find_replacement_candidates()` — уже установленный в этом модуле прецедент функции-не-класса для селектора с несколькими параметрами (в отличие от `JournalEntrySelector`, которая группирует ДВА связанных read-метода без параметров периода).

**Ревью (Blind Hunter + Edge Case Hunter + Acceptance Auditor)** — 3 действия применены:
1. `_split_hours_by_local_day()` больше НЕ поднимает `ValueError` на вырожденном/инвертированном интервале (`end_at <= start_at`) — возвращает `{}` (0 часов). Причина: `SecurityEvent.starts_at/ends_at` — nullable, БЕЗ DB CheckConstraint (в отличие от `DutyShift`, у которой есть `ck_duty_shift_starts_before_ends`) — только `full_clean()`-путь гарантирует порядок, `.objects.create()` его не вызывает; одна плохая строка не должна ронять агрегат по всему сотруднику. Тест: `test_plan_ignores_degenerate_event_window_without_raising`.
2. Округление до сотых перенесено из `_split_hours_by_local_day()` (раздельно на каждый кусок) в конец `compute_plan_load()`/`compute_fact_load()` (один раз, после слияния ВСЕХ источников за период) — раздельное округление могло разойтись с округлением суммы (тот же класс проблемы, что 18.4's day/night review-фикс). Тест: `test_plan_quantizes_once_after_merging_all_sources_not_per_source`.
3. Исправлена неточность в этой Completion Notes (было "15 тестов", факт — 11).

Отложено, не блокирует эту стори (задокументировано как известное ограничение, тот же класс допущения, что 18.4's non-DST-defensive нарезка):
- DST-safety цикла нарезки не протестирована (сейчас неактуально — `Asia/Qyzylorda` не наблюдает DST).
- Нет верхней границы на длину интервала (патологически длинный `DutyShift`/`SecurityEvent` — вопрос качества данных, не регресс этой стори).
