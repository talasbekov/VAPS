# Story 15.10: Эскалация неотработанного запроса Группе (FR-42)

Status: review

## Story

As a **система**,
I want **автоматически пометить и уведомить о запросе Группе, который долго не выполняется**,
so that **бездействие не остаётся незамеченным (FR-42)**.

## Scope Decision (найдено при create-story)

- **Story 15.10 (`epics.md:1425`, личная проверка research-агента + ре-верификация):** «Эскалация неотработанного запроса по вертикали (FR-42; редкое событие по конструкции)». FR-42 (`epics.md:69`): «Эскалация по бездействию вверх по штатной вертикали (управление → зам → рук. департамента); ОРГД не вовлекается».
- **КРИТИЧЕСКИЙ ОТКРЫТЫЙ ВОПРОС, НАЙДЕННЫЙ research-агентом: «N дней эскалации» явно помечен STOP-маркером в architecture.md:113** («N дней эскалации — открытый вопрос (СТОП-маркер для деталей)»). Порог НЕ определён нигде. PROVISIONAL-решение: Django setting `VAPS_FORCE_REQUEST_ESCALATION_DAYS` (дефолт `2`), легко перенастраиваемый, когда порог будет уточнён продуктом — тот же паттерн, что везде в проекте для неподтверждённых числовых констант.
- **Полная иерархия «управление → зам → рук. департамента» — НЕ реализуется буквально в этой стори.** Нет подтверждённого селектора/данных для разрешения этой конкретной вертикали в домене ОМ/`GroupForceRequest` (в отличие от FR-13's `NotifyRecipientSelector`, построенного специально для submissions-домена через 3 отдельные стори — 5.6a/5.7a/5.7b1). Изобретать эквивалентный селектор без спеки/данных — прямой путь к неверному предположению. **Упрощённое PROVISIONAL-решение:** уведомление направляется держателям `brokerage.manage` (та же роль, что выполняет выделение, 15.8) — не полная вертикаль, задокументированный открытый вопрос для будущего уточнения, когда появятся оргструктурные данные для полной эскалации.
- **Механизм — БЕЗ полной watermark/catch-up/advisory-lock инфраструктуры** (FR-13's `check_lagging_submissions`-паттерн, 5.7b2). Идемпотентность обеспечивается напрямую полем `escalated_at` на самой строке `GroupForceRequest` (если уже проставлено — пропускаем), не внешним watermark-состоянием — упрощение, оправданное отсутствием необходимости в day-by-day-хронологии (эскалация — per-row проверка, не daily-batch).
- **НЕ Celery** — management-команда, вызываемая по расписанию (beat-регистрация — будущая стори, тот же принцип, что 5.7b2/12.6's разделение).
- **Триггер — `status in (SENT, PARTIALLY_ALLOCATED)` и `updated_at` старше порога.** `ALLOCATED`/`NOT_SENT` не эскалируются (`NOT_SENT` — черновик, ещё не отправлен; `ALLOCATED` — уже выполнен).
- **Аудит + `apps.notifications`-уведомление** на реальной эскалации (не на каждом прогоне команды).

## Acceptance Criteria

1. **AC-1 (`escalated_at`-поле).** Новое nullable-поле на `GroupForceRequest`.
2. **AC-2 (management-команда).** `escalate_stale_force_requests` — находит `GroupForceRequest` с `status in (SENT, PARTIALLY_ALLOCATED)`, `escalated_at IS NULL`, `updated_at` старше `VAPS_FORCE_REQUEST_ESCALATION_DAYS` дней.
3. **AC-3 (идемпотентность).** Повторный прогон НЕ повторно эскалирует уже помеченные строки (`escalated_at IS NOT NULL` — пропуск).
4. **AC-4 (уведомление).** `apps.notifications.services.notify()` вызывается для каждой эскалированной строки, получатели — держатели `brokerage.manage`.
5. **AC-5 (аудит).** `GROUP_FORCE_REQUEST_ESCALATED` — на каждой реальной эскалации.
6. **AC-6 (не эскалирует `ALLOCATED`/`NOT_SENT`/свежие).** Явный негативный тест.
7. **AC-7 (регресс нулевой).** `make gate` зелёный, миграция чистая.

## Out of Scope

- Полная иерархия «управление → зам → рук. департамента» — открытый вопрос, нет данных/селектора (см. Scope Decision).
- Beat/Celery-регистрация — будущая стори (тот же паттерн, что 5.7b2/12.6).
- Watermark/advisory-lock-инфраструктура — не нужна для per-row идемпотентности этой стори.
- Настраиваемый per-запрос порог (сейчас — глобальная константа) — не запрошено.
