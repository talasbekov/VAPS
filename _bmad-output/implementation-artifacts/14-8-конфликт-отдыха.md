# Story 14.8: Конфликт Отдыха (soft+override по матрице 3.4)

Status: ready-for-dev

## Story

As a **разработчик**,
I want **зафиксировать и покрыть тестом, что `REST_AFTER_DUTY` классифицируется как SOFT в декларативной конфликт-матрице (Story 3.4) и что оператор, создающий ручной статус поверх живой `REST_AFTER_DUTY`-проекции (14.6), получает 409 `STATUS_OVERLAP_WARNING` с override-путём**,
so that **BR-DUTY-REST-001/002 выполняются через УЖЕ существующую, протестированную инфраструктуру (3.3/3.4/3.5), без изобретения нового механизма конфликтов**.

`epics.md:1408` (буква): «Story 14.8: Конфликт Отдыха (soft+override по матрице 3.4)». Восьмая стори Epic 14. `Epic 14` — явный «каркас» (skeleton), эта стори — узкая проверка/закрепление существующего поведения, не новая бизнес-логика.

## Scope Decision (найдено при create-story)

- **Донор даёт КОНФИГУРИРУЕМУЮ политику (`REST_AFTER_DUTY_POLICY` = `HARD_BLOCK`|`SOFT_OVERRIDE`, дефолт `HARD_BLOCK`) — VAPS выбирает ФИКСИРОВАННУЮ политику `SOFT_OVERRIDE`, без runtime-переключателя.** `docs/PersonnelStatus/VAPS_7.8.2.md:5883-5902` (§48.3, `BR-DUTY-REST-001/002/003`): при `HARD_BLOCK` — `422 REST_AFTER_DUTY_BLOCK`; при `SOFT_OVERRIDE` — `409 REST_VIOLATION_CONFLICT` без override-причины. Буква epics.md's стори-заголовка («soft+override по матрице 3.4») ФИКСИРУЕТ выбор VAPS: `REST_AFTER_DUTY` — SOFT, БЕЗ настраиваемого HARD_BLOCK-режима (это уже решённое архитектурное расхождение с донором, зафиксированное в epics.md на этапе планирования, не предмет пересмотра в этой стори — не AskUserQuestion-ситуация, в отличие от 14.7's BEFORE_DUTY, где донор явно резервировал решение «до заказчика»).
- **`conflict_matrix.py` (Story 3.4) — УЖЕ обеспечивает нужную классификацию, БЕЗ кода.** `HARD_STATUS_TYPE_CODES = ("SICK_LEAVE", "LEAVE_BY_REPORT", "VACATION", "COMMAND")` — `REST_AFTER_DUTY` туда НЕ входит → классифицируется как SOFT по умолчанию (всё, что не HARD и не в `COMPATIBLE_PAIRS`, — SOFT). Ничего не редактируется в `conflict_matrix.py` — стори лишь ФИКСИРУЕТ это тестом, чтобы случайное добавление `REST_AFTER_DUTY` в `HARD_STATUS_TYPE_CODES` будущей стори сломало явный тест, а не молча всплыло в продакшене.
- **Существующий `create_status()`'s override-механизм (Story 3.5) — УЖЕ универсален, работает для ЛЮБОЙ пары статус-типов, включая `REST_AFTER_DUTY`.** `status_service.py`'s `_assert_no_conflict`/override=True+override_reason — не переписывается, эта стори лишь ДОБАВЛЯЕТ end-to-end интеграционный тест, доказывающий: реально спроецированная (14.6) `REST_AFTER_DUTY`-запись (`source=OM_AUTO`) корректно триггерит 409 при попытке оператора создать пересекающийся `USER`-статус, и override реально проходит.
- **Направление конфликта — «оператор поверх REST_AFTER_DUTY», НЕ «новая смена поверх REST_AFTER_DUTY».** Донор's `BR-DUTY-REST-001/002` (§48.1, `POST .../assignments`) и epics.md's «по матрице 3.4» указывают на существующий `statuses`-путь (`create_status`), не на `DutyShift`-создание. Проверка НОВОЙ смены против существующей `REST_AFTER_DUTY` СОСЕДНЕГО дежурства того же сотрудника (донор `BR-DUTY-CONFLICT-001`) — ДРУГАЯ, более широкая задача (полный конфликт-детектор назначений), уже зарезервированная в epics.md за **Epic 16, Story 16.3** («Полный конфликт-детектор назначений… Отдых, перегрузка, несоответствие Посту») — НЕ 14.8.
- **`REST_AFTER_DUTY_POLICY` как Django-настройка — НЕ строится.** «Политика» в VAPS УЖЕ закодирована структурно — членство/отсутствие в `HARD_STATUS_TYPE_CODES`, не отдельный toggle. Донор's error-коды (`REST_AFTER_DUTY_BLOCK`/`REST_VIOLATION_CONFLICT`) — НЕ вводятся; переиспользуются существующие `STATUS_OVERLAP_WARNING`/409 (донор-специфичные имена для донор-специфичной формы ответа, которой в VAPS нет).
- **`ops_conflicts`/`ops_duty_conflicts`, `GET .../conflicts`, `POST .../validate` (донор §48.4-48.5) — вне этой стори.** Нет API-стори для 14.8 в epics.md; принадлежит 14.11 или Epic 16.

## Acceptance Criteria

1. **AC-1 (тест: `REST_AFTER_DUTY` классифицируется как SOFT).** Новый тест доказывает `"REST_AFTER_DUTY" not in conflict_matrix.HARD_STATUS_TYPE_CODES` (пин, не даёт будущей стори случайно перевести в HARD без явного изменения теста).
2. **AC-2 (end-to-end: оператор поверх живой OM_AUTO REST_AFTER_DUTY → 409, overridable).** Сценарий: `project_duty_shift()` (14.6) создаёт `REST_AFTER_DUTY` для сотрудника; `create_status()` для того же сотрудника с пересекающимся интервалом (другой `status_type_code`, `source=USER` по умолчанию) → `DomainError` с кодом `STATUS_OVERLAP_WARNING`, `http_status=409`, `overridable=True`.
3. **AC-3 (override реально проходит).** Тот же сценарий с `override=True`, непустым `override_reason` → `create_status()` УСПЕШНО создаёт статус, конфликт зафиксирован как `Override`-сущность (переиспользование 3.5's существующего пути, без нового кода).
4. **AC-4 (комментарий-якорь в `conflict_matrix.py`).** Однострочный комментарий у `HARD_STATUS_TYPE_CODES`, отсылающий к этой стори/BR-DUTY-REST-002 — предупреждает будущего редактора не добавлять `REST_AFTER_DUTY` в HARD без новой стори.
5. **AC-5 (регресс нулевой, `make gate` зелёный).**

## Out of Scope

- Проверка НОВОЙ `DutyShift` против существующей `REST_AFTER_DUTY` соседней смены (донор `BR-DUTY-CONFLICT-001`) — Epic 16, Story 16.3.
- Настраиваемый `REST_AFTER_DUTY_POLICY` (HARD_BLOCK↔SOFT_OVERRIDE toggle) — не строится; если продукт позже потребует донор-паритет, отдельная будущая стори.
- `ops_conflicts`/`ops_duty_conflicts`, `GET/POST .../conflicts`/`validate` — 14.11 или Epic 16.
- Донор-специфичные коды ошибок (`REST_AFTER_DUTY_BLOCK`/`REST_VIOLATION_CONFLICT`) — не вводятся, используются существующие.
