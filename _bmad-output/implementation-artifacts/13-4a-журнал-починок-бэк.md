# Story 13.4a: Журнал починок — модель+API (бэк)

Status: done

## Story

As a **разработчик**,
I want **пометить `BugReport` разрешённым (`resolved_at`/`resolved_in_version`/`resolution_summary`) + новый ПУБЛИЧНЫЙ (не `bugreports.view`) эндпоинт, отдающий анонимизированный журнал разрешённых репортов**,
so that **фронт (13.4b) может заполнить `ChangelogPage`'s пустой `CLOSED_FIXES`-дефолт реальными данными, без утечки личности отправителя ни через одно поле**.

Декомпозиция буквы стори 13.4 (эпик 13, `epics.md#L1372-1378`) на бэк/фронт — тот же паттерн, что 13.1a/13.1b (CLAUDE.md's backend/frontend-разделение).

## Scope Decision (найдено при create-story — важно для реализации)

`frontend/src/features/changelog/changelog.ts`'s `FixEntry.version` докстринг называет «semver из трёх частей» — но РЕАЛЬНЫЙ механизм версионирования, который эта сессия построила (12.2's `bundle.sh`, 13.3's `--hotfix`), отслеживает ИСКЛЮЧИТЕЛЬНО git short-sha (`manifest.json`'s `sha`), НЕ semver — ничто в пайплайне не бампает `frontend/package.json`'s semver-версию автоматически на каждый релиз. **Решение**: `resolved_in_version` хранит git short-sha (то же значение, что `install.sh` уже печатает как «Бандл sha: X» — разработчик копирует его оттуда), не semver. `FixEntry.version`'s тип (`string`) не меняется — это чисто интерпретационное решение, не breaking change контракта.

## Acceptance Criteria

1. **AC-1 (`BugReport` — 3 новых поля).** `resolved_at` (DateTimeField, null), `resolved_in_version` (CharField, blank — git short-sha), `resolution_summary` (CharField(500), blank — формулировка ДЛЯ ПОЛЬЗОВАТЕЛЯ, разработчик пишет заново при разрешении, НЕ копия исходного `description`, который мог содержать что угодно, вписанное оператором).
2. **AC-2 (`POST /api/bugreports/{id}/resolve/` — тот же гейт, что `list`/`retrieve`, `bugreports.view`-держатель).** Требует `resolved_in_version`+`resolution_summary` (оба непустые — валидация); устанавливает `resolved_at=Clock.now()`. Повторный вызов на уже разрешённом репорте — 409 (не тихая перезапись — второй разработчик не должен случайно переписать первого).
3. **AC-3 (новый ПУБЛИЧНЫЙ journal-эндпоинт — НЕ `bugreports.view`, `epics.md`'s «доступно всем пользователям»).** `GET /api/bugreports/journal/` — гейт: ТОЛЬКО аутентификация (`request.actor_id` непустой, тот же паттерн, что `create`, НЕ RBAC-право) — зеркалит вывод research'а при create-story: `bugreports.view` (developer-only) недостаточно открыт, `create`'s гейт («любой аутентифицированный») — правильный прецедент для НОВОГО эндпоинта, не старый `list`. Фильтр: `resolved_at__isnull=False`. Проекция — ТОЛЬКО `{id, resolved_in_version, resolved_at, resolution_summary}` (переименовано под `FixEntry`-контракт фронта в сериализаторе: `version`/`releasedAt`/`summary`) — `user_id`/`screen_path`/`description`/`last_request_ids` НЕ попадают в проекцию вовсе (не полагаться на «фронт не покажет» — бэк физически не отдаёт).
4. **AC-4 (пагинация — тот же паттерн 13.1a-ревью).** `journal`-эндпоинт использует ту же `LimitOffsetPagination`, что `list` (13.1a-ревью, Blind Hunter — не повторять уже исправленный пробел на новом эндпоинте).
5. **AC-5 (регресс нулевой).** `make gate` зелёный.

## Out of Scope

## Dev Notes

- **`resolve` — НЕ на новом эндпоинте с новым правом.** Зеркалит `bugreports.view`, тот же держатель (DEVELOPER-роль) — это ТА ЖЕ аудитория, что уже видит сырые репорты, разрешение — следующий шаг того же workflow, не отдельная роль.
- **`journal` — гейт по образцу `create`, не `list`.** `create`'s докстринг (13.1a) уже устанавливает паттерн «просто аутентификация, без RBAC-кода» для эндпоинтов, открытых широкой аудитории намеренно — `journal` та же ситуация, зеркалит существующий, не изобретает.
- **`resolution_summary` ≠ `description`.** `description` — сырой ввод ОПЕРАТОРА (мог написать что угодно, включая то, что не должно быть публичным). `resolution_summary` — НОВОЕ поле, которое пишет РАЗРАБОТЧИК на `resolve`, формулируя для публики. Не переиспользовать один текст для обеих аудиторий.

### Completion Notes

- **AC-1**: `resolved_at`(DateTimeField, null)/`resolved_in_version`(CharField)/`resolution_summary`(CharField(500)) на `BugReport`, миграция `0002_...`.
- **AC-2**: `resolve` использует ТОТ ЖЕ `bugreports.view`-гейт, что `list`/`retrieve` (не новый permission-код — та же аудитория). Новый error-code `BUGREPORT_ALREADY_RESOLVED` (409, `docs/registries/error-codes.yaml`) — повторный `resolve` НЕ переписывает поля первого вызова (live-тестом подтверждено: `test_resolve_twice_is_409` проверяет неизменность `resolved_in_version` после второго вызова).
- **AC-3**: `journal` использует гейт `create`'s паттерна («любой аутентифицированный», НЕ RBAC-код) — прямо по выводу research-агента при create-story. Проекция через `BugReportJournalEntrySerializer` — отдельный сериализатор, НЕ переиспользует `BugReportSerializer`'s поля, физически не может отдать `user_id`/`screen_path`/`description`.
- **Найден и исправлен реальный баг СОБСТВЕННЫМ тестом, до отправки на ревью**: изначальная реализация `releasedAt` через `serializers.DateField(source="resolved_at")` упала `AssertionError: Expected a date, but got a datetime` на первом живом прогоне (DRF's `DateField` намеренно отказывается неявно усекать datetime → date — избегает ИМЕННО того класса tz-бага, который эта кодовая база уже несколько раз ловила живыми пробами, memory: «Гвард даты требует минусовой зоны»). Исправлено: `SerializerMethodField` с явной конвертацией через `ZoneInfo(settings.VAPS_LOCAL_TIMEZONE)` — тот же паттерн, что `Clock.today_local()` применяет к «сейчас», применённый здесь к сохранённому моменту `resolved_at`. Голый `.date()` на сыром UTC-aware значении молча выбрал бы НЕПРАВИЛЬНЫЙ календарный день при переходе полуночи между UTC и локальным временем — не гипотетика, а именно тот баг-класс, что уже находили живые пробы в этой сессии.
- **AC-4**: `BugReportPagination` (13.1a) переиспользована для `journal`, не продублирована.
- **AC-5**: `make gate` — 3025 passed (было 2996), `ruff check` чисто, `make schema` без drift на новых путях (`operationId`-коллизий нет — `bugreports_resolve`/`bugreports_journal` уникальны). RBAC-матрица (`test_rbac_matrix.py`) и audit-матрица (`test_audit_coverage.py`) дополнены строками для обоих новых роутов (`bugreport-resolve`/`bugreport-journal`) — `resolve` классифицирован `_DeferredAudit` тем же обоснованием, что `bugreport-list` (13.1a) — строка сама себя аудирует (resolved_at/version/summary уже на записи).

**3-агентное ревью (Blind Hunter, Edge Case Hunter, Acceptance Auditor, параллельно) — Acceptance Auditor подтвердил все 5 AC genuinely satisfied (сам прогнал gate, сам структурно проверил анонимизацию); Blind Hunter + Edge Case Hunter НЕЗАВИСИМО нашли ОДНУ И ТУ ЖЕ HIGH-находку (сильный сигнал реальности), плюс по одной дополнительной каждый:**
- **Blind Hunter + Edge Case Hunter (HIGH, независимо, оба)** — TOCTOU-гонка в `resolve`: `get_object_or_404` + Python-проверка `is not None` + `save()` без `select_for_update`/`transaction.atomic` — два одновременных `resolve`-запроса могли ОБА прочитать `resolved_at=None` до того, как любой из них запишет, и второй `save()` молча переписал бы первый БЕЗ 409 — ровно то, что стори заявляет как защищённое. Оба агента указали на уже установленный в кодовой базе паттерн (`select_for_update()` в `apps/operations/statuses/services/dismissal.py` и др.), который не был применён здесь. **Исправлено**: `@transaction.atomic` + `BugReport.objects.select_for_update()`. **Живая регресс-проба**: новый `@pytest.mark.concurrency`-тест (`test_concurrent_resolve_exactly_one_wins_no_lost_update`) — два реальных потока, два реальных HTTP-запроса, реальная БД — подтверждает РОВНО один 200 + один 409, и запись в БД содержит ИМЕННО версию победителя, не гибрид (тот самый lost-update, который гонка бы произвела). Тест реально прогнан: assertions прошли (`1 passed`); teardown упал на УЖЕ известной, задокументированной проблеме окружения (append-only-триггер `audit_logs` блокирует `flush` для ЛЮБОГО `transaction=True`-теста в этом репо — воспроизведено на существующем прецедентном файле `test_employee_status_concurrency.py`, идентичное поведение «2 passed, 2 errors» — НЕ регресс этой стори).
- **Blind Hunter (MED)** — `journal`'s `order_by("-resolved_at")` без tie-breaker'а — записи, разрешённые в один и тот же тик часов, сортировались бы в порядке, зависящем от БД, что с limit/offset-пагинацией рискует дублями/пропусками между страницами. Исправлено: `order_by("-resolved_at", "-id")`.
- **Blind Hunter (MED)** — тест `releasedAt` проверял только НАЛИЧИЕ ключа, не формат значения — регрессия, вернувшая полный `datetime` вместо `date` (сломав фронтовый `FixEntry.releasedAt: string`-контракт), осталась бы незамеченной. Исправлено: явный regex-пин `\d{4}-\d{2}-\d{2}` через `json.dumps(default=str)` (тот же эффект, что реальный DRF JSON-рендерер для `date`-объектов).
- **Edge Case Hunter (документационная находка, не баг, но реальный landmine для 13.4b)**: `journal` возвращает `{count, next, previous, results}` (limit/offset-конверт), а `frontend/src/features/changelog/changelog.ts`'s `FixEntry[]`/`CLOSED_FIXES` — ГОЛЫЙ массив, без конверта. Несовпадение НЕ было задокументировано нигде для будущей 13.4b — явно зафиксировано здесь (Completion Notes) и будет перенесено в 13.4b's Dev Notes при create-story: фронт обязан читать `.results`, не тело ответа целиком.
- **Edge Case Hunter (проверено, не баг)**: `resolved_in_version`/`resolution_summary` не валидируют ФОРМАТ (только непустоту+длину) — принят как реальный, но приемлемый в скоупе стори пробел (ни один другой эндпоинт в кодовой базе не валидирует форму git-sha).
- Живой ре-прогон после всех фиксов: `apps/operations/bugreports/` — 22 passed (без учёта concurrency-теста, корректно отфильтрован `make gate`'s `not concurrency`) + 1 concurrency-тест passed отдельно (teardown — известная проблема окружения). `make gate` — 3025 passed, 58 deselected (было 57 — новый concurrency-тест корректно исключён).
