## Deferred from: code review of 1-5-минимальная-модель-статуса-с-exclusionconstraint (2026-06-11)

- Маппинг 3.1 «IntegrityError по имени constraint → 409» не покроет deadlock-исход реальной конкурентной гонки: при симметричной гонке двух hard-вставок Postgres может разрешить конфликт через `DeadlockDetected` (Django: `OperationalError`) — имени `excl_hard_status_overlap` в сообщении нет → будет 500 вместо 409. Воспроизведено ревью 1.5 (4 из 5 прогонов конкурентного теста). Стори 3.1 должна осознанно обработать OperationalError/deadlock как конфликтный исход.
- `date_start > date_end` бьёт не в `chk_status_dates`, а в вычисление generated column `period`: PostgreSQL кидает `DataError` (SQLSTATE 22000, «range lower bound must be less than or equal…») ДО проверки CHECK — тоже мимо маппинга 3.1. Сервисная 422-валидация — стори 3.3; маппинг 3.1 учесть DataError-путь.
- «Append-once» `cancelled_at` не охраняется БД: `UPDATE cancelled_at=NULL` (раз-отмена) и правка отменённой записи проходят свободно — комментарий в модели обещает инвариант, которого нет на уровне БД. Механика отмены (cancelled_by/reason, необратимость) — стори 3.6.
- ExclusionConstraint не DEFERRABLE: легитимный swap границ двух соседних hard-статусов одного сотрудника в одной транзакции падает или проходит в зависимости от порядка операторов — скрытый контракт для будущих сервисов редактирования статусов (3.6/E3).
- `XUserIdAuthentication` при отсутствующем/пустом заголовке не устанавливает `request.actor_id` вовсе (ветка else отсутствует) → downstream-код, читающий атрибут, получит AttributeError вместо None/403. Pre-existing (стори 1.2, `apps/core/auth/authentication.py:17-20`); закрыть вместе с JWT (5.1) или при первом downstream-потребителе.
- `status_type_code` — свободный текст до FK 2.2: опечатка/регистр/хвостовой пробел тихо выводит запись из-под exclusion-constraint (условие сравнивает точные литералы); окно мусора до 2.2 ограничено тем, что пишут только тесты и импорт 1.6. Закрывается FK + seed-тестом 2.2.
