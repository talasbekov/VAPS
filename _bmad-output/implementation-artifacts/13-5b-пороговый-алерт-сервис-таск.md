# Story 13.5b: Пороговый алерт — сервис + Celery-таск

Status: ready-for-dev

## Story

As a **разработчик**,
I want **интрадей-проверку «доля сдавших управлений < порога к настраиваемому часу» с эмиссией `SUBMISSION_THRESHOLD_ALERT`**,
so that **раздражение (никто не заметил массового отставания в течение дня) ловится ДО конца дня, не следующим утром**.

Вторая треть буквы стори 13.5 (эпик 13, `epics.md#L1380-1387`). Модельный фундамент (13.5a — `alert_hour`/`alert_threshold_pct` на `SubmissionControlSettings`, `Notification.Kind.SUBMISSION_THRESHOLD_ALERT`) уже done. Эта стори — детекция + эмиссия + beat-регистрация. «Пульс пилота» (ежедневная сводка) — отдельная стори 13.5c.

## Acceptance Criteria

1. **AC-1 (сервис детекции).** Новая функция `check_submission_threshold(*, today=None)` в `apps/operations/submissions/services/threshold_check.py`: читает `SubmissionControlSettingsSelector.required_division_ids()`/`.alert_hour()`/`.alert_threshold_pct()`, считает долю `required_division_ids`, у которых ЕСТЬ текущая сдача на сегодня (`DailySubmissionSelector.current_for_many`), и — если сейчас (`Clock.now()`, местное время) ≥ `alert_hour` И доля < `alert_threshold_pct` — эмиттирует ОДИН `Notification.Kind.SUBMISSION_THRESHOLD_ALERT` через `notify()` на `default_notify_recipient`.
2. **AC-2 (пустой список необходимых управлений — не алерт).** Если `required_division_ids()` пуст — функция НИЧЕГО не делает (нет требования — нет отставания; зеркалит `_emit_lagging`'s `if not laggards: return 0` в духе, не порождает алерт про 0-из-0).
3. **AC-3 (час-гейт — до `alert_hour` тихо).** До наступления `alert_hour` (местное время) — функция не эмиттирует и не читает состояние сдач (ранний возврат, зеркалит `lagging_check`'s control-hour gate стиль, но БЕЗ watermark/catch-up — это ИНТРАДЕЙ-проверка одного дня, не многодневный catch-up).
4. **AC-4 (идемпотентность — «одно в день» БЕСПЛАТНО от `notify()`).** Повторные вызовы `check_submission_threshold` в течение того же дня (после того, как алерт уже сработал) — НЕ создают вторую запись: `notify()`'s `get_or_create` на `(recipient, kind, business_date)` (13.5a's Dev Notes уже это отметили как готовый механизм) делает повторный вызов no-op. Никакого своего watermark/lock эта стори НЕ изобретает.
5. **AC-5 (пустой `default_notify_recipient` — лог+skip, не исключение).** Если `default_notify_recipient` пуст (`""`) — попытка алерта логируется и МОЛЧА пропускается (`notify()` иначе бросит `ValueError` на пустой recipient — эта стори обязана гейтовать ДО вызова `notify()`, зеркалит `_emit_lagging`'s «нет получателя → лог + skip» для НЕ-резолвящихся дивизионов).
6. **AC-6 (Celery-таск + beat-регистрация).** `apps/operations/submissions/tasks.py` получает `check_submission_threshold_task` (`@shared_task`, зеркалит `check_lagging_submissions_task`'s bare-call стиль), зарегистрированный в `config/settings.py`'s `CELERY_BEAT_SCHEDULE` — периодически (не раз в сутки ночью, как lagging — это ИНТРАДЕЙ, `crontab(minute="*/15", hour="8-19")`, чтобы не спамить всю ночь и не создавать нагрузку впустую до рабочего дня; повторные срабатывания после первого алерта — бесплатные no-op благодаря AC-4).
7. **AC-7 (payload — доля и счётчики, для будущего UI/диагностики).** `notify()`'s `payload` несёт `{"required_count": N, "submitted_count": M, "threshold_pct": P}` — достаточно для читателя уведомления понять КАКОЙ была нехватка, не только факт «отставание».
8. **AC-8 (регресс нулевой).** `pytest apps/operations/submissions apps/notifications apps/core/tests/test_celery_tasks.py` — все существующие тесты зелёные.

## Out of Scope

- «Пульс пилота» (ежедневная сводка разработчику) — **13.5c**, отдельная ответственность/триггер/агрегация.
- API/RBAC-экран для просмотра/настройки этих алертов — буква стори не просит экран, Admin уже покрывает настройки (13.5a).
- Per-division нотификации о том, КАКИЕ конкретно управления не сдали (это уже делает `SUBMISSION_LAGGING`/`lagging_check.py` на СЛЕДУЮЩЕЕ утро для полного отсутствия) — этот алерт агрегатный («половина»), не поимённый список.
- Фронтовое отображение нового вида уведомления (иконка/текст в `NotificationBell.tsx`) — `NOTIFICATION_KIND_LABELS`-карта уже документированно частичная с фолбэком на сырой код (13.5a-ревью, Edge Case Hunter подтвердил: не пробел, дизайн-решение) — эта стори НЕ обязана добавлять туда запись.

## Dev Notes

- **Модельный фундамент уже есть (13.5a, done).** `SubmissionControlSettingsSelector.alert_hour()`/`.alert_threshold_pct()`/`.required_division_ids()` читаются напрямую — НЕ изобретать параллельные поля. `Notification.Kind.SUBMISSION_THRESHOLD_ALERT` уже существует и зарегистрирован в `docs/registries/ws-message-types.yaml`.
- **Источник «кто сдал сегодня» — `DailySubmissionSelector.current_for_many(division_ids, business_date) -> dict`** (`apps/operations/submissions/selectors.py:74-90`) — уже существующий bulk-селектор (одна БД-строка на дивизион с ОДНИМ запросом, NFR-4). Дивизион ОТСУТСТВУЕТ в результате ⇔ не сдал. `len(current_for_many(required, today))` — «сколько сдало» напрямую, без доп. запросов.
- **Recipient — ОДИН `default_notify_recipient`, НЕ per-division `NotifyRecipientSelector`.** Буква стори говорит «уведомление ОТВЕТСТВЕННОМУ/разработчику» (единственное число, про АГРЕГАТНОЕ состояние), а не «каждому лагающему дивизиону своё уведомление» (это уже делает `SUBMISSION_LAGGING`/`lagging_check.py`). `NotifyRecipientSelector.resolve_many` — НЕ подходящий примитив здесь, он резолвит recipient ПО дивизиону, а этот алерт — один на весь чек.
- **Идемпотентность — НЕ watermark, а голый `notify()`'s `get_or_create`.** В отличие от `lagging_check.py`'s многодневного catch-up (свой watermark-ключ, advisory lock, per-day транзакции — обрабатывает ПРОШЕДШИЕ дни после простоя), эта проверка — ОДИН день, ОДНО «уже было» через существующий `UniqueConstraint(recipient, kind, business_date)` на `Notification`. Час-гейт (AC-3) даже не многодневный — просто «слишком рано СЕГОДНЯ», без концепции пропущенных дней. НЕ копировать watermark/lock-инфраструктуру `lagging_check.py` — она здесь не нужна и добавит сложность без пользы (over-engineering).
- **`notify()`'s `ValueError` на пустой recipient — гейтовать ДО вызова, не ловить исключение.** `apps/notifications/services.py:170-171`: `if not recipient or not recipient.strip(): raise ValueError`. `_emit_lagging`'s паттерн (per-division «нет получателя → лог + continue») — зеркалить ПРОВЕРКУ, а не try/except вокруг `notify()`.
- **Beat cadence — обоснование `*/15 8-19`, не «раз в сутки».** `lagging_check`'s ночной beat (01:45) проверяет ПРОШЕДШИЙ день ПОСЛЕ его `control_hour` — одного прогона достаточно. Эта проверка — ИНТРАДЕЙ («к 15:30» — конкретный час В ТЕЧЕНИЕ дня), а `alert_hour` конфигурируем (Admin может сдвинуть на любой час) → фиксированный ЕДИНСТВЕННЫЙ crontab-час не отследил бы правку конфига без деплоя. Периодический прогон с внутренним час-гейтом (AC-3) решает это дёшево: repeated no-op до/после первого срабатывания (AC-4) делает частый прогон безопасным. `8-19` — не всю ночь, разумные рабочие часы (буква не уточняет диапазон — это инженерное решение реализации, не открытый вопрос).
- **Тестовое время — НЕ `datetime.now()`.** Как и `lagging_check.py`, тесты обязаны передавать `today`/мокать `Clock.now()`/`Clock.today_local()` явно (`apps/core/tests/test_isolation.py`'s wall-clock deny-list гвард это enforce'ит на уровне AST — прямой вызов `datetime.now()`/`timezone.now()` внутри `apps.operations.submissions` красным упадёт).
