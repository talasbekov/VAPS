# Story 16.6c: Эскалация неподтверждённого ознакомления (FR-27, часть 3/4)

Status: done

## Story

As a **старший мероприятия**,
I want **узнать, что кто-то из назначенных не подтвердил ознакомление, пока событие ещё не началось**,
so that **я могу вмешаться до начала, а не постфактум (FR-27, `docs/registries/ws-message-types.yaml::ACK_MISSING_ESCALATION`)**.

## Scope Decision (найдено при create-story)

- **Часть 3/4 расщепления Story 16.6.** 16.6a (done) — уведомление `ASSIGNMENT_APPROVED`. 16.6b (done) — сама отметка (`acknowledge_placement_assignment()`). Эта стори — `ACK_MISSING_ESCALATION` (эскалация старшему при близком начале события и всё ещё отсутствующем ознакомлении). **`ACK_REQUIRED` (периодическое напоминание, `repeat: "every 2h until ack during event prep"`) — НАМЕРЕННО НЕ эта стори, найдено критическое архитектурное расхождение при проектировании (см. ниже) — вынесено в отдельную будущую стори 16.6e.**
- **КРИТИЧЕСКАЯ находка: `ACK_REQUIRED`'s заявленная периодичность («каждые 2 часа») структурно НЕСОВМЕСТИМА с `notify()`'s существующим контрактом без нового решения, не изобретаемого здесь.** `notify()`'s идемпотентность — `(recipient, kind, business_date)`, «один раз в день», «первый payload побеждает» (буквальный контракт, никем не переоткрывается со Story 5.7a). Честная реализация «каждые 2 часа» потребовала бы ЛИБО (a) нового bypass-механизма дедупликации специально для этого вида уведомлений (не установлено нигде в проекте — единственный прецедент многократной отправки за день, `escalate_stale_force_requests()`'s `select_for_update()`+мердж-в-существующую-строку, всё равно производит РОВНО ОДНУ видимую получателю строку в день, не «каждые 2 часа»-эффект), ЛИБО (b) молчаливого сужения до «один раз в день» вопреки прямому тексту `ws-message-types.yaml`. Ни один вариант не решается без явного архитектурного решения — вынесено целиком, не эта стори. `ACK_MISSING_ESCALATION` («once» — repeat: «once», буквально) СОВМЕСТИМ с существующим контрактом БЕЗ этой проблемы — единственная причина, почему эта стори делает ТОЛЬКО эскалацию.
- **Буквальный образец — `escalate_stale_force_requests()` (15.10, `apps/operations/events/services.py`).** Та же форма: находит «протухшие» строки (здесь — `PlacementAssignment` с `acknowledged_at IS NULL`, `ack_escalated_at IS NULL`, событие «скоро начнётся»), помечает `ack_escalated_at` (НОВОЕ поле — по образцу `GroupForceRequest.escalated_at`, идемпотентность батча: повторный прогон не переэскалирует уже помеченные строки), группирует по получателю (здесь — `event.senior_employee_id`, резолвится через 16.6a's `CoreEmployeeSelector.user_ids_for()`), один `notify()`-дайджест на получателя в день с мерж-в-существующую-строку при повторном прогоне В ТОТ ЖЕ день (буквально тот же `select_for_update()`-приём, что 15.10, не изобретается заново). «Beat-ready, NOT Celery» — та же формулировка, что 15.10's докстринг: ноль Celery-импортов, будущая стори оборачивает в `@shared_task`.
- **Новый порог «близко начало события» — `VAPS_ACK_ESCALATION_HOURS_BEFORE_EVENT`, PROVISIONAL, env-overridable.** Тот же паттерн, что `VAPS_FORCE_REQUEST_ESCALATION_DAYS` (15.10): grep `_bmad-output/planning-artifacts/architecture.md` за «близко начало» — НЕ находит зафиксированного значения (открытый вопрос продукту, не блокирует), дефолт — разумное conservative значение (4 часа), исправимо без правки кода.
- **Эскалация — ТОЛЬКО для события, которое ЕЩЁ НЕ началось** (`event.starts_at > Clock.now()`) — эскалировать «скоро начнётся» уже начавшееся/прошедшее событие бессмысленно (тот же принцип фильтрации по «живому» окну, что 15.10's `updated_at__lt=threshold` фильтрует только ещё актуальные запросы).
- **Новый `Notification.Kind.ACK_MISSING_ESCALATION` + миграция.** Тот же приём, что 16.6a's `ASSIGNMENT_APPROVED` — Python-choice + SQL `CheckConstraint` в одной миграции.
- **Только `PlacementAssignment` ТЕКУЩЕЙ (`version.is_current=True`) `APPROVED`-версии учитывается.** Назначение неутверждённой/невыбранной версии не может быть «неподтверждённым ознакомлением» в смысле FR-27 — ознакомление логически применимо только к утверждённой действующей расстановке (тот же вывод, что 16.6b's Scope Decision про `acknowledged_at`).

## Acceptance Criteria

1. **AC-1 (эскалация при близком событии, ознакомление отсутствует).** `PlacementAssignment` текущей `APPROVED`-версии, `acknowledged_at IS NULL`, `event.starts_at` в пределах `VAPS_ACK_ESCALATION_HOURS_BEFORE_EVENT` часов от `Clock.now()` (и ещё не наступило) — помечается `ack_escalated_at`, старший (если есть привязка аккаунта) получает `ACK_MISSING_ESCALATION`-уведомление.
2. **AC-2 (событие ещё далеко — не эскалируется).** `event.starts_at` дальше порога — строка НЕ помечается, уведомление не отправляется.
3. **AC-3 (уже подтверждено — не эскалируется).** `acknowledged_at IS NOT NULL` — строка исключается из выборки (уже не «неподтверждённое»).
4. **AC-4 (уже эскалировано — не повторяется).** `ack_escalated_at IS NOT NULL` — строка НЕ переэскалируется повторным прогоном (идемпотентность батча, тот же принцип, что `GroupForceRequest.escalated_at`).
5. **AC-5 (нет старшего/нет привязки — пометка есть, уведомления нет).** `event.senior_employee_id is None` ИЛИ у старшего нет `UserEmployeeBinding` — `ack_escalated_at` ВСЁ РАВНО ставится (batch-идемпотентность не зависит от успеха уведомления), но `notify()` не вызывается (нет получателя).
6. **AC-6 (дайджест — несколько неподтверждённых одного события/старшего — одно уведомление).** 2+ `PlacementAssignment`-строки ОДНОГО события с отсутствующим ознакомлением — старший получает РОВНО одно `ACK_MISSING_ESCALATION`-уведомление за прогон (не по строке).
7. **AC-7 (второй прогон в тот же день — мерж, не потеря).** Первый прогон эскалирует событие A (создаёт `Notification`-строку старшего за день); второй прогон В ТОТ ЖЕ день эскалирует НОВОЕ событие B того же старшего — второй payload МЕРЖИТСЯ в существующую строку (не теряется через `notify()`'s «первый payload побеждает», буквально образец 15.10's мердж-приём).
8. **AC-8 (регресс нулевой).** `make gate` зелёный; миграция — новое поле `ack_escalated_at` на `PlacementAssignment` + новый `Notification.Kind.ACK_MISSING_ESCALATION`.

## Out of Scope

- **`ACK_REQUIRED`-периодическое напоминание («every 2h until ack»)** — Story 16.6e (новая, требует отдельного архитектурного решения про несовместимость с `notify()`'s daily-dedup-контрактом, см. Scope Decision).
- **Celery-обвязка/`@shared_task`/beat-расписание** — не эта стори, тот же вывод, что 15.10's «Beat-ready, NOT Celery».
- **API/HTTP-обёртка (ручной запуск эскалации)** — Story 16.8.
- **Снятие/отмена уже проставленной `ack_escalated_at`** при последующем подтверждении — не требуется (эскалация — исторический факт «была отправлена», не текущий статус; `acknowledged_at`, если появится ПОСЛЕ эскалации, читается отдельно, не связано).
- **Учёт `ACK_MISSING_ESCALATION` в конфликт-детекторе (16.3b-d)** — не требуется, разные механизмы (SOFT-конфликты vs эскалация ознакомления).
