# Story 15.3c: `POST /security-events/{id}/recon/confirm` — двойной контроль + переход в RECON (FR-22)

Status: done

## Story

As a **старший оператор, подтверждающий рекогносцировку**,
I want **подтвердить прохождение рекогносцировки ДВУМЯ разными акторами перед переводом ОМ в `RECON`**,
so that **переход контролируется вторым независимым подтверждением (двойной контроль, FR-22), а не одним оператором единолично**.

## Scope Decision (найдено при create-story)

- **Последняя часть разбитого `15-3`** (15.3a — модели done, 15.3b — захват данных done, эта стори — двойной контроль + переход).
- **«Двойной контроль» (dual control) — НИГДЕ в кодбейзе нет прецедента** (личный грep: `двойн`/`dual_control`/`second_approv` — только нерелевантные совпадения про «режим без двойного ввода», Story 7.7, другая тема). Это НОВЫЙ паттерн для FR-22, синтезируется с нуля.
- **Модель двойного контроля — два РАЗНЫХ actor'а должны вызвать один и тот же эндпоинт.** Первый вызов записывает подтверждение (кто, когда) и возвращает 202 (принято, ждёт второго). Второй вызов ОТ ДРУГОГО actor'а завершает переход в `RECON` и аудирует. Вызов ТЕМ ЖЕ actor'ом повторно — 422 (`INVALID_LIFECYCLE_TRANSITION`, при имплементации переиспользован тот же код, не отдельный 409 — консистентность с 15.2b's единственным зарегистрированным конфликт-кодом важнее семантической точности статуса; см. Dev Agent Record).
- **Два новых nullable-поля на `SecurityEvent`** (`recon_first_confirmed_by` — flat actor-id, `recon_first_confirmed_at` — datetime): минимальное хранилище для однократного «первого подтверждения». НЕ отдельная модель (избыточно для двух полей, тот же выбор простоты, что везде в этом приложении).
- **Транзит СТРОГО из `BULLETIN`.** Симметрично 15.2b's `DRAFT`→`BULLETIN`-гейту: `RECON` — следующий шаг ПОСЛЕ `BULLETIN` в линейном цикле. Вызов из `DRAFT` или любого пост-`RECON`-статуса — `INVALID_LIFECYCLE_TRANSITION` (422, тот же переиспользуемый код).
- **«Обновление Паспорта» — ЯВНО ВНЕ ОБЪЁМА этой стори, зафиксировано как открытый вопрос.** Никакой конкретики о ТОМ, какие поля `ObjectPassport` (14.1) должны обновляться при завершении рекогносцировки, нигде не найдено (ни в epics.md, ни в architecture.md, ни во frontend-прототипе). Изобретать произвольную запись в чужую модель без спеки — прямой путь к неверному допущению (тот же принцип осторожности, что 15.1's «донор недоступен → PROVISIONAL, не выдумывать»). Открытый вопрос для будущей стори, когда появится конкретика (донор-спека или явное решение продукта).
- **Аудит — на реальном переходе (второе подтверждение), не на первом.** Первое подтверждение — промежуточное состояние (тот же принцип, что 15.3b's deferred-audit для черновиков), финальный переход — реальное бизнес-событие.

## Acceptance Criteria

1. **AC-1 (первое подтверждение).** `POST /security-events/{id}/recon/confirm` на ОМ в `BULLETIN`, ещё без подтверждений → 202, `recon_first_confirmed_by`/`_at` записаны, статус НЕ меняется.
2. **AC-2 (второе подтверждение другим actor'ом завершает переход).** Тот же эндпоинт, ДРУГИМ actor'ом → 200, `status_code` становится `RECON`, `recon_first_confirmed_by/_at` очищаются (использованы).
3. **AC-3 (тот же actor дважды — 422).** Повторный вызов ТЕМ ЖЕ actor'ом, что уже подтвердил первым → 422 (нельзя быть обоими подтверждающими; при имплементации выбран тот же переиспользуемый `INVALID_LIFECYCLE_TRANSITION`, не отдельный 409 — см. Dev Agent Record).
4. **AC-4 (конфликт статуса).** Вызов на ОМ не в `BULLETIN`/`RECON` → 422 (`INVALID_LIFECYCLE_TRANSITION`).
5. **AC-5 (идемпотентность на уже-RECON).** Повторный вызов на уже-`RECON` ОМ (любым actor'ом) → 200, no-op, без повторного аудита.
6. **AC-6 (аудит + реестры + гейт).** `SECURITY_EVENT_RECON_CONFIRMED` пишется ТОЛЬКО на реальном переходе (второе подтверждение); `AUDIT_MATRIX`+RBAC `MATRIX` — обе новые записи; `make gate` зелёный.

## Out of Scope

- Обновление `ObjectPassport` — открытый вопрос, нет спеки (см. Scope Decision). Будущая стори.
- Проверка «чек-лист/пересчёт заполнены» перед подтверждением — не запрошено FR-22 буквально, донор-спека недоступна для уточнения обязательности.
- Отмена первого подтверждения (например, если первый confirmer передумал) — не запрошено, будущая стори при необходимости.
