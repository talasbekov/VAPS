# Story 15.2b: `POST /api/operations/security-events/{id}/bulletin` — выпуск бюллетеня (FR-21)

Status: ready-for-dev

## Story

As a **оператор, управляющий охранными мероприятиями**,
I want **перевести ОМ из `DRAFT` в `BULLETIN`**,
so that **ОМ считается официально объявленным и Story 15.3 (рекогносцировка) может начаться**.

## Scope Decision (найдено при create-story)

- **Вторая половина разбитого планового `15-2`** (15.2a — создание+Старший, уже done; эта стори — переход статуса). См. 15.2a's Scope Decision для полного обоснования разбиения.
- **«Бюллетень» — единственный найденный источник: `SecurityEvent.StatusCode.BULLETIN`** (15.1's enum-значение, «Бюллетень выпущен»). Никакой отдельной спеки/документа/PDF-генерации нигде не найдено (research-агент подтвердил при 15.2a's research). Эта стори реализует ИМЕННО статус-переход `DRAFT`→`BULLETIN`, не документ-генерацию.
- **Транзит СТРОГО из `DRAFT`.** В отличие от `approve_duty_plan()` (14.11c/14.12a, permissive — любой не-`APPROVED` статус трактуется как «черновик» и переводится), здесь выбран строгий гейт: бюллетень можно выпустить ТОЛЬКО из `DRAFT`. Обоснование: `BULLETIN` — первый шаг ПОСЛЕ `DRAFT` в 10-значном линейном цикле (15.1's enum), не терминальное/повторно-достижимое состояние вроде `APPROVED` у `DutyPlan` (которое не продолжает свой цикл дальше). Повторный вызов на уже-`BULLETIN` — идемпотентный no-op (200, статус не меняется, аудит не дублируется, тот же паттерн `was_draft`-гварда, что 14.12a). Вызов из ЛЮБОГО другого статуса (`RECON`+) — `DomainError` 409 (конфликт состояния, тот же паттерн, что project's IntegrityError→422/DomainError→4xx backstop).
- **Паттерн — `services.py`-функция + тонкий view-`@action`**, буквальный образец `approve_duty_plan()`/`DutyPlanViewSet.approve()` (14.11c/14.12a): `select_for_update()`-блокировка внутри `transaction.atomic()`, `actor`-непустой-гвард, идемпотентный no-op без дублирующего аудита, `record()` внутри той же транзакции.
- **Новый `services.py`-файл в `apps/operations/events/`** (первый для этого приложения — 15.2a не завёл его, т.к. create/list не нуждались в отдельном сервисе, тот же выбор, что duty-plan create/list). Функция `issue_bulletin(event, *, actor)`.
- **Permission — переиспользуется `event.manage`** (тот же код, что 15.2a — единый гейт на весь `SecurityEventViewSet`, тот же паттерн, что `duty.manage` покрывает весь `DutyPlanViewSet`).
- **Роут — вложенный `@action(detail=True)`** на существующем `SecurityEventViewSet`, `url_path="bulletin"` → `POST /api/operations/security-events/{id}/bulletin`, зеркалит `DutyPlanViewSet.approve()`'s форму (`@action(detail=True, methods=["post"])`).

## Acceptance Criteria

1. **AC-1 (успешный переход).** `POST /api/operations/security-events/{id}/bulletin` на ОМ в `DRAFT` → 200, `status_code` становится `BULLETIN`.
2. **AC-2 (идемпотентность).** Повторный вызов на уже-`BULLETIN` ОМ → 200, статус не меняется, второй `AuditLog`-строки НЕ создаётся.
3. **AC-3 (конфликт состояния).** Вызов на ОМ в статусе, отличном от `DRAFT`/`BULLETIN` (например, искусственно выставленном `RECON`) → 409, статус не меняется.
4. **AC-4 (permission).** Требует `event.manage` — без него 403.
5. **AC-5 (аудит).** Реальный переход (AC-1) пишет `AuditLog` (`action="SECURITY_EVENT_BULLETIN_ISSUED"`, `entity_type="security_event"`, `entity_id=uuid.UUID(int=event.pk)`) в той же транзакции; idempotent-повтор (AC-2) НЕ пишет вторую строку.
6. **AC-6 (регресс нулевой).** `make gate` зелёный, включая route-классификацию в обеих живых матрицах (audit + RBAC).

## Out of Scope

- Рекогносцировка (`DRAFT`/`BULLETIN`→`RECON`) — Story 15.3.
- Любая генерация документа/PDF для «бюллетеня» — не найдено требования, не эта стори (см. Scope Decision).
- Retrieve отдельного ОМ по id (для проверки текущего статуса перед вызовом) — клиент полагается на 15.2a's list-ответ; отдельный GET detail — будущая стори при необходимости.
