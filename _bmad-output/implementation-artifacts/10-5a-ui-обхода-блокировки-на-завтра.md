# Story 10.5a: UI обхода блокировки «на завтра»

Status: ready-for-dev

## Story

As a **руководитель с правом `daily_report.override_block`**,
I want **на экране `/reports`, когда выпуск расхода на будущую дату заблокирован (422 `TOMORROW_BLOCKED`), иметь кнопку легального обхода с обязательной причиной**,
so that **я могу выпустить расход на завтра ДО того, как все сдали, не дожидаясь конца дня, и это решение осталось в системе с моим именем и обоснованием**.

## Acceptance Criteria

Источник: `_bmad-output/implementation-artifacts/sprint-status.yaml:382-385` (вынесено из скоупа 10.5 create-story 2026-07-19) и докстринг `frontend/src/features/expense/ExpenseReportPage.tsx:26-31` («Обход блокировки „на завтра“ — стори **10.5a**... Экран здесь только ОБЪЯСНЯЕТ блокировку»).

1. **AC-1 (кнопка обхода видна только держателю права).** Given блок `tomorrow-blocked` (422 `TOMORROW_BLOCKED`) уже рендерится (`ExpenseReportPage.tsx:306-326`), When актор ДЕРЖИТ `daily_report.override_block` (`hasPermission`, ARCH-FE-010, тот же паттерн, что `canAmend` в `DaySubmissionPanel.tsx:250`), Then внутри блока видна кнопка «Обойти блокировку». Given права НЕТ (или `['me']` ещё не загружен), Then кнопки НЕТ — сервер всё равно перепроверит (AC-6), фронтовый гейт — удобство, не единственная защита.
2. **AC-2 (форма — причина, без модалки).** Клик по кнопке открывает ИНЛАЙН-форму (Решение №2 стори 10.3/10.6 — модальность в jsdom не эмулируется) с ОДНИМ полем «Причина» (textarea, обязательное — пустое/пробельное блокирует кнопку отправки клиентски, DRF всё равно отклонит пустое 400 на сервере) и кнопкой «Подтвердить обход».
3. **AC-3 (тело POST — РОВНО `{business_date, reason}`).** Given форма отправлена, Then уходит РОВНО ОДИН `POST /api/operations/expense-reports/override-tomorrow-block/` с телом `{business_date: <дата экрана>, reason: reason.trim()}` — БЕЗ `division_id` (обход **day-level**, не per-division, см. `views.py:458-518` — `override_tomorrow_block` не принимает division вовсе) и без актора (сервер берёт `request.actor_id`).
4. **AC-4 (успех → подтверждение + подсказка повторить выпуск).** Given 201 `{business_date, overridden_by, reason}`, Then форма закрывается, показывается подтверждение «Обход подтверждён: {overridden_by}, {reason}» (дословно из ответа — не пересказ формы), и текст-подсказка «Нажмите «Сформировать» ещё раз» — экран НЕ ретраит выпуск автоматически (это ДВА разных действия разных прав/эндпоинтов, авто-ретрай замаскировал бы, что оператор должен нажать «Сформировать» снова осознанно).
5. **AC-5 (409 уже обойдено → инлайн, форма не закрывается тупиком).** Given `TOMORROW_BLOCK_ALREADY_OVERRIDDEN` (409), Then инлайн-сообщение «Обход на эту дату уже существует» — форма остаётся открытой с введённой причиной (не тупик, RBAC/E10.6-урок: отказ формы не должен требовать перепечатки).
6. **AC-6 (403 → сервер — источник истины, не фронтовый гейт).** Given актор ДЕРЖИТ право по `['me']`, но сервер всё равно отдаёт 403 (гонка ревокации, TTL кэша `['me']`), Then инлайн «Нет права на обход блокировки» — экран не падает, AC-1's клиентский гейт НЕ единственная защита (тот же принцип, что 10.3b AC-8: сервер решает, фронт удобство).
7. **AC-7 (400 → форма остаётся открытой с ошибкой).** Given 400 (дата не в будущем / дальше +31д / пустая причина, отфильтрованная гонкой формы), Then инлайн-текст ИЗ ОТВЕТА (`error.message`), форма НЕ закрывается.
8. **AC-8 (регресс нулевой).** Существующий рендер блока `tomorrow-blocked` (заголовок, `failure.message`, список `laggards` с фолбэком на UUID) — без изменений. Кнопка «Сформировать»/`issue`-мутация — без изменений (обход и повторный выпуск — раздельные действия, AC-4). `npm run gate` зелёный.

## Dev Notes

- **Backend УЖЕ существует, роут НЕ создаётся этой стори.** `POST /api/operations/expense-reports/override-tomorrow-block/` (`Backend/VAPS/apps/operations/submissions/api/views.py:452-518`, из стори 6.10b) — сериализатор `TomorrowBlockOverrideSerializer` (`{business_date, reason}`, оба обязательны), право `daily_report.override_block` (`_OVERRIDE_PERMISSION`), горизонт `MAX_OVERRIDE_HORIZON_DAYS = 31`. Схема (`schema.d.ts:941,1860,1865`) уже содержит и `TomorrowBlockOverrideRequest`, и `TomorrowBlockOverrideResponse` — регенерация схемы НЕ требуется, это чисто фронтовая стори.
- **День-level, не per-division — НЕ ошибка, а контракт.** `override_tomorrow_block` не принимает `division_id` вовсе (`views.py` сигнатура: `business_date, actor, reason`) — обход снимает блок на ВЕСЬ день целиком, для всех подразделений. Тело `{business_date, reason}` строго БЕЗ `division_id` — если дев-агент добавит `division_id` "по аналогии" с `issue.mutate({division_id, business_date})` (строка 269 того же файла) — это баг, AC-3 его ловит.
- **Почему НЕ `useApiMutation.conflict`/`ConflictDialog` (ARCH-FE-015, урок 10.5/10.6).** `TOMORROW_BLOCKED` — 422, НЕ 409 overridable; `conflict`-стейт `useApiMutation` поднимается только на 409 с кодом из `OVERRIDABLE_CODES`. Обход — ОТДЕЛЬНЫЙ эндпоинт с ОТДЕЛЬНЫМ телом (`{business_date, reason}`, не `{override, override_reason}` retry исходной мутации). Свой инлайн-диалог причины — легален (прецедент `DayAmendmentForm`, ARCH-FE-015 запрещает свои OVERRIDE-диалоги оверрайд-паттерна 8.5, но не формы причины на независимом пути).
- **Почему БЕЗ автоматического повтора выпуска после успешного обхода (AC-4).** Обход и выпуск — РАЗНЫЕ права (`daily_report.override_block` vs `daily_report.generate`), разные эндпоинты, разная семантика (один снимает орг-wide блок, другой создаёт документ ЗА ОДНО подразделение). Авторетрай `issue.mutate()` из `onSuccess` обхода замаскировал бы двухшаговость под одно действие и мог бы выпустить документ с правом, которого у актора для ВЫПУСКА нет (обход ≠ генерация).
- **`overridden`-стейт — ARCH-FE-010-легальное исключение, не второй источник истины.** Как `submitted`/`amended` в `DaySubmissionPanel.tsx` — «результат последнего действия» для мгновенного фидбека, а не пересказ серверных данных (обход не читается GET'ом нигде — `TomorrowBlockOverride`-модель не выставлена в списочный роут, только создаётся).
- **Красная проба ОБЯЗАТЕЛЬНА (память `feedback_redundant_guards_vacuous_probe`, прецедент 10.3b).** Кнопка «Обойти блокировку» рендерится ВНУТРИ уже существующего `tomorrow-blocked`-блока — классическое место, где новый гард может случайно связаться со старым (например, `overriding` по ошибке спрятал бы весь блок вместо только кнопки/формы). AC-8's тест — не опция.
