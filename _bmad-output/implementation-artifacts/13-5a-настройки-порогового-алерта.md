# Story 13.5a: Настройки порогового алерта

Status: ready-for-dev

## Story

As a **разработчик**,
I want **конфигурируемые порог/час интрадей-алерта на `SubmissionControlSettings` и новый вид уведомления `SUBMISSION_THRESHOLD_ALERT` на `Notification`**,
so that **13.5b (сервис+таск) и 13.5c (пульс пилота) имеют модельный фундамент, не изобретая свой на лету**.

Первая треть буквы стори 13.5 (эпик 13, `epics.md#L1380-1387`): «Given половина необходимых управлений не сдала к 15:30, Then уведомление ответственному/разработчику; пороги — настройки». Эта стори — ТОЛЬКО модельный слой (новые поля настроек + новый вид уведомления); детекция/эмиссия — 13.5b.

## Acceptance Criteria

1. **AC-1 (новые поля на `SubmissionControlSettings`).** `alert_hour` (`TimeField`, дефолт `time(15, 30)` — буква стори называет 15:30 конкретно, но поле конфигурируемо, не хардкод) и `alert_threshold_pct` (`PositiveSmallIntegerField`, дефолт `50` — «половина») добавлены к singleton-модели (`apps/operations/submissions/models/control_settings.py`), НЕ переиспользуют существующий `control_hour` (тот — час полной блокировки/lagging-catch-up, семантически другой контроль, 5.7b2 уже владеет им).
2. **AC-2 (DB-инвариант порога — CheckConstraint, не приложение).** `alert_threshold_pct` ограничен `[1, 100]` на уровне БД (`CheckConstraint`) — 0% или значение >100% бессмысленны и не должны существовать даже при обходе валидации (`bulk_create`/`.objects.create()` не гонят `full_clean()`, урок `[[feedback_vaps_db_integrity_checks]]`).
3. **AC-3 (новый вид уведомления, DB-CHECK синхронен с `Kind`).** `Notification.Kind.SUBMISSION_THRESHOLD_ALERT = "SUBMISSION_THRESHOLD_ALERT"` добавлен, `chk_notification_kind`'s `CheckConstraint` расширен на новое значение — `test_kind_check_covers_kind_choices` (существующий drift-тест, `apps/notifications/tests/test_notify.py:36`) остаётся зелёным и ДОКАЗЫВАЕТ синхронность (не переписывается на новый список вручную мимо теста).
4. **AC-4 (селектор читает новые поля).** `SubmissionControlSettingsSelector` получает `alert_hour()`/`alert_threshold_pct()` — зеркалит существующие `control_hour()`/`required_division_ids()` (`apps/operations/submissions/selectors.py:154-176`), той же сигнатуры (classmethod, без аргументов, без кеша).
5. **AC-5 (миграции — раздельные приложения).** Две миграции: одна в `apps.operations.submissions` (новые поля + CheckConstraint), одна в `apps.notifications` (расширенный `chk_notification_kind`) — не одна общая, приложения раздельные (Django ORM это и не позволил бы одной миграцией).
6. **AC-6 (регресс нулевой).** `pytest apps/operations/submissions apps/notifications` — все существующие тесты зелёные, включая `test_kind_check_covers_kind_choices` и любые существующие тесты на `SubmissionControlSettings`/`SubmissionControlSettingsSelector`.

## Out of Scope

- Сама детекция «половина не сдала» и эмиссия уведомления — **13.5b** (сервис+Celery-таск+beat-регистрация). Эта стори НЕ пишет никакой бизнес-логики порога, только модель+селектор.
- «Пульс пилота» (ежедневная сводка) — **13.5c**, отдельная ответственность (другой триггер, другая агрегация, вероятно свой вид уведомления).
- API/RBAC для чтения/правки этих настроек оператором — буква стори не просит экран настроек; `SubmissionControlSettings` уже Admin-editable (`admin.py`, комментарий модели L16 «once Admin lands in 2.8» — Admin уже есть).
- Изменение существующего `control_hour`/`required_division_ids`/`default_notify_recipient` — не трогаются, только ДОБАВЛЯЮТСЯ новые поля.

## Dev Notes

- **Модель-прецедент — `control_hour`/`required_division_ids` на ТОЙ ЖЕ модели** (`apps/operations/submissions/models/control_settings.py`). Новые поля — того же стиля (TimeField/PositiveSmallIntegerField с дефолтом), тот же singleton-паттерн, никакой новой модели не создаётся.
- **Почему НЕ переиспользовать `control_hour`.** `control_hour` (дефолт 17:00) — час, после которого катап-джоб (5.7b2, `apps/operations/submissions/services/lagging_check.py`) считает день «проверяемым» для ПОЛНОГО отсутствия сдачи (проверяется НОЧЬЮ следующего дня, beat в 01:45). Буква 13.5's «к 15:30» — ИНТРАДЕЙ-алерт В ТЕЧЕНИЕ дня о ЧАСТИЧНОМ отставании (доля, не бинарный факт) — семантически другой контроль с другим владельцем (13.5b), общий час их бы случайно связал.
- **DB CheckConstraint — не `full_clean()`.** Прямая находка памяти `[[feedback_vaps_db_integrity_checks]]`: числовой floor/потолок без DB-гарда пропускает `bulk_create`/`.objects.create()`. Зеркалить `ck_submission_control_settings_singleton`/`ck_submission_control_settings_duty_not_whitespace` (та же модель, L40-53) — уже установленный паттерн в ЭТОЙ модели, не новый для проекта.
- **`chk_notification_kind` — расширять, не переписывать заново.** Файл `apps/notifications/models.py:60-68`: `CheckConstraint(condition=models.Q(kind__in=["SUBMISSION_LAGGING"]), name="chk_notification_kind")`. Добавить `"SUBMISSION_THRESHOLD_ALERT"` в список. `test_kind_check_covers_kind_choices` (уже существует, `apps/notifications/tests/test_notify.py:36`) СВЕРЯЕТ constraint против `Kind.values` программно — если забыть расширить constraint, этот тест сам покраснеет (не нужно писать новый drift-тест, существующий уже покрывает).
- **`UniqueConstraint(recipient, kind, business_date)` уже даёт «одно уведомление на день» БЕСПЛАТНО для нового `Kind`** — 13.5b не должен изобретать свой watermark/idempotency-механизм для порогового алерта (в отличие от 5.7b2's полного watermark-catchup — интрадей-алерт проще: просто попытаться `notify()` и полагаться на `UniqueConstraint`, если уже было сегодня — 13.5b's забота, здесь только фиксирую как ориентир).
- **Migration-порядок.** Обе миграции НЕЗАВИСИМЫ (разные Django apps, ни одна не ссылается на объекты другой) — порядок применения не важен, `makemigrations` создаст по одной на каждое приложение автоматически при запуске из корня `apps.operations.submissions`/`apps.notifications`.
