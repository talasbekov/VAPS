## Project Context Analysis

### Requirements Overview

**Functional Requirements:**

43 FR в 11 группах PRD. Архитектурно — шесть кластеров:

1. **Кадровый фундамент (FR-1…FR-5)** — дерево Подразделений, Штатные единицы, карточка Сотрудника (кадровый + оперативный блоки), неудаляемые истории. Контекст `core` реализован; до появления КУ — эталон данных (source=VAPS).
2. **Статусный движок (FR-6…FR-16, FR-41)** — статус-как-интервал, жизненный цикл PLANNED→ACTIVE→COMPLETED/CANCELLED, гибрид hard/soft конфликтов через `is_hard_block` (422/409+override), парные статусы при-/откомандирования, массовое обновление. Главный инвариант: «на любую дату ровно один действующий статус». **Дополнено решением 2026-06-10:** модель должна вмещать честное состояние «уточняется» — иначе оператор врёт машине, а правда остаётся в телефоне (семантика проектируется вместе с движком).
3. **Официальные документы (FR-17, FR-18, FR-40)** — асинхронная генерация Расхода `.docx/.xlsx/.pdf/.csv` с формулами сходимости (Штат = Список + Вакансии; Список = Σ статусов без остатка), блокировка «на завтра» по каскадному Индикатору, экспорт. Реальный режим: **расход сдают «за день вперёд» до 17:00** — контрольный час 17:00 накануне; «закрытие дня» — явное действие сдачи.
4. **Operations: объекты и цикл ОМ (FR-19…FR-32, FR-42, FR-43)** — Паспорта объектов, дежурства с авто-проекцией статусов (DUTY / REST_AFTER_DUTY / BEFORE_DUTY), 8-шаговый цикл ОМ, Потребность, двухуровневый брокеридж, версионируемая Расстановка, конфликт-детектор, каскадные замены, эскалация по бездействию, опрос по итогам (источник Налёта часов), журнал штаба и инциденты.
5. **Сквозная платформа (FR-33…FR-39)** — RBAC со scope + временные дежурные полномочия (ОМД/ОРГД) с авто-включением/гашением, append-only аудит, in-app уведомления + WebSocket, календари, дашборды, справочники.
6. **Измеримость (следствие §7 PRD)** — метрики SM-1…SM-5 и контр-метрики требуют событийной инструментовки: каждый override — считаемое событие; «контрольный час» — first-class понятие; «подтверждено без изменений» ≠ «изменено» — разные события схемы (без этого контр-метрика фиктивного ввода математически невычислима).

**Non-Functional Requirements:**

- **Закрытый контур:** один сервер LAN, без интернета/облака; Docker Compose. Эксплуатация: **релизы доставляются переносом носителя** → kill-switch-флаги в конфиге обязательны (MTTR ≥ время доставки), offline-бандлы, бэкап PostgreSQL + проверка восстановления, ротация логов, self-hosted мониторинг, вендоринг всех ассетов (включая шрифты для казахского заголовка), offline-зеркало зависимостей, локальный quality gate (< 5 минут) вместо облачного CI.
- **Время как ресурс:** нет публичного NTP; источник времени, таймзона (Asia/Qyzylorda в коде), дрейф часов — фиксируются. **Операционные сутки — календарные** (граница «даты» инварианта = полночь; упрощает интервальную модель до чистого `daterange`).
- **Клиентское окружение:** старые офисные ПК, **4 ГБ RAM, без видеокарт; Firefox ~100** (2022 — WS/SSE умеет, жёсткое ограничение — железо). Бюджет на бандл и память вкладки; виртуализация/пагинация всех длинных таблиц; агрегация на сервере; запрет рендерить 5000 строк одним полотном (экран = одно подразделение × месяц); проверка на эталонной слабой машине — в Definition of Done.
- **Безопасность:** проверка каждого запроса (токен, роль, scope, ограничивающий статус); PermissionService — единая точка (реализован). Временные полномочия = authz от часов: граничные минуты и активная сессия при гашении — определить.
- **Аудит:** append-only, **enforced на уровне БД** (REVOKE UPDATE/DELETE / триггер), не конвенцией.
- **Производительность:** масштаб — ~5000 сотрудников, 200–300 онлайн. Это contention, не throughput: пик 16:00–17:00 перед дедлайном; гонки записи статусов реальны. Анти-паттерн донора (COUNT() в цикле) не должен воспроизвестись — селекторам нужен bulk-API.
- **Надёжность:** регламентные задачи — идемпотентность + catch-up («догнать всё к now()»); сервер будет выключаться в моменты переходов.
- **Локализация:** интерфейс русский; заголовок Расхода казахский.
- **Real-time:** **WebSocket — требование MVP (решение заказчика, переподтверждено после рассмотрения polling-альтернативы)** → Channels/ASGI фиксируются на шаге технологий; event/outbox-слой делает транспорт заменяемым адаптером и тестируемым (тестируем событие, не сокет); kill-switch с fallback на ручной refresh — с первого дня; контракт доставки best-effort + дочитка по REST.
- **Невидимый NFR выживания (урок донора):** сценарий UJ-1 целиком быстрее, чем тот же ритуал в Excel; стоимость багрепорта ~0; видимая скорость починки.

**Scale & Complexity:**

- Primary domain: full-stack web (backend-центричный модульный монолит + SPA React/Vue + Django Admin)
- Complexity level: высокая, но **сконцентрированная**: (1) статусный движок с интервальными инвариантами и конкурентностью, (2) корректность времени/планировщика, (3) cross-context целостность без FK. Остальные ~30 FR — дисциплинированный CRUD: рискованную тройку прототипировать и фиксировать жёстко, остальное не перепроектировать.
- ~13 модулей-контекстов по R6 — как структура папок; реальных швов ~5–6 (владелец один — соло-разработчик).

### История донора и стратегия второго запуска

**Причина смерти Personnel-Records (из первых рук):** (1) неверный список сотрудников (мусорный master data), (2) накопление мелких ошибок, раздражавших людей. Эрозия доверия; альтернатива (Excel/звонок) решала задачу → ввод стал необязательным → распад. Выжил один артефакт: **ежедневный документ расхода** — доказанный job-to-be-done с внешним заказчиком (руководство).

**Следствия (зафиксированы как требования):**

- **Качество миграции данных = условие выживания №1.** Миграция — фича со своим эпиком: identity mapping (integer PK донора → UUID core, mapping-таблица), профилирование данных, идемпотентные репетиции, формулы сходимости как post-migration check, diff-отчёты. Доверие возвращается демонстрируемой сверкой.
- **Скорость починки мелких багов — архитектурное свойство** (см. стратегию качества ниже).
- **Расход генерируется только системой** — закрытие параллельного канала производства артефакта; документ нумерован, фиксирован, воспроизводим.
- **Petля возврата ценности вниз:** оператор немедленно получает выгоду от ввода (авто-статусы из дежурств, свой срез, личный экспорт-«щит»).
- **Каждый неизбежный обход — дешёвый, видимый, аудируемый внутри системы** (override блокировки — сущность первого класса с причиной), иначе он случится снаружи и отравит данные.
- **Позиционирование:** не «вторая версия умершей системы»; первый организационный ход — решение руководства «расход принимается только из системы»; первый видимый результат бьёт в 17:00.
- **Канал обратной связи об ошибках** — вернуть в scope (был в доноре, потерян в PRD); вопрос анонимности — открыт.

**Решение о роадмапе (заказчик, 2026-06-10): этапы 0 и 1 PRD слиты.** Первый релиз = минимальный фундамент + статусный движок + расход к 17:00 + сверка с донором. Дежурства/цикл ОМ — следующими слайсами.

**Главный риск исполнения (pre-mortem, ~50%):** смерть на фундаменте — инфраструктурный перфекционизм до первого пользователя. Митигация — принцип отсечения (ниже). Прочие риски: parallel-run без критерия выхода (зафиксировать exit criterion заранее: N дней подряд расхождения только категории «донор неправ, подтверждено»); семантически неверный AI-код при зелёных тестах (property-based на ядро); эксплуатационная смерть деплоя (репетиция деплоя с носителя — тест-сценарий); выгорание соло-разработчика.

### Принцип отсечения механизмов (принят заказчиком)

Два теста для каждого механизма: **(1) необратимость** — без него данные/доверие необратимо портятся в первую неделю? **(2) ретрофит** — это уровень схемы БД (дёшево сейчас, мучительно потом) или уровень кода (добавляется в любой момент)?

**СЕЙЧАС (6):** parallel-run + diff-отчёты с донором; хранение выданного файла расхода байт-в-байт (+ входной снапшот + хэш); append-only аудит enforced на БД; колонки схемы для override-сущности и «подтверждено vs изменено» (UI минимальный); property-based тесты ядра расчёта расхода (только ядро!); kill-switch для WebSocket.

**DEFERRED с триггером возврата (8):** event/outbox → при подключении КУ (до тех пор — дисциплина «доменные изменения через сервис-слой»); ночной «доктор данных» → при первом инциденте целостности; телеметрия раздражения → при появлении пользователей; генератор синтетических данных (5000) → к нагрузочным тестам (до тех пор fixture-фабрика); конкурентные тесты → этап масштаба; нагрузочный сценарий «дедлайн 17:00» → перед пилотом; автосейв массовой формы → после первой жалобы на потерю ввода (сама форма — в первом релизе); делегирование/эскалации/брокеридж → своими этапами (делегирование в v1 — только явные записи, без транзитивных цепочек).

Каждый DEFERRED-механизм получает ARCH-ID со статусом и триггером в Decision Register.

### Технические точки напряжения (требуют решения на шагах 3+)

1. **Инвариант «один статус на дату» vs тестовый стек.** Надёжно держится только exclusion constraint PostgreSQL (`EXCLUDE USING gist` по `daterange`); SQLite не умеет, app-валидатор не защищает от гонок (200–300 онлайн — гонки реальны). Существующее решение «тесты на SQLite» пересмотреть: Postgres в интеграционных тестах, SQLite максимум для unit без БД.
2. **Celery Beat ≠ источник истины.** Derived-first: действующий статус вычисляется из интервалов и now(); beat материализует побочные эффекты с catch-up. Сдача до 17:00 — человеческое действие; Celery — напоминалка.
3. **Статусная проекция (OM_AUTO) — двусторонняя синхронизация.** Контракт владения: operations — единственный writer OM_AUTO, идемпотентное пересоздание по source_ref, ручное редактирование OM_AUTO запрещено (422).
4. **Конфликт-детектор — кандидат в god-module.** Контракт «интервал + тип + hard/soft» с адаптерами контекстов либо детектор в одном контексте на селекторах; матрица конфликтов — декларативные данные, не if-ы.
5. **Cross-context ссылки без FK.** Компенсация: integrity-check, soft-delete, конвенция адресации operations-сущностей (integer PK — чем ссылаться извне?).
6. **Снапшот-семантика документов.** Генерация по as_of-срезу; выданный файл хранится байт-в-байт (аудиторский вопрос «покажи расход за 3 июня, который ушёл наверх»).
7. **Golden master для .docx** — побайтово не работает: двухслойно (числа+формулы как рантайм-инварианты; нормализованный document.xml) + parallel run.
8. **X-User-Id → JWT.** Auth-контракт (request.user_context) — до роста API-поверхности.
9. **Ретроспективные правки — пользовательский сценарий** («дежурный ошибся вчера»), не только аудит; на нём висят SM-3 и Daily Marks. Питается и штатным регламентом «бумажный fallback → обратный ввод».

### Стратегия качества (качество = выживание)

Целевая функция: **MTTD/MTTR мелких багов** (убийца донора — длинный хвост мелочей: 30 мелких багов за квартал ≈ смерть продукта).

- **Тесты под хвост, не под хребет:** property-based (Hypothesis) на ядро агрегации «кто активен на дату X в срезе Y» — инварианты: никто не в двух списках, никто не потерян, суммы сходятся.
- **Скучный деплой:** trunk-based; expand-contract миграции (рискованная без rollback-заметки не проходит gate); один артефакт, одна команда, авто-smoke; kill-switch для рисковой логики; версия приложения в футере UI.
- **Quality gate локальный, < 5 минут** (lint + unit + интеграционные на Postgres); деплой без штампа gate не едет; тяжёлое — ночью по расписанию.
- **Видимое закрытие петли:** журнал «сообщено → исправлено в vX.Y.Z», доступный пользователям.
- **Наблюдаемость БД** вместо постоянного перф-тестирования: pg_stat_statements, алерт на lock waits, slow query log.
- НЕ делать на этом масштабе: chaos engineering, перф в каждом CI-прогоне, распределённая нагрузка.

### Cross-Cutting Concerns Identified

1. **RBAC + scope + ограничивающий статус** — каждый endpoint через PermissionService; временное измерение прав.
2. **Append-only аудит** — enforced БД; консолидация на AuditLog.
3. **Конфликт-детектор** — контракт + декларативная матрица (точка напряжения №4).
4. **Регламентные задачи** — идемпотентность + catch-up; порядок и поведение при сбое.
5. **Уведомления** — событие отделено от транспорта; WS — адаптер; тестируем событие.
6. **Генерация документов** — снапшот-семантика, файл байт-в-байт, golden master двухслойно, аудит скачиваний; маскирование в печатных формах.
7. **Статусная проекция** — контракт владения OM_AUTO.
8. **Миграция из донора** — фича с эпиком, parallel-run с exit criterion.
9. **Маскирование чувствительных полей** — экран/экспорт/печать; SensitiveFieldPolicy в core.
10. **Темпоральная логика** — конвенция интервалов `[start, end)` на всю систему; Clock как инжектируемая зависимость; календарные сутки; источник времени.
11. **Дерево подразделений** — один механизм обхода поддерева (CTE/materialized path) для трёх потребителей: каскадный индикатор, scope-subtree RBAC, расход.
12. **Инструментовка метрик** — overrides, контрольный час 17:00, «подтверждено vs изменено», детектор флэтлайна.

## Core Architectural Decisions

### Decision Priority Analysis

**Critical (приняты, блокировали имплементацию):**
- PostgreSQL в интеграционных тестах + exclusion constraint (ARCH-DATA-020)
- Сущность «Сдача дня» / DailySubmission (ARCH-DATA-021) — закрывает OQ-4
- Derived-first статусный движок + watermark/Clock (ARCH-DATA-022)
- Стили: донорские shadcn-компоненты (вид = токены донора) + Tailwind (лейаут); preflight ON — нужен shadcn (ARCH-FE-014 финал-2, ревизия 2026-07-04)

**Deferred (по принципу отсечения, с триггерами):** event/outbox, доктор данных, телеметрия, генератор данных, нагрузка/конкурентность — см. Project Context Analysis. Остаток семантики «уточняется» (N дней эскалации, права разрешения) — в эпике статусного движка.

### Data Architecture

**ARCH-DATA-020 — Тестовая БД = PostgreSQL; инвариант статусов в БД.**
- Интеграционные тесты — на PostgreSQL (compose-сервис); SQLite только для чистых unit без ORM-запросов (например, агрегация расхода по JSONB-фикстуре). Существующие тесты переводятся конфигом.
- Инвариант БД (time-independent, иначе не выразим constraint'ом): **«не-отменённые hard-статусы сотрудника не пересекаются по daterange»**. Реализация: `GeneratedField period = daterange(date_start, date_end, '[)')` (db_persist) + `ExclusionConstraint` (btree_gist: employee EQUAL, period OVERLAPS, condition: hard-типы AND cancelled_at IS NULL) + GiST-индекс (employee, period). FK на StatusType по to_field="code" (condition видит только stored-колонки).
- Формулировка «один активный статус на дату» — НЕ для constraint (state derived, CURRENT_DATE не IMMUTABLE): constraint = backstop hard×hard (сервис ловит раньше → 422); soft-пересечения и FR-10 (PLANNED-предупреждение) — сервисный слой → 409+override / warning. `[)` даёт смежность бесплатно (отпуск до 15-го + командировка с 15-го — не overlap).
- MUST NOT: полагаться на app-валидатор как единственную защиту; тестировать инвариант только на SQLite.

**ARCH-DATA-021 — DailySubmission («Сдача дня»).**
- Подразделение явным действием сдаёт день (date, division, submitted_by/at, snapshot); реальный контрольный режим — «за день вперёд» до 17:00. Unique(date, division, актуальная версия). Срез атомарный (одна транзакция, не «прочитал полчаса назад»).
- **Версионируемость + amendment-flow:** снапшот не правится — вытесняется (v1, v2…; ровно одна действующая). Поправка = событие AMENDED (кто/когда/причина/санкция/ссылка на ретро-правку). **Инвариант: ретро-правка статуса на дату, накрытую сданным днём, ОБЯЗАНА триггерить amendment** — иначе две правды. Санкция на пересдачу после ухода расхода наверх — выше, чем до.
- **Снапшот = интервалы-факты, не выводы** (JSONB rows: employee_id, денормализованные ФИО/звание — печать прошлых дат «как было», status_type, status_id, date_start/end; schema_version). Расход «на завтра» = derive(снапшот, дата) — детерминированно. Размер ~22 МБ/год — не проблема.
- События различают CONFIRMED_NO_CHANGES / CHANGED (diff против вчерашнего СНАПШОТА; изменение, откаченное до сдачи = NO_CHANGES). Контр-метрика фиктивного ввода вычислима.
- **Светофор трёхцветный:** сдано-и-совпадает / сдано-но-разошлось (drift = diff(derive(снапшот), derive(live)) — показывается, расход остаётся по снапшоту by design) / не сдано.
- **Фрактальность:** сводный расход наверх = та же сущность DailySubmission уровнем выше (те же версии и amendments); пересдача внизу протухает сводку — видимо, не молча. Одна модель на все эшелоны.
- Расход выпускается со ссылкой на версию сдачи; новый после amendment — «взамен ранее выданного исх. №…», старый superseded (не исчезает); выданный файл хранится байт-в-байт + хэш.
- День без сдачи: расход «на завтра» блокируется (FR-18), красный, эскалация (FR-42); легальный обход — override-сущность первого класса; за прошедший день без сдачи — честное «не сдано» в сводке.
- Блокировка — derived из существования сдачи, не отдельный флаг.

**ARCH-DATA-022 — Derived-first статусный движок.**
- Time-состояния (PLANNED/ACTIVE/FINISHED) вычисляются из [start, end) и business-даты: annotation (Case/When) + зеркальный @property (тест эквивалентности обязателен); «кто активен» = period__contains + GiST. Lifecycle-факты — stored append-once: cancelled_at/by/reason (отмена — событие, из дат не вычислима). **MUST NOT: единый мутируемый enum state, который перещёлкивают задачи (паттерн донора). Запрещён мутатор, не stored-факты.**
- Celery Beat материализует только побочные эффекты (уведомления, авто-возврат) идемпотентно (аудит — синхронный на мутации, реализация E4; ретро E4 AI#4): **catch-up = чистая функция от watermark** (last_materialized_date): план = f(watermark, today); хронологически, дата за датой, отдельными транзакциями; unique(сущность, business_date, версия сдачи) + upsert; pg_advisory_lock от конкурентного Beat; today < watermark (перевод часов) → стоп + алерт.
- **Clock-сервис** — единственное место чтения wall clock (override для тестов); все доменные функции принимают business_date явно. MUST NOT: timezone.now()/NOW()-defaults в доменной логике и business-полях (freezegun не трогает Postgres). freezegun — только тонкий слой границы.
- Catch-up за день, который пересдан, не дёргает эффекты повторно (идемпотентность по версии).

**ARCH-DATA-023 — Интервалы:** хранение полуоткрытое [start, end); UI отображает «по … включительно». Календарные сутки, полночь Asia/Qyzylorda. Допущение фиксируется явно: Казахстан = единый UTC+5 без сезонных переходов; tzdata-канарейка в gate (assert utcoffset == +05:00).

**ARCH-DATA-024 — Дерево подразделений:** adjacency (parent FK) + CoreDivisionTreeSelector (существует) — один канал обхода для индикатора, RBAC-scope, расхода. При деградации — recursive CTE внутри селектора без смены API. MUST NOT: django-mptt в новой системе.

**ARCH-DATA-025 — Cross-context целостность и сходимость:** soft-delete для сущностей под внешними ссылками; принадлежность подразделению — интервал [start, end) (перевод среди дня: человек ровно в одном снапшоте); Список(D) версионирован на дату (прибыл/убыл меняет знаменатель); сходимость проверяется глобально, не только внутри подразделения. Адресация operations извне — integer PK внутри API operations; cross-context ссылки только на UUID core.

**Кэширование:** не вводится (Redis — только брокер); read-cache — при доказанных лагах (PRD §6.2).

**Миграция данных:** identity mapping (donor_pk → uuid), идемпотентные репетиции, формулы сходимости как post-migration check. **Parallel-run exit criterion (3 слоя):** (A) frozen-suite — идентичный замороженный вход обеим системам → diff = 0 байт-в-байт, строго; (B) классификатор расхождений на живом прогоне — каждый diff ровно в одной категории: timing (реплей логики донора на момент снапшота сходится → объяснён) / model (намеренное улучшение: запись в реестре + подпись заказчика + сверка с регламентом — «донор неправ» только против документа) / unclassified (= блокер); (C) выход: 10 рабочих дней подряд с нулём unclassified + 100% авто-классификация + frozen-suite зелёный. Классификатор строится вместе с эпиком расхода, не на этапе parallel-run.

### Authentication & Security

- **ARCH-SEC-030 — Auth-контракт:** единственная точка извлечения идентичности — `request.actor_id` (user_id: str, ARCH-007); ставится только authentication classes в core/auth (реализовано в 5.1: JWT + X-User-Id-dev, взаимоисключающие через `build_auth_classes`). MUST NOT: читать заголовок/парсить токен вне core/auth.
- **ARCH-SEC-031 — Авторизация:** только PermissionService; права на каждый запрос, без кэша в сессии → гашение временного полномочия действует со следующего запроса (граничное поведение определено).
- **ARCH-SEC-032 — Аудит:** append-only enforced БД (REVOKE UPDATE/DELETE + триггер); консолидация на AuditLog.
- Маскирование: SensitiveFieldPolicy + применение в экспорте и печатных формах.
- HTTPS/IP-фильтрация/rate limiting — nginx + DRF throttling; эпик production hardening (не блокирует первый релиз: закрытый LAN).

### API & Communication Patterns

- REST (DRF), конвенции VAPS_7.8.2 §6: limit/offset, контракт ошибок §1255, 422 hard / 409 soft+override (фронтенд зеркалит ARCH-FE-015).

**Implementation Sequence (первый релиз = слитые этапы 0+1):**
1. Postgres-тесты + ExclusionConstraint + Clock/watermark-инфраструктура

### Naming Patterns

**База данных:**
- Таблицы: `core_<plural_snake>` / `ops_<plural_snake>` — точно по CREATE TABLE спеки, где секция существует (`core_employees`, `ops_roles`, `ops_daily_submissions`).
- Колонки snake_case; FK-колонка `<entity>_id`; cross-context — плоский `<entity>_id` (UUIDField, без FK).
- Constraints/индексы: `uq_`, `excl_`, `idx_`, `gist_` + смысл.
- Миграции: ручные имена `NNNN_<entity>[_<verb>].py`; **сущность + её собственные constraints/indexes = одна миграция**; отдельные миграции — для добавляемого позже. MUST NOT: `_auto_` имена.

**API:**
- `/api/<context>/<resource>/` — plural kebab-case, DRF DefaultRouter, trailing slash (`/api/operations/daily-submissions/`).
- Custom actions: POST `/<resource>/{id}/<verb>/` (`/{id}/amend/`, `/{id}/expire/`).
- Query-параметры snake_case; basename `<ctx>-<resource>`.

**Python:** PEP8 + ruff. Внутри app: `models/` — пакет, один агрегат = один файл, реэкспорт в `__init__.py`; `selectors.py|/`, `services.py|/`, `validators.py`, `tasks.py`, `api/{serializers,views,urls,permissions}.py`, `management/commands/seed_<context>.py`, `tests/`. Сервисы `<Domain>Service`; селекторы `<Context><Domain>Selector`.

**TypeScript:** фичи kebab-case; компоненты PascalCase.tsx; хуки useXxx.ts; типы PascalCase без I-префикса; константы UPPER_SNAKE.

### Базовые модели (канон существующего кода)

- core: `UUIDTimeStampedModel` (UUID PK, created/updated) — внешне-видимые кадровые сущности.
- operations: `TimeStampedModel` (BigAutoField PK, created/updated); Role/Permission — natural VARCHAR code PK.
- MUST NOT: третья базовая модель; UUID PK в operations (кроме cross-context ссылочных полей).
- JSONB-поля: рядом `*_schema_version`, валидатор схемы в `validators/`; схема фиксируется в спеке ресурса.
- DailySubmission уникальность: partial unique `(division, business_date) WHERE is_current` + `uq (division, business_date, version)` — версионирование и «одна действующая» совместимы.

### Format Patterns

**JSON:** snake_case end-to-end (DRF-дефолт; camelCase-трансформация запрещена — типы генерируются из схемы). FK в запросах и ответах — плоский `<fk>_id`; вложенные объекты — только явным решением спеки ресурса. Списки — конверт limit/offset `{count, next, previous, results}`; default limit 50, max 200; **ordering обязателен на каждом list-endpoint, tie-breaker `id` последним** (иначе пагинация молча теряет строки). POST возвращает detail-представление (201).

**Даты/время:** business-даты — `YYYY-MM-DD` (naive date в `VAPS_TIME_ZONE`); timestamps — UTC в БД (`USE_TZ=True`), ISO 8601 с офсетом в API; конверсия только на границе (сериализация/UI), в сервисах — никогда. Интервалы: `date_start`/`date_end` (end exclusive). MUST NOT: смешивать `date.today()` и `timezone.now().date()` — только Clock-сервис.

**Ошибки:**
- Семантика: 400 — нарушение ФОРМЫ (сериализатор, DRF-формат по полям); 422 — нарушение БИЗНЕС-ПРАВИЛА (hard-конфликт, окно дат); 409 — конфликт состояния (дубль, soft-конфликт; тело содержит details + overridable); 401/403/404/500 — стандартно, 500 без деталей наружу.
- Механика: `core.exceptions.DomainError(code, http_status, detail, overridable=False)` + единый DRF `exception_handler`; сервис ловит `IntegrityError` ПО ИМЕНИ CONSTRAINT'А → DomainError (поэтому имена constraints канонизированы). MUST NOT: try/except с ручным Response во view.

### Structure Patterns

- Тесты backend: `apps/<app>/tests/test_*.py`; для каждого эндпоинта — тест на каждый код ошибки из его спеки; фабрики — factory_boy в `tests/factories.py` (seed в тестах запрещён); время — только `core.clock.override(...)`; гонка на unique: тест маппинга IntegrityError→409 + один транзакционный тест constraint'а.
- Фронтенд: `*.test.tsx` рядом с компонентом; MSW-фикстуры в `src/shared/api/testing/`.
- AST-тест изоляции — в каждом новом app (образец operations).
- Конфиг: env `VAPS_*`; фронтенд `VITE_*`.

### Layer Contract (кто кого вызывает)

```
view → сервис → (селекторы, модели, аудит)   |   view ← сериализатор (форма) 
```
- Сериализаторы: только валидация формы и сериализация ответа. **MUST NOT: `serializer.create()/update()`** (AST-чек).
- Сервисы: типизированные kwargs (`division_id: UUID, business_date: date, actor: str`); MUST NOT: принимать `request` или сырой `validated_data`. `transaction.atomic` — в сервисе, не во view.
- Актор: authentication class (core) ставит `request.actor_id: str` (user_id, ARCH-007); чтение X-User-Id вне core запрещено (AST-чек).
- Permission-класс: грубая проверка роли/действия; **scope-проверка («своё ли подразделение») — в сервисе** через PermissionService → DomainError 403.
- Селекторы: возвращают QuerySet (bulk-форма; никаких per-item вызовов в циклах); единичный доступ — `.get(pk=...)` на селекторе в сервисе; `get_object_or_404` во view запрещён для ресурсов с бизнес-логикой. **Каждый list-селектор принимает `actor` первым аргументом и сам сужает видимость** — ViewSet по правам не фильтрует.
- request_id: middleware → contextvar; аудит-сервис читает сам.

### Communication Patterns

- Аудит: единый сервис записи (actor, action UPPER_SNAKE из реестра, target, before/after JSON, request_id, IP). MUST NOT: raw insert в аудит-таблицу.
- WS: `{"type": "<UPPER_SNAKE из реестра>", "payload": {...}}`; отправка **только через `transaction.on_commit`**; WS — сигнал «обнови», истина — REST/БД; после reconnect фронт дочитывает REST.
- Логи: structured JSON, `logging.getLogger(__name__)`, request_id в каждой записи. MUST NOT: print(), ПДн в логах.

### Process Patterns

- **Конкурентность:** мутация существующей строки = `select_for_update()` (в селекторе, внутри atomic сервиса). Constraint — последняя линия (срабатывание в проде = аномалия в лог), не стратегия. Optimistic locking (version-поле) не вводится. Append-only таблицы — без локов.
- **Идемпотентность POST:** естественный unique constraint обязателен для каждого POST (дубль → 409); Idempotency-Key не вводится (ретраи мутаций запрещены). Без естественного ключа — явная пометка «дубликаты допустимы» в спеке ресурса.
- **Долгие операции:** POST → Celery → 202 `{job_id}` → поллинг `GET /api/jobs/{id}` (pending/running/done/failed + error_code); одна generic-модель `AsyncJob` (type, payload, result_ref); WS-уведомление — ускоритель, поллинг — истина. Фронт: `refetchInterval`, стоп на терминальном статусе.
- **Файлы:** единая модель `Attachment` (uuid-имя на диске, original_name, content_type, size, sha256, явные FK — не GenericFK); приватный каталог вне MEDIA_URL; отдача только через endpoint с PermissionService → `X-Accel-Redirect` (nginx internal); Django не стримит. Whitelist content-type + `VAPS_MAX_UPLOAD_MB`.
- **Нумерация документов:** `DocumentSequence(doc_type, year, last_number)`, инкремент `select_for_update` в транзакции финализации; номер при финализации, не при черновике; монотонна, gap-tolerant. MUST NOT: Postgres SEQUENCE (не транзакционен).
- **Django Admin:** только справочники без бизнес-инвариантов + read-only просмотр (аудит, AsyncJob). MUST NOT: регистрация submissions/статусов/amendments/документов — запись мимо сервиса = мимо аудита и прав.
- **Удаление:** hard delete запрещён для версионируемого/аудируемого (только amendments/отмена); справочники — `is_active` deactivate; физический DELETE — только черновикам без номера/финализации.
- **Beat:** задачи идемпотентны + lock `cache.add` с TTL (при занятом — молча выйти); два параллельных catch-up недопустимы.
- **Фронт:** loading — только состояния TanStack Query (свои loading-флаги запрещены); optimistic updates запрещены (исключение — отдельным ARCH-ID); мутации не ретраить; 409 → ConflictDialog; валидация zod (мгновенно) + DRF (истина), ошибки бэка маппятся в поля.

### Enforcement Guidelines

**Каждый агент MUST:**
1. Имя/код/тип не покрыт Glossary/реестром/спекой → СТОП и вопрос, не выдумка.
2. `make gate` зелёный до закрытия стори.
3. Новые правила — только как ARCH-ID с enforcement; договорённость в чате правилом не является.

**Механически:** ruff + eslint (boundaries, no-restricted-imports, react-hooks, compat, tailwind) + AST-тесты (изоляция контекстов, serializer.create, чтение X-User-Id, timezone.now в домене) + CI (schema diff, npm ls запрещённых пакетов, tzdata-канарейка, сверка кодов с реестрами).

### Pattern Examples

**Good:** `db_table="ops_daily_submissions"` · `POST /api/operations/daily-submissions/` → 201 detail · `{"count":2,"results":[{"date_start":"2026-06-01","date_end":"2026-06-15"}]}` · `raise DomainError("STATUS_OVERLAP", 409, details=..., overridable=True)` · `submit_day(division_id=..., business_date=..., actor=request.actor_id)` (сервис-функции модульные, как `status_service`; класс-обёртки не заводятся).

### Architectural Boundaries

**Django apps = швы; субдомены operations — вложенные apps (`name="apps.operations.statuses"`, `label="ops_statuses"`), каждый со своими migrations/** — параллельные стори-агенты не конфликтуют по миграциям. `db_table` всегда явный → топология apps отвязана от схемы БД навсегда.

| Граница | Правило | Enforcement |
|---|---|---|
| core ↛ всех | core никого не импортирует | AST (есть) |
| operations/* → core | только selectors, exceptions, clock; НЕ models | AST (есть, расширить) |
| между субдоменами operations | statuses ← submissions ← reports (вниз); duties/events → statuses только через сервис проекции (единственный writer OM_AUTO — тест) | AST + **тест на графе моделей** (apps.get_models(), ловит string-FK) |
| audit ← все | запись только audit.services.record(); прямой импорт audit.models — бан | AST |
| documents ← operations | файлы только через documents.services (Attachment); разрешённая стрелка | AST |
| notifications ← все | только notifications.services.notify() (синхронно in-txn, вариант B 5.7a; non-fatal) | AST |
| core/auth | request.actor_id ставит только authentication class; чтение X-User-Id вне core/auth — бан | AST |
| frontend | features A ↛ B; shared ↛ features | eslint-boundaries |

Запрещено: общие services.py/selectors.py в корне operations (god-модули); кросс-субдоменная оркестрация — только именованный оркестратор с собственным AST-правилом.

**Django-механика (обязательные правила):** `makemigrations --check --dry-run` в gate (защита от молчаливого DeleteModel при рефакторе models.py→models/); реэкспорт моделей в `__init__.py` — контракт навсегда; миграции с ручными именами; squash — отдельная задокументированная процедура; tasks.py per app (autodiscover); AppConfig.ready() per app для сигналов.

**API:** `/api/core/…`, `/api/operations/…` (общий маунт, роуты из субдомен-apps), `/api/audit/` (read-only), `/api/notifications/`, `/api/jobs/{id}`; WS `/ws/notifications/`.

### Data Flow (ключевые цепочки)

- **Сдача дня:** status-grid → POST submissions → submit_day (atomic: срез из statuses-селектора → снапшот фактов → audit.record → notify in-txn) → светофор.
- **Расход:** POST reports → AsyncJob → Celery worker (documents: derive по снапшоту → docx → Attachment + DocumentSequence) → поллинг /api/jobs/ → скачивание X-Accel.
- **Ретро-правка:** statuses.amend → обнаружение накрытых сдач → Amendment-flow (submissions) → новый расход «взамен исх. №».
- **Проекция:** duties/events → statuses.projection_service (OM_AUTO, source_ref, идемпотентно).
- **Beat:** catch-up(watermark) → материализация эффектов → notifications.

### Test Organization & Make Targets

- Тесты — в tests/ субдомен-app'а, чей код проверяют; кросс-субдоменные — operations/tests/integration/ (единственное общее место).
- Маркеры: `property` / `concurrency` / `slow`; hypothesis-профили: ci (max_examples=10, в gate) / full (500+, в test-full); забытый маркер на медленном тесте = ошибка коллекции (conftest).
- Golden master: `operations/reports/tests/golden/case_NNN/{input.json, expected_values.json, expected_document.xml}` — в git без LFS; полных .docx — 2 смока; обновление только `make golden-update CASE=` с ревью diff.
- Обязательные сквозные тесты: RBAC-матрица роль×операция (параметризованная; новый endpoint без строки — не проходит ревью); audit-coverage (каждая мутирующая вьюха оставляет след); регистрация beat-задач; MSW-хендлеры валидируются против OpenAPI-схемы; тесты импортёров на golden-кейсах грязного входа.
