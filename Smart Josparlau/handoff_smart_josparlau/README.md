# Handoff: Smart Josparlau — Реестр ОМ и Реестр ГВО

## Overview
Прототип внутренней системы планирования и проведения охранных мероприятий (ОМ) СГО РК.
Покрывает полный жизненный цикл ОМ из шести этапов и связанные справочники:

Бюллетень → Рекогносцировка → Согласование → Сбор сил → Расстановка → Закрытие и итоги.

Ключевые связи между модулями:
- Запись в **Реестре ГВО** создаётся автоматически в момент создания бюллетеня ОМ (статус «Черновик»); из бюллетеня подтягиваются даты, охраняемые лица, объекты, старший/ответственный, остальное заполняется вручную по секциям.
- Тип мероприятия (внутреннее / с иностранцами) задаётся в бюллетене и определяет, назначается ли старший ГВО или старший наряда.
- Запрос личного состава (рекогносцировка) → утверждение (согласование, блок сравнения «Запрошено N / утверждено M») → распределение по департаментам и подразделениям (сбор сил) → расстановка.

## About the Design Files
Файлы в `design/` — **дизайн-референс, сделанный в HTML**. Это прототип целевого вида и поведения, а не production-код для копирования. Задача — **воспроизвести эти экраны в существующей среде целевого проекта** (React/Vue/Angular/native), используя его роутинг, слой данных, состояние и библиотеку компонентов. Если среды ещё нет — выбрать стек и реализовать в нём.

Прототип написан как «Design Component»: один файл = HTML-шаблон + класс логики, рантайм `support.js`. **Рантайм в продукт переносить не нужно.** Из файла берутся: разметка и вся вёрстка (инлайн-стили = точные значения), тексты, справочные данные, логика переходов, валидации и ролевых ограничений.

## Fidelity
**High-fidelity.** Цвета, типографика, отступы, радиусы и все тексты — финальные, воспроизводить точно. Значения заданы инлайн в HSL-нотации токенов shadcn/ui, поэтому читаются прямо из разметки.

## Как открыть прототип
1. Раздать папку `design/` любым статическим сервером из её корня, например: `npx serve design` или `python3 -m http.server` в `design/`.
2. Открыть `Smart Josparlau.dc.html`. Открытие через `file://` не сработает — нужен http.
3. Навигация — левое меню; экраны переключаются внутри одного файла (см. карту маршрутов ниже).

## Экраны и поведение (что важно не потерять)

### Реестр ОМ (`events`)
Таблица мероприятий. Колонки: код ОМ (бейдж `bg-purple-100 text-purple-800`), название, **Даты** (начало–окончание), объект, **Этап + готовность одним полем** («Расстановка — 82%», бейдж этапа + прогресс), потребность в личном составе, ответственный, шеврон.
Фильтры: «Мои / Все», поиск, статус, период, ответственный, **тип мероприятия (внутреннее / с иностранцами)**.
Действия по строке: открыть этап, архивировать, отменить (этап становится «Отменено», бейдж `bg-red-100 text-red-800`).

Открытый вопрос заказчику: колонка «Старший» в строке ОМ — удалить как устаревшую или оставить справочной.

### Создание бюллетеня (модальное окно из `events`)
Обязательный переключатель типа мероприятия. От него зависит поле назначения старшего: для мероприятия с иностранцами — старший ГВО, для внутреннего — старший наряда. Прочие поля: код (генерируется), название, даты, объекты (поиск + пагинация + добавление), охраняемые лица. Валидация — кнопка сохранения заблокирована до заполнения обязательных полей. После сохранения ОМ создаётся со статусом «Бюллетень» (progress 5%) и всплывает тост «Мероприятие создано со статусом «Бюллетень»».

### Рекогносцировка (`recon`)
Вкладки, включая **«Замещающий»** — назначение замещающего с явными правами доступа. Секция **«Запрос личного состава»** с ручным вводом требуемой численности; этот запрос дальше сравнивается с утверждённым.

### Согласование (`approval`)
Маршрут согласования по шагам + блок сравнения запроса и утверждения («Запрошено 120 / утверждено 20») с явным расхождением.

### Сбор сил (`forces`)
Два ролевых режима (переключатель вкладок): **Штаб 2-го департамента** и **Брокер · департамент**.
- Штаб: список ОМ с потребностью, собрано/нужно, прогресс-бар, срок, статус; в карточке ОМ — квоты по департаментам (числовые поля), предупреждение при несовпадении суммы квот с потребностью, кнопки «Принять» по департаменту.
- Брокер: своя квота, распределение по подразделениям, «Запросить», список поданного личного состава.
Статусы: «Собрано» / «Принято» / «Отправлено штабу» (зелёный/синий тон), после отправки квоты блокируются.

### Расстановка (`placement`)
Команды по охраняемым лицам и постам: время, маршрут, роли, потребность, назначенные сотрудники, старший команды, транспорт; подбор сотрудников через пикер с ролью.

### Закрытие и итоги (`closure`)
Итоги мероприятия и **постфактум-отметка визита охраняемого лица**: подтверждение либо отказ (визит не состоялся) с фиксацией причины.

### Итоговые оценки (`omratings`)
Оценки участников ОМ по завершении.

### Реестр ГВО (`gvo`) и Сводные данные (`gvosum`)
Полное описание этих двух экранов с точностью до пикселя — в `README_gvo.md` (перенесено из предыдущей передачи, актуально).
Кратко: список ОМ со статусом сводки («Заполнена» / «Черновик»), карточка сводных данных из секций — шапка со страной, охраняемые лица с фото 150×196, прибытие/убытие с встречающими и провожающими, организация, состав ГВО по группам с позывными, выделяемый транспорт, объекты посещения по дням. Каждая секция правится своим модальным окном; в модальном окне — «Вернуть исходные», «Удалить лицо/группу», «Отмена», «Сохранить» + тост.

### Отчёты (`reports`)
**Переключатель роли: руководство ↔ старший объекта**, с разными наборами прав выгрузки. Состав отчётов и доступных форматов зависит от роли.

### Мой профиль (`myprofile`)
Вкладки профиля, включая **«Инструкции»**. Блоки аналитики и аудита скрываются в зависимости от роли пользователя.

## Ролевая модель (реализовать явно)
Прототип показывает четыре точки, где интерфейс меняется от роли:
1. Сбор сил — штаб vs брокер департамента (кто задаёт квоты, кто их исполняет).
2. Отчёты — руководство vs старший объекта (что видно и что можно выгрузить).
3. Профиль — скрытие аналитики службы и аудита.
4. Рекогносцировка — замещающий с ограниченным набором прав.

## State Management
Прототип держит всё состояние в одном классе (аналог одного стора). Основные группы:
- `view` — активный экран; `sideOpen` — состояние левого меню.
- `omCreated`, `omBaseEdits`, `omCancelled`, `omArchived` — созданные, отредактированные, отменённые и архивные ОМ поверх базового справочника `omBase`.
- `omQ`, `omStage`, `omPeriod`, `omOwner`, тип мероприятия — фильтры реестра ОМ.
- `forces` — потребности ОМ, квоты департаментов и подразделений, поданный личный состав, флаги `requested` / `sentToHq` / `accepted` / `dispatched`; `forcesRole`, `forcesSel`.
- `vipStore` — расстановка: команды по лицам (время, маршрут, роли, потребность, назначенные, транспорт).
- `gvoStore` — сводные данные ГВО по ОМ, включая флаг `full` (заполнена/черновик) и данные секций.
- Модальные окна и тосты — отдельные флаги (`omModal`, секция правки, текст тоста).

В целевом проекте это раскладывается на серверные сущности: Мероприятие (ОМ), Бюллетень, Рекогносцировка, Согласование, Заявка на личный состав (квоты по департаментам/подразделениям), Расстановка (команда, пост, назначение), Сводные данные ГВО, Отчёт, Пользователь с ролями.

## Design Tokens
Дизайн-система — **VAPS** (shadcn/ui, стиль new-york), язык интерфейса русский, светлая тема. В `design/_ds/` лежат `styles.css` и `_ds_bundle.css` с токенами; в целевом проекте использовать их эквиваленты, а не хардкод hex.

Значения, которые встречаются в разметке напрямую:

| Назначение | Значение |
|---|---|
| Фон приложения | `hsl(210 40% 97.5%)` |
| Поверхность карточки | `#fff` |
| Мягкая поверхность / шапки таблиц | `hsl(210 40% 98%)` |
| Hover строки / кнопки | `hsl(210 40% 96.1%)` |
| Основной текст | `hsl(222.2 84% 4.9%)` |
| Приглушённый текст | `hsl(215.4 16.3% 46.9%)`, темнее — `hsl(215.4 16.3% 36.9%)` |
| Границы | `hsl(214.3 31.8% 91.4%)`, внутренние — `hsl(210 40% 94%)` / `hsl(210 40% 95%)` |
| Primary | `hsl(var(--primary))` = `hsl(221.2 83.2% 53.3%)` |
| Успех (прогресс, «Собрано») | `#16a34a` |
| Тёмный тег (транспорт) | `hsl(222.2 47.4% 11.2%)` |
| Радиусы | карточка 12px, модальное окно 16px, кнопка 7–9px, pill 999px |
| Тени | карточка `0 1px 2px rgba(16,24,40,.04)`, фото `0 8px 22px rgba(16,24,40,.10)`, модальное окно `0 30px 90px rgba(7,18,38,.35)` |
| Шрифт | системный sans (`ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto`), базовый размер 14px |
| Типографика | H1 21–25px/700, заголовок секции 13.5px/600, тело 12.5px, подпись 11–12px, надзаголовок 10.5px/700 uppercase `letter-spacing:.08–.12em` |
| Числовые колонки | `font-variant-numeric: tabular-nums` |

Статусные бейджи — пары Tailwind `bg-<цвет>-100 text-<цвет>-800`: purple — код ОМ, green — успешно/согласовано/собрано, amber — черновик/в работе, blue — информационное, red — отменено, `bg-secondary text-secondary-foreground` — нейтральное (например, «Бюллетень»).

## Assets
Фотографии охраняемых лиц и сотрудников в прототипе — плейсхолдеры (`image-slot`, подпись «Фото» / «Фото ОЛ»), реальных изображений в пакете нет. Иконки — lucide (в прототипе несколько инлайн-SVG, например карандаш 13×13, stroke-width 2). Все данные (ФИО, объекты, борта, позывные) — демонстрационные, не подлежат переносу как справочники.
