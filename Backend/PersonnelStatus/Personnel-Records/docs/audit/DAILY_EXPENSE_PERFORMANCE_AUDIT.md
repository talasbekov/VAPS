# DAILY_EXPENSE_PERFORMANCE_AUDIT

## 1. Цель аудита
Оценка производительности генерации ежедневного отчета (расход), выявление мест формирования N+1 запросов к БД, узких мест агрегации, рисков синхронной генерации файлов и выработка безопасной стратегии оптимизации без изменения текущей бизнес-логики.

## 2. Методика анализа
1. Использование статического анализатора `scripts/audit_daily_expense_queries.py` для поиска обращений к БД внутри циклов (`.filter()`, `.count()`, `.exists()`, `.get_descendants()`).
2. Ручной анализ исходного кода файлов `reports/utils.py`, `reports/infrastructure/data_aggregator.py`, `reports/api/views.py`.
3. Оценка рисков Python-уровня и I/O (синхронное построение файлов, потребление памяти).

## 3. Scope: какие файлы проверены
* `reports/utils.py`
* `reports/infrastructure/data_aggregator.py`
* `reports/api/views.py`

## 4. Current daily expense data flow
В проекте реализовано два независимых механизма расчета статистики по подразделениям:
1. **Синхронный** (`generate_personnel_expense_report` в `reports/utils.py`): генерирует XLSX "на лету". Выполняет обход каждого дочернего управления, запрашивает дерево подразделений (`get_descendants()`) и производит множественные запросы `.count()` и `.filter()` для подсчета вакансий, статусов, прикомандированных. Списки отсутствующих также запрашиваются отдельно.
2. **Асинхронный/Агрегирующий** (`DataAggregator` в `reports/infrastructure/data_aggregator.py`): использует `annotate()` и группировку `.values()` для агрегированного извлечения статусов, однако все еще содержит цикл вывода.

## 5. Query hotspots
Скрипт `audit_daily_expense_queries.py` обнаружил 25+ опасных запросов в `reports/utils.py` внутри цикла `for directorate in directorates:`.
Топ 5 проблемных мест:
1. `directorate.get_descendants(include_self=True)` внутри цикла (один тяжелый запрос на каждое управление).
2. Подсчет штаток и вакансий по зоне видимости `StaffUnit.objects.filter(...).count()` внутри цикла.
3. Расчет численности статуса (`EmployeeStatus.objects.filter(...).count()`) внутри цикла (10+ запросов на каждое управление для разных типов статусов).
4. Запрос полного списка сотрудников с конкретным статусом для примечаний (`[f"{s.employee.last_name}..." for s in ...statuses]`).
5. `Division.objects.filter(id__in=division_ids)` внутри цикла в `data_aggregator.py`.

## 6. N+1 / repeated-query patterns
Код в `reports/utils.py` генерирует классическую проблему N+1, помноженную на количество статусов (N*S запросов, где N - управления, S - статусы).
На каждое управление (Directorate) производится около 25 прямых обращений к БД, включая древовидные `get_descendants()`. Для департамента с 20 управлениями это порождает 500+ запросов к БД при генерации одной таблицы, что приведет к значительным задержкам отклика.

## 7. Synchronous generation risks
Генерация XLSX-отчета в `reports/utils.py` выполняется **синхронно** (внутри request-response цикла).
При большом количестве подразделений и сотрудников выполнение 500+ запросов в БД + генерация XLSX приведет к таймаутам HTTP-запроса (например, 502/504 Gateway Timeout со стороны Nginx).

## 8. XLSX/DOCX/PDF generator risks
Существует риск несоответствия логики подсчета. `generate_personnel_expense_report` использует один способ вычисления штатки и присутствия, в то время как `DataAggregator` использует немного другую логику (например, вычисление `inferred_in_service`). Это **CRITICAL RISK** (рассинхронизация бизнес-правил между интерфейсами отчетов).
Создание крупных XLSX-файлов в памяти (`load_workbook` и модификация ячеек) в один поток потребляет много ОЗУ.

## 9. Estimated impact on large departments
На тестовой среде или небольших департаментах задержка не видна. Но на департаментах, имеющих сотни штатных позиций и глубокую иерархию подразделений, синхронная выгрузка может занять 10-30 секунд, превышая типовые таймауты браузеров.

## 10. Risk matrix
* **CRITICAL**: Рассинхронизация бизнес-логики вычисления ежедневного расхода между `utils.py` и `DataAggregator`.
* **HIGH**: Множество тяжелых запросов в цикле (N+1, `get_descendants()`, `.count()`) в `utils.py` (25+ запросов на каждый элемент цикла).
* **HIGH**: Синхронная генерация файла при вызове из API.
* **MEDIUM**: Потребление оперативной памяти библиотекой `openpyxl` при синхронном формировании.

## 11. Safe optimization strategy
1. Унифицировать агрегацию. Вынести общий слой логики, чтобы XLSX генератор и JSON-агрегатор обращались к единому сервису/селектору.
2. Избавиться от циклов при работе с БД. Сделать единый запрос `StaffUnit.objects.values('division_id').annotate(...)` и `EmployeeStatus.objects.values(...).annotate(...)` (подобно `DataAggregator`). Распарсить данные в Python-словари (dict) до старта генерации Excel.
3. Единоразово выгрузить все дочерние узлы подразделений с использованием MPTT-возможностей (без цикла по каждому корневому узлу).
4. Перевести генерацию XLSX-отчета в Celery task. Возвращать `task_id` клиенту, а готовый файл выдавать через эндпоинт загрузки результатов.

## 12. Required tests before optimization
Перед любым рефакторингом (перевод на annotate или Celery) необходимо создать строгие black-box тесты для сверки чисел.
1. Тесты, проверяющие, что при определенных наборах данных (штаток, вакансий, статусов) XLSX-файл и `DataAggregator` отдают идентичные суммы.
2. Тест с 10+ управлениями, для проверки работоспособности (нагрузочное/профилирование).

## 13. What must not be changed yet
Запрещено менять код `reports/utils.py`, `DataAggregator` и API-views до тех пор, пока не будут добавлены строгие интеграционные тесты сверки текущего вывода. Запрещено включать кэширование или добавлять индексы в БД.

## 14. Результаты оптимизации (STORY-000.8)
* Созданы интеграционные contract тесты.
* Логика агрегации унифицирована в рамках `DataAggregator`.
* `reports/utils.py` избавлен от N+1 запросов. Все метрики и списки (ФИО) теперь извлекаются за 1-2 запроса перед стартом генерации XLSX файла. Запросов к БД внутри циклических обходов больше нет.
