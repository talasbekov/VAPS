# Design: автоматическая блокировка приёма списков по дедлайну (hd-2-7, новый)

**Дата:** 2026-08-21
**Статус:** решения приняты автономно (делегировано пользователем, ночная сессия).
**Источник:** докладная записка, п.5 — «Устанавливаемый дедлайн (за 3–5 суток до
мероприятия) массово не соблюдается... На программном уровне установить
автоматическую блокировку приёма списков по истечении дедлайна. Повторное
открытие доступа осуществлять исключительно на основании официального
письменного разрешения (рапорта)».

## 1. Решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Что именно блокируется? | Создание НОВЫХ участников (`Attendee` create) в событии после дедлайна | Буквально «приём списков» = приём/загрузка новых данных, а не редактирование уже поданных черновиков или админский review. Самая узкая, самая безопасная трактовка — не блокирует уже начатую работу |
| Где хранится дедлайн? | Новое поле `Event.submission_deadline` (DateTimeField, `null=True`) | `null` = дедлайн не задан → блокировки нет (обратная совместимость, не ломает существующие мероприятия без миграции данных) |
| Как «официальное письменное разрешение» превращается в код? | Два новых поля `Event.submission_reopened_until` + `Event.submission_reopen_reason` (оба редактируются ТОЛЬКО суперпользователем через Django admin `/embankment/`) | Это ручной admin-шаг (рапорт остаётся бумажным/организационным процессом вне системы) — система лишь фиксирует ЧТО и ПОЧЕМУ переоткрыто, и до какого момента |
| Аудит переоткрытия | Новое действие `event.submission_reopened` в СУЩЕСТВУЮЩУЮ категорию `"edit"` (не новая категория) | Не нарушает `test_registry_has_exactly_expected_categories`; фиксируется в `EventAdmin.save_model` при реальном изменении `submission_reopened_until`/`submission_reopen_reason` |
| Где enforcement? | `AttendeeSerializer.validate()` (DRF create-путь — основной, современный флоу по fe-* эпикам) | Легаси RU/KZ/EN шаблонные вьюхи НЕ трогаются (Strangler Fig — установившаяся конвенция проекта, см. `dashboard.py`/`pdn_consent.py` docstrings) |
| Ошибка при блокировке | 403 с понятным сообщением на русском, код `submission_deadline_passed` | Согласовано с существующим паттерном кодированных ошибок (fe-1.1) |

## 2. Открытый вопрос (НЕ решаю сам)

Дедлайн сейчас нигде не хранится и не вычисляется автоматически (докладная
говорит «устанавливаемый дедлайн», подразумевая ручную установку). Решение:
`submission_deadline` — простое ручное поле в админке события (не авто-расчёт
«дата_начала минус N дней»). Если служба хочет авто-расчёт по фиксированному
правилу (например, всегда «начало минус 3 суток») — это тривиальная доработка
поверх того же поля (заполнять его автоматически при создании события), но
сама докладная не указывает единое число дней («3–5 суток» — диапазон,
организационное решение по каждому мероприятию), поэтому ручное поле — более
безопасный выбор, не подразумевающий число, которое не подтверждено.

## 3. Архитектура

- `eventproject/models.py::Event` — 3 новых поля: `submission_deadline`,
  `submission_reopened_until`, `submission_reopen_reason`.
- `eventproject/validators/deadline.py::is_submission_open(event, now=None) -> bool`
  — единственный источник правды: `True`, если `submission_deadline` не задан,
  ИЛИ `now <= submission_deadline`, ИЛИ (`submission_reopened_until` задан И
  `now <= submission_reopened_until`).
- `eventproject/serializers/attendee.py::AttendeeSerializer.validate()` —
  на CREATE (`self.instance is None`) вызывает `is_submission_open(event)`;
  `False` → `PermissionDenied` с кодом `submission_deadline_passed`. UPDATE
  существующих участников не блокируется (правка уже поданных данных — не
  «приём новых списков»).
- `eventproject/admin.py::EventAdmin.save_model` — при реальном изменении
  `submission_reopened_until` ИЛИ `submission_reopen_reason` относительно
  сохранённого в БД значения → `audit_log(action="event.submission_reopened", ...)`
  с `extra={"reopened_until": ..., "reason": ...}`.

## 4. Тестирование

- `is_submission_open`: нет дедлайна → True; дедлайн в прошлом → False; дедлайн
  в будущем → True; дедлайн в прошлом, но `reopened_until` в будущем → True;
  дедлайн и `reopened_until` оба в прошлом → False.
- Serializer: create после дедлайна → 400/403 с кодом `submission_deadline_passed`;
  update существующего участника после дедлайна → проходит (не блокируется);
  create без дедлайна → проходит как раньше (регрессия по умолчанию).
- Admin: реальное изменение `submission_reopened_until`/`reason` → аудит-запись
  `event.submission_reopened`; сохранение БЕЗ изменения этих полей → аудита нет
  (не шуметь на каждое редактирование события).
