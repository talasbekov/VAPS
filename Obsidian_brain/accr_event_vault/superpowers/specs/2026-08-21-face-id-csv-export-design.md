# Design: CSV-экспорт для терминалов Face ID (hd-2-6, новый)

**Дата:** 2026-08-21
**Статус:** решения приняты автономно (делегировано пользователем в этой
ночной сессии) — см. `docs/OUTPUT/overnight-2026-08-21.md` для итогового
списка открытых вопросов.
**Источник требования:** докладная записка, п.4 — «Данные... выгружаются в
формате, непригодном для прямой загрузки в терминал Face ID. Операторы
вынуждены вручную конвертировать файлы... удалять пустые строки, запятые и
двоеточия».

## 1. Контекст

Существующий delta-экспорт (`views/export.py::export_delta`, Story 4.3,
Integration Spec v1.1) уже делает ровно то, что нужно по логике: выбирает
новых `ready`-участников категории с прошлого экспорта, атомарно переводит их
в `exported`, пишет `ExportLog` + audit, отдаёт ZIP (`attendees.json` + медиа).
Единственная реальная проблема — **формат** (JSON), не сама механика выборки.

## 2. Решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Новый эндпоинт или параметр существующего? | Параметр `?format=csv` того же `export_delta` | Не дублировать delta-выборку/atomic-транзакцию/ExportLog/audit — расхождение между двумя копиями этой логики было бы риском реальной рассинхронизации выгрузки |
| CSV — внутри того же ZIP или отдельным файлом? | Отдельный `.csv`-файл в ответе (не ZIP) | Терминалу нужен «готов к прямой загрузке» файл — заворачивать его в архив с фото противоречит буквальной цели докладной. Фото по-прежнему доступны через `?format=json` (ZIP), как раньше |
| Набор полей/порядок колонок | Тот же набор, что в `build_export_object` (Integration Spec v1.1) | Единственный согласованный с Erda набор полей (resident-ИИН и т.д.); не изобретаю новый |
| Кодировка | UTF-8 с BOM (`utf-8-sig`) | Стандартная практика для кириллицы в CSV, читаемом Windows-софтом/Excel-подобными системами — терминалы такого типа обычно на Windows |
| Экранирование | `csv.writer` с `QUOTE_ALL` | Докладная явно жалуется на «лишние... запятые и двоеточия» ломающие текущий ручной процесс — QUOTE_ALL гарантирует, что запятая/кавычка внутри поля (ФИО, место работы и т.п.) не порвёт структуру строки |
| Разделитель строк | `\r\n` (стандарт CSV/RFC 4180) | Максимальная совместимость с Windows-ориентированным терминальным ПО |
| Audit-действие | Новое `export.delta_csv` в существующую категорию `"export"` | Не создаю новую категорию реестра (нарушило бы `test_registry_has_exactly_expected_categories`); differentiates CSV export in audit trail from `export.download` (JSON) |

## 3. Открытый вопрос (НЕ решаю сам — нужен вендор/служба)

**Точная схема колонок, которую ожидает конкретное терминальное ПО Face ID
(имена колонок, их порядок, обязательные vs опциональные, кодировка per
конкретного вендора) — неизвестна из репозитория.** Использую существующий
согласованный набор полей Integration Spec v1.1 как разумную отправную точку
(это тот же набор, что уже уходит в службу охраны в JSON). Если у терминала
свой конкретный формат — это локализовано в ОДНОЙ функции-билдере
(`build_export_csv_rows`), править только маппинг колонок, вся механика
(delta/atomic/audit) не меняется.

## 4. Архитектура

- `eventproject/services/export.py`: новая функция `build_export_csv_rows(attendees, dir_names) -> (header, rows)` — переиспользует те же значения полей, что `build_export_object`, но плоским списком строк вместо dict (без вложенности, без `photo_file`/`doc_scan_file` — фото передаются отдельно через `?format=json`, CSV — только данные участника для загрузки в стойку).
- `views/export.py::export_delta`: ветвление в конце функции — при `request.GET.get("format") == "csv"` строит CSV-ответ (`HttpResponse(content_type="text/csv; charset=utf-8-sig")`) вместо ZIP; delta-выборка/`ExportLog`/переход статуса/audit — **общий код**, выполняется один раз до ветвления.
- Имя файла: `attendees_<category>_<timestamp>.csv` (тот же `_safe_category` helper, что и у ZIP).

## 5. Тестирование

- `build_export_csv_rows`: заголовок соответствует ожидаемому набору колонок; строка со спецсимволами (запятая/кавычка в ФИО) корректно экранируется и парсится обратно тем же `csv.reader`; нерезидент → ИИН пустой (та же логика, что в JSON).
- View: `?format=csv` возвращает `text/csv`, тот же набор участников, что и `?format=json` (та же delta-выборка); повторный вызов без новых участников → тот же ответ AC-5 «нет новых записей», что и сейчас; `ExportLog`/audit/переход статуса создаются РОВНО ОДИН РАЗ независимо от формата (не дублируются при смене format между вызовами на одних и тех же данных — это гарантируется тем, что once `ready→exported`, повторный выбор их не найдёт).
- Аудит: `export.delta_csv` зарегистрирован в `SIGNIFICANT_ACTIONS["export"]` + coverage-тест в `test_audit_action_coverage.py`.
