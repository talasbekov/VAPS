# hd-2-4 / hd-2-5 — Telegram: привязка chat_id и уведомления без ПДн

Дата: 2026-08-23 · Stories: hd-2-4-telegram-chatid-binding, hd-2-5-telegram-notifications-pii-min
Ветка: `security-hardening` · Роадмап: `epics-hardening.md` §2.4/2.5 (FR-6, NFR-9).

## 1. Решения по блокерам (приняты автономно)

Считалось, что нужны «бот и решение, что писать в сообщение».

**Бот.** Токен читается из окружения; **без токена функция выключена целиком** —
привязка недоступна, отправка не происходит, ошибок нет. Значит код можно влить и
проверить, не заводя бота: он просто спит. Сам сетевой вызов изолирован в одну
функцию-транспорт, которую тест подменяет — это же место потом подменяется на
реальный HTTP без изменения остальной логики.

**Что писать.** NFR-9 говорит: канал вне РК, значит ПДн туда не идут. Решение
жёстче формулировки AC: **в сообщении нет ни ФИО, ни ИИН, ни причины возврата** —
только тип события, номер заявки и приглашение открыть систему. Причина возврата —
свободный текст админа, который уже пришлось скрабить от ИИН (fe-3.7): переносить
его в трансграничный канал нельзя. Инвариант проверяется сканером по телу
сообщения, как в hd-1.1.

Формально AC 2.5 разрешает «№ заявки/событие/причина». Причину сознательно
исключаю и фиксирую расхождение здесь: увидеть её оператор может в системе,
которая для этого и существует, а цена ошибки в трансграничном канале несоизмерима.

## 2. Привязка (2.4)

Ключевое требование AC: **привязку инициирует сам оператор**, админ не может
привязать чужой chat_id.

```
оператор в системе → «привязать Telegram» → одноразовый код (TTL 15 мин)
   → он же отправляет код боту → бот подтверждает: код + chat_id
   → chat_id сохраняется тому оператору, который код запрашивал
```

- код одноразовый: подтверждён либо просрочен — второй раз не работает;
- код принадлежит конкретному оператору: чужой chat_id к нему не привязать, не
  зная кода, а код виден только тому, кто его запросил в системе;
- повторный запрос кода отменяет предыдущий (иначе «висящие» коды копятся);
- отвязка доступна самому оператору в любой момент.

`chat_id` — не ПДн, но идентификатор; хранится через `EncryptedCharField` (тот же
Fernet, что у ИИН): дамп БД не должен давать карту «оператор → его Telegram».

## 3. Отправка (2.5)

Врезается туда же, где живёт in-app-уведомление (hd-2.3) — в `notify()`. Порядок
принципиален: **сначала создаётся in-app-запись, потом отправляется Telegram**, и
сбой отправки не откатывает и не теряет уведомление (AC: «гарантированный
fallback in-app»). Telegram — дополнение к источнику событий, а не его замена.

## 4. Границы

- Приём сообщений ботом (webhook/polling) не строится: это отдельный процесс и
  отдельная поверхность атаки. Подтверждение кода — функция
  `confirm_binding(code, chat_id)`, которую вызовет будущий бот-обработчик.
- Ретраев отправки нет: событие уже сохранено in-app, а очередь ради
  вспомогательного канала — избыточна.
- Отражение трансграничности в согласии (связь с 7.3) — текст документа, не код.

## 5. Проверка

- Без токена: привязка не предлагается, отправка не идёт, ошибок нет.
- Код одноразовый, с TTL, повторный запрос гасит предыдущий.
- Чужой chat_id нельзя привязать без кода (негативный тест из AC).
- В теле сообщения нет ФИО, ИИН и причины возврата (сканер).
- Сбой отправки не теряет in-app-уведомление и не роняет решение проверяющего.
- Отвязка прекращает отправку.

## 6. Итог ревью (независимый агент, 2026-08-23)

Оба заявленных инварианта тестами держатся (мутанты «подтверждать любой код»,
«игнорировать TTL», «ФИО+ИИН в сообщении», «код не гасится» — убиты). Найдено
**пять Important**, все исправлены:

1. **Повторный запрос кода МОЛЧА убивал рабочую привязку.** `update_or_create`
   обнулял `chat_id`/`confirmed_at`: оператор, у которого Telegram уже работал,
   нажав «привязать» второй раз и не отправив код боту, терял уведомления
   навсегда и без единого признака в UI. Спека говорила «гасит предыдущий КОД» —
   код гасил всю привязку. Теперь меняется только код; привязка — лишь успешным
   подтверждением.
2. **Гонка в `confirm_binding`** (read-modify-write без лока) делала
   одноразовость кода видимостью: два параллельных подтверждения с одним кодом
   оба проходили проверки, побеждал записавший последним. Сценарий: код утёк
   (переслан не в тот чат, попал в лог бота) — атакующий шлёт свой `confirm`
   одновременно с легитимным и забирает привязку. Теперь строка берётся под
   `select_for_update`.
3. **`chat_id` писался в лог открытым текстом** — при том что колонку шифруют
   Fernet ровно ради модели угроз «дамп не должен давать карту оператор→Telegram».
   Лог не шифруется, а соседние строки того же запроса несут `user_id`, так что
   сопоставление по таймстампу тривиально.
4. **Отправка шла ВНУТРИ транзакции** (`notify` зовётся из `_record_decision` под
   `atomic` + `select_for_update`). С настоящим HTTP это означало бы: сетевой
   вызов держит row-lock всё время запроса к api.telegram.org; откат ПОСЛЕ
   отправки = трансграничное сообщение о решении, которого не было; проглоченная
   `DatabaseError` внутри atomic откатывает решение при 200 OK — ровно то, что AC
   2.5 запрещает. Перенесено в `transaction.on_commit`: инвариант «шлём только
   закоммиченное» стал структурным.
5. **Не было ни одной точки входа:** `request_binding_code` не вызывался ниоткуда,
   то есть AC «оператор запрашивает код В СИСТЕМЕ» был недостижим, а инвариант
   «админ не может привязать чужой chat_id» держался тривиально — не мог НИКТО.
   Добавлен `/api/v1/telegram/` (bind/unbind/status): код выдаётся только СЕБЕ,
   ни один параметр запроса не позволяет указать другого оператора.

Minor: `logger.exception` заменён на узкое логирование без traceback (исключения
HTTP-клиента несут URL, а URL Bot API содержит ТОКЕН); добавлен индекс на
`code_hash`; убрана недостижимая ветка проверки пустого хеша.

Отдельно: мутация «вернуть `chat_id` в лог» сначала ВЫЖИЛА — тест на это
отсутствовал. Добавлен, мутация теперь убивается.
