# hd-2-3 — In-app уведомления оператору (реальный источник вместо производного состояния)

Дата: 2026-08-22 · Story: hd-2-3-inapp-notifications-inbox · Ветка: `security-hardening`
Роадмап: `epics-hardening.md` §Story 2.3 (FR-6, in-app) · смыкается с `fe-3-7`.

## 1. Проблема

`fe-3-7` дал оператору бейдж и инбокс, но **источником** там служит производное
состояние — queryset `returned=true` (`submitted` + `return_count > 0`). Из этого
следуют три дефекта, и один из них уже отложен в `deferred-work.md`:

1. **Нет «прочитано».** Бейдж гаснет только когда оператор реально починит
   заявку. Увидел — не значит обработал; счётчик не отражает «новое».
2. **Виден ровно один тип события.** Возврат — да; одобрение, смена статуса,
   любое будущее событие — нет. Петля «узнать о судьбе заявки» (AC истории)
   закрыта наполовину.
3. **Устаревание** (отложено ревью `fe-3-7`): ни одна мутация не инвалидирует
   `['returns-count']`/`['returns-inbox']`, возврат инициирует ДРУГОЙ пользователь
   → до ~30 с бейдж врёт. Ревью прямо записало: «hd-2-3 становится реальным
   источником — тогда бейдж/инбокс читают его (не дубль-механизм)».

AC истории требует того же: **бейдж-счётчик и инбокс читают этот же источник, не
дубль-механизм**.

## 2. Решение

### Модель `Notification` — БЕЗ копии ПДн

```
recipient   FK(Operator)      # кому (владелец заявки)
kind        CharField          # attendee.returned | attendee.approved
attendee    FK(Attendee, SET_NULL, null)   # о чём
actor       FK(User, SET_NULL, null)       # кто вызвал событие
created_at  DateTimeField(db_index)
read_at     DateTimeField(null)            # null = непрочитано
```

**Текста уведомления в БД нет вообще** — только ссылки. Причина та же, что в
hd-4-3 и hd-3-1: durable-строка, живущая дольше самой записи, не должна
становиться вторым незашифрованным экземпляром ПДн. Формулировка («Заявка
Иванова возвращена: причина…») собирается на фронте из уже доступных оператору
данных, локализуется через i18n и не дублируется в трёх языках на бэкенде.
Отдельно: `last_return_reason` — свободный текст админа, который ревью `fe-3-7`
уже заставило скрабить от ИИН; копировать его в уведомление означало бы завести
ВТОРУЮ копию с тем же риском.

### Кто получатель

`attendee.request.created_by` — оператор, подавший заявку. ⚠ Это НЕ то же самое,
что видимость участника (`events ∩ category`), — ревью показало, что множества
реально расходятся (у оператора отобрали мероприятие: участник 404, уведомление
о нём — 200). Поэтому queryset сужается ОБОИМИ условиями: получатель И видимость
участника; только тогда «доступ к уведомлению = доступ к заявке» становится
правдой, а не декларацией.

### Где создаётся

В `_record_decision()` (`views/attendee_api.py`) — **уже существующая** единая
точка approve/return, ради которой fe-3.6 её и заводил. Одна врезка = оба
события, внутри той же `transaction.atomic()`, что и решение: решение без
уведомления невозможно. Это и есть «гарантированный in-app fallback» для 2.5:
Telegram будет отдельным, ПОСЛЕДУЮЩИМ слоем, а не заменой in-app.

### API

- `GET /api/v1/notifications/` — свои уведомления (scoped, пагинация);
- `GET /api/v1/notifications/unread_count/` — источник бейджа;
- `POST /api/v1/notifications/{id}/read/` — пометить прочитанным;
- `POST /api/v1/notifications/read_all/` — пометить все.

Scope — **fail-closed**: `recipient=own operator` И участник в видимом scope
(`attendee=None` — история удалённого участника — остаётся). Чужое уведомление не
читается и не помечается (404, не 403 — не раскрываем факт существования).

### Фронтенд

- бейдж `['returns-count']` → `['notifications-unread', kind]`, источник
  `unread_count?kind=attendee.returned`;
- `ReturnsInboxPage` остаётся списком РАБОТЫ (ФИО, причина, счётчик возвратов —
  уведомление этих полей намеренно не несёт), но состояние «новое» берёт из
  уведомлений: при успешной загрузке НЕПУСТОГО списка помечает прочитанными
  возвраты и инвалидирует ключ бейджа.

**Почему бейдж считает один тип, а не все** (исправлено по ревью): экран
называется «Возвраты» и показывает только возвраты. Бейдж, считавший все типы,
означал бы, что оператор видит «3», открывает экран, видит пустой список — и
`read_all` гасит уведомления об одобрении, которых он не видел ни разу. Теперь
клиент явно говорит, о каком типе спрашивает и что гасит; непоказанное не
помечается прочитанным и ждёт своего экрана/канала.

## 3. Границы

- Telegram (2.4/2.5) — вне скоупа: здесь строится источник, на который тот слой
  будет опираться.
- Реального push/WebSocket нет — инвалидация по мутациям + refetch. Событие
  инициирует другой пользователь, поэтому мгновенность без источника событий
  невозможна; уведомление хотя бы перестаёт быть производным и умеет «прочитано».
- Уведомления о создании/удалении участника не заводим — оператор сам их автор.
- **Одобрения копятся в источнике, но UI их пока не показывает** — отдельный
  экран «все уведомления» либо Telegram-канал (2.5). Важно, что они больше не
  уничтожаются молча: бейдж и пометка прочтения ограничены типом «возврат».

## 4. Проверка

- Возврат заявки → у ЕЁ оператора появилось непрочитанное; у чужого — нет.
- Одобрение → уведомление другого `kind` (тип события различим).
- В сериализованном уведомлении нет ФИО/ИИН/причины (сканер по телу ответа).
- Чужое уведомление: `read` → 404, в списке не видно.
- `unread_count` падает после `read`; `read_all` обнуляет.
- Решение и уведомление атомарны: сбой создания уведомления откатывает решение.

## 5. Итог ревью (независимый агент, 2026-08-22)

Подтверждено: врезка покрывает ВСЕ пути решений (approve/return — единственные,
других переходов в READY/возврат нет), атомарность реальна (убрать врезку — 10 из
15 тестов падают), ПДн в модели/сериализаторе нет, scope fail-closed для
суперпользователя без Operator. Найдено и исправлено четыре Important:

1. **Инбокс не читал новый источник, и уведомления об одобрении гасились, ни разу
   не показавшись.** Бейдж считал ВСЕ типы, список показывал только возвраты,
   `read_all` гасил всё. Исправлено `?kind=`-сужением: бейдж и пометка ограничены
   типом «возврат», одобрения остаются непрочитанными до своего экрана/канала.
   Мёртвая схема уведомления во фронт-клиенте удалена (списка фронт не запрашивает).
2. **`markAllRead` срабатывал при ошибке загрузки и на пустом списке** — оператор
   видел error-state, а события уже были погашены навсегда. Теперь пометка идёт
   только после успешной загрузки непустого списка.
3. **Scope уведомления ≠ scope заявки** (спека обещала совпадение — неверно):
   фильтр шёл только по `recipient` (`Request.created_by`), а видимость участника
   резолвится через `events ∩ category`. При `events.clear()` участник отдавал
   404, а уведомление о нём — 200 с его id. ПДн там нет, но обещание было ложным.
   Добавлено сужение по `get_operator_attendee_queryset` (с сохранением
   `attendee=None` как истории события).
4. **`models.py` целиком переехал CRLF→LF**, из-за чего диф показывал 1362 строки
   вместо 65 и обнулялся `git blame`. Возвращены исходные окончания строк.

Minor: докстринг `notify()` неверно ссылался на cron (`Request.created_by`
non-nullable — ветка недостижима на живых путях, оставлена как defensive-контракт);
`read_all` возвращал жёсткий `unread: 0` — теперь перечитывает остаток;
формулировка в `Attendee.__str__` завышала эффект (ФИО там остаётся — ушёл именно
ИИН). Замечание про «мёртвый мок `getAttendees` в AppShell.test» проверено и
отклонено: мок питает интеграционный рендер `AttendeesPage` под AppShell.

Все три содержательных исправления перепроверены мутационно (снятие сужения по
scope — 1 падение, игнор `kind` — 2, пометка без проверки загрузки — 2).
