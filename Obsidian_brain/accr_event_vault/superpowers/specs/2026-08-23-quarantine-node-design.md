# hd-5-4 — Узел «Не распределено»: карантин беспризорных заявок

Дата: 2026-08-23 · Story: hd-5-4-unassigned-quarantine-node · Ветка: `security-hardening`
Роадмап: `epics-hardening.md` §Story 5.4 (FR-22 orphan) · связь с Epic 3 (импорт).

## 1. Решение по блокеру (принято автономно)

Задача считалась заблокированной формулировкой «нужны продуктовые решения: что
такое карантинный узел». Решаю так:

**«Не распределено» — это не новая сущность, а обычное листовое мероприятие с
флагом `is_quarantine`, автоматически создаваемое под своим контейнером.**
Причины выбрать флаг, а не отдельную модель:

- вся существующая машинерия (scope-резолвер `events ∩ category`, leaf-only
  из hd-5.2, PROTECT-удаление из hd-5.8, экспорт, очередь проверки) начинает
  работать с карантином **без единой правки** — новая сущность потребовала бы
  трогать каждое из этих мест, и каждое стало бы новым местом для ошибки;
- «карантин» — это состояние привязки, а не другой тип объекта.

Один карантинный лист на контейнер (не один глобальный): иначе заявки разных
мероприятий смешались бы в общей куче, а операторский scope стал бы бессмысленным.

## 2. Что закрывается

Сегодня беспризорной заявке деваться некуда, и код выбирает **молчание**:

1. Импорт с неизвестным event_id (`cron.py` жёстко зашивает `pk=797`) —
   если события нет, тик просто пишет ошибку в лог и выходит: анкета остаётся в
   очереди источника навсегда, никто об этом не узнаёт.
2. Заявка, поданная до нарезки мероприятия на под-события, висит на будущем
   контейнере — а hd-5.2 (leaf-only) запретил заявки на контейнерах. То есть
   исторические заявки контейнера сейчас в подвешенном состоянии.

## 3. Механика

- `Event.is_quarantine` (bool) + `Event.get_or_create_quarantine(parent)` —
  создаёт лист «Не распределено» под контейнером (`parent=контейнер`,
  `is_container=False`, имя во всех трёх языках).
- **Импорт с неизвестным событием → reject, не тихая привязка** (AC): импорт
  НЕ создаёт карантинный узел сам и не подставляет его молча. Он пишет
  `ImportLog(status=conflict)` и не подтверждает анкету источнику — то есть
  ведёт себя ровно как временный сбой из hd-3.2, что и правильно: неизвестное
  событие — проблема конфигурации, а не данных, и решается человеком.
- Перенос из карантина — существующий путь смены `Request.event` (перепривязка,
  которую hd-4.3 уже сделала видимой в field-level истории).
- Карантинный лист **нельзя удалить, пока в нём есть заявки** — это уже даёт
  PROTECT из hd-5.8, дополнительной защиты не требуется.

Новый статус `ImportLog.STATUS_CONFLICT` — отдельный от `validation_error`
(там битые данные) и от `upstream_error` (там сбой канала): здесь данные целы,
а система не знает, куда их положить.

## 4. Границы

- UI карантина («распределить») — часть hd-5.6 (фронт-срез иерархии).
- Автоматическая миграция уже существующих заявок контейнеров в карантин **не
  делается**: это массовая правка живых данных, которую нельзя запускать из
  релиза. Даётся management-команда `quarantine_orphan_requests --dry-run`.
- `kazexpo_receive` (Avalon) не трогаем — отключён в cron (та же граница, что
  hd-3.1/hd-3.2).

## 5. Проверка

- `get_or_create_quarantine` идемпотентен: повторный вызов не плодит узлы.
- Карантинный узел — лист (заявки к нему крепятся, hd-5.2 не мешает).
- Импорт с неизвестным событием: `ImportLog(conflict)`, ACK НЕ отправлен,
  анкета не привязана никуда.
- Команда переноса: `--dry-run` ничего не меняет; перенос ставит заявке
  карантинный лист того же контейнера и не трогает чужие заявки.
- Scope: оператор карантинного листа видит только его заявки (обычный резолвер).

## 6. Что получилось (реализация)

- `Event.is_quarantine` + `Event.get_or_create_quarantine(container)` (миграция 0041) —
  идемпотентная фабрика листа «Не распределено» с трёхъязычным именем.
- `quarantine_orphan_requests --dry-run` — разбор УЖЕ существующих заявок,
  висящих на контейнерах. Такие строки могли появиться только до hd-5.2 (там
  проверка стоит лишь на создании), поэтому и в тестах они воспроизводятся через
  `.update()`, минуя `save()` — это точная модель того, как они возникли в проде.
- Перенос аудируется отдельным действием `request.quarantined` (внесено в
  `SIGNIFICANT_ACTIONS` с чек-лист-тестом): смена мероприятия у заявки меняет её
  scope — событие того же класса, что перепривязка участника из hd-4.3.
- Импорт с неизвестным событием: `ImportLog(status=conflict)` (новый статус,
  миграция 0042) + 404. Раньше тик возвращал 404 молча, не оставляя следа в
  durable-журнале.

Проверено, что карантин наследует всю существующую машинерию без правок: к нему
крепятся заявки (leaf-only не мешает), его нельзя удалить с живыми заявками
(PROTECT из hd-5.8), у каждого контейнера свой узел.

## 7. Итог ревью (независимый агент, 2026-08-23)

Ревью **опровергло центральный тезис спеки** — «вся машинерия работает без единой
правки». Нашлось четыре места, где карантин молча ломал существующие инварианты,
и одно, где новая логика в проде недостижима. Всё исправлено.

1. **[Critical] Участники карантина не удалялись по TTL НИКОГДА.** Узел
   создавался без дат («служебный»), а `purge_expired_pdn` пропускает событие без
   даты окончания. То есть записи, которые дольше всего никто не разбирает,
   выпадали из NFR-6 навсегда. Даты (и `pdn_retention_days`) теперь наследуются от
   контейнера — это же чинит и невидимость узла в легаси-админке, которая строит
   списки мероприятий фильтром по датам.
2. **[Critical] Ветка `ImportLog(conflict)` была недостижима из прода.** `cron.py`
   резолвит `Event`/`Operator` САМ, до вызова view, и просто выходил с записью в
   stdout — ровно тот молчаливый сценарий, который история закрывает. Тест был
   зелёным, потому что дёргал view напрямую. Запись перенесена в `cron._run_import`.
3. **[Important] Фабрика обходила `clean()`** (`objects.create`) и создавала
   ТРЕТИЙ уровень иерархии под уже вложенным событием; **не выставляла
   `is_container`** у родителя (флаг ведётся руками), из-за чего `Request.clean()`
   продолжал пускать заявки на сам родитель — плодя новых беспризорных; **не имела
   уникального ограничения**, поэтому гонка давала два узла «Не распределено» под
   одним контейнером.
4. **[Important] Команда искала не те заявки:** фильтр по `is_container` пропускал
   исторические контейнеры без ручного флага — то есть выводила «перенесено: 0»
   ровно в том сценарии, ради которого написана. Теперь предикат по факту наличия
   детей.
5. **[Important] `/api/v1/events/` отдавал карантин как обычное мероприятие** — без
   признака фронт не отличит его от под-события. Добавлено `is_quarantine`.
6. **[Minor] Экспорт карантина ничем не блокировался** (синтетический `QRT-N`
   проходил гейт `event_code`) — теперь явный отказ: выгрузить нераспределённых в
   госорган значит аккредитовать людей, которых никто не распределял.

Отдельно поучительное: старый тест `test_import_into_container_returns_400_and_logs_no_attendee`
УТВЕРЖДАЛ отсутствие записи в журнале — то есть закреплял молчаливый отказ как
ожидаемое поведение. Он обновлён: теперь ожидается `conflict`.
