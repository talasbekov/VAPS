# Design: ЭЦП-гейт обязательства о неразглашении ПДн (hd-7-3)

**Дата:** 2026-08-21
**Статус:** approved (design согласован с Erda в чате; открытые технические детали
ниже решены автономно в рамках делегированной ночной сессии — см. `docs/LOG.md`).
**Источник требования:** докладная записка 3-го управления Второго департамента
Службы, п.1. Backlog-тикет: `hd-7-3-pdn-consent-record` (`_bmad-output/implementation-artifacts/sprint-status.yaml`).

## 1. Проблема

Ответственные лица сторонних организаций (операторы) при первом входе получают
прямой доступ к вводу ПДн своих сотрудников. Обязательство о неразглашении сейчас
собирается на бумаге — бюрократично и не привязано к системе технически: ничто не
мешает оператору начать работать с ПДн, не подписав обязательство.

## 2. Согласованные решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Тип подписи | Упрощённое электронное подписание (не PKI/NCALayer) | Работает офлайн/air-gap, без внешней инфраструктуры; юридически достаточно для внутреннего регламента службы (не квалифицированная подпись в смысле закона об ЭЦП РК — это явно не то же самое, что настоящая ЭЦП; **открытый вопрос к юристу/заказчику**, см. §7) |
| Кто подписывает | Все операторы (не суперпользователи), при первом входе | Формулировка докладной — «ответственные лица сторонних организаций» = роль Operator |
| Версионирование текста | Да, с полем `document_version` на подписи | Текст обязательства может измениться; переиздание требует повторного подписания |
| Источник текста | Редактируется в Django admin | Сайт трёхязычный (ru/kz/en); суперпользователь правит без деплоя |
| Блокировка API | Да, 403 JSON с `code=pdn_consent_required` | Единообразно с `ForcePasswordChangeMiddleware` |
| Порядок гейтов | Сначала смена пароля, потом NDA | Пароль — гигиена аккаунта (только владелец может подписывать), NDA — юридический шаг поверх защищённого аккаунта |
| Механизм подтверждения | Чекбокс + повторный ввод пароля (вариант B) | Единственный вариант, доказывающий владение аккаунтом, без внешних зависимостей |

## 3. Архитектура

Три новых компонента, зеркалящие существующий `ForcePasswordChangeMiddleware`
(`eventproject/middleware/force_password_change.py`):

- **`PdnConsentDocument`** (модель, `eventproject/models.py`): `version` (AutoField/int),
  `text_ru`, `text_kz`, `text_en` (TextField), `is_active` (bool), `created_at`,
  `created_by` (FK User, nullable). Ровно одна запись с `is_active=True` в любой
  момент времени — обеспечивается в `save()`.
- **`PdnConsentSignature`** (модель): `operator` (FK Operator), `document_version`
  (FK PdnConsentDocument), `signed_at`, `ip` (GenericIPAddressField), `user_agent`
  (TextField, обрезать до разумной длины). `unique_together = ("operator", "document_version")`
  — защита от дублей при гонке двух вкладок. Записи неизменяемы (нет update-путей в
  коде вне создания).
- **`PdnConsentGateMiddleware`** (`eventproject/middleware/pdn_consent_gate.py`):
  подключается в `MIDDLEWARE` **сразу после** `ForcePasswordChangeMiddleware`.

## 4. Поток данных

1. Успешный логин → `ForcePasswordChangeMiddleware` (если применимо) →
   `PdnConsentGateMiddleware.__call__`.
2. `_should_gate(request)`: `False` для суперпользователя, неаутентифицированных,
   exempt-путей (`pdn_consent`, `logout`, `change_password`/`new_password` — на
   случай если force_password_change ещё активен параллельно, `/static`, `/media`,
   `/api/health`). Иначе: есть ли активный документ? Если активного документа нет —
   **fail-open** (не блокировать; залогировать `logger.warning`) — так фича не
   ломает вход всем операторам в день релиза, пока админ не создал первый документ
   через admin. Если активный документ есть — есть ли у `request.user.operator`
   `PdnConsentSignature` с `document_version_id == active_document.id`? Нет → gate.
3. HTML-запрос (`not path.startswith("/api/")`) → `redirect("/pdn_consent/")`.
   API-запрос → `JsonResponse({"detail": "Требуется подписание обязательства о
   неразглашении ПДн.", "code": "pdn_consent_required"}, status=403)`.
4. `GET /pdn_consent/` (новая view, `eventproject/views/pdn_consent.py`): рендерит
   активный документ на языке текущего интерфейса (ru/kz/en — определяется так же,
   как остальные вьюхи: через префикс `/kz/`, `/en/` зеркальных urls.py, аналогично
   `user_login`/`change_password`), чекбокс «Ознакомлен(а) и согласен(на)», поле
   пароля, скрытое поле `next`.
5. `POST /pdn_consent/`: валидация — чекбокс отмечен И
   `authenticate(request, username=request.user.username, password=...)` возвращает
   того же пользователя. Успех → `PdnConsentSignature.objects.get_or_create(operator=...,
   document_version=active_document, defaults={"ip": ..., "user_agent": ...})` внутри
   `transaction.atomic()` → `audit_log(action="pdn_consent.sign", ...)` → редирект на
   безопасный `next` (переиспользовать `_safe_next_url` из `views/views.py`, не
   дублировать логику) или дефолт `/application/`. Неуспех (галочка не стоит ИЛИ
   пароль неверный) → тот же шаблон с сообщением об ошибке, без создания записи и
   без audit-записи.

## 5. Обработка ошибок и граничные случаи

- **Активная версия сменилась после подписания.** Прежняя подпись не даёт доступа к
  новой версии (сравнение по `document_version_id`) — оператор гейтится снова.
  История подписей не трогается (аудиторский след сохраняется).
- **0 или 2+ активных документов.** `PdnConsentDocument.save()`: при
  `is_active=True` — в той же транзакции снять флаг со всех остальных
  (`PdnConsentDocument.objects.exclude(pk=self.pk).update(is_active=False)`).
  0 активных — fail-open, см. §4 п.2.
- **Гонка двух вкладок.** `get_or_create` + `unique_together` на уровне БД —
  вторая попытка тихо становится no-op (не ошибкой), редирект всё равно проходит.
- **Rate limiting.** Форма подписания под тем же `RatelimitMiddleware`, что уже
  глобально подключён (`eventproject/middleware/ratelimit.py`) — отдельного лимита
  не заводим, POST на пароль уже под общим прикрытием сессии (оператор уже прошёл
  `django-axes` на логине).

## 6. Тестирование (TDD, зеркалит `test_force_password_change`-стиль)

- Middleware: гейтит HTML/API без подписи → пропускает с подписью на активную
  версию → гейтит повторно после смены активной версии → не гейтит суперпользователя
  → не гейтит exempt-пути → fail-open при отсутствии активного документа (с логом
  warning).
- View: неверный пароль/неотмеченный чекбокс не создают подпись и не пишут аудит;
  успех создаёт подпись + audit_log-запись `pdn_consent.sign` + корректный редирект
  (включая `next`).
- Модель: `save()` гарантирует ровно одну активную версию; `unique_together` не даёт
  дублей подписи (race-тест по аналогии с `test_export_concurrency.py`, если время
  позволит — иначе достаточно constraint-теста на уровне БД).
- RBAC-матрица (`eventproject/tests/rbac_matrix.py`) — добавить `/pdn_consent/` как
  известный публичный-для-аутентифицированных-операторов путь, если матрица требует
  явного перечисления.

## 7. Открытые вопросы к пользователю (НЕ решаю сам — юридические/продуктовые)

1. Является ли «упрощённое электронное подписание» (чекбокс + пароль, без PKI)
   юридически достаточным для формулировки «ЭЦП» в докладной, или требуется
   согласование с юристом/заказчиком службы? Реализую упрощённый вариант как
   технически корректную MVP-основу; переход на настоящую ЭЦП/NCALayer — отдельная
   будущая итерация поверх той же модели данных (`document_version` не завязан на
   способ подписи).
2. Нужно ли ретроактивно гейтить уже существующих операторов (у которых нет вообще
   ни одной подписи) — дизайн выше это делает автоматически (нет подписи → гейт),
   но это значит, что при выкатке фичи **все текущие операторы** будут
   заблокированы до подписания при следующем входе. Это ожидаемое поведение или
   нужен льготный период/уведомление заранее? Реализую как есть (немедленный гейт
   для всех), т.к. это буквально то, что просит докладная («блокировать доступ до
   момента... подписания»).
