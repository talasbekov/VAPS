# Бизнес-процессы системы аккредитации

Простое, «человеческое» описание того, что система делает для пользователей.
Технические детали — в `architecture.md`, `data-models.md`, `api-contracts.md`.

## О чём система

«**Центр аккредитации**» для охранных/режимных мероприятий (заказчик — служба
госохраны, СГО РК). Организации (**операторы**) заранее подают **списки людей**,
которых нужно пропустить на мероприятие, с документами и фотографиями.
**Администратор** проверяет списки и **выгружает данные** в системы безопасности.
Дополнительно: модуль **QR-кодов по ИИН** и **автоматический импорт** заявок из
внешних систем.

Главные понятия (как «матрёшка»):

```
МЕРОПРИЯТИЕ ──1:N──► ЗАЯВКА (список) ──1:N──► УЧАСТНИК (человек)
     ▲
     └── к мероприятию привязаны ОПЕРАТОРЫ (N:M), которые ведут заявки
```

## Кто есть кто (роли)

| Роль | Что может |
|------|-----------|
| **Суперпользователь (админ)** | Всё: мероприятия, операторы, проверка, выгрузка |
| **Супероператор** | Расширенные права (видит события через API), помощник админа |
| **Оператор** | Заводит свои списки участников и отправляет их |
| **Пользователь** | Минимальный доступ (по умолчанию) |

## Карта ролей и сущностей

```
                ┌──────────────────────────────────────────────┐
                │           АДМИНИСТРАТОР (СГО)                 │
                │  создаёт мероприятия, заводит операторов,     │
                │  проверяет и выгружает данные                 │
                └───────────────┬──────────────────────────────┘
                  создаёт /      │       создаёт / привязывает
                  выгружает      │
            ┌──────────────┐ 1:N │ N:M ┌──────────────┐
            │  МЕРОПРИЯТИЕ  │◄────┴────►│   ОПЕРАТОР    │
            └──────┬───────┘           └──────┬───────┘
                   │ 1:N                       │ создаёт / ведёт
                   ▼                           ▼
            ┌────────────────────────────────────────┐
            │            ЗАЯВКА (список)              │
            │  Active → Checking → Sent → Exported    │
            └──────────────────┬─────────────────────┘
                               │ 1:N
                               ▼
                     ┌──────────────────┐
                     │     УЧАСТНИК      │  ФИО, ИИН (шифр.),
                     │                  │  фото, скан, документ
                     └──────────────────┘
```

## Процесс 1. Создание мероприятия (админ)

Админ создаёт мероприятие: название на трёх языках (рус/каз/англ), код, город,
даты начала и конца. Проверяется, что дата окончания не раньше начала и не в
прошлом. В списках показываются только актуальные мероприятия (заканчивающиеся в
ближайшие ~2,5 года).

## Процесс 2. Заведение операторов и доступов (админ)

- **Создаёт оператора**: ФИО, логин, телефон, организация. Пароль генерируется
  автоматически и показывается один раз.
- **Привязывает/отвязывает** операторов к мероприятиям (связь многие-ко-многим).
- Может **сбросить пароль** и **удалить** оператора.

## Процесс 3. Подача заявки оператором (главный рабочий процесс)

Оператор входит и видит мероприятия, к которым привязан. Далее:

1. **Создаёт заявку** для мероприятия — статус «Создано».
2. **Добавляет участников** по одному: ФИО, транслитерация, ИИН, дата рождения,
   пол, гражданство, должность, тип/серия/номер документа и его даты, **фото
   человека**, **скан документа**, объекты посещения, категория.
3. Система **проверяет**: документ не просрочен и уже выдан, дата рождения
   корректна, размер фото/скана в допустимых пределах, для граждан РК ИИН из 12
   цифр, и **нет дубликата** (один человек не добавляется на мероприятие дважды).
4. Участников можно **редактировать** и **удалять**. Удаление последнего участника
   удаляет и саму заявку.

## Процесс 4. Жизненный цикл заявки (статусы)

```
ОПЕРАТОР                                          АДМИНИСТРАТОР
   │ создать заявку
   ▼
[Active] ──добавить/править участников──┐
   │  ▲                                 │
   │  └─────────────────────────────────┘
   │ «Предпросмотр»
   ▼
[Checking] ──«Вернуться к редактированию»──► [Active]
   │ «Отправить»
   ▼
[Sent] ─────────────────────────────────────► проверка → выгрузка JSON
                                                     │
                                                     ▼
                                                [Exported] ──► в системы СГО
```

- **Active (Создано)** — можно редактировать.
- **Checking (Предпросмотр)** — список «заморожен» для проверки (можно вернуть).
- **Sent (Отправлено)** — ушло администратору, правка закрыта.
- **Exported (Принято/Выгружено)** — данные выгружены в систему безопасности.

(Автоимпорт использует свои статусы: «в обработке» → «завершено».)

## Процесс 5. Проверка и выгрузка данных (админ)

Админ открывает мероприятие, видит присланные заявки и **выгружает данные в JSON**:
весь список, только новых (ещё не выгруженных) или по одной заявке. После выгрузки
заявки помечаются «Выгружено», действие пишется в **журнал аудита** (кто/что/когда/
сколько участников). Эти JSON уходят в системы службы охраны.

## Процесс 6. Скачивание фотографий и архивов (админ)

Админ скачивает **ZIP со всеми фото и сканами** документов участников мероприятия
или отдельный подготовленный архив. Тяжёлые архивы могут готовиться в фоне (Celery),
статус проверяется отдельным запросом.

## Процесс 7. QR-верификация по ИИН (отдельный модуль)

Авторизованный пользователь вводит **ИИН**. Система строго проверяет его: ровно 12
цифр, корректная дата рождения внутри ИИН, верная контрольная цифра. При успехе
генерируется **QR-код** с этим ИИН и открывается страница успеха (QR можно
посмотреть и скачать). Используется как быстрый пропуск/проверка на входе. Страница
с QR доступна только создателю записи (или админу).

## Процесс 8. Автоматический импорт из внешних систем

```
KazEnergy (regist.kz)  ┐
                       ├─ каждые 2 мин ─► cron ─► забрать анкеты (+фото base64)
Avalon/KazExpo         ┘                          │  создать Заявку + Участников
(avalon.kazintec.kz)                              │  отсеять дубликаты/пустые поля
                                                  ▼
                                          ACK обратно в источник
                                          (принято / ошибка)
```

Система **каждые 2 минуты** сама обращается к внешним регистрационным системам по
API, забирает анкеты (с фото в base64), **создаёт заявку и участников**, проверяет
обязательные поля, отсеивает дубликаты и **подтверждает приём** обратно источнику
(ACK). Так данные партнёров попадают в аккредитацию без ручного ввода. Ключи API —
в переменных окружения, не в коде.

## Процесс 9. Управление паролями

Оператор **меняет свой пароль** (старый + дважды новый). Админ **сбрасывает пароль**
оператору. Есть защита от перебора (блокировка после серии неудачных входов,
django-axes) и ограничение частоты запросов.

## Процесс 10. Очистка устаревших мероприятий (админ)

Админ разом **удаляет старые мероприятия** (уже закончившиеся) вместе с их папками
фото/сканов — чтобы не копить лишние персональные данные.

## Процесс 11. Мультиязычность

Кабинет оператора и формы работают на **трёх языках**: русский (`/`), казахский
(`/kz/`), английский (`/en/`). Названия мероприятий и интерфейс — на выбранном языке.

## Процесс 12. Защита персональных данных (сквозной процесс)

Система работает с паспортными данными, поэтому:

- **ИИН шифруется** в базе (Fernet) — не читается напрямую из БД;
- **фото и сканы** отдаются только через защищённый доступ: оператор видит файлы
  **только своих** мероприятий, админ — все; чужие файлы недоступны (защита от
  подбора пути);
- **важные действия пишутся в аудит** (создание/удаление/выгрузка);
- доступ к API разграничен по ролям; секреты и PII не попадают в репозиторий и
  Docker-образ.
