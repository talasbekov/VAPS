# Аудит системы аккредитации — пробелы, риски, приоритеты

**Основа анализа:** `business-processes.md` + ранее виденная реализация (код экспорта `download_guests_json`, стек Django MVT / PostgreSQL / Redis / Celery / Fernet / django-axes, автоимпорт KazEnergy + Avalon, Face ID + air-gap деплой в Docker).
**Ограничение:** полный репозиторий недоступен. Статус «❓ неясно» = в документе не описано и по коду не подтверждено → требует проверки в репозитории, прежде чем считать сделанным.

Легенда статусов: ✅ реализовано · 🟡 частично · ❌ отсутствует · ❓ неясно (нужен код)

## 1. Краткое описание системы

1. Веб-система аккредитации участников на режимные мероприятия; конечный потребитель данных — служба охраны (выгрузка идёт в её системы и в терминалы Face ID).
2. Архитектура: Django (серверный рендеринг шаблонов; экспорт — FBV с `@user_passes_test(is_superuser)`), PostgreSQL, Redis, Celery, деплой в Docker, в т.ч. на офлайн/air-gap серверах.
3. Доменная «матрёшка»: Мероприятие → Заявка (список) → Участник; операторы привязаны к мероприятиям N:M.
4. 4 роли: суперпользователь (админ), супероператор, оператор, пользователь.
5. Жизненный цикл заявки: Active → Checking → Sent → Exported (возврат Checking→Active возможен оператором).
6. Экспорт в JSON помеченных `Sent` заявок с пометкой `Exported` и записью в аудит; этот JSON + фото/сканы переносятся в Face ID.
7. Автоимпорт каждые 2 мин по cron из KazEnergy/regist.kz и Avalon/kazintec: тянет анкеты с фото в base64, создаёт заявку+участников, отсев дублей, ACK обратно.
8. ПДн-защита: ИИН шифруется Fernet; доступ к фото/сканам — только к своим мероприятиям; аудит ключевых действий; секреты в env.
9. Безопасность входа: django-axes (блокировка перебора), rate limiting.
10. Мультиязычность ru/kz/en; ручная очистка устаревших мероприятий с папками файлов; (в описании заявлен модуль QR по ИИН, но процесс не расписан — Процесс 7 пропущен).

## 3. Недостающие обязательные функции

Для каждой: чего нет → почему нужно → что будет без неё → как реализовать.

### 3.1 Whitelist полей при экспорте JSON `[Critical]`
- **Нет:** экспорт сериализует участников через `model_to_dict(attendee)` — выгружаются *все* поля модели (зашифрованный ИИН, внутренние id, технические/служебные поля).
- **Почему:** терминалу Face ID и службе нужен фиксированный набор (ФИО, фото, документ, объекты, категория). Зашифрованный ИИН в JSON либо бесполезен, либо требует осознанной расшифровки.
- **Последствие:** в файл, который вручную переносят на флешке (air-gap), попадают лишние PII и мусорные поля; схема экспорта неконтролируема и ломается при изменении модели.
- **Как:** явный сериализатор (DRF Serializer или функция-builder) с белым списком полей; ИИН включать только если терминалу он реально нужен, и тогда расшифровывать явно; добавить `schema_version` в выгрузку.

### 3.2 Транзакционность и идемпотентность экспорта `[Critical]`
- **Нет:** в `download_guests_json` статусы `Sent→Exported` меняются в цикле без `transaction.atomic`; нет защиты от гонки/двойного клика.
- **Почему:** обрыв запроса оставит часть заявок `Exported`, часть `Sent`; повторный экспорт даст дубль отправки в службу.
- **Последствие:** рассинхрон состояния, двойная передача данных, спорный аудит «что реально выгрузили».
- **Как:** обернуть выборку+пометку в `transaction.atomic`, `Request.objects.select_for_update()`; повторная выгрузка — отдельное действие с подтверждением и отдельной записью аудита (`re-export`), не меняющее статус молча.

### 3.3 Возврат/отклонение заявки админом с причиной `[Critical]` — ✅ ЗАКРЫТО
> **Обновление 2026-08-22:** решено в **Attendee-уровне** через Epic fe-3 (React admin review queue),
> не в legacy Request-уровне, который эта заметка описывала. `fe-3-5-return-single` (done
> 2026-07-01): `POST /api/v1/attendees/{id}/return/`, FSM `in_review→submitted`
> (`eventproject/state_machine.py`), обязательный `reason`, `last_return_reason`/`return_count`,
> RBAC (только superoperator), полный audit (`attendee.returned`). Уведомление оператору (см. 3.6)
> закрыто на in-app/pull-уровне через `fe-3-7-operator-returns-inbox` (done). Легаси
> RU/KZ/EN HTML-флоу (`Request.status` "Sent→Active") эту возможность не получил и
> получать не будет — Strangler Fig, вытесняется React SPA. `sprint-status.yaml`
> (`hd-2-1-return-backend-fsm`) исправлен со stale `backlog` на `done`.
>
> Оригинальный текст ниже (для истории/трассировки):
- **Нет:** после `Sent` админ не может вернуть заявку оператору. Есть только операторский возврат `Checking→Active` (до отправки).
- **Почему:** при проверке админ находит ошибки (просрочен документ, плохое фото, не тот человек) и должен вернуть на исправление.
- **Последствие:** либо ошибочные данные уходят в выгрузку (человек не пройдёт Face ID / пройдёт не тот), либо админ правит чужую заявку вручную — теряется ответственность и аудит.
- **Как:** статус `Rejected`/`Returned` + поле `reject_reason` + кто/когда вернул; переход `Sent→Active` (только админ); уведомление оператору (см. 3.6).

### 3.4 Лог ошибок и повторная обработка автоимпорта `[Critical]`
- **Нет:** автоимпорт делает ACK, но не хранит неуспешные анкеты, нет лога ошибок и ретраев.
- **Почему:** источник может прислать битую/неполную анкету, может упасть сеть, прийти дубль.
- **Последствие:** анкета теряется молча — человек не аккредитован, расследовать нечем.
- **Как:** модель `ImportLog` (источник, ссылка на raw payload, статус, текст ошибки, попытки, время); ретрай с backoff (Celery); dead-letter для ручного разбора; ACK с кодом успех/ошибка (как уже сделано в `kazexpo_integ`).

### 3.5 Инвалидация сессий после смены/сброса пароля `[Critical]`
- **Нет:** старые сессии оператора не завершаются при смене/сбросе пароля.
- **Почему:** если пароль скомпрометирован и сброшен, активная сессия злоумышленника остаётся.
- **Последствие:** сброс пароля не отрезает доступ — мнимая защита.
- **Как:** при смене/сбросе обновлять `session_auth_hash` (Django делает при корректном flow `update_session_auth_hash`) и принудительно удалять остальные сессии пользователя (по `user_id` в таблице сессий).

### 3.6 Уведомления оператору `[High]`
- **Нет:** оператор не узнаёт о судьбе заявки и об ошибках автоимпорта по его источнику.
- **Почему:** цикл асинхронный — отправил и ждёт.
- **Последствие:** оператор не знает о возврате → участники не попадают на мероприятие вовремя; срывается SLA.
- **Как:** модель `Notification` (in-app минимум), триггеры на смену статуса заявки и на ошибку импорта; email/Telegram — опционально.

### 3.7 Фильтры и поиск в кабинете админа `[High]`
- **Нет:** нет фильтрации заявок по мероприятию/оператору/статусу и поиска участника.
- **Почему:** на режимном мероприятии — сотни участников и несколько операторов.
- **Последствие:** админ физически не находит нужную заявку/человека — система не работает на реальном объёме.
- **Как:** django-filter в кабинете + поиск по ФИО (по ИИН — только через расшифровку при необходимости, осознанно).

### 3.8 История изменений заявки/участника `[High]`
- **Нет:** аудит покрывает create/delete/export, но не правки полей.
- **Почему:** при спорах «кто поменял дату документа/ФИО» нужна трассировка.
- **Последствие:** невозможно доказать, кто внёс ошибочные данные.
- **Как:** `django-simple-history` или собственный change-log (поле, было/стало, кто, когда).

### 3.9 Согласие субъекта ПДн + политика хранения/TTL `[Critical]`
- **Нет:** не фиксируется основание обработки ПДн и срок хранения; очистка только ручная.
- **Почему:** РК закон №94-V ограничивает обработку без согласия; фото для Face ID — биометрия (повышенная чувствительность).
- **Последствие:** правовой риск, претензии регулятора, невозможность доказать законность обработки.
- **Как:** фиксировать основание обработки на уровне мероприятия/участника; авто-TTL удаление ПДн после мероприятия; зафиксировать политику. *(Не юридическая консультация — согласовать с юристом.)*

### 3.10 Контроль целостности экспорта для air-gap `[High]`
- **Нет:** JSON+фото переносятся вручную без контрольной суммы/манифеста.
- **Почему:** между бэкендом и терминалом нет сети — файл могут побить/подменить при копировании.
- **Последствие:** в терминал загрузят повреждённый/подменённый список доступа.
- **Как:** манифест с SHA-256 по каждому файлу + общий хэш (опц. подпись); проверка на терминале перед загрузкой.

## 5. Риски

### Безопасность
- `model_to_dict` в экспорте → утечка лишних полей/PII в файл (см. 3.1).
- Сессии не инвалидируются после сброса пароля (см. 3.5).
- Раздача media: заявлена защита от подбора пути — **проверить в коде** (X-Accel-Redirect / проверка прав, без public URL).
- Если есть GraphQL/REST наружу (были правки CORS/GraphQL) — закрыть introspection в prod, проверить CORS-whitelist и авторизацию по ролям на каждом резолвере/endpoint.
- Перенос на флешке в Face ID без хэш-манифеста (см. 3.10).

### Персональные данные
- Хранение **сканов документов** при наличии запрета РК на сбор копий удостоверяющих документов — согласовать с юристом/заказчиком.
- Биометрия (фото для Face ID) без зафиксированного согласия и TTL (см. 3.9).
- Расшифровка ИИН при экспорте — должна быть осознанной, не «по умолчанию через `model_to_dict`».
- JSON с PII на съёмном носителе — регламент уничтожения после загрузки.
- **Локализация серверов в РК** — подтвердить размещение (требование с 2025).
- PII в логах — проверить маскирование ИИН/документов.

### Бизнес-процесс
- Нет возврата заявки админом → либо плохие данные в выгрузке, либо ручная правка чужих заявок (см. 3.3).
- Нет уведомлений → срыв сроков аккредитации (см. 3.6).
- Нет истории правок → споры без трассировки (см. 3.8).
- Неидемпотентный экспорт → двойная отправка/рассинхрон (см. 3.2).

### Интеграции
- Молчаливая потеря анкет автоимпорта без лога/ретрая (см. 3.4).
- Наложение запусков cron каждые 2 мин без lock → гонки и дубли.
- Дрейф схемы внешних API (Avalon/KazEnergy) — нет версионирования/валидации схемы на входе.
- Поведение при отказе принять ACK источником — не определено.

### Эксплуатация
- Нет регламента бэкапа/восстановления БД и media.
- Нет мониторинга healthcheck / очередей Celery / cron.
- Обновление офлайн-Docker деплоя — процесс «как накатываем фикс на air-gap» не описан.
- Ротация логов и рост хранилища media.

### Масштабирование
- Экспорт: цикл `model_to_dict` по каждому участнику + выборка `Attendee` на каждую `Request` → N+1 и медленный синхронный ответ на крупных мероприятиях; нужен streaming/пагинация (как уже сделали для ZIP).
- Зашифрованный ИИН не индексируется → проверка дублей и поиск по ИИН дороже; продумать (например, хранить отдельный hash(ИИН) для дедупа/поиска, как уже делалось для номеров телефонов в мессенджере).
- Рост папок фото/сканов без архивной стратегии.

## 6. Рекомендованный MVP scope

Базовый «happy path» уже есть. Чтобы версия была **безопасной для эксплуатации**, в MVP обязательно входят, помимо текущего функционала:

1. Экспорт: whitelist полей + `transaction.atomic` + идемпотентность (3.1, 3.2).
2. Возврат заявки админом с причиной + статус `Rejected` (3.3).
3. Лог ошибок автоимпорта + ретрай/dead-letter + lock на cron (3.4).
4. Инвалидация сессий после смены/сброса пароля (3.5).
5. Уведомления оператору (in-app) о возврате/ошибке/приёме (3.6).
6. Фильтры + поиск участника у админа (3.7).
7. История изменений заявки/участника (3.8).
8. Согласие ПДн + авто-TTL удаление + подтверждение размещения серверов в РК (3.9).
9. Подтвердить в коде: закрытая раздача media, защита от удаления актуальных мероприятий + аудит, ограничение доступа к архивам.
10. Регламент бэкапа/восстановления.

Отложить: Excel-импорт, QR-формализацию, дашборды, доп. форматы экспорта, OpenAPI, доп. каналы уведомлений.

## 7. Рекомендованный Backlog по эпикам

**Events**
- Редактирование мероприятия + аудит.
- Явная защита от удаления актуальных мероприятий + подтверждение.

**Operators & Access**
- Деактивация оператора (soft-delete) с сохранением истории.
- Аудит входов и действий оператора.

**Requests**
- Статус `Rejected` + `reject_reason` + переход `Sent→Active` (админ).
- История изменений заявки (field-level).
- Сводка ошибок по участникам в предпросмотре.

**Participants**
- Проверка MIME/расширения файлов (не только размер).
- (post-MVP) Excel/CSV импорт участников с отчётом ошибок.

**Admin Review**
- Фильтры (мероприятие/оператор/статус) + поиск участника.
- (post-MVP) Дашборд по статусам.

**Export**
- Whitelist-сериализатор + `schema_version`.
- `transaction.atomic` + `select_for_update` + идемпотентность.
- Ветки «только новые» / «по одной заявке» (подтвердить/доделать).
- Отдельное действие re-export с подтверждением и аудитом.
- SHA-256 манифест для air-gap.

**Archives**
- Подтвердить ограничение доступа по роли.

**Auto Import**
- `ImportLog` + ретрай/backoff + dead-letter.
- Lock на cron-запуск.
- Валидация/версионирование схемы внешних API.

**Security & PII**
- Инвалидация сессий при смене/сбросе пароля.
- Закрытая раздача media (подтвердить/доделать).
- Маскирование PII в логах.
- Согласие субъекта + TTL-удаление ПДн.
- Подтверждение локализации серверов; решение по хранению сканов.
- (если есть API) закрыть introspection/CORS, авторизация по ролям.

**Audit**
- Единый аудит: вход, смена статуса, правки, удаления, экспорт/re-export.

**Multilanguage**
- Локализация сообщений валидации и уведомлений (i18n).

**Cleanup**
- Аудит удаления + двойное подтверждение для массового удаления.

**API**
- (если применимо) OpenAPI/Swagger (drf-spectacular).

**Ops**
- Бэкап/восстановление БД и media.
- Healthcheck + мониторинг Celery/cron.
- Регламент обновления офлайн-деплоя.

## 9. Вопросы владельцу продукта

1. Есть ли внешнее API (DRF/GraphQL) или только серверный рендеринг + автоимпорт? От этого зависит scope auth/JWT/Swagger и закрытие introspection/CORS.
2. Нужен ли службе/терминалу Face ID **расшифрованный ИИН** в JSON, или достаточно ФИО + фото + документа? Определяет схему экспорта и объём PII в файле.
3. Где физически размещены серверы (РК?) и кто по закону оператор ПДн? Нужно для локализации и оформления согласия.
4. Сканы документов: требование заказчика хранить копии vs запрет РК на сбор копий удостоверяющих документов — как разрешаем противоречие?
5. Админ должен **возвращать** заявку оператору или править сам? Это решает, нужен ли статус `Rejected` и блокировка ручной правки чужих заявок.
6. Какой канал уведомлений оператору доступен и достаточен (in-app / email / Telegram)?
7. Что делать с неуспешным автоимпортом — авто-ретрай или ручной разбор, и сколько хранить raw payload анкеты?
8. Процесс 7 в описании пропущен — это QR-модуль? Каков его рабочий сценарий и где он применяется (на входе вместо/вместе с Face ID)?
9. Пиковый объём участников на одно мероприятие? Определяет необходимость streaming/пагинации экспорта и архивов.
