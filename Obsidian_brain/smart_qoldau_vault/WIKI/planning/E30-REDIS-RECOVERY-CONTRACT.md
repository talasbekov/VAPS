# Smart Qoldau — bounded Redis recovery contract (static read-only)

Scope: only the current source tree and `infra/docker-compose.prod.yml`; no Redis/DB access, no runtime inspection, no backup execution. PG and MinIO are deliberately out of scope. Admin/auth correctness and E29 are excluded except where a Redis namespace changes recovery risk.

## Contract established from code

Production Redis is `redis:7-alpine` with AOF enabled and a named `redisdata:/data` volume (`infra/docker-compose.prod.yml:38-47`). The backend uses one Redis URL (`backend/src/redis/redis.service.ts:6-12`), connects Socket.IO through Redis at boot (`backend/src/main.ts:11-16`), and runs the offer/rescan sweep every second (`backend/src/requests/offer-timer.service.ts:62-76`). There is no application-level Redis export/import, key scan, or rebuild job found by the static search.

## Cross-store conclusion

PostgreSQL owns request/candidate status, audit rows, payment/payout records, and notification outbox; Redis contains independent operational timing/policy/provider state. Writes are not a single Redis+PostgreSQL transaction: for example timeout first conditionally updates PostgreSQL then ZREMs Redis (`backend/src/requests/offer-timer.service.ts:173-187`), and after a failed rotation it adds a Redis rescan hint (`:205-226`). Therefore an arbitrary Redis snapshot cannot be made cross-store consistent with a separately timed PostgreSQL backup merely by restoring both. A Redis volume backup is useful for *disaster artifact preservation and isolated replay validation*, not as authorization to roll it into a running/shared Redis.

## Recommended minimal next implementation slice

Implement one narrow, operator-run **Redis-volume backup + isolated restore-validation** script, not a recovery framework:

1. Require an explicit stopped/quiesced named production Redis container/volume identity and write a timestamped archive plus manifest (Compose project, Redis image digest/version, AOF setting, archive hash, operator time). Do not copy a changing live `/data` volume.
2. Restore only into a new, randomly named validation volume and isolated Compose project/network with no backend, no credentials from production, and no external endpoints.
3. Start only Redis from the production image/config; assert `PING`, AOF load completion, and a read-only key-family inventory/count/TTL sample against the isolated instance. Do not invoke `FLUSHALL`, write keys, point at shared Redis, or attach to live PostgreSQL.
4. Emit a human-readable pass/fail manifest and leave validation artifacts for normal retention/cleanup policy. A successful validation says the archive is Redis-readable; it does **not** certify safe business recovery.

The implementation must stop before a production restore procedure. A separate bounded change is required to decide/implement (a) offer-deadline and rescan rebuild from PostgreSQL after empty Redis, and (b) policy handling for abuse/SMS counters. A third, separately gated production-readiness change must replace or explicitly prohibit the mock providers in production.

## Acceptance tests for that slice

1. Fixture Redis AOF with representative string/hash/set/zset/list keys can be backed up, restored into the isolated volume, and reports the same `DBSIZE` and per-type/key-family sampled values/TTLs.
2. Corrupt/truncated archive or AOF produces non-zero validation and a manifest that marks it unusable; it never falls back to a shared/live volume.
3. Script rejects absent/ambiguous source volume, a running source Redis (unless its verified quiesce contract is met), and any validation target equal to the source volume/project.
4. Test harness proves validation starts no backend and performs no network connection other than its isolated Redis endpoint.
5. A static/config test pins `--appendonly yes`, `redisdata:/data`, and named-volume use in production Compose so drift breaks the recovery contract visibly.

## Operator prerequisites and limitations

- Identify the exact Compose project and `redisdata` volume before backup; Compose volume names are project-prefixed, so `redisdata` alone is not an operational identifier.
- Obtain an approved quiesce window or documented Redis-consistent snapshot mechanism. Copying an active AOF directory is not proven safe by this repository.
- Encrypt/restrict/archive lifecycle outside this slice: keys include user IDs, admin state, and mock payment token/state; no secrets or live data were inspected here.
- Do not claim a backup restores application correctness until the mock-provider production binding is resolved and an explicit PostgreSQL/Redis consistency strategy exists.
- No wipe, `FLUSHALL`, shared restore, or live validation is recommended by this report.

## Root scope decision — 2026-09-17

Static planning evidence only, not recovery acceptance. Root spot-checked Redis throttler binding, offer ZSET-only sweep and presence freshness. Proceed with exact already-stopped source cold artifact and isolated AOF-readable validation, no source stop or live restore. TTL absolute expirations mean restored counts need not match after delay; tests must distinguish persistent/expiring keys. Auth namespace recovery excluded. Mock-only providers are existing launch gates, not a newly discovered runtime incident. Operator exclusive quiescence window remains mandatory.
