## 3. Предположения ([ASSUMPTION])

A-01 Владелец подтверждает, что прототип v2 — эталон **раскладок**, а продуктовые правила из него принимаются поштучно (Q-*). A-02 Команда — 1–3 человека + ИИ; поэтому монолит и плоская структура. A-03 Пилот — 20–30 экспертов, 50–100 клиентов (WIKI E11). A-04 Мобильные клиенты обновляются не мгновенно → аддитивные контракты. A-05 Боевой push будет FCM (Android) + APNs (iOS) без стороннего сервиса.

## 4. ADR

### ADR-001 Платформы: два native Flutter + role-aware Next.js + admin SPA + монолит NestJS
Контекст: бриф сомневается в необходимости native и просит сравнить варианты. Решение: вариант D ([[08_PLATFORM_STRATEGY]] §3–4). Обоснование: ТЗ §11.6 (пуш в убитом приложении), экстренный путь, фон звонка; код и тесты уже существуют. Последствия: реестр экранов и трассируемость обязательны; правило «функция на всех поверхностях роли». Отвергнуто: PWA-только (не выполняет §11.6), разделение веба на два проекта (дублирование BFF/i18n), React Native (переписывание без выгоды).

### ADR-002 Структура репозитория: плоская, без workspaces
Решение: сохранить `backend/ web/ admin/ app_client/ app_expert/ packages/shared/ infra/ docs/`, добавить `contracts/` и `scripts/`. Обоснование: нет общего JS-кода между пакетами; шесть независимых lock-файлов — осознанный паттерн; переезд ломает Dockerfile/CI/историю. Отвергнуто: `apps/*+packages/*` с Turborepo/Nx (нет второго общего пакета), отдельные репозитории (контракт в одном PR).

### ADR-003 Админка — отдельная SPA с отдельной идентичностью
Решение: `admin/` остаётся; токены переносятся из localStorage в память + httpOnly refresh-cookie на бэкенде (или BFF-lite). Обоснование: `AdminUser` — отдельная модель угроз (2FA, роли, lockout); изоляция от публичного `web/` уменьшает blast radius XSS. Отвергнуто: перенос в `web/(admin)` (общий origin с публичным сайтом и клиентскими cookie).

### ADR-004 Терминология шифрования
Решение: «серверное шифрование хранимой переписки (AES-256-GCM), доступ только участникам»; e2e не заявляется. Следствие: тексты политики/лендинга/сторов проверяются на слово «end-to-end».

### ADR-005 Модульный монолит, без микросервисов
Обоснование: нагрузка (500 онлайн-экспертов, 200 сессий) подтверждена одним инстансом; нет отдельных команд; таймеры/матчинг/деньги связаны транзакциями. Условие пересмотра: >1 команды или измеренная необходимость отдельного масштабирования медиа-сигналинга/уведомлений — тогда «worker»-профиль того же образа, не сервисы.

### ADR-006 Прототип v2 — источник раскладок, не продуктовых правил
Решение: раскладки берутся из v2 без выдумывания; каждое правило (цены, проценты, статусы, роли), которого нет в ТЗ/Р-решениях, проходит через Q-* → Р-28+. Обоснование: v2 содержит 8 противоречий с принятыми решениями и кодом ([[04_FEATURE_INVENTORY]] §5).

### ADR-007 Контракты: OpenAPI генерируется из Nest; TS-клиенты генерируются; Dart — ручной с контрактным тестом
Обоснование: генерация Dart (openapi-generator) сейчас дороже, чем ручной клиент с тестом по спецификации; пересмотреть при >150 операций или при 3+ расхождениях за квартал.

### ADR-008 Realtime: at-most-once + обязательный REST-ресинк + `events?since`
Обоснование: буферизация в socket.io сложна и не нужна при наличии источника истины в БД; критичные события дублируются пушем/SMS.

## 5. Отвергнутые альтернативы (сводно)
Переписать бэкенд «чище» (нет оснований: инварианты, тесты, нагрузка); Flutter Web как веб (выключен по SEO/a11y); pnpm/Turborepo (нет общего кода); отдельный микросервис матчинга (транзакционные инварианты с консультацией/платежом); e2e-шифрование чата (сервер обязан видеть текст для модерации жалоб и удаления; иначе — другой продукт).
