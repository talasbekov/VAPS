# 08 — Стратегия платформ

Статус: готов (рекомендация исполнителя; утверждение — владелец) · Дата: 2026-09-13.
Связано: [[03_AS_IS_ARCHITECTURE]], [[09_TARGET_ARCHITECTURE]], [[16_RISKS_QUESTIONS_AND_ADRS]] (ADR-001).

## 1. Разделение терминов

| Термин | Что это в SmartQoldau | Есть ли |
|---|---|---|
| Адаптивный веб | `web/` (Next.js): все страницы работают на телефоне и десктопе; Tailwind-брейкпоинты | да |
| PWA | манифест/service worker/офлайн/установка | **нет** (не заявлено, не нужно для сценариев) |
| Native mobile | Flutter iOS/Android `app_client`, `app_expert` (фон, пуши, разрешения, LiveKit SDK) | да |
| React Native / Expo | — | нет и не планируется |
| Flutter Web | сборки существовали (E14/E15), **выключены** E16-13 в пользу Next.js | нет |

## 2. Требования, которые решают вопрос «нужен ли native»

| Требование (ТЗ) | Что нужно от платформы | Возможно в вебе/PWA? |
|---|---|---|
| §5.8, §11.6: оффер эксперту ≤ 3 с p95, включая фон и убитое приложение | high-priority FCM / APNs VoIP, CallKit/ConnectionService, фоновая служба presence | нет (Web Push не обходит DND, iOS PWA-пуши ограничены, фон убивается) |
| §5.4: экстренный путь «телефон в руке», звонок 103/112 одним касанием | `tel:` работает и в вебе, но пуш «специалист найден» и возврат в сессию из фона — только native | частично |
| §5.5: аудио/видео с реконнектом ≤ 30 с в фоне | native LiveKit SDK, аудио в фоне | в вебе — только при активной вкладке |
| Верификация: загрузка документов с камеры | file input ок | да |
| Каталог/профили/материалы для поисковика | SSR | только веб |
| Эксперт за столом: камера, заметки, расписание | десктопный веб | да (Р-26) |

[INFERENCE] Native-приложение **эксперта** необходимо (критерий §11.6 невозможен иначе); native **клиента** оправдано экстренным сценарием и фоном звонка; веб нужен для SEO-входа и рабочего дня эксперта. Это ровно текущее состояние.

## 3. Варианты

| | A. Единый responsive web/PWA для клиента и эксперта + admin + API | B. Mobile клиент + web эксперт + admin + API | C. Отдельные web client и web expert + admin + native позже + API | **D. AS-IS: два native (клиент, эксперт) + role-aware web (public + client + expert) + admin SPA + API** |
|---|---|---|---|---|
| Что выбросить/построить | выбросить оба Flutter-приложения (~340 Dart-файлов, 130 тестов) | выбросить `app_expert`, веб-кабинет клиента | разделить `web/` на два проекта; отложить native | ничего не выбрасывать |
| Критерий §11.6 (пуш ≤ 3 с в убитом приложении) | невыполним | выполним только если эксперт в native — противоречие | невыполним до native | выполним после боевого push/VoIP |

## 4. Рекомендация

**[DECISION] Основной вариант — D (сохранить текущее разделение и укрепить).** Запасной — **B′**: если пилот покажет, что клиенты не устанавливают приложение, а сторы задерживают публикацию, веб-кабинет клиента становится основной клиентской поверхностью (он уже есть), а native-клиент остаётся для экстренного пути и пушей. Ни один вариант не предполагает отказа от native-эксперта.

Что не делать: не строить PWA «вместо приложения» (не решает §11.6); не разделять `web/` на два проекта (общие шапка, i18n, BFF, дизайн-токены; расхождение ловится одним реестром экранов); не переносить админку в `web/` (разные идентичности и модель угроз, см. ADR-003).

## 5. Границы поверхностей

| Поверхность | Что это | Роли | В MVP | Что нельзя делать общим |
|---|---|---|---|---|
| **Web** = `web/` | публичный сайт (SEO) + кабинет клиента + кабинет эксперта; BFF | Аноним, Клиент, Эксперт | да | серверные правила (в Nest), device identity гостя |
| **Mobile** = `app_client`, `app_expert` (Flutter) | native-клиенты с фоном/пушами/LiveKit SDK | Гость, Клиент; Эксперт | да | UI-компоненты с вебом (разные стеки — общие только токены дизайна как данные и OpenAPI) |
| **Admin** = `admin/` (Vite SPA) | внутренний инструмент 6 ролей | Сотрудники | да | идентичность и токены с пользовательскими |
| **API** = `backend/` | правила, состояния, деньги, realtime | все | да | — |
| **Shared** | `packages/shared` (Dart: API-клиент, модели, дизайн-токены, чат/звонок/пуш), `docs/openapi.json` (контракт → `web/lib/api/generated.ts`) | — | да | бизнес-логика (остаётся в API) |
| **Infrastructure** | `infra/` compose dev/prod/stand, Dockerfile'ы, CI | — | да | секреты |

Интерфейсы MVP: все существующие. Откладываются: PWA, desktop-сборки Flutter (каталоги `linux/macos/windows` удалить), Flutter Web (выключен).

## 6. ADR-001 (кратко; полный текст в [[16_RISKS_QUESTIONS_AND_ADRS]])

Контекст: бриф спрашивает, что такое «mobile» и нужны ли отдельные приложения. Решение: два native Flutter-приложения + один role-aware Next.js + отдельная admin SPA + модульный монолит NestJS. Последствия: четыре кодовые базы UI → обязательны реестр экранов, матрица трассируемости и правило «функция появляется на всех поверхностях, где есть роль, или явно помечается как поверхностно-ограниченная». Отвергнуто: A (PWA), C (разделение веба), микросервисы, монорепо-workspaces (ADR-002).
