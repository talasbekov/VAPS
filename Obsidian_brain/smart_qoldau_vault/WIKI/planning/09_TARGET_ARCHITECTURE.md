# 09 — Целевая архитектура TO-BE

Статус: готов (проект; физически не создаётся до `PLAN APPROVED`) · Дата: 2026-09-13.
Связано: [[08_PLATFORM_STRATEGY]], [[10_DOMAIN_API_AND_EVENTS]], [[13_MIGRATION_PLAN]], [[16_RISKS_QUESTIONS_AND_ADRS]] (ADR-002…ADR-006).

## 1. Принцип

Целевая архитектура **равна текущей по форме** (модульный монолит + 4 клиента) и отличается **контрактами, границами и эксплуатационной зрелостью**. Никакой физической реорганизации каталогов: код зрелый, история ценна, «переработка» — это закрытие пробелов и укрепление, а не переезд.

## 2. Структура репозитория

### Вариант 2 — workspace-монорепо `apps/* + packages/*` (npm workspaces/Turborepo)
Плюсы: единый `npm ci`, кэш задач, общий eslint/prettier. Минусы: между backend/web/admin **нет общего JS-кода** (только OpenAPI-файл); три Flutter-пакета в JS-workspace не входят; переименование `backend → apps/api` ломает Dockerfile-ы, CI, README и историю пути в 327 коммитах ради красоты. **Отвергнуто до появления второго общего JS-пакета** (ADR-002).

### Вариант 3 — отдельные репозитории
Отвергнуто: контракт OpenAPI меняется в том же PR, что и эндпоинт (правило мастер-плана); разнос репозиториев превращает это в межрепозиторные релизы при команде из 1–3 человек.

## 3. Границы ответственности

**Backend владеет:** бизнес-правилами и всеми переходами состояний ([[10_DOMAIN_API_AND_EVENTS]]), авторизацией (guards + ABAC в сервисах), матчингом, транзакциями и инвариантами БД, persistence, audit, идемпотентностью (ключи операций, дедуп вебхуков), проверками безопасности, производством realtime-событий, шаблонами уведомлений, ценами и константами (таймеры, комиссии, планы — только из API).

**Клиенты владеют:** представлением, навигацией, локальным состоянием, optimistic UI только там, где контракт безопасен (typing, отметка «прочитано»; **не** accept оффера, **не** оплата), доступностью, платформенной интеграцией (пуши, разрешения, CallKit), UX реконнекта и ресинка.

**Клиентам запрещено:** решать права окончательно (сервер — источник 403/409), менять state machine (только команды API), обращаться к БД, импортировать Prisma-типы, дублировать серверные расчёты (скидки, комиссии, дедлайны — приходят из API; допускается только отображение обратного отсчёта по `deadlineAt`).

## 4. Контракты

| Аспект | Целевое правило | Сейчас |
|---|---|---|
| Источник истины | `contracts/openapi.json`, генерируется из Nest (`openapi:dump`) в том же PR | `docs/openapi.json` (то же, другой путь) |
| TS-клиент | `openapi-typescript` → `web/lib/api/generated.ts`; для admin — тот же генератор (сейчас ручные обёртки `admin/src/lib/*`) | web ✓, admin ✗ |
| Dart-клиент | контрактный тест `SqApi` по OpenAPI (уже есть) + генерация моделей `openapi-generator dart-dio` — **отложить**: ручной клиент с контрактным тестом достаточен, пока API стабилен (ADR-007) | ✓ тест |
| WS-события | `contracts/ws-events.md` со схемой payload каждого события и `version` в payload; клиенты игнорируют неизвестные поля | описано только в коде |
| Версионирование | путь `/v1`; несовместимое изменение → новый эндпоинт/`/v2` с периодом сосуществования ≥ 1 релиз мобильных | `/v1` |
| Error envelope | `{error:{code,message,details}}`, коды — перечислены в `contracts/errors.md`; клиенты матчат по `code` | ✓ (`apiError`) |
| Пагинация | `take/cursor` (как в консультациях/выплатах: `DEFAULT_TAKE 20`, `MAX_TAKE 100`) — единообразно для всех списков | частично |
| Request ID | `X-Request-Id` принимается/генерируется, попадает в логи и ответ ошибки | нет |
| Idempotency | доменные ключи (`hold:{payment}:{attempt}`, `@@unique(kind, refId)`, `ProviderEvent`); для `POST /requests`, `/bookings`, `/payouts` — заголовок `Idempotency-Key` (клиенты повторяют при обрыве) | частично |
| Дата/время | ISO-8601 UTC в API; отображение — Asia/Almaty; дни дохода считаются по Алматы | ✓ |
| Деньги | integer тиыны, поле `*Tiyn`; форматирование — клиент | ✓ |
| Локаль | `Accept-Language`/`User.locale` (ru|kz) для шаблонов | ✓ |
| Deprecation | заголовок `Deprecation` + запись в `contracts/CHANGELOG.md`; удаление только после того, как в сторах нет версии, использующей путь | нет |

## 5. Слои бэкенда (без церемониала)

| Модуль | Текущее разделение | Целевое |
|---|---|---|
| Простые CRUD (`topics, favorites, devices, schedule, content`) | controller + service + Prisma | **оставить** |
| Ядро (`requests, matching, consultations, payments, payouts, premium, booking`) | сервисы 400–750 строк с транзакциями | **выделить use-case-функции внутри модуля** (`accept-offer.ts`, `complete-consultation.ts`, `settle-payment.ts`) с явным входом/выходом и одной транзакцией; доменные инварианты — рядом с моделью (`request.rules.ts`); инфраструктура (Redis, провайдеры) — через существующие порты (`PaymentProvider`, `PushProvider`, `SmsProvider`) |
| Интеграции (`media, storage, notifications/provider, auth/sms`) | порты + адаптеры (mock/боевой) | оставить; добавить боевые адаптеры FCM/APNs и эквайера за теми же портами |
| Cross-cutting (`common, audit, ws`) | — | добавить `RequestContext` (requestId, actor) для логов и audit |

Правило: новый слой/абстракция вводится только при втором подтверждённом использовании (миграционное правило §15.1 брифа).

## 6. Realtime TO-BE

| Аспект | Решение |
|---|---|
| Источник истины | БД; события — уведомления об изменении, клиент всегда может восстановить состояние REST-запросом |
| Комнаты | `user:{id}`, `expert:{id}` (оставить); подписка на консультацию не нужна |
| Именование | `domain.event` (`offer.new`, `consultation.updated`) — оставить; payload содержит `id`, `updatedAt`, `version` сущности |
| Гарантии доставки | at-most-once по сокету + **REST-ресинк после `ready`** (обязательный на клиентах); для критичных (`offer.new`) — дублирование пушем + SMS (есть) |
| Пропущенные события | `GET /v1/me/events?since=<ts>` — журнал последних N событий пользователя за 24 ч (новый, S), клиент вызывает после реконнекта вместо N запросов |
| Дубли | клиент дедупит по (`event`, `id`, `version`) |
| Порядок | не гарантируется между инстансами; `version`/`updatedAt` разрешают конфликты (позднее выигрывает) |
| Heartbeat/presence | оставить (heartbeat 30 с, свежесть фильтром); веб — только видимая вкладка |
| Рестарт сервера | клиенты реконнектятся, `ready` → ресинк; дедлайны офферов в БД (`deadlineAt`) — таймер восстанавливается сканом |
| Масштабирование | redis-adapter есть; интервал-задачи должны быть идемпотентны при нескольких репликах (уже: перечитка статусов, unique-ключи); при росте — выделить «worker»-профиль того же образа (`ROLE=worker`) без HTTP |

## 7. Медиа (LiveKit) TO-BE

Токен: выдаёт только API участнику ACTIVE-консультации, identity без PII (`client-{code}`/`expert-{id}`), grant `roomJoin` на одну комнату = id консультации, TTL короткий, `canPublish/canSubscribe` явно (сейчас по умолчанию — HARDEN). Вебхуки: подпись `WebhookReceiver` (есть) + **дедуп по `event.id` в `ProviderEvent(kind='livekit')`** (replay). Эскалация chat→audio→video через `media-token {format}` (есть). Тайм-аут: no-show 3 мин (есть). Завершение: `complete` → комната закрывается API (`RoomServiceClient.deleteRoom`, S). Приватность: запись выключена, egress не включать; логи без идентификаторов клиента. Тесты: unit токена, e2e вебхуков (есть), ручной чек-лист на устройствах, синтетический звонок в мониторинге пилота.

## 8. Хранилище TO-BE

Upload через API (multer, лимит по границе, magic-bytes) — оставить, presigned upload не нужен при 10 МБ. Presigned GET 300 с для документов, 900 с для контента (есть). Приватный бакет документов, отдельный публичный аватаров (есть). Антивирус: **вопрос** — при пилоте достаточно ограничения типов; ClamAV-скан как фоновая задача — после пилота (Q-15). Ретенция: документы отклонённых/удалённых экспертов удалять через 30 дней; аудит доступа админа к документу — записывать `expert.document_read` (T-09). Экспозиция: ключи объектов не угадываются (uuid), список бакета закрыт.

## 9. Диаграмма TO-BE (контейнеры)

Совпадает с AS-IS ([[03_AS_IS_ARCHITECTURE]] §2) плюс: `contracts/` как артефакт сборки клиентов; профиль `worker` у API (опционально); внешние — боевые эквайер/выплаты/FCM/APNs; периметр — TLS-прокси, бэкапы, мониторинг (вне репозитория, но обязательные — [[14_ROADMAP_AND_BACKLOG]] Phase 6).
