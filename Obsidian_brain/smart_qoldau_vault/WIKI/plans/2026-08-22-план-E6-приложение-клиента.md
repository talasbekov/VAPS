# E6 «Приложение клиента (Flutter)» — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Собрать приложение клиента П1 (iOS + Android, Flutter) поверх уже готового бэкенда E1–E5/E8a/E9: от анонимного входа до полного цикла «тема → подбор → оплата холдом → сессия в чате/аудио/видео → оценка», включая экстренный сценарий БП-02, каталог, консультации, уведомления и поддержку.

**Architecture:** Монорепо: `app_client/` (приложение) + `packages/shared/` (Dart-пакет: типизированный API-клиент по OpenAPI бэкенда, модели, socket.io-шина событий, дизайн-токены и базовые виджеты). Состояние — Riverpod, навигация — go_router с redirect-гардом сессии, HTTP — dio с интерцептором авто-refresh, реалтайм — `socket_io_client` на неймспейс `/ws` (бэкенд использует socket.io, не голый WebSocket), медиа — `livekit_client` по токену от `POST /v1/consultations/:id/media-token`. Приложение НЕ содержит бизнес-правил: таймеры заявок, эскалация Р-16, эскроу-холд, статусные машины живут на бэкенде; клиент отображает статусы и реагирует на WS-события.

**Tech Stack:** Flutter stable (Dart 3), Riverpod, go_router, dio, freezed + json_serializable, socket_io_client, livekit_client, flutter_secure_storage, permission_handler, url_launcher, google_fonts, intl/gen_l10n, mocktail + http_mock_adapter (тесты), integration_test.

## Global Constraints

- **Локализация ru/kz с первого экрана.** Коды локалей расходятся: Flutter/ICU знает казахский как `kk`, бэкенд принимает `kz` (`?locale=`, `PATCH /v1/me/locale`, `POST /v1/devices`). Единственная точка перевода — `localeToApi()` в shared; напрямую строку `'kk'` в API не отправлять никогда.
- **Деньги — `int` в тиынах** во всех моделях и во всём состоянии. В UI форматировать через единый `formatTenge(int tiyn)` (₸, разделитель тысяч — неразрывный пробел). Никакого `double` для сумм.
- **Часовой пояс Asia/Almaty, валюта ₸.** Даты с бэкенда — ISO-8601 UTC; парсить `DateTime.parse(...).toLocal()`.
- **Длительность консультации 50 минут (Р-05), цена не зависит от формата (Р-04).** В шторке оплаты — ровно «50 минут» и `priceTiyn` эксперта. «30 минут» из прототипа — ошибка прототипа, не воспроизводить.
- **Таймеры Р-10 (45 с / 20 с) клиент НЕ реализует** — они на бэкенде. Клиент показывает прогресс поиска и реагирует на `request.updated`.
- **Дисклеймер экстренных служб (102/103)** обязателен на: экране экстренного скрининга, экране экстренного поиска (постоянная кнопка «Позвонить 103 / 112»), экране эскалации Р-16, экране поддержки. ТЗ §4.3.
- **Анонимность (ТЗ §4.1):** клиент нигде не вводит имя и не отправляет ПД эксперту. Единственные ПД клиента — телефон при регистрации.
- **Единый формат ошибок бэкенда:** `{"error":{"code","message","details?}}`. Клиент показывает СВОЙ локализованный текст по `code`; `message` с сервера — только в debug-логе. Полный перечень кодов — в задаче 4.
- **Гость — полноправный пользователь ядра.** Гостевой JWT (`isGuest: true`) проходит `JwtAuthGuard` на всех клиентских маршрутах: заявка, оплата, чат, звонок, отзыв. Ограничения гостя — только продуктовые (нет истории между устройствами, конверсионная подсказка в профиле, Р-22).
- **Access-токен живёт 15 минут** (`JWT_ACCESS_TTL=15m`), refresh — 30 дней. Авто-refresh — single-flight в интерцепторе; при провале refresh — разлогин и переход на `/welcome`.
- **Никаких бизнес-правил в UI-слое.** Виджет получает готовое состояние от Riverpod-контроллера; вся работа с API — в репозиториях `features/*/data/`.
- **TDD:** сначала падающий тест (`flutter test` / для задачи 9 — `npm run test:e2e` в backend), затем реализация. Перед каждым коммитом полный регресс: статический анализ (0 issues) + `flutter test` в `app_client` и `packages/shared`; для задачи 9 дополнительно полный бэкенд-регресс (lint + unit + e2e + build).

## Уроки исполнения задач 1–19 — действуют на все оставшиеся задачи

Внесено 2026-08-22 по итогам девяти задач и восемнадцати раундов ревью. Каждый пункт стоил как минимум одного раунда исправлений, поэтому сформулированы как требования, а не советы.

1. **Перечень тестов в задаче — минимум, а не потолок.** В задаче 6 экран, которого не было в списке, оказался непокрыт — и первый же написанный тест нашёл настоящий баг (двойной вызов гостевого входа при быстром двойном тапе), а за ним ещё три дефекта того же класса. Пишешь код с нетривиальной логикой — покрывай, даже если план молчит.
2. **Тест обязан исполнять реальный путь пользователя.** В задаче 5 два теста прошли мимо полностью сломанного ввода телефона, потому что подавали строку одним `enterText` вместо посимвольного ввода. Жесты — настоящими жестами (`tester.drag` по `PageView`, а не `jumpToPage`), ввод — по символу, переходы — тапами. Синтетический путь, обходящий дефект, хуже отсутствующего теста: он создаёт ложную уверенность.
3. **Гонку нельзя проверить без управления временем.** Тест, полагающийся на то, что операция «успеет» или «не успеет», не проверяет ничего. Затвор на `Completer` (образцы в задачах 6 и 8) либо инжекция функции времени. В задаче 6 первая версия теста гонку не воспроизводила: `SharedPreferences` успевал разрешиться внутри самого `tester.tap()`.
4. **Флаг занятости — только с `try/finally`.** Исключение оставляет флаг взведённым навсегда, элемент блокируется без возможности восстановиться. В задаче 6 узор встретился трижды, в одном случае давая буквально вечный спиннер.
5. **Тестовый двойник обязан воспроизводить связку настоящего компонента.** В задаче 8 фейковый транспорт не публиковал состояния соединения сам — и критическая регрессия (принудительный разлогин исправной сессии при обычном обновлении токена) прошла мимо всех тестов. Если двойник проще оригинала там, где живёт логика, — он не двойник.
6. **Платформенные каналы не подменять.** Узкий интерфейс + подстановка через Riverpod (образцы: `SecureStore`, `PermissionService`, `UrlLauncherPort`, `SqSocket`). В задаче 2 подмена канала протекла на соседние тесты файла. Если подмена неизбежна — обязателен `addTearDown`.
7. **Ошибку не проглатывать молча.** Пустой `catch (_) {}` прячет и настоящие программные ошибки. Логируй тип и факт (без токенов, ПД и текстов сообщений), сужай перехват там, где ожидаемый класс ошибок известен.
8. **Различай отказ пользователя и сбой механизма.** Отказ в разрешении — нормальный исход, идём дальше молча; сбой самого запроса — аварийный, нужно сообщение, и всё равно идём дальше. Слипшись, они дают экран, не отвечающий на тап ничем.
9. **Утверждение в отчёте — не доказательство.** «Нагрузка тривиальна», «это не воспроизводится», «пакет ведёт себя так» проверяются измерением, пробником или чтением исходника. Ревью проверяет отчёт, а не верит ему. Если проверить нечем — так и напиши, это законный исход (в задаче 8 честный отказ написать вводящий в заблуждение тест был принят).
10. **Расхождение брифа с фактическим кодом решается в пользу кода — но вслух.** Не подгоняй молча ни в одну сторону: назови расхождение в отчёте. Так корректно закрыты три расхождения контракта в задачах 4, 7 и 8.

## Решения, принятые при планировании (документы молчат — переиграть можно)

1. **Управление состоянием — Riverpod, навигация — go_router.** В ТЗ и мастер-плане выбора нет. Riverpod даёт тестируемость без виджет-дерева (контроллеры проверяются юнит-тестом), go_router — декларативный redirect-гард сессии, который нужен на каждом экране.
2. **API-клиент пишется руками, а не генерируется.** Мастер-план говорит «API-клиент по OpenAPI». Буквальная кодогенерация (`openapi-generator` dart-dio) даёт неревьюируемый объём и ломкий build. Вместо неё: тонкий рукописный `SqApi` + **контрактный тест** (задача 4), который сверяет каждый путь и метод, используемый клиентом, с `docs/openapi.json`, выгруженным из бэкенда. Расхождение контракта роняет тест — цель кодогенерации достигнута, читаемость сохранена.
3. **Модели — freezed + json_serializable.** Value-равенство нужно виджет-тестам и Riverpod-сравнениям; писать `==`/`hashCode`/`copyWith` руками на ~20 моделях дороже, чем один генератор.
4. **Аватар эксперта — инициалы на цветном фоне.** В модели `Expert` бэкенда поля фото нет вовсе, а прототип показывает фотографии. Заводить загрузку и модерацию фото внутри клиентского эпика неправильно — это бэкенд-объём (хранилище, модерация, ПД). Решение записано в «Отложено».
5. **Теги в оценке не реализуем.** `CreateReviewDto` бэкенда — только `rating`, `publicText`, `privateText`. Класть теги в свободный текст = портить публичные отзывы. В «Отложено».
6. **Перенос консультации (БП-03) вне объёма.** Бэкенд не знает записи на слот: `Consultation` создаётся в момент матча и сразу `ACTIVE`, эндпоинта переноса нет, напоминание за 15 мин (Р-15) в E9 явно отложено «в E6 вместе с booking-слотами». Booking — бэкенд-эпик, а не экран. E6 реализует то, что контур поддерживает: отмену активной консультации и историю. Записано в «Отложено» как отдельный бэкенд-эпик.
7. **Счётчик «Сейчас онлайн: N» требует крошечного бэкенд-эндпоинта** — E3 отложил его «в E6, когда клиентское приложение определит формат». Формат определён, эндпоинт добавляется задачей 9 (единственная бэкенд-задача эпика).
8. **Push (FCM/APNs) вне объёма — ключей проекта нет.** В E9 боевой адаптер отложен до появления ключей. В E6 делается вся обвязка вокруг: центр уведомлений по HTTP + живое обновление по WS, регистрация устройства через абстракцию `PushTokenSource` с no-op реализацией по умолчанию. Появятся ключи — добавляется одна реализация, экраны не трогаются.
9. **Удаление аккаунта (ТЗ §5.1) — через обращение в поддержку** категории `ACCOUNT_DATA`. Эндпоинта удаления в бэкенде нет; категория тикета ровно под это уже существует (E8a).
10. **Шрифт Inter через `google_fonts`** (прототип весь на Inter). Файлов шрифта в репозитории нет, а докачка на первом запуске с системным фолбэком дешевле, чем тащить TTF в git. Офлайн-бандл — в «Отложено».
11. **Экран «Анализ», разделы «Материалы» (медитации/музыка/статьи/дыхание) и Premium из прототипа НЕ входят в E6** — это R2 (эпики E12/E13) и явно вынесенное «вне MVP» (ТЗ §2). В нижней навигации их места нет.
12. **PAN отправляется на наш бэкенд** (`POST /v1/payment-methods {pan, expiry, holderName}` — текущий контракт с мок-провайдером). Для боевого эквайера это неприемлемо (PCI-DSS): экран карты заменяется формой/SDK провайдера с 3DS. Реализуем по текущему контракту, риск записан в «Отложено» как входное условие интеграции с эквайером.

## Заблокировано внешними обстоятельствами (не «отложено»)

Здесь только то, что невозможно закрыть кодом в этом репозитории. Для каждого пункта указано, что именно блокирует и что реализовано вместо ожидания.

- **Боевой эквайер и PCI-DSS.** Экран «Добавить карту» отправляет PAN на наш бэкенд, потому что таков контракт мок-провайдера. Заменить его формой/SDK провайдера с 3DS невозможно, пока не подписан договор и не известен API провайдера (блокер E0 мастер-плана). Реализовано вместо ожидания: `PaymentProviderPort` на бэкенде и изоляция экрана карты в один виджет — переключение затрагивает один экран и одну реализацию порта. **Входное условие эпика боевого эквайера, а не долг клиента.**
- **Ключи FCM/APNs.** Задача 22 реализует весь клиентский код, но проверить доставку реального пуша нельзя без проекта Firebase и сертификатов APNs. Реализовано вместо ожидания: полный код за флагом `PUSH_ENABLED`, тесты на фейковом порту, `.example`-конфиги и раздел README. Серверный адаптер `PushProviderPort` → FCM HTTP v1 идёт отдельной бэкенд-задачей.
- **iOS-сборка и VoIP/CallKit.** Требуется macOS с Xcode и аккаунт Apple Developer; в системе их нет. Android-путь проверяется на эмуляторе полностью. iOS-специфика (CallKit для входящих заявок) относится к приложению эксперта E7 и остаётся входным условием сборочной машины.
- **Публикация в сторы** — эпик E11, требует аккаунтов Apple Developer / Google Play.
- **Пререлизная `freezed: 4.0.0-dev.3` в `packages/shared`** (задача 4). Стабильная 3.2.5 генерирует конструкторные параметры коллекций как `final List<T> x`, а грамматика Dart 3.13.1 отвергает этот модификатор (`extraneous_modifier`). Проверено контроллером независимо на отдельном пробнике: на простой модели дефект не проявляется, на представительной (sealed-объединение, `@Default`, вложенная модель) — воспроизводится дословно. Пин точный, не диапазоном, и объяснён комментарием в самом `pubspec.yaml` с условием снятия. **Снять, когда выйдет стабильная freezed 4.0.0** — это единственное действие, и оно зависит от апстрима, а не от нас.
