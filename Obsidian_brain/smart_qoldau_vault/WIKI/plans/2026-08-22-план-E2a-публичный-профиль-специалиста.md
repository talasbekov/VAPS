# E2a «Публичный профиль специалиста: фото, «о себе», теги отзывов» — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Закрыть три расхождения между прототипом и данными, обнаруженные при разработке клиентского приложения: у специалиста нет фотографии, нет текста «о себе», а оценка не принимает теги, хотя прототип показывает все три. Плюс мелкий контрактный долг — клиент не может узнать идентификатор своего отзыва, чтобы дать его удалить.

**Architecture:** Фотография и текст «о себе» — публичный контент, который видит любой клиент, поэтому оба проходят модерацию по образцу верификации документов (БП-04, Р-18): у каждого поля есть опубликованное значение и значение на проверке, профиль во время проверки продолжает работать со старым. Хранилище фотографий — **отдельный бакет**, а не тот, где лежат документы верификации: у них противоположные требования доступа (документы зашифрованы и доступны единицам, фото раздаётся всем). Теги отзыва — фиксированный словарь, зависящий от числа звёзд, ровно как в прототипе; свободный ввод тегов не допускается.

**Tech Stack:** NestJS 10, Prisma 6, S3-совместимое хранилище (MinIO в dev), `sharp` для проверки и нормализации изображений, Jest/supertest; Flutter/Riverpod на клиенте. **Новая npm-зависимость: `sharp`.**

## Global Constraints

- **Фотография и «о себе» — публичный контент и модерируются до публикации.** Платформа психологической поддержки: неподходящее фото или текст в профиле специалиста — репутационный и этический риск, а не косметика. Немодерируемая публикация недопустима.
- **Бакет фотографий отделён от бакета документов.** `S3_BUCKET_DOCUMENTS` зашифрован и закрыт (ТЗ §6); аватары раздаются публично. Класть их вместе — значит либо ослабить защиту документов, либо сломать раздачу фото.
- **Ключ объекта фотографии неугадываем** (UUID v4, не производный от id специалиста): публичный бакет без списка объектов защищён только неугадываемостью ключа.
- **Во время проверки нового значения старое продолжает публиковаться** — принцип Р-18 («смена документа после верификации → повторная проверка только этого документа, профиль продолжает работать»), перенесённый на поля профиля. Для первого заполнения публиковать нечего, и это нормально.
- **Теги отзыва — закрытый словарь, зависящий от оценки** (взят из прототипа `docs/Прототип/SmartQoldau - Оценка.dc.html`, а не придуман):
  - 1 звезда: «Не помогло», «Долгое ожидание», «Плохая связь»
  - 2: «Мало пользы», «Не понял меня», «Технические проблемы»
  - 3: «Средне», «Могло быть лучше», «Стандартно»
  - 4: «Внимательный», «Помог разобраться», «Профессионально»
  - 5: «Внимательный», «Помог разобраться», «Превзошёл ожидания»
  Тег, не принадлежащий набору выставленной оценки, отклоняется. Свободный текст в тегах не принимается: иначе это второй канал публичного отзыва в обход модерации.
- **Теги хранятся кодами, а не текстом.** В БД лежит стабильный код (`not_helpful`, `attentive`, …), отображаемый текст живёт в локализации клиента — иначе казахская локаль получит русские теги, а переименование сломает историю.
- **PII:** фотография — единственное изображение в публичном профиле; фото клиента не существует в системе вовсе. Специалист не получает никаких новых данных о клиенте.
- **Audit (§4.5) на все переходы:** `expert.photo_submitted`, `expert.photo_approved`, `expert.photo_rejected`, `expert.about_submitted`, `expert.about_approved`, `expert.about_rejected`.
- Пагинация: `take` default 20, max 100, `orderBy` всегда с вторичным ключом `id`.
- e2e ТОЛЬКО `npm run test:e2e` (тестовая БД 5433); полный регресс (lint + unit + все e2e + build) перед каждым коммитом. Клиент — `dart analyze` (не `flutter analyze`) + `flutter test`.
- После каждой задачи, меняющей контракт, — `npm run openapi:dump` и проверка клиентского контрактного теста.
- Ветка `feature/e2a-expert-public-profile` от `main`. TDD: сначала падающий тест.
