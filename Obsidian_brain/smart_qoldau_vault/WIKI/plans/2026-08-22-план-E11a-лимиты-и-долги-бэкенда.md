# E11a «Лимиты, пагинация и эксплуатационные долги бэкенда» — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Закрыть долги, накопленные эпиками E1–E9 и E8a и записанные в их разделы «Отложено», прежде чем они станут инцидентами: неограниченный перебор паролей и неограниченная запись в открытые эндпоинты, платные SMS без потолка расхода, доступ деактивированного сотрудника, монотонно растущие таблицы, отсутствие способа восстановить доступ в админку.

**Architecture:** Ничего нового не проектируется — эпик состоит из точечных правок в существующих модулях. Единственная новая инфраструктура: `@nestjs/throttler` с хранилищем в Redis (иначе лимиты считаются по репликам независимо и множатся на их число) и таблица `outbox` для уведомлений, снимающая веер сетевых вызовов с пути запроса. Остальное — индексы, пагинация, транзакционные проверки и sweep-уборка на уже работающем планировщике.

**Tech Stack:** NestJS 10, Prisma 6, Redis, `@nestjs/schedule`, Jest/supertest. **Новые npm-зависимости: `@nestjs/throttler`, `@nest-lab/throttler-storage-redis` (или эквивалент с Redis-хранилищем), `otplib` + `qrcode` (2FA), `helmet`.**

## Global Constraints

- **Лимиты считаются в Redis, а не в памяти процесса.** Иначе при двух репликах пользователь получает вдвое больший лимит, а после рестарта — чистый счётчик. Это не оптимизация, а условие корректности.
- **Лимит никогда не должен ломать легитимный сценарий.** Каждое числовое значение сопровождается расчётом в комментарии: сколько запросов делает нормальный пользователь за окно и во сколько раз лимит выше. Значения без обоснования — дефект.
- **`POST /v1/requests` — самый латентно-критичный путь продукта** (обещание «помощь за 1–2 минуты», ТЗ §6: p95 подбора ≤ 5 с). Всё, что добавляется на этот путь, обязано быть либо асинхронным, либо стоить микросекунды. Троттлинг на Redis — один `INCR`, это допустимо; отправка уведомлений — нет, и она с этого пути снимается.
- **Ни одна правка не меняет внешний контракт молча.** Пагинация добавляется совместимо: существующие вызовы без `take`/`skip` продолжают работать, отдавая первую страницу с прежним порядком. Изменение формы ответа (голый массив → `{items,total}`) допускается только там, где клиент ещё не написан, и обязано быть отражено в `docs/openapi.json` и в клиентском `SqEndpoints`.
- **Пагинация: `take` по умолчанию 20, максимум 100; `orderBy` ВСЕГДА с вторичным ключом `id`** — одноключевая сортировка по `createdAt` даёт недетерминированные страницы (дефект, найденный финальным ревью E9 и повторно — E8a).
- **Все статусные переходы и административные действия — в `audit_log`** с актором и временем (ТЗ §4.5).
- **Секреты 2FA хранятся зашифрованными**, в ответах API не появляются никогда, кроме единственного момента первичной привязки.
- **Деньги — `int` в тиынах.** PII: телефон, PAN, тексты сообщений не попадают в логи, метрики и уведомления.
- e2e ТОЛЬКО `npm run test:e2e` (тестовая БД 5433), время — виртуальное через `ClockService`; полный регресс (lint + unit + все e2e + build) перед каждым коммитом. **Базовая линия на момент начала эпика: unit 99/99, e2e 285/285 в 53 сьютах** — любое расхождение вниз разбирается, а не списывается.
- После каждой задачи, меняющей контракт, — `npm run openapi:dump` и проверка, что клиентский контрактный тест в `packages/shared` остаётся зелёным.
- Ветка `feature/e11a-limits-and-debts` от `main`. TDD: сначала падающий тест.

## Порядок задач выбран по риску, а не по удобству

Первыми идут дыры, которые эксплуатируются снаружи без аутентификации (перебор пароля, неограниченная запись, платные SMS). Затем — доступ, который не отзывается. Затем — рост таблиц и эксплуатация. Косметика контрактов последней.

## Вне объёма эпика (осознанно)

- **WAF, защита от DDoS на уровне инфраструктуры** — задача хостинга, не приложения.
- **Полноценный аудит ASVS L2** — эпик E11 (стабилизация), здесь закрываются только конкретные названные дыры.
- **Ротация ключа шифрования чата** (`CHAT_ENCRYPTION_KEY`) и KMS — инфраструктурный эпик, требует решения по облаку.
- **Боевые адаптеры** эквайера, FCM, Mobizon — ждут внешних учётных данных; здесь только защита вокруг них.

    - `createTicket`: 5 / час на пользователя, 10 / час на IP для гостей. Эндпоинт неаутентифицированный и принимает 4200 символов; форма поддержки на лендинге E10 сядет ровно на него.

  - `helmet()` в `main.ts` — базовые заголовки безопасности; для `/v1/docs` при необходимости смягчить CSP.
  - Env: `THROTTLE_ENABLED` (default `true`) — чтобы e2e могли отключать лимиты там, где они мешают, точечно, а не глобально.

**Interfaces:**
- Produces:
  - `model NotificationOutbox { id, userId?, expertId?, type, payload Json, attempts Int @default(0), nextAttemptAt DateTime, sentAt DateTime?, lastError String?, createdAt, @@index([sentAt, nextAttemptAt]), @@map("notification_outbox") }`.
  - `OutboxService.enqueue(...)` — **синхронная запись одной строки** вместо цикла сетевых вызовов. Именно это вызывается из `POST /v1/requests` и из broadcast Р-16.
  - `OutboxSweepService.tick()` под `@Interval(1000)` — забирает пачку (`take: 50`), отправляет с ограничением конкурентности (`Promise.allSettled` по 10), при ошибке увеличивает `attempts` и отодвигает `nextAttemptAt` с экспоненциальной задержкой, после 5 попыток помечает мёртвым с `lastError`.
  - Выборка устройств получает `take: 20` (сейчас без ограничения, а число `Device` на пользователя растёт монотонно).
  - **Критерий приёмки ТЗ §11.6 (доставка ≤ 3 с p95) не должен пострадать:** при пустой очереди задержка добавляется не более чем на один тик. Замерить в тесте лаг «enqueue → отправлено» на виртуальном времени.
  - Существующий `NotificationsService.dispatch()` сохраняет сигнатуру и продолжает никогда не бросать — меняется только его внутренность.
