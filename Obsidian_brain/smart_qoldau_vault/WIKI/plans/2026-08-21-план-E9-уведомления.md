# E9 «Уведомления» — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Шина уведомлений поверх E1–E5: регистрация устройств, порт push-провайдера (мок сейчас, FCM/APNs при ключах), шаблоны событий §5.8 (ru/kz), in-app центр уведомлений в обоих приложениях, критичный пуш входящей заявки с SMS-fallback за 10 с без подтверждения доставки, отслеживание доставки (задел метрики §11.6), боевой Mobizon-адаптер SMS (долг E1). Закрывает долги E1 (Mobizon), E3 (пуш оффера + SMS-fallback), E4 (пуш no-show), E5 (пуши о зачислении/выплате).

**Architecture:** Новый модуль `notifications` + `devices`. Единственная точка отправки — `NotificationsService.dispatch(userId, type, data)`: рендерит шаблон по локали получателя, пишет In-app запись (`Notification`), эмитит WS `notification.new` (EventsService уже @Global) и шлёт push на все устройства пользователя через `PushProviderPort`. Доменные сервисы (requests/escalation, payments, payouts, verification, consultations, chat) вызывают dispatch fire-and-forget — сбой канала уведомлений НИКОГДА не откатывает доменную операцию (try/catch внутри dispatch, паттерн settleSafely E5). Подтверждение доставки — ack от приложения (`POST /v1/notifications/:id/ack`); критичный пуш оффера без ack за 10 с добивается SMS-fallback'ом в существующем sweep (виртуальное время, шаг 8). Эксперт адресуется через `Expert.userId` — у уведомлений единый адресат-пользователь.

**Tech Stack:** NestJS 10, Prisma 6, Redis, Jest/supertest. Mobizon — голый `fetch` (Node 22), НОВЫХ npm-зависимостей нет. Боевой FCM/APNs-адаптер — вне эпика (нет ключей проекта; порт готов, подключение при E6/E7).

## Global Constraints

- Шаблоны §5.8: типы `offer.incoming` (критичный), `earning.credited`, `payout.updated`, `consultation.cancelled`, `consultation.no_show_hint`, `verification.updated`, `chat.message`. Код входа — SMS из E1, НЕ через шину. Напоминание за 15 мин (Р-15) — E6 вместе с booking-слотами (решение E4). Каждый тип — title/body на ru и kz; локаль получателя: `User.locale` (`ru`|`kz`, default `ru`), устанавливается при регистрации устройства и `PATCH /v1/me/locale`.
- In-app запись создаётся ВСЕГДА (даже без устройств); push — на все зарегистрированные устройства получателя; WS — как раньше (существующие события `offer.new`/`consultation.updated`/… НЕ трогаем — приложения слушают их для реактивности, `notification.new` — отдельное событие центра уведомлений).
- Критичный пуш (`offer.incoming`): `critical: true` в порт (боевой адаптер замапит в data-only+CallKit/VoIP; мок просто фиксирует флаг). SMS-fallback: если за 10 с нет ack И оффер ещё PENDING → одно SMS эксперту, `smsFallbackAt` проставлен, повторно не шлётся. Sweep-шаг изолирован try/catch (паттерн OfferTimerService).
- Отслеживание доставки: `pushSentAt` (dispatch), `pushDeliveredAt` (ack устройства), `smsFallbackAt`, `readAt`. Метрика §11.6 (≤3 с p95 на реальных устройствах) проверяется в E11 — здесь только полнота данных для неё.
- Токены устройств уникальны глобально (`@unique token`); повторная регистрация того же токена другим пользователем — перепривязка (телефон сменил владельца аккаунта). Удаление токена при logout — обязанность приложения (`DELETE /v1/devices/:token`), мёртвые токены чистит боевой адаптер по ответам FCM (отложено).
- PII: в push НЕ кладём имя клиента/тему/цену для оффера («Новая заявка» без деталей — контент в приложении за auth); в чат-пуше — без текста сообщения (E2E-шифрование, «Новое сообщение»).
- Чат-пуш — только если у получателя НЕТ активного WS-сокета (онлайн-пользователь видит сообщение в чате); проверка через EventsService (метод `isUserConnected`).
- Новые коды ошибок: `DEVICE_NOT_FOUND`, `NOTIFICATION_NOT_FOUND`. Audit: `notification.sms_fallback` (единственный «дорогой» переход — платное SMS); остальное не аудитим (шум).
- Env: `PUSH_PROVIDER: valid('mock').default('mock')` (fcm добавится с боевым адаптером), `SMS_PROVIDER` расширяется реальным `mobizon`: `MOBIZON_API_KEY: string when SMS_PROVIDER=mobizon required`. e2e ТОЛЬКО `npm run test:e2e`, тестовая БД 5433, таймеры — виртуальное время, полный регресс перед каждым коммитом.

## Отложено в следующие эпики (не забыть)

### Долги, зафиксированные финальным ревью E9 (обязательны ДО боевого включения)

- **Модель исполнения dispatch — решить раньше, чем появятся ключи FCM.** Сейчас `await dispatch(...)` стоит на пути запроса `POST /v1/requests` и невидим только потому, что провайдер — Redis-мок. Выборка устройств без `take`, отправка последовательным циклом; чистка мёртвых токенов отложена, значит число `Device` на пользователя растёт монотонно. С боевым FCM это N последовательных сетевых вызовов в бюджете отклика самого латентно-критичного сценария продукта. Варианты: outbox/очередь либо `void dispatch().catch()` с отдельной метрикой лага; плюс `take: 20` и `Promise.allSettled`.
- **Broadcast Р-16 — тот же веер внутри секундного тика.** `escalation.service.ts` диспатчит последовательно каждому эксперту, `matching.findCandidates` сверху не ограничен, а у `OfferTimerService.tick()` нет защиты от наложения тиков. Параллелить с ограничением конкурентности либо вынести веер из sweep.
- **SMS-fallback без ограничителя расхода — до включения `SMS_PROVIDER=mobizon` в проде.** Одно платное SMS на каждый `offer.incoming` без ack за 10 с, до 100 за тик, без per-expert cooldown и глобального бюджета; `POST /v1/requests` не троттлится и доступен гостю. Нужны cooldown + потолок + ограничение конкурентности, иначе всплеск трафика конвертируется прямо в счёт. Там же — сверить фактический контракт Mobizon API (в коде помечен `// ДОПУЩЕНИЕ` про body-vs-query).
- **Push-токен в пути URL.** `DELETE /v1/devices/:token` кладёт токен в path, откуда он попадает в access-логи, трейсы APM и историю прокси; в паре с перепривязкой токена при регистрации это даёт угон пушей (глушение критичного `offer.incoming` у жертвы). Перевести на `DELETE /v1/devices` с токеном в теле. Замечание к плану, не к реализации.
- **Частичный индекс под sweep.** `notifications` растёт монотонно (ретенция отложена в E8), а рабочее множество sweep'а — единицы строк: `WHERE sms_fallback_at IS NULL AND push_delivered_at IS NULL` даст лучший профиль, чем текущий трёхколоночный btree.

### Известные расхождения, оставленные сознательно

- Типы уведомлений в коде гранулярнее плана: `payout.paid`/`payout.rejected`/`verification.approved`/`verification.rejected` вместо `payout.updated`/`verification.updated` (разные тексты ru/kz для успеха и отказа). Контракт для приложений E6/E7 — по коду, не по тексту плана выше.
- `markRead` с чужим id — тихий no-op, тогда как `ack` даёт 404; DoD требовал 404 для обоих. Выбранное поведение защитнее (не подтверждает существование чужого id).
- `smsFallbackAt` проставляется и когда SMS не отправлялось (оффер уже не PENDING) — поле означает «окно fallback закрыто», а не «SMS отправлено». Факт отправки отличим только по audit `notification.sms_fallback`; при расчёте метрики §11.6 в E11 это учесть.
- kz-тексты: юнит проверяет наличие и различие ru/kz для всех 9 типов, сквозные e2e подтверждают выбор локали для 4 из них.
- `PUSH_PROVIDER` валидируется в env, но фабрики нет — `MockPushProvider` зашит в модуль (та же конвенция, что у `PAYMENT_PROVIDER`); фабрика появится с боевым адаптером.
