# Статусы сотрудников

> В прототипе Smart Жоспарлау этот модуль объединён с тремя другими как «Сотрудники и штат».

## Назначение
Управление статусами личного состава: просмотр, назначение, планирование на любую выбранную дату и массовое обновление, обработка запросов на прикомандирование и формирование ответа управления на сбор сил ОМ.

## Маршрут и доступ
`/statuses`; текущий ресурсный доступ — `statuses/read`. Целевая область зависит от актора: начальник управления — своё управление; `FORCES_GATHERING_OFFICER` — весь свой департамент с правом изменения; `DUTY_OFFICER` — вся организация только для чтения по отдельному глобальному гранту.

## Экраны и флоу
- Карточки статистики: всего сотрудников, требуют обновления, просрочено, запланировано (считаются на клиенте из полученных staff units).
- Три вкладки: «Таблица сотрудников» (`StatusTable`), «Календарь статусов» (виджет `status-calendar`), «Массовое обновление» (`MassStatusUpdate`).
- Кнопка «Запланировать» прямо из списка статусов сотрудника (диалог планирования в `StatusTable`); также пункт меню «Запланировать статус».
- При задании управления на сбор сил начальник выбирает сотрудников и вид участия «Физнаряд»/группа. До распределения Штабом поле мероприятия необязательно; после распределения обязательны мероприятие и объект (`[СБС-30]`–`[СБС-32]`, `[СТА-04]`).
- Ответственный за сбор сил департамента должен уметь менять статусы в своём поддереве и из отдельной вкладки собирать/отправлять свод; оперативный дежурный статусы не меняет (`[РАСХ-ПЛН-03]`–`[РАСХ-ПЛН-05]`).
- Диалог запросов на прикомандирование (`SecondmentRequestsDialog` из `features/secondment-requests`).
- Обновление данных вручную (RefreshCw + инвалидация react-query).

## Данные и API
- `/api/staff_unit/staff-units/directorate/` — штатные единицы своего управления с текущими статусами (apps `staff_unit`, `statuses`).
- `/api/secondments/secondment-requests/` и `.../incoming/` — запросы на прикомандирование (app `secondments`).
- Изменение статусов — фича `employee-status-update` поверх app `statuses`.

## Ограничения и расхождения
- Инвариант «один активный статус на сотрудника»: `create_status` закрывает предыдущий; прикомандирование — тоже один статус. `EmployeeStatus.save()` зовёт `full_clean()` — два действующих статуса недостижимы.
- Клиентский парсер поддерживает два формата ответа (`unit.employee` и `unit.employees`) для обратной совместимости.
- Каждому работающему сотруднику статус по умолчанию проставляет сигнал `on_commit` на бэке.
- Текущий код требует мероприятие для ручного «Участия в ОМ» и не выдаёт `status.manage` роли `FORCES_GATHERING_OFFICER`; оба пункта расходятся с новым контрактом и требуют отдельных задач кода.

## Уточнение заказчика 09.09.2026 — группы и специальности (Plane №1088)

«Участие ОМ» → **«Физнаряд» / «Группы»**. В ветке «Группы» сначала выбирается группа подразделения, затем специальность внутри группы. Группы могут принадлежать департаменту, управлению или отделу. Сначала предлагаются свои группы; через отдельный доступ с поиском доступны группы других подразделений, включая другие управления и департаменты. Начальник управления вправе назначить своему сотруднику чужую группу и её специальность; область управляемых сотрудников от этого не расширяется. Для группы ОМ обязательно, для физнаряда до штабного распределения необязательно.

Обязательный контракт, условный пример БВС и дополнение к проходке: [[../../RAW/README#22. Участие ОМ: группы подразделений и специальности — решение заказчика от 09.09.2026|RAW/README §22]]. Исполнитель: Кодекс Астра 6.
## Требование заказчика 10.09.2026 — актуальный текущий статус у каждого сотрудника

Для каждого активного сотрудника в системе в обязательном порядке должен быть
текущий статус на сегодняшнюю деловую дату. Дата должна быть актуальной на
момент чтения и считаться по `Asia/Almaty`; пустой блок «Текущий статус» у
работающего сотрудника — дефект, а не допустимое отсутствие данных.

Наблюдение на стенде: у сотрудника Токтарова Азамата окно показывает «Текущий
активный статус отсутствует», хотя рядом есть записи статусов с датами
06.09.2026—07.09.2026 и 10.09.2026—13.09.2026. Требование и проверка цепочки
Celery worker + beat + ежедневных задач заведены в Plane №1113
(`3e3ee2b7-0781-46a8-ac6a-6ff657f2cb81`, `Backlog`, `high`). Связанные №961 и
№962 не заменяют эту проверку: они покрывают обработку ошибок задач и наличие
расписания, но не доказывают наличие актуального статуса у всех сотрудников в
рабочем контуре.

Исполнитель: Кодекс Астра 6.
