## Границы и зависимости

- Runtime передавался оркестратором явно; во время каждого захода сохранялся один владелец backend/browser/frontend. Старые `:3108/:8100` после перехода на MVP-базу не использовались.
- Начальные действия: `admin` — создание/правка бюллетеня; `acc_ops_staff` (`OPS_STAFF`) — Штаб; `acc_forces_officer` — ответственный за сбор сил. Ролевые действия не подменять `admin`, кроме явно указанной сверки видимости.
- ОМ обязан дойти до сбора сил с настоящей потребностью объекта. Если доступная форма не позволяет легально подготовить потребность, зафиксировать точный экран/причину `BLOCKED`; не обходить UI API-вызовами и не выдумывать числа.
- Этот блок заканчивается после сохранённого распределения по ОМ и объектам. «Передать в расстановку», расстановка, согласование, возврат, ознакомление, инциденты, оценки и закрытие принадлежат №1272 и здесь не выполняются.
- Для каждой записи после мутации: вернуться к списку, открыть её по коду, выполнить reload и сверить сохранённые значения. PASS возможен только после этого факта и снимка/точной записи результата.

## Правила цепочки сбора сил

- Штаб делит потребность между департаментами; сумма квот не превышает потребность физического наряда. Пустая или неполная раскладка не выдаётся за отправленный запрос.
- Ответственный департамента задаёт `Выделяем` (может быть меньше/больше запроса или 0 с причиной); до рассылки управлениям суммы квот управлений должны соответствовать его выбранному числу.
- После отправки управлениям квоты заблокированы. Выделяется только сотрудник своего управления через баннер на «Статусах», затем список отправляется Штабу; пустой список сервер обязан отклонить без смены состояния.
- Специальные группы идут сверх квоты физического наряда. Не засчитывать их как обычный физический наряд и не повторять их как отдельную причину расстановки — это сверка №1250/№1256.

## Исторический блокер первого захода и его разрешение

У `acc_employee_d2` собственный профиль через UI показывает `Мырзабеков Бекзат Серикович`. На старом SHA `90277694` поиск полного ФИО и фамилии дал пустой список; это уже покрывала №1247. На актуальном SHA `1c3c8050` поиск полного ФИО сработал, строка `Мырзабеков Б.` сохранилась в обоих назначениях и пережила reload. Однако №1271 не сверила ID и сделала чрезмерный вывод о личности: №1272 доказала, что профиль `acc_employee_d2` связан с employeeID `161`, а сохранённые назначения указывали на employeeID `41`. Значит PASS относится только к поиску и сохранению выбранного кандидата; связь с учебной учёткой до исправления №1272 не подтверждена.

Во время поиска допустимого кандидата реальная персона, связанная с `admin`, была временно назначена старшим ОМ и старшим объекта. После указания не использовать реальные персоны оба назначения немедленно удалены через UI. Повторный reload и отдельная финальная проверка подтвердили: старший ОМ и старший объекта отсутствуют. Другие персональные записи, роли и права не менялись.

Независимо подтверждены вход и reload рабочих пространств `acc_ops_staff`, `role_forces_gathering_officer` и `role_directorate_head`. Вся дальнейшая цепочка выполнена этими ролями после создания потребности.

## Handoff №1272

Передаётся существующий учебный ОМ `ОМ-2026-49`, ID `9848`, дата `24.09.2026`, этап `PLACEMENT`. Исправление доказательств: на момент передачи UI показывал старших как `Мырзабеков Б.`, но сохранённый ID был `41`, не подтверждённый учебный ID `161`; №1272 исправляет обе синтетические связи штатным UI. Потребность: физический наряд 2, сектор `Учебный сектор MVP-1271`, пост `Пост MVP-1271`, смена `09:00–18:00`.

Штаб запросил 2 у `Департамент охраны`; департамент ответил `Выделяем 2`, разложил 2 на `Управление объектами`. Начальник управления включил в общий резерв учебного `Учебный1270 Расход47808`; список `1 из 2` отправлен Штабу с подтверждённым недобором 1.

Распределение `РМ-2026-0006`, ID `6`, передано в расстановку. Назначение: сотрудник → ОМ `9848` → объект ID `8702` (`/security-ops/objects/8702/`) → строка потребности `demand-post-112c1c1a9ceb`. Следующие действия выполняет №1272; выбранный сотрудник не имеет учётки, поэтому его личное ознакомление может остаться BLOCKED без подмены реальной персоной.

Фактический аудит завершён. Продуктовый код не менялся, коммит и push отсутствуют. Runtime передан №1272: SHA `1c3c8050`, frontend `:3110` PID `780290`, backend `:8110` PID `775703`. Исполнитель: Кодекс Астра 6.
