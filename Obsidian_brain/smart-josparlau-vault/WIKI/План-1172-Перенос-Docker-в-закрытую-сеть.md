## Схема и выбор

Выбрана адаптация существующего deploy/contour отдельным профилем deploy/lan: переиспользовать проверенные Dockerfile и зависимости, не менять действующий контур3118 и не внедрять другой технологический стек. Альтернативы: прямой проброс Next/Django проще по числу контейнеров, но не покрывает защищённые файлы, статику и WebSocket; локальный registry оправдан для нескольких серверов, но для одного сервера добавляет ненужную зависимость. Поэтому поставляем image tar + sha256 + Compose без build/pull и nginx, обслуживающий портал3300 и backend8300. Оба внешних HTTP-порта проходят через nginx, Django остаётся отдельным контейнером8000. PostgreSQL отдельный контейнер5432 с публикацией5300, без подмены адреса db:5432 внутри контейнеров.

Дополнительные обязательные сервисы: Redis для каналов/cache/broker, Celery worker и один beat для расписания статусов. Worker и beat переиспользуют backend image, не запускают миграции, стартуют после healthy backend. Redis volume/AOF сохраняет очередь, beat volume хранит расписание. Отдельный слой settings lan включает существующее расписание base, без изменения контурных умолчаний. Логи worker/beat только console, чтобы не делить RotatingFileHandler с backend. КонтейнерыUTC, деловая зона Asia/Almaty. Почта/внешние интеграции не объявляются работающими без локальных серверов.

Поставляем приложение, PostgreSQL и Redis как заранее собранные образы; Docker Engine/Compose на целевой ОС — отдельная предпосылка, установочные пакеты подбираются после ответа об ОС. Сборка linux/amd64 соответствует текущему daemon, совместимость с неизвестным CPU не утверждается. Новые секреты генерируются отдельно и не включаются в Git/журнал. Данные media/private отдельно от образов. Backup/restore в локальную новую базу; пароль БД не переносится как роль суперпользователя, роли владельца dump не восстанавливаются. Ни удаления, ни перезапуска исходной БД.
