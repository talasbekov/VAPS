# КАК ПРОВЕРЯЕТСЯ — ТОЛЬКО БРАУЗЕР

- pytest НЕ ГОНЯТЬ и новых тестов НЕ ПИСАТЬ. Бэкенд-тесты, e2e-спеки и смоук в этой работе не считаются
  доказательством и не входят в гейт. Единственное доказательство — прогон В БРАУЗЕРЕ по прод-стенду
  (`npm run stand:prod`, :3108, живой Django :8100): открыть экран, нажать КАЖДУЮ кнопку, ссылку, вкладку,
  фильтр, пункт меню, действие в диалоге — и записать, что произошло.
- Форма записи — карта кликов в vault (`<vault>/QA-Audits/Прогон-тестовый-прод-<дата>.md`), таблица:
  экран | роль | элемент | ожидалось | получилось | вердикт (ОК / P0 / P1 / мелочь) | скрин.
  P0 — 500, потеря данных, невозможно пройти шаг сценария, чужие данные видны, вход не работает.
  P1 — кнопка ничего не делает, неверный запрет по роли, справочник пуст на живом сервере, экран
  без данных при наличии данных. Мелочь — всё остальное: записывается, НЕ чинится.
- Чинятся только P0 и P1. После правки — тот же клик повторяется в браузере, скрин «после» рядом.
- Прод-сборка (`npm run build:check`) нужна не как тест, а потому что бандл контура собирается из неё:
  красная сборка = нет бандла. Больше никаких обязательных прогонов.
- Проверять под ВСЕМИ учётками `acc_*` (`<vault>/Infrastructure/Учётки-стенда.md`) и под суперпользователем
  в админке. Консоль браузера и вкладка Network открыты: ошибки консоли и запросы вне LAN — в карту.

Начни с Plane: эпик «Тестовый прод в закрытом контуре» в `Backlog` (задача заказчика — строка в
`<vault>/RAW/README.md`, раздел 17), план в `<vault>/WIKI/`, шаги через `plane_task.py plan`. Каждый блок
ниже — карточка со своим коммитом.

# БЛОК 1. Офлайн-готовность

Проверить ФАКТОМ, что ни сборка, ни запуск, ни браузер не ходят в интернет. Известные точки:
- `app/layout.tsx` фронта тянет `Inter` и `JetBrains_Mono` через `next/font/google` — в контуре сборка упадёт.
  Перевести на `next/font/local` (или на установленный пакет `geist`), шрифты — в `public/fonts`.
  `grep -rn "fonts.googleapis\|next/font/google\|cdnjs\|jsdelivr\|unpkg" app components widgets features shared lib`.
- `@sentry/nextjs` во фронте: без DSN пакет должен молчать; во вкладке Network на прод-стенде — ни одного
  адреса вне LAN.
- Бэкенд: wheelhouse (`pip download`) для `requirements.txt` под целевую версию Python; ничего не тянется
  при старте.
- Docker: `postgres:15`, `redis:7-alpine`, базовые node/python — `docker save` в `.tar` + `sha256sums.txt`;
  в compose контура нет `build:`. Опора — проверенный путь `deploy/spike-1.9/` (`build-bundle.sh`,
  `install-probe.sh`, `RUNBOOK.md`): расширить до полного стека, не писать заново.
- Хардкод `10.15.3.187` в `docker-compose.prod.yml` и `Dockerfile` фронта (`NEXT_PUBLIC_MEDIA_URL`,
  `NEXTAUTH_URL`, `BACKEND_URL`) — в `.env.example`. `NEXTAUTH_SECRET` в git скомпрометирован — шаг
  рунбука «сгенерировать новый».
- Django production: `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` из env;
  `collectstatic` в entrypoint (сейчас только `migrate`) — статика админки в проде обязана отдаваться.
- Время: контейнеры в UTC, NTP в контуре нет. Зафиксировать `TIME_ZONE` (канон `Asia/Qyzylorda`, в `base.py`
  `Asia/Almaty`; выбрать одно, записать в `Infrastructure/Decisions.md`), в рунбуке — `timedatectl` и
  проверка даты в админке.
- Celery/beat/Redis: либо в бандле и проверены в браузере (статус по расписанию появился), либо честно
  выключены с записью в `Known-Issues.md`. Известно: «Celery-задачи статусов не доезжают на стенде».
- Ротация логов: `django.log` рос до 22 ГБ (Plane №1110).
Проверка блока — на этой машине с ВЫКЛЮЧЕННОЙ сетью: `docker load` → `docker compose up -d` → вход в
портал и в админку по IP хоста (не `localhost`) из браузера. Вывод команд и скрины — в
`Infrastructure/Changelog.md`.

# БЛОК 2. Аутентификация, авторизация, учётки, сотрудники

Проверить в браузере и довести до рабочего:
- Аутентификация: вход по логину/паролю, неверный пароль — понятная ошибка, выход, повторный вход;
  протухание access-токена при живой сессии (известный дефект «портал сломан через 8 часов») — после
  правки проверить принудительно (укоротить TTL на стенде); отзыв refresh (№828) не мешает работе;
  заблокированный пользователь (`is_active=False`) входить не может.
- Авторизация: под каждой учёткой `acc_*` — меню по правилу `[РЕЕ-09]` (пункт виден, недоступное
  отключено), чужой раздел по прямому URL — честный «нет доступа», не 500 и не пустой экран; данные
  чужого департамента не видны; критический authorization gap в `/organization` (Sentinel 23.08.2026)
  закрыть в первую очередь.
- Пользователи: создать пользователя, выдать роль и область (управление/департамент), выдать и отозвать
  право, сменить пароль, деактивировать — на сайте (`/settings/users`, `/settings/roles`,
  `/settings/permissions`) И в админке. Созданное на сайте видно в админке и наоборот; новый пользователь
  тут же входит и видит ровно то, что дала роль.
- Сотрудники: добавить сотрудника, привязать к подразделению и должности, привязать к пользователю,
  поставить статус, редактировать, уволить/деактивировать — на сайте (`/employees`, модуль сотрудников
  Службы) И в админке; новый сотрудник сразу появляется в расходе, календаре и сборе сил.
- Импорт сотрудников (`import_employees`, кнопка «Импорт») — либо работает по образцу файла из рунбука,
  либо кнопка убрана до готовности с карточкой.

# БЛОК 3. Админка: паритет с сайтом, порядок по значимости, лишнее убрать

Правило: ВСЁ, что делается на сайте, делается и в админке (пользователи, роли, права, сотрудники,
подразделения, должности, статусы, справочники, мероприятия, объекты, посты, обращения обратной связи).
- Пройти админку в браузере по каждому разделу: список открывается, поиск и фильтры работают, создание,
  правка, удаление сохраняются и видны на сайте. Раздел с 500 или без формы — P0.
- Отсортировать по значимости, а не по алфавиту. Целевой порядок разделов (`admin_categories.py`,
  `admin_site.py`): 1) Доступ: пользователи, роли, права, области; 2) Структура и штат; 3) Сотрудники и
  статусы; 4) Справочники; 5) Охранные мероприятия (мероприятия, объекты, посты, расстановка, оценки);
  6) Сбор сил и расход; 7) Обратная связь; 8) Документы и отчёты; 9) Служебное (журналы, токены).
  Внутри раздела — сначала то, с чем работают ежедневно. Категория «Прочее» после наведения порядка
  должна быть ПУСТОЙ.
- Убрать лишнее: `admin_auto.py` регистрирует всё подряд (`register_remaining`) — заменить на явный
  перечень. Снять с регистрации модели, с которыми не работаем: технические (результаты Celery, sessions,
  sites, blacklist-токены, промежуточные through-таблицы, версии/снимки без ручной правки), архивные и
  дублирующие. Таблицы не удалять — только не показывать. Список снятого с причиной — в
  `Personnel-Records/Decisions.md`.
- Известные карточки: №1055 (несбалансированная категория), №1135 (bootstrap смешан с демо).
- Начальные данные — чистый bootstrap одной командой (`manage.py bootstrap_contour`: `init_dictionaries`,
  `seed_positions_ranks`, `seed_status_types`, `seed_org_structure`, `seed_access_matrix`,
  `seed_role_accounts`), демо-набор — отдельной командой по флагу. Суперпользователь — шагом рунбука.

# БЛОК 5. Основной сценарий проходки ОМ

Пройти в браузере под ролевыми учётками без единого 500 и мёртвой кнопки:
  бюллетень (сотрудник 2-го департамента) → объекты посещения и старший объекта (старший наряда/ГВО) →
  рекогносцировка → расстановка постов → согласование → ознакомление → оценка → закрытие → архив;
  рядом — сбор сил, календарь ОМ, реестр ГВО / визиты иностранных ОЛ в объёме, который уже есть.
- Чинить только то, что РВЁТ путь (P0/P1). Расхождения с каноном, не мешающие пройти, — карточками.
- Проверить первыми открытые дефекты: №1112 (будущие статусы ОМ исчезают из диалога), №1102/№1103
  (скрытые 403 у старшего объекта), №1101, №1114, №1120 (вход ведёт observer на закрытый экран),
  №1125 (скрыт вход в «Отчёты по Службе»), №972 (RBAC сбора сил).
