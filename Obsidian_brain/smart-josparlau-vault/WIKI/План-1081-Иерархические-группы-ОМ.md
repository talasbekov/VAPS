# Иерархические группы участия ОМ — план реализации

> **Для agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Реализовать `[ОМ-ГР-01]`–`[ОМ-ГР-07]`: статус «Участие ОМ» выбирается через две подгруппы, группы принадлежат подразделениям, свои показаны первыми, чужие находятся отдельным поиском, специальность всегда принадлежит выбранной группе.

**Architecture:** `OpsDictionaryEntry` получает необязательного владельца-подразделение только для записей `EVENT_PARTICIPATION_KINDS`. API справочника отдаёт текущий путь владельца и `isOwn`, вычисленный по области `status.manage` актора; каталог на клиенте разделяет один `PHYSICAL_SQUAD` и специальные группы, а компонент выбора хранит прежний контракт `kind_code + role_code`. Чужая группа влияет только на выбранный код участия и не меняет область доступных сотрудников.

**Tech Stack:** Django/DRF/PostgreSQL, Next.js/TypeScript, React Query, Playwright, pytest.

**Spec:** `/home/erda/Музыка/Obsidian_brain/smart-josparlau-vault/RAW/README.md`, §22 `[ОМ-ГР-01]`–`[ОМ-ГР-07]`.

## Global Constraints

- Первая развилка подписана «Физнаряд» / «Группы».
- Для группы обязательны мероприятие и специальность; физнаряд сохраняет действующий контракт общего резерва.
- Свои группы показываются первыми; чужие доступны отдельным поиском с полным путём подразделения.
- Выбор чужой группы не расширяет область сотрудников `status.manage`.
- Смена группы всегда очищает специальность прежней группы.
- Существующие записи без владельца остаются читаемыми в разделе других групп.
