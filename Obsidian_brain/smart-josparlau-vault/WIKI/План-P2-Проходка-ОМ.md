К вечеру 03.09.2026 из 22 карточек P1 в `Review` четырнадцать (№385–389, 391–394, 396–398, 402 и семь шагов №407–413 плана №385), две в работе (№395 [СБС-31], №399 [СОГ-08]), шесть в `Backlog` (№390 [СБС-13], №400 [ВОЗ-03], №401 [СОГ-12], №403 [ОЗН-09], №404 [ЗАК-12], №405 [ПРФ-04], №406 [СТА-01]). Ключевое следствие плана №385: этапы, потребность, расстановка, маршрут и документ теперь живут на **объекте посещения**, а не на мероприятии. Из 47 строк P2 по статусам аудита: ❌ отсутствует — 19, 🟡 частично — 20, 🔄 сделано иначе — 8. Иначе сделанное — самое дорогое: там уже есть код и данные, и переделка требует бэкфилла (визит ГВО как JSON-патч, рейтинг отдельным модулем, заявки в JSON `force_allocation`).

## Развилки, решённые до кода

**Порядок — по сценарию проходки, а не по алфавиту кодов.** Спецификация читается как один путь: справочники → создание ОМ → бюллетень → реестр → рекогносцировка → сбор сил → статусы → расстановка → согласование → возврат → ознакомление → закрытие → профиль → визит ГВО → дело. Шаги идут в этом порядке, и ранний шаг заводит данные, на которые опирается поздний (коды ОЛ нужны форме создания; таблица заявок нужна колонкам сбора сил; реквизиты подписи нужны подвалу PDF; статус визита нужен странице визита).

**Три модельных переезда делаются «расширять, не подменять»** — как план №385. Заявки (МД-06), визит ГВО (МД-05), оценки (МД-08) сейчас работают; новая таблица заводится рядом, миграция с бэкфиллом переносит существующее, читатели переводятся по одному, старый источник снимается отдельным шагом. Отвергнуто: снести JSON и чинить читателей одним коммитом — раздел стоял бы всё время переезда, а откат невозможен.

**Права штаба — одним шагом, а не по кусочку в каждом экране.** Аудит нашёл отсутствие прав у `HEAD_OPS_UNIT` в четырёх местах (БЛН-10, РАС-08, ГВО-09, СБС-10). Это одна причина — сид ролей — и один шаг Ш-5; экранные шаги на права не тратятся, а опираются на него.

**Что НЕ делает этот план.** Не трогает P1 (свои карточки), не трогает P3, не заводит новых персон обхода (решение заказчика от 29.08.2026 не пересматривается). Строки с пометками ⚠/❓ раздела 15 аудита остаются вопросами заказчику.

## Риски

- **Три переезда данных (Ш-9, Ш-17, Ш-19) — необратимы по смыслу**: обратная миграция снимает таблицы, но не восстанавливает JSON после того, как в таблицы писали. У каждого — число перенесённых строк в выводе миграции и старый источник, живущий до отдельного шага снятия.
- **Ш-6 может отменить сделанное в №350** («прятать или оставить „Доступ закрыт“» — карточка в `On test`). Решение заказчика по №350 читается до кода Ш-6.
- **Ш-11 закрывает ручной ввод участия** — если на стенде есть статусы участия без запроса, они станут нередактируемыми. Миграция помечает их «заведён вручную», а не удаляет.
- **Стенд**: три волны — минимум три полных прогона по прод-стенду; между шагами с моделями — замер RSS и `seed_smoke_fixtures`.
- **Пины проб** реестра и этапов изменятся у Ш-7, Ш-8, Ш-12 — правятся с комментарием почему, не подгонкой.
