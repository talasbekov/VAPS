## Граница разбора

Статическая инвентаризация кода для ручной браузерной проверки №1139. Код и данные не изменялись, тесты и браузер не запускались. Наблюдение браузера передано основной сессией: под `acc_employee` страница `/organization` показывает корректно ограниченную сводку (первое управление, 26 занятых), но диаграмма пуста с текстом «Данные не загружены из API»; запрос `getStaffUnits` получает 403. `/settings/users` отвечает «Доступ закрыт», недоступные пункты меню после загрузки роли отсутствуют. Эти динамические факты принадлежат основной сессии; ниже — их объяснение по исходникам.

## Сессия и сроки JWT

- Бэкенд закрыт по умолчанию: `REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES = IsAuthenticated`; публичные ручки должны открываться явно. Источник: `organization_management/config/settings/base.py:167-177`.
- Access JWT живёт 8 часов, refresh JWT — 7 суток. Включены `ROTATE_REFRESH_TOKENS=True` и `BLACKLIST_AFTER_ROTATION=True`. Источник: `organization_management/config/settings/base.py:202-229`.
- NextAuth хранит access и refresh в JWT-сессии. Срок refresh на фронте продублирован константой `7 * 24 * 60 * 60`, поэтому изменение серверного TTL требует синхронной правки клиента. Источник: `PersonalRecordFront/lib/auth-config.ts:30-40`.
- Клиент извлекает `exp` из access JWT и начинает продление до истечения; неизвестный срок получает короткий запасной интервал. Источник: `PersonalRecordFront/lib/refresh-policy.ts:1-116`.
- Продление сериализовано по значению refresh-токена, сохраняет новый refresh после ротации, различает окончательный отказ 400/401/403 и временный сетевой/5xx отказ. При окончательном отказе access удаляется; временный отказ оставляет сессию и ставит повтор. Источник: `PersonalRecordFront/lib/auth-config.ts:61-157`.
- Риск для ручной проверки: фронтовое семисуточное значение не выводится из серверной настройки; рассинхронизация TTL будет статически незаметна. Это точка риска, не подтверждённый дефект №1139.

## `/organization`: две разные цепочки данных

### Сводка и таблица

`app/organization/page.tsx:22-64` вызывает `useStaffUnitStatistics`, то есть `GET /api/staff_unit/statistics/`. Сервер:

- требует аутентификацию (`staff_unit/views.py:1671-1677`);
- принимает `orgstructure.view` либо `status.view` (`staff_unit/views.py:1832-1894`);
- строит область через `PermissionService.visible_division_ids`, раскрывая выданный узел вместе с потомками (`staff_unit/views.py:1612-1649`);
- считает подразделения, штат, занятые места и вакансии только по `division_ids` этой области (`staff_unit/views.py:1704-1805`).

Это объясняет корректно ограниченную сводку `acc_employee`, увиденную в браузере.

### Диаграмма

`OrgChart` использует `useStaffUnits()` (`features/organization-structure/ui/OrgChart.tsx:43-65`), хук вызывает `apiClient.getStaffUnits()` (`hooks/use-staff-units.ts:4-10`), а тот обращается к `GET /api/staff_unit/staff-units/?page_size=500` (`lib/api.ts:914-970`). Это стандартный action `list` класса `StaffUnitViewSet`.

Для стандартного чтения `StaffUnitViewSet.get_permissions()` возвращает `CanViewStaffingTable`, а `get_queryset()` фильтрует через `get_user_scope_queryset` (`staff_unit/views.py:196-242`). Последующее чтение `common/rbac.py:53-76, 271-294` уточнило смысл этих legacy-имён: `view_staffing_table` переводится в `orgstructure.view`, и queryset получает scope того же `orgstructure.view`. Исключение `directorate_management` действительно отдельное: безопасное чтение `/staff-units/directorate/` принимает `CanReadDirectorate`, который признаёт `status.view` (`staff_unit/views.py:213-231`, `1542-1589`).

### Корневая причина подтверждённого браузером отказа — уточнено при №1152

Первичная формулировка выше требовала уточнения после чтения адаптера RBAC и сидов. `CanViewStaffingTable` не остаётся отдельным кадровым разрешением: `common/rbac.py` переводит `view_staffing_table` в `orgstructure.view`, а `get_user_scope_queryset` фильтрует штатные единицы областью именно этого права. Роль `EMPLOYEE` имеет `status.view`, но не `orgstructure.view`. Поэтому сводка проходила по своему альтернативному `status.view`, а диаграмма закономерно получала 403. Реальный разрыв — отсутствующий гейт всей страницы `/organization`, а не недостаточно широкий backend staff-units. Отдельная карточка исправления — Plane №1152 (`2d06bcee-b175-457f-9b22-c1c4ae02ccf7`).

### Минимальное предлагаемое исправление для №1152

Наиболее узкая корректная правка — добавить `/organization: orgstructure.view` в общий `MODULE_PERMISSION` и не монтировать компонент с data-хуками, пока право не загружено и не подтверждено. Backend list/retrieve штатных единиц уже согласован с этим правом и его scope; менять его не требуется. Расширение по `status.view` отвергнуто как раскрытие модуля роли `EMPLOYEE`, которой оргструктура по сиду не выдана.

## Учётные записи, сотрудники и маршруты

- Администрирование учёток живёт в `/api/operations/accounts/` (`operations/api/urls.py:30-34`). List/retrieve/create/update/reset-password каждый явно вызывает `require_permission(request, "admin.roles")`; удаления нет, блокировка идёт через `is_active`, временный пароль возвращается один раз. Источник: `operations/api/views.py:760-857`.
- Фронтовый `/settings/users` берёт код гейта из общей карты `MODULE_PERMISSION`, ждёт загрузки прав и при отсутствии `admin.roles` показывает `OpsAccessDenied` (`app/settings/users/page.tsx:59-113`). Хук всё же создаёт запрос учёток до раннего return (`:86`), но серверный гейт остаётся обязательной защитой. Браузер подтвердил ожидаемый экран отказа.
- `/settings/permissions`, `/settings/roles`, `/settings/users` в общей карте требуют `admin.roles`; меню и страницы используют один источник (`entities/portal-access/index.ts:74-76`).
- `/service-employees` в карте помечен `null`, то есть сам маршрут открыт любому вошедшему, но фактический API ограничивает список и при 401/403 экран показывает отказ (`entities/portal-access/index.ts:24-27`, `features/service-employees/ui/ServiceEmployeesScreen.tsx:21-44`). Это следует проверять как серверное разграничение данных, а не только видимость пункта.
- `/organization` отсутствует в `MODULE_PERMISSION`. Функция `modulePermissionsOf` трактует неизвестный адрес как список без требований, поэтому клиентский маршрут/пункт сам по себе не гейтится; защита и область сейчас зависят от API. Это согласуется с тем, что `acc_employee` открывает страницу, но делает особенно важным единообразный серверный scope обеих её ручек. Источник: `entities/portal-access/index.ts:24-84, 112-124`.
- Новый `GET /api/core/employees/` требует `personnel.view` и фильтрует сотрудников через `PermissionService.visible_division_ids` и `StaffUnitSelector.employee_ids_in` (`core/api/views.py:81-112`). Новый `GET /api/core/divisions/` требует `orgstructure.view`, но его queryset в показанном коде не применяет scope и отдаёт все подразделения (`core/api/views.py:36-55`). Это статическая точка риска для адресных браузерных/API-проверок, не подтверждённый дефект: permission проверяется, но ограничение по выданному подразделению в queryset не видно.
- Legacy `DivisionTreeViewSet` требует только вход и сериализует первый корень целиком (`divisions/api/views.py:18-36`); обычные read-actions `DivisionViewSet` также не получают scope, кроме `employees`, а write-actions требуют `orgstructure.manage` и фильтруют адресуемые объекты/родителей (`divisions/api/views.py:39-112`). Эти маршруты следует считать зонами для отдельной проверки только если браузер реально их вызывает; статический обзор не доказывает утечку в пользовательском сценарии №1139.

## Что целесообразно кликнуть основной сессии

1. Под `acc_employee` повторить `/organization`: сохранить 200 статистики и 403 `/api/staff_unit/staff-units/` как пару, показывающую расхождение двух источников одной страницы.
2. На доступном кадровом экране проверить `/service-employees`: список должен содержать только сотрудников области роли; прямая карточка чужого employee ID должна получить серверный отказ/404, если такой id безопасно получен основной сессией.
3. Под ролью с `admin.roles` открыть `/settings/users`; под `acc_employee` подтвердить не только UI-отказ, но и 403 прямого запроса `/api/operations/accounts/` в Network. Сам UI уже подтверждён.
4. Если `/api/core/divisions/` вызывается каким-либо доступным экраном, сравнить ответ scoped-роли с выданной областью. До динамической проверки не регистрировать это как дефект.

## Результат

Причина пустой диаграммы локализована до отсутствующего гейта страницы: `EMPLOYEE` входил по прямому URL, сводка принимала его `status.view`, а дерево правильно требовало отсутствующий `orgstructure.view`. №1152 добавляет единый гейт и откладывает data-запросы до подтверждения права; backend не расширяется. Остальные перечисленные места остаются картой проверок и точками риска. Тесты и браузер в этой подзадаче не запускались.

Реализация №1152: коммит `2b2a1b33` (`fix(front): gate organization by structure access (Plane #1152)`). Изменены только `app/organization/page.tsx` и `entities/portal-access/index.ts`; backend изучен и оставлен без изменений, поскольку его текущая защита соответствует целевому праву и области.
