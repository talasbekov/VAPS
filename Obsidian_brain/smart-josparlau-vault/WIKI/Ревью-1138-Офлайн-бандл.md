## C1 — закрыт в 45d67d29; исходный Critical: nginx теряет внешний порт при относительных редиректах

Ниже сохранена исходная находка для истории. Актуальное состояние — исправлено; scoped re-review приведено в конце.

Файл: `deploy/contour/nginx.conf:7`, `:22`, `:25`; связанный port mapping `deploy/contour/docker-compose.yml:104` (`3118:80`).

В server отсутствует `absolute_redirect off;`. По умолчанию nginx делает абсолютным любой выходной Location, начинающийся с `/`, используя локальный порт соединения. В контейнере этот порт — 80, а браузер пришёл на 3118. Поэтому `http://LAN:3118/admin` получает `Location: http://LAN/admin/` и покидает origin контура. Аналогично ломаются относительные редиректы, возвращённые backend, включая обычный анонимный переход Django `/admin/` → `/admin/login/?next=/admin/`. Существующий `proxy_set_header Host $http_host` корректно передаёт порт Django, но не меняет алгоритм nginx для выходного относительного Location.

Доказательство — статический разбор конфигурации и исходника ровно nginx 1.28: [ngx_http_header_filter_module.c, release-1.28.0](https://github.com/nginx/nginx/blob/release-1.28.0/src/http/ngx_http_header_filter_module.c#L298): ветка `absolute_redirect` выбирает host и получает порт через `ngx_inet_get_port(c->local_sockaddr)`; HTTP80 не добавляется в Location. [Официальная документация absolute_redirect](https://nginx.org/en/docs/http/ngx_http_core_module.html#absolute_redirect) подтверждает default on и режим относительных редиректов при off.

Исправление: `absolute_redirect off;` на уровне server (либо эквивалентная настройка, сохраняющая опубликованный origin для всех редиректов). Затем контроллеру открыть `/admin` и `/admin/` в браузере по LAN IP:3118, проверить цепочку Location и успешное открытие login на том же origin. Это статически подтверждённый дефект; браузерное воспроизведение reviewer не выполнял согласно ограничению.
