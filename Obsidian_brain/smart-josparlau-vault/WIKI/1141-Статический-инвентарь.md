## №342 и актуальные читатели статусов

Каноническая таблица — `operations.StatusType` / `ops_status_types`. В ОМ `F/hooks/use-ops-status-types.ts` получает API, хранит полный каталог для подписей и активный поднабор для выбора. При ошибке/пустоте он возвращает пустой массив, зашитой копии **в этом хуке нет**. Читатели:

Кадровый `/api/statuses/types/` разрешён IsAuthenticated. Каталог `B/apps/statuses/catalog.py` читает ту же таблицу, отдаёт `legacy_code` при наличии, иначе `code`. `use-employee-status-types.ts` получает `/api/statuses/types/` (через apiClient.getEmployeeStatusTypes), useStatusNaming расходится по таблице статусов, структуре и диалогам. При ручном выборе убираются placeholder и прикомандирование/откомандирование; исключения участия дополнительно контролирует бизнес-сервис.

**Оставшиеся статические копии**:

1. `F/app/employees/page.tsx:501–505`: при `catalogStatusTypes.length === 0` фильтр подставляет EMPLOYEE_STATUS_ITEMS.
2. `F/components/status-table.tsx:646–653`: то же поведение фильтра.
3. `F/entities/status/naming.ts:92–99`: fallback старых подписей, а цвет остаётся клиентской палитрой; неизвестный код выводится самим кодом. Деактивированный тип исключён кадровым API и может потерять изменённую оператором подпись в таких кадровых отображениях.
4. `B/apps/dictionaries/api/urls.py` сохраняет **подключённый** `/api/dictionaries/status_types/`; его StatusTypeListSerializer отдаёт 13 EmployeeStatus.StatusType.choices и требует только IsAuthenticated. Современные frontend-читатели этой ручки не найдены; legacy API всё ещё расходится с канонической таблицей.
5. `B/apps/statuses/catalog.py:94–120`: серверный fallback старых 13 подписей только когда код не найден в таблице. Основной каталог и валидация берутся из таблицы.

Историческое утверждение «ни одной копии» верно для удалённых STATUS_TYPE_OPTIONS/STATUS_LABEL_BY_CODE в daily-grid, но **не является полным описанием нынешнего кадрового frontend/backend**. По строгому требованию №1141 «живые данные нельзя заменять зашитой копией» пункты 1/2 требуют исправления или отдельной зафиксированной оценки.

## Находки и браузерный приоритет

### P1-кандидат: чистый контур не получает секции общей расстановки

`B/apps/common/management/commands/bootstrap_contour.py:11–21` не вызывает sync_placement_sections. `seed_operations.py:773–828` наполняет 8 generic-справочников, PLACEMENT_SECTIONS среди них нет. Migration 0066 добавляет только разрешённый код в constraint. `use-placement-sections.ts` и `ops/security_events.py:5880` требуют активные секции, поэтому на чистой базе оператор не сможет выбрать вторую координату назначения.

Файл шаблона прочитан стандартными zipfile/XML средствами без Django/test runtime: `placement_full.docx` содержит **29 подходящих заголовков и 24 уникальные подписи**, что совпадает с назначением sync-команды. Браузер: открыть `/security-ops/dictionaries/PLACEMENT_SECTIONS` на contour_bootstrap_1140, увидеть ноль; после санкционированного исправления bootstrap получить 24 и проверить форму назначения.

### P1-кандидат по прямому требованию №1141: пустой кадровый каталог маскируется копией

Пункты 1/2 выше показывают старые статусы даже при настоящем пустом ответе или отказе загрузки. Это не регрессия живого непустого каталога: нормальный серверный результат имеет приоритет. Для подтверждения не удалять статусы и не очищать БД: проверить через браузер контролируемый отказ запроса/пустой разрешённый контур либо показать статическое доказательство и отдельно оценить исправление. Потеря API должна давать читаемый отказ/повтор вместо ложного каталога.

### P2-кандидат: правка группы не обновляет уже прогретую форму

`F/hooks/use-dictionaries.ts:46–50` инвалидирует только ключ `ops-dictionaries`. `use-participation-catalog.ts:31–35` использует отдельный `ops-participation-catalog`, staleTime 10 минут. После открытия формы участия, перехода в справочник, создания/переименования группы и возврата в прежнюю сессию новая группа может не появляться до refresh/истечения TTL. Это не hardcode; это несовпадение ключей кэша. Браузерный сценарий следует прогонять без перезагрузки всей страницы, затем сравнить с refresh.

### P2-кандидат: каталог журнала не управляет журналом

`B/apps/ops/security_events.py:8422–8428` принимает только INSTRUCTION/ORDER/INCIDENT; REPLACEMENT системный. Тип фронта `entities/security-event/model/types.ts:594` и подписи stage-meta также фиксированы. Generic-редактор принимает новый JOURNAL_ENTRY_TYPES, но ни подпись существующего кода, ни новый тип не обязаны попадать в форму журнала. То же различие нужно явно показывать в рунбуке, а не обещать «все формы читают справочник». Это более широкая интеграционная работа, оценку допуска P1 принимает основной исполнитель после проверки сценария.

### Дополнительные ограничения

- seed_operations использует update_or_create с `is_active=True`, label, description и group_code: повторный bootstrap повторно включает/переименовывает исходные generic-значения, description сбрасывает. seed_status_types тоже восстанавливает канонические поля, но сохраняет color/is_active существующих типов. Оператору нельзя обещать, что bootstrap сохраняет все ручные настройки без изменения.
- Кадровый useStaffDictionary берёт только `?page_size=500` без обхода страниц. При количестве больше 500 отдельная проверка необходима; текущие seed-числа меньше порога.
- Нормативные акты из seed_legal_documents — демонстрационные записи, не доказательство реальной действующей нормативной базы. По уточнению основного исполнителя 10.09.2026 они сознательно исключаются из чистого bootstrap; отсутствие их строк не оформляется дефектом автоматического наполнения.
- P0 по этому статическому срезу не обнаружен. Браузер, реальные права и фактические counts этой проверкой не подтверждались.
