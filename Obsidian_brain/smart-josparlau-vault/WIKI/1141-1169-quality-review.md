## Корректность backend

- `_validated_group()` на EVENT_GROUP_ROLES нормализует пробелы/регистр, отвергает пустое значение, PHYSICAL_SQUAD и отсутствие активной записи именно в EVENT_PARTICIPATION_KINDS. Код другого словаря не проходит. Ошибка попадает в общий field_errors[groupCode] и приводит к 400 до INSERT/UPDATE.
- Одна и та же проверка вызвана в create_entry и update_entry, поэтому создание и правка не имеют расходящихся правил.
- У POST_REQUIREMENTS сохранена прежняя необязательность, родитель POST_REQUIREMENT_GROUPS и проверка активного родителя. Новая нормализация и запрет физнаряда на этот справочник не распространяются.
- У справочников без GROUP_PARENT helper возвращает None; create не сохраняет чужую группу, update сохраняет прежний путь wants_group=False. Изменение не открывает запись дополнительных полей.
- Обе операции сохраняют transaction.atomic, update блокирует изменяемую запись через _lock_entry. Валидация до присваивания полей означает, что отказ не оставляет частично обновлённую строку. Аудит update по-прежнему включает старый/новый groupCode.
- PATCH роли без groupCode теперь получает 400 согласно утверждённому spec: новая форма это поле передаёт всегда. Это явное изменение обязательности контракта, а не случайная потеря значения на успешном PATCH.

## Корректность frontend и кэша

- Видимость поля определяется типом справочника, а не тем, было ли заполнено старое значение. Поэтому старый null в EVENT_GROUP_ROLES теперь исправим; POST_REQUIREMENTS также можно дополнить группой после создания.
- Пустой/пробельный код роли блокирует кнопку; непустой код проверяется сервером. Тип button не полагается на native required-валидацию, но явный disabled и серверный guard выполняют проверку.
- Create передаёт newGroup, edit — groupCode при hasGroup. lowercase и лишние внешние пробелы корректно нормализуются backend для EVENT_GROUP_ROLES. При server error onFormError сохраняет groupCode-сообщение в видимом role=alert.
- `useInvalidateDictionaries` добавляет точный ключ `["ops-participation-catalog"]`, совпадающий с useParticipationCatalog. Общий callback подключён к create/update/set-active/delete. Активный query перечитывается, неактивный помечается stale и перечитывается при включении; прежний десятиминутный staleTime не препятствует этому.
- Инвалидирование выполняется после успешной записи, поэтому сервер уже видит новое значение. Две независимые invalidateQueries запускаются без ожидания — допустимо для обновления UI; интерфейс не утверждает, что повторное чтение уже завершилось в момент завершения mutation. Страница потребителя при открытии выполняет штатную query-логику.
- Callback также инвалидирует участие при изменении несвязанного справочника: это лишнее обновление, но не ошибка данных/прав и не основание расширять исправление.
