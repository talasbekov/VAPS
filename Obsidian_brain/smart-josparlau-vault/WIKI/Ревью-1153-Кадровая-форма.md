## Найденные проблемы

### P1 — новые поля изменяются без административных прав

`Personnel-Records/organization_management/apps/staff_unit/views.py:1345–1376`, также создание user на строках 1024–1028. В `get_permissions` действие `directorate_management` для PATCH/POST не попадает в ветку CanManageStaffingTable: получает default CanViewStaffingTable (orgstructure.view). Само действие затем проверяет только status.view. Таким образом учётка с этими двумя правами чтения может напрямую отправить PATCH employees:[{id, is_active:false}] либо сменить user на свободную учётку; новые поля сохраняются без orgstructure.manage/admin.roles. Проверка UI в ServiceEmployeesScreen обходится прямым запросом. Дополнительно область записи берётся через _own_scope_divisions из status.view, а не области кадрового права. Следствие: административные изменения состава/связи идентичности доступны читателям в их области просмотра. Нужен серверный гейт новых кадровых операций и область именно права записи; текущие операции статусов нельзя случайно заблокировать общим ужесточением всей пакетной ручки.

### P1 — повторное сохранение откатывает предыдущую правку

`PersonalRecordFront/features/service-employees/ui/EmployeeAdminDialog.tsx:105` и `:125`. Форма читает исходные значения из query ['staffing-employee', id] (строки 63–70), но после записи инвалидирует только ['service-employees']. Общий staleTime — 60 секунд. Если изменить фамилию/позывной, сохранить и сразу снова открыть того же сотрудника, форма получает старые значения из свежего кэша. Следующий save отправляет все поля, включая неизменённые пользователем старые значения, и перезаписывает недавнюю правку. Нужно обновить/инвалидировать query кадровой формы и связанные читатели. Перед браузерным гейтом полезна последовательность двух правок разных полей с немедленным переоткрытием.

### P2 — поиск учётной записи стирает несохранённый ввод

`PersonalRecordFront/features/service-employees/ui/EmployeeAdminDialog.tsx:141`. key формы включает accounts.isSuccess, а accountSearch входит в queryKey useAccessAccounts. Для нового поискового запроса isSuccess меняется true→false→true: React перемонтирует всю форму и возвращает uncontrolled поля к defaultValue. После заполнения карточки поиск учётки стирает изменения и выбранные значения. Нужна стабильная форма после первичной инициализации; состояние сетевого поиска не должно менять её key.

### P2 — ошибка сохранения оставляет частично изменённую карточку

`PersonalRecordFront/features/service-employees/ui/EmployeeAdminDialog.tsx:91–104` использует пакетный PATCH для одной карточки. В `_directorate_update` штатная единица сохраняется первой (views.py:1299–1325), затем обрабатывается Employee; исключение привязки либо full_clean ловится и превращается в errors без отката успешной штатной правки. Сценарий: изменить должность и выбрать занятую учётку. UI показывает отказ сохранения, но должность уже записана. Пакетная семантика endpoint историческая, однако новая форма впервые связывает две части как единое сохранение. Нужна атомарность единичной кадровой команды либо точная обработка частичного результата с перечитыванием, без обещания полного отказа.
