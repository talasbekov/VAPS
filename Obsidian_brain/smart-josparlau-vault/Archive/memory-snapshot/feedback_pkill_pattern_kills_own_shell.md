`pkill -f "manage.py runserver 0.0.0.0:8100"` в bash-инструменте убивает не только Django, но и СВОЙ ЖЕ шелл: строка команды содержит паттерн и попадает под совпадение. Команда падает с exit 144, стенд остаётся лежать, а следующая красная проба краснеет по чужой причине — и ничего не доказывает.

**Why:** 18.08.2026 так дважды ронялся стенд посреди красных проб; один прогон пришлось признать недействительным и повторить. Плюс `pgrep -af "<паттерн>"` по той же причине показывает собственную bash-строку и создаёт ложное «процесс жив».

**How to apply:** самое надёжное — гасить по ПОРТУ (`fuser -k 8100/tcp`), потому что `for P in $(pgrep -f "<паттерн>")` ловит собственную bash-строку ровно так же, как `pkill`, и убивает себя (проверено 18.08 — уронил стенд ещё раз уже этой формой). Проверять живость тоже по порту, а не по `pgrep`: `curl -s -o /dev/null -m 3 http://127.0.0.1:8100/api/token/`. Django поднимать через `setsid ... & disown`, иначе он уходит вместе с фоновой командой. Перед красной пробой убеждаться, что стенд отвечает, — иначе см. [[feedback-noop-red-probe]].

Django на стенде запускается ТОЛЬКО с `DJANGO_SETTINGS_MODULE=organization_management.config.settings.local_postgres` (дефолт из `manage.py` — production, он ищет докерный хост `db` и падает на резолве имени).
