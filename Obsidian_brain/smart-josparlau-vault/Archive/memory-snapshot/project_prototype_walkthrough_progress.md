⚠️ Оценка «источника нет у большей части» для «Аналитики ОМ» оказалась
ЗАВЫШЕННОЙ: `/api/ops/operations-analytics/` (срез H) закрыл шапку
показателей, структуру (по состояниям, не по типам), воронку в двух режимах,
обеспеченность, таблицу объектов и карточку ОМ — это 6 блоков из 17 плюс всю
навигацию по пяти уровням. Не нашлось источника у 13: период и фильтры,
динамика по датам, типы ОМ, департаменты (`group` — свободная строка расчёта,
не подразделение), дефицит по ОМ (аналитика даёт СУММЫ, а командный центр
считает по каждому запросу), посты по всем ОМ, человеко-часы, замены,
план/факт, конфликты по видам, хронология, «требует внимания», экспорт.
Вывод на будущее: прежде чем записывать экран в «источника нет», сходить в
ответ живой ручки — реестр возможностей шире, чем читается по прототипу.

🔴 За «Аналитикой ОМ» остался ОТКРЫТЫЙ хвост (§ экрана в `docs/api-gaps.md`):
одиночный кадр, где плитка «В подготовке» показала `0` вместо `63`. Ноль —
законное значение для СУЖЕННОГО снимка (`level=OBJECT&object_id=2`), то есть
кадр выглядит как чужой снимок на общем экране. Не воспроизвёлся: 6 холодных
прогонов, 8 повторов, 60 кадров по 40 мс. Ретраем не гасил — это прикрыло бы
ровно тот кадр, ради которого проба написана. Повторится — смотреть ключ кэша
`useOperationsAnalytics`. Тогда же таблице добавлен `aria-sort` (порядок
сообщался только стрелкой с `aria-hidden`), и проба сортировки пинит его, а не
выводит такт из первой строки. См. [[feedback_order_assert_needs_three_items]].

Приём, которым закрывался каждый экран: перенести то, чему есть ЖИВОЙ
источник, а остальное назвать вслух (строкой на экране + строкой в
`docs/api-gaps.md`), а не рисовать пустыми ячейками. См.
[[reference_vaps_docs_ledger_location]], [[project_ops_backend_plan]].

**Аналитика службы: источник был у СОСЕДА.** Прототип этого экрана — про
личный состав, а живая `ops/service-analytics` — про дежурства и сама
объявляет кадровые показатели недоступными. Числа нашлись у расхода
(`/api/operations/strength-report/` + `/period/` для ряда по датам) и у
светофора (`/traffic-light/tree/`, экран стал первым его потребителем во
фронте). Вывод для следующих экранов: «у этой ручки источника нет» ≠ «источника
нет» — смотреть соседние домены хоста, а не только ручку раздела.
Ловушки, всплывшие здесь: счёт по светофору только по ЛИСТЬЯМ (родитель несёт
худший цвет поддерева); у светофора ПЯТЬ цветов (NEUTRAL/UNKNOWN не зелёные);
пресеты аналитики уходят в будущее, а расход за будущее сервер отклоняет 400.
См. [[feedback_vaps_fixture_must_separate_fields]].

**Сотрудники и штат: поля были В МОДЕЛИ, но не в ответе.** `_directorate_get`
собирал сотрудника литеральным словарём из четырёх ключей, хотя у `Employee`
есть `rank`, `iin`, `hire_date`, `birth_date`, `personnel_number`. Отсюда
пустая подстрока под именем (поле `manager` без источника) и снятая колонка
«Дата найма». Вывод к урокам «Аналитики ОМ»: прежде чем писать «источника
нет», смотреть не только соседние РУЧКИ, но и саму МОДЕЛЬ — ответ ручки уже
и модели. ИИН маскирует сервер (`employees/masking.py`), хвостом.
🔴 Рейтинг в кадровой таблице НЕДОСТИЖИМ в принципе: `OpsRatedParticipant`

**Сбор сил: источник лежал В МОДЕЛИ целиком.** У `OpsSecurityEvent` уже были
и стадия `FORCES`, и `force_requests` (`{id, group, requestedCount,
allocatedCount, status}`), и ручка правки выделения — всё это читала карточка
ОМ. Не хватало РАЗРЕЗА ПО РЕЕСТРУ (`?stage=FORCES`), его и сделал новый
маршрут. Не дубль «Расстановки»: в прототипе это тоже отдельный маршрут, вне
`lifecycleViews`.
🔴 `force_need` и сумма `requestedCount` пишутся из ОДНИХ строк расчёта в одном
месте — разойтись не могут. Значит две плитки печатали одно число, а
прототипное предупреждение «квоты не сходятся с потребностью» — недостижимая
ветка (оно осмысленно там, где квоты ставит человек; такого механизма в бэке
нет). Деления «штаб / брокер» нет по той же причине, что и разреза по
департаментам в аналитике: `group` — свободная строка, не подразделение.
Стадия FORCES ТРАНЗИТНАЯ: на стенде на ней не стояло ни одного из 77 ОМ →
фикстуру заводить самим, см. [[feedback_stage_fixture_accumulates_without_delete]].

**Подразделения: узел дерева — ПОДРАЗДЕЛЕНИЕ, а не штатная единица.** Дерево
строилось по `staff_units.parent_id`, но подписывалось `division.name` — отдел
из пяти ставок рисовался пятью одинаково названными карточками. Склейка по
`division.id` чуть не съела ВАКАНСИИ (отбор `emp.employee`): пока узлом была
одна ставка, вакансия была «руководителем» карточки и была видна. Ручка
`/api/staff_unit/statistics/` отдаёт ещё три массива разреза — страница их
выбрасывала. См. [[feedback_dead_control_needs_owner_component]].

**Профиль: у бэка не было ответа «который сотрудник я».** `api/employees/`
закомментирован, связь `User → Employee` наружу не отдавалась — понадобилась
своя ручка `/api/operations/my-employee/` (самообслуживание по образцу
`my-permissions`). Отсутствие привязки отвечает **200 с причиной, а не 404**:
поле заполняется вручную, сид его не делает. Найдено по дороге:
`/api/statuses/statuses/?employee=N` МОЛЧА игнорирует фильтр (отдаёт всех) —
для своего экрана брать `/api/operations/statuses/?employee_id=`; фича
`features/edit-profile` бьёт в несуществующие `/api/user/profile|change-password/`.
Данные стенда: `erda` привязана к сотруднику 9 (было связано 1 из 3 учёток).
