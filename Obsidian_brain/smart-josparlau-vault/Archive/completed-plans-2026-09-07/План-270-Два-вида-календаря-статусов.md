# План №270 — два вида календаря в модуле «Статусы сотрудников»

Задача заказчика (Plane №270, «Модуль Статусы сотрудников.»). Что показали эталоны — записано при разборе очереди 28.08.2026 ([[Бэклог-Smart-Josparlau]], раздел «Что показали картинки»):

> два вида взамен нынешнего «Календаря статусов»: (1) месячная сетка с точками по дням и панелью занятости за выбранный день (на дежурстве / задействованы в ОМ / отсутствуют, поимённо); (2) матрица «сотрудник × день» с буквенными кодами — Д, П, ОМ, О, Б, К и «·» для «в строю».

Взята 29.08.2026 как седьмая в очереди — крупная самостоятельная работа, ни от чего не зависит и ничего не блокирует. Соседняя сессия в это же время ведёт №295/№296/№297 (шаги плана №273): пересечения по файлам нет, стык (`entities/daily-grid`, `hooks/use-ops-status-*`) объявлен и не трогается.

## Что уже есть, а чего нет

| Нужно эталону | Состояние |
|---|---|
| Вкладка «Календарь статусов» на `/statuses` | ЕСТЬ: `widgets/status-calendar` на FullCalendar |
| События по дням месяца | **НЕТ по сути**: виджет раскладывает по дням ТЕКУЩИЕ статусы (`useStaffUnitsPage`, `statusNot: in_service`), а не факты месяца — это прямо записано в его же комментарии |
| «Задействованы в ОМ» | **НЕТ**: кадровый словарь `statuses.EmployeeStatus` кодов участия в ОМ не содержит вовсе |
| «На дежурстве» | ЕСТЬ в обоих пространствах (`on_duty` / `DUTY`) |
| Факты с периодом за месяц по всем сотрудникам | ЕСТЬ в каноне: `operations.OpsEmployeeStatus` — полуинтервал `[date_start, date_end)`, поле `period` (daterange) и GiST-индекс ровно под такие выборки |
| Ручка «месяц × состав» | **НЕТ** — ни в `statuses/api`, ни в `ops/api` |
| Ручка «занятость на дату поимённо» | **НАПОЛОВИНУ**: `statuses/division_headcount` даёт числа на дату по кадровому словарю, поимённого состава и разреза ОМ не даёт |
| Матрица «сотрудник × день» | **НЕТ** |

## Решение об источнике данных

Календарь читает **канонический** `OpsEmployeeStatus`, а не кадровый `statuses.EmployeeStatus`.

Причина: эталон требует различать «на дежурстве», «задействован в ОМ» и «отсутствует». Участие в ОМ существует только в каноне (`EVENT_ASSIGNMENT`, `EVENT_ASSIGNMENT_GROUP` — заведены сидом `seed_status_types`), и с №274 Ш-3 именно статус участия ведёт цепочку сбора сил. Кадровый словарь такого кода не имеет и иметь не должен — мост `LEGACY_CODE_BY_CODE` покрывает 13 старых значений, участия среди них нет. Календарь на кадровом словаре не смог бы показать вторую из трёх групп панели занятости, то есть не выполнил бы задачу.

Подписи и буквы берутся из справочника `ops_status_types` (имя, приоритет), а не из своей таблицы в компоненте: своя таблица уже расходилась с палитрой в нынешнем виджете.

## Отвергнутые варианты

- **Достроить нынешний виджет до месяца, оставив источником `useStaffUnitsPage`.** Ручка отдаёт текущий статус, истории у неё нет; за месяц пришлось бы тянуть весь состав и домысливать дни. Ровно этим путём экран раньше набирал 2,7 МБ на пяти тысячах сотрудников (№236, №231).
- **Считать месяц на клиенте из списка статусов.** Матрица «сотрудник × день» на 5000 × 31 — это 155 000 ячеек; раскладку по дням делает сервер, где для этого есть `period` и индекс.
- **Одна ручка на оба вида.** Виды спрашивают разное: сетке нужны СЧЁТЧИКИ по дням и состав ОДНОГО выбранного дня, матрице — коды по каждому сотруднику за все дни. Общая ручка отдавала бы каждому виду лишнее.
- **Оставить FullCalendar под матрицу.** Матрица — таблица, а не календарь; у FullCalendar нет вида «строка на сотрудника» без платного `resource-timeline`. Месячная сетка при этом может остаться на нём — решается в Ш-3 после `/ui-ux-pro-max`.
- **Новая ручка внутри `ops/api/views.py`.** Файл сейчас правит соседняя сессия (№295). Вид кладётся отдельным модулем — это и без соседа честнее: 3475 строк в одном файле.

## Буквенные коды (эталон → канон)

| Буква | Канонический код | Подпись справочника |
|---|---|---|
| Д | `DUTY` (и `GEV`) | На дежурстве / ГЭВ |
| П | `REST_AFTER_DUTY` | После дежурства |
| ОМ | `EVENT_ASSIGNMENT`, `EVENT_ASSIGNMENT_GROUP` | Привлечён на мероприятие |
| О | `VACATION`, `LEAVE_BY_REPORT` | В отпуске / по рапорту |
| Б | `SICK_LEAVE` | На больничном |
| К | `COMMAND` | В командировке |
| · | `IN_SERVICE` или строки нет | В строю |

Коды, эталоном не названные (`STUDY`, `COMPETITION`, `CONFERENCE`, `OTHER_ABSENCE`, `DETACHED`, `ATTACHED`, `BEFORE_DUTY`, `PENDING_CLARIFICATION`), получают свою букву по первой букве подписи и обязаны быть в легенде: молча схлопнуть их в «·» значило бы объявить человека в строю.

## Шаги

- Ш-1: ручка месяца — коды по каждому сотруднику за все дни выбранного месяца
  - `GET /api/ops/status-calendar/month/?month=YYYY-MM[&division_id=]`; область по умолчанию — подразделение пользователя, как у остальных вкладок экрана. Ответ: сотрудник (id, ФИО, должность, подразделение) + массив дней с каноническим кодом. Один запрос по `period && [первое, последнее)`, без запроса на день. Отменённые строки не существуют. Тесты: раскладка полуинтервала по дням (день `date_end` НЕ занят), перекрытие двух фактов решается приоритетом справочника, отменённая строка не видна; красная проба — на подмене `[)` на `[]`.
- Ш-2: ручка занятости на дату — три группы поимённо
  - `GET /api/ops/status-calendar/day/?date=YYYY-MM-DD[&division_id=]`: «на дежурстве», «задействованы в ОМ», «отсутствуют» — списками ФИО с подписью статуса, плюс счётчики и «в строю» числом. Разрез ОМ берётся из участий, а не из имени типа. Тесты: человек с двумя фактами попадает в одну группу; область чужого подразделения закрыта.
- Ш-3: вид «Месяц» — сетка с точками по дням и переключатель видов
  - Вкладка «Календарь статусов» получает переключатель «Месяц / Матрица». В ячейке дня — точки по типам с числом; клик по дню выбирает день для панели Ш-4. Перед кодом — `/ui-ux-pro-max`; снимок экрана обязателен.
- Ш-4: панель занятости за выбранный день
  - Рядом с сеткой: три группы поимённо + «в строю» числом, состояния загрузки/ошибки/пустоты. Читает ручку Ш-2.
- Ш-5: вид «Матрица» — сотрудник × день с буквенными кодами
  - Строка на сотрудника, колонка на день, буква по таблице выше, «·» для «в строю»; липкая первая колонка, горизонтальный скролл внутри своего контейнера, легенда под таблицей. Читает ручку Ш-1.
- Ш-6: снятие старого вида и уборка
  - Нынешний `StatusCalendar` на `useStaffUnitsPage` уходит после переезда обоих видов; грепом найти всех читателей виджета (страница, пробы, обход портала) и решить по каждому. Гейт целиком: `pytest` по `ops`+`operations`, `npm run gate:front`, целевые пробы обоих видов.
