# Story 1.4: Поле актора в базовых моделях

Status: done

## Story

As a аудитор,
I want created_by (user_id строкой) в базовых абстрактных моделях,
so that аудит не потребует миграции всех таблиц задним числом.

## Acceptance Criteria

1. **Given** новая модель на UUIDTimeStampedModel/TimeStampedModel, **When** запись создаётся через сервис, **Then** created_by заполнен actor_id.
2. **And** существующие таблицы получают nullable-колонку одной миграцией на app.

### Что НЕ трогать (Out of Scope)

- **`updated_by` / was-стало** — это AuditLog (E4, ARCH-SEC-032); базовые модели несут только created_by по AC.
- **Backfill исторических строк** — created_by=NULL у старых записей = честное «неизвестно»; никаких data migrations.
- **Enforcement «каждый сервис заполняет created_by»** — статически невыразимо AST-чеком (заполнение — рантайм-семантика); системная гарантия придёт audit-coverage тестом E4 (AR-9). Не изобретать линт здесь.
- **Рефактор create-путей ModelViewSet на сервисы** (Employee/Division/… POST через serializer) — pre-existing нарушение Layer Contract, чинится своими сторями E2; расширять скоуп нельзя.
- **`timezone.now()` в `apps/core/api/views.py:129,141,154`** — вне скоупа ещё с 1.3, не трогать (даже в строках, которые правишь в Task 5 — меняешь только аргумент created_by).
- **Рефактор `models.py` → пакет `models/`** — по-прежнему отдельная стори («при первом касании» осознанно отложено в 1.2 и 1.3, не пересматривается).
- **`X-User-Permissions` доверяется клиенту** (`apps/core/api/views.py:26`) — известная deferred-дыра 1.2, закрывается при переводе маскирования на PermissionService (E2/2.9). Здесь закрываем только сестринскую дыру created_by (Task 5).
- **`Backend/PersonnelStatus/` — ДОНОР, не трогать.**
- Сериализаторы ответов: created_by в API-ответы НЕ добавлять — поле служебное; выдача наружу — явным решением спеки ресурса (Format Patterns: «вложенные объекты/поля — только явным решением спеки»).

### Архитектурные нормы, которые исполняет стори

- **ARCH-007 / BR-ACCOUNT-002:** user_id — строка внешнего auth; created_by хранит её же. Существующие образцы: `UserRole.user_id`, `Vacancy.created_by`, `TemporaryDutyPermission.created_by` — все CharField(100). [Source: architecture.md#Technical Constraints & Dependencies]
- **Layer Contract:** «Сервисы: типизированные kwargs (`division_id: UUID, business_date: date, actor: str`)»; «Актор: authentication class (core) ставит `request.actor_id: str`». Параметр сервиса называется `actor`, колонка — `created_by`. [Source: architecture.md#Layer Contract (кто кого вызывает)]
- **ARCH-SEC-030 (дух):** идентичность — только из auth-контракта; `created_by` из тела запроса = клиент диктует, кем он был (Task 5 закрывает). [Source: architecture.md#Authentication & Security]
- **ARCH-002/003 (cross-context):** никаких FK на core_users — created_by плоская строка, как все user_id-поля проекта. [Source: architecture.md#Technical Constraints & Dependencies]
- **Naming/Django-механика:** ручные имена миграций `NNNN_<entity>[_<verb>]`; «модель + её схемная миграция = одна стори»; `makemigrations --check` уже в gate. [Source: architecture.md#Naming Patterns, #Architectural Boundaries]
- `make gate` зелёный до закрытия стори. [Source: architecture.md#Enforcement Guidelines]

### Решения, принятые при создании стори (дефолты; менять только осознанно)

1. **`CharField(max_length=100, null=True, blank=True)`, НЕ FK на core_users:** все идентичности проекта — плоские строки (ARCH-007); FK привязал бы каждую таблицу к core_users и сломал cross-context правило (operations не ссылается на core FK'ями). `blank=True` — чтобы `full_clean()` в сервисах не требовал поле там, где актор неприменим (импорт, system).
2. **Vacancy: локальное поле снять, не оставлять override:** определения побайтно идентичны — два источника одного поля это дрейф-риск; наследование делает Vacancy неотличимой от остальных. Автодетектор обязан промолчать (state-сравнение идёт по деконструкции поля, не по классу-владельцу) — проверка состава миграции в Task 3 это сторожит.
3. **TemporaryDutyPermission: override остаётся:** NOT NULL — более сильная гарантия, ослаблять ради единообразия нельзя. Django официально разрешает переопределение полей абстрактной базы.
4. **`create_defaults` (Django 5.0+), не `defaults`:** created_by — это «кто создал ЗАПИСЬ», append-once семантика (как cancelled_at в 1.3); положить в `defaults` = реактивация роли молча переписывает создателя — ложь в данных аудита.
5. **`actor` — обязательный keyword в сервисах записи:** опциональный параметр = конвенция, которую забывают; обязательный = каждый будущий вызов (1.5+, импорт 1.6) обязан явно решить, кто действует. Правок вызывающих ровно три тестовых файла + одна view-строка — дёшево сейчас.
6. **Справочники и Watermark без created_by:** plain models не на базах — осознанно: их пишут seed-команды и Admin (актор аудита справочников придёт консолидированно с E4), а Watermark — служебный маркер процесса, не доменная запись. Не расширять базу на них «для полноты».
7. **Имя миграции `0015_created_by` / `0005_created_by`:** паттерн `NNNN_<entity>[_<verb>]` читаем как «NNNN_<что добавили>»; прецедент полевых миграций в проекте появится этой сторией — имя по полю, не по списку моделей.
