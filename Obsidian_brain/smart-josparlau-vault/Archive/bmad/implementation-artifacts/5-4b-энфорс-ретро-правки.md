## Story

As a **система**,
I want **чтобы ретро-правка статуса на дату, накрытую действующей сдачей дня, АТОМАРНО триггерила amendment (новую версию v2+ через сервис 5.4a) для каждой накрытой сдачи**,
so that **не возникает «двух правд» (live молча расходится со сданным снапшотом, ARCH-DATA-021 L288) — правка и поправка-сдачи неотделимы, расход остаётся восстановимым**.

## Acceptance Criteria

1. **Given** ретро-правка статуса (`resolve_pending_clarification`, хук 3.9), затрагивающая дни, накрытые действующей `DailySubmission`, **When** правка коммитится, **Then** для КАЖДОЙ накрытой `(division, business_date)` создаётся amendment (`amend_day` 5.4a, `event=AMENDED`) В ТОЙ ЖЕ транзакции — правка и amendment коммитятся вместе (rollback правки откатывает amendments). Amendment несёт производные `reason`/`sanction` (из ретро-правки) + `triggered_by_status_id` = id разрешающего статуса.
2. **And** инверсный seam: `statuses/amendment_hook.py` — РЕЕСТР+ДИСПЕТЧЕР (`register_amendment_handler(fn)` + `mark_days_for_amendment(...)` зовёт зарегистрированный обработчик; **no-op, если ничего не зарегистрировано** — прежний контракт сохраняется); `submissions` регистрирует обработчик в `AppConfig.ready()`. Граница `statuses ↛ submissions` НЕ нарушена (`test_isolation` зелёный; `statuses` НЕ импортирует `submissions`).
3. **And** корректный union над набором интервалов вместо наивного `min/max` bounding-box: затронутые дни = объединение СТАРОГО интервала «уточняется» и НОВОГО разрешающего интервала, полуоткрытые `[date_start, date_end)` (день `date_end` НЕ включён); разрозненные интервалы НЕ триггерят amendments для дней в разрыве. Закрывает deferred VAPS_7.8.2 §82.2 + `deferred-work.md` L315.
4. **And** детекция накрытости: для каждого затронутого дня D — division сотрудника на D (`HistoricalEmployeeSelector`, зеркало `roster_on`) → `DailySubmissionSelector.current_for(division, D)`; amendment создаётся ТОЛЬКО для дней с действующей сдачей; дни без сдачи игнорируются; дедуп по `(division, business_date)`.
5. **And** анти-gold-plating: 5.4b НЕ строит сервис amendment (это 5.4a — переиспользуется), НЕ эмитит аудит `DAILY_SUBMISSION_AMENDED` (эмиссия — 5.9; auto-amendment audit-silent до неё, как `amend_day`/`submit_day`), НЕ гейтит права (5.8), НЕ реализует эскалацию санкции (forward-seam E6), НЕ подключает ПРОЧИЕ пути ретро-правки (update_status/cancel/dismissal — будущее; 5.4b энфорсит существующий call-site хука 3.9 `resolve_pending_clarification`). НЕ светофор (5.5).

### Архитектурные правила, которые 5.4b ОБЯЗАНА соблюсти

- **Граница `statuses ← submissions ← reports` (architecture.md:587):** `submissions` зависит от `statuses` (можно импортировать), ОБРАТНОЕ запрещено. Поэтому: реестр-слот живёт в `statuses` (чистый Python), а РЕАЛИЗАЦИЯ (детекция+amend_day) — в `submissions`, регистрируется в `ready()`. `statuses` НИКОГДА не импортирует `submissions`. Страж: `apps/operations/tests/test_isolation.py` (AST-скан). **Это центральный инвариант 5.4b — не нарушить.**
- **ARCH-DATA-021 (architecture.md:286–295, 749):** amendment = новая версия (вытеснение), снапшот прежней неизменен; auto-amendment делает `amend_day` (5.4a уже корректен). Хук лишь решает КОГДА и для каких `(division, day)`.
- **Атомарность ретро-правки:** хук в `@transaction.atomic` → amendments в той же txn (AC1). Если `amend_day` бросит — вся ретро-правка откатывается (правка не «проскочит» без amendment).
- **operations ↛ core.models (ARCH-004):** обработчик ходит в core только через `apps.core.selectors` (`HistoricalEmployeeSelector`). Страж `test_isolation`.
- **Полуоткрытые интервалы [start,end) (ARCH-DATA-023):** день `end` НЕ входит в затронутые. Согласовать с тем, как статусы/снапшот трактуют даты.
- **Idempotency / гонка:** `amend_day` сам держит version=max+1 + unique-констрейнты (5.4a). Обработчик зовёт его по разу на накрытый `(division, day)`.

### Инверсный seam — паттерн (registry/callback)

```
statuses/amendment_hook.py  (чистый Python, НЕ импортит submissions):
    _handler = None
    def register_amendment_handler(fn): global _handler; _handler = fn
    def mark_days_for_amendment(employee_id, intervals, *, actor, reason, triggered_by_status_id=None):
        if _handler is None: return None          # no-op контракт сохранён
        return _handler(employee_id, intervals, actor=actor, reason=reason,

submissions/amendment_enforcement.py  (импортит statuses — РАЗРЕШЕНО):
    def enforce_amendment_on_retro_edit(employee_id, intervals, *, actor, reason, triggered_by_status_id=None):

submissions/apps.py  AppConfig.ready():
```

### Решения, принятые при создании стори (дефолты — менять осознанно)

1. **AUTO-AMEND (атомарно), не BLOCK** — решено архитектурой (L356/623/295). Правка и amendments в одной txn.
2. **Инверсный seam = registry-callback** (один слот, регистрация в `ready()`), не Django-signal (проще, синхронно, в txn). statuses держит слот, submissions — реализацию.
3. **Сигнатура хука меняется** на `(employee_id, intervals, *, actor, reason, triggered_by_status_id)` — `amend_day` требует actor/reason/sanction. intervals — список, не bounding-box (закрывает interval-union defer).
4. **`sanction` auto-amendment = `reason` ретро-правки** (в `resolve_pending_clarification` `reason` И есть санкция, см. её docstring/`cancelled_reason`); `reason` amendment = производный маркер. См. Открытый вопрос Q1.
5. **`triggered_by_status_id` = `resolved.id`** (id разрешающего статуса — наиболее естественная «ссылка на ретро-правку»).
6. **Только call-site 3.9** в скоупе; прочие пути — будущее (Q2).

### Подводные камни для dev-агента

- **НЕ импортировать `submissions` из `statuses`** — это сорвёт `test_isolation` и нарушит ARCH-587. Только registry-callback. Проверять страж после правок.
- **Хук — внутри txn ретро-правки.** Не открывать лишних транзакций; `amend_day` атомарен сам. Исключение в обработчике ДОЛЖНО откатывать всю ретро-правку (AC1 «правка без amendment невозможна»).
- **Полуоткрытость [start,end):** день `end` НЕ затронут. Наивная итерация `range(start, end+1)` — БАГ; правильно `start … end-1`.
- **employee→division по дате:** division мог меняться (секондмент). Брать division НА КАЖДЫЙ затронутый день (`division_at`), не один раз. Зеркалить инстант, как снапшот-билдер (5.3a) мапит business_date в историю — иначе детекция разойдётся со снапшотом.
- **Дедуп `(division, business_date)`** перед `amend_day` — иначе двойной amendment одного дня (второй сорвёт unique-version или создаст лишнюю версию).
- **Регистрация в `ready()`, импорт внутри** — иначе apps.py на уровне модуля потянет модели до готовности реестра приложений.
- **Обновить мок-тест** `test_resolve_marks_days_for_amendment` — старая сигнатура `(employee_id, date_start, date_end)` сломается.
