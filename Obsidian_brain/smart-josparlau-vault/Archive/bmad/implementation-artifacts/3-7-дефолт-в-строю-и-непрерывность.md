## Story

As a **система (и разработчик, доверяющий расходу)**,
I want **формально зафиксировать тестами, что derived-правило «дата без интервала = В строю» и тотальность (ровно один derived-статус на (сотрудник, дата)) держатся ИМЕННО для AC-формулировок 3.7 — FR-9-переход «к следующему PLANNED, иначе В строю» и авто-возврат БЕЗ единой записи в БД**,
so that **FR-9 (авто-возврат после спецстатуса) доказан by construction и AC-traceable, а не подразумевается; будущие правки движка ломают именно эти инварианты с явным красным тестом**.

## Acceptance Criteria

Источник: [epics.md#L531-L538] (Story 3.7), FR-9 [epics.md#L40] «Авто-возврат после спецстатуса: к следующему PLANNED, иначе «В строю»», ARCH-DATA-022 (derived-first; lifecycle-факты stored append-once; НЕ мутируемый enum, перещёлкиваемый задачами — паттерн донора).

1. **AC-1 (авто-возврат в «В строю» без записи в БД — DB-level).** Given сотрудник, чей единственный спецстатус закончился ВЧЕРА (`date_end == today`) и нет PLANNED-статуса, When спрашиваю derived-статус на сегодня через DB-путь (`EmployeeStatusSelector.status_on(employee_id, today)` / `StrengthReportService.compute`), Then результат `IN_SERVICE` («В строю»), И число строк `EmployeeStatus` ДО и ПОСЛЕ запроса одинаково (авто-возврат — чистое derived-чтение, НИ одного мутатора/INSERT; FR-9 by construction).
2. **AC-2 (FR-9 handoff «к следующему PLANNED, иначе В строю» — unit на `resolve_status`).** Given статус A `[.., D)` и следующий статус B `[D, ..)` (смежные, B был PLANNED до D), When резолвлю на D, Then победитель = код B (НЕ IN_SERVICE — эстафета без записи). Given вместо смежности ЗАЗОР (A `[.., D)`, B `[D+2, ..)`), When резолвлю на D и D+1, Then `IN_SERVICE` оба дня (возврат «В строю» до следующего PLANNED), а на `D+2` — код B.
3. **AC-3 (тотальность на DB-пути — pin).** Given сотрудник с НЕсколькими пересекающимися live-статусами в БД, When спрашиваю `status_on` на ряде дат, Then ровно один код на каждую дату (никогда не пусто, никогда не двусмысленно), И отменённая (`cancelled_at`) строка НЕ участвует (запись = «нет факта»).
4. **AC-4 (нулевой регресс ядра, анти-gold-plating).** Существующая property-сюита 1.7 (`test_strength_report_properties.py`) и сервис-тесты — зелёные без правок. Код движка (`strength_report.py`, `selectors.py`, `employee_status.py`) НЕ изменяется (3.7 — тесты + документация). `make gate` зелёный.

### Архитектурные правила (developer guardrails)

- **НЕ трогать движок.** `strength_report.py`, `selectors.py`, `employee_status.py` — read-only для 3.7. Любая правка кода = выход за скоуп (это verification-стори). Если тест требует правки движка — значит нашёлся РЕАЛЬНЫЙ баг: HALT, эскалировать Bratan (не чинить молча).
- **`IN_SERVICE` == «В строю».** Канонический код дефолта. НЕ вводить новый код/строку/enum-значение, НЕ хранить «В строю» как строку статуса (весь смысл — оно DERIVED, не stored; ARCH-DATA-022 запрещает мутируемый enum-state).
- **business_date — явный аргумент.** Тесты передают дату явно (как 1.7), НЕ читают Clock. `D = date(2026, 6, 4)` (как в существующих тестах) или свой константный.
- **Точечный `status_on` НЕ в цикле по сотрудникам** (анти-донор COUNT-in-loop). В тесте AC-3 цикл по ДАТАМ одного сотрудника — допустимо (это тест, не прод-агрегация); прод-путь массовой агрегации — `overlapping_on`+`derive_report`.
- **Коды для фикстур — из `STATUS_TYPE_PRIORITIES`** (`strength_report.py:17-34`): SICK_LEAVE(10) < VACATION(20) < STUDY(32) < IN_SERVICE(999). Невалидный код → `resolve_status` raise ValueError (STOP-семантика, 1.7) — в тестах использовать только валидные.
