## Story

As a **система (учётный слой)**,
I want **чистый билдер, который для (`division_id`, `business_date`) собирает SELF-CONTAINED иммутабельный срез `{schema_version, roster:[{employee_id, full_name, rank}], rows:[{employee_id, status_type_code, status_id, date_start, date_end, source}]}` — денормализованный списочный состав (denominator) + действующие интервалы-факты статусов**,
so that **расход `derive(снапшот, дата)` воспроизводим байт-в-байт без повторного обращения к live-данным (ARCH-DATA-021; фундамент атомарной сдачи 5.3b и property-иммутабельности 5.10), а заявление-на-момент-T хранит и людей, и факты как было**.

## Acceptance Criteria

### Форма и состав среза (ядро)

1. **Self-contained форма.** **Given** `(division_id, business_date)`, **When** вызываю `build_division_snapshot`, **Then** возвращается dict `{"schema_version": 1, "roster": [...], "rows": [...]}` (JSON-сериализуемый: uuid→str, date→"YYYY-MM-DD"). [Source: epics.md 5.3a; architecture.md ARCH-DATA-021]
2. **roster = списочный состав на дату (denominator).** **Given** срез, **Then** `roster` — по строке на КАЖДОГО сотрудника списочного состава подразделения на `business_date` (own-level, `HistoricalEmployeeSelector.roster_on`), `{employee_id (str uuid), full_name, rank}`; ФИО/звание ДЕНОРМАЛИЗОВАНЫ (как было на момент T). Сотрудник без статусов всё равно в `roster` (derive → «В строю»). [Source: epics.md 2.4/5.3a; core/selectors.py roster_on; ARCH-DATA-021]
3. **rows = действующие интервалы-факты (с status_id + source).** **Given** срез, **Then** `rows` — действующие на `business_date` интервалы-факты (полуоткрытые `[date_start,date_end)`, `cancelled_at IS NULL`): `{employee_id, status_type_code, status_id (int pk), date_start, date_end, source}`. У сотрудника 0/1/несколько фактов (все действующие, не только derive-победитель). [Source: statuses/selectors.py; employee_status.py; ARCH-DATA-022/023]
4. **Пустое подразделение.** **Given** подразделение без сотрудников на дату, **Then** `roster=[]`, `rows=[]` (валидный срез; расход сойдётся 0=0+0 в 5.3b/derive). [Source: epics.md 5.3a/5.3b empty-division]
5. **Самодостаточность (иммутабельность).** **Given** срез, **Then** `derive(snapshot, business_date)` вычисляет расход ТОЛЬКО из `roster`+`rows` (не обращается к `roster_on`/EmployeeStatus повторно) — после сдачи мутации статусов/перевод не меняют исторический расход (фундамент 5.10). [Source: architecture.md ARCH-DATA-021; epics.md 5.10]

### Селектор-пробел и гейт

6. **Новый selector-метод (не ломая overlapping_on).** **Given** нужны `status_id`+`source` (которых нет в `overlapping_on`), **Then** добавлен `EmployeeStatusSelector.snapshot_facts_on(on_date, employee_ids)` → `.values("id","employee_id","status_type_code","date_start","date_end","source")` (тот же предикат `cancelled_at__isnull=True, period__contains`); существующий `overlapping_on` НЕ изменён (на нём строится strength_report). [Source: statuses/selectors.py; agent-1 critical gap]
7. **Гейт + анти-gold-plating.** **Given** билдер в `apps/operations/submissions/services/`, **Then** `make gate` зелёный, `ruff` чист, `makemigrations --check` пуст (миграций НЕТ — read-only код). **And** 5.3a НЕ пишет рядов DailySubmission; НЕ делает окно/дубль/event/late/atomic/amendment/API/аудит (5.3b+). [Source: реш. границы]

### 🔑 Решения по реализации (ДЕФОЛТЫ — подтвердить/переопределить; вопросы в конце)

1. **Схема `{schema_version, roster, rows}` — self-contained [ДЕФОЛТ, РЕКОМЕНД.].** Денорм. ФИО/звание — на `roster` (по человеку), `rows` = чистые интервалы-факты (`employee_id`+поля статуса+`status_id`+`source`). *Почему:* derive нужен denominator (Список) — сотрудник без статусов обязан быть в снапшоте, иначе пост-фактум он «исчезнет» из исторического расхода. Это УТОЧНЯЕТ контракт 5.2 (там ФИО/rank были на rows; рядов 5.2 не писала — 5.3a как первый писатель финализирует форму). *Альтернатива:* rows-only + повторный roster_on на чтении — отклонено (ломает иммутабельность 5.10).
2. **roster scope = own-level `{division_id}` [ДЕФОЛТ].** Снапшот одного подразделения. Роллап вверх по дереву — отдельная DailySubmission родителя (фрактальность ARCH-DATA-021, стори 5.11), НЕ subtree-cascade здесь. *Альтернатива:* `CoreDivisionTreeSelector.subtree_ids` — отклонено (это 5.11). *Под-вопрос для владельца расхода (пилот).*
3. **`rank` = резолв `Rank.name` (fallback `rank_code`) [ДЕФОЛТ].** `Employee` хранит только `rank_code` (flat string, не FK; `Rank` — справочник code→name). Для печати «как было» снапшот несёт человекочитаемое звание, не нуждаясь в live-справочнике. *Альтернатива:* хранить `rank_code` — проще, но печать прошлых дат потребует live `Rank`. *Вопрос в конце.*
4. **rows = ВСЕ действующие факты (0/1/N на человека) [ДЕФОЛТ].** Снапшот хранит полноту интервалов-фактов; derive-победитель (`resolve_status`) выбирается на ЧТЕНИИ, не на сдаче (derived-first). *Альтернатива:* хранить только победителя — отклонено (теряет факты для drift 5.5 и аудита).
5. **Новый `snapshot_facts_on`, overlapping_on НЕ трогаем [ДЕФОЛТ].** `overlapping_on` отдаёт 4 поля (без `id`/`source`) и на нём строится `strength_report.compute`; менять его return — регрессия. Новый метод-сосед даёт 6 полей. *Альтернатива:* расширить overlapping_on extra-полями — отклонено (молчаливое изменение контракта общего селектора).
6. **Билдер — read-only функция в `submissions/services/snapshot.py` [ДЕФОЛТ].** `build_division_snapshot(division_id, business_date) -> dict`; рядов не пишет, транзакцию не открывает (её даёт 5.3b). Зеркало read-assembly `StrengthReportService.compute` (statuses/services). schema_version=1.
7. **snapshot НЕ хранит штат/вакансии [ДЕФОЛТ, граница].** Self-containment 5.3a — про denominator (roster) + статусы. Штат/вакансии (Штат=Список+Вакансии) — отдельная ось; 5.10 требует иммутабельность ПО СТАТУСАМ. Если позже понадобится байт-иммутабельность вакансий — отдельное решение (не здесь).
