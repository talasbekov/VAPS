# Story 3.4: Конфликт-детектор на матрице-данных

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As **система (статусный движок)**,
I want **декларативную матрицу пар типов статусов (hard / soft / совместимо) и чистый детектор пересечений интервалов, который классифицирует каждое пересечение по матрице и состоянию (PLANNED → предупреждение)**,
so that **правила конфликтов — это данные, а не разбросанные if-ы; hard-пересечение даёт 422, soft — 409+override, а будущий PLANNED — предупреждение; и детектор/БД-констрейнт никогда не расходятся**.

## Acceptance Criteria

Источник: [epics.md#L504-L511] (Story 3.4), FR-10 [epics.md#L41], FR-11 [epics.md#L42], AR-8 [epics.md#L110], ARCH-DATA-020 [architecture.md#L280-L284].

1. **AC-1 (hard → 422).** Given новый статус пересекает существующий hard-статус (тип ∈ hard-набора), When создаю статус, Then `DomainError(422)` `OVERLAPPING_HARD_STATUS` — классификация идёт через матрицу (не через локальный tuple-чек). Поведение 3.3 сохранено.
2. **AC-2 (soft → 409 overridable).** Given новый статус пересекает существующий soft-статус (оба не-hard), и существующий статус **ACTIVE** на бизнес-дату, When создаю, Then `DomainError(409)` `STATUS_OVERLAP_WARNING`, `overridable=True`, `detail.conflicts[]` несёт пересечения. (Без эскейпа override — он в 3.5.)
3. **AC-3 (PLANNED → предупреждение).** Given пересечение с **soft**-статусом в состоянии **PLANNED** (date_start > бизнес-даты), Then детектор классифицирует это как **WARNING** (не блокирует) — создание проходит, предупреждение возвращается в `ConflictReport.warnings`. (HARD-пересечение остаётся 422 даже если другой PLANNED — консистентно с GiST-констрейнтом, который состояние не смотрит.)
4. **AC-4 (property-тест всей матрицы).** Property-тест (hypothesis) прогоняет **все пары** типов из справочника: классификация **тотальна** (любая пара классифицирована), **симметрична** (`classify(a,b) == classify(b,a)`), и **консистентна с hard-набором** (пара HARD ⟺ хотя бы один тип ∈ `HARD_STATUS_TYPE_CODES`).
5. **AC-5 (матрица = данные).** Правила конфликтов читаются из декларативной структуры (hard-набор + явные COMPATIBLE-исключения), а не из россыпи if-ов. Детектор — **чистый модуль** (без ORM/Django), property-тестируемый без БД (паттерн `core.sorting`).
6. **AC-6 (детектор ≡ констрейнт — разрешение D3).** hard-классификация матрицы и GiST-констрейнт `excl_hard_status_overlap` используют **один источник истины** для hard-набора — детектор и БД не могут разойтись. (Разрешает отложенную находку 3.3 «tuple vs is_hard_block».)
7. **AC-7 (интеграция в create/update).** `create_status` и `update_status` (3.3) вызывают детектор: HARD → 422, SOFT(ACTIVE) → 409; пред-проверка `_assert_no_hard_overlap` обобщена до матрицы. Существующий тест 3.3 `test_soft_overlap_allowed` обновлён → теперь soft-overlap даёт 409 (осознанная смена поведения 3.4; см. Решение №2).
8. **AC-8 (закрытый мир).** Коды `OVERLAPPING_HARD_STATUS` (422) и `STATUS_OVERLAP_WARNING` (409, overridable) уже в `error-codes.yaml` — переиспользуются, новые коды НЕ вводятся. `overridable=True` проставляется на `DomainError` для soft.
9. **AC-9 (out of scope, без протечек).** Override-ЗАПИСЬ (3.5), секондмент-совместимые пары (3.10), assignment-conflict_codes (DOUBLE_ASSIGNMENT/REST_VIOLATION/… — E15/16), bulk (3.8), surfacing warnings в HTTP-ответ/прод-REST, ConflictDialog (8.5) — НЕ строятся. COMPATIBLE-категория поддержана структурно, но не заполняется (зарезервирована под 3.10).

### Архитектурные правила (developer guardrails)

- **Чистота модуля (паттерн `core.sorting`).** `conflict_matrix.py` — БЕЗ `django`/ORM/`apps.*.models` импортов; работает на переданных строках (dict/namedtuple). Это даёт property-тесты без БД и переиспользование детектора адаптерами E14/E16 (AR-8 [epics.md#L110]). [core/sorting.py — образец]
- **hard×hard = backstop в БД (ARCH-DATA-020).** GiST `excl_hard_status_overlap` ловит гонку → IntegrityError → handler → 422 (3.1). Матрица-детектор ловит РАНЬШЕ (чистый 422). Оба используют ОДИН hard-набор (Решение №3). [architecture.md#L280-L284]
- **soft → 409 + override = сервисный слой, не БД.** [architecture.md#L283] «soft-пересечения и FR-10 (PLANNED-предупреждение) — сервисный слой → 409+override / warning».
- **`resolve_status` ≠ `state` ≠ детектор-severity.** `resolve_status` (strength_report) = расход-победитель (priority); `derive_state` = lifecycle (PLANNED/ACTIVE/…); детектор = severity пары. Не смешивать. PLANNED определяется `derive_state(... business_date)` / `date_start > business_date`. [employee_status.py#L26-L39, strength_report.py#L74-L103]
- **Полуоткрытый overlap `[date_start, date_end)`**: предикат `existing.date_start < date_end AND existing.date_end > date_start` (как в 3.3 `_assert_no_hard_overlap`). Смежные `[1,10)+[10,20)` НЕ пересекаются. Зафиксировать в ОДНОМ месте (детектор или выборка), не дублировать. [status_service.py — `_assert_no_hard_overlap`]
- **DomainError.overridable.** Для soft-409 ставить `overridable=True`. ⚠️ §36-конверт (exception_handler) СЕЙЧАС НЕ кладёт `overridable` в тело (проверено в 3.1/3.3) — клиент выводит overridability из HTTP 409 + наличия `conflicts[]`. Surfacing `overridable`/`conflicts[]` в ответ — забота API-стори; в 3.4 это в `detail`. [exception_handler.py, exceptions.py]
- **Коды реестра — переиспользовать, не плодить.** `OVERLAPPING_HARD_STATUS` (422) и `STATUS_OVERLAP_WARNING` (409, overridable, «ручной статус пересекает soft-статус») уже есть — это ровно status×status. `SOFT_CONFLICT_DETECTED` + `conflict_codes` (UNAVAILABLE_STATUS_CONFLICT/DOUBLE_ASSIGNMENT/…) — assignment-домен (E15/16), НЕ для 3.4. [error-codes.yaml#L94-L105, L235-L267]
- **Бизнес-дата** — `Clock.today_local()`, не `date.today()`/`now()`. Тесты — `clock.override`. [clock.py, ARCH-DATA-022/023]
