# Story 3.9: Статус «уточняется»

## Story

As a **оператор**,
I want **тип `PENDING_CLARIFICATION` («уточняется») как первоклассный статус: своя строка в расходе, разрешение ретро-заменой интервала одной санкционированной операцией (закрыть «уточняется» + создать реальный статус), с прогоном разрешающего интервала через конфликт-детектор и хуком пометки затронутых сданных дней к amendment (для E5)**,
so that **неопределённость фиксируется ЧЕСТНО — отдельной строкой расхода, а не враньём «В строю»; когда выясняется правда («госпиталь со вторника»), оператор разрешает её одной операцией, конфликты ловятся до записи, а сданные дни корректно уходят в пересдачу (когда появится E5)**.

1. **AC-1 (своя строка расхода — переворот provisional, AC3 epics).** Given сотрудник со статусом `PENDING_CLARIFICATION` на дату, When строю расход (`StrengthReportService`), Then «уточняется» попадает в СОБСТВЕННУЮ колонку расхода (НЕ в `IN_SERVICE`); три константы `strength_report.py` (`STATUS_TYPE_PRIORITIES`, `REPORT_COLUMN_BY_CODE`, `REPORT_COLUMNS`) и `seed_statuses.py` (`report_column_code`) обновлены когерентно; `resolve_status` больше НЕ кидает `ValueError` на `PENDING_CLARIFICATION`; **формулы сходятся** — `Σ columns == Список` и `Штат == Список + Вакансии` остаются зелёными на строках И итогах ([strength_report.py:176-226]).
2. **AC-2 (ретро-разрешение одной операцией с санкцией, AC1 epics).** Given сотрудник «уточняется» интервал `[A, B)`, When вызываю `resolve_pending_clarification(pending, *, resolved_type_code, date_start, date_end, actor, reason)`, Then АТОМАРНО (одна транзакция) PENDING-строка закрывается И создаётся реальный статус (`source=USER`) на разрешающем интервале; `actor` + `reason` (санкция) обязательны (`_require_actor`; пустой reason → 400 `VALIDATION_ERROR`). Решение №2=B (close+create, реюз примитивов).
3. **AC-3 (конфликт-детектор на разрешающем интервале → 422 ДО записи, AC2 epics).** Given разрешающий интервал пересекает hard-статус сотрудника, When вызываю resolve, Then `_assert_no_conflict(... exclude_pk=pending.pk)` поднимает `OVERLAPPING_HARD_STATUS` (422) ДО любой записи; в БД ничего не создано/не изменено (PENDING-строка цела). soft-пересечение → `STATUS_OVERLAP_WARNING` (409, overridable) по существующему пути 3.4/3.5.
4. **AC-4 (хук amendment для E5 — no-op seam, AC1 epics).** Given разрешение статуса на интервале `[date_start, date_end)`, When операция успешна, Then вызывается seam-функция `mark_days_for_amendment(employee_id, date_start, date_end)` (документированный E5-хук, СЕЙЧАС no-op — `DailySubmission` не существует до E5); тест ассертит вызов с верным интервалом (spy/monkeypatch). **НИКАКОГО импорта `apps.operations.submissions`** (граница слоёв architecture.md#L587, поток statuses→submissions только вниз; E5 читает statuses, не наоборот).
5. **AC-5 (резолв не-PENDING → 422; PENDING остаётся soft).** Given статус НЕ типа `PENDING_CLARIFICATION`, When вызываю `resolve_pending_clarification`, Then `INVALID_LIFECYCLE_TRANSITION` (422) до мутации (guard как 3.6). И `PENDING_CLARIFICATION` НЕ добавляется в `HARD_STATUS_TYPE_CODES` ([conflict_matrix.py:37]) — остаётся soft (provisional подтверждён), миграция GiST НЕ нужна.
6. **AC-6 (закрытый мир + гейт, AC из FR-6/архитектуры).** Новых кодов ошибок НЕТ (реюз `VALIDATION_ERROR`/`OVERLAPPING_HARD_STATUS`/`STATUS_OVERLAP_WARNING`/`INVALID_LIFECYCLE_TRANSITION`/`INVALID_DATE_RANGE`/`INVALID_STATUS_TYPE` — все в реестре); `makemigrations --check` «No changes detected» (3.9 без схемной миграции — seed reseed + derive-only код); `make gate` зелёный; регресс 2.2-seed / strength_report / 3.3–3.8 нулевой (с обновлением 2.2-seed-теста под новую колонку).
7. **AC-7 (out of scope — без протечек).** НЕ строится: **N дней эскалации / авто-экспирация PENDING** (AR-11 СТОП-маркер — открытый вопрос, НЕ выдумывать); **права разрешения** (кто может разрешать — открыто, architecture.md#L276); трёхцветный светофор-селектор (E5 стори 5.5) и его UI/цвет (E10 стори 10.4) — 3.9 даёт только СОБСТВЕННУЮ колонку расхода, цвет — E5/E10; реальный amendment-flow + событие `AMENDED`/санкция-эскалация (E5 стори 5.4 / E4 4.4); граница «накрытой даты» `[start,end)` для amendment (E5, VAPS_7.8.2 §82.2 — deferred-work#L140); прод-REST/сериализатор (E10).
