# Story 2.4: Списочный состав на дату

Status: done

## Story

As a система расчёта расхода,
I want bulk-селектор состава подразделения на дату (`roster_on(business_date, division_ids)` — контракт `division_roster(division_id, date)`) поверх интервалов **уже существующей** модели `EmployeeDivisionHistory` с fallback на текущий `Employee.division`, и глобальную сверку Σ,
so that знаменатель расхода (**Список**) версионирован на дату — приём/перевод/увольнение меняют состав корректно (ARCH-DATA-025), а «дыра принадлежности» (активный сотрудник нигде) ловится как ошибка данных, а не теряется молча.

## Acceptance Criteria

1. **(AC-1) Интервальная принадлежность на дату.** **Given** сотрудник переведён из подразделения A в B 10.06 (через `assign_employee_division` — закрывает интервал A `ends_at=10.06`, открывает интервал B `starts_at=10.06`), **When** запрашиваю состав A и B на 09.06 и на 10.06, **Then** на 09.06 он только в A, на 10.06 — только в B. Граница полуоткрытая `[starts_at, ends_at)` при `T = local_midnight(date)` (ARCH-DATA-023): дата перевода = первый день в новом подразделении.
2. **(AC-2) Приём/увольнение ограничивают принадлежность.** **And** уволенный/архивный сотрудник (`employment_status != WORKING` ИЛИ `is_active = False`) в состав на дату НЕ попадает (паритет с текущим `working_by_division`, Решение №3 ревью 1.7); состав = «член подразделения на дату» ∧ «работает на дату».
3. **(AC-3) Глобальная сверка.** **And** `Σ(состав по ВСЕМ подразделениям, division_ids=None)` == число всех активных (`WORKING ∧ is_active`) сотрудников; расхождение (активный сотрудник, не попавший ни в один состав — реальность донорских данных) фиксируется как **finding/violation в отчёт**, НЕ как исключение и НЕ молча (прецедент `derive_report` Решение №6 стори 1.7; категория `data/skipped_employee` стори 1.8).
4. **(AC-4) Bulk, без wall-clock, переиспользование.** **And** селектор — bulk (один проход, ≤2 запроса: интервалы + fallback; **никаких per-item вызовов `division_at` в цикле** — анти-паттерн донора, architecture.md:61/326/451); `business_date`/`date` — явный аргумент, время только через `local_midnight(...)` (ARCH-DATA-022, `test_isolation` зелёный); переиспользованы существующие `EmployeeDivisionHistory` / `division_at`-предикат / `local_midnight` / `subtree_ids` — новая модель/миграция НЕ создаётся.
5. **(AC-5) Знаменатель расхода версионирован (behavior-preserving на пилоте).** **And** `StrengthReportService.compute` берёт Список из нового версионированного roster вместо снапшотного `working_by_division` (`strength_report.py:267`); на пилотной БД (0 history-строк — импорт 1.6 их не пишет) всё идёт через fallback → числа расхода **идентичны** до/после (нулевая регрессия, convergence-asserts `derive_report` держатся); `make gate` зелёный.

## Dev Notes

### Что это за стори (суть и риск)
**Премис эпика вводит в заблуждение:** модель `EmployeeDivisionHistory`, её миграция (`core/0007_employeedivisionhistory.py`), write-сервис `assign_employee_division` и per-employee селектор `HistoricalEmployeeSelector.division_at` **уже построены и в репо**. 2.4 — это **bulk-селектор `roster_on` (инверсия `division_at`) + глобальная сверка + версионирование знаменателя расхода**, а НЕ новая модель. Риск стори — НЕ в схеме (её нет), а в (1) корректности интервального предиката на границе дня (tz-trap), (2) нагруженном fallback (на пилоте history пуст → всё через fallback, и если его не сделать — сверка теряет всех донорских сотрудников), (3) хрупких convergence-assert в `derive_report` при свопе знаменателя.

### Источник истины: целевая кодовая база — `Backend/VAPS`
Работаем в `Backend/VAPS/`. Донор `Backend/PersonnelStatus/` — эталон parallel-run, не трогаем. [Source: project memory `project_vaps_architecture.md`]

### Что УЖЕ существует — ПЕРЕИСПОЛЬЗОВАТЬ, не изобретать
- **Модель** `EmployeeDivisionHistory` [Source: apps/core/models.py:237-261]: `employee` FK CASCADE (related_name `division_history`), `division` FK PROTECT, `starts_at` (DateTimeField, NOT NULL), `ends_at` (nullable = открытый интервал), `source` (default `MANUAL`), `created_by`; `db_table="core_employee_division_history"`; index `idx_emp_div_hist_lookup` на `(employee, starts_at, ends_at)`; `clean()` бьёт `starts_at >= ends_at`. **Имена полей — `starts_at`/`ends_at`** (НЕ `valid_from`/`valid_to` — то у staffing-слотов). Базовый класс — `UUIDTimeStampedModel` (UUID PK, ARCH-002).
- **Write-сервис** `assign_employee_division(employee, division, *, starts_at, actor, source)` [Source: apps/core/services.py:13-53]: закрывает прошлый открытый интервал, открывает новый, зеркалит `employee.division` (BR-CORE-HISTORY-001/002), `select_for_update`+`@transaction.atomic`. AC-1 «move A→B» write-часть УЖЕ покрыта им — 2.4 делает READ.
- **Per-employee предикат** `HistoricalEmployeeSelector.division_at(employee_id, at)` [Source: apps/core/selectors.py:146-169]: `starts_at__lte=at & (ends_at IS NULL | ends_at > at)`, `order_by("-starts_at").first()`; **BR-CORE-HISTORY-003 fallback** на текущий `division_id` + warning, если history-строк нет. `roster_on` = bulk-инверсия этого предиката — копировать дословно.
- **`local_midnight(business_date)`** [Source: apps/core/selectors.py:16-25]: единственный корректный способ сравнить дату с aware-колонками таймлайна (tz `VAPS_LOCAL_TIMEZONE`, Asia/Qyzylorda UTC+5); наивная/UTC-полночь = off-by-one на границе дня (грабли 1.7).
- **`CoreDivisionTreeSelector.subtree_ids(division_id)`** [Source: apps/core/selectors.py:42-51]: поддерево (self+потомки), один проход, без mptt (ARCH-DATA-024). Уже зовётся в `compute` (`strength_report.py:266`).
- **`CoreEmployeeSelector.working_by_division(division_ids=None)`** [Source: apps/core/selectors.py:86-104]: ТЕКУЩИЙ (неверсионированный) знаменатель `{div_id: [emp_id]}` для `WORKING ∧ is_active`. **Это его заменяет `roster_on`.** Его фильтр (Решение №3, D1 2026-06-15) — baseline сверки AC-3.
- **`CoreStaffingSelector.allocated_slots_on(business_date, division_ids=None)`** [Source: apps/core/selectors.py:109-131]: **эталонная форма bulk-версионированного селектора** для копирования (предикат `valid_from<=T & (valid_to NULL | >T)`, max-`valid_from`, dict-возврат, `division_ids` параметр).

### Прецедент для копирования
`allocated_slots_on` — точный шаблон (bulk, версионированный, dict, max-tiebreak). `roster_on` зеркалит его форму, но по `EmployeeDivisionHistory.starts_at/ends_at` + fallback на `Employee.division`.

### Как расход считает знаменатель сегодня и что меняет 2.4
[Source: apps/operations/statuses/services/strength_report.py:253-287] `StrengthReportService.compute(business_date, division_id=None)`: `subtree_ids` (:266) → **`working_by_division(division_ids)` (:267) — снапшот по `Employee.division`, НЕ версионирован** → `allocated_slots_on` (Штат, уже версионирован) → `overlapping_on` (статусы) → `derive_report(...)`. **Точка интеграции 2.4 — ровно `:267`** (своп на `roster_on`). `derive_report` [Source: strength_report.py:135-240] — чистый stdlib, трактует `employees` как непрозрачный `{div_id:[emp_id]}` → своп drop-in. **РЕГРЕССИОННЫЙ РИСК:** `derive_report` жёстко `assert`-ит сходимость (Σ колонок == Список `:176-180`; Штат == Список+Вакансии `:192-196`; тотали `:217-226`) — если roster и статус-строки разойдутся по скоупу (`employee_ids` :278), assert упадёт. Держать `employee_ids` из НОВОГО roster.

### Архитектурные правила и границы (соблюсти)
- **ARCH-DATA-025** (спина 2.4) [Source: architecture.md:307,753]: принадлежность = интервал `[start,end)` (перевод среди дня — человек ровно в одном снапшоте); Список(D) версионирован; сходимость проверяется ГЛОБАЛЬНО.
- **ARCH-DATA-023** [architecture.md:303,751]: полуоткрытые `[start,end)`; UI «по … включительно».
- **ARCH-DATA-022** [architecture.md:300,429,485]: `Clock` — единственное чтение wall-clock; домен берёт `business_date` явно; **запрет `timezone.now()`/`NOW()` в домене** (AST/lint). Селектор НЕ читает часы.
- **ARCH-DATA-024** [architecture.md:305,752]: дерево = adjacency + `CoreDivisionTreeSelector`, один канал обхода; **не mptt**.

### Решения, принятые при создании стори (дефолты; менять только осознанно)
1. **Поля `starts_at`/`ends_at`** (не `valid_from`/`valid_to`). Предикат — как у `division_at`.
2. **Fallback на текущий `Employee.division`** для сотрудников без history-строк (BR-CORE-HISTORY-003). **Нагружен:** 1.6 пишет 0 history-строк → на пилоте ВЕСЬ состав через fallback; без него AC-3 теряет всех донорских сотрудников. Бэкафилл истории из донора — **E7, НЕ 2.4** [Source: import_donor_slice.py:261, transform.py:121 — «full timeline policy = E7»].
3. **Границы employment: `WORKING ∧ is_active`** на обоих источниках (паритет `working_by_division`, Решение №3 — без раздувания Списка).
4. **Сигнатура:** `HistoricalEmployeeSelector.roster_on(business_date, division_ids=None) -> {div_id:[emp_id]}` (форма `working_by_division` для drop-in); контракт эпика `division_roster(division_id, date)` = `roster_on(date, subtree_ids(division_id))`. **Без `actor`** — внутренний агрегирующий селектор (как `working_by_division`; RBAC-сужение придёт с API-стори).
5. **Сверка = finding/violation, НЕ exception** (1.7 Решение №6; 1.8 `data/skipped_employee`). Программные инварианты держатся конструкцией; дыра данных — в отчёт, не краш.
6. **БЕЗ миграции/индекса в 2.4.** Модель существует → `makemigrations --check` чист. Индекс `(division, starts_at, ends_at)` под bulk-by-date scan — **follow-up** (таблица почти пуста на пилоте: 0 history-строк → fallback бьёт по `Employee` с `idx_emp_div_active`; «индекс только при деградации», architecture.md ARCH-DATA-024 + предостережение против преждевременной оптимизации). [Связано: deferred-work.md:64 — `working_by_division` без индекса.]
7. **KEY DECISION — своп знаменателя в `compute` (Task 4) ВКЛЮЧЁН в 2.4 — ПОДТВЕРЖДЕНО Bratan (2026-06-22).** Обоснование: цель эпика — «знаменатель расхода версионирован»; без свопа знаменатель не версионирован в отчёте. На пилоте (0 history) `roster_on` == `working_by_division` (всё fallback) → поведение идентично, регрессии нет. Следствие: 2.4 трогает 2 app (core + operations) — допустимо decomp-правилом 3. (Рассмотренная альтернатива — отгрузить только селектор+сверку, своп отдельной стори — отклонена: оставила бы знаменатель неверсионированным, цель эпика не закрыта.)

### Подводные камни для dev-агента
- **tz off-by-one:** только `local_midnight(business_date)`, не наивная/UTC-полночь (грабли 1.7).
- **`derive_report` жёстко assert-ит сходимость** (`strength_report.py:176-226`) — держать `employee_ids` статусов из НОВОГО roster (`:278`), иначе краш расхода.
- **Bulk, не per-item:** запрещено звать `division_at` в цикле (анти-паттерн донора). 2 запроса + merge в Python.
- **max-`starts_at` wins:** на `EmployeeDivisionHistory` НЕТ ExclusionConstraint (в отличие от hard-статусов) — перекрытие интервалов возможно (write-сервис его не допускает, но read должен быть устойчив). Тай-брейк = рантайм-защита.
- **Fallback обязателен** — иначе пилот (0 history) даёт пустой состав и сверка падает на всех.
- **ruff E501** — длинные строки/комменты заворачивать сразу; `ruff format` по файлу, не по папке (память `feedback_vaps_ruff_format_scoping`).
- **AST-isolation НЕ сканирует `selectors.py`** (deferred-work.md:164) — чистоту от wall-clock/cross-import держать дисциплиной, не тестом.
