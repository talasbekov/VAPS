## 2. Модуль «Сотрудники и штат» — модалка «Статусы сотрудника»

**Точка входа:** в таблице сотрудников ячейка со статусом становится кликабельной. Клик открывает модальное окно «Статусы сотрудника» для этого сотрудника.

**Поля формы:**

| Условие | Поля |
|---|---|
| Статус = «В строю» | без дат (бессрочный, статус по умолчанию) |
| Любой другой статус | обязательные «Дата начала» и «Дата окончания» |
| Статус = «На дежурстве» | даты + дополнительный блок (см. ниже) |

**Дополнительный блок для «На дежурстве»** (появляется только при выборе этого статуса):
1. `Тип дежурства` — select (справочник видов дежурств)
2. `Объект` — select (справочник объектов)
3. Зависимое поле — рендерится по выбранному типу дежурства:
   - тип «постовое» → `Пост` — select, отфильтрован по выбранному объекту
   - тип «групповое» → `Группа` — select из справочника групп

Правила:
- Поле 3 заблокировано, пока не выбран `Объект`.
- При смене `Объекта` значение `Поста` сбрасывается.
- При смене `Типа дежурства` зависимое поле пересобирается и сбрасывается.
- Валидация: сохранение блокируется при незаполненных обязательных полях.

**Перечень статусов** (из справочника, брать целиком):
В строю (по умолчанию) · На дежурстве · После дежурства · В командировке · Учёба · Соревнования · Конференция · В отпуске · Отпуск по рапорту · На больничном · Прикомандирован · Откомандирован

## 3. Модуль «Объекты и паспорта» — блок дежурных в карточке объекта

При открытии карточки любого объекта добавить раздел «Дежурные силы» со структурой:

```
Департамент
  └─ Пост / Группа
       └─ Сотрудник (ФИО, звание, должность), период дежурства «с … по …»
```

- Список строится из статусов «На дежурстве», у которых поле `Объект` = текущий объект.
- Группировка: департамент (по штатной принадлежности сотрудника) → пост или группа → сотрудники.
- Показывать только действующих на выбранную дату; дата по умолчанию — сегодня, с возможностью её сменить.
- Пустое состояние: «На объекте нет заступивших сотрудников».

---

## Ключевое требование — связанность

Это один сквозной поток данных, а не три независимые правки:
`Статус «На дежурстве» (сотрудник + тип + объект + пост/группа)` → **единственный источник** для раздела «Дежурные силы» в карточке объекта.

Проверка приёмки: оформить сотруднику статус «На дежурстве» на объект X с постом Y → открыть карточку объекта X → сотрудник появился под своим департаментом и постом Y. Изменить/завершить статус → запись из карточки объекта исчезла.

3.1. Судя по описанию — это классическая модель "план vs факт с довыделением", и её стоит делать не как один number per department, а как append-only список заявок, иначе потеряете аудит "кто когда доложил".

**Модель данных (концептуально):**

```
Event (ОМ)
  - id, дата, локация, total_required (например 30)

StaffRequest (заявка департаменту)
  - event_id
  - department_id
  - requested_count      // сколько запросили изначально
  - confirmed_count      // сколько департамент подтвердил (может быть < requested)
  - actual_count         // сколько реально пришло в день ОМ
  - type: initial | reallocation   // изначальная заявка или довыделение из-за нехватки
  - status: pending | confirmed | partial | fulfilled
```

Если департамент недодал — вы **не редактируете** его старую заявку, а создаёте новую строку `type=reallocation` другому департаменту (или тому же). Так остаётся история: кто когда и сколько недодал, кто закрыл дыру.

**Агрегация на уровне Event:**
```
total_requested = Σ requested_count по всем StaffRequest
total_confirmed = Σ confirmed_count
total_actual    = Σ actual_count
gap = total_required - total_confirmed  // если < 0, штаб рассылает reallocation
```

Superpowers: как работать
Установка:

```
/plugin install superpowers@claude-plugins-official

```

Перезапусти Claude Code — увидишь "SessionStart:startup hook succeeded".
Как это работает: мастер-скилл "using superpowers" автоматически запускается в начале каждой сессии и работает как диспетчер: читает запрос и сам активирует нужные скиллы в правильной последовательности. Вручную вызывать ничего не обязательно, но есть slash-команды:

* `/superpowers:brainstorm` — перед сложной фичей, `/superpowers:write-plan` — для миграций и мультифайловых рефакторов, `/superpowers:execute-plan` — выполнение плана батчами с чекпоинтами ревью.

Ключевые правила:

1. Основная ценность — на этапе планирования: прочитать и поправить план до аппрува предотвращает больше багов, чем любое ревью после. Частые ошибки — аппрувить план не читая.
2. TDD жёсткий: если Claude пишет код до тестов, скилл заставляет удалить код и начать заново. Работа идёт в git worktrees — изолированная ветка, main остаётся чистым. Для тебя это плюс после BMAD: каждый сабагент стартует с чистым контекстом на одну задачу — нет накопленной каши из длинных сессий → меньше токенов.
3. Отключение по месту: конфига нет — скиллы триггерятся от промптов. Скажи "skip planning and just write the code" или "не пиши тесты, это throwaway-скрипт" — и скиллы не активируются.
4. Твой CLAUDE.md главнее: если CLAUDE.md говорит "не использовать TDD", а скилл говорит "всегда TDD" — приоритет за инструкцией пользователя. Так что свой 12-этапный алгоритм можешь встроить поверх, конфликтов не будет.

Чтобы вам было проще разобраться с архитектурными задачами, сперва необходимо рассказать про особенности производства и эксплуатации протезов. Именно они сформировали основные вызовы для команды разработки.
Как работают протезы
Каждый бионический протез состоит из шести компонентов.

1. Миодатчики. Они считывают миосигналы с мышц, которые остались выше культи. Миосигналы — это биоэлектрические сигналы, которые возникают в результате электрической активности мышц.
2. Чип типа ESP32. Он считывает данные с миодатчиков. В чипе установлена программа на C++. Она анализирует миосигналы и по ним определяет, какое действие необходимо совершить. Затем она посылает сигнал актуаторам.
3. Актуаторы. Исполнительные устройства, которые преобразуют электрическую энергию в механическую. Они позволяют протезу выполнять движения, которые соответствуют командам пользователя.
4. Батарея. Источник питания, который обеспечивает энергией все компоненты протеза.
5. Система управления батареей. Она контролирует заряд и разряд батареи, а также предотвращает её перегрев и перегрузку.
6. Корпус. Это оболочка протеза, которая защищает его компоненты от внешнего воздействия.

Как изготавливают протез

1. Пациент заказывает у компании протез и оплачивает его.
2. После оплаты пациент приходит на первичный замер, чтобы сделать слепки ампутированной конечности. По слепкам делают культеприёмник, который вставляют в протез.
3. Протез изготавливают от одного до двух месяцев. В это время пациент должен периодически посещать офис компании для примерки.
4. Когда протез готов, пациент приходит на финальную примерку.
5. Если во время финальной примерки новые доработки не были запланированы, стартует серия обучений для пользователя. В это время команда записывает индивидуальные миосигналы пациента на протез.

Одно из важнейших свойств протеза — это скорость реагирования. Желательно, чтобы она не превышала 100 миллисекунд. В противном случае протезом будет сложно пользоваться.
Обеспечить высокую скорость реагирования непросто. Миодатчики сами по себе производят много шума в данных. Это происходит из-за того, что миосигналы достаточно слабые. Их могут искажать электромагнитные помехи от электронных устройств, механические вибрации и даже нестабильная работа батареи.
При этом миосигналы каждого человека уникальны. К тому же со временем они могут меняться. Иногда это происходит уже через месяц после первичной настройки.
Чтобы повысить скорость реагирования, программу распознавания движения помещают на сам протез — в чип. А чтобы она правильно интерпретировала сигналы мышц, её периодически приходится донастраивать.
Как донастраивать протез
Для этого в BionicPRO разработали приложения на Android и iOS. Они позволяют пилоту протеза самостоятельно донастраивать протез в процессе эксплуатации.
Компании важно, чтобы алгоритмы распознавания движения работали как можно быстрее. Чтобы улучшить свою ML-модель, BionicPRO собирает и хранит информацию о сигналах и движениях протеза по всем своим пользователям. Чип отправляет данные через 4G-модуль.
Изначально компания получала данные с протезов раз в день. Но недавно она переключилась на сбор данных в режиме реального времени. По необходимости пользователи могут отключить эту функцию.

    Масштабируемость. Система должна стабильно работать в условиях расширения бизнеса: компания открывает филиалы, нанимает десятки сотрудников и даёт клиентам возможность работать через мобильное приложение.
    Сопровождаемость. Нужно предусмотреть внесение изменений и улучшений в систему. Этот процесс должен быть простым и понятным.
    Конфигурируемость. В конфигурации можно вносить изменения без дополнительных доработок.

 * Проценты уже частично выплачены: при аннуитетном графике львиная доля банковской переплаты выплачивается в первые 2–3 года. Сейчас каждый ваш платеж в 350 000 ₸ всё больше уменьшает именно само тело долга.
 * Ограничение по сроку: просто «добавить» годы к текущему договору сверх 7 лет банк не сможет. Однако в рамках программы урегулирования задолженности БЦК может оформить реструктуризацию остатка долга как новый график на 5–7 лет либо предоставить кредитные каникулы.
Три сценария решения через Банк ЦентрКредит
1. Запрос кредитных каникул на 3–6 месяцев (экспресс-разгрузка)
 * Суть: вы подаете заявление на отсрочку погашения основного долга на 3–6 месяцев.
 * Результат: ежемесячный платеж временно снижается (оплачиваются только проценты, что существенно меньше 350 000 ₸).
 * Зачем это нужно: за эти 3–6 месяцев передышки вы полностью закрываете свои мелкие кредиты и рассрочки на 1–1.5 млн ₸ и выводите личный баланс из минуса.
2. Реструктуризация остатка долга на новый срок (5–7 лет)
 * Суть: банк берет оставшуюся сумму основного долга и распределяет ее заново на 60–84 месяца.
 * Результат: ежемесячный платеж снижается ориентировочно до 220 000–260 000 ₸, освобождая вам около 100 000 ₸ в месяц на постоянной основе.
3. Внутренний выкуп / рефинансирование
 * Если у машины достаточная рыночная стоимость, банк может рассмотреть переоформление залогового займа с включением туда ваших мелких беззалоговых рассрочек, чтобы объединить все выплаты в один понятный платеж.
План действий на ближайшие дни
 * Подать заявление в БЦК: через приложение bcc.kz или в отделении запросить урегулирование (причина: снижение платежеспособности из-за высокой долговой нагрузки, запрос — кредитные каникулы либо растягивание остатка).
 * Зафиксировать срок друзьям: обязать их подать заявки на потребительские кредиты в своих банках, чтобы закрыть висящие на вашем ИИН суммы в течение 10–14 дней.
 * Не брать новые микрозаймы и рассрочки: любые новые заимствования сейчас окончательно заблокируют согласование реструктуризации со стороны кредитного комитета БЦК.
