## 2. Модуль «Сотрудники и штат» — модалка «Статусы сотрудника»

**Точка входа:** в таблице сотрудников ячейка со статусом становится кликабельной. Клик открывает модальное окно «Статусы сотрудника» для этого сотрудника.

**Поля формы:**

| Условие | Поля |
|---|---|
| Статус = «В строю» | без дат (бессрочный, статус по умолчанию) |
| Любой другой статус | обязательные «Дата начала» и «Дата окончания» |
| Статус = «На дежурстве» | даты + дополнительный блок (см. ниже) |

**Дополнительный блок для «На дежурстве»** (появляется только при выборе этого статуса):
1. `Тип дежурства` — select (справочник видов дежурств)
2. `Объект` — select (справочник объектов)
3. Зависимое поле — рендерится по выбранному типу дежурства:
   - тип «постовое» → `Пост` — select, отфильтрован по выбранному объекту
   - тип «групповое» → `Группа` — select из справочника групп

Правила:
- Поле 3 заблокировано, пока не выбран `Объект`.
- При смене `Объекта` значение `Поста` сбрасывается.
- При смене `Типа дежурства` зависимое поле пересобирается и сбрасывается.
- Валидация: сохранение блокируется при незаполненных обязательных полях.

**Перечень статусов** (из справочника, брать целиком):
В строю (по умолчанию) · На дежурстве · После дежурства · В командировке · Учёба · Соревнования · Конференция · В отпуске · Отпуск по рапорту · На больничном · Прикомандирован · Откомандирован

## 3. Модуль «Объекты и паспорта» — блок дежурных в карточке объекта

При открытии карточки любого объекта добавить раздел «Дежурные силы» со структурой:

```
Департамент
  └─ Пост / Группа
       └─ Сотрудник (ФИО, звание, должность), период дежурства «с … по …»
```

- Список строится из статусов «На дежурстве», у которых поле `Объект` = текущий объект.
- Группировка: департамент (по штатной принадлежности сотрудника) → пост или группа → сотрудники.
- Показывать только действующих на выбранную дату; дата по умолчанию — сегодня, с возможностью её сменить.
- Пустое состояние: «На объекте нет заступивших сотрудников».

---

## Ключевое требование — связанность

Это один сквозной поток данных, а не три независимые правки:
`Статус «На дежурстве» (сотрудник + тип + объект + пост/группа)` → **единственный источник** для раздела «Дежурные силы» в карточке объекта.

Проверка приёмки: оформить сотруднику статус «На дежурстве» на объект X с постом Y → открыть карточку объекта X → сотрудник появился под своим департаментом и постом Y. Изменить/завершить статус → запись из карточки объекта исчезла.

В `Backend/PersonnelStatus/PersonalRecordFront/e2e/smoke-buttons.spec.ts` функция `signInPersona` (строка ~804) выполняет полный вход (`GET /api/auth/csrf/` + `POST /api/auth/callback/credentials/`) на КАЖДЫЙ проверяемый маршрут. За полный обход это сотни запросов к `/api/auth/csrf/`.

Проблема, подтверждённая прогоном 19.08.2026: все три падения обхода произошли ровно на этом вызове — у разных персон и разных маршрутов, с разными подписями (`read ECONNRESET` и `TimeoutError 10000ms`). При повторе на свежем стенде каждое зелёное. То есть падает не экран, а вход, и это даёт ложные красные в длинном прогоне. Хуже того, `smoke-buttons` объявлен `test.describe.configure({ mode: 'serial' })`, поэтому одно такое падение снимает весь хвост персоны — 19.08 так потерялось 52 проверки из прогона.

Задача: переиспользовать сессию персоны вместо повторного входа на каждый маршрут — например через `storageState` (залогиниться один раз на персону в `beforeAll`/глобальной настройке и переиспользовать состояние в контекстах), сохранив изоляцию между персонами.

# SmartQoldau — Второй мозг (Obsidian Vault)

Это хранилище Obsidian одновременно является рабочей директорией проекта SmartQoldau

- `OUTPUT/` — готовые результаты: отчёты, сценарии, планы, презентации, документы для

- `LOG.md` — журнал: что и когда обработано.

3.1. Судя по описанию — это классическая модель "план vs факт с довыделением", и её стоит делать не как один number per department, а как append-only список заявок, иначе потеряете аудит "кто когда доложил".

**Модель данных (концептуально):**

```
Event (ОМ)
  - id, дата, локация, total_required (например 30)

StaffRequest (заявка департаменту)
  - event_id
  - department_id
  - requested_count      // сколько запросили изначально
  - confirmed_count      // сколько департамент подтвердил (может быть < requested)
  - actual_count         // сколько реально пришло в день ОМ
  - type: initial | reallocation   // изначальная заявка или довыделение из-за нехватки
  - status: pending | confirmed | partial | fulfilled
```

Если департамент недодал — вы **не редактируете** его старую заявку, а создаёте новую строку `type=reallocation` другому департаменту (или тому же). Так остаётся история: кто когда и сколько недодал, кто закрыл дыру.

**Агрегация на уровне Event:**
```
total_requested = Σ requested_count по всем StaffRequest
total_confirmed = Σ confirmed_count
total_actual    = Σ actual_count
gap = total_required - total_confirmed  // если < 0, штаб рассылает reallocation
```
