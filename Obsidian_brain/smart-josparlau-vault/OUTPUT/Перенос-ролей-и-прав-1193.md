## Что переносится

Каждый существующий на сервере пользователь получает собственные настройки по точному совпадению логина. Набор ролей и их прав берётся из локальной выгрузки; дополнительные прежние назначения совпавшей учётки заменяются. Копируются настройки Django-доступа (`is_staff`, `is_superuser`, `is_active`), группы и индивидуальные разрешения. Пароли, персональные данные, сотрудники и организационная структура не переносятся.

По прямому уточнению заказчика подразделения исключены. Все перенесённые назначения глобальные (`scope=None`), то есть без ограничения подразделением. Несколько исходных назначений одной роли объединяются; роль активна, если активно хотя бы одно исходное назначение.

Логины, отсутствующие на сервере, не создаются; их список попадёт в приватный `result.json`. Если совпадений нет вообще, запись не выполняется. Настройки серверных пользователей вне выгрузки не заменяются; конфликт состава общей роли/группы с такими пользователями останавливает импорт до записи. Действующие или будущие временные полномочия требуют отдельного согласованного переноса: при обнаружении скрипт останавливается. В текущем источнике их нет.

## Запуск на закрытом сервере

Поместить архив в каталог Docker-комплекта, где уже находится `ctl.sh`. Из этого каталога:

```bash
tar -xzf access-1193.tar.gz
(cd access-1193 && sha256sum -c SHA256SUMS)
bash access-1193/apply-access.sh
```

Последняя команда только проверяет и показывает количество совпавших логинов, затронутых настроек учёток и изменений определений ролей/групп/прав. Для применения:

```bash
bash access-1193/apply-access.sh --apply
```

Нужен установленный `python3` на сервере; библиотеки используются из существующего backend-контейнера. Ничего из интернета не скачивается; образы не собираются, контейнеры не пересоздаются. Используется `ctl.sh exec -T backend`, поэтому сохраняется конфигурация Docker-комплекта, включая `images.env`.

После завершения должно быть **ПРИМЕНЕНО**. Пользователю стоит выйти из портала и войти снова, чтобы интерфейс перечитал права. Пароль остаётся прежним.

## Отчёт и резервный снимок

Каждый запуск печатает новую папку `.access-transfer/run-…/`. В ней:

- `result.json` — результат, `applied`, число совпадений/изменений, отсутствующие логины;
- `before.json` — прежние настройки доступа всей серверной БД, создаётся только перед применением;
- `error.json` — ошибка проверки/применения, если она возникла;
- `backend.log` — технический журнал.

Файлы создаются с правами600, каталог запуска700. В резервном снимке и отчёте нет паролей или хэшей. Хост сохраняет и синхронизирует резервный снимок и новые каталоги до разрешения записи в БД. Изменения применяются одной транзакцией; ошибка БД/аудита откатывает их. При обрыве связи после начала записи исход может быть неизвестен: нельзя принимать отсутствие итогового сообщения за успех.

Повторное применение того же снимка не создаёт дублей и сохраняет пароли. Отчёт учитывает также изменения прав через определения ролей и групп, даже если сами назначения совпали.

Явный откат по резервному снимку восстанавливает весь состав прав этой БД, включая прежние области назначений. Он не является повторным импортом локальных прав:

```bash
bash access-1193/apply-access.sh --restore './.access-transfer/run-ИМЯ/before.json' --apply
```

Выбирать снимок именно нужного запуска: откат возвращает настройки всего снимка, включая изменения, сделанные позднее. При смене состава пользователей или другой базе автоматический откат отклоняется. Перед самим откатом также сохраняется резервный снимок.
