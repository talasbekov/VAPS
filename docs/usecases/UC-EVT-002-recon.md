## Цель
Ведущий мероприятие фиксирует результаты осмотра объекта посещения (чек-лист), формирует расчёт постов по секторам и завершает этап, чтобы потребность в личном составе ушла штабу, а мероприятие перешло к расстановке.

## Предусловия
- Мероприятие (OpsSecurityEvent) существует и находится на стадии `RECON`. ОМ, заведённое с объектом реестра, стартует сразу на `RECON` (`initial_stage = "RECON" if security_object is not None else "BULLETIN"`); ОМ без объекта попадает на `RECON` через `POST bulletin/complete` (экран `AwaitingReconStage`, кнопка «Открыть рекогносцировку»).
- У мероприятия есть объект(ы) посещения (OpsSecurityEventVisitObject); у объекта, чьи посты правятся/импортируются/завершаются, назначен старший (`chief_employee_id`, ставится через `POST visit-objects/<id>/chief`, право event.manage).
- Для импорта постов: у объекта посещения есть `passport_binding` с `versionId` существующей OpsPassportVersion (либо у мероприятия — если объект посещения совпадает с `security_object` мероприятия).
- Расстановка объекта не заморожена (`placement_frozen` — по статусу документа OpsPlacementDocumentVersion, не по этапу).
- Пользователь имеет право `event.manage`.

## Main Flow
1. Актор открывает карточку ОМ (`/security-ops/events/<id>`); на стадии `RECON` система показывает экран «Рекогносцировка объекта»: сведения об объекте, переключатель объекта посещения, чек-лист, таблицу «Посты и секторы» и подвал с потребностью.
2. Актор проходит чек-лист из пяти пунктов шаблона (`RECON_CHECKLIST_TEMPLATE`), выставляя каждому состояние «Норма / Замечание / Не проверено»; при «Замечание» вводит комментарий.
3. Актор формирует расчёт постов: нажимает «Импорт из паспорта» (система добавляет посты и секторы из `sectors_snapshot` привязанной версии паспорта выбранного объекта посещения, need = 1, смена пустая) и/или добавляет секторы, посты и подпосты вручную (сектор, пост, задача, сотрудников, смена, требования; в раскрытии — тип, вооружение, форма одежды, примечание, мин. рейтинг).
4. Актор нажимает «Сохранить расчёт»; система (`PATCH recon`) проверяет чек-лист и строки, проверяет старшего у объектов, чьи посты изменены, сохраняет `recon_checklist` и `recon_sector_posts`, отвязывает замечания согласования от удалённых постов и пересчитывает потребность по объектам (`recompute_visit_needs`).
5. Система показывает в подвале «Потребность по объекту: N → уйдёт в „Сбор сил на ОМ“» и, если объектов несколько, отдельно сумму по мероприятию, которая уйдёт штабу.
6. Актор нажимает «Завершить рекогносцировку →» (доступна только при сохранённом расчёте, назначенных старших у всех объектов на `RECON`, непустом расчёте и полностью проверенном чек-листе) и подтверждает в диалоге «Отправить потребность N сотрудников штабу 2-го департамента?».
7. Система (`POST recon/complete`) повторно проверяет условия, считает `recon_force_request` как сумму `need` по постам (если ранее не был введён вручную), проставляет `recon_force_requested_at`.
8. Система автопроходом проводит мероприятие через `DEMAND` и `FORCES`: строит `demand_rows` из постов, `demand_approved = True`, `force_need` по объектам и мероприятию, одну автозаявку `force_requests` («По расчёту рекогносцировки», статус `NOT_SENT`), ставит объектам и мероприятию стадию `PLACEMENT`, `readiness_percent` этапа, пишет переходы `RECON→DEMAND`, `DEMAND→FORCES`, `FORCES→PLACEMENT` в OpsSecurityEventTransition.
9. Система возвращает обновлённое мероприятие; карточка переключается на экран расстановки.

## Alternative Flow
- **AF1. Объект без старшего**: шаг 1 → для активного объекта посещения без `chiefEmployeeId` экран показывает пустое состояние «Назначьте старшего объекта, чтобы начать рекогносцировку» с кнопкой «+ Назначить» (диалог `AssignChiefDialog`); форма чек-листа и постов не рисуется. Сервер на сохранение постов этого объекта, импорт и завершение отвечает 422 `VISIT_CHIEF_REQUIRED`. Сохранение чек-листа и постов ДРУГИХ объектов гард не блокирует (`_visits_with_changed_posts`, №634).
- **AF2. Ошибка валидации при сохранении**: шаг 4 → 422 с `fieldErrors`: `checklist.<i>.comment` «Укажите комментарий.» (состояние REMARK без комментария), `sectorPosts.<i>.sector` / `.post` «Обязательное поле.», `.need` «Должно быть не меньше 1.», `.visitObjectId` «Объекта посещения нет в этом мероприятии.», `forceRequest` «Укажите целое число не меньше нуля.». Экран показывает `FieldErrors` и `StageError`.
- **AF3. Импорт вне стадии**: шаг 3 → 422 `RECON_STAGE_REQUIRED` «Расчёт постов формируется на этапе рекогносцировки.».
- **AF4. Объект для импорта не выбран**: шаг 3 → объектов нет — 422 `VISIT_OBJECT_REQUIRED` («добавьте объект…»); объектов несколько и `visitObjectId` не передан — 422 `VISIT_OBJECT_REQUIRED` («выберите, для какого импортировать посты»); неизвестный id — 404 `VISIT_OBJECT_NOT_FOUND`. На экране кнопка импорта отключена, пока объект не выбран.
- **AF5. Нет паспорта**: шаг 3 → 422 `NO_PASSPORT_VERSION` («нет привязанной версии паспорта») или `PASSPORT_VERSION_NOT_FOUND` («Привязанная версия паспорта недоступна»). На экране кнопка отключена с подсказкой «У объекта нет привязанной версии паспорта.». Проверка паспорта идёт раньше проверки старшего.
- **AF6. Всё уже импортировано**: шаг 3 → 422 `NOTHING_TO_IMPORT` «Все посты этой версии паспорта уже в расчёте.» (повтор считается по `sourcePostId` в пределах объекта).
- **AF7. Расстановка объекта заморожена**: шаги 3–4 → 422 `PLACEMENT_FROZEN` (`_require_visit_placement_editable`) для объектов, чьи строки реально правятся / в который импортируют.
- **AF8. Завершение с нарушением условий**: шаг 7 → 422 `INVALID_STAGE_TRANSITION` (стадия не `RECON`), `VISIT_CHIEF_REQUIRED` (любой объект на `RECON` без старшего), `RECON_CHECKLIST_INCOMPLETE` «Обязательные пункты чек-листа остались в „Не проверено“» (считается по `TEMPLATE_CHECK_IDS` — отсутствующий пункт шаблона тоже «не проверен»), `RECON_SECTOR_POSTS_EMPTY` «Добавьте хотя бы один пост…». Экран заранее показывает причину видимой строкой у выключенной кнопки (`RightGate`).
- **AF9. Нет права event.manage**: все шаги → 403 (permission_map); на экране кнопка «Завершить» выключена с причиной `access.reason(EVENT_MANAGE)`, в пустом состоянии без старшего вместо «+ Назначить» показывается текст причины.
- **AF10. Мероприятие не найдено**: 404 (`lock_event`).

## Изменения в системе
| Объект | Действие | Описание |
|---|---|---|
| OpsSecurityEvent | update | `recon_checklist` (state/done/result/comment по пунктам), `recon_sector_posts` (нормализованные строки с `id`, `sector`, `post`, `task`, `need`, `shift`, `visitObjectId`, `requirements`, `comment`, `sourceSectorId`/`sourcePostId`, `minRating`), `recon_force_request` (если прислан или при завершении — сумма need), `recon_force_requested_at`, `updated_at` |
| OpsSecurityEvent | update | При завершении: `demand_rows`, `demand_approved=True`, `force_need`, `force_requests` (одна автозаявка `force-request-1`), `stage=PLACEMENT`, `readiness_percent` |
| OpsSecurityEventVisitObject | update | `force_need`, `force_assigned` (`recompute_visit_needs`) при каждом сохранении; `stage=PLACEMENT` при завершении |
| OpsSecurityEventTransition | create | Записи `RECON→DEMAND`, `DEMAND→FORCES`, `FORCES→PLACEMENT` (kind FORWARD, `occurred_at`) |
| Замечания согласования (approval remarks в JSON мероприятия) | update | `_detach_remarks_of_post` — отвязка замечаний от удалённых постов |
| OpsPassportVersion | read | `sectors_snapshot` привязанной версии при импорте |
| Леджер сил (`project_forces_ledger`, signal post_save) | update | Проекция пересчитывается при каждом сохранении OpsSecurityEvent |
| Audit log (AuditMiddleware) | create | Запись каждого успешного PATCH/POST к `/api/ops/security-events/<id>/recon*` |

## Бизнес-требования (BR)
- **BR1.** Чек-лист новых ОМ состоит из пяти пунктов шаблона `RECON_CHECKLIST_TEMPLATE` («Подъездные пути и парковка», «Периметр и ограждение», «Входные группы и КПП», «Пути эвакуации», «Связь и электропитание»), все обязательные; обязательность определяется шаблоном, а не телом запроса (`_required_of`, №541).
- **BR2.** Состояние пункта — одно из `NORMAL` / `REMARK` / `UNCHECKED`; явное `state` побеждает унаследованные `done`/`result` (№538); при `REMARK` комментарий обязателен.
- **BR3.** Завершить этап можно только когда ни один обязательный пункт шаблона не остался `UNCHECKED` (отсутствующий пункт шаблона считается непроверенным); `REMARK` завершению не мешает.
- **BR4.** Строка поста: `sector` и `post` обязательны, `need ≥ 1`, `visitObjectId` — только объект посещения этого мероприятия либо пусто (нераспределённый пост).
- **BR5.** Правка постов объекта и импорт в объект требуют назначенного старшего этого объекта; проверяются только объекты, чьи наборы постов фактически изменены (№424, №634).
- **BR6.** Правка/импорт постов объекта с замороженной расстановкой (документ отправлен/согласован) запрещена (№535, №868).
- **BR7.** Импорт из паспорта берёт `passport_binding` объекта посещения; снимок мероприятия допустим только при совпадении объекта посещения с объектом мероприятия; дубли по `sourcePostId` в пределах объекта не добавляются; импортированные посты получают `need=1`, пустую смену и `visitObjectId` целевого объекта.
- **BR8.** Отсутствие ключа `sectorPosts` или `forceRequest` в PATCH означает «не трогать», а не «обнулить» (№416).
- **BR9.** Удаление поста через PATCH отвязывает замечания согласования, ссылавшиеся на него (№510).
- **BR10.** Завершение требует: стадия `RECON`, старший у каждого объекта на `RECON`, чек-лист по BR3, непустой `recon_sector_posts`.
- **BR11.** Потребность, уходящая штабу, — сумма `need` по всем постам мероприятия; ранее введённый вручную `recon_force_request ≥ 1` не перезаписывается; `recon_force_requested_at` ставится в момент завершения.
- **BR12.** Стадии `DEMAND` и `FORCES` человек не ведёт: они проходятся сервером при завершении рекогносцировки с записью обоих переходов в журнал (№110); мероприятие оказывается на `PLACEMENT`.
- **BR13.** Потребность и «назначено» объекта — снимки в OpsSecurityEventVisitObject, пересчитываемые при каждом сохранении; у единственного объекта его посты — все, включая неразмеченные; при нескольких объектах неразмеченные строки не входят ни в чью потребность.
- **BR14.** Все три операции атомарны (`@transaction.atomic`) с блокировкой мероприятия (`lock_event`).

## Требования к логированию
- Доменный аудит (`audit_service.record`) на пути рекогносцировки не вызывается: кодов `SECURITY_EVENT_RECON_*` в `audit_service.py` нет. Назначение старшего объекта (предусловие) пишет `SECURITY_EVENT_CHIEF_SET`.
- HTTP-аудит: `AuditMiddleware` (`apps/audit`) фиксирует каждый успешный `PATCH …/recon/`, `POST …/recon/import-from-passport/`, `POST …/recon/complete/`.
- Журнал переходов OpsSecurityEventTransition — append-only записи трёх переходов при завершении (см. «Изменения в системе»).
- `logger` в `apps/ops/security_events.py` объявлен, но вызовы `logger.warning`/`logger.exception` есть только в цепочке ответа департамента (уведомление штабу); на пути рекогносцировки логирование — `Не реализовано в коде`.
- Логирование факта отправки потребности штабу (кто, когда, число) отдельным событием — `Не реализовано в коде` (есть только `recon_force_requested_at` в модели).

## Требования к UX/UI
- Экран: карточка ОМ `/security-ops/events/[id]`, стадия `RECON` → `ReconStage` (`role="region"`, aria-label «Рекогносцировка объекта»); стадия `BULLETIN` → `AwaitingReconStage` (карточка «Рекогносцировка ещё не начата», кнопка «Открыть рекогносцировку», ссылка на реестр ОМ для ОМ без объекта). Заголовок этапа — в шапке страницы («Этап N из 5 · …»), внутри карточки его нет (№70).
- Состав `ReconStage`:
  - `ObjectFacts` — сведения об объекте из реестра и привязанной версии паспорта (read-only).
  - `VisitObjectPicker` — переключатель объекта посещения (общий `useVisitObjectScope` с расстановкой); для нераспределённых постов — подсказка «Эти посты заведены до разметки. Отнести все к: <кнопки объектов> — затем „Сохранить расчёт“».
  - Секция «Чек-лист рекогносцировки»: счётчик «Проверено: K из N» (Норма и Замечание засчитываются); на пункт — подпись (со `*` у обязательных), группа из трёх кнопок «Норма / Замечание / Не проверено» (`aria-pressed`), поле «Комментарий» (placeholder «Комментарий (обязателен)» при «Замечание», подпись ошибки «Укажите комментарий», `aria-invalid`).
  - Секция «Посты и секторы»: подзаголовок «Расчёт объекта „…“ / Расчёт для текущего ОМ · есть несохранённые изменения / изменения сохранены»; кнопки «Импорт из паспорта» (отключена без выбранного объекта или без паспорта, с `title`-подсказкой), «+ Добавить сектор», «Сохранить расчёт» (активна только при `dirty`). Таблица (`min-w-[840px]`, горизонтальный скролл): сворачиваемые секторы (кнопка «Удалить» сектора), колонки «Сектор / Пост», «Задача поста», «Сотрудников», «Смена» (placeholder «07:00–15:00»), «Требования», действия «+ Подпост», ✎ (раскрытие: тип, вооружение, форма одежды, примечание, мин. рейтинг), ✕ «Удалить пост / подпост». Пустое состояние: «Постов пока нет — добавьте сектор или импортируйте из паспорта.» / «Нераспределённых постов нет.».
  - Ошибки: `FieldErrors` (полевые), `StageError` для сохранения, импорта, завершения.
  - Липкий подвал `recon-footer`: «Потребность по объекту „…“: N → уйдёт в „Сбор сил на ОМ“» (ссылка на `/employees?view=forces&tab=collections`, если модуль доступен); при расхождении — «штабу уйдёт по мероприятию M»; кнопки «Сохранить», «Завершить рекогносцировку →» (`RightGate` с видимой причиной: нет права / «Сохраните расчёт перед завершением этапа.» / «Не назначен старший объекта [«…»].» / «Нет постов расчёта.» / «Обязательные пункты чек-листа остались в „Не проверено“.»).
  - Диалог подтверждения: «Отправить потребность N сотрудников штабу 2-го департамента?», описание «Потребность зафиксируется, объект перейдёт к расстановке, штаб получит заявку.» (+ разница по объекту при нескольких объектах), кнопки «Отмена» / «Отправить».
  - Пустое состояние без старшего (`recon-chief-empty`): «Назначьте старшего объекта, чтобы начать рекогносцировку», кнопка «+ Назначить» → `AssignChiefDialog`.
- Состояния загрузки: подписи кнопок «Импорт…», «Сохранение…», «Завершение…», «Открытие…». Zod-схемы формы нет — валидация на сервере (`fieldErrors`) плюс подсказка комментария на клиенте.
- Поле `forceRequest` (ручной запрос личного состава) в UI отсутствует: экран шлёт только `checklist` и `sectorPosts`; число считает сервер при завершении.

## Открытые вопросы
