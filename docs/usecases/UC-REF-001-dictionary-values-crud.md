## Цель
Актор ведёт значения любого справочника системы из единого раздела «Справочники», различая четыре операции по смыслу: **добавление** новой записи, **корректирование** формулировки на месте, **редактирование** значения по сути с сохранением историчности (запись-преемник) и **удаление** — физическое при отсутствии ссылок либо деактивация при их наличии.

## Предусловия
- Актор вошёл в систему; у него есть `dictionary.view` (просмотр перечня и значений) и **отдельное право `dictionary_value.manage`** (изменение справочных значений) — см. BR13.
- Справочник заведён в перечне системы (`DEFINITIONS` для раздела ОМ, модели `apps/dictionaries` для кадровых) и заполнен сидом либо руками.

## Main Flow
1. Актор открывает «Система → Справочники» (`/security-ops/dictionaries`) — система показывает **единый перечень всех справочников системы** с поиском по наименованию: справочники раздела ОМ, кадровые (должности, звания), канон типов статусов, страны и города, а также справочники, появляющиеся по мере развития системы.
2. Актор выбирает справочник — система отдаёт таблицу его значений: «Наименование (KZ)», «Наименование (RU)», статус (активна / неактуальна), счётчик ссылок из данных системы, сведения о последнем изменении (вид операции, дата, ФИО изменившего), дата неактуальности.
3. Актор нажимает «Добавить запись» — система открывает форму: «Наименование (KZ)», «Наименование (RU)» и, у кодируемых справочников, «Код».
4. Актор заполняет поля и нажимает «Сохранить» — система проверяет обязательность наименований, отсутствие активного дубля и ищет **похожие записи** (AF4).
5. Система создаёт активную запись (`POST /api/ops/dictionaries/{CODE}/entries/`, 201), пишет `DICTIONARY_ENTRY_CREATED` и событие в журнал; запись немедленно доступна во всех выпадающих списках, использующих справочник.
6. Актор нажимает «Корректировать» в строке записи, меняет текст наименований, нажимает «Сохранить» — система обновляет **ту же запись** (`PATCH /api/ops/dictionaries/entries/{id}/`): новое наименование отображается везде, в том числе в ранее созданных данных; фиксируются вид операции «корректирование», дата и ФИО изменившего; пишется `DICTIONARY_ENTRY_UPDATED`.
7. Актор нажимает «Редактировать» — система предупреждает, что будет создана запись-преемник, а прежняя останется в ранее созданных данных со старым наименованием; актор вводит новые наименования и сохраняет — система создаёт **новую запись с внутренней ссылкой на прежнюю**, прежняя закрывается для нового выбора, новая появляется в выпадающих списках; фиксируются вид операции «редактирование», дата и ФИО; пишется `DICTIONARY_ENTRY_SUPERSEDED`.
8. Актор нажимает «Удалить» у записи **без ссылок** — система запрашивает подтверждение и удаляет запись физически (`DELETE /api/ops/dictionaries/entries/{id}/`, 204); пишется `DICTIONARY_ENTRY_DELETED`.
9. Актор нажимает «Удалить» у записи **со ссылками** — система предупреждает, что запись будет помечена неактуальной, а не удалена; после подтверждения запись деактивируется (`POST /api/ops/dictionaries/entries/{id}/set-active/`), проставляется дата неактуальности; пишется `DICTIONARY_ENTRY_SET_ACTIVE`.
10. Актор отбирает записи по статусу (показать / скрыть неактуальные) и по наличию ссылок — система показывает счётчик использований, чтобы неиспользуемые значения можно было выявить и убрать при ревизии справочника.

## Alternative Flow
- **AF1. Нет `dictionary.view`**: шаги 1–2 → экран `OpsAccessDenied` «справочников»; сервер отвечает 403 (`RequirePermissionMixin`). Пункт «Справочники» в меню не отображается.
- **AF2. Есть `dictionary.view`, но нет `dictionary_value.manage`**: шаги 1–2 проходят (актор видит перечень и значения), шаги 3–9 → «Добавить запись», «Корректировать», «Редактировать», «Удалить» не показываются; при прямом обращении к ручке сервер — 403. Наличие `dictionary.manage` само по себе доступа к изменению значений **не даёт** (BR13).
- **AF3. Ошибка валидации** (пустое наименование, активный дубль, занятый код): шаги 4, 6, 7 → 400 `VALIDATION_ERROR` с текстом у соответствующего поля; сохранение не выполняется, **введённые данные не теряются**.
- **AF4. Обнаружены похожие записи**: шаг 4 → система показывает список похожих (совпадение без учёта регистра и лишних пробелов, схожее написание, совпадение по любому из языков kz/ru) с наименованиями, статусом и счётчиком использований; актор либо выбирает «Использовать существующую» (новая запись не создаётся, форма закрывается), либо «Всё равно создать» — далее по шагу 5.
- **AF5. Редактирование записи-преемника**: шаг 7 → цепочка замен может быть многозвенной; система связывает звенья и в сводных представлениях (рейтинг, аналитика, отчёты) учитывает цепочку как одно направление.
- **AF6. Корректирование или редактирование неактуальной записи**: шаги 6–7 → 409 `DICTIONARY_ENTRY_INACTIVE`; над деактивированной записью доступна только активация.
- **AF7. Удаление значения справочника, связи которого не отслеживаются**: шаг 8 → 422 `DICTIONARY_USAGE_UNKNOWN` «Связи не отслеживаются — удаление запрещено, используйте деактивацию»; кнопка «Удалить» для такого справочника предлагает деактивацию.
- **AF8. Справочник или запись не найдены**: шаги 2, 6–9 → 404 `ENTITY_NOT_FOUND` по `code` / `id`; на экране — «Справочник не найден».
- **AF9. Ошибка загрузки перечня или значений**: шаги 1–2 → врезка `LoadFailure` с повтором; ошибка мутации — текст ответа сервера под формой.

| Объект | Действие | Описание |
|---|---|---|
| Запись справочника (`ops_dictionary_entries` / кадровые модели) | create | Наименования kz/ru, код (у кодируемых), `is_active=true`, вид операции «добавление», `updated_by`, `updated_at` |
| Запись справочника | update (корректирование) | Наименования kz/ru той же записи, вид операции «корректирование», `updated_by`, `updated_at`; ссылки из данных не меняются |
| Запись справочника | create + link (редактирование) | Новая запись с внутренней ссылкой на прежнюю (`supersedes`); прежняя получает признак «заменена» и закрывается для нового выбора, но остаётся в ранее созданных данных |
| Запись справочника | delete | Физическое удаление — только при нулевом счётчике ссылок и отслеживаемых связях |
| Запись справочника | deactivate | `is_active=false`, дата неактуальности, `updated_by` — при наличии ссылок вместо удаления |
| `OpsAuditLog` (`audit_service`) | create | `DICTIONARY_ENTRY_CREATED`, `DICTIONARY_ENTRY_UPDATED` (old/new наименования), `DICTIONARY_ENTRY_SUPERSEDED` (прежняя запись и преемник), `DICTIONARY_ENTRY_SET_ACTIVE` (old/new `isActive`), `DICTIONARY_ENTRY_DELETED` |
| HTTP-аудит `apps/audit` | create | `AuditMiddleware` на успешные `POST/PUT/PATCH/DELETE` по путям справочников |
| Выпадающие списки и формы системы | read | Читают только активные записи; ранее созданные данные продолжают отображать наименование своей записи |

## Бизнес-требования (BR)
- **BR1.** Раздел «Справочники» — **единое место ведения всех справочников системы**. Справочник, на который ссылается хотя бы один выпадающий список любой формы, обязан быть в перечне раздела; перечень пополняется по мере развития системы.
- **BR2.** Точечные кнопки ведения справочников внутри модулей **сохраняются**; один и тот же справочник ведётся и из «своей» кнопки в модуле, и из раздела «Справочники» — данные общие, изменение в одном месте видно в другом.
- **BR3.** Над записью доступны **четыре операции, различающиеся по смыслу**:
  - **Добавление** — создание новой записи;
  - **Корректирование** — изменение текста «на месте» (update той же записи), когда суть значения не меняется, меняется формулировка; новое наименование отображается во всех данных, включая созданные ранее;
  - **Редактирование** — замена значения по сути с сохранением историчности: создаётся запись-преемник с внутренней ссылкой на прежнюю, прежняя остаётся со старым наименованием в ранее созданных данных и закрывается для нового выбора;
  - **Удаление** — при отсутствии ссылок запись удаляется физически; при наличии ссылок **не удаляется**, а помечается неактуальной.
- **BR4.** Значения справочников двуязычные (kz/ru); оба наименования обязательны.
- **BR5.** Добавленная запись немедленно доступна во всех выпадающих списках, использующих справочник; деактивированная и заменённая — недоступны для нового выбора, но сохраняются в ранее созданных данных.
- **BR6.** **Контроль похожих записей при добавлении.** Система ищет похожие среди существующих (без учёта регистра и лишних пробелов, схожее написание, совпадение по любому из языков) и предлагает сослаться на найденную; создание новой — только осознанным подтверждением. Риск в этой системе — справочники со свободным вводом (организации, вузы, страны и города).
- **BR7.** Функционал **слияния дублей** (объединение записей с перепривязкой ссылок) — **вне скоупа**: ставка сделана на отсечение дублей при создании; при необходимости описывается отдельным UC.
- **BR8.** По каждой записи хранятся и показываются прямо в справочнике **сведения об изменениях**: вид последней операции (добавление / корректирование / редактирование / деактивация), дата изменения, ФИО изменившего, дата неактуальности. По таблице должно быть видно, какие записи корректировались, какие заменены преемником и какие деактивированы.
- **BR9.** Система определяет по каждой записи **наличие и число ссылок** из данных системы; записи со ссылками и без ссылок различаются визуально. Назначение — периодическая ревизия: неиспользуемые значения выявляются и убираются, чтобы не держать справочники, где большая часть записей фактически не используется.
- **BR10.** Цепочка замен многозвенная: запись-преемник может быть отредактирована в свою очередь. В дашбордах и аналитике, где нужна сводная картина по направлению, звенья цепочки учитываются связанно.
- **BR11.** Код записи после создания не меняется — на него ссылаются по коду (`uniq_ops_dictionary_entry_code`, `Position.code`, `Rank.code`).
- **BR12.** Канон типов статусов (`operations.StatusType`) остаётся read-only и пересинхронизируется сидом `seed_status_types`; в перечне раздела он показывается без действий ведения (см. UC-ORG-003, BR5).
- **BR13.** Доступ к функционалу изменения справочных значений предоставляется **отдельным правом** — «Изменение справочных значений» (`dictionary_value.manage`):
  - право покрывает все четыре операции над значениями (добавление, корректирование, редактирование, удаление и деактивацию) в **любом** справочнике раздела;
  - право **самостоятельное**: оно не выводится из `dictionary.manage`, `settings.manage` или роли `ADMIN`-подобных, выдаётся ролям явно и может быть выдано без `dictionary.manage` и снято независимо от него;
  - просмотр перечня и значений остаётся по `dictionary.view` — читатель работает со справочником без права изменения;
  - без этого права действия изменения не показываются в UI и отбиваются сервером 403, включая прямое обращение к ручкам;
  - существующие модульные права на точечные кнопки справочников внутри модулей (BR2) продолжают действовать только для своих кнопок и доступа к изменению значений из раздела «Справочники» не дают.

## Требования к логированию
- `audit_service.record` на каждую успешную операцию: `DICTIONARY_ENTRY_CREATED`, `DICTIONARY_ENTRY_UPDATED`, `DICTIONARY_ENTRY_SUPERSEDED`, `DICTIONARY_ENTRY_SET_ACTIVE`, `DICTIONARY_ENTRY_DELETED` (актор — `resolve_actor_id(request)`, entity `dictionary_entry`, old/new значения).
- В журнал попадает **сам текст записи, а не только факт операции**. Состав по операциям:
  - **добавление** — наименование справочника + наименования (kz/ru) созданной записи;
  - **корректирование** — наименование справочника + старые и новые наименования;
  - **редактирование** — наименование справочника + наименования прежней записи и записи-преемника;
  - **удаление** — наименование справочника + наименования удалённой записи;
  - **деактивация** — наименование справочника + наименования деактивированной записи.
- Поля события: дата и время сохранения, ИИН пользователя, ФИО пользователя, операция, объект события (раздел + субъект). Поле «Подписание: хэш подписи» — **отдельное самостоятельное поле**, не объединяется с другими; операции раздела выполняются без ЭЦП, поле остаётся пустым.
- HTTP-аудит успешных write-запросов — `AuditMiddleware` (`apps/audit`); для кадровых справочников `ContentType` разрешается из пути (`dictionaries.position`, `dictionaries.rank`).
- Отказы 400/409/422 в журнал раздела не пишутся.
- Просмотр справочников не логируется.

## Требования к правам
| Роль | Доступ | Как обеспечивается |
|---|---|---|
| `ADMIN` | полный | `*` |
| `REFERENCE_ADMIN` | полный: просмотр перечня, всех значений и четыре операции над ними | `permission_map`: `list` / `retrieve` / `entries` → `dictionary.view`; `create_entry` / `update_entry` / `supersede_entry` / `set_active` / `delete_entry` → **`dictionary_value.manage`** (BR13) |
| Держатели `dictionary.view` без `dictionary_value.manage` | только просмотр перечня и значений | Действия изменения скрыты в UI, ручки отвечают 403 |
| Держатели `dictionary.manage` без `dictionary_value.manage` | изменение значений **не доступно** | Право самостоятельное и из `dictionary.manage` не выводится (BR13) |
| Держатели `status.view` | чтение канона типов статусов | `require_any_permission("status.view", "dictionary.view")` |
| Держатели `orgstructure.view` | чтение должностей и званий в контракте `/api/core/positions/`, `/api/core/ranks/` | `permission_map` → `orgstructure.view` |
| Держатели модульных прав на точечные кнопки справочников | ведение «своего» справочника из своего модуля | Модульное право действует только для своей кнопки и **не даёт** доступа к разделу «Справочники» |
| Остальные роли | нет доступа к разделу и к API справочников | 403; `OpsAccessDenied`; пункт меню «Справочники» не отображается |

## Требования к UX/UI
- Пункт «Справочники» — отдельная строка бокового меню рядом с «Администрирование»; отображается только при наличии `dictionary.view`.
- Раздел открывается **полноценной отдельной страницей** (не модальным окном). Две зоны: слева — перечень справочников системы с поиском по наименованию, справа — таблица значений выбранного справочника.
- Колонки таблицы: «Наименование (KZ)», «Наименование (RU)», «Статус» (активна / неактуальна), «Использований» (счётчик ссылок), «Последнее изменение» (вид операции, дата, ФИО), «Дата неактуальности».
- Визуальные признаки:
  - записи со ссылками и без ссылок различаются: счётчик показывает число ссылок, записи с нулём — приглушены или с маркером «не используется»;
  - запись-преемник — со значком связи и подсказкой «Заменяет: {прежнее наименование}»; прежняя — с подсказкой «Заменена на: {наименование преемника}»;
  - неактуальные записи приглушены или зачёркнуты; есть фильтр по статусу (показать / скрыть неактуальные).
- Действия: «Добавить запись» над таблицей; в строке — «Корректировать», «Редактировать», «Удалить». Кнопки изменения видны только держателям отдельного права `dictionary_value.manage` (BR13); без него страница открывается в режиме просмотра, без форм и кнопок.
- Формы добавления, корректирования и редактирования: поля «Наименование (KZ)», «Наименование (RU)» (+ «Код» у кодируемых справочников). Форма редактирования дополнительно предупреждает о создании записи-преемника; удаление записи со ссылками сопровождается предупреждением о деактивации вместо физического удаления.
- Форма добавления при обнаружении похожих записей показывает их список (наименования kz/ru, статус, счётчик использований) с действиями «Использовать существующую» и «Всё равно создать».
- Состояния: «Загрузка…», пустой справочник, `LoadFailure` с повтором, текст ошибки сервера под формой, «Справочник не найден», `OpsAccessDenied`.
- Даты отображаются в формате ДД.ММ.ГГГГ.

## Post-Conditions
- Справочник актуализирован: запись добавлена, скорректирована на месте, заменена преемником с сохранением связи либо удалена / помечена неактуальной.
- Изменения немедленно отражены во всех выпадающих списках и функционалах, использующих справочник; ранее созданные данные сохранили свои ссылки и (при редактировании и деактивации) прежние наименования.
- По записи зафиксированы вид операции, дата, ФИО изменившего и дата неактуальности; событие записано в журнал.

## Разрыв с текущей реализацией
| Требование | Состояние в коде | Что нужно сделать |
|---|---|---|
| Единый раздел для всех справочников (BR1) | Частично: `/security-ops/dictionaries` показывает справочники ОМ и блок кадровых; стран и городов нет (метка «В разработке» №417), охраняемые лица и законы ведутся в Django Admin | Свести перечень, добавить поиск по наименованию |
| Добавление (BR3) | Есть: `create_entry`, `POST /api/dictionaries/positions/` | Двуязычные поля, проверка похожих |
| Корректирование (BR3) | Есть: `update_entry` (PATCH), `PUT` кадровых — семантика совпадает | Явно назвать операцию «корректирование» в UI и журнале |
| Редактирование с записью-преемником (BR3, BR10) | **Нет**: у `OpsDictionaryEntry`, `Position`, `Rank` нет ссылки на прежнюю запись | Поле `supersedes`, ручка, миграция, учёт цепочки в аналитике |
| Удаление / деактивация по наличию ссылок (BR3) | Расходится: у справочников ОМ удаление разрешено только для `TRACKED` (JOURNAL_ENTRY_TYPES, POST_REQUIREMENT_GROUPS), остальные всегда отбиваются 422; у кадровых деактивации нет вообще | Довести `usage_of` до отслеживания связей по всем справочникам; добавить деактивацию кадровым |
| Двуязычность kz/ru (BR4) | **Нет**: у `OpsDictionaryEntry` одно поле `label`, `LANGUAGE_CODE = 'en-us'`, i18n не подключён | Решение заказчика + миграция полей (см. «Открытые вопросы») |
| Контроль похожих записей (BR6) | **Нет**: проверяется только точный дубль кода и уникальность на модели | Поиск похожих и диалог выбора |
| Счётчик ссылок (BR9) | Частично: `usage_of` считает связи у справочников ОМ; у кадровых — только отказ при удалении с числом ссылок | Счётчик в таблице для всех справочников |
| Сведения об изменениях в таблице (BR8) | Частично: `updated_by` / `updated_at` есть в модели и `OpsAuditLog`, но в таблицу не выводятся; вида операции и даты неактуальности нет | Вывести колонки, хранить вид операции и дату неактуальности |
| Журнал с текстом записи | Частично: `DICTIONARY_ENTRY_UPDATED` хранит old/new `label`; у кадровых справочников `audit_service` не вызывается вовсе | Довести состав событий и подключить кадровые справочники |
| Отдельное право на изменение значений (BR13) | **Нет**: права `dictionary_value.manage` не существует, изменение значений идёт по общему `dictionary.manage` (`seed_operations.py`, `PERMISSIONS`, `ROLE_PERMISSIONS["REFERENCE_ADMIN"]`) | Завести право в `PERMISSIONS` («Изменение справочных значений»), выдать его `REFERENCE_ADMIN` в `ROLE_PERMISSIONS`, перевести на него `permission_map` операций изменения в `OpsDictionariesViewSet` и `_StaffDictionaryViewSet`, добавить в клиентский гейт (`entities/portal-access`, `hooks/use-ops-permissions.ts`); отдельно решить судьбу выданных `dictionary.manage` при миграции |

## Открытые вопросы
- **Двуязычность kz/ru** взята из канона ERP, но в Smart Josparlau сейчас нет ни языковых полей, ни подключённого i18n (`LANGUAGE_CODE = 'en-us'`). Нужно решение заказчика: вводить два наименования на запись или ограничиться одним, оставив BR4 на будущее.
- Разделение «корректирование» и «редактирование» требует от пользователя понимать разницу. Нужно ли объяснять выбор подсказкой прямо в UI и допустимо ли откатить ошибочное редактирование (удалить преемника и вернуть прежнюю запись в активные).
- Область действия UC: распространяется ли он на кадровые справочники (UC-ORG-003), охраняемых лиц и справочник стран и городов (№417) или на первом шаге только на справочники раздела ОМ (UC-OBJ-003).
- Семь архивных справочников (`ARCHIVED_DICTIONARIES`, решение заказчика 27.08.2026, Plane №200) в единый перечень не возвращаются — подтвердить, что архив сохраняется при переходе на единый раздел.
- Канон типов статусов правится только сидом; в едином перечне строка есть, действий ведения нет — подтвердить, что это остаётся так.
- Порог «похожести» записи (нормализация, расстояние редактирования) и поведение при большом числе совпадений не определены.
- Код нового права (`dictionary_value.manage`) — предложение: он держится схемы `noun.verb`, принятой в `seed_operations.py` (трёхсегментных кодов среди прав нет). Название в каталоге прав — «Изменение справочных значений». Требует утверждения.
- Какие ещё роли, кроме `REFERENCE_ADMIN`, получают `dictionary_value.manage` при заведении, и сохраняется ли у `REFERENCE_ADMIN` право `dictionary.manage` после разделения.
- Миграция действующих доступов: у кого сейчас есть `dictionary.manage`, тем право на изменение значений выдаётся автоматически или назначается заново вручную.
