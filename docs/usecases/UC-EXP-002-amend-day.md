# UC-EXP-002. Внести поправку в сданный день

| Поле | Значение |
|---|---|
| Модуль | Ежедневный расход |
| Актор | DIRECTORATE_HEAD (начальник управления), ADMIN |
| Статус | Done |
| Основание | `apps/operations/day_submission_service.py` (`amend_day`), `apps/operations/models_submission.py` (`OpsDailySubmission.Event.AMENDED`, `reason`, `sanction`, `triggered_by_status_id`, `chk_ops_submission_amended_explained`), `apps/operations/api/views.py::DailySubmissionViewSet.amend` (`POST /api/operations/daily-submissions/{id}/amend/`), `apps/ops/api/views.py::OpsDailySubmissionsViewSet.amend` (`POST /api/ops/daily/daily-submissions/{id}/amend/`), `DailySubmissionAmendSerializer`; FRONT `features/ops-daily/day-submission-panel.tsx` (`DayAmendmentForm`), `entities/daily-grid/index.ts` (`describeAmendFailure`, `isAmendmentComplete`, `SANCTION_MAX`) |
| Дата актуализации | 2026-09-08 |

## Цель
Актор исправляет уже сданный день, создавая новую версию снимка с обязательными причиной и санкцией, не переписывая прежнюю версию.

## Предусловия
- Актор аутентифицирован, имеет право `daily_report.correct` с областью, включающей подразделение сдачи.
- День подразделения сдан хотя бы одной версией (`DailySubmissionSelector.lock_day` ≠ None).
- Известен `id` любой версии дня (панель берёт текущую версию).

## Main Flow
1. Актор в панели «Сдача дня» сданного дня нажимает «Исправить сдачу».
2. Система показывает форму «Исправить сдачу за <дата>?» с полями «Причина» и «Санкция» (счётчик N/255).
3. Актор заполняет оба поля и нажимает «Подтвердить исправление» (кнопка активна только при непустых полях и санкции ≤ 255 символов после обрезки).
4. Система проверяет форму тела (обе строки непусты, санкция ≤ 255), находит версию по `id`, проверяет право и область по подразделению найденной строки.
5. Система берёт замок на строке первой версии дня и перечитывает голову цепочки.
6. Система собирает свежий снимок состояния, гасит `is_current` у прежней версии и создаёт новую версию `version = latest + 1` с `event = AMENDED`, `late = False`, `reason`, `sanction`.
7. Система пишет событие журнала `DAILY_SUBMISSION_AMENDED` (old_value — прежняя версия, new_value — новая, reason).
8. Система возвращает 201 с проекцией поправки; экран перечитывает состояние дня и историю версий, показывает новую версию как текущую.

## Alternative Flow
- **AF1. Пустая причина/санкция или санкция длиннее 255**: шаг 4 → 400 (валидация DRF); экран показывает сообщение и детали.
- **AF2. Нет права или подразделение вне области**: шаг 4 → 403; экран: «Недостаточно прав на исправление сдачи. Требуется право daily_report.correct.»
- **AF3. Версия с таким `id` не найдена / нечисловой `id`**: шаг 4 → 404 `ENTITY_NOT_FOUND`; экран: «Сдача не найдена.»
- **AF4. День не сдан** (нет ни одной версии): шаг 5 → 422 `NO_SUBMISSION_TO_AMEND`.
- **AF5. Гонка поправок**: вторая вставка срывает уникальность версии → IntegrityError → 409 `DAY_ALREADY_SUBMITTED`; экран: «День успел измениться: появилась новая версия. Состояние перечитано — откройте исправление заново.»
- **AF6. Подразделение не найдено**: 404 `ENTITY_NOT_FOUND`.
- **AF7. Сеть / 5xx / 401**: панель молчит, сообщение отдаёт общий канал.

## Изменения в системе
| Объект | Действие | Описание |
|---|---|---|
| `ops_daily_submissions` | update | у прежней текущей версии `is_current=False` |
| `ops_daily_submissions` | create | новая версия `version+1`, `is_current=True`, `event=AMENDED`, `late=False`, `reason`, `sanction`, `triggered_by_status_id=NULL`, свежий `snapshot` |
| `ops_audit_log` | create | `DAILY_SUBMISSION_AMENDED` с `old_value`/`new_value`/`reason` |
| HTTP-аудит (`AuditMiddleware`) | create | запись CREATE на успешный POST |

## Бизнес-требования (BR)
- **BR1.** Сданное не переписывается — поправка создаёт новую версию; прежняя остаётся целиком.
- **BR2.** Причина и санкция обязательны и содержательны (непробельные); санкция ≤ 255 символов; хранятся обрезанными. Непустоту держит и CHECK БД.
- **BR3.** Событие поправки всегда `AMENDED`; окно дат не применяется (поправляют прошлое); `late` всегда `False`.
- **BR4.** `id` в пути адресует цепочку дня, а не конкретную версию — поправка идёт поверх текущей головы.
- **BR5.** Подразделение и актор в теле не принимаются; область проверяется по подразделению найденной строки.
- **BR6.** `triggered_by_status_id` от клиента не принимается (ставит система; в API сейчас всегда `None`).
- **BR7.** Право поправки (`daily_report.correct`) отдельно от права сдачи (`daily_report.mark_update`).
- **BR8.** Конкурентные поправки сериализуются замком строки первой версии.

## Требования к логированию
- Журнал раздела: `DAILY_SUBMISSION_AMENDED` (actor, entity_id новой версии, old/new снимки, reason).
- HTTP-аудит: `AuditMiddleware` пишет CREATE.
- Console-логгер в сервисе отсутствует. Логирование отказов поправки — `Не реализовано в коде`.

## Требования к правам
| Роль | Доступ | Как обеспечивается |
|---|---|---|
| ADMIN | полный | `*` |
| DIRECTORATE_HEAD | полный в своей области | `daily_report.correct` — `permission_map["amend"]` обоих вьюсетов + `_assert_division_in_scope` |
| Роли со `status.view` | чтение версий (history=true) | `status.view` |
| Остальные | нет | — |

## Требования к UX/UI
- Панель «Сдача дня» в раскрытой строке управления на `/employees` (без `?view=`): кнопка «Исправить сдачу» видна при наличии текущей сдачи.
- Форма (настоящий `<form aria-label="Исправление сдачи">`): подпись «Появится новая версия дня; прежняя останется в истории с автором, временем и основанием.», textarea «Причина», input «Санкция» с `maxLength=255` и счётчиком, кнопки «Подтвердить исправление» (disabled при неполной форме/отправке) и «Отмена».
- Ошибки: плашка с сообщением по виду отказа (`describeAmendFailure`), детали валидации списком.
- Кнопка не гейтится правом на клиенте — отказ читается по 403 с сервера.

## Открытые вопросы
- Кнопка «Исправить сдачу» показывается всем (`canAmend = current !== null`, комментарий «Демо-персона wildcard: право daily_report.correct есть»); проверки права на клиенте нет.
- `triggered_by_status_id` (авто-поправка от изменения статуса) — писателя нет; в сервисе и модели поле есть, «будущий хук ретро-правки» (комментарий в сериализаторе).
- Дублирование маршрута: `/api/operations/daily-submissions/{id}/amend/` и `/api/ops/daily/daily-submissions/{id}/amend/` с одинаковой логикой.
