# UC-GEN-003. Получать уведомления в реальном времени

| Поле | Значение |
|---|---|
| Модуль | Общие |
| Актор | Любая вошедшая учётная запись — получатель (`recipient = str(User.pk)`) |
| Статус | Partial |
| Основание | `apps/operations/notify_service.py` (`notify`, `_publish`, `mark_read`, `mark_all_read`), `models_notification.py` (`OpsNotification`), `ws_consumers.py` (`OpsNotificationConsumer`), `ws_routing.py` (`ws/operations/notifications/`), `ws_auth.py` (`resolve_actor_id` по `?token=`), `ws_groups.py` (`group_name_for`), `NotificationViewSet` в `apps/operations/api/views.py` (`/api/operations/notifications/`, `unread-count/`, `read-all/`, `{id}/read/`), `config/asgi.py`, `settings.OPS_WS_ENABLED`, `CHANNEL_LAYERS` (Redis); FRONT `lib/ops-ws.ts`, `features/ops-notifications/notification-bell.tsx`, `features/notifications/` (`NotificationsDropdown`, `notifications-api.ts`), `app/security-ops/layout.tsx` |
| Дата актуализации | 2026-09-08 |

## Цель
Актор узнаёт о фактах раздела ОМ, адресованных ему (запрос сил, возврат расстановки, заступление, отставание по сдаче и т.д.), без перезагрузки экрана и отмечает их прочитанными.

## Предусловия
- Актор вошёл в систему (UC-GEN-001).
- Для канала: сервер запущен через ASGI (`config/asgi.py`), доступен Redis (`CHANNEL_LAYERS`), `OPS_WS_ENABLED=1` (значение по умолчанию).
- Деловая операция, порождающая факт, выполнена (сдача дня, рассылка запроса сил, возврат расстановки и др.).

## Main Flow
1. Деловая операция вызывает `notify(recipient, kind, business_date, payload, dedupe_key)`; система создаёт строку `OpsNotification` в транзакции вызывающего.
2. По коммиту транзакции система (`_publish`) отправляет конверт `{"type": <kind>, "payload": {...}}` в группу канального слоя `ops.notif.<sha256(recipient)[:32]>`.
3. Актор открывает раздел `/security-ops/*`; лэйаут вызывает `startOpsWs()`, клиент открывает WebSocket и показывает статус канала на плавающем колокольчике («подключение…» → «онлайн»).
4. Потребитель `OpsNotificationConsumer` принимает соединение по `?token=<access JWT>`, подписывает его на группу актора и ретранслирует конверты дословно.
5. Клиент получает кадр, увеличивает счётчик «новых» на колокольчике и инвалидирует запрос списка (список перечитывается с сервера, а не собирается из кадров).
6. Актор открывает выпадающий список уведомлений в шапке (`NotificationsDropdown`): система читает `GET /api/operations/notifications/?unread=true` (и `GET /api/notifications/unread/` старого приложения) и показывает непрочитанные с текстом по виду (`describeOpsNotification`) и ссылкой.
7. Актор нажимает уведомление → `POST /api/operations/notifications/{id}/read/`; система ставит `read_at` (момент первого прочтения) и переводит по ссылке.
8. Актор нажимает «Отметить все как прочитанные» → `POST /api/operations/notifications/read-all/` с `until` = момент самого свежего показанного; система отмечает непрочитанные до этого момента и возвращает `marked`.

## Alternative Flow
- **AF1. Токен в строке запроса отсутствует или недействителен**: шаг 4 → соединение закрывается кодом `4403` (`CLOSE_UNAUTHENTICATED`); клиент переходит в «переподключение…» и повторяет с экспоненциальной задержкой (1 с × 2ⁿ, потолок 30 с, джиттер 0,5–1,0).
- **AF2. `OPS_WS_ENABLED=0`**: шаг 4 → соединение принимается и сразу закрывается кодом `4503`; шаг 2 не выполняется (`_publish` возвращается первой строкой); строки уведомлений по-прежнему пишутся и читаются по REST.
- **AF3. Канальный слой недоступен (Redis)**: шаг 2 → `logger.exception("WS-публикация не удалась…")`, исключение проглатывается, деловая операция и возврат `notify()` не меняются.
- **AF4. Сбой записи уведомления (БД)**: шаг 1 → `logger.exception("notify() не сработал…")`, `notify()` возвращает `None`; деловая операция не падает (кроме путей, где уведомление и есть операция — догон отставших сам обрабатывает `None`).
- **AF5. Повторный `notify` с тем же ключом (получатель, вид, дата, `dedupe_key`)**: шаг 1 → `get_or_create` возвращает существующую строку, первый `payload` сохраняется, публикации в сокет нет. При `dedupe_key=None` каждый вызов создаёт свою строку (событие, а не состояние дня).
- **AF6. Отметка чужого уведомления**: шаг 7 → 404 (строка ищется своим селектором; `mark_read` дополнительно бросает `DomainError PERMISSION_DENIED` при несовпадении получателя).
- **AF7. Нечитаемый `until` или наивное время в `since`**: шаги 6/8 → 400.
- **AF8. Нет идентичности (`resolve_actor_id` пуст)**: шаги 6–8 → 403 `PERMISSION_DENIED`.
- **AF9. Один из двух источников ленты (legacy или ops) не ответил**: шаг 6 → список показывается из ответившего, `partlyFailed` — предупреждение с кнопкой «Повторить»; оба не ответили — состояние ошибки с «Повторить».
- **AF10. Мок-режим фронта**: шаг 3 → вместо WebSocket опрос `sessionStorage` (`ops-mock-ratings`, 1,2 с) для актора `demo-admin`.

## Изменения в системе
| Объект | Действие | Описание |
|---|---|---|
| `ops_notifications` (`OpsNotification`) | create | `recipient`, `kind` (из `Kind`), `business_date`, `payload`, `dedupe_key`; уникальность `(recipient, kind, business_date, dedupe_key)`; `CheckConstraint` на список видов и непустого получателя |
| `ops_notifications.read_at` | update | `mark_read` — только первое прочтение, только своё; `mark_all_read` — одним `UPDATE` по непрочитанным до `until` |
| Redis (канальный слой) | send | `group_send` в группу получателя по `transaction.on_commit`, только для СОЗДАННОЙ строки |
| Соединение WebSocket `/ws/operations/notifications/` | send | Ретрансляция конверта `event["message"]` клиенту |
| E-mail / SMS / push | — | Не реализовано в коде |

## Бизнес-требования (BR)
- **BR1.** Единственная точка записи уведомления — `notify()`; запись синхронна, в транзакции вызывающего: откат операции откатывает и уведомление.
- **BR2.** Публикация в сокет — по коммиту и только для новой строки; истина — строка в базе, сокет — знак. Выключатель `OPS_WS_ENABLED` гасит только знак.
- **BR3.** Виды уведомлений закрыты списком `OpsNotification.Kind`: `SUBMISSION_LAGGING`, `EVENT_ACKNOWLEDGEMENT`, `FORCES_REQUEST`, `FORCES_REQUEST_DEPARTMENT`, `PLACEMENT_RETURNED`, `ACKNOWLEDGEMENT_DUE_SOON`, `FORCES_RESPONSE`, `ASSIGNMENT_DECLINED`, `FORCES_REQUEST_SENT`.
- **BR4.** Группа сокета выводится только из проверенного сервером токена; параметры клиента (`user_id`, `recipient`) на неё не влияют. Токен принимается той же `JWTAuthentication`, что и REST (подпись, срок, `is_active`).
- **BR5.** Лента — только своя: фильтр по получателю накладывается селектором безусловно; чужое уведомление — 404, не 403.
- **BR6.** `since` — строгая нижняя граница (ISO 8601 с зоной), `until` — включительная верхняя; `unread-count` считает по всей ленте без `since`.
- **BR7.** Прочитано — момент, а не флаг: повторное чтение момент не двигает; `read-all` не трогает уже прочитанные.
- **BR8.** Порядок ленты задаёт сервер: свежие первыми, при равном времени — по возрастанию `id`.
- **BR9.** Клиент дедуплицирует кадры по `id` (память 500 последних) и держит одно соединение на вкладку (`epoch`/`started`).

## Требования к логированию
- `notify_service`: `logger.exception` (логгер `organization_management.apps.operations.notify_service`, уровень ERROR со стеком) при сбое записи и при сбое публикации; выводится в `console` (root DEBUG).
- Выключенный `OPS_WS_ENABLED` не логируется намеренно (комментарий `_publish`).
- Подключение/отключение сокета, коды закрытия 4403/4503: `Не реализовано в коде` (потребитель не пишет в лог).
- `OpsAuditLog` по уведомлениям и отметкам прочтения: `Не реализовано в коде` (в словаре `ACTIONS` событий уведомлений нет; отчёт рассылки пишется в аудит самих операций, например `FORCE_ALLOCATION_NOTIFIED`).
- HTTP-аудит `audit.AuditLog` для `POST …/read/`, `read-all/`: `ContentType(app_label="operations", model="notification")` не существует (модель `opsnotification`) — запись не создаётся.
- Токен в строке запроса WS попадает в журнал доступа веб-сервера (предупреждение в `ws_auth.py`; закрывается конфигурацией `/ws/`, в коде не задано).

## Требования к правам
| Роль | Доступ | Как обеспечивается |
|---|---|---|
| Любая вошедшая учётная запись (все роли, `ADMIN`) | чтение своей ленты, `unread-count`, отметки прочтения, WebSocket своей группы | `NotificationViewSet` — гейт `resolve_actor_id` (без кода права); `OpsNotificationConsumer.connect` — `ws_auth.resolve_actor_id` по `?token=`; `http_method_names = ["get","post","options"]`, общих `create/update/destroy` нет (405) |
| Аноним | нет | 403 на REST; закрытие сокета `4403` |
| Отправка уведомления | только сервер | `notify()` вызывается из сервисов (`lagging_check`, `ops/forces_notify`, `placement_return_notify`, `assignment_decline_notify`, `acknowledgement_*`, `security_events`); внешней ручки отправки нет |

## Требования к UX/UI
- Колокольчик раздела ОМ — плавающая кнопка внизу справа на всех экранах `/security-ops/*` (`OpsNotificationBell`): точка статуса канала (серый «канал не запущен», жёлтый «подключение…»/«переподключение…», зелёный «онлайн»), бейдж числа новых кадров, `aria-live` «Новых уведомлений: N». Панель «Уведомления ОМ» показывает список `GET /api/ops/rating-notifications/` (уведомления оценивания: текст по `RATING_NOTIFICATION_TEXT`, ссылка, время), состояния «Загрузка…» / «Уведомлений нет.», подпись «Кадр канала — сигнал „обнови“…» и ссылку на журнал изменений порта.
- Выпадающий список «Уведомления» в шапке портала (`NotificationsDropdown`, `staleTime` 30 с): непрочитанные из двух источников (legacy + ops) с текстом по виду, кнопка «Отметить все как прочитанные», состояния загрузки / ошибки с «Повторить» / частичного отказа; клик по уведомлению отмечает его прочитанным и переходит по ссылке; при ошибке отметки — тост «Уведомление осталось непрочитанным. Попробуйте ещё раз.».
- Лента уведомлений на странице аналитики (`useOpsLaggingNotifications`) — чтение `GET /api/operations/notifications/`.

## Открытые вопросы
- Клиент открывает `ws://<host>/ws/notifications/` (`lib/ops-ws.ts`) — это маршрут СТАРОГО приложения `apps.notifications` (`NotificationConsumer`, идентичность из сессии `scope["user"]`), а потребитель раздела ОМ слушает `/ws/operations/notifications/` и требует `?token=`; клиент токен в адрес не подставляет. Живой канал раздела ОМ до браузера не доходит.
- `next.config.js` не содержит правил для `/ws/*` (rewrites не проксируют WebSocket) — при стенде на :3106/:3108 соединение идёт на сам Next.
- Формат кадра: клиент (`asFrame`) требует поля `id: string`, `createdAt: string`, `code`, `deepLink`; сервер (`_publish`) шлёт `id` числом, `created_at`, `kind`, `payload` — даже при доставке кадр отбрасывался бы как нечитаемый.
- Колокольчик раздела показывает список уведомлений оценивания (`/api/ops/rating-notifications/`), а не ленту `OpsNotification`; лента `OpsNotification` читается в шапке портала без сокета (перечитывание по `staleTime` 30 с и фокусу окна).
- В мок-режиме WS подменён опросом `sessionStorage` (`ops-mock-ratings`) — контракт мока не совпадает с серверным конвертом.
- E-mail/SMS-доставка: `Не реализовано в коде`. Причина `NOTIFY_AUTHOR` в `ops/feedback.py`: «канал уведомлений раздела ОМ несёт события оценивания; события обратной связи появятся отдельным срезом».
- Настройка «логировать путь `/ws/` без аргументов» — рекомендация в `ws_auth.py`, конфигурации в репозитории нет.
