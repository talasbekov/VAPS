# Offline post maps and combat overview implementation plan

> Use executing-plans for controller integration and dispatching-parallel-agents for the separate server/frontend domains. Existing linked worktree is isolated; branch codex/post-maps-20261102 starts at be99caf0.

**Goal / user spec:** “карту добавь в боевое дежурство и в объектах и паспортах там тоже есть да для постов?” Make existing local maps useful for combat assignments and permanent passport posts, retaining the current3380 application and all its data.

**Design:** Reuse the existing offline Astana renderer/assets. Add nullable coordinates to passport posts, edit them as part of the existing passport draft, freeze them in published versions. Show posts on object/passport maps. Combat choices expose scoped object/post points; new assignments freeze their selected place coordinates, and a visible daily board map shows assignment snapshots. Unknown locations remain unknown. Existing event-placement GeoJSON is a separate event-owned source and is not silently merged with permanent passport posts.

**Alternatives:** Reusing online tiles conflicts with the user's explicit offline requirement. Storing passport points in event GeoJSON would mix ownership/history. The minimal extension of existing relational passport rows and map renderer keeps a single permanent location per post and preserves existing authority.

**Stack:** Existing Django/PostgreSQL, Next/React, local canvas assets. No new dependencies, public services, background map or theme changes.

## Contracts and constraints

- SecurityPost DTO gains optional `location: {latitude:number,longitude:number}|null`; optional accommodates old version snapshots. New draft reads return an explicit nullable value. Passport PATCH accepts the same field; omission on an existing row preserves coordinates, explicit null clears, malformed/nonfinite/bool/out-of-range/partial pairs fail atomically.
- Add migration0156_security_post_locations after0155. Two nullable floats plus paired/range constraint. Existing migrations unchanged, no rows/grants/seeds/backfills modified.
- Existing object.manage gate controls passport writes. Existing scoped combat grants control choices and snapshots. No newly broadened readers.
- CombatCatalogRow places gain optional nullable `location`; their posts gain optional nullable `location`. Coordinates come only from the scoped server catalogue.
- OBJECT/POST CombatLocation snapshots gain optional latitude/longitude from their authoritative stored object/post; ignore client-forged coordinates for these kinds. No post→object point fallback. Old shift snapshots without coordinates stay without coordinates.
- Passport publication freezes post coordinates in sectors_snapshot; later edits/deletion do not rewrite versions. Location edits participate in passport freshness/changed-draft determination without treating missing historical keys differently from null.
- Combat overview uses shift snapshots, excludes cancelled groups from active map markers, identifies groups without map positions. Selecting a marker opens/focuses the existing shift. POINT editor remains functional; OBJECT/POST show a readonly selected-place preview; ROUTE/RESERVE have no fabricated geometry.
- Current real3380 data, files, passwords, session key, local AI and shared node_modules/Git must survive. No fixture writes or default point creation in the live DB. Existing dirty user docs remain unstaged. DigitalTwin unchanged.

## Review focus

Coordinate omission must not erase an existing post during unrelated edits. Old snapshots cannot inherit current post positions. Foreign catalogue objects/posts cannot be located by injecting IDs. Stale or read-only map callbacks cannot mutate a draft. Zero coordinates are valid; NaN/bool/partial/outside-range inputs are not. Out-of-city points must be reported honestly. Map controls must never submit enclosing forms.
