# Рабочее место дежурного и API Цифрового двойника

Запрос: семь задач из серверных скриншотов 16 октября. Пользователь подтвердил состав интеграции: объекты, посты, ОМ и численность, без персональных данных. Сохраняем рабочую локальную БД на 2008 сотрудников; Digital и другие проекты не изменяем. Серверного SSH нет.

## 1. Существующие пункты и каталог мест дежурства

Два зачёркнутых пункта уже объединены в «Журнале дежурств», объекты ОМ компактны в коммитах 022d5a01/7e303e91. Повторно такие экраны не создаём.

Исправляем найденные дефекты каталога: сохранение паспорта должно сохранять ID существующих секторов/постов, чтобы статусный наряд и почасовое назначение не теряли место. Чужие и повторные ID запрещены до изменений. Новые временные ID создают строки; удаляются только исключённые из переданного дерева строки. Невалидные типы/длины дают атомарный 400. Коды новых объектов уникальны при разрывах старой нумерации и конкурентном создании, существующие коды не меняются.

## 2. Рабочий экран и отчёты

На прежнем маршруте command-center размещаем «Оперативный контроль»: действительные числа штатных единиц/людей, незавершённые ОМ, конфликты и незакрытые заявки сил. Убираем демонстрационный процент этапа и его среднее. Прошлые незакрытые ОМ названы отдельно от предстоящих. Ошибка загрузки не превращается в нули или частичный итог. Переход в свод передаёт ту же дату.

Один пункт «Отчёты» ведёт в доступную поверхность: расход при daily_report.generate, иначе смены/документы при report.generate. Внутри обеих прежних страниц общая навигация объясняет различие источников. API выгрузок, задания, история и права не меняются.

## 3. Доступ к кадровому экрану

Новый явный код status.workspace вместе с status.view открывает /statuses. DUTY_OFFICER сохраняет status.view для свода и status.manage_root для существующих API, но по умолчанию не получает кадровый экран. Миграция и чистый сид добавляют экранное право существующим ролям с status.view, кроме DUTY_OFFICER и INTEGRATION_USER. Кастомные роли, пользовательские назначения и сочетания ролей сохраняются; явный дополнительный грант открывает экран. Нет запрета по имени роли. Обычный сотрудник продолжает стартовать с профиля. Настройки честно объясняют экранное право.

## 4. Интеграция

GET /api/integrations/digital-twin/v1/snapshot/?date=YYYY-MM-DD. Дата по умолчанию — бизнес-дата Службы; строгая проверка формата. Только GET/HEAD/OPTIONS, существующий JWT, отдельное глобальное право digital_twin.read. Роль DIGITAL_TWIN_READER содержит только это право. Старый INTEGRATION_USER со status.manage автоматически доступа не получает. Не создаём пароли или аккаунты на сервере.

Ответ: schema_version, business_date, generated_at, time_zone, objects, events и duty. Все идентификаторы — строки. Объекты содержат текущие посты паспортов; мероприятия — площадки, их этапы, потребность и назначенных, посты расстановки и сохранённые точки карты. ID поста паспорта и поста ОМ явно различаются по источнику. Неизвестная потребность/точка остаётся null. Координаты принадлежат конкретной площадке/посту ОМ: не выводим общую точку здания из случайного мероприятия и не геокодируем адреса.

Численность кадровых нарядов на дату следует каноническому выбору статуса и действующим почасовым назначениям из общего журнала. Агрегация использует ID и уникальных сотрудников внутри группы места, без отдачи ФИО, employee_id, ИИН, телефонов, паспортов и закрытых файлов. Это численность назначенных за дату; она не называется текущим присутствием на посту. Расстановка ОМ и кадровые наряды — отдельные источники, общий итог их не складывает.

OpenAPI описывает отдельный явный контракт. При недоступной карте выдаётся честная ошибка/признак недоступности, а не пустая успешная карта. При отказе прав данные не читаются. Начальная версия без обратной записи, вебхуков и фоновой синхронизации.

## Проверка и поставка

Регрессии RED→GREEN: ID поста/состав, валидация/атомарность/конкурентный код, права workspace/смешанные роли, счётчики и сбой второй страницы, API авторизация/методы/даты/неизвестное/агрегаты/отсутствие ПДн. PostgreSQL проверяется в отдельном временном окружении без рабочих БД; временные ресурсы удаляются. Канонический gate:front и реальные browser-проверки после сборки.

Применение локально сохраняет БД и текущий стек. Новая additive data migration устанавливает только права и роли; резервная копия и сравнение кадровых данных обязательны. Для сервера документируется необходимость миграции, app-only guard не ослабляется. Новая серверная ZIP-поставка не входит в этот запрос.
