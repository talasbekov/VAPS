# Перенос редактируемого каталога объекта

`PersonnelStatus/Personnel-Records/tools/object_catalog_transfer.py` переносит
только объект, текущие секторы и посты паспорта. Файл можно скопировать в
совместимый backend без установки пакетов, миграции и перезапуска приложения.
Он использует существующие модели `OpsSecurityObject`, `OpsObjectSector`,
`OpsSecurityPost`, `OpsAuditLog`, `Division`, действующий RBAC и PostgreSQL.

Это дополнение к обновлению приложений, а не замена базы. Предварительно
проверяются совместимость схемы и резервная копия целевой установки. Скрипт
сам не восстанавливает, не очищает и не обновляет схему. Текущий updater
`deploy/lan/update-with-migrations.py` привязан к согласованной поставке
17 октября; перенос каталога не расширяет его список допустимых миграций.

## Формат

```json
{
  "format": "smart-object-transfer/v1",
  "exportId": "UUID конкретного экспорта",
  "source": {
    "namespace": "UUID источника в этой поставке",
    "objectId": "исходный Smart ID",
    "code": "исходный код, только справочно"
  },
  "object": {
    "name": "Название",
    "objectType": "Тип",
    "region": "Регион",
    "address": "Адрес",
    "ownership": "GUARDED",
    "objectState": "ACTIVE"
  },
  "sectors": [
    {
      "id": "исходный ID сектора",
      "name": "Название сектора",
      "posts": [
        {
          "id": "исходный ID поста",
          "name": "Название поста",
          "task": "",
          "requirements": ""
        }
      ]
    }
  ],
  "bundleSha256": "sha256 канонического JSON остальных полей"
}
```

UUID в действительном файле должны быть каноническими, ID — положительными
десятичными строками. Порядок массивов задаёт порядок новых строк.
Канонизация для SHA256: UTF-8, ключи отсортированы, `ensure_ascii=False`,
`separators=(",", ":")`, поле `bundleSha256` исключено. Хэш проверяет целостность,
но не подтверждает доверенность отправителя; поставку передают по установленному
процессу обновления. Неизвестные поля и повторяющиеся JSON-ключи запрещены.
Пределы: 2 МиБ, 100 секторов, 1000 постов; длины полей совпадают с моделями.

Не входят сотрудники, личные профили, назначения, мероприятия, история,
опубликованные версии паспорта, роли, пароли, фотографии и URL источника.
Координат у паспортных постов Smart нет: они переносятся частью двойника.
Для Аккорды местный каталог содержит 20 постов, а размещение в двойнике
условное. Эти подписи и происхождение данных сохраняются в общей поставке.

## Экспорт и проверка

Команды ниже выполняет оператор нужной установки; `BACKEND` — проверенное
имя её backend-контейнера, `ACTOR` — ID действующей учётной записи. При работе
на сервере не использовать локальные ID департаментов или учёток как универсальные.

```sh
docker cp smart/. BACKEND:/app/transfer-20261020
docker exec -w /app BACKEND python /app/transfer-20261020/tools/object_catalog_transfer.py \
  --app-root /app export --object-id SOURCE_OBJECT_ID --actor-id ACTOR \
  --source-namespace SOURCE_UUID --export-id EXPORT_UUID \
  --output /app/transfer-20261020/catalog.json
```

Экспорт требует глобального `object.view`, читает согласованный снимок в
транзакции PostgreSQL `REPEATABLE READ, READ ONLY`. `DJANGO_SETTINGS_MODULE`
берётся из окружения действующего приложения; без него команда отказывает.
Сохраняйте `source.namespace` и `exportId` вместе с файлом поставки.

```sh
docker exec -w /app BACKEND python /app/transfer-20261020/tools/object_catalog_transfer.py \
  --app-root /app import --input /app/transfer-20261020/catalog.json \
  --actor-id ACTOR --target-department-id TARGET_DEPARTMENT_ID \
  --expected-department-name "Точное название целевого департамента" \
  --receipt /app/transfer-20261020/smart-receipt.json
```

Это dry-run: рабочие таблицы и аудит не меняются; receipt содержит
`applied:false`. ID ещё не созданных строк равны `null`. Для применения той же
команды добавить `--apply`. Требуются активная учётка, глобальное
`object.manage` и проверка этого права для указанного департамента. Проверяется
тип подразделения `department`, активность и точное название.

Каталог объектов глобальный: у объекта нет FK на департамент.
`target.departmentId` — проверенный контекст будущего подключения двойника,
а не новая связь владения. Локальный department ID82 нельзя автоматически
считать ID шестого департамента в другой базе.

## Существующий объект

Без `--target-object-id` создаётся новый объект со штатно выданными кодом и ID.
Совпадение названия с существующим объектом вызывает `OBJECT_COLLISION`;
скрипт ничего не выбирает по имени или исходному `OBJ-…`.

Для добавления в существующий объект нужны одновременно `--target-object-id`
и `--mapping mapping.json`. Все исходные ключи обязаны присутствовать:

```json
{
  "sectors": {"SOURCE_SECTOR_ID": {"id": "TARGET_SECTOR_ID"}},
  "posts": {
    "SOURCE_EXISTING_POST_ID": {"id": "TARGET_EXISTING_POST_ID"},
    "SOURCE_NEW_POST_ID": {"id": null}
  }
}
```

`null` означает создать строку при первом применении. Указанные target ID
проверяются на принадлежность объекту/сектору, уникальность и совпадение
названия, задачи и требований. Основные поля выбранного объекта также должны
совпасть с пакетом. Несовпадение — конфликт, без перезаписи.
Остальные строки объекта сохраняются. Этот CLI не вызывает заменяющий весь
паспорт PATCH и не удаляет отсутствующие в пакете строки.

## Повтор, receipt и редактирование

Каталог и запись `SECURITY_OBJECT_CATALOG_IMPORTED` сохраняются одной
транзакцией. Запись в существующем append-only `OpsAuditLog` содержит ID,
digest и сопоставление, без кадровых данных. Advisory locks сериализуют
одновременные применения одного экспорта/источника.

Повтор того же файла возвращает `applied:true,reused:true`, не меняет каталог
и не создаёт новую запись аудита. Работает и с первоначальным mapping, где
были `null`. Локальный receipt можно восстановить повторным запуском: он
не является источником идемпотентности. При ошибке записи receipt после commit
нужно повторить ту же команду, не создавать новый exportId.

Если пост или сектор из сопоставления удалён/перенесён в другой объект,
команда отказывает с `MAPPING_DAMAGED`. Изменение названия, описания, порядка,
добавление своих строк и перенос поста между секторами того же объекта
сохраняются при повторе. Новый exportId для уже импортированного source-object
отклоняется: обновление существующего импорта требует отдельного согласования,
а не скрытого перезаписывания ручных правок.

```json
{
  "format": "smart-object-transfer-receipt/v1",
  "exportId": "UUID",
  "bundleSha256": "digest",
  "applied": true,
  "reused": false,
  "source": {"namespace": "UUID", "objectId": "SOURCE_OBJECT_ID"},
  "target": {
    "objectId": "TARGET_OBJECT_ID",
    "departmentId": "TARGET_DEPARTMENT_ID",
    "departmentName": "Название департамента"
  },
  "sectors": {"SOURCE_SECTOR_ID": {"id": "TARGET_SECTOR_ID"}},
  "posts": {"SOURCE_SMART_POST_ID": {"id": "TARGET_SMART_POST_ID"}}
}
```

Общий сборщик подключения двойника принимает только `applied:true` receipts
из обеих систем. Сопоставление с UUID точек двойника строится по исходным
Smart ID через link manifest поставки. Credentials в receipt и пакет не входят.

После переноса: **Объекты → нужный объект → Посты и секторы**. Обладатель
`object.manage` может редактировать обычные поля паспорта. Публикация версии
паспорта остаётся отдельным штатным действием; импорт её не выполняет.

Целевые проверки: `organization_management/apps/ops/tests/test_object_catalog_transfer.py`
на отдельной PostgreSQL через `python -m pytest -q --create-db …`.
