# Пробелы API: экраны без бэкенда

Снято на живом стенде: целевой бэк `Backend/PersonnelStatus/Personnel-Records`
(Django, :8100), фронт `Backend/PersonnelStatus/PersonalRecordFront` (Next, :3106),
ветка `claude/smart-josparlau-e55`.

Источники истины:

* список маршрутов целевого бэка — резолвер Django (`get_resolver()`, 391 запись);
* список маршрутов донора — `Backend/VAPS/schema.yaml` (39 записей).

**Ни один путь с префиксом `/api/ops/` не существует ни в целевом бэке, ни в
доноре.** На стенде эти запросы отдаёт браузерный мок-слой MSW
(`mocks/ops/browser.ts`, включён по умолчанию: `lib/ops-env.ts` считает режим
мок-ом, пока не выставлен `NEXT_PUBLIC_OPS_DATA_SOURCE=api`). Из-за этого экраны
раздела выглядят рабочими — именно это и маскирует дыру.

## Как устроена заглушка

Один переиспользуемый компонент, одна точка врезки:

| Файл | Роль |
| --- | --- |
| `PersonalRecordFront/lib/api-gaps.ts` | реестр «маршрут → недостающие пути», поиск по самому длинному префиксу |
| `PersonalRecordFront/components/api-gap-notice.tsx` | единственная разметка пометки |
| `PersonalRecordFront/components/dashboard-layout.tsx` | врезка в `<main>` — общий корень контента хостовых экранов, `/security-ops/*` и `/ops` |

Пометка не скрывает содержимое и не ломает навигацию: она рисуется над контентом
экрана и прямо говорит, что данные ниже — мок.

## Найденные и починенные дефекты (для контекста)

1. **`/organization/`** — схема штатных единиц. `getStaffUnits` в `lib/api.ts` не
   понимал конверт DRF-пагинации `{count,next,previous,results}` и плоскую строку
   списка (`position`/`employee` в корне вместо массива `employees`), молча
   возвращал `[]`, и экран писал «Данные не загружены из API» при HTTP 200.
   Починен адаптер формы на фронте — контракт бэка не трогали.
2. **`/feedback/`** — бесконечный опрос 404. `FeedbackChat` глушил ошибку в
   `console.error` и продолжал опрос раз в 3 секунды; экран показывал «Пока нет
   сообщений», выдавая отсутствующий бэк за пустой список. Опрос теперь
   останавливается на первой ошибке, ошибка выводится на экран.

### Обход стенда Playwright 11.08.2026 (коммит `00a7c37f`)

Полный клик-обход по всем кнопкам, 80 страниц. Четыре дефекта — все 404:

3. **`/statuses`** — маршрут `/api/secondments/` был выключен в корневом
   urlconf с самого импорта донора: вьюхи ходили в поля кастомного пользователя
   (`user.role`, `user.division`), которых у целевой модели нет. Область
   портирована на цепочку `User → Employee → StaffUnit → Division`, сериализатор
   отдаёт `employee_detail`/`division_detail` в форме, которую ждёт фронт;
   роут включён.
4. **Карточка отчёта** — `/api/ops/service-report-jobs/{id}/detail/`. Фронт
   зовёт **только** `/detail/`, ручки не было. Заведён алиас `retrieve` по
   контракту мока — контракт фронта не трогали.
5. **Уведомления рейтинга** — `deep_link` вёл на `/ratings/workspace` (адрес
   выведенной SPA-встройки). Генератор и сид переведены на нативный
   `/security-ops/ratings/workspace`; стендовые строки поправлены данными.
6. **Сайдбар «Настройки»** — `/settings` был 404. Страница рендерит модуль
   настроек политик по приёму `/feedback`: одна реализация, два входа.

**Не дефекты** (валидация/домен, а не дыра): `DAY_NOT_SUBMITTED` на экспорте
несданного дня; 400/422 на пустых формах диалогов.

7. **Hydration mismatch на `/dashboard`** (коммит `8179e037`) — три `new Date()`
   прямо в JSX (шапка «Последнее обновление», бейдж «Синхронизация»,
   «Последняя проверка») расходились SSR/клиент на границе секунды: 2 из 8
   жёстких перезагрузок падали. Время ставится в `useEffect`, до маунта — «…».

**`CLIENT_FETCH_ERROR` next-auth — не чинится:** `net::ERR_ABORTED` на
`/api/auth/session`, когда жёсткая навигация обрывает in-flight фетчи страницы
логина. Библиотечный шум next-auth v4, сессия поднимается штатно.

### Живость раздела ОМ держалась на untracked-файле (коммит `907f9c99`, 11.08.2026)

8. **Раздел `/security-ops/*` молча уезжал в мок на любом чекауте без
   `.env.local`.** Пер-доменный переключатель в `lib/ops-env.ts` был
   инвертирован: домен считался живым, только если его имя перечислено в
   `NEXT_PUBLIC_OPS_LIVE_DOMAINS`, а список жил в untracked `.env.local`.
   Чистый клон, tarball и внешний агент получали мок — и не могли этого
   заметить: фикстуры несут те же названия ОМ, что и сид БД (отличие —
   лишняя строка `ОМ-2026-3`). Теперь домен живой по умолчанию, на мок
   возвращает явный `NEXT_PUBLIC_OPS_MOCK_DOMAINS`.

   `isOpsMockMode()` намеренно не тронут — он про транспорт (host-MSW и
   подмена WebSocket), а не про данные. Живой сокет висел бы на
   `${location.host}/ws/notifications/`, то есть на Next-хосте, который WS не
   проксирует; колокольчик остаётся на мок-сокете. На моке осознанно остался
   и `*/api/operations/my-permissions/` (`identityHandlers`), хотя ручка на
   живом бэке есть.

**Ловушка проверки:** `onUnhandledRequest: "bypass"` означает, что промах пути
уходит в сеть без ошибки — «данные показались» не доказывает живость.
Проверять мутацией БД. И не поднимать вторую копию `next dev` в том же
чекауте для сравнения режимов: серверы делят `.next/`, `NEXT_PUBLIC_*`
инлайнятся при компиляции, и проба переписывает поведение основного стенда.

### Права раздела ОМ рисовал мок — RBAC не работал (11.08.2026)

9. **`identityHandlers` снят: `*/api/operations/my-permissions/` теперь живой.**
   Мок отдавал `{"permissions":["*"]}` ЛЮБОМУ посетителю, поэтому раздел
   `/security-ops/*` на каждой учётке выглядел администраторским, а гейты
   страниц (`!isLoading && !hasPermission(...)`) не срабатывали никогда.

10. **Коды прав фронта не существовали на бэке.** Страницы спрашивали
    `ops.object.view` / `ops.duty.view` / `ops.security_event.view`, справочник
    RBAC знает `object.view` / `duty.view` / `event.view` (префикса `ops.` нет
    ни в одном коде). Под мок-wildcard-ом расхождение было невидимо: `*`
    проходит любую проверку. Со снятым моком раздел закрылся бы у ВСЕХ, кроме
    ADMIN. Коды приведены к бэку.

11. **Запрос прав отключался без host-логина.** `enabled: isOpsMockMode() ||
    user !== null`: `/security-ops/*` не закрыт middleware (его нет в
    `matcher`), а выключенный запрос навсегда оставляет `isLoading=true` —
    гейты не срабатывают и раздел открывается анониму. Запрос уходит всегда;
    без токена бэк отвечает 403 → прав нет → гейт закрыт (проверено).

12. **Календарь смен звал реестр ОМ без права.** `useSecurityEvents` не
    принимал `enabled`, и персона без `event.view` получала 403 на каждый
    рендер (баннер «Мероприятия скрыты» при этом рисовался верно).

**Проверка на трёх учётках** (стенд :8100/:3106, ручка отвечает с бэка —
видно в access-логе Django):

| Учётка | `my-permissions` | Объекты | Дежурства | Реестр ОМ | Командный центр | Календарь |
|---|---|---|---|---|---|---|
| `admin` (ADMIN) | `["*"]` | открыт | открыт | открыт | открыт | полный |
| `observer` (`OPS_READER`) | `["duty.view","object.view"]` | открыт | открыт | **закрыт** | **закрыт** | только дежурства + баннер |
| `erda` (DIVISION_OPERATOR) | 7 кодов, ни одного ОМ-чтения | **закрыт** | **закрыт** | **закрыт** | **закрыт** | пуст |
| аноним | 403 | **закрыт** | — | — | — | — |

**Роль `OPS_READER` внесена в сид** (`seed_operations`, единственное
отступление от дословного порта раскладки — помечено на месте). Раскладка
намеренно неполная — `object.view` + `duty.view`, БЕЗ `event.view`: это
единственная сеяная персона, на которой видно, что гейты раздела вообще
работают. У ADMIN «*» проходит любую проверку, у прочих ролей не проходит ни
одна — обе крайности одинаково зелены и при сломанном RBAC (так и было под
мок-wildcard-ом). Закреплено тестом
`test_the_ops_reader_holds_two_registers_and_not_the_third` (красная проба:
добавление `event.view` в раскладку роняет тест).

**ОТКРЫТОЕ (решение за владельцем продукта):** портированные роли по-прежнему
не несут чтения раздела ОМ — держатель `object.view`/`duty.view` теперь один
(`OPS_READER`), `event.view` не достался никому напрямую. Кому в проде
полагается видеть реестр ОМ, план дежурств и объекты — продуктовое решение, не
догадка разработчика.

### Два предупреждения сюиты — одно из них был латентный дефект (12.08.2026)

13. **Список отчётов пагинировался без порядка.** `Report.Meta` не задавал
    `ordering`, а `/api/reports/` отдаётся пагинатором DRF: раскладку по
    страницам выбирал планировщик, поэтому одна и та же запись могла прийти
    дважды или не прийти вовсе. Django предупреждал ровно об этом
    (`UnorderedObjectListWarning`), но предупреждение тонуло в сводке.
    Порядок задан МОДЕЛЬЮ — `['-created_at', '-id']`; `-id` обязателен
    вторым ключом: `created_at` это `auto_now_add`, и записи одной транзакции
    делят штамп до микросекунды. Пин литеральный (`_meta.ordering`) плюс
    проба tie-breaker-а на записях с принудительно равным `created_at` —
    поведенческая проба на паре записей вакуумна, планировщик и без ordering
    обычно отдаёт их в порядке вставки. Красная проба: `ordering = []`
    роняет и новый тест, и `test_list_visibility_scopes`.

14. **`CheckConstraint.check` → `condition`** (Django 6.0 убирает `check`) в
    `dictionaries/models.py` (`ck_position_code_not_blank`,
    `ck_rank_code_not_blank`) и в применённой миграции
    `0003_position_rank_code`. Переименование состояние не меняет —
    `makemigrations --check` не видит расхождений, лишней миграции нет.

Сюита после правок: **2995 passed, предупреждений НЕТ** (было 2994 и пять
предупреждений).

### Фоновый рефетч затирал открытую форму (коммит `53658a6d`, 14.08.2026)

Модалка правки статуса (`EditStatusDialog`) засевала поля с сервера в эффекте
с данными штатки в зависимостях. Данные там нужны — диалог открывается раньше
их загрузки, — но эффект прогонялся заново на КАЖДОМ обновлении запроса
`staff-units-by-directorate`: кнопка «Обновить», `invalidateQueries` после
чужого действия, массовая правка. Выбранные пользователем статус и даты молча
возвращались к серверному снимку.

Ловушка воспроизведения: React Query отдаёт ПРЕЖНЮЮ ссылку, если данные не
изменились (structural sharing), поэтому «просто нажать Обновить» дефект не
показывает — красная проба обязана менять данные на сервере. Проба: открыть
модалку, выбрать другой статус, завести сотруднику статус через API, нажать
«Обновить». С гардом форма держит введённое (таблица под модалкой при этом
обновляется — рефетч реально дошёл), без гарда перескакивает на серверный.

Лечение — засев один раз на открытие (`seededForRef` по `employeeId`, сброс
при закрытии). То же в `EditProfileDialog`: объект `user` пересоздаётся на
каждом обновлении сессии NextAuth, в том числе фоновом по возвращении фокуса
на вкладку.

### Тот же дефект в карточке ОМ — через ключ монтирования (коммит `7c560dc6`)

`app/security-ops/events/[id]/page.tsx` монтировал форму этапа с ключом
`${event.stage}-${event.updatedAt}`: любое изменение данных ОМ пересобирало
компонент и сбрасывало локальное состояние формы. Своя же мутация в соседней
панели (журнал штаба в «Проведении», импорт постов в «Рекогносцировке») или
чужая правка возвращали набранное к серверному снимку. Ключ теперь — этап.

Ловушка при проверке: повторный импорт постов идемпотентен («Все посты этой
версии паспорта уже в расчёте»), `updatedAt` не меняется — форма выживает и
на дырявом коде. Чтобы проба была не вакуумной, серверное состояние должно
реально измениться: сохранить рекогносцировку с нулём постов, потом
импортировать.

Побочное следствие: импорт на этой пересборке и держался — ответ мутации
теперь переносится в форму явно (`onEvent` у стадийных мутаций).

### Три модуля прототипа перенесены без бэка (14-15.08.2026)

Коммиты `28eb2588` (Реестр ГВО), `4a602ecb` (Охраняемые лица), `144aac67`
(Законы об ОМ). Все три экрана прототипа Smart Josparlau не имеют серверного
хранилища, и это первый случай в разделе, когда врезка `api-gaps` ставится
БЕЗ пер-доменного переключателя: `isDomainLive()` по умолчанию отдаёт «живой»,
и домен без бэка, заведённый по общему шаблону, молча ушёл бы в сеть за 404.

Что стоит знать при подключении бэка:

* **Сводка ГВО — проекция, а не запись.** Персистится только патч ручных
  правок по коду ОМ; база каждый раз выводится из бюллетеня. Статус
  «Заполнена» = патч непуст, пустой патч не хранится вовсе — иначе «Вернуть
  исходные» не вернул бы черновик. Удаление лица или группы это тоже правка:
  статус остаётся «Заполнена», пока раздел не сброшен явно.
* **Связь «охраняемое лицо → ОМ» держится на ФИО в сводке ГВО.** Ссылки на
  лицо у `SecurityEvent` нет; сводка — единственное место, где лицо и
  мероприятие названы рядом. Переименование лица в сводке рвёт связь в
  каталоге молча.
* **Ловушка мок-слоя.** Паттерны handlers обязаны начинаться с `*`
  (``http.get(`*${PATH}`)``): в dev клиент бьёт по абсолютному `BACKEND_URL`
  (:8100), относительный путь резолвится от origin документа (:3106), а при
  `onUnhandledRequest: "bypass"` промах не падает ошибкой — запрос молча
  уходит в сеть. Признак: GET «работает» (пустой список выглядит нормально),
  а мутация тихо не доезжает.

Пробы (нужен `SMOKE_LIVE=1` и поднятый стенд): `e2e/gvo-sections.spec.ts`,
`e2e/protected-persons.spec.ts`, `e2e/legal-documents.spec.ts`.
