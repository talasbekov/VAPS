### Этапы 0–1 — Done (baseline, mock-runtime foundation, MSW bootstrap, persona/demo toolbar)

### Этап 2 (первый сквозной срез ОМ) — **Done**
Все 6 стадий базового жизненного цикла ОМ реализованы и проверены и автотестами, и вручную в браузере от начала до конца одного сценария:

**Бюллетень** → **Рекогносцировка** (чек-лист 6 пунктов + посты/секторы) → **Потребность** (строки расчёта, утверждение с авто-агрегацией в запросы группам) → **Запрос сил** (ручное выделение, статусы NOT_SENT/PARTIALLY/ALLOCATED) → **Расстановка** (назначение/снятие сотрудников на посты, hard-rule двойного назначения, read-only кадровый ростер через `GET /api/ops/personnel/`) → **Согласование** (утвердить / вернуть на доработку с причиной, откат стадии).

- `SecurityEvent` — полная модель (bulletin/recon/demand/forces/placement/approval поля).
- Repository: 15 доменных операций (list/get/create/updateBulletin/updateRecon/completeRecon/approveDemand/updateForceAllocation/completeForces/assignPlacement/unassignPlacement/completePlacement/approvePlacement/returnPlacement), все с permission-check + server-like валидацией + атомарными мутациями.
- `SecurityEventDetailPage` ветвится по `event.stage` — единый паттерн для всех 6 стадий, честные read-only сводки для не-текущих стадий (не мёртвый контент).
- **Найдено и исправлено 2 реальных бага** при браузерной проверке (не гипотетических): (1) `DemoClock.advanceMs()` терял таймзону, нормализуя в UTC — переписан на epoch+offset; (2) `ensureSeeded()` не ловил дрейф ФОРМЫ существующего слайса при добавлении новых полей — добавлено `SCHEMA_VERSION`-версионирование с безопасным полным reset. Оба закрыты тестами (`demo-clock.test.ts`, `demo-runtime.test.ts`).
- Сознательно НЕ реализовано (см. `FRONTEND_DECISIONS.md` A15-A18): межсобытийные конфликты (Epic 16.3), точный подсчёт need vs assigned (демо-ростер мал), материалы/фото рекогносцировки (нет blob-хранилища).

### Этап 3 (остальной жизненный цикл ОМ) — **Done**
Оставшиеся 3 стадии реализованы поверх Этапа 2, доведены до `CLOSED` (терминал):

**Согласование** (утверждение → авто-переход в «Ознакомление», без промежуточного клика; возврат → откат в «Расстановка») → **Ознакомление** (каждое назначение подтверждается индивидуально; переход в «Проведение» разблокирован только когда ВСЕ назначения подтверждены) → **Проведение** (журнал штаба: инструктаж/распоряжение/инцидент/замена — добавление без редактирования/удаления, хронологический append-only) → **Закрыто** (обязательные итоги по КАЖДОМУ направлению из `reconSectorPosts.sector`, терминальная стадия — read-only сводка).

- `SECURITY_EVENT_STAGES` расширен до 9 значений; `SCHEMA_VERSION` поднят до 5 (backfill demo-данных старой формы через safe-reset).
- Repository: +4 операции (`acknowledgePlacement`, `completeAcknowledgement`, `addJournalEntry`, `closeSecurityEvent`) — итого 19, все permission-check + server-like валидация + атомарные мутации.
- `StageTracker` переведён с хардкод `grid-cols-6` на динамическую сетку по `SECURITY_EVENT_STAGES.length` (иначе визуально ломался на 9 стадиях).
- `ApprovalPanel`: убрана мёртвая ветка `approvalStatus === 'APPROVED'` — недостижима с автопереходом (approve/return теперь ВСЕГДА уводят со стадии APPROVAL, `PENDING` — единственное видимое состояние).
- **Найден и исправлен реальный баг** при браузерной проверке: `securityEventAcknowledgePath` и `securityEventAcknowledgementCompletePath` использовали общий сегмент `acknowledgement/`, из-за чего path-to-regexp у MSW матчил `POST .../acknowledgement/complete/` через РАНЕЕ зарегистрированный роут `.../acknowledgement/:assignmentId/` (assignmentId="complete") → 404 от не того handler'а. Фикс: индивидуальное подтверждение переименовано в `.../acknowledge/:assignmentId/` (разные сегменты для разных операций).
- Сознательно НЕ реализовано: опрос по факту и оценки участников (Epic 18.3, hidden-score) — см. `FRONTEND_DECISIONS.md`; архив ОМ (отдельный список закрытых, вне текущего Reestr) — Not started.
