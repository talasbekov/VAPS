## 6. Расхождения с прототипом — что упустили

Свежий обход 12 маршрутов против 16 эталонных слайдов `docs/screens/Smart Josparlau скрины/screenshots/slides/`. Список ниже — не претензия к слою оформления (палитра/плотность/каркас там, где есть общий состав, совпадают убедительно), а инвентаризация оставшихся зазоров:

1. **`/security-ops/daily-expense` («Расход дня») сильно уже прототипа «Расход и светофор» (13-rashod-svetofor.png) по составу.** У нас — форма выбора подразделения + дата + кнопка «Сдать день», пусто до выбора. В прототипе — сразу видны KPI-плитки (подразделений/сдали/черновик/не сдали), дерево подразделений со статусами сдачи по каждому узлу, панель версий выпуска и история. Это не вопрос оформления (карточки/шрифты уже в системе) — не хватает самого функционала агрегации. По памяти проекта (`project_reports_expense_aggregator`) это известное направление, отдельное от слоя прототипа.

2. **`/security-ops/analytics` — другой продукт, не клон «Аналитика ОМ» (11-analitika-om.png).** У нас страница называется «Аналитика службы» и построена вокруг численности/укомплектованности/дежурств — обширный, содержательный экран, но с иным набором виджетов (нет донат-диаграммы «Структура мероприятий», нет карточек «Инциденты»/«Мероприятия с проблемами», нет фильтров «Все объекты/Все департаменты»). Оформление карточек и таблиц при этом системное. Похоже, продукт разошёлся с прототипом по составу данных задолго до этого слоя — фиксирую факт, не относя к задачам плана.

3. **`/security-ops/persons` («Охраняемые лица») — фото-плейсхолдеры вместо портретов.** Структура карточек (имя, позывной, описание, две кнопки справа) совпадает с прототипом почти дословно, но там, где в прототипе круглые фотографии людей, у нас серый прямоугольник с подписью «Фото». Ограничение мок-данных, не оформления.

4. **`/security-ops/command-center` — упрощён относительно «Командного центра» (01-komandnyy-tsentr.png).** У нас 4 KPI-плитки без иконок и список «Ближайшие мероприятия» с прогресс-барами — само по себе аккуратно оформлено. Но в прототипе есть вторая колонка («Требует решения» со счётчиком эскалаций, «Карта готовности подразделений» цветными карточками по департаментам, мини-график «Нагрузка» за 14 дней) и надзаголовок раздела сверху («КОМАНДНЫЙ ЦЕНТР») — этого функционала нет вовсе, не только визуально. KPI-плитки прототипа несут иконки (люди/щит/пульс/человек), у нас — только точка-индикатор и число.

5. **`/security-ops/ratings` («Оперативный рейтинг») не имеет аналога среди 16 слайдов прототипа.** Экран не сверить напрямую — он развился как отдельная функция проекта (вкладки «Сводка/Оценивание/Итоговые оценки/Выгрузка/Журнал/Аналитика», таблица с состояниями расчёта, график динамики по сотруднику, два текстовых блока «Что в расчёт не входит»/«Что не показывается»). ## 8. Правки по итогам финальной проверки

Три находки из §3/§4/§5 (регрессии 1 и 2 — наши, внесены этим же слоем; находка 3 — точечная). Правки внесены отдельной сессией поверх HEAD `4011eed9`, стенд не поднимался заново.

### Находка 1 — actions-слот `PageHeader` обрезался на 375px

**Красная проба (до правки).** Добавлен `data-slot="page-header-actions"` на обёртку actions в `components/page-header.tsx` и два новых теста в `e2e/prototype-skin.spec.ts` (`actions-слот PageHeader не обрезается на 375px: /employees/` и `.../statuses/`), проверяющие `getBoundingClientRect().right` блока actions и кнопки внутри против ширины вьюпорта (375px). На исходном коде (`shrink-0` без `min-w-0`) тест на `/employees/` **упал**:

```
Error: на /employees/ блок actions уходит за правый край вьюпорта (375px): right=498.40625
Expected: <= 375
Received:    498.40625
```

(`/statuses/` на исходном коде уже проходил — там в actions только бейдж + одна кнопка, контента меньше; регрессия воспроизводится не на каждой странице с `PageHeader`, а там, где actions тяжелее по контенту — это и объясняет, почему баг не был замечен раньше.)

**Правка.** `components/page-header.tsx`, обёртка actions:

```diff
- {actions ? <div className="flex shrink-0 items-center gap-2">{actions}</div> : null}
+ {actions ? (
+   <div
+     data-slot="page-header-actions"
+     className="flex w-full min-w-0 flex-wrap items-center gap-2 sm:w-auto sm:shrink-0"
+   >
+     {actions}
+   </div>
+ ) : null}
```

Почему так: `shrink-0` изначально не давал кнопкам сжиматься в кашу на умеренной ширине — этот эффект нужно было сохранить, а не просто снять. На узком экране (`< 640px`, ниже `sm:`) блок теперь `w-full` — занимает всю ширину строки и переносится на свою строку под заголовком (родитель — `flex flex-wrap`), а `flex-wrap` внутри самого actions-блока даёт кнопкам перенос на несколько строк, если даже полной ширины экрана не хватает. `min-w-0` снимает нижнюю границу intrinsic-ширины по контенту (баг был в этом: `shrink-0` без `min-w-0` в `flex-wrap`-контексте не давал блоку сжаться меньше суммы intrinsic-ширин детей). От `sm:` (640px) и выше — `w-auto sm:shrink-0`, поведение идентично исходному.

**После правки** оба новых теста проходят:

```
✓ actions-слот PageHeader не обрезается на 375px: /employees/
✓ actions-слот PageHeader не обрезается на 375px: /statuses/
```

Замерено на живом стенде (`getBoundingClientRect`):
- `/employees/`, 375px: блок actions `x=16, width=343` → правый край 359px (в пределах вьюпорта), внутри 3 строки (бейдж + 2 кнопки перенеслись).
- `/statuses/`, 375px: блок actions `x=16, width=343` → правый край 359px.
- `/employees/`, 1440px: блок actions `width=481.8px`, высота 36px — одна строка, как и до правки (`sm:shrink-0` вернул исходное поведение).

### Находка 1 — глобальный CSS протекал на все таблицы приложения (критично)

**Причина.** `features/organization-structure/ui/org-board.styles.css` — обычный (не CSS Module) `.css`, импортированный из `OrgBoard.tsx`. Правила `tbody td`, `table`, `td:empty` не были нискольку скоуплены. Механика утечки — App Router: чанк маршрута `/dashboard/` (там смонтирован `OrgBoard`) дописывает эти правила в документ при клиентской навигации и не снимает их при уходе с маршрута. После клика по пункту меню на любую другую страницу (например `/employees/`) правила оставались в силе и красили её таблицы: чёрная рамка ячеек (`border: 1px solid #000`) и `min-width: 140px`.

Дефект маскировал себя: сам `OrgBoard` несёт на `TableCell` `border border-border` (специфичность `(0,1,0)`), которая перебивает `tbody td` `(0,0,2)`. У всех остальных таблиц (`components/ui/table.tsx:91-103`, базовый `TableCell`) нет собственного `border-*`/`min-w-*` — на них глобальное правило применялось в полный рост.

**Обнаружена также мёртвая копия** `components/org-board.styles.css` — идентичный по содержанию файл, ни разу не импортированный (сверено грепом). Удалена вместе с основным.

**Красная проба.** Добавлен тест `e2e/prototype-skin.spec.ts` → «переход с /dashboard кликом не красит таблицу /employees чужим CSS»: заходит на `/dashboard/`, дожидается видимой таблицы (носитель утечки смонтирован — чанк загружен), переходит на `/employees/` **кликом** по пункту меню «Управление персоналом» (не `page.goto` — обычная навигация не ловит утечку, потому что js-чанк `/dashboard/` тогда вообще не грузится), затем проверяет `borderBottomColor` и `minWidth` первой ячейки таблицы сотрудников.

На исходном коде (до правки) проба падала:
```
Error: ячейка таблицы /employees закрашена рамкой org-board.styles.css
(утечка нескоупленного tbody td): rgb(0, 0, 0)
```

**Правка.** Единственное реально нужное из глобального блока — `min-width:140px` и `overflow:hidden` на ячейках самой доски (`padding` перебивался собственным `px-4 py-3`, `border` — собственным `border-border`, `table { width:100% }` дублировал `w-full` примитива). Перенесено в `className` обоих `TableCell` в `OrgBoard.tsx` (`min-w-[140px] overflow-hidden`), импорт и оба CSS-файла удалены.

После правки проба зелёная.

### Находка 2 — вакуумная проба «контролы фильтров одной высоты»

Тест проверял совпадение вычисленных высот всех контролов в `FilterBar`, но каждый контрол уже нёс `h-9` сам по себе в разметке (`Input` — в базовом классе, оба нативных `<select>` реестра ОМ — инлайн в `app/security-ops/events/page.tsx`, кнопка — через `size="default"`). Правило самого `FilterBar` (`[&_button]:h-9 [&_input]:h-9 [&_select]:h-9`) можно было снести целиком — проба осталась бы зелёной, потому что сверяла совпадение дефолтов детей, а не действие компонента.

**Правка.** Снят инлайновый `h-9` с `<select aria-label="Этап">` в `app/security-ops/events/page.tsx` — теперь его высоту навязывает исключительно `FilterBar`. Красная фаза проверена вручную: с пустым `className` у `FilterBar` тест падал (`высоты контролов: 36, 23`, `select` без ряда просел до 23px), с восстановленным — проходит.

Заодно поднят порог числа контролов с `toBeGreaterThan(0)` до `toBeGreaterThan(1)` — на единственном контроле `toHaveLength(1)` истинно тривиально и ничего не доказывает.
