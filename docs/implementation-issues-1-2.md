# Доработка GitLab issues #1 и #2

Дата: 24.09.2026. Основание: описания issues и UC-REF-001 / UC-ADM-006
из указанных в них веток. Продолжена локальная работа после коммита `0e667c3`.
Изменения находятся в рабочем дереве; публикация в GitLab не выполнялась.

## Справочники — #1

- Продолжена существующая реализация отдельного права `dictionary_value.manage`,
  корректирования, исторической замены и удаления/деактивации ОМ, должностей и званий.
- Добавлены страны и города с теми же операциями, двуязычными названиями,
  счётчиками связей и аудитом. Используются существующие записи географии мероприятий.
  Корректирование географии обновляет также сохранённый текст места мероприятия.
- Единый перечень справочников с поиском; таблица значений показывает названия RU/KZ,
  активность, ссылки, последнюю операцию, дату, автора и дату неактуальности.
  Доступны фильтры активности и использования, выбор записи для действий.
- Поиск похожих при создании: нормализация Unicode, регистра и пробелов,
  сравнение обоих языков; для строк от четырёх символов порог SequenceMatcher 0.85.
  Показывается до 20 совпадений. Клиент предлагает открыть существующую запись
  либо явно подтвердить создание. Ошибка сохранения не стирает введённые значения.
- Код после создания неизменяем; неактивную запись нельзя корректировать.
  Аудит операций включает тексты записей, при замене — также преемника.
- API списка возвращает `replacementFamily`: корень, звенья цепочки,
  текущее значение и суммарное число ссылок. Сумма показывается в таблице.
  Сохранён прежний формат пагинации кадровых справочников.

## Учётки и область доступа — #2

- Сводка отсутствий использует область `status.view`, включая поддерево,
  и работает без привязки учётки к сотруднику.
- Чтение подразделений требует `orgstructure.view` и ограничивается областью.
  Дерево для администратора доступа доступно целиком; остальным — по области,
  без раскрытия скрытых родителей и соседних подразделений.
- В API учёток и на странице пользователей добавлена привязка к сотруднику,
  поиск кандидатов, снятие связи и аудит `ACCESS_ACCOUNT_EMPLOYEE_LINKED`.
  Занятого сотрудника перепривязать нельзя; изменение выполняется в транзакции
  с блокировкой строк. Отсутствие поля в PATCH не снимает существующую связь.
- При выдаче роли проверяется существование пользователя. Роль с правом `*`
  нельзя выдать с ограниченной областью; интерфейс выбирает «Вся служба».
- Права перечитываются при возврате фокуса окна. Добавлены предупреждения
  о пустой роли и объяснение, что отключение роли/права не отзывает выдачи.
- Удалён неиспользуемый `scripts/create_users.py`, в том числе из обновляемого образа.
- Уже имевшиеся ограничения кадровых статусов, мутаций подразделений и
  HTTP-аудита сохранены. Добавлены проверки областей, кадровой связи,
  выдачи ролей и соответствия прав меню серверному каталогу.

## Принятые допущения и оставшиеся границы

Это решения для совместимости, а не полученное согласование заказчика:

1. Казахское название поддерживается, но пока необязательно; автоматического
   перевода старых данных нет. Дата и автор старого изменения без аудита
   показываются как неизвестные, не восстанавливаются предположением.
2. Связь учётки с сотрудником необязательна для технических учёток.
   Область сводки определяется грантом, а не кадровой связью.
3. Право `dictionary_value.manage` автоматически выдаётся `REFERENCE_ADMIN`
   существующей миграцией; остальные держатели `dictionary.manage` не получают
   его автоматически. Архивные справочники не возвращаются, статусы остаются read-only.
4. Охраняемые лица и законы доступны ссылками на специализированные реестры;
   их предметная модель, права и операции не переведены на общий механизм замен.
5. Область реестров ОМ по департаменту-владельцу не добавлена: в задании это
   открытый вопрос, требующий определения владельца и миграции данных.
6. Глобальное снятие `is_superuser` в переходных модулях не выполнено.
   Задание предусматривает его поэтапно при переносе модулей на права раздела;
   обычный API учёток не позволяет назначать этот флаг.
7. Цепочки замен агрегируются в API и таблице справочника. Отдельные бизнес-отчёты
   и дашборды с группировкой по цепочкам в эту доработку не добавлены;
   конкретные показатели и экраны для такой группировки требуют определения.
8. Интерфейс использует единый перечень и отдельные страницы значений.
   Постоянная двухколоночная компоновка «перечень слева, значения справа»
   из полного UC не реализована.

По этим причинам отчёт не означает безусловное закрытие всех пунктов полного UC.
