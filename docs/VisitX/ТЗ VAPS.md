## 1. Контекст и цель проекта

**Проблема.** Ежедневный учёт расхода личного состава и подготовка охранных мероприятий ведутся вручную: звонки, мессенджеры, бумага, разрозненные Excel/Word/PDF, память конкретных людей. Нет единого источника правды о том, кто где задействован; своды расходятся со списочной численностью; история теряется; нет цифрового следа решений; перегрузка людей не видна системно (PS §1; VX §1; PR §1.2).

**Цель.** Единая цифровая среда, в которой:

- у каждого сотрудника на каждую дату есть один однозначный статус с цифровым следом (PS §2);
- ежедневные дежурства и охранные мероприятия сведены в **одну картину расхода ЛС и карту нагрузки** (PR §1.2, §4.1);
- каждое действие оставляет цифровой след (VX §2; PS §2);
- руководство в любой момент получает актуальный, корректный, юридически значимый документ расхода (PS §2, §30).

**Для кого** (PR §1.3): руководство Службы; начальники СПС/подразделений; старшие объектов ОМ; ГАП СПС и распределяющие ЛС; сотрудники; контролирующие/проверяющие.

**Принцип объект-центричности (PR §4.1, BS A2).** В центре модели — **Объект** (постоянная сущность с паспортом). От объекта расходятся два направления службы: **ежедневные дежурства** (планируются на месяц вперёд, базовая нагрузка) и **охранные мероприятия** (планируются заново под каждый выезд ОЛ). Оба направления задействуют одних людей и сходятся в общем расходе ЛС и карте нагрузки.

**Целевая архитектура продукта (BS Фаза 2, Ось 3).** Модульный монолит на Django:

```
core/             # Сотрудник, Должность, Звание, Оргструктура (кэш из КУ), общие справочники
talent/           # Рейтинги отношений, OKR, навыки, кадровый резерв, поощрения, аналитика по людям
operations/       # Статусы, объекты, дежурства, ОМ, группы, расстановка, нагрузка, оценки, расход .docx
  objects/  duties/  events/  groups/  load/  ratings/
integration_ku/   # Sync с кадровой системой (КУ); на MVP — заглушка (Admin + сидер)
integration_auth/ # Middleware валидации JWT внешнего Auth-сервиса
```

> Примечание о происхождении: PS как самостоятельный концепт описывал «систему ежедневного расхода». В BS («Стратегический пересмотр») PS переопределён в **Talent & Performance**, а статусы и расход .docx перенесены в `operations`. Это переопределение зафиксировано как противоречие 10.C7 и открытый вопрос 11.OQ-12.

### 3.2. Служебная роль на дату (не роль доступа)

У каждого сотрудника на конкретную дату есть **служебная роль** (чем занят): в ОМ (старший объекта/сектора, на посту, в составе группы) либо вне ОМ (на дежурстве, отдых после дежурства, дежурный по КХО и иные). Любая служебная роль учитывается в общем расходе ЛС (PR §5.1).

### 3.3. Дежурство как срочное полномочие на личную учётку (BS Ось E)

Дежурства (ОМД/ОРГД) моделируются как `DutyAssignment(user, роль, с 08:00, по 08:00 след. дня)` на **личную** учётку (не общий логин); права роли включаются на срок и авто-гаснут, что даёт аудит «кто именно был дежурным». Один ОМД на сутки на все ОМ дня (BS Ось E, п.3–4).

### 3.4. Смежные государственные органы (ГО1…ГО5)

Могут предоставлять ЛС, технику, собственные расстановки, подписанные PDF/сканы; даже не работая в системе напрямую, их документы прикрепляются к делу ОМ (VX §3.7, §6.4, §22.2).

### 3.5. Внешние системы

- **Кадровая система (КУ)** — эталон ФИО/должности/звания/подразделения и длительных статусов; через неё вход (PR §3.1; BS Фаза 2). На MVP — заглушка `integration_ku` (BS Фаза 4, этап 0.6).
- **Auth-микросервис** — единственный источник аутентификации и ролей; VAPS — потребитель чужой identity, своих users не хранит (BS Ось 4/12).

## 4. Функциональные требования

> Формат каждой функции: **вход → процесс → выход → бизнес-правила → краевые случаи**. ID вида `FR-<модуль>.<функция>`.

### Модуль 1 — Идентичность, оргструктура, штатное расписание (core)

**FR-1.1. Поддержка гибкой оргиерархии.**

- Вход: тип узла (организация/департамент/управление/отдел/группа), наименование, код, родитель, ответственный руководитель, признак активности, описание.
- Процесс: построение дерева; каждый узел ссылается на родителя через `parent`.
- Выход: дерево подразделений + орг-диаграмма.
- Правила: поддерживаются варианты подчинённости — Орг→Деп→Упр→Отдел→Сотр; Орг→Упр→Отдел→Сотр; Орг→Отдел→Сотр; Орг→Упр→Сотр; Орг→Деп→Упр→Сотр; ветка может доходить до Орг→группы (PS §4.1; BS Ось A «контекст оргструктуры»). Управление может не входить в департамент; отдел — не входить в управление (PS §4.1).
- Краевые: временные структурные единицы на период проекта (PS §4.3).
- **Владелец данных по PR §3.1 — КУ**; в системе оргструктура временно ведётся как кэш/фасад до прихода КУ (BS Фаза 2). См. противоречие 10.C6.

**FR-1.2. Доступ к дереву.** Быстрый доступ к прямым/всем потомкам, пути от корня, высоте поддерева, числу сотрудников в поддереве (PS §4.5).

**FR-1.3. Штатная единица (ставка).** Пара «подразделение+должность»; порядковый номер; привязка 1:1 к сотруднику ИЛИ вакансии; родительская ставка (дерево управления, отдельное от дерева подразделений); активность; даты создания/упразднения (PS §5.1).

**FR-1.4. Вакансия.** Состояние незанятой ставки: статус (открыта/закрыта), требования, обязанности, даты открытия/закрытия, причина (справочник), инициатор, комментарий. Закрывается при назначении сотрудника или явным действием (PS §5.2).

**FR-1.5. Назначение на ставку.** Выбор свободной ставки → привязка сотрудника → закрытие вакансии (дата+причина) → авто-статус «В строю» от даты приёма → запись в истории переводов (PS §5.3).

**FR-1.6. Освобождение ставки.** При переводе/увольнении/откомандировании (если предусмотрено)/упразднении: создаётся вакансия (если ставка сохраняется), фиксируется дата освобождения, запись «откуда→куда», обновление статуса (PS §5.4).

### Модуль 2 — Карточка сотрудника (core; единая, блоки по правам — BS Ось E)

**FR-2.1. Полная карточка (кадровый ракурс).** Состав: фото 3×4, ФИО, дата рождения, пол, табельный номер, должность, звание, подразделение, ставка, дата приёма, дата увольнения, служебный email, служебный телефон, статус занятости (действующий/уволен), текущий статус с периодом, история переводов, история статусов, документы, отметка о прикомандировании (PS §6.2).

**FR-2.2. Оперативный ракурс карточки.** Доп. поля: рост, телосложение, антропометрия, деловые качества, проф. навыки, опыт работы, опыт на ОМ, налёт часов, участие в прошлых ОМ, наличие оружия/спецсредств/формы/гражданской формы, знание объекта, замечания, рейтинг, поощрения, ограничения (VX §9.2).

- Правило: карточка одна; блоки скрываются по правам (BS Ось E, п.1).

**FR-2.3. Сокращённая (списочная) карточка.** Фото 3×4, ФИО, должность, текущий статус, подразделение. Чувствительные данные (телефон, email, дата рождения, служебные комментарии, документы) скрыты в списке (PS §6.3, §17.5).

**FR-2.4. История переводов.** Запись: сотрудник, из/в подразделение, дата, причина, тип перевода, инициатор, документ, комментарий (PS §6.4).

**FR-2.5. Увольнение.** Дата увольнения + причина (справочник) → архивный статус → освобождение ставки → карточка сохраняется для истории → исключение из списочной численности с даты (PS §6.5).

- Краевой: карточка после увольнения не удаляется (PS §28 п.29).

**FR-2.6. Подбор под пост.** Подсказки соответствия сотрудника требованиям поста (допуск/оружие, рост/внешний вид/опыт, гражданская форма и т.п.) (VX §9.3).

### Модуль 3 — Справочники (core)

**FR-3.1. Должности.** Наименование, `level` (меньше = выше), порядок сортировки, активность, опц. привязка к типу подразделения. Базовый перечень из 20 позиций (PS §7.1). Редактируется без изменения кода.

**FR-3.2. Звания.** Наименование, `level`, категория (мл./ср./ст./высш. начсостав), активность (PS §7.2).

**FR-3.3. Типы статусов.** Код, наименование, «требует периода», «по умолчанию», «исключает редактирование», область видимости (орг/деп/упр), цвет, приоритет в выгрузке (PS §7.3). Допускаются кастомные статусы подразделений и составные статусы (PS §8.1).

**FR-3.4. Справочники причин.** Причины увольнения, перевода, открытия вакансии, досрочного завершения статуса, отмены планового статуса; каждая — наименование, активность, комментарий (PS §7.4).

**FR-3.5. Справочник групп.** Наименование/специализация, состав/численность, задачи; на пост/задачу можно назначить группу целиком или отдельного сотрудника (PR §6.4; VX §3.3).

### Модуль 4 — Статусы сотрудников (ядро; PS §8 + PR §3.1)

**FR-4.1. Перечень статусов и владение.**

- Базовый перечень PS (PS §8.1): В строю (по умолчанию), На дежурстве, После дежурства, В командировке, Учёба, Соревнования, Конференция, В отпуске, Отпуск по рапорту, На больничном, Прикомандирован, Откомандирован.
- Владение по PR §3.1: **КУ** владеет — отпуск, больничный, командировка, учёба, соревнования, прикомандирование, откомандирование (длительные → недоступность); **система** владеет — боевое дежурство (БД), отдых после БД, ГЭВ и иные оперативные.
- Дополнительно (VX §10.1): пример общих и специальных статусов техдепартамента (связист, мини-штаб, ИКИ, ИБ, ИТСО, ПДТР, купол, аэроразведка, Алмаз, Рубин, Янтарь, сакшы/бекет кундизги-тунги).
- Правило: «В строю» — статус по умолчанию (PS §8.1); запрет «пустого» статуса (PS §8.8). См. противоречие 10.C1 и открытый вопрос 11.OQ-2 (куда ГЭВ/учёба/соревнования).

**FR-4.2. Статус-как-интервал.** Статус хранится диапазоном дат + `source` (USER / KU_SYNC / OM_AUTO) для аудита; расход на день вычисляется на запрошенную дату; планирование наперёд — в основе модели (BS Ось «Жизненный цикл», Ось 1).

**FR-4.3. Жизненный цикл состояний.** PLANNED → ACTIVE → COMPLETED / CANCELLED (PS §8.2).

**FR-4.4. Автоматические переходы.** 00:01 — PLANNED со `start_date=сегодня` → ACTIVE; 00:15 — ACTIVE c `end_date<сегодня` → COMPLETED; каждый переход → запись истории (AUTO_APPLY/AUTO_COMPLETE), опц. уведомление, пересчёт сводных (PS §8.4, §21.2–21.3). Next-day откат после ОМ — авто (BS Ось A п.5).

**FR-4.5. Продление (extend).** Новая дата окончания + причина + опц. документ; запись «было/стало»; состояние не меняется (PS §8.5).

**FR-4.6. Досрочное завершение (terminate).** Факт. дата окончания ≤ сегодня + причина + опц. документ → COMPLETED; запись TERMINATED; опц. уведомление (PS §8.6).

**FR-4.7. Отмена (cancel).** Только если PLANNED и дата начала не наступила → CANCELLED; не учитывается в сводках; запись CANCELLED; не удаляется из архива (PS §8.7).

**FR-4.8. Документы-основания статуса.** Несколько на один статус; запись: наименование, автор загрузки, дата, файл (PDF/JPG/PNG/DOCX), описание (PS §8.9).

**FR-4.9. История изменений статуса (цифровой след).** Типы CREATED/APPLIED/EXTENDED/TERMINATED/COMPLETED/CANCELLED/MODIFIED; запись: статус, тип, старое/новое значение, инициатор, дата-время, IP, комментарий; неудаляемо (PS §8.10).

### Модуль 5 — Объект, паспорт, посты, секторы, чек-лист (operations/objects)

**FR-5.1. Объект и паспорт.** Объект — постоянная сущность. Паспорт: наименование/тип, посты, секторы, проблемные места, чек-лист, привлекаемые группы, история изменений (что/когда/кем) (PR §6.1). Расширенный состав паспорта (VX §18.3): адрес, ответственное лицо, схемы объекта/эвакуации, входы/выходы/служебные входы, подъездные пути, парковки, зоны посадки/высадки, лифты, лестницы, крыши, подвалы, техпомещения, видеокамеры, электроснабжение, вентиляция, связь, интернет, уязвимые места, высотные здания рядом, общественные зоны, места скопления, ремонтные работы, история мероприятий/инцидентов/расстановок, документы, фото.

- Правило: объекты различаются частотой ОМ (частые → расстановка меняется мало; редкие → рекогносцировка заново) (PR §6.1).

**FR-5.2. Пост.** Задачи поста, особенности, тип (наружный/внутренний), предельное время несения без смены, требования по антропометрии, требования к рейтингу (PR §6.2). Задачи+особенности доводятся при уведомлении = предварительный инструктаж (PR §6.2, §8.5).

**FR-5.3. Предельное время поста.** Зависит от типа поста, времени суток/года, погоды; основа сменяемости; сравнивается с фактическим временем (опрос по итогам ОМ) → при превышении отметка перегрузки (PR §6.2.1, §9.2). См. открытый вопрос 11.OQ-5.

**FR-5.4. Сектор.** Зона ответственности из нескольких постов; старший сектора (PR §6.2; VX §8.2).

**FR-5.5. Чек-лист объекта.** Типовой единый чек-лист + дополнение/правка под объект. Итог прохождения: подтвердить расчёт постов/секторов ИЛИ внести изменения; решение и обоснование фиксируются (PR §6.3). = механизм рекогносцировки (PR §8.2).

**FR-5.6. Обновление паспорта.** До начала каждого ОМ ответственные направления обновляют паспорт (распределение по департаментам в VX §18.4). Красный статус при незаполненных обязательных полях; ОМ не закрывается без обязательных данных (VX §18.5, §25.4).

### Модуль 6 — Ежедневные дежурства (operations/duties)

**FR-6.1. Виды дежурств вокруг объекта.** Дежурства привязаны к объекту; создаются виды дежурств (PR §7.3).

**FR-6.2. Планирование на месяц вперёд.** На каждые сутки определяется, кто заступает; при планировании — проверка доступности (FR-8.x конфликты) (PR §7.3).

**FR-6.3. Посменность и обязательный отдых.** Заступил на сутки → следующие сутки обязательный отдых; после суток дежурства сотрудник **недоступен для любого назначения** (ни дежурство, ни ОМ) (PR §7.2). См. открытый вопрос 11.OQ-3 (абсолютный блокер vs soft warning).

**FR-6.4. Авто-статусы дежурства.** На сутки — «на дежурстве», на след. сутки — «отдых после дежурства»; попадают в общий расход ЛС (PR §7.3). Дежурства — базовая картина, поверх которой накладываются ОМ (PR §7.1).

### Модуль 7 — Охранное мероприятие: полный цикл (operations/events)

**Канонический поток — 8 шагов (PR §8; разворот процессов — VX §4–17):**

**FR-7.1. Создание ОМ вокруг объекта.** ОМ всегда привязано к объекту (паспорт даёт посты/секторы/проблемные места). Назначается старший объекта (PR §8.1).

- Доп. поля карточки ОМ (VX §4.2): название, тип, дата, время, место, объект(ы), основание, организатор, ОЛ, формат участия, программа, уровень важности, потребность в силах/транспорте/аккредитации/Face ID, ответственные подразделения, старший наряда, статус подготовки.
- Статусы ОМ (VX §4.1): Черновик → Бюллетень создан → Предв. подготовка → Назначен ст. наряда → Рекогносцировка → Ожидаются расчёты → Расчёты частично/полностью → Формируется расстановка → На согласовании → Возвращено → Подписано → Готово → В работе → Завершено → Ожидает закрытия → Закрыто → Архив.

**FR-7.2. Информационный бюллетень.** Стартовый документ ОМ: описание, дата/время, объект, ОЛ, программа, направления, первичные задачи, сроки, ответственные, перечень документов; запускает подготовку расчётов (VX §4.3).

**FR-7.3. Рекогносцировка и планирование.** Старший объекта проходит чек-лист (FR-5.5) → подтверждает или корректирует расчёт постов/секторов; контролирующие руководители могут править расчёт (двойной контроль) (PR §8.2). Результат предв. рекогносцировки (VX §5.2): объекты, зоны, предв. посты, потребность в наружн./внутр. секторах, БВС, ПДТА, Мерген, боевых группах, физнаряде, сотрудницах, технике, предв. риски, примечания.

**FR-7.4. Расчёт и утверждение потребности.** Система формирует Потребность (необходимое число сотрудников от каждого СПС/группы) из закрываемых постов/задач; уточняется и утверждается старшим объекта и контролирующими; после утверждения — основание для запроса (PR §8.3).

- Распределённый расчёт (VX §6.1–6.3): каждое направление само вносит свой блок (объект, направление, кол-во сотрудников/групп/техники, старший, обоснование, риски, документы, статус); расчёт физнаряда — с полами, формой, оружием, спецсредствами, временем, точкой сбора, сектором, постом.

**FR-7.5. Уведомление и ознакомление.** Сотрудник в расстановке видит пост/задачи/особенности, ставит отметку ознакомления; старший видит, кто не ознакомился, и досылает (PR §8.5).

### Модуль 8 — Запрос, распределение, проверка конфликтов, замена

**FR-8.1. Двухуровневый брокеридж/запрос-распределение.**

- На основании утверждённой потребности система рассылает запрос группам (сколько и какой специализации) (PR §8.4).
- Группы выделяют конкретных людей; при выделении — проверка конфликтов (FR-8.4) (PR §8.4).
- Поток выделения на ОМ (BS Ось A): сотрудники со статусом «ОМ-физнаряд» видны ОМД → ставятся в расстановку напрямую; нужно больше → ОМД шлёт запрос брокеру департамента → брокер запрашивает управления → руководитель управления (или замещающий) выделяет людей. ОМД не берёт чужих сам — только через брокер ↔ руководитель управления.
- Правила (BS Ось A): прямой захват «физнаряда»; при конфликте нескольких ОМ за одного «физнаряда» ОМД решает сам; нехватка/избыток — система ничего не делает, ОМД работает с тем, что есть; возврат — на след. день авто-обновление участников на запланированный статус.
- Соответствие канону (PR A3): ОМД/ГАП ↔ механизм запроса/распределения протокола; роли ОМД/ОРГД — надстройка сессии (валидировать).

**FR-8.2. Запрос приданных сил у смежных органов.** Фиксируется: кому/кто направил, дата-время, основание, количество, тип сил/техники, ответ, выделенные ресурсы, документы (VX §6.4).

**FR-8.3. Дополнительный наряд (допнаряд).** Экстренное привлечение незапланированных; только по санкции руководства; фиксируется кто запросил/санкционировал, причина, откуда сняли, куда направили, срок, задачи, документ-основание; помечается как недополновый (VX §7).

**FR-8.4. Проверка конфликтов (soft warning + override).** При каждом назначении (дежурство или ОМ) система **предупреждает** о конфликте, но не блокирует — решение за тем, кто планирует; факт игнорирования пишется в историю расстановки (кто, когда, какой конфликт проигнорировал) (PR §8.6; BS A1).
Перечень проверяемых конфликтов (PR §8.6):

1. статус из КУ (отпуск/больничный/командировка/учёба/прикомандирование/откомандирование) → недоступен;
1. двойное назначение (уже на дежурстве или на другом ОМ в эту дату);
1. отдых после дежурства;
1. перегрузка (FR-12);
1. несоответствие посту (антропометрия/рейтинг).
   Доп. предупреждения VX §10.2 (ночь/нагрузка/оснащение/замечания).

- См. противоречие 10.C3 (было hard gating).

**FR-8.5. Каскадная замена (авто + ручной override).** Сотрудник недоступен → система предлагает следующего по штатной должностной цепочке (зам → и.о.), без тай-брейков по стажу/налёту/рейтингу; ответственный может выбрать вручную (BS Ось B).

- Граница: авто — только внутри управления; ручной выбор — в пределах подразделения 1-го уровня под организацией (департамент; или управление, если департамента нет); за границей — эскалация. Замещать можно любого сотрудника расстановки (BS Ось B).
- Требование: система должна знать иерархию должностей, а не только подразделений (BS Ось B, креатив 3).

### Модуль 9 — Расстановка, согласование, утверждение, изменения (operations/events)

**FR-9.1. Формирование расстановки.** Результат распределения собирается в расстановку (наименование ОМ, посты, привлечённые группы, поимённо сотрудники); не статична (PR §8.4). Черновая авто-расстановка (VX §8.1): объект, сектор, пост, направление, старший, сотрудники, техника, оружие, спецсредства, времена прибытия/заступления/снятия, точка сбора, примечания.

**FR-9.2. Назначение старших и ручная доработка.** Старшие внешнего/внутреннего секторов, направлений, вторые/третьи номера, ответственные за группы; ручная замена/смена поста/усиление/добавление техники-оружия/смена старшего/комментарий/повторный расчёт (VX §8.2–8.3).

**FR-9.3. Согласование.** Отправка руководству фиксирует дату, автора, версию, документы, расчёты, комментарии, статус (VX §12.1). Руководство проверяет посты/сотрудников/оружие/технику/старших, оставляет замечание, возвращает или утверждает (VX §12.2).

**FR-9.4. Возврат на доработку.** Замечание фиксируется текстовым комментарием к ОМ; каждый возврат сохраняется в истории (VX §12.3).

**FR-9.5. Утверждение итоговой расстановки.** Утверждает руководитель → расстановка действующая, основной документ ОМ (PR §8.7).

- Вариант VX §12.4: подписание ЭЦП → присвоение номера → блокировка от свободного редактирования → версия в архив. См. противоречие 10.C4 и открытый вопрос 11.OQ-6 (обязательность ЭЦП).

**FR-9.6. Оперативные изменения после утверждения.** Допустимы (выбытие, доп. силы); каждое — проверка конфликтов (FR-8.4) + запись в истории расстановки (что/когда/кем), видно отличие от первоначально утверждённой и почему (PR §8.8).

- Санкционированное изменение (VX §13): выбрать утверждённую расстановку, заменяемого и нового сотрудника, причину, основание, санкционирующего руководителя, подтвердить → новая версия, старая сохраняется. Минимальная запись (VX §13.3): было/стало, пост, причина, инициатор, санкционировал, дата, время, комментарий.
- Юридическое значение: расстановка — основание нахождения сотрудника на объекте (VX §13.4).

**FR-9.7. Печать расстановки.** Включать: сектор, пост, ФИО, подразделение, старший, времена сбора/заступления, точка сбора, задача, примечание (VX §14.2). Не включать: фото, расширенную антропометрию, внутренние оценки, чувствительные комментарии, рейтинг, ограничения (VX §14.3).

### Модуль 10 — Проведение ОМ, инструктаж, штаб, инциденты, закрытие

**FR-10.1. Инструктаж.** До выезда (сбор, проверка прибытия/формы/оружия/спецсредств, задачи, маршруты, ответственные, время) и после прибытия (по секторам/постам/маршрутам/особенностям/докладам) (VX §15.1–15.2). Старшие секторов видят список своих сотрудников (VX §15.3).

**FR-10.2. Режим проведения.** Отображение: статус, активные объекты/посты, старшие, состав наряда, журнал штаба, инциденты, изменения, указания, движение ОЛ, логистика, аккредитация (VX §16.1).

**FR-10.3. Журнал штаба.** Электронный журнал: начало/завершение, прибытие/убытие ОЛ, изменения маршрута, указания, доклады, замены, инциденты, проблемы техники/объекта (VX §16.2). Интерфейс штаба — планшет/защищённый ноутбук/адаптивный веб, карта, схемы, поиск, кнопка инцидента (VX §16.3, §3.6).

**FR-10.4. Инциденты.** Карточка инцидента: дата, время, объект, ОМ, пост, участники, описание, кто зафиксировал, меры, кому доложено, документы, фото/файлы, итоговое решение (VX §17.2). Перечень типов инцидентов — VX §17.1. Инцидент сохраняется в истории ОМ, паспорте объекта, карточке сотрудника (если связан), аналитике (VX §17.3).

**FR-10.5. Закрытие ОМ.** Статус «Ожидает закрытия направлений»; закрывают старший наряда/штаб/старшие направлений/техслужбы/аккредитация/боевые группы/оперативное направление/ответственные по объекту (VX §25.1–25.2). Заполняются: итоговая справка, фактическая расстановка, изменения, замены, инциденты, замечания, документы, выводы, предложения, обновление паспорта, оценки, фактический налёт часов (VX §25.3). Без обязательных данных закрытие невозможно (VX §25.4).

**FR-10.6. Архив и история.** По каждому ОМ хранится полный комплект (VX §26.1), включая паспорт объекта на момент ОМ; история нужна для подготовки будущих ОМ (VX §26.2).

### Модуль 11 — Прикомандирование / откомандирование (PS §11)

**FR-11.1. Откомандирование.** В штатном управлении сотрудник получает статус «Откомандирован», остаётся в штатном списке, отображается отдельным блоком внизу, учитывается «по списку», но не «в строю» (PS §11.2). Запись: сотрудник, откуда, куда, даты, причина, инициатор, документ (PS §11.4).

**FR-11.2. Прикомандирование.** В принимающем подразделении — статус «Прикомандирован», отдельный блок внизу, не входит в штатную численность, учитывается числом со знаком `+` (напр. `25 +2`) (PS §11.3, §12.6).

**FR-11.3. Выбор принимающего подразделения по иерархии** (департамент → управление → отдел, с учётом фактической структуры) (PS §11.4).

**FR-11.4. Запрос на возврат.** Кнопка «Вернуть» → запрос → уведомление принимающему → подтверждение/отклонение; при подтверждении сотрудник снова редактируем в штатном управлении, статусы «Откомандирован»/«Прикомандирован» завершаются, ставится новый (как правило «В строю»); при отклонении — причина и дата ожидаемого возврата (PS §11.5).

**FR-11.5. Запрет редактирования прикомандированным.** Сотрудник, сам прикомандированный, не редактирует статусы ни своего, ни принимающего управления; только просмотр (PS §11.6, §16.4).

- См. противоречие 10.C10 (PR §3.1 относит прикомандирование/откомандирование к статусам КУ).

### Модуль 12 — Нагрузка (operations/load; PR §9, VX §11)

**FR-12.1. Расчёт нагрузки.** Нагрузка = вся занятость (дежурства + ОМ) (PR §9.2).

**FR-12.2. Перегрузка по постоянной задействованности.** Ориентир: >3 дней подряд ежедневно >8 часов → признак перегрузки, нужна разгрузка/отдых (PR §9.2).

**FR-12.3. Перегрузка по времени на посту.** Факт (опрос по итогам ОМ) > предельного времени поста (FR-5.3) → перегрузка по посту (PR §9.2).

**FR-12.4. Учёт сменности.** Когда заступал, сколько часов, ночная ли смена, сколько прошло после смены, можно ли назначать, нужен ли отдых (VX §11).

**FR-12.5. Использование нагрузки.** При планировании — предупреждение (FR-8.4); при контроле — дашборды (FR-17) (PR §9.3).

### Модуль 13 — Оценивание и рейтинг (operations/ratings)

**FR-13.1. Двустороннее оценивание ОМ.** Старший объекта → группа и каждый сотрудник; сотрудник → свои старшие (сектора, объекта) (PR §10.2).

**FR-13.2. Шкала и значения.** 10-балльная, default = 8 каждому участнику (нет замечаний → действий не нужно); снижение <8 требует обязательного комментария, иначе не принимается (PR §10.3).

**FR-13.3. Рейтинг.** Складывается из оценок; ≈8 — норма; заметное отклонение вниз — сигнал руководству (PR §10.3).

**FR-13.4. Закрытость оценок.** Никто не видит выставленную лично ему оценку; сотрудник видит только итоговый рейтинг; старший не видит оценок от подчинённых (PR §10.4).

**FR-13.5. Налёт часов.** Учёт по полям: дата, ОМ, объект, пост, кол-во часов, дневная/ночная смена, сложность, замечания, оценка (VX §24.6).

- Расхождение формата с VX §24.2–24.4 (5/10-звёзд, 10 параметров) — см. противоречие 10.C8.

### Модуль 14 — Документ расхода ЛС (.docx) и альтернативные форматы (PS §12–14)

**FR-14.1. Формирование расхода.** За один день / за период / «на завтра» (PS §12.1).

**FR-14.2. Формат .docx.** Альбомная ориентация; заголовок шрифт 16; названия колонок 12; записи 8; итоговая строка — жирным; `.docx` (PS §12.2).

**FR-14.3. Заголовок.** `{Подразделение} ЖЕКЕ ҚҰРАМЫНЫҢ САПТЫҚ ТІЗІМІ {дата} ЖЫЛҒЫ`; имя берётся по уровню выгрузки (департамент/управление/организация); формат даты — принятый в организации (PS §12.3). См. открытый вопрос 11.OQ-10.

**FR-14.4. Таблица.** Колонки 1–15: № строки, название управления, по штату, по списку, вакансии, в строю, до дежурства, на дежурстве, после дежурства, в командировке, «учёба/соревнования/конференция», в отпуске, на больничном, прикомандирован, откомандирован (PS §12.4). Строка = одно управление/отдел по уровню выгрузки.

**FR-14.5. Содержимое ячеек статусов.** Кол-во → список «Фамилия И.О.» → комментарий → период «с…по…» (для колонок: на дежурстве, после дежурства, командировка, учёба/соревн./конф., отпуск, больничный, прикомандирован, откомандирован) (PS §12.5).

**FR-14.6. Расчёт численности.** По штату = по списку + вакансии; по списку = в строю + на дежурстве + после дежурства + командировка + учёба/соревн./конф. + отпуск + больничный + откомандирован; прикомандированные — отдельно со знаком `+`, не увеличивают штатную численность принимающего (PS §12.6).

**FR-14.7. Итоговая строка.** Жирным: № строки, «Общее», суммы по всем 13 числовым колонкам по всем управлениям (PS §12.7).

**FR-14.8. Выгрузка за период.** Один файл `.docx`, отдельная страница (с новой страницы) на каждую дату (PS §12.8).

**FR-14.9. Выгрузка «на завтра».** Только когда все необходимые управления обновили статусы на завтра (FR-16.3) (PS §12.9).

**FR-14.10. Альтернативные форматы.** `.xlsx` (те же колонки, лист на дату); `.pdf` (фиксированный вид, печать/обмен) (PS §13.1–13.2). Выгрузка списков сотрудников `.csv`/`.xlsx`, истории переводов/статусов, журнала аудита (PS §13.3).

**FR-14.11. Жизненный цикл документа-отчёта.** Запрос (тип/формат/подразделение/дата) → «В очереди» (уникальный номер) → асинхронная генерация → «Готов» + уведомление + ссылка «Скачать»; отмена до готовности; хранение ≥90 дней, удаление фиксируется в аудите (PS §14).

- Принадлежность расхода .docx к operations (BS strategic) — см. противоречие 10.C7.

### Модуль 15 — Уведомления (PS §15, VX §30, BS Ось F)

**FR-15.1. Канал (MVP).** Только in-app «колокольчик» в портале + признак непрочитано; внешних каналов (push/SMS/email/Telegram) нет — закрытый контур без интернета (BS Ось F).

- Противоречит PS §15.1/§23.3 (in-app + realtime push + email + SMS) — см. противоречие 10.C5.

**FR-15.2. Адресность.** Уведомление прилетает затронутому лицу по факту (пример: сотрудника сняли/заменили в расстановке) (BS Ось F).

**FR-15.3. Эскалация по бездействию.** Вверх по штатной вертикали: запрос не отработан → руководителю управления → не отреагировал → зам. рук. департамента и рук. департамента; ОРГД в эскалацию ОМ не вовлекается (BS Ось F).

**FR-15.4. Типы уведомлений.** Базовый перечень PS §15.2 (STATUS_APPLIED/UPCOMING/ENDING/COMPLETED/TERMINATED/EXTENDED/CANCELLED, DIVISION_UPDATED/PENDING, SECONDMENT_*, REPORT_READY/FAILED, ROLE_ASSIGNED, SYSTEM_ALERT) + события ОМ (VX §30: назначен старший, создано ОМ, нужен/просрочен расчёт, расстановка на согласовании/возвращена/подписана, сотрудник назначен/заменён, требуется санкция, ОМ началось/завершено, блок не закрыт, паспорт не обновлён).

**FR-15.5. Центр уведомлений.** Непрочитанные/прочитанные, фильтр по типу, «прочитано»/«прочитать всё», подписка/отписка в пределах разрешений (PS §15.5).

- Руководителя департамента не уведомляют о ежедневных обновлениях — контроль через назначенных ответственных (PS §15.3, §3.2).

### Модуль 16 — Индикатор обновления статусов (PS §10)

**FR-16.1. Состояния индикатора.** Зелёный (обновлено полностью) / Жёлтый (частично) / Красный (не обновлено) / Серый (не требует обновления) (PS §10.1).

**FR-16.2. Каскадный расчёт по дереву.** Управление зелёное ⇔ все сотрудники получили статус на дату; департамент зелёный ⇔ все управления зелёные; организация зелёная ⇔ все департаменты и независимые управления зелёные (PS §10.2).

**FR-16.3. Блокировка расхода «на завтра».** Скачивание за завтра доступно только когда все необходимые управления подтвердили обновление на завтра; иначе кнопка недоступна, показывается список неотчитавшихся + предложение уведомить; за прошедшие даты блокировки нет (PS §10.3, §12.9).

**FR-16.4. Уведомление об отставании.** «Управление N не обновило статусы за дату D»: управление, дата, плановое время, ссылка, контакт (PS §10.4).

**FR-16.5. Фиксация факта обновления управлением.** После успешного массового сохранения: фиксируется факт за дату, индикатор → «обновлено», запись в аудит, уведомление назначенным ответственным (управление, дата, ФИО, время) (PS §9.5).

### Модуль 17 — Массовое ежедневное обновление статусов (PS §9)

**FR-17.1. Рабочее место управления.** Наименование, выбранная дата (по умолчанию сегодня), таблица сотрудников, индикатор, кнопки массового обновления/добавления/скачивания (PS §9.1). Колонки таблицы: №, ФИО, отдел, должность, статус на дату, комментарий; откомандированные/прикомандированные — отдельными блоками (PS §9.2).

**FR-17.2. Форма массового обновления.** Дата/диапазон → по каждому сотруднику статус из списка → для спец. статуса даты начала/окончания → опц. комментарий/документ → сохранение одним действием; «В строю» можно оставить без доп. полей (PS §9.3).

**FR-17.3. Валидация формы.** 10 проверок PS §9.4: наличие статуса у всех (иначе «В строю»); период у спец. статусов; окончание ≥ начало; начало ≥ дата приёма; начало ≤ дата увольнения; нет пересечений с активными статусами; длительность ≤ максимума типа (напр. 45 дней отпуск); право редактировать управление; пользователь не в ограничивающем статусе; штатная принадлежность. При нарушении — данные не сохраняются, сообщение с конкретным сотрудником и причиной.

- Максимальные длительности типов — не заданы (открытый вопрос 11.OQ-9).

### Модуль 18 — Дашборды и аналитика (PR §11, PS §20, VX §27, BS Ось C)

**FR-18.1. Дашборд готовности к ОМ.** Чек-лист пройден? потребность утверждена/закрыта? ознакомились? расстановка утверждена? (PR §11.1).

**FR-18.2. Дашборд нагрузки.** Для начальников подразделений: кто перегружен, кому разгрузка (PR §11.2).

**FR-18.3. Дашборд общего расхода ЛС.** «Где сейчас сотрудники» на любую дату (дежурства/ОМ/отдых/др.) (PR §11.3).

**FR-18.4. Рекомендации руководству.** По накопленным оценкам/нагрузке: проблемные объекты/ОМ, регулярная перегрузка, люди/группы, требующие внимания (PR §11.4 — раздел в протоколе без тела текста, см. пробел 10.G3).

**FR-18.5. Кросс-сервисная видимость дежурного.** ОРГД видит сводку по организации; командный центр — общая ситуация (BS Ось C, креатив 2).

**FR-18.6. Аналитика по подразделениям/сотрудникам/дням.** Заполненность (штатная/списочная/вакансии/при-/откомандированные/% заполненности), статистика отсутствий, сравнение подразделений, динамика по дням, аналитика по сотрудникам (PS §20). Аналитика ОМ: количество ОМ, привлечение людей, частые объекты, задействованные сотрудники, налёт, инциденты, задержки закрытия (VX §27).

**FR-19.1. Журнал действий.** Кто, тип действия, объект, время, IP, было/стало, комментарий (PS §18.1; PR §5.2).

**FR-19.2. Типы действий.** CREATE/UPDATE/DELETE/LOGIN/LOGOUT/DOWNLOAD/VIEW(опц.)/ROLE_ASSIGN/ROLE_REVOKE/STATUS_TRANSITION (PS §18.2).

**FR-19.3. Просмотр.** По объекту/пользователю/типу/периоду/IP; только администраторам и аудиторам (PS §18.3).

**FR-19.4. Неизменяемость и хранение.** Записи не удаляются/не редактируются через интерфейс; хранятся постоянно; архивация только «холодным хранением» (PS §18.4–18.5). Юридическое основание при проверках/расследованиях (PS §18.4).

### Модуль 20 — Календарь статусов (PS §19)

**FR-20.1. Календарь сотрудника.** Дни месяца/квартала/года, цветовые отметки, детали при наведении, отметки PLANNED/ACTIVE/COMPLETED, подсветка пересечений (PS §19.1–19.2).

**FR-20.4. Календарь подразделения.** По горизонтали — дни, по вертикали — сотрудники, в ячейках — статусы, итоговые строки снизу; для планирования дежурств (PS §19.5).

## 5. Пользовательские сценарии (User Stories) с критериями приёмки

> По одному ключевому сценарию на модуль (не исчерпывающе; формат: «Как [роль], я хочу [действие], чтобы [цель]» + критерии приёмки).

**US-1 (Оргструктура).** Как администратор, я хочу строить дерево подразделений с разной глубиной подчинённости, чтобы отразить фактическую структуру.

- Приёмка: поддержаны все 5 вариантов подчинённости (PS §4.1); узел без родителя = корень; смена родителя пересчитывает дерево; орг-диаграмма отображает результат.

**US-2 (Карточка).** Как руководитель управления, я хочу видеть карточку сотрудника с актуальным статусом и историей, чтобы принимать решения.

- Приёмка: одна карточка, блоки скрываются по правам (BS Ось E); в списочной выдаче чувствительные поля скрыты (PS §6.3); история переводов и статусов доступна.

**US-4 (Статусы).** Как руководитель управления, я хочу планировать отпуск заранее, чтобы он применился автоматически в день начала.

- Приёмка: статус создаётся PLANNED; 00:01 переходит в ACTIVE; запись AUTO_APPLY в истории; «расход на завтра» учитывает плановый статус (PS §8.4, §19.4, §21.2).

**US-6 (Дежурства).** Как планировщик, я хочу составить график дежурств на месяц, чтобы заранее видеть базовую нагрузку.

- Приёмка: дежурства привязаны к объекту; заступивший на сутки получает «на дежурстве», следующие сутки — «отдых после дежурства»; назначение на сутки отдыха выдаёт предупреждение (PR §7).

**US-7 (ОМ).** Как старший объекта, я хочу провести ОМ по 8 шагам протокола, чтобы получить утверждённую расстановку.

- Приёмка: ОМ привязано к объекту; чек-лист пройден; потребность утверждена; запрос разослан; расстановка собрана; ознакомления отмечены; конфликты проверены; расстановка утверждена (PR §8).

**US-8 (Брокеридж/конфликты).** Как ОМД, я хочу запросить недостающих людей через брокера и видеть предупреждения о конфликтах, чтобы расставить осознанно.

- Приёмка: «физнаряд» ставится напрямую; доп. люди — через брокер→управление; при конфликте — предупреждение + возможность override с записью в историю (PR §8.6; BS Ось A, A1).

**US-8b (Каскадная замена).** Как ответственный, я хочу авто-предложение замены по должностной цепочке, чтобы быстро закрыть выбытие.

- Приёмка: авто — внутри управления; ручной выбор — в пределах топ-подразделения; за границей — эскалация; можно заменить любого (BS Ось B).

**US-9 (Расстановка после утверждения).** Как утверждающий, я хочу, чтобы изменения после утверждения фиксировались, чтобы был цифровой след.

- Приёмка: оперативное изменение проходит проверку конфликтов; пишется в историю расстановки (что/когда/кем); видно отличие от первоначальной (PR §8.8; VX §13).

**US-12 (Нагрузка).** Как начальник подразделения, я хочу видеть перегруженных, чтобы перераспределить нагрузку.

- Приёмка: помечается >3 дней подряд >8 ч; помечается превышение предельного времени поста по факту (PR §9.2).

**US-13 (Оценивание).** Как старший объекта, я хочу оценить участников после ОМ, чтобы накопить рейтинг.

- Приёмка: default 8 всем; снижение <8 требует комментарий; оценки закрыты, сотрудник видит только итоговый рейтинг (PR §10).

**US-14 (Расход .docx).** Как руководитель, я хочу получить расход за период одним файлом, чтобы отчитаться.

- Приёмка: один `.docx`, страница на дату; альбомная, шрифты 16/12/8, итоговая жирным; «на завтра» доступно только при полном обновлении статусов (PS §12).

**US-16 (Индикатор).** Как назначенный ответственный, я хочу видеть отстающие управления, чтобы напомнить им.

- Приёмка: каскадный светофор; красный по неотчитавшимся; уведомление об обновлении/отставании (PS §10).

**US-17 (Массовое обновление).** Как руководитель управления, я хочу сохранить статусы всех сотрудников одним действием, чтобы не делать это по одному.

- Приёмка: валидация по 10 правилам; при ошибке — конкретный сотрудник и причина, без частичного сохранения (PS §9.4).

**US-19 (Аудит).** Как аудитор, я хочу видеть, кто и на каком основании поставил статус, чтобы ответить проверке.

- Приёмка: запись с было/стало, инициатором, временем, IP; неудаляема (PS §18).

**US-23 (Дежурство-полномочие).** Как ОМД, заступив в 08:00, я хочу автоматически получить права на сутки, чтобы координировать день.

- Приёмка: права включаются на срок назначения и гаснут по окончании; в аудите видно, кто был ОМД (BS Ось E).

## 6. Нефункциональные требования

**NFR-1. Развёртывание/контур.** Один сервер в закрытой локальной сети, web-клиенты в LAN, без облака/интернета; межузловой синхронизации нет (BS Ось D, Фаза 4). Контейнерная модель (Docker Compose на MVP; K8s при масштабировании) (PS §25.3).

**NFR-2. Архитектура.** Модульный монолит Django 5.x + DRF, один Postgres, Django Admin для справочников; строгие модульные границы (общение через `*.api`); логическая изоляция схем `core.*`/`talent.*`/`operations.*` (BS Ось 3). Слоистая серверная архитектура api/application/domain/infrastructure (PS §25.1).

**NFR-3. Асинхронность.** Celery + Celery Beat + Redis для регламентных задач, генерации `.docx`, уведомлений; тяжёлые операции не блокируют пользователя (PS §14.2, §25.1).

**NFR-4. Аутентификация/авторизация.** Внешний Auth-микросервис как единственный источник identity/ролей; JWT в заголовке Authorization; ABAC при необходимости через `django-rules`, читая роль/подразделение/время из JWT; VAPS не хранит users/пароли (BS Ось 4/12).

- Расхождение с PS §24.1 (собственный JWT HS256, хеш паролей) — см. противоречие 10.C6.

**NFR-5. Разграничение на уровне API.** Каждый запрос: действителен ли токен; не отозван ли; есть ли роль/право; в пределах ли scope объект; не в ограничивающем ли статусе пользователь (PS §24.2).

**NFR-6. Защита соединения.** HTTPS, защищённый realtime-канал уведомлений (в закрытом контуре — без внешних каналов), фильтрация IP, rate limiting, блокировка после неуспешных входов (PS §24.3).

- В закрытом контуре «realtime push в браузер» допустим только в пределах LAN; внешние каналы исключены (BS Ось F).

**NFR-7. Хранение файлов.** Фото 3×4, документы, `.docx` — в выделенном хранилище; доступ только после авторизации и проверки прав на объект; скачивание — в аудит; отдельные сроки хранения (PS §24.4); документы-отчёты ≥90 дней (PS §14.5).

**NFR-8. Минимально необходимые данные.** Чувствительные поля скрыты по умолчанию, раскрываются в полной карточке по праву (PS §24.5, §17.5).

**NFR-9. Безопасность учёток.** Принудительный выход всех сессий, временная блокировка, отзыв всех ролей в один клик (PS §24.6). (Хранение паролей/хешей — в Auth-сервисе, не в VAPS, NFR-4.)

**NFR-10. Аудит как комплаенс.** Append-only история, неизменяемость через интерфейс, постоянное хранение, холодная архивация (PS §18.4–18.5; BS Домен 11).

**NFR-11. Производительность отчётов.** Генерация `.docx` — от секунд до минут, асинхронно (PS §14.2).

**NFR-12. Расширяемость интеграций.** Подключение новых интеграций без переработки ядра; единый журнал интеграционных событий; единые механизмы безопасности; мониторинг отказов внешних систем (PS §23.5).

**NFR-13. Локализация.** Заголовок расхода на казахском (`ЖЕКЕ ҚҰРАМЫНЫҢ САПТЫҚ ТІЗІМІ`) (PS §12.3); интерфейс — русскоязычный (по тексту источников). Точный набор языков не задан — см. пробел.

**NFR-14. Отказоустойчивость/масштабирование.** Раздельный жизненный цикл фронт/бэк, независимое масштабирование web и фоновой обработки, горизонтальное масштабирование (PS §25.4).

- На MVP ограничено одним сервером (NFR-1) — см. противоречие 10.C9-related.

**NFR-15. Клиент.** Единый портал, один URL/вход, ролевые экраны; без деления на «PS»/«VX» для пользователя (BS Ось E). Современный фронт (React/Vue) поверх DRF + Django Admin (BS Ось 3).

- Расхождение со стеком PS §25.2 (Next.js/shadcn/TanStack и пр.) — см. противоречие 10.C9.

**NFR-16. Офлайн-планшеты (будущая фаза).** Планшет — «читалка» расстановки/списков + проставление рейтинга; синхронизация после ОМ; сервер всегда главный, планшет только дописывает факты (BS Ось D).

## 9. Ограничения

**CON-1 (ресурсные).** Соло-разработчик → план линейный, без параллельных треков (BS Фаза 4).
**CON-2 (технические).** Закрытый контур, один сервер, без интернета/облака; нет внешних каналов уведомлений (BS Ось D, F).
**CON-3 (зависимость).** КУ ещё нет → оргструктуру/сотрудников поставляет заглушка `integration_ku`; контракт sync фиксируется заранее (BS Фаза 4).
**CON-4 (архитектурное).** Объект-центричная модель — Object корневой агрегат; текущие дежурства плоские, без привязки к объекту → пересадка на Object — самый тяжёлый пункт рефакторинга и ключевой риск (BS Фаза 4, этап 0.3).
**CON-5 (brownfield).** PS возобновляется через рефакторинг существующего кода дежурств (не чистый старт) (BS Фаза 4).
**CON-6 (правовые/процессные).** Система не ведёт кадровый учёт, не заменяет приказы (издаются вне системы), не присваивает уровень угрозы объекту, не оценивает оперативную обстановку (PR §3.2).
**CON-7 (форматные).** Расход — строго `.docx` альбомный, шрифты 16/12/8, итог жирным, заголовок на казахском (PS §12.2–12.3).
**CON-8 (временные/бюджетные).** Сроки внедрения и состав работ протоколом не описываются (PR §1.1); поэтапный план — BS Фаза 4 (этапы 0–5). Точные сроки/бюджет в источниках отсутствуют.

## 10. Противоречия и пробелы между документами

**C1. Владелец и перечень статусов.** PS §8.1/§31: 11 базовых статусов ведутся в PS. PR §3.1: длительные статусы (отпуск/больничный/командировка/учёба/соревнования/при-/откомандирование) принадлежат КУ; система владеет только БД/отдых/ГЭВ и оперативными. BS B1 подтверждает PR. → **Приоритет PR.**

**C2. Центральная сущность.** VX — ОМ-центрична; PS — вокруг подразделения/расхода; PR §4.1 / BS A2 — **Объект** корневой. → **Приоритет PR (объект-центричность).**

**C3. Обработка конфликтов.** BS (исходно) — hard gating (занятый не в выборке); PR §8.6 / BS A1 — soft warning + override с фиксацией. → **Приоритет PR.**

**C4. Утверждение расстановки.** VX §12.4 — обязательная ЭЦП, номер, блокировка; PR §8.7 — «утверждает руководитель», ЭЦП не упомянута. → **Расхождение механизма; открытый вопрос OQ-6.**

**C5. Каналы уведомлений.** PS §15.1/§23.3 — in-app + realtime push + email + SMS; BS Ось F — закрытый контур, **только in-app**. → **Приоритет BS (закрытый контур); email/SMS невозможны на MVP.**

**C6. Аутентификация/владение пользователями.** PS §24.1 — собственный JWT HS256, хеш паролей, своя БД учёток; PR §3.1 / BS Ось 4-12 — вход через КУ, внешний Auth, VAPS не хранит users. → **Приоритет PR/BS.**

## Приложение А. Сводный поэтапный план (источник BS Фаза 4; для дорожной карты, не для scope MVP-функций)

- **Этап 0 — Аудит + рефакторинг дежурств:** аудит кода; целевая структура `core/operations`; объект-центричность (агрегат Object, пересадка плоских дежурств — главный риск); статус-как-интервал; `integration_auth` (JWT); заглушка `integration_ku` + контракт sync.
- **Этап 1 — Дежурства до полноты:** виды дежурств, план на месяц, статусы «на дежурстве»/«отдых после», нагрузка (>3дн >8ч), дашборд «Общий расход ЛС на дату», расход `.docx`.
- **Этап 2 — Полный цикл ОМ:** 8 шагов протокола, groups, Потребность, брокеридж, конфликты (soft warning + override), каскадная замена, in-app уведомления + эскалация по вертикали.
- **Этап 3 — Масштаб + интеллект:** несколько объектов, наложение дежурств+ОМ в общей нагрузке, перегрузка по посту, дашборды (готовность/нагрузка/рекомендации), оперативные изменения с историей.
- **Этап 4 — Talent + оценивание:** рейтинги/OKR/навыки/резерв, двустороннее оценивание ОМ (10б, default 8, закрытость), опрос по итогам ОМ.
- **Этап 5 — Будущие фазы:** реальная интеграция КУ, планшеты (офлайн-читалка + рейтинг), денормализованный read-cache при лагах.

> Примечание: MVP-разбивки PS §26 (MVP-1..4) и VX §31 (MVP-1..4) описаны для двух исходных систем по отдельности; в объединённой модели они подчинены поэтапному плану BS Фаза 4. Это расхождение планирования — следствие слияния PS+VX (см. C7, OQ-12).

### Б.4. Сквозные бизнес-правила доступа (применяются поверх матрицы)

1. Право редактирования статусов действует только если пользователь по штату принадлежит управлению, имеет роль, **не** в статусе «Откомандирован» и **не** в другом ограничивающем статусе (PS §16.4, §17.1–17.2). Перечень ограничивающих статусов настраивается, базово `["Откомандирован"]` (PS §17.1).
1. Запрет действий на чужих сотрудников без отдельной санкции (PS §17.4).
1. Видимость ограничена scope: подразделения, сотрудники, статусы, документы — только в пределах scope (PS §17.3); по принадлежности (свои объекты/ОМ/подразделение) — PR §5.2.
1. Чувствительные поля (телефон, email, дата рождения, служебные комментарии, документы) скрыты в списочной выдаче, доступны только в полной карточке по праву (PS §17.5, §24.5).
1. Каждый запрос к API проверяет: токен действителен; пользователь не отозван; есть роль и право; объект в пределах scope; пользователь не в ограничивающем статусе (PS §24.2).
1. Один пользователь может иметь несколько ролей с разными scope (PS §16.7); администратор может динамически создавать/редактировать/удалять роли и наборы прав (PS §16.8); все операции с ролями — в аудит (PS §16.8, §18.2).
1. После утверждения/подписания расстановки свободное редактирование запрещено; изменения только через санкционированную процедуру с новой версией (VX §12.4, §13; PR §8.8). Механизм подписания (ЭЦП vs утверждение) — открытый вопрос OQ-6.

### Б.5. Легенда scope (PS §16.7, PR §5.2)

`ORGANIZATION` — вся организация · `DEPARTMENT` — департамент и потомки · `OWN_DIVISION` — собственное подразделение · `CUSTOM` — произвольный перечень · дополнительно для ОМ-ролей — **scope по объекту/мероприятию** (свои объекты и ОМ).
