> **Что это.** Экран №1 — самая сложная и самая частая рабочая поверхность: оператор утром **вслепую, с клавиатуры, без мыши** проставляет статусы своему подразделению. Клавиатурный ввод — это и есть продукт; мышь — фолбэк. Документ фиксирует **поведение** экрана (грамматику, раскладку, конфликты) так, чтобы его можно было **утвердить на бумаге до написания кода и заморозки API**. Осознанное расхождение с донором: у донора этого нет — VAPS добавляет слепой грид, потому что он кратно быстрее донорской «карточки → изменить статус» на массовом утреннем расходе (решено 2026-06-10).

> **Что фиксирует контракт, а что — нет.** Фиксируется ПОВЕДЕНИЕ (грамматика клавиш, колонки, семантика конфликтов, преднабор, сдача, скоуп, перф-инварианты). НЕ фиксируется: библиотека/пиксели (визуал = донор-shadcn + Tailwind-токены, см. `DESIGN.md`), HTTP-контракт статусов (задан бэкендом E3), экран целиком с роутом (E10).

## 1. Назначение и границы экрана

- **Роль:** оператор подразделения (`daily_report.mark_update`), видит и правит **только своё поддерево** (`scope_division_id`, subtree).
- **Задача:** за минуты проставить/скорректировать статусы личного состава на **один день**, затем **сдать день**.
- **Один экран = одно подразделение** (виртуализация не рассчитана на 5000 строк разом).
- **Не в этом экране:** светофор готовности (экран №2, контракт `10-01-светофор-дерево.md`) и расход (экран №3, контракт `10-02-расход.md`) — контракт 10.1 разбит на два файла; журнал/аудит; карточка сотрудника (донор-фолбэк — см. §8).

## 2. Раскладка

Плотная таблица (`size="sm"`) **внутри карточки-контейнера** — тёплый «воздух» card-языка не размывает рабочие строки ввода.

```
┌───────────────────────────────────────────────────────────────────────────┐
│  Расход дня · [Подразделение]            [ Изменено 4 из 40 ]  [ Сдать день ]│
│  [🔎 поиск/фильтр]   [☑ только отклонения]        [ bulk: применить статус ] │
├────────────────────────┬────────────────────┬─────────────────────────┬────┤
│ ФИО                    │ Статус             │ Период (по … включит.)  │ !  │
├────────────────────────┼────────────────────┼─────────────────────────┼────┤
│ Иванов И. И.           │ [В строю        ▾] │                         │    │
│ Петров П. П.           │ [На больничном  ▾] │ по 12.07 включительно   │    │
│ Сидоров С. С.          │ [В командировке ▾] │ по 15.07 включительно   │ ▲  │  ← жёлтый (409 soft)
│ …виртуализованные строки…                                                   │
└────────────────────────┴────────────────────┴─────────────────────────┴────┘
```

**Колонки** (предложено по макету — уточняется на согласовании, см. §11):

| # | Колонка | Содержимое | Правится? |
|---|---------|-----------|-----------|
| 1 | **ФИО** | Фамилия И. О.; ИИН — **маскируется** | нет (read-only) |
| 2 | **Статус** | type-ahead combobox (см. §5) | да — основная ячейка ввода |
| 3 | **Период (по … включительно)** | конечная дата действия статуса (для срочных); пусто = бессрочно/на день | да (при статусе с периодом) |
| 4 | **!** | флаг конфликта строки (жёлтый 409 / красный 422) | индикатор, не вводится |

- **Преднабор:** грузится **вчерашняя расстановка** как дефолт; оператор правит **только отклонения**. Счётчик «**изменено N из M**» наверху.
- **Фильтр «только отклонения»** — тумблер для самопроверки перед сдачей.
- **Виртуализация** (TanStack Virtual): длинные списки не рендерятся целиком.

## 3. Клавиатурная грамматика — спецификация конечного автомата (ЯДРО контракта)

Грамматика — **чистый конечный автомат без React** (`architecture.md L253`): реализуется отдельным модулем (9.2), тестируется исчерпывающей таблицей переходов + property-based (9.3) без рендера, и лишь подключается к гриду (9.4).

### 3.1. Состояния

| Состояние | Смысл |
|-----------|-------|
| `NAVIGATE` | фокус на ячейке, редактирование не открыто |
| `EDIT` | ячейка «Статус» открыта, combobox активен, идёт поиск/выбор (type-ahead) |
| `PERIOD_EDIT` | открыта правка ячейки «Период» |
| `CONFLICT` | показан ConflictDialog (409 soft) поверх экрана; грид под ним заморожен |

### 3.2. Таблица переходов

| Состояние | Клавиша | Эффект → следующее состояние |
|-----------|---------|------------------------------|
| `NAVIGATE` | `Enter` | на ячейке «Статус» — открыть правку → `EDIT`; на ячейке «Период» — открыть правку → `PERIOD_EDIT`; на read-only (ФИО, флаг) — нет эффекта |
| `NAVIGATE` | буква/цифра | на ячейке «Статус» — открыть правку и начать type-ahead с этого символа → `EDIT`; на прочих колонках — нет эффекта |
| `NAVIGATE` | `Tab` / `→` | фокус на ячейку справа (в границах строки) → `NAVIGATE` |
| `NAVIGATE` | `Shift+Tab` / `←` | фокус на ячейку слева (в границах) → `NAVIGATE` |
| `NAVIGATE` | `↑` / `↓` | фокус на строку выше/ниже (в границах грида) → `NAVIGATE` |
| `NAVIGATE` | `Esc` | нет эффекта (правка не открыта, отменять нечего) → `NAVIGATE` |
| `EDIT` | ввод символов | фильтрация списка статусов (type-ahead) → `EDIT` |
| `EDIT` | `↑` / `↓` | перемещение по списку кандидатов → `EDIT` |
| `EDIT` | `←` / `→` | текстовый курсор внутри поля поиска; позиция/состояние грида не меняются → `EDIT` |
| `EDIT` | `Enter` | **подтвердить** выбранный статус, закрыть правку, **фокус ↓ на следующую строку той же колонки** → `NAVIGATE` |
| `EDIT` | `Tab` / `Shift+Tab` | подтвердить и фокус на колонку справа/слева → `NAVIGATE` (правка «Периода» открывается оттуда отдельным `Enter` — авто-открытия нет) |
| `EDIT` | `Esc` | **отмена**: вернуть ячейке значение ДО правки (pre-edit), закрыть → `NAVIGATE` |
| `PERIOD_EDIT` | `Enter` | подтвердить дату, фокус ↓ → `NAVIGATE` |
| `PERIOD_EDIT` | `Tab` / `Shift+Tab` | подтвердить дату, фокус на колонку справа/слева → `NAVIGATE` |
| `PERIOD_EDIT` | `Esc` | вернуть pre-edit, закрыть → `NAVIGATE` |
| `PERIOD_EDIT` | прочие клавиши (символы, стрелки) | обслуживает редактор даты; позиция/состояние грида не меняются → `PERIOD_EDIT` |
| `CONFLICT` (409) | `Enter` / «Подтвердить оверрайд» | ретрай с `override:true` (после причины) → `NAVIGATE`, **фокус возвращается в исходную ячейку** |
| `CONFLICT` (409) | `Esc` / «Отмена» | закрыть диалог, значение НЕ сохранено → `NAVIGATE`, **фокус в исходную ячейку** |
| `CONFLICT` (409) | прочие клавиши | захвачены диалогом, грид под ним заморожен → `CONFLICT` |
| любое | `Ctrl+Enter` | **сохранение правок** (кнопка грида), **не сдача дня** — обрабатывает ЭКРАН, не грид; состояние и фокус грида не меняются |

**Клавиатурный выход из грида (`Ctrl+Enter`, закрытие Q4 §11, стори 10.2; уточнён в 10.3).** Аккорды с модификаторами принадлежат ЭКРАНУ, а не гриду: экран перехватывает `Ctrl+Enter` **на входе** (capture-фаза) и до грида его не пропускает, поэтому таблица переходов выше и её реализация (`grammar.ts`, стори 9.2) остаются **нетронутыми**. ⚠️ **`Ctrl+Enter` сохраняет правки и день НЕ сдаёт** (10.3): сдача клавиатурного шортката не получает намеренно — это осознанное действие через панель сдачи. Побочный эффект, зафиксированный как ожидаемый: обработчик висит на корневом `div` экрана, который теперь оборачивает и панель сдачи, — `Ctrl+Enter` при фокусе внутри панели тоже сохраняет правки. Это согласовано с запретом сдавать при несохранённых правках (§7) и специально не «чинится». ⚠️ Отдельно отмечено, потому что `Enter` сам по себе — рабочая клавиша грамматики: без перехвата на входе `Ctrl+Enter` сначала открыл бы правку ячейки и лишь потом дошёл до экрана. Tab-клампинг на границах остаётся by design (см. ниже), инварианты §3.3 не меняются.

**Границы грида:** движение на краю **упирается, не «заворачивает»** (wrap-а нет): `→` в последней колонке, `↓` в последней строке и т. п. оставляют фокус на месте. `Enter`-подтверждение на последней строке сохраняет значение, фокус остаётся в той же ячейке — оператор при слепом вводе не «выпадает» из грида. Это и гарантирует инвариант 1 (§3.3).

### 3.3. Инварианты (проверяются property-based, стори 9.3)

1. **Фокус ВСЕГДА в границах грида** — ни одна последовательность клавиш не выводит фокус за пределы строк/колонок.
2. **Нажатия НЕ теряются** — каждое валидное нажатие даёт ровно один детерминированный переход/эффект.
3. **`Esc` возвращает pre-edit** — отмена правки восстанавливает значение ячейки, каким оно было до входа в `EDIT`/`PERIOD_EDIT`.

## 4. Ячейка «Статус» (type-ahead)

- **Combobox с поиском:** ввод «бол» → отфильтрован «На больничном», `Enter` подтверждает. Опционально — быстрые коды (см. §11, Q3 — на согласование).
- **Единый стиль:** light-tint для **всех** статусов (донор-палитра); «В строю» = **green** light-tint (не нейтральный baseline).
- **Красная заливка 422** — это **отдельный слой конфликтов** поверх ячейки, **не** статус-цвет (см. §5).
- **ИИН** нигде в гриде не показывается открыто (маскировка).

## 5. Инлайн-конфликты 409 / 422 (граница с бэкендом E3)

Семантику hard/soft, коды и правило причины задаёт **бэкенд** (E3: `status_service`, реестр `error-codes.yaml`). Контракт фиксирует **поведение UI**, не переопределяет коды. **Деление hard/soft конфигурируется при деплое** — UI не зашивает (напр. «после дежурства» может быть soft или absolute по политике вида дежурства).

| Тип | Индикация в гриде | Диалог | Коммит |
|-----|-------------------|--------|--------|
| **409 soft (overridable)** | жёлтый маркер строки + флаг `▲` | ConflictDialog на коммите: **причина 10–500 символов обязательна** → «Подтвердить оверрайд» → ретрай `override:true` → запись в аудит | проходит после оверрайда |
| **422 hard (non-overridable)** | **красная заливка строки** | красный ConflictDialog / инлайн-сообщение; **оверрайда нет** | **БЛОКИРУЕТСЯ** |

- После закрытия любого диалога **фокус возвращается в исходную ячейку** грида.
- Стек модалок — на один уровень (Dialog поверх экрана, не поверх другого Dialog).

## 6. Массовое действие (bulk)

- **Multi-select строк** → один статус на всю группу через **bulk-тулбар** сверху.
- **Частичная ошибка не теряет валидный ввод:** строки с ошибкой подсвечиваются (409/422), остальные применяются.

## 7. Преднабор · автосейв · сдача дня

- **Преднабор** = вчерашняя расстановка (см. §2).
- **Автосейва НЕТ (решено, Q4 §11, стори 10.2):** правки копятся в гриде и уходят одной отправкой. Инвариант «ровно **1 commit на правку**» относится к React-рендеру (детерминанта производительности, §9) и сохраняется — он никогда не означал сетевой вызов на ячейку. Защита ввода вместо автосейва: `beforeunload` при непустом числе дельт + явное подтверждение в приложении при смене даты/подразделения (они уничтожают несохранённые правки). Оптимистичный автосейв остаётся DEFERRED (`ARCH-DEFERRED-046`), триггер пересмотра — первая жалоба на потерю ввода.
- **Ритуал ДВУХФАЗНЫЙ (уточнено стори 10.3).** До 10.3 на экране была одна кнопка «Сдать день», и она день **не сдавала**: отправляла дельты статусов в bulk-роут, а ряд в `ops_daily_submissions` не появлялся, `submit_day` не вызывался, лист в светофоре оставался RED. Фазы разведены явно:

  1. **«Сохранить правки»** (кнопка **грида**) — отправка дельт статусов массовым роутом. Это и есть прежнее поведение кнопки, только названное своим именем. `Ctrl+Enter` жмёт **её** (см. §3.2).
  2. **«Сдать день»** (кнопка **панели сдачи**, канон-строка) — `POST /api/operations/daily-submissions/` с телом `{division_id, business_date}` → **предпросмотр с подтверждением** → создаётся версия сдачи, и лист **зеленеет** в дереве подразделений.

- **Сдача при несохранённых правках ЗАПРЕЩЕНА** (не предупреждение, а блокировка). Причина инвариантная: `submit_day` снимает снапшот с **серверного** состояния — несохранённые дельты в него не попадут, и оператор сдал бы не то, что видит на экране. Текст отказа называет счёт: «Сначала сохраните правки: изменено N».
- **Окно сдачи — `{сегодня, завтра}`** (сервер: `Clock.today_local()` в `VAPS_LOCAL_TIMEZONE`). Экран считает окно по зоне браузера и вне него не отправляет; на границе суток зоны расходятся, поэтому истина при отказе `422 BUSINESS_DATE_OUT_OF_WINDOW` — список `details.allowed` **из ответа**, а не пересказ клиентского предположения.
- **Предпросмотр — предварительный и говорит об этом.** Категорию (`Подтверждено без изменений` / `Изменено` / `Исправлено`) окончательно определяет сервер, сравнивая ростер и интервалы-факты снапшота с предыдущей сдачей, — а не дельты экрана. Показанная после сдачи подпись берётся **из тела ответа**, а не из предсказания.
- **Пересдача** (amendment) здесь не живёт: отказ `409 DAY_ALREADY_SUBMITTED` называет путь, но кнопок под него не даёт — это отдельное право `daily_report.correct` и отдельная стори (10.6).

## 8. Скоуп-гейтинг и ограничения прав

- Оператор видит/правит **только своё поддерево**.
- **«Откомандирован» → view-only:** ограничивающий статус снимает права редактирования статусов на всех экранах (грид и ячейки — только просмотр), **навигацию не трогает**.
- **Донор-фолбэк (точечная правка):** единичное изменение вне утреннего ритуала — карточка сотрудника → «Изменить статус» (статус + период + комментарий + планирование на будущее). Грид — основной массовый путь; карточка — точечный; **оба пишут одну и ту же сущность статуса**.

## 9. Перф-инварианты (детерминированные, не тайминги)

Контракт производительности задан **счётчиками**, а не секундами (`architecture.md L246`) — их энфорсит перф-смоук 9.8:

1. **Ровно 1 React-commit на нажатие клавиши** в гриде (React Profiler `onRender`).
2. **≤ N DOM-узлов при 5000 строк** (виртуализация; бюджет N — из перф-спайка E1).

Тайминги (p95 keydown→commit) — тренд-артефакт (Playwright CDP throttling), **не блокирующий**.

## 10. Что требует ПОДПИСИ заказчика ДО заморозки API

Именно эти пункты просим утвердить чемпиона-скептика (оператора, чьему Excel доверяют) — 2–3 официальных испытателя по распоряжению:

2. **Набор и порядок колонок** (§2): ФИО · Статус · Период · флаг — достаточно ли? нужна ли колонка «комментарий» прямо в гриде?
3. **Политика hard/soft по умолчанию** (§5) — какие пересечения статусов блокируют (422), а какие оверрайдаются с причиной (409)?
4. **Быстрые коды статусов** (§4, Q3) — нужны ли короткие коды помимо type-ahead?
