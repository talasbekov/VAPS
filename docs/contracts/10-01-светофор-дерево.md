> **Что это.** Экран №2 — руководитель видит **готовность сдачи по дереву подразделений**: где сдано и сходится (зелёный), где сдано но расход разошёлся (жёлтый), где не сдано вовсе (красный). Это поверхность **наблюдения**, а не ввода: светофор только **вскрывает** расхождение, никогда не переписывает расход (by-design 5.5a).

> **Что фиксирует контракт, а что — нет.** Фиксируется ПОВЕДЕНИЕ (семантика цветов, каскад, фильтр, polling, раскладка дерева, перф). НЕ фиксируется: пиксели (визуал = донор-shadcn+Tailwind, `DESIGN.md`), **HTTP-контракт дерева — его ЕЩЁ НЕТ** (`traffic_light.py` = сервис 5.5a/5.5b без роута; см. §5 — требуемый shape + бэкфилл ДО 10.4), экран целиком с роутом (10.4).

---

## 1. Назначение и границы экрана

- **Роль:** руководитель/оператор, видит готовность **своего поддерева** (`scope_division_id`, subtree — RBAC-нарровинг приходит с API-стори, mirror `StrengthReportService`).
- **Задача:** одним взглядом понять, кто сдал день, а кто отстаёт; провалиться вглубь дерева к отстающему листу.
- **Не в этом экране:** ввод/правка статусов (экран №1, грид, `09-01`); выпуск расхода (экран №3, `10-02`); уведомления/напоминания (E11 WS; здесь — только индикация «late»).
- **Связь со сдачей (10.3):** «Сдать день» на гриде (09-01 §7) зеленит лист в этом дереве; drift после сдачи → лист желтеет (YELLOW). Экран сдачи-дня 10.3 читает тот же светофор — отдельного контракта не заводим.

## 2. Раскладка

Дерево подразделений вложенными **строками-карточками** (card-язык `DESIGN.md`), с трёхцветным маркером на каждом узле и каскадным цветом вверх.

```
┌───────────────────────────────────────────────────────────────────────────┐
│  Готовность сдачи · [Дата: 14.07]         [☑ только отстающие]  [🔄 обновлено 30с назад]│
├───────────────────────────────────────────────────────────────────────────┤
│ 🔴 Департамент                                    (свёрнутый цвет = худший) │
│   ├─ 🟢 1-е управление                                       сдано ✓        │
│   ├─ 🔴 2-е управление                       НЕ сдано · отв.: кап. Дамир    │
│   │    └─ 🔴 Отдел А                                          НЕ сдано       │
│   ├─ 🟡 3-е управление              сдано, но расход разошёлся (drift: 2)   │
│   └─ ⚪ Резерв                                    нет данных (нечего сдавать)│
│   …ленивые ветки: узел раскрывается по клику, не грузим всё дерево разом…   │
└───────────────────────────────────────────────────────────────────────────┘
```

- **Ленивые ветки:** узел раскрывается по требованию (400 подразделений на 4ГБ — не рендерить всё дерево разом; перф-бюджет как у грида, §6).
- **Фильтр «только отстающие»:** тумблер прячет полностью зелёные поддеревья — руководитель видит только проблемные ветки.
- **Каждый узел:** цвет-маркер · имя · статус-текст (сдано / НЕ сдано / drift N / нет данных) · `late`-метка · ответственный (для красных — из данных сдачи).

## 3. Семантика цветов (ЯДРО контракта — РОВНО по `traffic_light.py`)

Цвета — **не выдумка UI**, а прямое отражение `TrafficLightStatus` (`traffic_light.py:59-72`). UI НЕ вводит оттенков/порогов сверх этих.

### 3.1. Per-division цвета (лист, 5.5a)

| Цвет | Значение | Условие (`traffic_light.py:6-10`) |
|------|----------|-----------------------------------|
| 🟢 **GREEN** | сдано и сходится | есть действующая `DailySubmission` И `derive(снапшот) == derive(live)` |
| 🟡 **YELLOW** | сдано, но расход **дрейфанул** | сдача есть, но derived-расход разошёлся; `drift` несёт per-employee детали `{added, removed, changed}` |
| 🔴 **RED** | не сдано | действующей сдачи нет, а own-ростер НЕпуст |

**Ключевой инвариант (by-design 5.5a):** drift считается на уровне **derived winners** (`resolve_status` — победитель расхода сотрудника на дату), НЕ сырых фактов. Переименование, delete+recreate идентичного факта, любая правка, не сдвинувшая победителя, **остаётся GREEN** — расход держится снапшотом BY DESIGN; светофор только вскрывает расхождение, **никогда не переписывает расход**.

### 3.2. Каскадные цвета (узлы дерева, 5.5b)

| Цвет | Значение | Правило |
|------|----------|---------|
| ⚪ **NEUTRAL** | «нет данных» — узлу нечего сдавать | нет сдачи И пустой own-ростер; нейтральный элемент свёртки (не влияет на цвет родителя) |
| ⬛ **UNKNOWN** | «неопределён» — узел с битым derive | `status_type_code` вне priorities → `derive` бросил `ValueError`; per-node изоляция (D1), обход НЕ падает |

- **NEUTRAL/UNKNOWN — только каскадные:** лист (`division_traffic_light` 5.5a) их НЕ возвращает; они рождаются в свёртке дерева 5.5b.
- **Свёртка вверх (worst-colour, `traffic_light.py` 5.5b):** цвет узла = худший по precedence **UNKNOWN > RED > YELLOW > GREEN**; `NEUTRAL` нейтрален (узел без не-нейтральных вкладчиков → NEUTRAL). Один post-order обход дерева (`CoreDivisionTreeSelector`, ARCH-DATA-024), НЕ запрос на узел (NFR-4).
- **`late` видим в каскаде:** хоть одна поздняя сдача в поддереве → узел несёт `late=True` (OR по поддереву).

## 4. Обновление (polling, не WS)

- **Polling-интервал** (не WebSocket — WS = E11): дерево перезапрашивается периодически; индикатор «обновлено N секунд назад».
- **WS-переход** (мгновенное позеленение листа при сдаче) — E11; в 10.4 — polling.
- Интервал — на согласование (§10, Q4: баланс свежести против нагрузки на 4ГБ/400 подразделений).

---

## 5. Граница с бэкендом — HTTP-роут дерева ОТСУТСТВУЕТ (бэкфилл ДО 10.4)

**Сервис есть, роута нет.** `traffic_light.py` даёт `traffic_light_tree(root_division_id, business_date) -> dict[div, CascadeTrafficLight]` (5.5b) и `division_traffic_light` (5.5a), но HTTP-эндпоинта в `schema.d.ts` **НЕТ** (проверено grep). Экран 10.4 не сможет ходить в дерево без роута.

**Требуемый response-shape** (предложение на подпись — бэкфилл-стори реализует, §10 Q1):
```
GET /api/operations/traffic-light-tree/?root_division_id=<uuid>&business_date=<ISO>
→ 200 { nodes: [ { division_id, name, parent_id, status: "GREEN|YELLOW|RED|NEUTRAL|UNKNOWN",
                   late: bool, drift?: {added:[], removed:[], changed:[{employee_id,from,to}]},
                   responsible?: "<для RED>" } ] }
→ 403 чужой scope · 404 корень не найден · 422 дата до начала данных
```
- Плоский список с `parent_id` (UI строит дерево) vs вложенный `children` — **на подпись (Q1)**.
- **Бэкфилл-флаг:** роут светофор-дерева = отдельная бэк-стори ДО 10.4 (тот же механизм, что REST-бэкфилл статусов ДО 10.2 — ретро E9 AI-4). Без него 10.4 упрётся в тот же разрыв, что 9.7 (контракт против несуществующей поверхности).

## 6. Перф-инварианты (детерминированные, не тайминги — как §9 грида)

- **Ленивые ветки:** не рендерить всё дерево (400 подразделений на 4ГБ); раскрытие узла грузит его детей.
- **Bulk на бэке (уже соблюдён 5.5b, NFR-4):** один проход дерева, один `roster_on`/`overlapping_on`/`current_for_many` на поддерево — НИ ОДНОГО запроса в цикле по узлам.
- **DOM-бюджет фронта** (по образцу грида §9.2): число отрендеренных узлов ≪ полного дерева при глубоком раскрытии — точный бюджет на замер 10.4 (перф-спайк класса 1.10).

## 7. Что требует ПОДПИСИ заказчика ДО заморозки API

1. **Response-shape дерева** (§5): плоский список с `parent_id` или вложенный `children`? Это замораживает и бэкфилл-роут, и рендер 10.4.
2. **Раскладка дерева** (§2): вложенные строки-карточки, ленивые ветки — ложится ли на привычку руководителя видеть готовность?
3. **Цвет пустого/нейтрального узла в UI** (§3.2): NEUTRAL «нет данных» — какой визуал (серый/пунктир), чтобы не путать с RED?
4. **Polling-интервал** (§4): приемлемая свежесть на 4ГБ до перехода на WS (E11)?

## 8. Открытые вопросы

- **Q1 (роут-shape):** плоский `parent_id`-список vs вложенный `children`; кто бэкфиллит роут — отдельная бэк-стори до 10.4 [реком.] или внутри 10.4?
