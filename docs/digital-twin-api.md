# API Цифрового двойника, версия 1

Smart отдаёт объекты, посты паспортов, охранные мероприятия и обезличенную численность. Digital и другие проекты этим изменением не затрагиваются. Внешняя сеть, геокодирование, обратная запись, вебхуки и фоновые задания не используются.

```http
GET /api/integrations/digital-twin/v1/snapshot/?date=2026-10-16
Authorization: Bearer <существующий JWT Smart>
```

Доступ требует **глобального**, без области подразделения, `digital_twin.read`. Глобальный `*` также допускается. Грант с областью запрещён, включая scoped wildcard. Роль `DIGITAL_TWIN_READER` содержит только `digital_twin.read`; она не открывает кадровые API и журнал с персональным составом. Старое право `status.manage` и роль `INTEGRATION_USER` автоматически доступа не дают. Установка прав требует additive migration `0144`; приложение само не создаёт учётные записи или пароли.

Для подключения администратор назначает технической учётной записи активную роль `DIGITAL_TWIN_READER` без области подразделения в «Ролях и доступе». Существующая авторизация: `POST /api/token/` с JSON `{"username":"<логин>","password":"<пароль>"}` возвращает `access` и `refresh`; access передаётся как Bearer, обновление выполняется через `POST /api/token/refresh/`. Реквизиты технической учётки в код или клиентский JavaScript не помещаются. Локально путь доступен через основной адрес `http://127.0.0.1:3380`; на сервере используется его адрес Smart.

Для серверного применения потребуется новая поставка с явной поддержкой миграции `0144`, резервированием и rehearsal. В текущем этапе серверный архив не собирался. `update-app-only.py` обоснованно откажет, пока `0144` отсутствует в БД; прежние серверные установщики новой миграции не разрешают. Обходить эти проверки или запускать `seed_operations` для обновления заполненной базы не следует.

Поддерживаются GET, HEAD и OPTIONS. POST, PUT, PATCH, DELETE возвращают 405. Проверка доступа выполняется до чтения объектов, мероприятий, кадровых источников и карты. Без JWT — 401, при недостаточных правах — 403. Формат даты строго `YYYY-MM-DD`, неверный календарный день, повторный параметр даты, неизвестный фильтр и границы `0001-01-01`/`9999-12-31` дают 400. При отсутствии `date` используется `Clock.today_local()` в зоне Службы.

Полный явный контракт опубликован в OpenAPI (`/api/schema/`, операция `digital_twin_v1_snapshot`). Верхний уровень содержит ровно:

| Поле | Содержание |
| --- | --- |
| `schema_version` | Строка `1.0` |
| `business_date` | Выбранная бизнес-дата |
| `generated_at` | Момент формирования с часовым поясом |
| `time_zone` | Зона Службы из `OPS_LOCAL_TIMEZONE`, с fallback на `TIME_ZONE` |
| `objects` | Текущий каталог объектов и постов паспортов, включая архивные объекты |
| `events` | Мероприятия, календарный период которых включает дату, и их площадки |
| `duty` | Отдельная численность кадровых нарядов и действующих почасовых назначений |

Все ID — строки, в том числе импортные числа выше безопасного диапазона JavaScript. Неизвестные значения — `null`. Ответ формируется по списку разрешённых полей и повторно ограничивается явными serializers. В нём отсутствуют employee ID, ФИО, ИИН, телефоны, охраняемые лица, старшие, исполнители, комментарии, паспортные снимки, фото и ссылки на закрытые файлы.

`objects[]`: `id`, `code`, `name`, `object_type`, `region`, `address`, `state`, `ownership`, `location`, `posts`. Каждый пост содержит `id`, `source: "PASSPORT"`, `sector_id`, `sector_name`, `name`, `need`, `location`. У каталога нет общей координаты и нет расчётной потребности поста: эти поля равны `null`. Случайная координата мероприятия не становится координатой здания.

`events[]`: `id`, `code`, `title`, `business_date`, nullable `business_date_end`, `stage`, `visits`, `unresolved_posts`. Даты начала/окончания включительные. Для легаси-строки без даты окончания выборка использует день начала, сохраняя `business_date_end: null`. Закрытые мероприятия также входят в ответ за свой период. Этапы являются **последними сохранёнными** значениями, а не реконструкцией этапа на прошлую дату; процента готовности нет.

`visits[]`: `id` площадки, nullable `object_id`, сохранённое `object_name`, nullable `visit_date`, `stage`, `placement_need`, `placement_assigned`, `location`, `posts`. Сохранённый `visit_date: null` сохраняется. Потребность и назначения следуют каноническому разрезу расчёта ОМ: у единственной площадки все посты её, у нескольких площадок неразмеченные посты не приписываются произвольно, а неизвестные итоговые числа остаются `null`. У полностью размеченной площадки без постов — известный ноль. Отсутствующая или нечисловая потребность импортного поста остаётся `null`, известное число назначений сохраняется; исходный JSON не изменяется.

Пост мероприятия содержит `id`, `source: "EVENT"`, nullable `passport_post_id` из сохранённого `sourcePostId`, `name`, nullable `sector_name`, `need`, `assigned`, `location`, nullable `outdoor`. Его `id` принадлежит расстановке ОМ и отличается от ID поста паспорта даже при одинаковом названии. `assigned` — фактическое количество строк назначения на этот пост в расстановке; сотрудники и строки назначений наружу не передаются.

`unresolved_posts` имеет тот же явный состав полей поста мероприятия. Здесь сохраняются строки расчёта, которые каноническое распределение не относит ни к одной существующей площадке: неразмеченные посты при нескольких площадках, ссылки на отсутствующую площадку и посты мероприятия без площадок. Сохраняются ID, потребность, фактическое число назначений и точка карты; площадка не угадывается. При пустом остатке возвращается `[]`. Эти строки не добавляются к итогам площадок, а неизвестные канонические итоги `(null, null)` остаются неизвестными.

Координаты `{latitude, longitude}` читаются существующим `map_locations.read(event)` из приватного GeoJSON: площадка по visit ID, пост по ID поста ОМ. Несохранённая точка равна `null`; недоступный или повреждённый файл возвращает 503 `PLACEMENT_MAP_UNAVAILABLE`, сохраняя обычный конверт ошибки Smart. Ошибка карты не выдаётся за успешную пустую карту.

`duty` содержит `count_basis: "UNIQUE_PEOPLE_ASSIGNED_DURING_BUSINESS_DATE"`, `allocated_headcount`, `placed_headcount`, `unplaced_headcount`, `objects`. Выбор состава и действительности почасовых назначений общий с журналом дежурств: канонический победитель статуса, активный сотрудник, срок, отмена, принимающий департамент и действительность места. Сам по себе проигравший кадровый статус человека не учитывает. Для кадрового наряда учитывается сохранённое место именно выигравшего источника; для почасового — действующее назначение, пересекающее выбранный день. Это назначенные **за дату**, а не текущая посещаемость.

`duty.objects[]`: `object_id`, сохранённое nullable `object_name`, `headcount`, `posts`, `groups`. Посты содержат `post_id`, nullable `post_name`, `headcount`; группы — `group_id`, nullable `group_name`, `headcount`. Человек учитывается один раз в каждом месте и один раз в объекте, даже при нескольких сменах. Одинаковые названия разных ID не объединяются. Снимки кадровых мест сохраняют ID и название удалённого поста или архивного объекта. Суммы дочерних мест могут превышать число уникальных людей в объекте, если человек назначен в разные места за день; суммы объектов могут превышать `placed_headcount` по той же причине.

Численность расстановки ОМ и `duty` являются разными источниками: общий итог их не складывает. `allocated_headcount` включает канонически выделенных на дежурство, `placed_headcount` — людей с известным сохранённым местом, `unplaced_headcount` — остальных. Сервис внутри читает кадровые источники для расчёта, но наружу отдаёт только числа и места; интеграционное право не даёт права на сырые кадровые маршруты.

Для проверки используются только временные PostgreSQL и приватное файловое хранилище тестов. Фокус: `python -m pytest -q organization_management/apps/ops/tests/test_digital_twin_api.py` из `PersonnelStatus/Personnel-Records`; регрессии общего журнала: `organization_management/apps/ops/tests/test_duty_register_roster.py` и `organization_management/apps/ops/tests/test_duty_dispatch.py`. Рабочую локальную БД и PostgreSQL Digital не пересоздавать.

Текущий раздел «Люди по графику» использует серверный коннектор к двум прежним маршрутам Smart: `GET /api/ops/objects/{id}/` и `GET /api/statuses/statuses/duty-assignments/?object_id=…&date=…`. Он не читает обезличенный `snapshot` выше: подключение ОМ и общей численности к экранам Двойника остаётся отдельной задачей. Право `digital_twin.read` не заменяет кадровые права этого коннектора.

Ограничения прежнего персонального контракта, подтверждённые чтением кода:

- `status.view` с областью может вернуть HTTP200 с частичным/пустым составом. При выдаче технической учётке ограниченных прав нужно проверить полноту по всем нужным подразделениям; `ready` не доказывает полноту списка. Для текущего глобального wildcard этот сценарий не воспроизведён.
- Паспорт отдаёт всю историю `passportVersions`, а HTTP-клиент Двойника ограничивает ответ2 МиБ: при росте истории возможен502. Требуется компактный контракт актуальных постов; повышать лимит без границ не следует.
- Кадровые идентификаторы прежнего API числовые; Двойник безопасно отвергает значения выше `MAX_SAFE_INTEGER`. Новый обезличенный контракт сохраняет строковые ID, но не подменяет персональный график.
- Групповая строка, пересекающая два прочитанных дня, учитывается в предупреждении до дедупликации и может завысить число исключённых назначений. На состав постов это не влияет.
