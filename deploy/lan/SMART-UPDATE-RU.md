# Smart Josparlau — обновление 20.10.2026

Это поставка **только для сервера Smart**: актуальные backend/frontend/proxy,
необходимые миграции, паспорт Аккорды с 20 редактируемыми постами и начальные
характеристики сотрудников. База, PostgreSQL/Redis, тома, пользователи, права,
адреса и настройки действующей установки сохраняются. Интернет не требуется.
Приложение и БД цифрового двойника сюда не входят.

Требования: Linux/amd64 Docker, Compose v2 (проверяется также 2.17.2), Python3.9+,
существующая установка LAN на PostgreSQL16. Применение выполняется в окно
обслуживания: интерфейс и фоновые задания временно останавливаются; внешние
программы, напрямую записывающие в БД, нужно приостановить отдельно.

## 1. Распаковать и проверить

Скопировать ZIP и его `.sha256` в обычный каталог обновлений Smart, войти в Bash:

```bash
set -euo pipefail
umask 077
sha256sum -c Smart-Josparlau-update-2026-10-20.zip.sha256
python3 -m zipfile -e Smart-Josparlau-update-2026-10-20.zip update-2026-10-20
cd update-2026-10-20/smart-josparlau-update-2026-10-20
sha256sum -c SHA256SUMS
```

Внешняя `.sha256` проверяет весь ZIP. `SHA256SUMS`, `release.json` и граф
миграций связывают файлы и образы внутри. Исходный пакет данных дополнительно
проверяется по закреплённой SHA256 и всем своим внутренним контрольным суммам.

## 2. Обновить действующее приложение

`STACK` — прежняя папка, где находятся `.env`, `images.env`, `docker-compose.yml`.
Для известного стека из этой установки:

```bash
STACK="$(docker inspect smart-josparlau-lan-backend-1 --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')"
python3 update-with-migrations.py --stack "$STACK" --check
python3 update-with-migrations.py --stack "$STACK" --apply
```

Если имя backend отличается, посмотреть `docker compose ls` и указать фактический
путь в `STACK` явно. Выполнять `--apply` только после `SCHEMA CHECK PASSED`.
Результат — `UPDATE PASSED`. `--check` не останавливает сервисы и не меняет БД.

Это новый выпуск с полным графом миграций из его образа. Разрешённый переход
включает `employees.0006–0007`, `operations.0132–0145`, `statuses.0005`, из которых
исполняются только ещё не применённые шаги в проверенном порядке. Неизвестная
история или более старая схема отклоняются до остановки. Старый пакет/patch17.10
не нужен. При уже актуальной схеме выполняется безопасное обновление приложения
без миграций. Повтор также делает backup и проверяет данные.

Обновлятор сохраняет конфигурацию и меняет только три образа приложения.
Нестандартные startup/config overlays, скрывающие проверенную конфигурацию
прокси, требуют отдельного разбора и отклоняются до записи.

## 3. Один раз выбрать боевые ID

```bash
python3 import-smart-data.py --stack "$STACK" ids
```

По выводу выбрать действующего администратора и **реальный шестой департамент**:

```bash
ACTOR_ID='ЗАМЕНИТЬ_ID_АДМИНИСТРАТОРА'
DEPARTMENT_ID='ЗАМЕНИТЬ_ID_ШЕСТОГО_ДЕПАРТАМЕНТА'
DEPARTMENT_NAME='ЗАМЕНИТЬ_ТОЧНЫМ_НАЗВАНИЕМ_ИЗ_ВЫВОДА'
OBJECT_ARGS=()
```

Номера с ноутбука не подставляются. У администратора проверяются активность,
глобальное `object.manage`, права на указанный департамент и штатные полномочия
начального заполнения: `personnel.view`, `orgstructure.manage`, `admin.roles`.
Каталог сам не назначает права, не создаёт учётки и не меняет оргструктуру.

## 4. Проверить и импортировать

```bash
RUN_ROOT="$STACK/backups/updates/akorda-$(date +%Y%m%d-%H%M%S)-$$"
python3 import-smart-data.py --stack "$STACK" check --actor-id "$ACTOR_ID" --department-id "$DEPARTMENT_ID" --department-name "$DEPARTMENT_NAME" "${OBJECT_ARGS[@]}" --backup-root "$RUN_ROOT"
python3 import-smart-data.py --stack "$STACK" apply --actor-id "$ACTOR_ID" --department-id "$DEPARTMENT_ID" --department-name "$DEPARTMENT_NAME" "${OBJECT_ARGS[@]}" --backup-root "$RUN_ROOT"
cp "$RUN_ROOT"/apply-*/smart-applied.json ./smart-applied.json
```

`check` не пишет в БД; планы сохраняются в `check-…`. `apply` ещё раз проверяет
план, останавливает писателей, делает и действительно восстанавливает backup
в отдельный PostgreSQL, затем применяет каталог и характеристики в одной
транзакции. Успешная квитанция находится в `apply-…/smart-applied.json`.

Если Аккорда уже существует, инструмент остановится без подбора по имени.
Нужна явная привязка существующего объекта и всех секторов/постов. Формат
`mapping.json` описан в исходном `smart-data/SMART-AKKORDA-2026-10-20.tar.gz`,
файл `SMART-AKKORDA-2026-10-20/OBJECT-IMPORT.md`. Например, перед повторным check:

```bash
OBJECT_ARGS=(--target-object-id 'БОЕВОЙ_ID_ОБЪЕКТА' --mapping '/закрытый/путь/mapping.json')
```

Указанная привязка используется одинаково в `check` и `apply`. Повтор того же
экспорта сохраняет целевые ID и ручные изменения без дублей. Для повторной
проверки/применения выбрать новый `RUN_ROOT`, сохранив прежний batch ID.
Потерянная квитанция восстанавливается повтором по долговечной записи аудита.

Начальное заполнение охватывает всех существующих сотрудников: только отсутствующие
оценки5/5/5, рост180см и вес75кг. Уже внесённые значения, здоровье и имущество
сохраняются. Оно записывается как начальное заполнение, а не аттестация/измерение.
Batch всегда `akorda-initial-profiles-20261020`; повтор сохраняет и последующие
ручные очистки полей. Все сведения остаются редактируемыми в карточке сотрудника.

## 5. Назначения и ротации

После импорта открыть «Объекты и паспорта» → Аккорда: два сектора и 20 постов
редактируются обычным способом. Каталог не связан с ОМ второго департамента.
Для шестого источник — его собственные «Статусы сотрудников»: «На дежурстве» →
«Постовое» → Аккорда → конкретный пост → даты → «Добавить выход».

Задать реальные интервалы, например08:00–10:00 и12:00–14:00. Для ночного выхода
23:00–01:00 выбрать дату окончания следующего дня. Начало включено, конец
исключён; соседние смены не учитываются одновременно. Больничный/отпуск и область
доступа имеют обычный приоритет. Только даты означают неизвестные часы.
Приложение не создаёт вымышленные назначения или подтверждения присутствия.
Ознакомление и фактическое заступление учитываются отдельно в журнале.

Вооружение/магазины/гранаты/прочее с количеством, оценки1–5, рост/вес и внесённые
сведения о здоровье редактируются через карточку сотрудника. Это текущий профиль,
а не ведомость выдачи вооружения на историческую смену. Кадровые права проверяются
отдельно; одно право читать статусы не открывает эти дополнительные сведения.

## 6. Проверить API и передать квитанцию

Использовать сетевой адрес **сервера Smart**, доступный с сервера двойника.
Внутренние имена контейнеров и localhost не подходят. В приватном JSON-файле
с правами600 задать `{"username":"…","password":"…"}` действующей учётки чтения.
Пароль не передавать аргументом команды. Нужны `object.view`/`status.view` в нужной
области и отдельные кадровые права, если требуются служебные характеристики.

```bash
python3 import-smart-data.py verify-api --origin 'http://АДРЕС_SMART:ПОРТ_API' --credentials '/закрытый/путь/smart-reader.json' --receipt ./smart-applied.json --date "$(date +%F)"
```

Проверяются паспорт/20 постов и полный ответ `duty-assignments` с
`source=employee_status&department_id=…`, включая пустой scoped-ответ. Квитанция
содержит боевые ID и не содержит кадровых сведений/паролей. Передать на сервер
двойника **только полученный `smart-applied.json`**. Тестовой квитанции в ZIP нет.
Дальнейшее сопоставление и сетевое подключение выполняются на сервере двойника
отдельно; прямого подключения к БД Smart не требуется.

## Резервные копии и сбой

Обновление: `STACK/backups/updates/schema-ДАТА-ID` либо каталог обычного
application-only backup, если миграций нет. Импорт: `$RUN_ROOT/apply-ДАТА-ID`.
Внутри находятся `database.dump`, конфигурация/файлы, отпечатки и результаты
пробного восстановления. Доступ к backup должен оставаться закрытым.

При отказе проверки не продолжать следующие команды. До начала рабочей записи
прежнее приложение возобновляется только после доказанной неизменности БД.
После попытки миграции/импорта при неопределённом результате сохраняются backup,
`.offline-update-lock/owner.json` и `RECOVERY_REQUIRED.json` (для импорта —
`DATA-RECOVERY-REQUIRED.json` и `live-data.json`); интерфейс остаётся
закрытым. Рабочая БД автоматически не восстанавливается и назад не мигрируется.
Старый образ нельзя считать совместимым с новой схемой только по его запуску.
Для восстановления сначала определить стадию по протоколам и проверить копию
на отдельном PostgreSQL; не удалять lock и не накатывать старые пакеты вслепую.
