# Обновление сервера одной командой

Для пакета **20.10.2026** используйте `SMART-UPDATE-RU.md` и
`update-with-migrations.py --check`, затем `--apply` с путём действующей установки.
В пакет включён новый граф и рассмотренные17миграций, включая employees0007 и operations0145;
подробности — `SCHEMA-TRANSITION-RU.md`. Ниже описан сохранённый строгий
режим `update.py` для схемы, которой миграции уже не требуются.

Для существующего комплекта LAN: Docker Compose v2, Linux-контейнеры amd64,
PostgreSQL 16, Python 3.9+. Интернет на сервере не нужен.

## Запуск

Распакуйте **новый пакет обновления в отдельную папку**, перейдите в неё:

```bash
python3 update.py --stack /opt/smart-josparlau
```

Замените `/opt/smart-josparlau` на папку **действующей установки**, где лежат
`.env`, `images.env`, `docker-compose.yml`. Её можно увидеть в `docker compose ls`.
На Windows команда начинается с `python`. При единственном подходящем стеке
`--stack` можно опустить. Запускается один скрипт; остальные файлы пакета нужны ему
как зависимости — отдельно их запускать не требуется.

Проверить совместимость заранее, не останавливая приложение:

```bash
python3 update.py --stack /opt/smart-josparlau --check
```

## Что защищено

- Проверяются контрольные суммы, образы и принадлежность запущенных контейнеров
  указанной установке. Два обновления одновременно запрещены.
- **Миграции рабочей БД не запускаются.** Если новой версии нужна другая схема,
  обновление отклоняется до остановки приложения. Тогда нужен отдельно проверенный
  переход схемы для конкретной версии сервера; обходить отказ не следует.
- До остановки оценивается свободное место для копии и пробного восстановления.
- На время обновления отключаются интерфейс и фоновые задания. PostgreSQL и Redis,
  их контейнеры и тома остаются на месте. Длительность зависит от размера базы и файлов.
- Сохраняются БД, media/private/static и настройки. Копия восстанавливается в отдельный
  изолированный PostgreSQL; данные, колонки и состояния последовательностей сверяются.
- После запуска новой версии повторно сравниваются данные до открытия интерфейса
  и включения фоновых заданий. Адрес сервера и его `.env` сохраняются.

Сторонние программы, напрямую записывающие в БД, нужно остановить на окно обновления.
Скрипт не может остановить неизвестные интеграции. Копии содержат данные и секреты;
по умолчанию хранятся в `ПАПКА_УСТАНОВКИ/backups/updates/ДАТА-ID`.
Другой защищённый каталог задаётся `--backup-root /srv/backups/smart-josparlau`.

## Результат и ошибки

`UPDATE PASSED` и `SUCCESS.json` в папке копии означают завершение. Проверьте вход
и рабочую страницу на прежнем адресе сервера.

При сбое запуска скрипт проверит неизменность БД и вернёт прежние образы приложения
по их точным идентификаторам. Результат — `ROLLED_BACK.json`, код завершения ненулевой.
Рабочая БД автоматически не восстанавливается и не откатывается.

При несовпадении данных или неудачном откате приложение остаётся закрытым, а блокировка
сохраняется. Проверьте `ПАПКА_УСТАНОВКИ/.offline-update-lock/owner.json`: там указана
папка копии. В ней — `RECOVERY_REQUIRED.json` и доступные протоколы сравнения:
`database-before.json`, `database-after.json`. При раннем сбое часть этих файлов
или сама папка ещё не созданы. Сохраните имеющиеся файлы и вывод команды для разбора.
После обрыва питания/процесса блокировка также остаётся: повторный запуск откажется.
Удалять её или восстанавливать дамп поверх рабочей базы без разбора нельзя.
После жёсткого прерывания могут остаться временные контейнеры `sj-update-check-*`
или `sj-image-probe-*`: сначала проверьте их принадлежность, не используйте общую очистку томов.

## Удаление старых пакетов после успешного обновления

При необходимости добавьте явно указанный каталог **с пакетами проекта**:

```bash
python3 update.py --stack /opt/smart-josparlau --cleanup-root /srv/updates/Smart-Josparlau
```

Очистка выполняется внутри той же блокировки только после `UPDATE PASSED`, проверки
восстановленной копии и неизменности рабочей БД. При `--check`, отказе или откате
удаления нет. Интернет не требуется. Приложение уже работает, пока проверяются старые архивы.

Удаляются только непосредственные дочерние ZIP/каталоги с корректным `release.json`,
образами Smart Josparlau backend/frontend и совпадающими хэшами всех файлов manifest.
У распакованного пакета допустима одна внешняя папка. Состав ограничен файлами
обновления и Python-кешем; полная установка с `source`, `.env`, данными либо любым
неизвестным файлом сохраняется. Каждый кандидат проверяется повторно перед удалением.

Сохраняются текущая версия и **одна последняя предыдущая версия пакета** — все её
распознанные копии; предыдущая выбирается по последнему времени изменения пакета.
Также защищены действующая установка, запускаемый обновлятор, резервные копии,
Compose-каталоги и подключённые пути всех контейнеров, включая остановленные.
Ссылки и точки монтирования пропускаются. Docker images/контейнеры/volumes и другие
проекты эта функция не удаляет. Старые полные установки автоматически не считаются мусором.

План и результат: `CLEANUP-PLAN.json` и `CLEANUP.json` рядом с `SUCCESS.json` в новой
резервной копии. Статус `complete` означает завершение, `partial` — остановку при
изменении/ошибке файлов, `refused` — отказ по защите. Успешное приложение из-за
необязательной очистки не откатывается; причина печатается отдельно.

Посмотреть кандидатов отдельно, без удаления:

```bash
python3 cleanup-old-releases.py --stack /opt/smart-josparlau --updates-root /srv/updates/Smart-Josparlau
```

Предварительная команда не имеет режима удаления. Самостоятельно передавать или
редактировать сохранённый JSON-план для удаления нельзя: обновлятор строит новый план.

## Подготовка пакета разработчиком

Из чистого сохранённого коммита: `python deploy/lan/build.py prepare`, затем
`python deploy/lan/build.py build /новый/каталог/поставки`. Первый шаг получает
зависимости через интернет, второй собирает образы без сети. Пакет содержит
`update.py`, служебные модули, `release.json` и `application-images.tar`.
База ноутбука и его `.env` в обновление не входят. Сам скрипт без образов не является
готовым обновлением. Старые названия `obnovit-bez-bazy.py` и `update-app-only.py`
оставлены как совместимые входы в тот же безопасный режим. Прямой запуск старого
миграционного `update-offline.py` отключён; файл используется как внутренняя библиотека.
