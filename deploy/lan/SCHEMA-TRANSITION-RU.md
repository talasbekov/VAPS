# Проверенный переход схемы в поставке 20.10.2026

Пакет `Smart-Josparlau-update-2026-10-20.zip` содержит backend/frontend/proxy и все файлы перехода. Источник зафиксирован в `source-revision.txt` и `release.json`; полный граф из построенного образа с SHA256 файлов находится в `migration-graph.json`. `schema-transition.json` связывает граф, новую политику20.10, исходники и образы. Подробные команды и импорт Аккорды — в `SMART-UPDATE-RU.md`.

## Поддерживаемые состояния

Прежние patch/fix17.10 на этот выпуск не накладываются. Проверка учитывает только доказанное lossless распределение array cast в двух точных enum-CHECK, сохраняя все их значения и порядок, включая новый вариант STATUS. Остальная схема сравнивается без ослабления.

- Нет ожидающих миграций: выполняется защищённое обновление только приложения.
- Ожидающие миграции из рассмотренного набора17 шагов: `employees.0006–0007`, `operations.0132–0145`, `statuses.0005`. В том числе отдельно0144/0145/0007, если предыдущие уже установлены.
- Порядок берётся из полного графа нового образа; применённая история должна быть согласована. Каждый файл миграции проверяется по SHA256.

Более старые/неизвестные шаги, дубли, обратный порядок, несогласованная история и несовместимые импортные колонки отклоняются до остановки сервисов. Требования: Python3.9+, Linux/amd64 Docker, Composev2 (включая2.17.2), PostgreSQL16; шесть сервисов с worker/beat вместе либо семь с отдельным beat. Интернет не используется. Образы PostgreSQL/Redis сервера не подменяются.

## Запуск

Из новой распакованной папки пакета:

```bash
STACK="$(docker inspect smart-josparlau-lan-backend-1 --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}')"
python3 update-with-migrations.py --stack "$STACK" --check
```

После `SCHEMA CHECK PASSED`, в окно обслуживания без пользователей и внешних записей в БД:

```bash
python3 update-with-migrations.py --stack "$STACK" --apply
```

Без `--apply` проводится только проверка. `update.py` остаётся строгим режимом без миграций и не обходит его отказ. Для полного нового выпуска используется `update-with-migrations.py`; команды распаковки находятся в `SMART-UPDATE-RU.md`.

## Что проверяет обновлятор

Проверяются manifest/контрольные суммы образов и модулей, точная принадлежность контейнеров указанной Compose-установке, версия PostgreSQL и свободное место. Общая блокировка исключает одновременное применение старого и нового обновлятора.

При установке останавливаются интерфейс, backend и планировщики, затем дожидаются остановки worker. В `ПАПКА_УСТАНОВКИ/backups/updates/schema-ДАТА-ID` сохраняются дамп БД, media/private/static, `.env`, images.env и Compose. Дамп восстанавливается в отдельный PostgreSQL на образе действующего сервера, без его сетей и томов. Проверяется точное совпадение восстановленной БД.

На копии выполняется только утверждённый план. Прежние таблицы, колонки и строки проецируются по исходным колонкам и первичным ключам; все значения, включая старые имена/активность/описания ролей и прав, остаются неизменными. Разрешены лишь новые служебные строки в перечисленных seed-таблицах. `ops_user_roles` не входит в исключения и сохраняется полностью. Рабочие последовательности ID защищены; служебные sequence могут продвигаться при добавлении разрешённых строк.

0144 использует `get_or_create`: добавляет `status.workspace`, `digital_twin.read`, роль `DIGITAL_TWIN_READER` и разрешённые новые связи. Имеющаяся пользовательская роль с тем же кодом сохраняет прежние настройки и права; ей нельзя автоматически приписывать состав новой стандартной роли. Учётные записи и пароли не создаются. `seed_operations` не запускается.

Только после успешной репетиции рабочая схема меняется одной транзакцией PostgreSQL с блокировкой прежних таблиц. В транзакции проверяются прежние данные и совпадение целевой схемы с репетицией. Новое приложение запускается без автозаполнения и повторных миграций; до открытия интерфейса и включения фоновых заданий повторно проверяются БД, файлы media/private и идентичность исходного контейнера/тома PostgreSQL.

## Завершение и ошибка

Успех: `UPDATE PASSED`, `SUCCESS.json` в резервной копии. Если схема уже актуальна, используется ветка без миграций и её обычный каталог резервной копии; повторное применение0144 не выполняется.

При отказе репетиции рабочая схема не меняется. Если прежнее состояние подтверждено, возвращаются старые образы приложения и сохраняется `ROLLED_BACK.json`.

После начала рабочей миграции при обрыве связи или неопределённом результате приложение остаётся закрытым. Нет автоматического восстановления поверх рабочей БД или обратных миграций. Сохраняются `.offline-update-lock/owner.json`, резервная копия, `RECOVERY_REQUIRED.json` и сведения контейнера миграции `live-migration.json`. Не удаляйте блокировку и не запускайте следующую миграцию до разбора.

Прежние серверные подразделения, сотрудники, ОМ, учётные записи и файлы не заменяются данными ноутбука. Локальная связь Аккорды с Двойником и изменения приложения Двойника в пакет не входят. Старые пакеты и Docker-ресурсы автоматически не удаляются.
