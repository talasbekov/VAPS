# Smart Жоспарлау — обновление приложения 28.10.2026, выпуск r7

## Рекомендуемый запуск одним файлом на Linux

Скопировать `Smart-Update-2026-10-28-r7.sh` в `/home/user/` на сервере.
Когда пользователи закончат работу, выполнить:

```bash
bash /home/user/Smart-Update-2026-10-28-r7.sh
```

Файл содержит весь проверенный ZIP с образами. Сам проверяет встроенную
контрольную сумму, распаковывает в новую приватную папку `smart-update-*`
в текущем каталоге и проверяет каждый файл, принимая LF и CRLF в SHA256SUMS.
Затем запускает `update-with-migrations.py --apply`: тот находит действующий
стек, проверяет совместимость до остановки приложения, делает резервную копию
серверных данных и пробное восстановление, выполняет миграции и обновляет образы.
Нужны права на Docker и запись в текущий каталог и папку установленного Smart.
При нескольких установках автоматический выбор останавливается; можно передать
`--stack /папка/нужного/Smart`. Параметр `--check` выполняет только проверку
совместимости, `--verify-only` — только распаковку и проверку файлов без Docker.
Ожидать `UPDATE PASSED`. При ошибке сохранить вывод и резервную копию;
не удалять lock и не восстанавливать базу вручную вслепую.

Отдельный ZIP и ручная распаковка не требуются.

Выпуск r7 исправляет карточку дежурства: подтверждение явно сохраняется текущим
временем сервера, ручное фактическое время доступно для начала и завершения.
Длинное слитное примечание переносится внутри карточки на узком экране.
На новом образе через настоящий backend проверены восстановление сохранённой
записи после обрыва ответа и изменения прав, отдельные отметки исполнения,
закрытие несохранённой попытки и отказ её позднего повтора без создания дубля.

Сохранено исправление r6 ширины формы шаблонов дежурств: длинное слитное примечание
переносится внутри диалога, поля и кнопки остаются в его пределах. Проверены
личная видимость и доступ подразделения, изменение общего шаблона коллегой,
точный повтор после потери успешного ответа, устаревшие версии и мягкое удаление

сохраняет выбранного сотрудника и сама не создаёт запись дежурства.

Сохранены исправления r5: кэш наряда учитывает пользователя, права и области ролей.
После отзыва доступа к подразделению его прежние строки исчезают до нового
ответа сервера, даже если коды прав остались прежними; поздний старый ответ
не возвращает эти строки. Также исправлен перенос длинного имени проверяющего
в мобильной карточке обследования без сокращения текста. Проверены настоящий
черновик, завершение, устранение замечания вторым сотрудником, повтор без дубля
и отказ исходного запроса после отзыва права на отдельных учебных базах.

Сохранено исправление r4 мобильной истории квалификаций: длинное имя автора
переносится внутри карточки и остаётся видимым целиком. Проверены сохранение
четырёх оценок, порядок истории, сроки действия, повтор без дублирования и
отказ после отзыва права на учебной базе через настоящий backend.

также распознаёт проверенные эквивалентные записи PostgreSQL для списков значений

операторы и остальные условия продолжают сравниваться строго. Новых миграций
сверх первого выпуска 27.10 нет. В выпусках до r6 нет исправления ширины формы
шаблонов; в выпусках до r7 нет новых исправлений времени подтверждения

В поставке актуальные backend/frontend/proxy, пошаговые уточнения помощника,

## Постоянный доступ API и worker к модели

В исходном шаблоне от 27.10.2026 `backend` (проверка подключения) и `worker`
(фоновая обработка поручений) подключены к внутренней `default` и обычному мосту
`ingress`. Redis и frontend остаются во внутренней сети. Новых опубликованных
портов нет. Обычный мост даёт общий исходящий маршрут; ограничения назначения
и порта задаются правилами сети сервера, а не этим Compose.

До остановки приложения обновлятор проверяет исходный и предложенный Compose
через `docker compose config`: допускается только добавление `ingress` к
`backend` и/или `worker`. Поддерживаются внутренняя `default` и `ingress` с
`driver: bridge`, прежнее отсутствие `networks` у этих сервисов или простой
список `[default]`. Если обе сети уже подключены, файл не переписывается.
Иная топология, нестандартный синтаксис изменяемого блока или дополнительные
сетевые параметры требуют отдельного разбора: обновление откажет до остановки.

После остановки, резервного копирования и пробного восстановления обновлятор
атомарно записывает только необходимые строки в действующий `docker-compose.yml`.
Остальные байты, комментарии, права, владелец и группа файла сохраняются.
Полная исходная копия лежит в папке резервного копирования рядом с
`compose-network-transition.json` с хэшами и перечнем изменённых сервисов.
Это выполняется и тогда, когда миграций БД уже нет. `--check` проверяет
предложенное изменение без записи Compose и без остановки приложения.

Если запуск не удался и данные не менялись, безопасный откат восстанавливает
исходный Compose вместе с прежними образами. После попытки миграции автоматический
откат не выполняется: приложение остаётся закрытым, резервная копия и lock
сохраняются для разбора. Не менять Compose во время работы обновлятора.

После успешного обновления проверить подключение в `/settings/ai` и выполнить
одно реальное поручение с фоновой обработкой. Для отдельной проверки TCP
перейти в действующую папку Smart, где лежат серверные `.env`, `images.env` и
`docker-compose.yml`, и выполнить, подставив фактический адрес модели:

```bash
smart_compose() {
  docker compose --project-directory "$PWD" --env-file images.env --env-file .env -f docker-compose.yml "$@"
}
for service in backend worker; do
  smart_compose exec -T "$service" python -c 'import socket; connection = socket.create_connection(("10.15.3.100", 8002), timeout=5); connection.close(); print("Model TCP reachable")' || break
done
```

TCP-проверка подтверждает маршрут и порт; ключ, совместимость API, имя модели
и генерацию проверяет приложение. Доступность только с хоста или из API
не подтверждает работу worker. Настройки ИИ в БД сетевой переход не меняет.

## Подключить помощника ОМ к серверу ИИ

После обновления войти администратором и открыть «Администрирование» →
«Подключение ИИ» (`/settings/ai`). Выбрать совместимый API, указать адрес,
название модели и при необходимости ключ. Нажать «Проверить соединение»,
затем «Сохранить». Проверка использует введённые сведения и сама их не сохраняет.
Сохранённый ключ обратно в браузер не выдаётся; пустое поле сохраняет прежний
ключ при том же сервере. Для смены сервера прежний ключ нужно явно заменить
или удалить.

В документации «Цифрового двойника» ранее записаны адрес
`http://10.15.3.100:8002` и модель `gemma-4-31b-it`. Это примеры для сверки
с фактическими настройками сервера, а не автоматически включённое подключение.
Поставка не содержит ключей и не записывает демонстрационные настройки в БД.
Проверять доступность модели нужно с сервера приложения. Обычным пользователям
экран недоступен. Новая таблица настроек создаётся пустой; сохранённые настройки
в последующих обновлениях остаются серверными.

## Сохранность данных и требования

Внутри готовые Linux/amd64 образы backend/frontend/proxy и обновлятор.
**База остаётся существующей базой боевого сервера.** Дампа ноутбука,
учебных сотрудников, дежурств, оценок, паролей и локального `.env` в пакете нет.
Импорт данных и начальное заполнение не запускаются.

Требуются существующая LAN-установка Smart, Docker с Compose v2,
PostgreSQL16 и Python3.9+. Интернет на сервере не нужен. Адреса, `.env`,
базы PostgreSQL/Redis, тома, пользователи, назначения ролей, media/private
сохраняются. В Compose меняется только описанное подключение API/worker к
существующей сети; остальные серверные настройки сохраняются.
«Цифровой двойник» этим пакетом не обновляется.

На время обновления пользователи должны закончить работу; внешние программы,
пишущие непосредственно в БД, остановить отдельно.

Обновлятор останавливает приложение и фоновые задания, сохраняет базу и файлы
**сервера**, восстанавливает эту копию в отдельном PostgreSQL и проверяет
сохранность прежних строк. Только затем выполняет проверенные миграции
в существующей рабочей базе и меняет образы приложения. Дамп не загружается
поверх рабочей базы. `seed_operations` и импорт данных не выполняются.

Разрешены только ещё не применённые шаги из рассмотренного набора:
employees0006–0008, operations0132–0154, statuses0005. В том числе добавляются
таблицы помощника, диалогов, шаблонов, квалификаций и проверок объектов,
а также метаданные проверки подключения и формата ключа ИИ. Существующие строки,
права пользователей и серверные настройки подключения не переписываются.
Неизвестная или более старая схема отклоняется до остановки приложения.
Если миграций нет, выполняется обновление приложения с теми же проверками.

Ожидать `UPDATE PASSED`. Протокол `SUCCESS.json` и резервная копия находятся
в `STACK/backups/updates/schema-ДАТА-ID`. Открыть прежний адрес Smart
(для этой установки ранее `http://10.15.3.251:3300`) и проверить вход,

При ошибке не запускать следующие команды. Сохранить вывод, резервную копию
и `.offline-update-lock/owner.json`, если он остался. При неопределённом
результате миграции приложение остаётся закрытым; база автоматически назад
не восстанавливается. Не удалять lock и не ставить старый образ вслепую.

`update.py` и `obnovit-bez-bazy.py` — прежний строгий режим без миграций;
для этой поставки использовать единый файл `.sh`, который запускает нужный режим.

## Хранение ключа ИИ в выпуске 27 октября

При сохранении настроек новый ключ ИИ записывается в БД в зашифрованном виде.
Прежние записи продолжают читаться без изменения данных; они переводятся при
явном сохранении или обслуживании. Миграция добавляет только признак формата,
не переписывает существующие ключи и не меняет параметры модели.
Результат явной проверки подключения хранит время, успех, провайдера, модель
и связь с проверенной версией. Адрес, ключ и тело ответа модели туда не попадают.

По умолчанию ключ шифрования производится из существующего `DJANGO_SECRET_KEY`
с отдельным назначением. Сохраняйте резервную копию серверного `.env` вместе
с соответствующей копией БД, отдельно от публичного пакета: одного дампа БД
недостаточно для восстановления зашифрованного ключа.
Не заменяйте `DJANGO_SECRET_KEY` случайно при переезде или обновлении.
При утрате серверного секрета администратор сможет явно ввести новый ключ API
или удалить сохранённый через `/settings/ai`; повреждённые данные не отправляются
на сервер модели как ключ.

Для отдельного управления ключами допускается `OPS_ASSISTANT_CREDENTIAL_KEYS`:
список Fernet-ключей через запятую, первый используется для новых записей,
остальные временно сохраняются для чтения прежних. Если параметр пуст,
используется серверный секрет. `DJANGO_SECRET_KEY_FALLBACKS` поддерживает
временное чтение прежних серверных секретов при их плановой смене.
В исходном Compose оба параметра передаются backend и worker одинаково.
При обновлении существующего Compose меняются только сети: дополнительные
переменные для ручной ротации автоматически не добавляются. Обычная работа
использует прежний `DJANGO_SECRET_KEY` без нового параметра. Для отдельной
настройки ротации одних новых строк в `.env` недостаточно, если в Compose
отсутствует передача этих переменных обоим сервисам.
Ключи не размещают в Git, протоколах, переписке или общей инструкции.

После резервного копирования и согласованного переключения ключей backend/worker
проверка необходимости перешифрования выполняется без записи:

```bash
smart_compose exec -T backend python manage.py rotate_assistant_credentials
```

Только явный запуск с `--apply` меняет способ хранения:

```bash
smart_compose exec -T backend python manage.py rotate_assistant_credentials --apply
```

Функция `smart_compose` определена выше для существующей установки.
Команда не выводит ключ, не меняет адрес, модель или версию настроек и не делает
сетевых запросов. Сначала сохраните старый ключ в списке, выполните перевод,
проверьте чтение новым ключом, затем удаляйте старый из активного окружения.
Старые резервные копии всё ещё требуют соответствующего старого ключа.

Образы до этого изменения не понимают зашифрованный формат. После первого
сохранения/перевода нельзя откатывать только backend на прежний образ:
используйте согласованную резервную копию приложения, БД и серверных секретов.
Эти действия на production в ходе разработки не выполнялись.
