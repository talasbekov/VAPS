# Smart Josparlau — чистая установка в закрытой сети

Эта инструкция — для нового пустого контура. Обновление работающего приложения и его автоматическая резервная копия описаны в [UPDATE-RU.md](UPDATE-RU.md). `install.sh` не проверяет, что обычный запуск выбран именно для новой базы: не используйте его как команду обновления существующего стека.

## Требования

- Linux x86_64, Docker с доступом к Linux-контейнерам, Docker Compose **2.17.2 или новее** (`docker compose`). Платформа должна совпасть с `platform.txt` комплекта.
- `bash`, `python3`, `sha256sum`, `tar`, `gzip`; назначенный серверу IPv4 и три свободных порта. По умолчанию: портал **3300**, backend **8300**, PostgreSQL **5300**.
- Ориентир для небольшого стенда: 4 ядра, 8 ГБ RAM, 40 ГБ свободного диска и отдельное место для резервных копий. Это не результат нагрузочного испытания.
- Верные часы; деловой часовой пояс — `Asia/Almaty`. Доступ к порту PostgreSQL нужен только администраторам базы.

Интернет для установки не требуется: образы входят в комплект. Docker и Compose должны быть установлены заранее. Профиль использует HTTP; HTTPS требует отдельной настройки. Ограничение исходящей сети обеспечивает политика площадки.

```bash
docker compose version
docker info --format '{{.OSType}}/{{.Architecture}}'
```

## Установка

Перенесите весь каталог поставки, включая `runtime-images.tar.gz`, `images.env`, скрипты и файлы контрольных сумм. Работайте из этого каталога. При переносе архива сначала проверьте его сопроводительную SHA-256 сумму, затем распакуйте в новый каталог.

```bash
sha256sum -c sha256sums.txt
python3 configure.py --ip "IP_СЕРВЕРА"
bash install.sh
bash ctl.sh ps
bash ctl.sh logs --tail=50 backend worker
```

Замените `IP_СЕРВЕРА` назначенным IPv4. Для другого имени стека или портов укажите при создании настроек `--name`, `--frontend-port`, `--backend-port`, `--postgres-port`. Порты должны быть разными, в диапазоне 1024–65535. Имя нового стека не должно совпадать с существующим контуром.

`configure.py` создаёт закрытый `.env` с тремя независимыми секретами и не перезаписывает существующий файл. Не пересоздавайте секреты работающего стека: пароль PostgreSQL уже хранится в его томе. `.env` не входит в поставку; храните его защищённую копию отдельно.

`install.sh` проверяет суммы, настройки и платформу, загружает образы и ждёт готовности до десяти минут. Backend применяет миграции. Используются локальные образы без скачивания и сборки. Все шесть сервисов должны работать; планировщик beat встроен в worker, отдельного сервиса beat нет.

## Первый администратор

На новой базе заполните справочники, начальную структуру и права, затем создайте администратора:

```bash
bash ctl.sh exec backend python manage.py bootstrap_contour
bash ctl.sh exec backend python manage.py createsuperuser
```

Обычный bootstrap не создаёт демо-сотрудников и проверочные учётки. Не используйте `--demo` на рабочей площадке. Начальную структуру проверьте перед заполнением реальными данными.

Откройте `http://IP_СЕРВЕРА:8300/admin/`, войдите созданным пользователем. В «Доступ → Users» найдите его ID. В «Роли пользователей (ОМ)» создайте назначение: этот ID, роль `ADMIN`, пустая область подразделения, включённый `Is active`. Войдите заново в портал `http://IP_СЕРВЕРА:3300/`. Django-суперпользователь и роль портала назначаются отдельно; готовых аккаунтов и паролей в поставке нет.

Создайте реальные подразделения и сотрудников, свяжите учётки с кадровыми записями и назначьте рабочие права в нужных областях. Пустой личный профиль до связи с сотрудником ожидаем.

## Проверка и повторный запуск

С клиентского компьютера проверьте вход в портал и Django admin, загрузку фотографий после добавления, доступ обычной роли только к её подразделениям. На `http://IP_СЕРВЕРА:8300/docs` документация должна открываться без интернета. Проверьте плановый статус на отдельной учебной записи и журнал worker; работа контейнера сама по себе не подтверждает выполнение планового задания.

Для PostgreSQL по умолчанию используются порт 5300, база и пользователь `smart_josparlau`; пароль — `POSTGRES_PASSWORD` из `.env`. Это служебная учётка базы, не логин портала. Внутренние адреса `db:5432` и `backend:8000` не заменяйте внешними портами.

Остановка и повторный запуск с сохранением томов:

```bash
bash ctl.sh down
bash ctl.sh up -d --pull never --no-build --wait --wait-timeout 600
```

Не добавляйте флаг удаления томов. Для обновления версии перейдите к [UPDATE-RU.md](UPDATE-RU.md).

## Резервные копии и восстановление

Резервная копия должна включать PostgreSQL, media и private uploads; `.env` хранится отдельно. Автоматический backup обновления описан в [UPDATE-RU.md](UPDATE-RU.md). Самостоятельную согласованную копию создаёт `bash data.sh backup /srv/backups/НОВЫЙ-КАТАЛОГ`: путь должен быть абсолютным и ещё не существовать. Скрипт временно останавливает вход и планировщик, ждёт опустошения очереди, останавливает worker, копирует базу и файлы, затем возобновляет прежние сервисы. Поддерживаются встроенный beat и отдельный сервис beat старой поставки. Планируйте окно обслуживания; при ошибке незавершённый каталог не считайте готовой копией, проверьте журнал и доступность приложения.

Существующий проверенный backup для `install.sh --restore` должен содержать `database.dump`, `media.tar.gz`, `private.tar.gz`, `postgres-version.txt` и `sha256sums.txt`. Требуется PostgreSQL 16. Проверяйте происхождение и версию приложения по `source-revision.txt`; запуск backend после восстановления может применить миграции. Для отката используйте совместимый сохранённый комплект.

Восстанавливайте только в новый каталог поставки с новым именем стека и пустыми томами. Пример отдельного контура на том же сервере; указанные порты должны быть свободны:

```bash
python3 configure.py --ip "IP_СЕРВЕРА" --name smart-josparlau-restore --frontend-port 13300 --backend-port 18300 --postgres-port 15300
bash install.sh --restore /srv/backups/ПРОВЕРЕННАЯ-КОПИЯ
```

Ни обычный `install.sh`, ни bootstrap перед этим не запускайте: они заполнят новую базу. Восстановление проверяет суммы, версию PostgreSQL, остановленное приложение и пустоту базы и файловых томов. Если операция прервана, сохраните журнал и разберите частично заполненный новый контур, не повторяйте восстановление поверх него. После восстановления не запускайте демо-наполнение.

Проверьте вход, роли, состав данных, скачивание закрытых файлов и плановые задачи восстановленного приложения. Redis и состояние планировщика в этой копии не переносятся. Сохраняйте исходный контур до проверки восстановления; записи после момента backup в восстановленной базе отсутствуют.
