# EXPORT-RECIPE — рецепт полной выгрузки донора + шаблон отчёта

> Дурабельный продукт спайка 1.11 и **вход эпика E7** (миграция). Рецепт делает
> реальную выгрузку механическим прогоном: команда `dumpdata` шести моделей →
> профилировщик → заполнить `EXPORT-REPORT`. Митигирует допущение **A1**.

---

## ⚠️ PII — прочитать ПЕРЕД выгрузкой

Полная выгрузка донора содержит **ИИН** (нац. идентификаторы, 12 цифр) и **ФИО** —
персональные данные.

- **Реальный `*.json`-дамп НИКОГДА не коммитится.** `.gitignore` в этом каталоге
  запрещает всё, кроме источников (`*.md`, `profile_export.py`, `.gitignore`).
- В репозиторий едут **только**: этот рецепт, `profile_export.py` и заполненный
  `EXPORT-REPORT` (**агрегатные числа**, без сырых строк).
- `profile_export.py` маскирует примеры (`ИИН …1234 ×2`), сырые значения не печатает.
- Утечка PII в git **необратима** (история). При сомнении — не коммить.

## Рецепт выгрузки (`manage.py dumpdata`)

Выгружаются **ровно шесть** моделей, которые ест импортёр 1.6
(`apps/migration_legacy/.../import_donor_slice.py`). Явный список — НЕ полный
`dumpdata` (он тянет `auth`/`contenttypes`/`admin`/`sessions`: лишний объём и
**лишний PII**).

Строки моделей подтверждены по `donor_slice.json` (поля `model`) и импортёру 1.6
(как он группирует `by_model[...]`), а НЕ угаданы:

| # | Донор-модель (`app_label.model`) | Ключевые поля | Что профилируем |
|---|---|---|---|
| 1 | `divisions.division`       | `code` (unique), `parent` (MPTT), `division_type` | объём, целостность дерева (E7) |
| 2 | `dictionaries.rank`        | `pk`, `name`, `level` («меньше=выше», НЕ инвертируется) | объём |
| 3 | `dictionaries.position`    | `pk`, `name`, `level` | объём |
| 4 | `employees.employee`       | `iin` (12 цифр, unique), `personnel_number` (unique), `pk` | дубли ИИН, дубли табельных, NULL/невалидные ИИН |
| 5 | `staff_unit.staffunit`     | `division` FK, `position` FK, `employee` (вакант=NULL) | объём, вакансии |
| 6 | `statuses.employeestatus`  | `employee` FK, `status_type`, `start_date`/`end_date`/`actual_end_date` | осиротевшие (employee pk вне множества), объём |

> Идентичность (для E7, НЕ здесь): `donor_pk → external_id`, `iin → iin`,
> `personnel_number → personnel_number`. Спайк лишь МЕРЯЕТ дубли/NULL ключей;
> merge-стратегию строит 7.3.

### Команда (на ПРОДе донора, в его окружении)

```bash
# 0. SANITY-CHECK: убедиться, что live-AppConfig донора даёт ТЕ ЖЕ строки model,
#    что в donor_slice.json (на этой dev-машине исходник донора отсутствует —
#    фикстура авторитетна, но прод-реестр приложений подтверждается одной строкой):
python manage.py dumpdata employees.employee --format json --indent 2 | head -n 8
#    Ожидаем "model": "employees.employee". Если префикс иной (напр. вложенный
#    app_label organization_management.*), заменить строки моделей ниже на реальные.

# 1. Полная выгрузка ШЕСТИ моделей в один файл (UTF-8, отступ для читаемости):
python manage.py dumpdata \
    divisions.division \
    dictionaries.rank \
    dictionaries.position \
    employees.employee \
    staff_unit.staffunit \
    statuses.employeestatus \
    --format json --indent 2 \
    --output donor-export-FULL.json
#    Имя donor-export-*.json уже в .gitignore (не закоммитится).

# 2. Профилирование (числа для EXPORT-REPORT, PII маскирован):
python3 profile_export.py donor-export-FULL.json
```

**Ожидаемый формат** (импортёр 1.6 завязан на него строго): JSON-массив
`[{"model": "app_label.model", "pk": N, "fields": {...}}, ...]`, кодировка UTF-8
(кириллица в `name`/ФИО сохранена). Если реальный формат разошёлся с образцом
(иные строки моделей, иные имена полей, экзотические значения) — отдельная строка
отчёта как вход для **7.1**.

## Шаблон `EXPORT-REPORT` (заполнить по факту)

Заполняется в `EXPORT-REPORT.md`. Каждый факт помечается маркером:
**`VERIFIED-on-prod`** (реальная выгрузка) · **`apparatus-verified-on-sample`**
(прогон на `donor_slice.json`) · **`PENDING-prod-access`** (доступ к проду не
получен — путь B).

```
СПОСОБ ДОСТУПА   : <как физически получена выгрузка: dumpdata на проде / SQL-дамп /
                   экспорт от админа донора>                     [маркер]
ФОРМАТ           : Django dumpdata JSON [{model, pk, fields}], UTF-8 — совпал с
                   образцом? <да / расхождения: ...>             [маркер]
ОБЪЁМ (строк/модель):
    divisions.division      : N
    dictionaries.rank       : N
    dictionaries.position   : N
    employees.employee      : N
    staff_unit.staffunit    : N
    statuses.employeestatus : N                                   [маркер]
ВЛАДЕЛЕЦ ДОСТУПА : <кто выдаёт/поддерживает доступ — единая точка контакта E7;
                   где живёт прод донора (та же закрытая сеть, что A5?)> [маркер]
КАЧЕСТВО КЛЮЧЕЙ  :
    ИИН NULL/пустой          : N
    ИИН невалидный формат    : N
    ИИН дубли (значений)     : N   (примеры маскированы)
    табельный NULL/пустой    : N
    табельный дубли          : N
    осиротевшие статусы      : N
    вакантных слотов         : N                                  [маркер]
ДАТА/ОКРУЖЕНИЕ   : <дата выгрузки, версия Django донора, окружение> [маркер]
АНОМАЛИИ         : <формат не совпал / экзотические дубли / битая кодировка /
                   осиротевшие ссылки — вход для 7.1>
```

## Fallback (если доступ невозможен / формат непригоден) — ВХОД, не реализация

Если путь A провалился (нет доступа сейчас / формат непригоден), риск A1
реализовался — переключаемся на запасной план. **Строит это E7**, спайк лишь
фиксирует путь:

1. **Синтетическая фабрика по формам донора** — skeleton (E1) ест синтетику вместо
   реального среза; техническая часть E1 не блокируется. (deferred-механизм E7,
   триггер: provision parallel-run / fallback A1.)
2. **Доверие → построчная сверка с Excel владельца расхода (7.9 раньше)** — механизм
   доверия переключается с «эталон = донор» на «эталон = Excel-списки владельца».
   7.9 поднимается в очереди.

Реальную полную выгрузку при пути B делегируем **7.0** (стенд в контуре) / **7.1**
(профилирование), помечаем `PENDING-prod-access`, эскалацию A1 фиксируем заказчику.

## Находка → стори E7 (перенос результата спайка)

| Находка спайка 1.11 | Куда питает | Стори E7 |
|---|---|---|
| **формат** (dumpdata-форма, имена моделей/полей, версия Django) | профилирование грязи + правила обработки | **7.1** |
| **объём** (строк/модель) | бюджет производительности импорта; окно frozen-suite parallel-run | **7.1**, 6.9 |
| **способ доступа + владелец** | стенд в контуре / ежедневный доступ; импортёры | **7.0**, 7.2–7.3 |
| **качество ключей** (дубли ИИН/табельных, NULL/невалидные) | правила обработки грязи + merge-стратегия дублей идентичности | **7.1**, **7.3** |
| **осиротевшие** (статусы без employee, dangling parent) | правила обработки осиротевших ссылок | **7.1** |
| **провал доступа** (нет выгрузки / формат непригоден) | fallback: синтетическая фабрика + Excel-сверка | deferred E7, **7.9** |
