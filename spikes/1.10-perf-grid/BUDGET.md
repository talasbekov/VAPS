## 2. Как провести авторитетный замер (путь A, человеко-исполняемо)

1. **Собрать на dev (online):** `npm install && npm run build` → каталог `dist/` (статика, без Node-рантайма).
2. **Перенести `dist/` на целевую машину** (реальный клиентский ПК контура 4ГБ/FF~100 ИЛИ эталонная замена: 4ГБ-VM + архивный **Firefox 100 ESR**). На целевой Node НЕ нужен.
3. **Поднять статикой** (любой способ): `python3 -m http.server 8080` в `dist/`, либо nginx, либо `npm run preview` если на машине есть Node. Открыть в Firefox ~100.
4. **Слепой ввод 100 символов** (без мыши): кликнуть один раз в грид для фокуса (или Tab до него), далее только клавиатура — печатаемые символы пишутся в активную ячейку, `Enter`↓, `Tab`→, `Esc` отменяет правку ячейки. Ввести 100 символов, периодически перемещаясь.
5. **Списать с HUD** (зелёный оверлей справа сверху): TTI, p50/p95/max keydown→commit, commits/last key (должно быть 1), max commits/key, DOM-строк в гриде. Либо в консоли: `__vapsPerf.exportJson()`.
6. **Память вкладки — ВРУЧНУЮ из Firefox:** открыть `about:processes` (или `about:memory` → Measure) ПОСЛЕ ввода 100 символов, записать пик памяти вкладки. *(В Firefox нет `performance.memory` — инструментацией не снимается.)*
7. **Зафиксировать**: модель/ОЗУ машины и точную сборку Firefox (версия/ESR). Заполнить таблицу §4, пометить числа `VERIFIED-on-target`.

## 3. Методология (как меряется каждая метрика и оговорки)

| Метрика | Метод | Оговорка |
|---|---|---|
| **TTI** | `performance.now()` в момент монтирования App (≈ от navigation start). На ПРОД-сборке. | Грубый прокси «готова к вводу»; для спайка достаточно. Не `vite dev`. |
| **Память вкладки** | Firefox `about:processes` / `about:memory` ПОСЛЕ 100 символов | `performance.memory` в FF отсутствует → только ручное чтение. |
| **p95 keydown→commit** | `performance.now()` на keydown → дельта в `useLayoutEffect` (после коммита, до paint); выборка ≥100, p95 | Playwright на FF100 невозможен (architecture.md:258) → только in-page + HUD. Тайминги — тренд, не блок-гейт (architecture.md:244). |
| **commits/keystroke** | счётчик в `useLayoutEffect` без deps (тик на каждый коммит) | **НЕ через `<Profiler>`** — его onRender но-оп в прод-сборке (см. §6, находка). Инвариант: edit-keystroke = 1 коммит. |
| **DOM-строк в гриде** | `querySelectorAll('[data-grid-row]').length` на HUD | Инвариант виртуализации: ≈ окно (десятки), не ~1000. |
| **bundle initial gzip** | отчёт `vite build` | Информационно; канон-бюджет ≤300 КБ gzip (architecture.md:231). |

## 5. Apparatus-smoke (dev, headless Chromium) — НЕ перф-бюджет

Прогон на dev-ноутбуке через headless Chromium (`google-chrome`, режим shell), 100 keystroke (30 правок in-place + 70 со смешанной навигацией). **Chromium ≠ FF100, dev-ноут ≠ 4ГБ — тайминги ниже НЕ являются бюджетом E9.** Цель прогона — доказать, что АППАРАТ замера корректен, чтобы прогон на FF100 свёлся к механическому списыванию с HUD:

- console: **чисто** (favicon подавлен `<link rel=icon data:,>`).
- DOM-строк: **30** (не меняется со вводом) → виртуализация работает.
- edit-commit-delta: **30 / 30** → ровно 1 коммит на edit-keystroke на ПРОД-сборке.
- max commits/key: **1** → навигация (Enter/Tab+scrollToIndex) не каскадит.
- samples_n: **100**, p95: **0.5 ms**, max: **1 ms**, TTI: **~137 ms** — *(Chromium/dev — не бюджет, только подтверждение, что числа вычисляются)*.

## 6. Находки спайка

1. **`build.target: 'firefox100'` — обязателен и работает.** Дефолт Vite 7 = FF≥104; явный `firefox100` в `vite.config.ts` собирается без ошибок (Vite 7.3.5, esbuild). Без него риск белого экрана на FF~100. Это центральная техническая проверка A9 — пройдена на этапе сборки.
2. **`<Profiler onRender>` — но-оп в стандартной ПРОД-сборке react-dom.** Инвариант «1 коммит/keystroke» нельзя мерить Profiler'ом на проде (нужна profiling-сборка). Здесь коммиты считаются через `useLayoutEffect`-тик (работает везде). **Вход для 9.8:** Profiler-инварианты в гейте 9.8 живут в Vitest/dev-окружении (там Profiler работает); рантайм-замер на проде — через layout-effect/иной механизм.
3. **Память — только вручную из Firefox.** `performance.memory` в FF отсутствует; не закладываться на него в 9.8.
4. **Бандл прототипа ~70 КБ gzip** — React 19 + TanStack Virtual укладываются с большим запасом под ≤300 КБ.

## 7. Гейт A9 — вердикт

- **Путь B (A9 открыт).** Целевое железо/FF~100 не подтверждено в dev-сессии; AI-агент не может физически провести слепой ввод на контурном ПК и снять память из `about:processes`. Аппарат собран и верифицирован на dev (headless Chromium) — числа §5 предварительные и НЕ являются бюджетом.
- **Авторитетный прогон делегирован** Bratan (путь A, §2) — на реальном клиентском ПК контура (можно совместить с 12.7, «тот же класс машины», см. 1.9) ЛИБО на эталонной замене (4ГБ-VM + FF100 ESR).
- **Предварительный вывод по A9:** риск белого экрана на FF~100 снят на этапе сборки (`firefox100`-таргет ок); виртуализация и 1-коммит-инвариант кода подтверждены. Открыто — абсолютные TTI/память/p95 на слабом железе (заполнить §4).
