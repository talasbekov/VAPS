## 1. Что измеряем и зачем

`architecture.md:49/466/624` и `NFR-4` предполагают асинхронную генерацию (Celery +
`AsyncJob` 202+поллинг). Story 6.5 оставила `issue_expense_document` СИНХРОННЫМ by
design. **Принцип отсечения механизмов** (`architecture.md:91-99`) требует: async
вводится по ИЗМЕРЕНИЮ, не по умолчанию. Меряем wall-clock генерации на реалистичном
объёме (~5000 сотрудников, `architecture.md:61`) по ДВУМ путям:

- **«Управление» (одна строка)** — целевой синхронный путь сегодня
  (`issue_expense_document`, лист дерева = один отдел/управление).
- **«Свод» (многострочный roll-up)** — ПО КОМПОНЕНТАМ: реальная стоимость
  `StrengthReportService.compute` по поддереву + одноразовый N-строчный адаптер →
  `generate_expense_docx`. Прод-генератор свода 6.6 НЕ строит (зона 6.10;
  `build_expense_document` одностроч by design Д11) — свод-документ как объект ещё
  не существует, его латентность измеряется загодя.

## 2. Порог отсечения sync→async — ЗАЯВЛЕН ДО ЧИСЕЛ (Q1, Bratan-overridable)

> Порог — интерактивный бюджет одного HTTP-POST, который руководство ждёт со
> спиннером после «выпустить расход». Заявляется ДО замера, чтобы не подгонять
> решение под числа (Ловушка №3).

**Q1 (дефолт):** синхронно, пока **p95 худшего реалистичного сценария < 2.0 с**;
жёсткий async-триггер при **p95 ≥ 2.0 с** ИЛИ **любой единичной генерации ≥ 5.0 с**.

Обоснование: ниже ~2с синхронное ожидание с loading-состоянием терпимо, а машинерия
202/поллинг (новая модель+миграция, worker+beat-контейнеры, `/api/jobs`, WS-ускоритель,
фронт `refetchInterval` — `architecture.md:466/624/337`) — существенная сложность, не
оправданная до ДОКАЗАННОЙ блокировки. **Пик-контенция 16:00–17:00 — вне этого порога**
(нагрузка дедлайна отдельно отложена — `ARCH-DEFERRED-045`, триггер «перед пилотом»);
6.6 меряет латентность ОДНОЙ генерации, не worker-starvation под пиком.

**Калибровка «ядро ≈ весь issuance»:** полный `issue_expense_document` (38.5 мс) =
чистое ядро (15–22 мс) + ORM-обвязка (derive×2 для release-ассерта + `allocate_number`
+ `create_attachment` sha256/запись файла + `IssuedDocument` + аудит ≈ +15–20 мс). Ядро
— добросовестный прокси issuance в пределах малой аддитивной константы; оба ≪ порога.

**PDF = fpdf2 нативно:** нет LibreOffice/subprocess/сети; ветка «деферрал PDF/LibreOffice»
(`epics.md:846`) НЕ активирована. Тяжёлой системной зависимости в air-gap контуре НЕТ —
это подтверждает эмпирику 6.4 (34мс/25КБ) на реалистичном объёме.

## 5. Вердикт: **СИНХРОННО ДОСТАТОЧНО** — AsyncJob деферится (ветка AC-5)

**Худший реалистичный сценарий сегодня** — выпуск расхода одного управления
(`issue_expense_document`) = **38.5 мс** (полный путь) / p95 ~22 мс (ядро). Это
**×52 под порогом 2.0 с** по полному пути. Ни одна единичная генерация не близка к
5.0 с (max наблюдён = 262 мс, свод-рендер). ⇒ **порог не превышен ни по одному
критерию Q1.**

**Запас держит даже на слабом железе:**

| Путь | dev p95/полн. | ×4 контур | ×10 контур (консерв.) | Вердикт |
|---|---|---|---|---|
| **Управление (issuance) — ТЕКУЩИЙ синхронный путь** | 38.5 мс | ~0.15 с | ~0.39 с | ✅ ≪ 2с c огромным запасом |
| Свод: `compute` по всему штабу | 84.7 мс | ~0.34 с | ~0.85 с | ✅ под порогом |
| Свод: рендер 109 строк (**НИЖНЯЯ ГРАНИЦА**, `members=()`) | 235.7 мс | ~0.94 с | ~2.4 с | ⚠️ см. ниже |
| Свод целиком (compute+рендер, envelope) | ~0.32 с | ~1.3 с | ~3.2 с | ⚠️ см. ниже |

**Ключевой вывод — где на самом деле живёт async-триггер:** текущий синхронный путь
(лист-issuance) далёк от порога с любым разумным множителем железа. Риск концентрируется
НЕ здесь, а в БУДУЩЕМ **многострочном своде-документе** (зона 6.10): его dev-нижняя-граница
рендера (`members=()`) уже ~0.24 с на 109 строк, а с ФИО в ячейках и на слабом железе
(×10) она проецируется к порогу 2 с. Это **ровно** тот «тяжёлый рендер-путь 6.10»,
который уже назван в триггере `ARCH-DEFERRED-048` — замер его не опроверг, а
**подтвердил и оцифровал**. ⇒ 6.6 деферит AsyncJob; 6.10 при постройке многострочного
свода-с-ФИО ОБЯЗАН перемерить рендер и, вероятно, именно там триггер сработает.

**Async по умолчанию (`architecture.md:49/466/624`) для текущего пути — НЕ оправдан
числами.** Ветка AC-5: `ARCH-DEFERRED-048` + `deferred-work.md`, прод-код `apps/` не
тронут, семена async (`DOCUMENT_GENERATED`, §34.1-имя, `DOCUMENT_GENERATION_FAILED`)
остаются семенами, контракт состояний AsyncJob (§82.4) ре-деферится.

## 6. Находки спайка (находка → стори)

1. **PDF-генератор 6.4: envelope ≈ 3 членских колонки.** 17-колоночная вёрстка fpdf2
   нормализует ширины как доли; лист с именованными членами в **≥4** статус-колонках
   одновременно (напр. отпуск+больничный+командировка+прикомандирован, ФИО+звание в
   каждой) переполняет: `FPDFException: Not enough horizontal space to render a single
   character`. Замерено точно: 3 колонки со званием — OK (~25.9 КБ), 4-я — падение; без
   звания 4 колонки — OK. **docx (первичный официальный формат, 6.3) рендерит любую
   форму** — ограничение только у вторичной PDF-формы (FR-17). Ортогонально async-решению.
   → **находка → generator-hardening / пересмотр в 6.10** (адаптивная ширина/перенос
   членских колонок ИЛИ многостраничная развёртка членов). Замер 6.6 берёт форму, которую
   рендерят ВСЕ 4 генератора (3 членских колонки), чтобы мерить «из одного `ExpenseDocumentData`».
2. **Свод-документ — реальный async-кандидат, не лист-issuance.** Лист = 38.5 мс (×52 под
   порогом); многострочный свод-с-ФИО (6.10) — где p95 может подойти к 2с на слабом железе.
   → **вход в 6.10**: строить многострочный свод — перемерить рендер-с-ФИО; это точка
   срабатывания триггера `ARCH-DEFERRED-048`.

## 7. Гейт path A/B — вердикт

  реальном 4ГБ-контуре — заполнить последнюю строку §4. RUNBOOK-строчка: тот же

  golden-master 6.8 / перф-смоук E12. Если target-p95 свода-с-ФИО ≥ 2с — сработает
  триггер `ARCH-DEFERRED-048`, заводится наследник (AsyncJob).
- **Открыто (`PENDING-target`):** абсолютные p95 на слабом железе; стоимость свода-**с-ФИО**
  (не нижняя граница) — оба переходят в 6.10 / E12, «никакого тихого пропуска».
