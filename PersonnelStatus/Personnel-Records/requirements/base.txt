# 🔴 БОЕВОЙ ЗАПУСК ЗОВЁТ GUNICORN, А ОБЪЯВЛЕН ОН НЕ БЫЛ (Plane №830). Образ
# ставил зависимости и запускал бинарь, которого в них не значилось: находило
# это не сборкой, а первым запуском контейнера.
#
# Почему gunicorn остаётся, а не заменяется голым uvicorn: управление
# процессами (перезапуск воркеров, graceful-выход, единая точка сигналов)
# остаётся у него, а протокол даёт воркер uvicorn — `-k
# uvicorn.workers.UvicornWorker`.
#
# 🔴 МОДУЛЬ ЕСТЬ, НО UPSTREAM ОБЪЯВИЛ ЕГО УСТАРЕВШИМ — И ЭТО НЕ ОДНО И ТО ЖЕ
# (Plane №888, найдено ревью). Разбором колеса проверено: `uvicorn/workers.py`
# в закреплённой 0.52.4 присутствует, и пара совместима — `Arbiter` и
# `workers.base.Worker`, которые он импортирует, в `gunicorn==26.2.0` на месте.
# Но первым же оператором этот модуль печатает: «The `uvicorn.workers` module
# is deprecated. Please use `uvicorn-worker` package instead». Прежняя
# редакция комментария кончалась на «модуль ПРИСУТСТВУЕТ», и читатель выносил
# отсюда вывод «тревога была напрасной». Тревога была наполовину верной, и
# вопрос ОТКРЫТ.
#
# Чем это грозит: строка выше разрешает `uvicorn>=0.30`, то есть любую новее.
# В момент, когда модуль уберут, отказ будет ПРИ СТАРТЕ КОНТЕЙНЕРА, в бою.
# Гейт этого не поймает ничем: образ здесь не собирается, `uvicorn` в `.venv`
# не стоит, а сторожа команды запуска проверяют другое — что команда зовёт

#
# Что с этим делать — вопрос о составе боевой поставки, а не строка кода:
